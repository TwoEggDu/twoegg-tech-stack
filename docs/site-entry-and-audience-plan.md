# 站点定位与演进原则

> 更新：2026-10-14。依据作者本轮确认的职业经历与站点方向。本文是当前定位、内容组织原则和渐进调整顺序的唯一主维护位置；沿用原文件路径，替代此前以顾问合作与求职展示为中心的入口策略。

## 1. 当前定位

> 以游戏产品交付为主线，记录从引擎工具、内容生产到客户端与服务端协作，再到上线运行与持续迭代的工程实践与技术研究。

站点面向希望理解游戏研发全貌、解决具体交付问题或深入技术机制的读者。以内容和问题组织入口，暂时撤下求职、顾问合作等对外转化入口，不围绕招聘、咨询或投资对象安排公开内容。

这里的交付覆盖：玩法成立、内容可生产、系统协作正确、体验与性能达标、版本可发布、上线后可观测和维护，以及反馈进入下一轮改进。构建与发布是其中的重要环节。

## 2. 职业经历提供问题来源

作者此前主要从事游戏引擎与工具相关工作，目前工作重心是把策划、美术、客户端和服务端的产物组织成一个产品，并开始接触运营数据分析、服务器部署、服务器压力测试和服务端设计。

由此形成持续演进的叙事：

**引擎与工具建设 → 内容生产与跨工种协作 → 产品交付 → 上线运行、观测与持续改进。**

引擎工具是长期技术根基，需要继续补强；承担交付责任使研究范围向上下游延伸。具体案例中的项目身份、时间、个人职责、数据和结果仍须逐项核对。这段职业方向说明不代表已独立负责所有领域，也不为存量文章中的经历或数字背书。

“实践与演进”记录问题视角怎样变化、做法怎样被修正和复用；技术系列沉淀可以反复查阅的机制。个人经历提供背景，正文落在读者能够理解和检验的问题、约束、取舍与结果上。

## 4. 全局视野与技术深度

| 层次 | 要回答的问题 | 研究范围 |
| --- | --- | --- |
| 游戏研发与交付 | 为什么做、怎样做成、如何持续运行？ | 立项、玩法验证、协作、研发、测试、发布、运营、商业化与退役 |
| 游戏系统 | 产品需要哪些能力，它们怎样配合？ | 战斗、技能、世界、UI、存档、多人同步与内容生产 |
| 引擎与技术机制 | 这些能力如何实现，代价和边界是什么？ | 引擎架构、Unity、Unreal、渲染管线、动画、物理、资产与工具链 |
| 计算基础 | 实现的成本和限制从何而来？ | C# / C++、运行时、内存、并发、操作系统、网络与 CPU / GPU |

Unity、Unreal 是游戏研发体系中的具体实现路径。先说明通用问题和模型，再进入引擎差异；C# 运行时按相关实现路径展开，Unreal 的 C++、对象系统与内存管理沿自己的路径研究。不将某个引擎或语言当作所有读者的必经入口。

读者可从正在面对的问题下钻，也可直接深入基础专题。四层是关联视角，不是从操作系统到玩法的统一硬前置顺序。独立的渲染、运行时和算法研究可以按自身问题展开，并说明它与产品约束的关系。

全生命周期地图保持完整视野；近期内容投入聚焦“内容生产—研发协作—版本交付—线上反馈”。市场、商业化和退役等领域先保留必要上下文与研究入口，随真实证据逐步扩展。地图覆盖范围不代表作者经验或正文深度已覆盖全部领域。

AI / Agent / Harness 继续由原系列维护，可通过内容检查、构建诊断、工具执行和验证等问题接入主线；课程和实验状态按各自证据表达。

## 6. 选题与证据原则

选题进入写作前，先明确：解决哪个问题、服务哪个环节、已有文章能否复用、由哪份系列规划维护、需要什么证据。引擎与工具主题持续投入，新领域优先写清实际接触的边界和未知项。

案例围绕背景、职责、输入与产物、约束、候选方案、取舍、验证结果及后续反馈展开。跨工种问题进一步交代契约、变更通知、失败退回和联合验收责任；技术专题遵循现有[文章方法](article-writing-method.md)与[系列规划方法](series-planning-method.md)。

- 内容成熟度分别标明：仅规划、正文草稿、已有正文、待核对或待更新。
- 证据分别表达：官方资料、源码核对、实验观察、工程建议与待验证假设。正文存在不代表结论已验证。
- 构建通过、隔离测试、压测容量、真机体验和线上效果分别记录适用环境与范围；不能用一个环节的结果替代其他验收。
- 新接触领域按正在实践或研究的状态呈现；性能数字、玩家指标、故障影响和个人贡献需要真实依据。
- 公开仓库中的 docs 和 content 都遵守许可及脱敏边界。撤下导航不会使原有页面或仓库文件变为私密。
- 公开知识继续在本仓维护；固定 ET 工程与原始验证记录在 ET-Learning-Lab 维护。ET9 历史文章与 ET10 固定研究仍按各自版本处理。

### P1：对应文章、经历和证据

先把现有内容组织成清楚的阅读路径，沿第 5 节的三个贯穿问题逐环节盘点：

1. **一项玩法怎样成为可交付的版本？** 玩法目标 → 策划配置与美术内容 → 客户端和服务端实现 → 联调 → 功能、性能与体验验收 → 发布反馈。
2. **一份资源怎样到达玩家设备？** 创作规格 → 导入与序列化 → 依赖和校验 → 构建与分包 → 下载、缓存和加载 → 内存与渲染成本。
3. **一个线上问题怎样推动产品改进？** 玩家反馈与运营数据 → 复现和观测 → 定位 → 修复 → 回归 → 放量 → 效果复核。

**交付物**：形成“三条阅读路径 × 现有文章 × 实际经历 × 证据缺口”的对应表。每项至少记录所属路径与环节、核心问题、真实文章入口、内容状态与覆盖判断、相关经历及个人职责、可公开证据与未知项、唯一主规划、处理决定与优先级。

处理决定区分直接复用、补衔接、旧文修订与真实缺口。已有覆盖审查可作为起点，文章存在性、状态和证据仍按实际文件核对；有标题不等于有正文，正文完整不等于案例已验证。

**完成标准**：三条路径的各环节都有可用入口或明确缺口；每个缺口有唯一主归属，候选回写原系列规划；案例明确个人职责、证据和未知项。对应表只串联阅读与证据，不成为第二份权威篇级目录。盘点结果应能支持首页推荐、补桥顺序和首批案例的选择。

**本轮结果**：[P1 对应表](game-delivery-reading-paths-audit.md)已按三条路径登记文章、经历线索与未核实项；增量提纲回写交付、服务端及实践演进原规划。资源机制与技能协作优先复用，产品研究和数据实验沿用既有候选。案例补证据、旧文修订与入口调整分别留在后续阶段。

### P2：调整网站入口

首页采用作者选定的 A「清爽阅读」方案：少量文章选读作为主栏，按技术领域进入的目录与简短作者介绍作为侧栏。交付主线通过选文及研发地图呈现，完整阶段与技术体系在研发总览展开；首页不再堆叠三条路径卡片、栏目数量和课程大横幅。保留阶段阅读、工程案例与站内搜索入口。技术目录进入全站主导航：首页与目录共用领域分组，读者可直接找到 Unity、Unreal、URP、各运行时和计算基础；首页搜索放在介绍之后。

核对并撤下主导航中的求职入口、首页作品集导流中的求职导向，以及相关顾问合作文案。逐项处理旧入口引用和页面定位，保留原文章地址；撤下入口与删除内容分别处理。

Agent 课程继续保留，通过工具执行、构建诊断和验证等问题接入整站。“实践与演进”说明工作怎样从引擎工具扩展到完整交付，具体经历和结果按 P1 的证据补入。

**交付物**：调整后的首页、导航、研发总览与相关入口页面，以及必要的定位文案同步。

**完成标准**：读者能从首页进入上述四类内容；原文章地址有效，新增入口与链接可用；阶段导航与技术导航职责清楚；Hugo 构建及移动端阅读检查通过。页面调整依赖 P1 的代表内容与证据选择。

**本轮结果**：[研发总览](../content/game-development.md)提供阶段、路径和技术阅读；首页已按作者选定的 A 版接入 Hugo，选文与摘要由 `content/_index.md` 维护，领域分组及系列入口由 `content/technical-topics.md` 维护，原文章标题及地址不变。career 保留旧书签提示，portfolio 改为案例阅读入口。关于及实践页面使用已确认的职业方向。Hugo、生成站链接、桌面与手机宽度检查见 [P2 记录](site-p2-entry-adjustment-report.md)；作者已授权提交推送 P2，Pages 部署尚未核验。

### P4：扩展上线运行与数据反馈

从作者正在接触的实际问题开始，优先收集材料，再判断适合形成案例、实验记录还是研究提纲。例如：

- 服务端一次发布需要哪些验收，客户端、配置与服务端版本怎样配合？
- 压测怎样建立接近业务的负载，怎样判断容量边界？
- 怎样区分程序瓶颈与环境限制，并验证改动效果？
- 运营指标异常怎样追到事件和数据链路，再反馈到产品与研发？

这些是问题方向，不预设作者已有完整实践或确定结论。具体选题复用服务端、性能、质量和长线运营等现有规划。

**交付物**：依据实际材料逐步形成服务端设计、部署、压测和运营分析内容，并与前面的交付路径相连。

**完成标准**：每篇明确适用环境、个人职责、验证范围和结论边界，说明结果怎样进入下一轮研发改进；证据不足处保留未知项。实验记录与生产效果分别表达。

### 每批调整的共同检查

每批工作都检查：入口是否清楚、技术深度是否保留、结论是否有依据、系列是否仍只有一个主规划。涉及页面时，补充旧地址与新增链接、Hugo 构建和移动端阅读检查；检查结果按实际执行情况记录。
