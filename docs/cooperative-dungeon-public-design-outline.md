# 无尽对决公开设计：共同模型、Unity 落地与其他引擎方案讨论

项目名称：无尽对决；当前范围：教学优先的最小两人合作流程。

日期：2026-10-25（Asia/Shanghai）
状态：公开设计初稿，尚未发布；本文的设计与验证目标不表示 Demo 已完成。
读者：希望沿同一款游戏理解玩法、架构、内容制作、引擎实现、交付与运营的开发者。

## 1. 我们准备公开什么

我们围绕最小双人清怪流程公开设计与教学，说明各功能解决什么学习问题、各工种怎样制作，以及怎样验证结论。上线运营设想放到远期，不是当前完成条件。读者可以看到问题、规则、系统职责、交接约定、方案取舍和验收方法；随着工程推进，再补充允许公开的实际结果与验证边界。

Demo 工程保持私有。公开设计的完整程度，不以公开完整源码、制作资产或可运行包为前提。文档应能独立说明设计，不要求读者取得私有工程才能理解核心规则和判断依据。

| 内容 | 本项目的公开边界 |
| --- | --- |
| 玩法与系统设计 | 公开体验目标、规则、职责、数据含义、状态与时序、失败处理和取舍 |
| 制作与交付设计 | 公开策划、美术、程序和测试的工作流程、交付约定、检查与验收方法 |
| 引擎实现说明 | 公开实现方案、对象与模块的职责、工具流程和经过核对的机制解释 |
| 教学示例 | 可以编写独立伪代码、示意数据与最小例子；明确它们不是私有工程的源码或完整实现 |
| 实验与结果 | 公开允许公开的证据摘要，注明版本、环境、实际执行范围；实验未做时只写计划 |
| 私有 Demo | 完整客户端／服务端工程、项目资产、正式配置和运行制品保持私有，不因撰写实现文章自动公开 |

运行证据公开到什么粒度，后续随案例选择；不默认公开账号、玩家数据、内部部署信息或完整原始日志。公开文章只使用允许公开的材料，引用来源与设计推导分开标明。

## 2. 一份共同设计，Unity 实际落地

“引擎无关、Unity、Unreal、Piccolo”是文档的组织层次。引擎无关部分定义规则与职责，Unity 承担实际开发和运行验证，Unreal、Piccolo 仅讨论对应落地方案与机制差异。后两部分不属于项目实施计划，也不要求建立对应游戏工程。

| 部分 | 要回答的问题 | 设计边界与当前推进顺序 |
| --- | --- | --- |
| 引擎无关设计 | 游戏要实现什么，各系统如何协作，内容如何制作，怎样判断正确？ | 共同设计先形成，以规则和验收条件为依据，不要求读者掌握某个引擎 |
| Unity 实现 | 怎样用选定的 Unity 技术栈实现共同设计？ | 实际落地，先跑通 Editor 单项制作与最小双人流程；平台、更新和运营按需专项 |
| Unreal 方案讨论 | 相同问题在 Unreal 中怎样组织，有哪些不同取舍？ | 仅讨论关键系统与内容流程的方案，不安排项目开发或运行验收 |
| Piccolo 方案讨论 | 相同问题在固定版本的 Piccolo 中怎样落地，缺少哪些能力？ | 仅讨论已有机制、能力缺口与可能方案；不安排项目开发或运行验收 |

当前确定：项目采用 Unity 实际落地，T01～T18 的实施与验收由 Unity 路线承担。Unreal 和 Piccolo 只作知识讨论，围绕相同案例解释其他引擎可能怎样实现，不承诺后续移植或开发。

共同设计不等于一套跨引擎代码库。规则含义、输入输出和验收场景可以共用，语言、文件格式、对象模型、调度、网络、工具和构建方式可以分别设计。引擎特有能力可以形成扩展，但应说明它对共同目标的影响。

## 3. 引擎无关部分的设计范围

### 3.1 产品与玩法

用简单配合连接框架与内容制作：一张斜俯视小场地、两名角色、一种普通怪、一种测试奖励；移动、普攻与各一个主动技能。A 施加标记，B 消耗有效标记产生额外伤害。

当前共同流程为：进入 → 清怪 → 简单结算 → 返回 → 重开。清空本局怪物获胜，两人全部倒下失败。测试身份、简化入口与内存奖励即可承载首轮教学，不要求真实账号、完整匹配或持久化。

已确定斜俯视和简单操作、标记／消耗配合。暂不加入复杂 Boss、机关、职业、装备、成长、闪避、救援／复活。目标选择、标记与消费边界、冷却、奖励与胜负优先级仍待细化。逐项功能与教学目标见[总览的 T01～T18 表](cooperative-dungeon-engine-independent-overview.md#3-功能教学目标与验证内容)，实施与实际验证分别记录。

### 3.2 领域模型与规则

先解释玩家、队伍、副本实例、角色、技能、效果、怪物、关卡目标、奖励与存档的含义，再定义它们的标识、状态、输入输出、生命周期和相互约束。

例如，一次技能请求需要说明谁发起、如何选择目标、何时校验、何时消耗、何时生效、如何打断，以及结束后怎样清理。是否用状态机、数据驱动或某种设计模式，是在变化需求与失败场景明确后比较的实现选择。

### 3.3 两端职责与版本关系

设计操作意图、权威判定、状态同步、表现反馈、重复请求、超时、断线和恢复。联机战斗与奖励由服务端最终判定，是当前建议的初始边界，随详细玩法核实。

配置、协议、代码、资源和服务端的版本关系也属于共同设计。客户端看到什么、服务端认可什么、哪些变更能兼容、何时必须升级或停止进入副本，都需要明确规则。

### 3.4 资源、表现与交互

共同部分定义逻辑内容标识、加载与释放责任、异步取消、场景交接、模型和动作语义、特效触发与结束、界面状态和用户操作。

这里可以要求“施法取消后，相关表现按约定结束”，不把 Prefab、UGUI 或某种动画系统写成共同设计的前提。Unity 实现再决定通过哪些引擎对象表达这些职责，其他引擎部分讨论可能的映射。

### 3.5 内容生产、测试与交付

策划应能在已提供的能力内独立配置技能、怪物、关卡与奖励；美术应能在约定兼容范围内独立替换模型、动画、特效与 UI。两类修改都应能通过检查、预览和运行验证看到结果。

共同要求是“源内容 → 检查 → 生成或导入 → 采用一致版本 → 预览 → 集成验收”。Unity 首阶段在 Editor 完成；其他引擎部分仅讨论可能的操作入口及差异，不承担制作工具的实施与验收。

验证方法覆盖单项、完整流程、双客户端、版本迭代和平台运行。更新、平台、持久化、性能与运营选择独立专项，复用同一小流程；每项先确定教学问题与验证内容，不作为最小版前置条件。

## 4. Unity 实现路线

Unity 路线沿用已经确定的方向：Unity、UGUI、ET、Luban、YooAsset 与 HybridCLR。先完成单项内容制作与 Editor 预览，再跑通最小双人清怪循环。资源与代码更新、持久化、多平台和运营按教学问题单独实验，不要求先用齐全部技术组件。

| 共同设计问题 | Unity 路线要写清的实现内容 |
| --- | --- |
| 游戏流程与状态所有权 | 客户端和服务端的模块组织、ET 机制与业务边界、流程切换及异常处理 |
| 技能与内容定义 | Luban 数据定义、引用与业务校验、两端消费、生成失败和数据采用 |
| 资源与表现 | YooAsset 加载地址、句柄与所有权、场景交接、模型／动画／特效映射和释放 |
| UI 与交互 | UGUI 视图、业务与绑定边界，兼容外观替换、异步作用域及界面状态预览 |
| 策划与美术工具 | 配置检查、资源检查、指定内容预览、版本显示、失败定位和测试环境重置 |
| 代码与版本更新 | AOT 与热更代码边界、HybridCLR 相关加载与兼容，以及资源、配置、服务端的配套 |
| 平台与运行成本 | Windows、Android、iOS 和具体小游戏平台分别设计、构建、运行和测量 |

组件版本、数据格式、编辑器入口及平台组合仍需锁定与验证。Editor 成功不能代替 Player／真机结果；使用某组件也不能直接推定所有目标平台具备相同能力。

## 5. Unreal 落地方案讨论

Unreal 部分沿 Unity 的实际案例讨论关键系统与内容制作流程可能怎样组织。需要引用引擎机制时，按明确版本核对来源；这里只形成方案分析，不安排本项目的 Unreal 工程开发。

需要逐项回答：

1. 共同领域对象如何映射到本路线的对象与模块，各自由谁创建、更新和清理？
2. 技能、怪物、关卡与奖励如何表达，策划怎样编辑、检查和预览？
3. 模型、动画、特效和 UI 如何交付、替换与验证？
4. 双端规则、输入、同步和恢复由什么机制承接，怎样验证相同业务结果？
5. 资源加载、版本交付、运行成本和工具流程与 Unity 有何不同？

每次只讨论一个关键问题，说明共同输入、预期、异常路径和候选取舍。设计推导、机制事实与待验证假设分别标注，不将讨论写成已实现结论，也不要求照搬 Unity 技术栈。

## 6. Piccolo 落地方案讨论

Piccolo 部分围绕相同案例讨论关键系统与内容流程，先建立能力清单，避免把拟议扩展写成现有引擎功能；当前不安排对应项目实现。

每项研究记录四类内容：

- 固定版本中已有的机制及证据。
- 为完成该案例需要增加的项目能力或引擎扩展。
- 各候选方案的职责、边界与取舍。
- 尚待验证的假设及可采用的验证方法；不要求执行实验。

候选问题包括逻辑对象到场景表现的连接、配置与资源的装载、生命周期、编辑预览与内容保存，以及简单技能或怪物的规则与表现协作。候选不表示已经具备对应能力，也不预先决定其实现方式。

本路线不将完整联机、热更新、移动端或小游戏支持列为已知能力。讨论这些能力时，分别列出依据、缺口和待验证问题。

## 7. 端服关系与跨引擎复用

共同设计把游戏规则、服务端权威、协议语义与引擎客户端分开说明。ET 是 Unity 主实现中已经选定的框架方向，不因此成为所有引擎路线的强制客户端依赖。

本项目只落实 Unity 客户端与服务端的连接。Unreal 和 Piccolo 是否能接入相同协议与服务端，可作为方案讨论题；当前不建设对应客户端或通信验证工程。

跨引擎首先复用的是规则说明、测试场景、语义数据定义和验收方法。共享服务端、配置源文件、生成工具、协议制品或逻辑代码，需要分别评估并验证。不假定不同语言或引擎对象能够直接共享同一实现，也不默认混合引擎客户端能够同场游玩。

## 8. 同一个案例怎样横向写作

建议从“策划新增一项技能，美术替换它的表现”开始。这同时覆盖独立制作、规则与表现分工、工具、资源和生命周期，并能继续延伸到联机与发布。

| 内容 | 本案例需要交代的事情 |
| --- | --- |
| 引擎无关设计 | 技能输入、目标、消耗、生效、打断、表现与清理；策划和美术的修改边界；通过条件 |
| Unity 实现 | 在既定技术栈中完成数据定义、资源映射、Editor 预览和运行验证，记录实际结果 |
| Unreal 方案讨论 | 选择相同规则与观察点，说明本路线的数据、对象、制作入口与表现机制 |
| Piccolo 方案讨论 | 列出已有机制与缺口，讨论规则和表现的可能组织，标注待验证假设 |

共同的语义示例可以先使用“技能标识、目标规则、冷却、效果、表现标识”这些概念，实际字段和数值后续设计。增加新行为由程序扩展；策划在已提供的行为内配置。表现替换须满足挂点、时序、绑定与生命周期约定。

方案对照应保持规则目标、输入和失败场景一致，并区分 Unity 的实际结果与其他引擎的设计推导。性能比较还需要可比的负载、环境和测量方法；一个最小实验不能与完整运营项目直接作性能优劣结论。

### 9.1 设计模式教学贯穿四部分

设计模式教学是本项目明确的产出要求，贯穿引擎无关设计、Unity 实现及 Unreal、Piccolo 方案讨论。公开设计要让读者沿实际需求学会识别变化、比较方案、划分职责、判断成本，并验证选择；每个对象使用了什么模式，只是分析的一部分。

教学沿用[设计模式唯一主规划](game-programming-patterns-plan.md)的教科书线与应用线：[教科书入口](../content/system-design/design-patterns-textbook-series-index.md)解释概念与最小例子，合作副本承载应用案例；Unity／ET 应用案例继续补充职责、所有权、异步与框架边界。本文只登记项目案例和教学要求，不另建模式篇目表，也不要求读者先读完整套教材再开始项目。

| 设计部分 | 教学要完成的事情 | 应形成的公开材料 |
| --- | --- | --- |
| 引擎无关设计 | 从需求和变化出发，比较直接写法、数据配置、函数拆分与候选模式，明确状态所有者和不变量 | 场景、职责与依赖关系、候选方案、取舍、最小教学例子及验收条件 |
| Unity 实现 | 结合 ET 与 Unity 的实际组织、UGUI 和资源生命周期，落实或拒绝某项候选设计 | 设计映射、实现理由、独立示例、允许公开的验证摘要 |
| Unreal 方案讨论 | 对照相同问题，研究其对象与模块组织怎样影响方案选择 | 语义与生命周期对照、方案差异、机制依据与待验证项 |
| Piccolo 方案讨论 | 区分已有机制与拟扩展能力，讨论案例中的职责和所有权 | 能力与缺口、候选设计、机制依据与待验证项 |

独立教学示例可公开，使用伪代码、纯 C# 或按需补充的最小 C++ 例子。示例另行编写，不抽取私有 Demo 的完整源码；语言语法、业务规则和引擎机制分别解释。Unity 实现与其他引擎方案讨论可以选择不同组织方式，包括保留直接实现，不要求相同类结构或相同模式覆盖率。

### 9.2 从项目变化选择教学案例

以下是待设计和待验证的候选，不表示正式实现已采用这些模式。每行先研究问题与直接方案，再决定是否引入相应抽象。

| 需求变化或失败 | 候选设计与比较重点 | 学习与验证重点 |
| --- | --- | --- |
| 技能从一种目标规则增加到两种，策划需要组合已有能力 | 条件分支、配置参数、函数组合与 Strategy | 能否识别独立变化；新增规则影响哪些位置；旧规则与两端结果是否保持正确 |
| 怪物或副本增加阶段、打断与恢复 | 显式分支、转换表、State 对象与 FSM | 非法转换、重入、退出清理、延迟回调和状态所有者；不把所有状态机都判定为 GoF State |
| 一次击杀需要更新 HUD、任务提示与表现 | 直接调用、Observer／事件通知 | 同步还是异步、先后顺序、订阅作用域、重复通知与退出后残留；本地通知与网络消息分开 |
| 玩家操作需要记录、排队或测试重放 | 直接调用与 Command | 操作意图、接收者、传输与执行边界；幂等、撤销和确定性重放分别设计与验证 |
| 多类怪物或表现对象的创建与依赖开始变化 | 直接创建、集中创建入口、Factory Method／Abstract Factory 候选 | 简单工厂函数与 GoF 创建模式的区别、所有权、初始化失败及清理 |
| 美术更换 UI 外观，策划调整展示数据 | 视图与业务职责拆分、MVP 等 UI 组织方案 | 兼容替换的改动范围、绑定与交互约定、视图关闭后的异步结果处理 |
| 资源或平台接口变化，调用点分散 | 直接调用、Adapter、Facade | 隔离哪种变化、入口是否丢失取消／错误／释放信息，以及额外维护成本 |
| 配置、美术检查与构建增加不同步骤 | 顺序函数、Pipeline、Template Method 候选 | 固定流程骨架是否确实存在，步骤能否变化，错误如何回到源内容；不按“流程”名称判断模式 |
| 怪物、特效和飘字频繁创建，怀疑有分配成本 | 直接创建销毁与对象池 | 重置、取消、回收和旧引用失效；在可比负载下测量收益与成本 |

分类沿用既有主规划：设计原则与代码组织、GoF 等对象协作模式、游戏架构／性能／执行模型分别说明。SOLID、DI、对象池、ECS、Actor、Fiber、async/await、MVP 和 Pipeline 不因纳入教学就统称 GoF 模式。组合原则也不等于 Composite。

### 9.3 每个案例的教学过程与验收

每个应用案例保留同一条推理线：

1. 描述玩家、策划或美术提出的具体需求，以及当前规模下可理解的直接方案。
2. 引入一个变化或失败，定位职责、依赖、状态与生命周期中出现的困难。
3. 比较少量真实可选方案，说明各自隔离的变化、保留的问题和增加的成本。
4. 给出当前选择与拒绝其他方案的理由；只有存在相应压力时才引入模式。
5. 在 Unity 中落实约定并设计正常、失败和清理的验证；其他引擎部分核对机制、讨论映射与待验证假设。
6. 记录实际结果，再给出不适用场景及一次新的变化，检验读者能否迁移判断。

每个案例至少应有一组直接方案与候选方案的对比、一份职责／状态关系说明、一项变化练习和一组预期结果。需要执行才能支持的结论，在实验完成前标记待验证；不编造历史故障或改造收益。

掌握标准是：读者能解释变化由谁负责、状态由谁持有、为什么选择或不用某模式、怎样发现失败，以及新增需求后哪些内容需要改变。用接口或类数量、模式名称数量评价设计不构成验收。

公开的最小示例和练习应能独立理解，并给出预期或讲解；若提供运行方式，应记录示例自身的验证状态。它们的通过结果与私有游戏验收分开，读者无需取得 Demo 即可学习和比较方案。正式游戏只维护选定实现，直接方案和对照方案可留在独立教学材料或实验中。

### 9.4 首个案例：技能目标规则的演进

建议沿既有最小技能案例开始：先提供单一目标规则，再提出第二种目标规则。具体规则随玩法确定，先不承诺自动选敌、范围攻击或其他尚未确定的能力。

引擎无关部分先判断变化只是数据不同，还是选择算法与约束不同，再比较配置参数、分支、函数与 Strategy。Unity 路线在选定能力内连接策划配置、服务端校验、表现预览和回归；Unreal 与 Piccolo 仅讨论目标选择与生命周期的对应方案，不为此安排工程实现或联机实验。

练习让读者面对第三种规则，指出应改哪些配置或实现、谁负责修改，并列出既有技能和异常输入的回归条件。是否引入策略接口及其具体形态仍由设计决定，不因为教学需要提前定型。

后续按阶段扩展：最小制作阶段优先研究技能变化、UI／表现替换与创建清理；最小双人阶段加入局状态、事件／消息、操作和异步作用域；更新与平台专项再按问题研究适配和生产流程。具体阶段衔接见[项目规划的设计模式安排](cooperative-dungeon-project-outline.md#design-patterns-application)。

## 10. 公开设计的写作结构与状态

建议按以下主题展开；这是跨系列的主题结构，尚未建立新的篇级编号或系列目录：

1. 项目总览、公开边界与阅读方式。
2. 合作体验、玩家流程与详细规则。
3. 领域模型、两端职责与状态转换。
4. 技能、效果、怪物、关卡与奖励。
5. 配置、内容标识与版本关系。
6. 美术、动画、特效、UI 与资源生命周期。
7. 各工种制作、预览与质量检查。
8. 联机、数据、异常恢复与验收场景。
9. 构建、多平台、性能、更新与运营准备。
10. 各主题的 Unity 实现，以及 Unreal、Piccolo 对应方案的知识讨论。

设计模式教学按第 9.1～9.4 节贯穿这些主题：每个相关设计附上需求变化、方案比较与练习，并回链既有教科书和应用线。它不构成四部分之外的第五条引擎路线。

共同设计先明确一个小范围，再展开 Unity 实现；实现发现问题后，回到共同设计记录修订理由。Unreal、Piccolo 讨论按教学需要选题，不要求跟随每个主题完成，也不生成项目实施里程碑。

每个主题写清：要解决的问题、已确定要求、候选方案、选择理由、对外约定、正常和失败流程、验收条件、开放问题，以及实现与证据链接。Unity 记录设计中、待实现、待验证或已验证；Unreal、Piccolo 记录讨论状态、机制依据与待验证假设。

公开验证摘要至少包含版本、环境、操作、预期、观测方法、实际结果和限制。读者没有私有工程时，仍应能判断结论由什么证据支撑；缺少可公开证据时明确限制，不要求读者以信任代替证据。

## 11. 与现有规划的衔接及下一步

现有[项目整体规划](cooperative-dungeon-project-outline.md)保留项目阶段、工种管线、具体验收任务和设计模式案例；本总纲增加公开边界与共同设计、Unity 实现与其他引擎方案讨论。原规划中的既定技术栈与 Editor 操作主要属于 Unity 主实现，不能直接泛化到其他引擎。

[全栈学习提纲](fullstack-framework-learning-outline.md)继续组织学习目标；各系列原有目录继续维护篇目和状态。本站的 [Unity](../content/reading/unity-engine.md)、[Unreal](../content/reading/unreal-engine.md)、[Piccolo](../content/reading/piccolo-engine.md) 入口提供机制学习路径，不代表对应游戏实现已经存在。

共同设计采用已确定的最小清怪循环与标记／消耗案例；先形成规则边界、领域／状态和 Unity 单项制作验证设计，再接双客户端。Unreal 与 Piccolo 在共同案例稳定后按需选择关键问题作方案讨论，不安排对应项目开发。

下一轮固定标记、消费、冷却、目标选择、奖励和胜负优先级，选择输入映射、测试进入方式与工程基线。具体小游戏平台随 Unity 专项确定；Unreal／Piccolo 讨论题按教学需要选择。本文未实施游戏或运行实验。
