# 性能优化专栏：专家方向的内容与证据标准

> 版本：2026-11-04。适用范围仅为“游戏客户端性能工程”及其复用的性能内容。本文是本专栏的质量与验收约定，不是网易内部 P5 任职标准，也不接管各系列的篇级目录。唯一归属见[主规划](client-performance-engineering-series-plan.md)，推进见[执行计划](client-performance-budget-tiering-monitoring-execution-plan.md)。

## 1. 我们要展示什么能力

读者应能沿文章重建作者的判断：**明确体验与约束 → 解释成本来源 → 获得可信观测 → 排除候选原因 → 比较方案及代价 → 验证收益与正确性 → 把有效做法变成可维护的规则。**

专栏深度体现在问题建模、证据质量、技术取舍与落地能力。高级 API、术语数量、篇幅或工具规模本身不构成专家水平的证明。基础讲解仍须让读者逐步理解；不要求每篇贯穿全部底层，也不把缺少真实项目数据变成基础文章不能成稿的理由。

本轮已核验的网易公开岗位可作为方向参考：[互娱引擎技术专家](https://hr.163.com/job-detail.html?id=75977)强调核心架构、复杂 CPU/GPU 性能问题、profiling 与监控体系及技术指导；[雷火引擎负责人](https://hr.163.com/job-detail.html?id=79522)强调性能分析、监控、回归与跨工种管线。两者均未标 P5；它们的具体技术栈、年限或管理职责不作为每篇性能文章的统一要求。以下标准是我们对本专栏的编辑与工程约定。

## 2. 八项可检查的标准

编号只用于审查定位，不是篇号或评分。每项按本篇职责判断“满足／局部满足／待补／不适用”，附正文或证据位置；不适用须说明理由。

| 条款 | 要求 | 怎样确认做到 | 未达到的典型表现 |
| --- | --- | --- | --- |
| S1 问题与适用条件 | 说明用户感受到什么、发生在哪个任务阶段，以及约束什么决定 | 能指出对象、任务、设备／配置条件、目标、影响及本篇范围；原则文章也能给出适用情形 | 只有“优化性能”，没有负载、阶段和判断目标 |
| S2 成本与因果模型 | 从内容和执行机制解释观测，区分工作量、资源规模、执行、等待和关键路径 | 有足够的依赖、时间线或成本关系推导，并能解释一个容易误判的反例；明确模型失效条件 | 把 DrawCall、粒子数或文件大小直接当耗时；把 CPU/GPU 时间相加；单体结果线性外推组合 |
| S3 测量定义与可信度 | 每个关键指标能追到测量对象、方法和有效性条件 | 定义对象、单位、起止点／计数范围、时钟／帧关联、来源、窗口、聚合、缺失状态、干扰和校准办法 | 只写“帧时间／内存”；Editor 数字直接用于真机预算；不支持时记为 0；工具开销未知 |
| S4 证据与因果验证 | 把现象、假设、证据、推断分开，允许结果推翻原假设 | 诊断列候选解释及区分办法；收益结论有同条件对照、重复和必要的恢复／交叉核验；保留失败与波动 | 凭一张 Profiler 截图认定根因；一次变快就宣称有效；把冷缓存 A 与热缓存 B 比较 |
| S5 方案取舍与收益边界 | 说明为什么选择此方案、付出什么，以及何时不值得做 | 比较相关备选方案及保持现状的成本；核对画质、玩法正确性、内存、加载、能耗和维护负担中受影响的部分 | 只报 FPS 提升；预加载改善首用却不记启动／驻留代价；不讨论降画质的信息损失 |
| S6 预算与设备校准 | 从体验和代表负载推导阈值，区分设备能力、画质配置和运行时状态 | 给出目标→基线→候选分配／余量→组合复测→规则修订的依据；验证代表与边界设备、未知设备和必要体验 | 凭经验给通用粒子上限；型号表当测量；分进 High 就视为 High 配置通过；硬兼容失败降档了事 |
| S7 工具与系统设计 | 每个模块对应明确测量需求；准确性、可复现性和演进边界可检验 | 说明公共能力／领域适配、身份与数据版本、原始记录、失败／不支持／超时、扰动与校准；第二领域接入能检验抽象 | 能读出数字就算正确；只画架构图；报告无法回到原始帧；五类对象强行共用同一采集逻辑 |
| S8 生产使用与持续治理 | 说明规则由谁使用、处理和维护，效果怎样持续确认 | 对应制作／导入／运行／回归入口、基线、负责人、异常复验、例外到期、回滚与规则退出；采用效果有实际记录 | CI 绿色当设备达标；脚本提交当团队采用；告警没有处理动作；阈值永不复核 |

关键结论依赖的条款不能用其他项的亮点抵消。存在单位／归因错误、虚构实测、超出证据范围的通用结论时，应修正或收窄结论后再作为推荐正文。必要机制解释、可读性和来源准确性对所有正文都适用。

## 3. 根据文章职责验收

| 类型 | 应交付的核心结果 | 证据要求与允许的边界 |
| --- | --- | --- |
| 原理／基础篇 | 读者能够解释机制、判断适用条件和反例，并知道如何验证 | 严密推导、版本明确的可靠资料或公开实现可以支持机制；教学算例标明身份。不强制每篇附设备实验 |
| 测量方法篇 | 读者能定义观测并识别错误数据 | 指标规格、来源和局限、校准设计及误判样例；没有执行校准时只能称方法／设计，不能称工具已准确 |
| 预算／分档篇 | 读者能从项目条件推导、校准并维护规则 | 方法可先用教学条件演示；声称某组实际阈值或机型方案适用时，必须提供匹配负载和边界的验证 |
| 优化案例篇 | 读者能复核根因、方案、收益和副作用 | 环境与输入身份、原始数据、分析过程、对照与重复、正确性及结论范围；教学案例不能冒充作者项目经历 |
| 工具／体系设计篇 | 读者能评审职责、接口、失败处理和演进取舍 | 设计稿说明未执行项；声称已实现须有实现证据，声称可用须有运行与校准证据，声称团队有效须有采用结果 |
| 首页／索引 | 读者知道从哪里进入、已有与待补各是什么 | 链接、推荐理由、阅读依赖和状态准确；不要求索引自身包含全部实验与模型 |

每篇围绕一个主要读者问题，先解释必要概念，再落引擎和工具；术语第一次出现时说明它帮助判断什么。图和表必须服务因果或比较，不靠堆图制造复杂感。审稿时应能用自己的话复述模型，并回答一个变更条件的问题。

## 4. 性能数字怎样才有资格支持结论

涉及自己的设备结果、实际预算或优化收益时，记录以下信息；引用他人数据则保留原来源、环境和适用范围，不能写成自己的实测。

- **输入与环境**：构建／内容版本、引擎与管线、平台／驱动、设备、分辨率与画质、帧率目标、路线或镜头、并发内容，以及缓存、生命周期、温度／供电等对结论有影响的状态。
- **测量规格**：指标定义、采集范围、工具版本、事件／帧身份、窗口与汇总方法；CPU／GPU／呈现的时钟和异步结果如何关联，不假设时间戳天然可减。
- **数据有效性**：预热与正式窗口分开；保留缺失、不支持、超时、丢样和异常退出。失败不能从报告中静默消失，缺失不能按通过或零成本处理。
- **对照与重复**：尽量保持条件可比，记录改变的变量；必要时采用交错顺序或恢复测试，识别热状态、缓存及背景变化。重复次数依据波动和要作出的决定确定，不规定一个适用于所有实验的次数。
- **统计解释**：说明帧样本和独立运行次数的区别，记录运行间波动；存在时序相关的帧不能简单视为大量独立重复。分位数写明算法和样本，不用平均值掩盖首放事件；相对收益同时给绝对量和基线。
- **接受条件**：事先说明要改善什么、可接受的波动与副作用。收益是否足以影响预算或体验，比只有统计显著性更接近工程决定；超出测试覆盖的设备和场景仍保持未知。

证据按主张分别标注：资料／公开实现、教学推演、受控实验、项目运行、团队采用。它们回答不同问题，不是可相互替代的荣誉等级。把采样结果归给单对象、把若干阶段加成总耗时、把单机结果推广到档位，都需要单独论证归属和边界。

## 5. 整套专栏需要形成的作品

以下是覆盖要求，不是新增篇数。优先从已有正文、样表与实验中复用，并随现有 A–F 批次完成。

| 作品 | 必须能够展示的判断 | 完成证据 |
| --- | --- | --- |
| 共同度量与成本模型 | 帧／事件／资源／实例如何连接；工作量如何经过机制影响体验 | 可查定义、事件依赖示意、反例与自检；不重复建立多套“帧时间”定义 |
| 预算与分档推导记录 | 在质量目标、内容规模、兼容性和持续能力之间作选择 | 完整教学推导；实际规则另有设备／配置／场景记录与校准结果 |
| 五类内容观测规格 | 特效、UI、角色、动画、场景各测什么，哪些成本共享 | 对象生命周期、指标、来源、阈值依据与无效条件；组合账本能避免重复记账 |
| 代表性深度案例 | 从复杂现象走到可证伪的解释，再落实优化取舍 | 代表案例共同覆盖 CPU／依赖、GPU／渲染、内存／生命周期，并检验首用和持续运行；保留未奏效方案或被推翻的假设。具体案例数由覆盖决定 |
| 可校准的采集与回归原型 | 设计能够落地，公共抽象可被第二种内容检验 | 先完成特效任务，再接 UI；配置、原始记录、报告、复跑及故障／回退检测可追溯。其余领域按需扩展 |
| 规则维护与采用记录 | 技术结果怎样转化为团队持续使用的能力 | 真实触发、处理、复验、例外和修订记录；没有团队采用时如实标为受控试运行，不编写团队收益 |

“基础文章可以阅读”“实验可以复验”“工具体系实际运行”“团队持续采用”分别记录。整套专栏以专家方向作品展示时，应有连贯模型、代表性可复核案例和实际运行的测量链路；若还要主张跨团队影响或生产收益，则必须进一步提供采用证据。任职等级仍由招聘与实际职责评价决定，不由文章自评授予。

## 6. 用现有文章试评

### 一帧拆解：基础讲解可以先成立

[一帧拆解](../content/performance/game-performance-frame-breakdown.md) L84–105 已给指标对象、起止点、聚合和窗口；L20 明确教学时间线没有设备 trace 或收益实测。因此可用来支撑 S2／S3 的基础模型，不能拿该时间线证明某机型的优化收益。摘要同帧收口问题已随 P1 原位修订并复审关闭，见[旧文审查 R1](client-performance-existing-content-review-2026-11-04.md)。

### 能力指纹：规则结构与性能接受条件分开

[能力指纹](../content/performance/from-model-table-to-capability-fingerprint-android-and-pc-tiering.md) L292 将代码标为伪代码，L309–311 用 80／50 分档。它可以讲规则结构；要满足 S6 的方法要求，还应明确这些数值未校准，并修正[旧文审查 R3／R4](client-performance-existing-content-review-2026-11-04.md)的兼容性与状态边界。

若声称这套阈值适用于项目，需冻结评分规则、目标配置、场景与预算，用未参与调参的边界设备执行预先约定的重复测试，核对原始时间线、内存和必要表现。算法输出 High 只能证明规则执行；配置接受与否要看实际测试。

一个拟验证反例是：两台设备总分都超过 80，一台 GPU 较强但 CPU 较弱，在密集角色动画任务中出现 CPU 关键路径超预算。若观测到该情况，就说明总分并不足以支持相同配置的接受，需要保留不可互相抵消的约束或调整映射。此处是反例设计，没有宣称已测得。

## 7. 每次开写与审稿怎样用

1. 先执行[旧文检索与复用判断](article-production-workflow.md#article-reuse-preflight)，写清已有覆盖、相关修订及本次增量。
2. 指明文章类型、主要问题、需要支撑的决定，选出本次适用的 S1–S8；不强迫原理篇承担完整监控平台职责。
3. 主张逐条对应来源或实验身份，预先列出一个反例／竞争解释和验证办法；有选择时比较代价。
4. 用下表记录审查，修正关键缺项或收窄结论；自审与独立审阅分开记录，阅读审稿不等于技术复现实验。
5. 正文、实验、工具和发布状态分别回写原规划；正文变化按仓库规范构建并检查页面，数字变化另核对证据。

| 主张／工程决定 | 适用条款 | 正文／证据位置 | 判断 | 最小修改或待验证事项 |
| --- | --- | --- | --- | --- |
| 按本篇填写 | S 编号 | 版本、文件、记录 | 满足／局部满足／待补／不适用及理由 | 明确到动作与完成证据 |

每批再做一次理解检查：改变一个条件，让作者重新判断。例如保持粒子数但改变屏占比、保持设备但改变缓存状态、保持画质但增加同屏角色。应能说明哪个指标可能先变化、模型依据、还缺什么证据，以及原结论是否仍成立。涉及自己的实测时，还应能够从原始记录复算关键结果，说明曾排除的解释和自己作出的决定；文稿审校与作者掌握程度分别记录。

标准制定时仅完成试评，未新增设备测量、优化结果或工具实现。2026-11-04 P1 已按本标准完成 A1/A2 的观测方法正文与 R1 修订，审阅范围及复审记录见[执行计划](client-performance-budget-tiering-monitoring-execution-plan.md)的 P1 交付记录。后续转入 P2 的数据可比性教学；实验、工具与采用继续独立验收。
