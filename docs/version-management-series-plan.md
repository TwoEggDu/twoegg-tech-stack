# 版本管理专栏规划

> 创建：2026-10-29。本文是“版本管理”专栏唯一的 canonical 篇级目录。
> 当前状态：首页与 10 篇章节已建立，第 01 篇已有正文，其余 9 篇为提纲；教学工程、工具实验、引擎验证与迁移试点均未执行。提交与线上发布状态以 Git 和部署记录为准。

## 1. 定位与读者

主问题：**一份本地修改，怎样成为团队可以审查、集成、构建和交付的版本？**

面向客户端和工具链工程师、参与资源与配置提交的美术和策划，以及版本与技术负责人。先解释工作区、变更集合、历史和共享基线，再分别理解 Git、SVN、P4，最后进入游戏工程的协作问题。

读者不必先熟悉三种工具。共同模型是入口，具体工具按需选择，后续工程篇说明所需前置。文章以原理与因果为主，命令和客户端操作用于验证模型。

## 2. 归属与组织选择

- 专栏名称：**版本管理**；副标题：**从 Git、SVN、P4 到团队协作**。
- 网站路径：**首页 → 工程与交付 → 版本管理 → 具体章节**。
- 物理目录：`content/delivery-engineering/`，沿用同目录内以文件前缀区分系列的方式。
- 首页：[`version-management-series-index.md`](../content/delivery-engineering/version-management-series-index.md)。
- 系列 ID：`version-management`；章节前缀：`version-management-`；篇级目录只在本文维护。
- 根 `doc-plan.md` 只登记系列路由；网站首页通过现有系列模板读取真实章节与提纲状态。

前一轮讨论比较了三种组织方式：三套独立工具教程方便查操作，但容易重复；逐问题横向比较便于选型，但初学者容易缺少完整模型；本轮采用“共同模型 → 各工具模型 → 工程问题”的组织方式，兼顾系统学习与按需查阅。

放在工程与交付之下，是因为主线跨越代码、资源、配置、审查与构建交接。引擎工具链通过资源身份和导入问题交叉阅读，代码质量通过审查和检查交叉阅读。本轮不新增一级栏目，也不调整站点模板。

## 6. 单篇写法与最小验证

默认采用“具体问题 → 对象和状态模型 → 机制与工具映射 → 最小实验 → 工程边界”的结构。每篇围绕一个问题展开，命令服务于解释；GUI 菜单只保留必要映射。

拟建立一个自建小型游戏工程，包含脚本、Prefab 与 `.meta`、配置和不适合文本合并的资源。先用普通文件验证版本控制机制，再按需进入引擎检查依赖，避免把引擎行为与仓库行为混成同一种保证。示例由两名协作者或两个明确区分的工作区演示，不使用公司项目资产。

| 实验方向 | 应保存的证据 | 当前状态 |
| --- | --- | --- |
| 工作区与历史 | 工具版本、配置、每一步文件与差异、操作结果及版本身份 | 未执行 |
| 任务提交与恢复 | 提交候选、保留的本地修改、依赖清单、失败后核对记录 | 未执行 |
| 分支、资源与审查 | 基线关系、冲突输入、锁的实际限制、审查绑定修订和最终内容 | 未执行 |
| 构建基线 | 输入清单、依赖取得、工具链、构建日志与验收范围 | 未执行 |
| 选型与迁移 | 同任务对照、约束记录、历史抽查、外部对象及权限核对 | 未执行 |

实验在临时仓库、自建测试服务和独立工作区完成。提纲阶段不修改生产仓库设置、分支保护或部署服务。文件一致、依赖完整、可重构建、功能正确及产物字节一致分别验证，不互相替代。
