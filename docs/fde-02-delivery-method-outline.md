## 2. 贯穿场景与最小模型

承接第一篇的通用检查系统，用三条虚构反馈演示判断：P-001 制作人员已打开报告却无法辨认输入；P-002 QA 在另一独立任务中也无法确认报告覆盖的提交；P-003 检查已完成但通知未送达。前两条归入输入辨认热点 H-001，第三条单列通知热点 H-002。反馈、核对结果与排期集中标明为教学推演。

先按受阻步骤归类，再核对共同工程落点；明确当前任务可恢复、查询页可用和改进时间有限的条件。恢复 P-003 后，让 H-001 进入小范围改进，同时由维护者排查 H-002，并写出应重排优先级的条件。选中的 H-001 关联拟议能力 C-001；记录体系随具体问题引入。

## 3. 正文结构

| 部分 | 要解决的问题 | 具体落点 |
| --- | --- | --- |
| 开篇与模型 | 收到功能请求后，怎样形成可判断的改进事项？ | 用一条请求引出观察、核实、归类、取舍与复验，暂不引入完整记录体系 |
| 1. 发现需求 | 走访看谁、看什么、怎样问，如何看见没有被主动反馈的问题？ | 跟随一次任务，观察交接、等待和绕行；开放问题；紧急协助单独记录 |
| 2. 核实问题 | 原话、观察、解释与需求如何区分？ | P-001 示意记录、版本与日志核对、反证检查、共同确认目标 |
| 3. 判断热点 | 哪些合并、哪些拆分，为什么先推进这一项？ | 三条记录归为两个热点；核对共同落点；恢复与改进分别决定；写明负责人、理由和重排条件 |
| 4. 形成能力 | 怎样从热点走向有限方案与可维护工具集？ | 候选方案与目标对应；C-001 标为拟议；用户任务入口、权责、依赖和退出条件 |
| 5. 使用复验 | 怎样发现方案可运行但用户仍然受阻？ | 同类真实任务观察，记录协助、错误结果、回退和跨场景限制 |
| 附录与收束 | 读者如何开始一轮小范围实践？ | 正文提供填写简例，三份完整模板放入默认折叠附录，保留原有 29 个字段供按需使用 |
