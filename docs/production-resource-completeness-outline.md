## 作者在本次讨论确认的顺序

| 阶段 | 已确认事实 | 写作落点 |
| --- | --- | --- |
| 起点 | QA 反馈某处内容缺了一块；当时 Missing 检查尚未上线。作者去美术工位是为了核对其本地是否也有问题，本地显示正常 | 从真实异常与现场对照开始，不能以机器人已经上线开场 |
| 本地定位 | 人工找缺失节点困难，排查后补充本地工具；最初由作者使用，定位后再到美术本地检查；美术本地用同样工具没有查出对应问题 | 区分工具开发时间与最初使用者，不倒写成美术先提功能需求 |
| 仲裁机 | 引入仲裁机后能查出相应 Missing，美术可以自行排查、调整缺失内容 | 共同排查环境；已有案例明确由人工 SVN 更新 |
| 检查范围 | 先选定资产，后检查全部资源，再收紧到需要进包的内容 | 覆盖与检查成本之间的调整；不补编耗时或资源总数 |
| 触发时机 | 定时安排检查或 QA 发现异常后由专人处理，压力集中在少数人并在版本日前增大；后来提交即触发 Missing 检查并自动 @ 提交者 | 区分进包检查范围与提交触发时机；没有依据声称只检查本次改动 |
| 依赖提交 | 自动检查后的提醒多到难以查看，随后才补充依赖提交；美术既不易识别完整依赖，也会在手动选择时遗漏；一个场景可能依赖几百个资源 | 从使用者修改的资产出发，由工具收集依赖，再确认提交候选 |

## 六段正文

1. 人工找节点太难，先补定位工具。
2. 美术本地正常，仲裁机提供共同排查环境。
3. 从单资产、全资源收紧到进包内容。
4. 将检查接到提交，把压力从版本日前移到生产过程。
5. 频繁提醒之后，继续改善依赖提交。
6. 配套文档、使用跟进与定性结果；简短联系 FDE 方法。
