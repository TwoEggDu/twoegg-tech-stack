# TwoEgg 单篇生产流程

> 这份文件回答的是：`一篇文章怎样从想法走到发布。`

## 1. 适用范围

这份流程适用于：

- 新文章起草
- 旧文章重写
- 系列中的单篇推进

它不替代：

- 系列 plan
- 写作方法规范
- 证据卡模板

也就是说：

- 系列 plan 决定写什么
- 写法规范决定怎么写
- 这份流程决定怎么推进到成稿

## 2. 默认流程总览

默认按下面这条链推进：

```text
选题
-> 检索相似旧文，判断复用方式
-> 判断文章类型
-> 确认系列与边界
-> 起 outline
-> 补前置资料 / 证据
-> 写初稿
-> 自查与修订
-> 构建验证
-> 发布 / 回写状态
```

这条链的核心目标不是增加流程感，而是避免两种常见坏法：

- 没有 outline 就直接写，最后结构散
- 文章写完了，但系列状态和索引没有回写

## 3. 第一步：选题

先回答：

- 这篇想解决什么问题
- 它属于哪个系列
- 它是否真的值得单独成篇

如果一个话题只是某篇正文里的一段，或者没有稳定问题空间，就不要硬拆成单篇。

<a id="article-reuse-preflight"></a>

### 3.1 开稿前：检索相似旧文，判断复用方式

新选题在开始 outline、创建新文章文件或作为新稿推荐前，先做这一步。先确定它要回答的读者问题，再检索；不能因为计划里写着“待写”或换了标题，就认定仓库缺少相关内容。

**检索与阅读范围：**

- 从[根路由](../doc-plan.md)定位目标系列及相关 canonical plan，核对篇目边界；同时在 `content/` 跨系列检索文件名、标题／摘要、正文关键词与小节。将问题中的关键概念、常见别名、中英文术语和相关现象作为检索线索，不只匹配拟标题或查前后篇。
- 先轻量检索候选，再读命中文章的相关正文，确认它实际回答的问题、目标读者、适用版本与证据范围。关键词相同不等于重复，标题不同也可能已有完整覆盖；只看搜索命中不能下复用结论。
- 区分已有正文、提纲、草稿与仅规划的篇目；`docs/` 中的 outline、证据卡和执行记录是支持材料，不当作已写正文。目录登记与文件不一致时列待核对项，不编造完成状态。
- 现有明确材料可以直接复用。本轮已经完成且主题、范围、相关文件没有变化的检索，不必重复；主题变化或发现新的相关材料时再补查。不默认全文读取全站，也不把仓库以外的技术事实核查混成这一步。

**复用判断：**

| 已有覆盖与当前需求 | 优先处理方式 |
| --- | --- |
| 旧文已经回答核心问题，读者与条件适合 | 直接引用或接入阅读路径，不再写同义新篇 |
| 核心问题一致，只缺一段解释、案例或验证 | 优先原位补节、补桥或补证据，保留原文章身份 |
| 旧文的结论、版本或证据已过时 | 优先判断修订范围；有保留历史版本的阅读需要时说明关系，不机械覆盖全部旧内容 |
| 有独立的读者问题、场景、版本对照或新增论证，适合单独阅读 | 可以另开新篇，但必须说明新增价值、与旧文的边界及必要回链 |

独立成篇的判断服务于内容职责；用户明确要求保留新篇时，仍交代与旧文的关系和增量，不擅自取消用户指定产物。确认新增篇目后，按原 canonical plan 登记，不在这里建立另一份目录。

**开稿前的简短结论：** 在编辑工作单或本轮回复中交代以下四项即可，无需每篇另建检索报告，也不把这些工作备注复制进读者正文。

1. **检索范围**：查了哪些系列／目录，用了哪些主要概念和别名。
2. **相似旧文与已有覆盖**：列出实际读过的文章路径和相关内容；只有提纲的如实标注。没有发现时说明本轮范围，不凑相似文章。
3. **复用决定**：直接引用、补旧文、修订旧文或另开新篇，并给原因。
4. **本次增量**：还缺哪一项解释、证据或独立问题；新篇如何与旧文分工。

无法检索或只完成局部检查时明确写“尚未完成旧文核对”及限制，不能宣称“没有类似文章”。纯状态查询、局部勘误不必额外执行整套开稿检查。

## 4. 第二步：判断文章类型

开写前先判断这是哪一类文章。

默认从下面四种里选：

- 原理篇
- 映射篇
- 案例篇
- 索引篇

不要写到一半才决定它到底是什么。

文章类型一旦判断清楚，后面的 outline 才会稳定。

## 5. 第三步：确认系列与边界

在 outline 前先回答：

- 这篇在本系列里站在哪
- 它的前置文章是什么
- 它不该吞掉哪些别的系统

例如：

- 技能系统里的 AI 边界篇，不该写成完整 AI 系列
- 技能系统里的多人同步篇，不该写成完整网络同步百科

如果这一步不做，文章很容易越写越大，边界失控。

## 6. 第四步：起 outline

默认先读：

- `docs/article-writing-method.md`
- `docs/article-outline-template.md`

然后根据文章类型起 outline。

最少也要先有：

- 这篇在解决什么问题
- 抽象模型是什么
- 最后落到什么具体实现

没有 outline 就直接写，大概率会导致：

- 第一屏先讲 API
- 中间没有抽象模型
- 结尾回不到工程实现

## 7. 第五步：补前置资料 / 证据

不是每篇都要重证据驱动，但默认要先判断：

- 这篇是否需要查官方资料
- 这篇是否需要引用已有 plan / outline / evidence card
- 这篇是否需要交叉引用仓库内已有文章

建议分三种情况。

### 7.1 纯原理与方法文

如果主要在讲问题空间、抽象模型、工程边界，且内容稳定，可以少依赖外部资料。

### 7.2 引擎实现文

如果明显涉及：

- Unity / Unreal 具体机制
- 版本差异
- 官方 API / 包行为

就应该查证，不要只凭记忆写。

### 7.3 案例与诊断文

要优先整理：

- 现象
- 排查过程
- 根因证据
- 修法依据

不要只留最终结论。

## 8. 第六步：写初稿

写初稿时，默认遵守下面几条：

- 第一屏先立问题，不先讲 API
- 中间必须有抽象模型层
- 最后必须回到具体实现
- 要主动拆边界，而不是把交叉系统写糊
- 末尾用一句最短结论收口

写初稿时可以不追求“完全正确的字句”，但结构必须先站住。

## 9. 第七步：自查与修订

初稿出来之后，至少自查下面这些问题：

### 9.1 结构检查

- 问题空间是否清楚
- 抽象模型是否存在
- 是否落回具体实现
- 系统边界是否清楚

### 9.2 文章类型检查

- 原理篇有没有退化成工具说明书
- 映射篇有没有退化成 API 对照表
- 案例篇有没有只写现象，不写根因
- 索引篇能不能真的回答“先读哪篇”

### 9.3 交叉引用检查

- `series` 是否正确
- `slug` 是否稳定
- 文内链接 / `relref` 是否正确
- 是否需要在索引页或系列 plan 里回写

## 10. 第八步：构建验证

文章不是写完 Markdown 就结束了。

至少要做一次站点构建验证，确认：

- front matter 合法
- 页面可被 Hugo 正常生成
- `relref` 没断
- 没有明显渲染结构问题

如果文章涉及系列索引页，还要确认它的阅读路径和链接能成立。

按[文章呈现与创建约定](article-presentation.md)使用新建模板，并执行：

```powershell
python -m unittest discover -s tests -p test_reading_layouts.py -v
hugo --gc --minify --destination .tmp/publish-check
python scripts/check-reading-pages.py --public .tmp/publish-check
```

普通文章无须额外指定样式。新系列需填写真实 ID、索引与顺序，先保持草稿状态，检查完再发布。页面呈现有变化时，在浏览器确认主题、系列和前后篇导航，查看桌面侧栏与窄屏目录。生成页检查通过和线上发布成功分别记录。

## 11. 第九步：发布 / 回写状态

一篇文章发布之后，至少要回写这些地方中的相关项：

- 本系列专属 plan
- 总 `doc-plan`
- 系列索引页

如果只把文章发出去，不更新系列状态，后面的 plan 很快就会过期。

## 12. 什么时候需要单独 evidence card

不是每篇都要 evidence card。

更适合单独补 evidence card 的情况通常是：

- 引擎实现细节重
- 明显依赖官方资料
- 计划做系统性系列
- 同一主题会反复扩写

如果只是高层原理或方法文，不必机械地先建 evidence card。

## 13. 什么时候适合直接写，不必先补完整计划

下面这些情况通常可以直接写：

- 这个主题边界已经很清楚
- 文章类型已经明确
- 系列主线已经存在
- 这篇不会改变整个系列结构

换句话说，不是每篇都要先做大 planning。

但即使直接写，也应该至少先有 outline。

“直接写”仍需完成上面的[旧文检索与复用判断](#article-reuse-preflight)；已有有效结论可复用，不必重复规划或检索。

## 14. 发布前最小检查清单

发布前至少确认：

- 标题、slug、series 是否一致
- 是否已检索相似旧文，并明确复用方式与本次新增内容
- 文章类型是否明确
- 第一屏是否先立问题
- 是否有抽象模型
- 是否落回具体实现
- 是否讲清系统边界
- 是否有一句最短结论
- 本地构建是否通过
- 模板回归与生成页样式、导航检查是否通过
- 是否需要更新系列索引或 plan

## 15. 最短结论

`一篇文章的生产，不是“想到就写完发出去”，而是先定类型和边界，再起 outline，再补必要资料，再写稿、验证、回写状态。结构和维护都应该从一开始就被设计进去。`
