## 二、单篇怎么审：看读者能不能作出一个判断

先写一句：**谁在什么条件下，需要依据本文决定什么？** 例如：“目标机型首次释放技能时掉帧，客户端程序需要决定先采 I/O 时间线还是主线程激活时间线。”如果只能写出“了解资源加载”，先收窄问题。术语解释、速查与索引的职责见下节。

| 审查项 | 通过时，审稿人能从正文指出 | 应退修的典型情形 |
| --- | --- | --- |
| 问题与约束 | 谁遇到什么困难；哪项平台、版本、玩法目标、生产条件或成本真正改变选择；怎样才算解决 | 标题写“最佳实践”，但换项目、换目标仍给同一答案 |
| 机制与因果 | 从一个可观察现象追到起作用的机制；能指出一个容易混淆的解释，以及怎样辨别 | 堆 API、术语、管理流程，或把调用顺序当作根因 |
| 取舍与边界 | 为什么推荐这个做法；与维持现状或一个可行替代相比牺牲了什么；哪个条件改变时应改选 | 只有优点；“视项目而定”却说不出看什么 |
| 证据与验证 | 关键断言能定位到版本化规范、公开源码、同次实验记录、脱敏项目材料或清楚标注的推演；交代证据没覆盖什么 | 从静态代码推出设备耗时，从一次跑通推出长期可靠，从体验偏好推出留存增长 |
| 应用与复用 | 读者遇到相似问题时，有可执行的下一步和判据；涉及交接时能说清谁接收什么、何时退回或升级 | 建议“加强协作、持续优化”，接手的人却不知道先查什么、何时停止 |

**判定方式：** 每项记“满足 / 缺项 / 不适用”，附段落或证据位置；不适用要按篇型说明理由。适用项全部满足才记“通过”；核心论断可能成立但缺依据，记“待补证”，允许缩小论断后重审；其余缺项记“退修”，写明一项足以改变结论的最小修改。出现伪造经历或数据、关键事实错误、受限源码或未脱敏材料，直接记“阻断”，先纠正或移除再复审。篇数、字数、图表数与平均分都不能抵消这些问题。

## 三、不同篇型，交不同的证据

| 篇型 | 应看到的最小成果 |
| --- | --- |
| 基础／原理 | 读者能用模型解释一个现象，并知道模型在哪种条件下失效。规范、公开源码或可核对的推演可以支撑原理；可不比较实施方案，可不提供生产业绩。 |
| 设计／映射／方法 | 在同一目标和约束下比较可行选择，给出改选条件。跨引擎比较须对齐职责与版本；管理或玩法方法须说明适用的人、任务或体验目标。 |
| 案例／实验／项目复盘 | 区分作者、团队及工具分别做了什么；给出基线、动作、可核对结果和未排除因素。教学实验可以通过实验篇审核；声称某次生产事故、团队采用或收益，则须另有相应材料。 |
| 操作／速查 | 有适用版本、输入、成功信号和至少一个常见失败的识别办法；可不单列方案比较。 |
| 索引／阅读导览 | 按读者问题指向可读正文；标清已写、仅规划与仍待验证的内容，抽查跳转。机制、方案比较不适用。索引通过不计为栏目代表作。 |
| 随笔／职业反思 | 论点、经历与价值判断分开；从一次经历能推出什么、不能推出什么说清楚。若只是个人观察，可单独发表，不据此证明工程成效。 |

## 四、六个主栏目，各用一道专业问题验收

以[当前阅读入口](../data/reading_paths.yaml)的六个主栏目为单位。下表给的是代表作验收题，不是要求每个栏目都写同一种文章。

| 栏目 | 审稿人可以当场追问 | 能回答追问的材料示例 |
| --- | --- | --- |
| 工程与交付 | 一项错误配置通过构建后，在哪一步还能拦住？谁决定退回、修正后拿哪个候选版本复验？ | 一份贯穿制作、校验、发布的交接记录或隔离演练；区分发现、修复、验收。FDE 另查原任务是否恢复、使用者是否实际采用。 |
| 项目管理 | 里程碑不动、美术产能下降时，谁在减范围、降规格和延期之间作决定？凭什么改排期？ | 带依赖、产能假设、决策人和复查时间的取舍记录。通用基础篇可用教学情景；声称管理有效要有执行反馈。 |
| GamePlay | 修改攻击前摇后，希望哪类玩家在哪个窗口作出不同选择？怎样区分规则改变和玩家刚好更熟练？ | 规则与输入反馈对照、试玩观察或明示的验证设计。作者体验、玩家样本、指标因果分别表述。 |
| 全栈框架 | 同一个技能在客户端预测成功、服务端拒绝时，谁拥有最终状态？重复消息或旧版本客户端怎样处理？ | 一条跨端状态轨迹、契约与异常分支；ET 标明版本。单进程推演只能回答模型问题。 |
| 引擎研发 | 人物画面抖动来自骨骼变换、更新时序还是渲染提交？在哪个边界观察什么量，足以排除一种解释？ | 固定版本的公开实现、最小输入、帧捕获或调试记录；工具链还要交代产物由谁消费、失败怎样定位。 |
| 性能优化 | 首次释放技能掉帧，怎样区别读盘等待、主线程激活和 GPU 工作？优化后成本转移到了哪里？ | 目标场景与预算、同条件基线、对应线程或设备观测；涉及收益时说明设备、构建、采样条件及画质、内存等代价。 |

**跨栏内容按其主要结论加审。** 长线运营查告警信号、处置与恢复验证；代码质量查规则能捕获的缺陷、误报与例外；问题解决查竞争假设和排除证据；AI / Agent / Harness 查任务基线、失败样例、权限边界与回归集；系统设计及服务端查不变量、负载与故障条件；渲染查阶段输入输出与画面证据。ET 前置、运行时、算法按基础篇审；工程实践与演进、项目作品及实践练习按真实项目或教学案例分别审；杂文和阅读入口用第三节。不因文章存放在另一目录而重复计作两个栏目的独立成果。

## 五、栏目怎么判定：沿一个问题读到可复核的结果

每个主栏目选一个本领域重要、会影响实际决定的问题。从首页点进去，记录三个位置：**哪里讲清必要基础，哪里解释如何取舍，哪里给出可复核的应用或验证。** 三处可以在同一篇，也可以由几篇衔接。审稿人再换一个条件：换机型、换版本、缩短制作周期或改变玩家目标，能否根据正文说出原建议还成不成立？能给出判据，就是方法可迁移的证据；声称已被其他团队复用，仍须实际采用记录。

- **达到本站代表作标准**：路径可达，所选正文按其篇型通过；同一问题的基础、判断、验证能够接上；至少一项关键判断有可复核的已完成材料。可以是公开实现对照、带观察结果的独立实验、带记录的试玩或脱敏决策复盘，材料强度须与结论相称。
- **部分达到**：有可靠基础或设计方法，但缺应用结果、关键证据或文章间的连接。保留合格文章，列最小补项，例如“补一次目标设备的首次使用采样”，不笼统要求“再写几篇”。
- **待建立／待审**：已检查而仅有规划、目录或术语介绍，记“待建立”；尚未读过正文，记“待审”。六栏分别出结论。一次代表路径通过，只能证明该栏目已有代表作，不能推断全栏目文章合格。

**校准示例。** [《读盘完成，为什么还是不等于资源可用》](../content/performance/game-performance-read-does-not-mean-ready.md)明确把读取、激活和用途就绪拆开，并标明没有设备 trace。审原理时，可引用其阶段示例，检查读者能否指出“已读完”后还应观测哪一段；若要用同文证明“某机型掉帧由 I/O 引起”，现有证据不够，要补该机型上同次卡顿的时间线。这是对两种断言的校准，不是对性能栏目的整体验收。

## 六、留下可复审的记录

在原系列审查记录或本轮工作单填一行；栏目审核附代表路径。复审人按同一主张、同一证据位置核对，不以“已改稿”代替通过。

| 对象／篇型 | 关键判断与适用条件 | 正文及证据位置 | 分项缺口／不适用理由 | 结论 | 最小补项与复审判据 |
| --- | --- | --- | --- | --- | --- |
| 栏目 → 系列 → 篇名或代表路径 | 一句能被追问的话 | 小节、版本、记录链接 | 对照第二至五节 | 单篇或栏目结论 | 补什么；看到什么即可关闭 |

新稿和实质重写在自查时使用；存量先审六栏各一条代表路径，再按风险抽查结论最强的旧文。正文修改、实验完成、本地页面检查和上线状态分别记录。此标准建立时没有对六栏做达标评级。
