## 2. 开头与贯穿例子

### 开头骨架

- 情境：接入法杖模型时，资产表里有一个面数。程序准备判断是否需要简化，但尚未确认它指 DCC 多边形还是导入三角形，也不知道在主要游戏镜头中能看见多少细节。
- 第一段任务：从日常接入问题出发，说明这个数字有价值，但还缺数据身份与使用条件。不要用虚构的卡顿事故或“同面数却慢几倍”制造悬念。
- 第二段任务：给出全文观察顺序：**制作拓扑 → 导入顶点与索引 → 镜头中的投影与贡献 → 实际绘制用途 → 候选版本比较**。这是分析顺序，不是 GPU 执行时序。
- 第三段任务：承诺用同一个教学对象逐步补齐信息，文末形成判断表，而非给统一的模型面数上限。

### 主例子与候选材料

主例子复用[美术制作 03](../content/delivery-engineering/game-art-production-03-character-assets.md)中的法杖金属框 `staff_frame`。该文的基础框由四个相交的简单盒体组成，分组不代表焊接、单一 Mesh 或一次绘制。这里借用对象身份，讲解版模型与工程仍待制作。

基础盒框适合解释对象、边和属性关系；为了展示细节取舍，可另制轮廓相近、带倒角的教学变体。必须写明这是新设计的对照材料，不暗示原有简单盒框已经构成几何性能问题。

| 对照轴 | 准备怎样的材料 | 主要回答什么 | 需保持或记录的条件 |
| --- | --- | --- | --- |
| 计数口径 | 同一个框的 DCC 拓扑与导入 Mesh | 多边形、三角形、索引与顶点记录的区别 | 导出/三角化、导入设置、属性、拓扑类型 |
| 属性边界 | 轮廓与三角形尽量相同，单独改变一类法线或 UV 边界的两个版本 | 属性不连续怎样影响顶点记录 | 其他属性及导入优化保持一致；实际结果待观察 |
| 细节表达 | 倒角/表面细节由几何或法线表达的候选 | 移除了什么几何，又引入什么表面工作和画面差异 | 镜头、光照、材质功能、纹理与渲染设置分别记录 |
| LOD | 同一对象的至少两个显式简化版本 | 细节在哪些显示条件下可以切换 | 包围范围、轮廓、切换配置、LOD Bias 与运行条件 |

四行分别建立比较，不把它们同时改成一个“优化版”后归因于面数。法线表达比较本来就会改变材质输入，应记录这项成本转移。首稿可先用原创示意讲清关系；真实截图和测量需有实际材料后再补。

## 3. 正文六节详细骨架

### 正文一 “多少面”描述了模型的哪一部分

**本节职责：** 建立计数口径，解释为什么接到一个数字后应先问“数的是什么”。

建议 H3 与展开点：

1. **制作中的面，与绘制使用的拓扑**：用框上一块四边形表面说明，多边形会按导出/导入过程形成具体三角形；非共面或复杂多边形的三角化也可能影响最终形状与着色。文中主例固定为三角形 Mesh，说明 Unity 还支持其他拓扑即可。
2. **三角形怎样引用顶点**：用两个共享边的三角形示意索引引用；先解释“索引是找到顶点记录的位置”，无需上来就讲缓冲 API。
3. **资产表应该写下哪个口径**：记录源模型统计还是导入统计、所统计的对象范围、是否包含全部子网格和 LOD。三角形拓扑下可以由索引数理解三角形数，但不能把任意 Mesh 的索引数都除以三。

核心论点：面数是几何规模的一个描述，必须绑定阶段、对象与拓扑，才有可比较的含义。

拟图：框上一块表面的“DCC 多边形—三角化—索引引用”三联图，标示示意数据，不填未经导入确认的实际数量。

本节结束读者应能判断：美术说“几百面”时，应该追问哪三个条件，而不是马上判定合格或超标。

承接下一节：知道三角形引用顶点后，还需要解释这个“顶点”保存了什么。

### 正文二 导入后的数据为什么值得单独检查

**本节职责：** 从几何点的位置，桥接到带属性的顶点记录。

建议 H3 与展开点：

1. **一个位置可以对应多份属性记录**：先画金属框的转角。若相邻面在同一位置需要不同法线或 UV，一条完整记录无法同时表达两组值，因此可能需要不同顶点记录。硬边和 UV 接缝的实际处理还取决于导出、导入和优化规则。
2. **法线、切线和 UV 各在传递什么**：只解释它们给着色提供的信息；详细 TBN 推导与法线烘焙转到旧文。强调可见形状相同，属性集合和存储布局仍可能不同。
3. **模型计数与一次绘制的工作分开看**：`Mesh.vertexCount` 描述 Mesh 的顶点数；它不能直接给出某帧顶点着色器的实际调用数，更不能给出时间。索引复用、缓存、实例和实际 pass 等条件需要另查。

核心论点：源模型中的位置点、导入顶点记录和设备实际处理工作是三个不同观察对象。不要把“导入顶点更多”简单归因于美术错误，也不要写“一个立方体永远是 24 个顶点”。

拟图：同一转角的“位置相同、法线/UV 不同”记录表，与两个三角形的引用图并排；显示为什么拆分，而非只列结论。

Unity 对照位置：本节后放检查卡 A。不写顶点字节估算器；属性格式、索引位宽、压缩和 Read/Write 的进一步内容链接[存储基础](../content/rendering/unity-rendering-supp-a-mesh-texture-storage.md)。

本节结束读者应能提出：导入后顶点记录是否符合预期、增加的是哪类数据，以及要看哪项设置才能继续解释。

### 正文三 把网格放进游戏镜头

**本节职责：** 将几何数据与屏幕上的贡献连起来，解释为什么简化要有目标镜头。

建议 H3 与展开点：

1. **从模型空间到屏幕大小**：固定法杖与材质，改变视角或距离，观察轮廓、倒角与内部细节；记录相机投影/FOV、实际渲染分辨率和显示条件。距离本身不足以代表屏幕大小。
2. **小三角形为什么值得注意**：解释三角形准备、光栅化与片元着色承担不同工作；很细小的三角形仍可能带来几何处理，而新增细节未必形成稳定可辨的像素贡献。低于一个像素并不意味着自动零成本或绝对不可见。
3. **密度应该服务哪些视觉信息**：优先观察轮廓、孔洞、曲率和显著高光，再看对当前镜头贡献有限的平面细分。阴影和运动中是否显露差异，留作后续检查条件。

核心论点：三角形在屏幕中的大小，是判断几何投入与视觉贡献的线索；它不是独立的设备耗时公式。涉及具体 GPU 对细小三角形的吞吐、缓存或执行行为时，必须另有硬件资料或测量。

拟图：同一个框的近/中/远三组投影，配轮廓和线框示意；另画局部像素网格说明覆盖尺度。固定渲染分辨率，图中放大观察与实际显示尺寸分开标注。

正文可留一个“先查什么”短框：**哪些细节在目标镜头下可辨？投影尺寸是否记录？如果减少它们，轮廓、高光、阴影会改变什么？**

本节结束读者应能判断：某处密度值得进一步比较的理由来自哪里，以及仅凭线框很密还不能证明什么。

### 正文四 模型实际被用在哪些绘制中

**本节职责：** 防止只看主画面的单次使用，补齐几何参与运行工作的范围。

建议 H3 与展开点：

1. **主画面以外，哪些用途还会用到它**：主相机着色、阴影投射、深度或其他相机等作为候选；实际出现什么取决于管线、材质、质量设置、可见性和 Renderer 配置。
2. **对象、子网格与 pass 的关系**：回到框的分组提醒：DCC 里的组、一个 Renderer、一个 Mesh 和一次绘制不是等价关系。只解释需要检查哪些对应，批处理机制转到旧文。
3. **建立一张实际使用图**：将“待确认用途”改为捕获中看见的用途，区分提交、裁剪和最终可见结果。不能用“资产三角形数 × 固定 pass 数”冒充真实 GPU 工作量。

拟图：法杖 Mesh 被主视图与阴影等用途引用的关系图，用虚线标候选用途、实线标后续捕获确认的用途。未捕获时全部作为教学示意。

Unity 对照位置：本节后放检查卡 B。阴影具体模式、级联与替代方案转到[移动端阴影](../content/performance/gpu-opt-04-shadow-mobile.md)。

本节结束读者应能判断：在主画面很小或不可见的细节，是否仍需要检查其他用途；找到多次绘制后，是否还缺耗时和视觉证据。

### 正文五 几何、法线与 LOD 怎样比较

**本节职责：** 将前三类观察转为有条件的候选方案，解释它们改变了哪些成本。

建议 H3 与展开点：

1. **保留几何，保留的是什么**：轮廓、遮挡、孔洞和真实形体与几何有直接关系；倒角还可能影响高光。先列画面要求，再讨论是否值得简化。
2. **用法线表达细节，改变的是什么**：普通法线贴图改变着色使用的法线，不直接补回被删去的轮廓和遮挡几何；它增加纹理与相应 Shader 工作，收益需要结合原有材质和投影覆盖。本文不展开位移、视差等其他路径。
3. **LOD 怎样根据显示条件保留不同细节**：解释多个几何版本与选择条件；Unity LODGroup 的阈值以对象相对屏幕高度为基础，不写成固定世界距离。哪些细节应在哪一级消失，需要目标镜头与画面约束决定。
4. **切换也有成本和观感**：额外 Mesh 数据、配置与维护需要计入；淡入淡出需具体版本/Shader 支持，过渡区可能同时绘制相邻级别。资源是否同时驻留由加载/引用路径确认，不能只凭存在多级就断言驻留结果。

正文比较表拟用：

| 候选 | 预期改变 | 要保住的画面信息 | 下一步该查什么 |
| --- | --- | --- | --- |
| 删去贡献有限的细分 | 几何数据与相关处理候选减少 | 轮廓、曲面、高光、阴影 | 导入数据是否减少；目标镜头是否出现差异 |
| 部分细节转到法线 | 几何与表面工作的分配改变 | 可接受的表面细节与材质表现 | 材质输入、纹理、采样/着色与实际显示结果 |
| 增加 LOD | 不同显示条件使用不同网格 | 各级效果与切换连续性 | 实际级别、阈值、过渡、引用与驻留，以及后续性能 |

Unity 对照位置：本节后放检查卡 C。普通法线贴图的技术机制链接[法线映射](../content/rendering/shader-lighting-02-normal-map.md)。

本节结束读者应能解释：自己选择一个候选是为了改善什么、会付出什么代价、还有哪些假设未确认。不要用固定减面比例或统一 LOD 级数替代比较。

### 正文六 怎样决定保留哪个版本

**本节职责：** 用法杖候选记录完成一次有依据的判断流程。

建议 H3 与展开点：

1. **写下同一组比较条件**：候选版本、Unity/管线/平台、镜头、渲染分辨率、材质、灯光、实例和显示范围；一次比较只围绕一个问题。检查属性边界与比较几何/法线时，分别用前文材料表中的不同条件。
2. **把数据、画面和工作证据并排**：导入数量回答数据是否改变；匹配视角回答视觉是否可接受；绘制记录回答参与哪些工作；设备采样才进一步回答运行成本变化。证据间可相互解释，但不能彼此冒充。
3. **允许结论暂时只到下一步检查**：数据减少而视觉可接受，可以进入目标设备比较；未发现可辨的收益或出现画面问题，可以调整候选；没有可靠时间数据时，保留性能收益待确认。

正文最终判断表拟用：

| 问题 | 需要记录的证据 | 当前可作的决定 |
| --- | --- | --- |
| 导入数据是否按预期变化 | 顶点/索引/子网格与相关属性、导入设置 | 材料是否适合继续比较，是否需要解释意外差异 |
| 目标画面能否接受 | 匹配镜头的轮廓、高光、阴影与运动/切换观察 | 保留哪些细节、调整哪个候选 |
| 实际参与什么工作 | 对象/子网格与相关绘制用途 | 是否需要检查额外 pass、材质或场景条件 |
| 实际成本是否值得 | 对应问题的稳定设备记录与条件 | 是否采用该方案及其适用范围；无数据则继续待验证 |

结尾回到开头：面数是起点，继续查“导入了什么、在镜头里贡献什么、被哪些用途使用、候选改变了什么”。沿当前问题跳转到存储、Draw Call、Shader 或阴影旧文。

## 4. 三张 Unity 检查卡

检查卡均为待执行步骤。建议示例环境为 Unity 6000.0 / URP 17，执行时记录实际补丁与包版本；使用专门的教学副本，不改生产资源。三张卡服务原理，完整设备实验不作为本篇前置要求。

### 检查卡 A 看到导入的 Mesh 数据

1. 从目标 Renderer 找到实际使用的 Mesh 子资源，在 Mesh Inspector/Preview 查看顶点、面类型与数量、子网格、UV 等可见信息；不要把 FBX 文件的总览当成这个 Mesh 的全部数据。
2. 对照模型导入设置与 DCC 导出约定，检查法线、切线、UV 和三角化相关处理；选用材料表中的属性边界对照，其他条件保持一致。
3. 写出一条“数据观察—可能原因—还需确认”的记录；看见数量差异后，回到属性边界解释，不先写性能提升。

产物：两份导入信息和一张属性边界示意。可按需查 `Mesh.vertexCount`、`Mesh.HasVertexAttribute` 的含义，不要求读者写导出脚本或在运行时启用可读副本。参考 [Mesh 数据预览](https://docs.unity3d.com/6000.0/Documentation/Manual/view-mesh-data-visualizations.html)。

### 检查卡 B 看到同一对象的绘制用途

1. 在有目标对象、主相机和可投影光源的教学场景中固定视角，打开 Frame Debugger，记录 Editor/Player 目标与实际渲染配置。
2. 找到与该对象有关的事件，分别记录主画面和阴影等实际存在的用途、子网格与 pass；未出现的候选用途保持“未观察到”，不按预设补齐。
3. 将事件记录对应回正文的使用图，说明当前只确认了什么；需要定量成本时，进入后续设备采样。

产物：带对象与用途说明的事件截图。限制：事件数、三角形统计或这张图都不能直接折算为毫秒。参考 [Frame Debugger](https://docs.unity3d.com/6000.0/Documentation/Manual/FrameDebugger.html)。

### 检查卡 C 看到 LOD 的选择与切换

1. 为同一教学对象准备两个显式简化网格，放入 LODGroup 对应级别，核对包围范围与 Renderer 引用；材质和显示目标保持可比较。
2. 固定相机路径与渲染分辨率，观察当前级别和切换；记录相对屏幕高度阈值、LOD Bias 与画面差异，不把编辑器预览的距离直接当作项目通用规则。
3. 若检查淡入淡出，先确认 Fade Mode 与 Shader 支持，再观察过渡区相关事件；分别记录级别选择、切换观感与可能并存的绘制，时间数据继续留空。

产物：一段切换条件记录和匹配视角对照。限制：不规定统一级数、阈值或减面比例，不声称已节省帧时间。参考 [LODGroup](https://docs.unity3d.com/6000.0/Documentation/Manual/class-LODGroup.html)。
