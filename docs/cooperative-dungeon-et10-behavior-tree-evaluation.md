# 无尽对决行为树评估：ET10 首选候选、近战怪设计与最小验证

日期：2026-10-25（Asia/Shanghai）

> 首选候选 · 待验证。当前只完成源码静态核对与接入设计，未编译、编辑导出、运行怪物 AI 或验证服务端调试。ET10 内置行为树尚未标记为“已采用”；v0.1 玩法规则保持已确认状态，游戏仍待实现与验证。

## 1. 选型结论与教学目标

无尽对决优先评估 ET10 的 `cn.etetet.behaviortree`。它已有节点模型、执行入口与 Unity 编辑器代码，有机会复用现有 ET 组织和制作链路，减少额外引入行为树库与图形工具的接入工作。这是候选排序的理由，不是已证明的成本或性能收益。

首版只组织已确定的普通近战怪行为：选最近存活玩家、直线追击、范围内等待并攻击、倒下与本局结束后停止。不增加巡逻、逃跑、仇恨值、新怪物或其他玩法。

教学从直接分支实现开始，再用同一套规则组织行为树，比较条件与动作、组合顺序、运行上下文、调度与清理。策划的目标是使用程序已提供的节点和参数编辑、检查和预览；新节点能力仍由程序开发。行为树不替代全部状态管理，也不要求把整个游戏流程都改成树。

项目采用 Unity 实际落地，权威怪物决策在 ET 服务端执行；Unity 用于内容制作、预览与表现。Unreal、Piccolo 保持方案讨论，不因行为树选型增加对应工程。

## 2. 备选方案与当前取舍

| 方案 | 可核对的特点 | 本项目当前取舍 |
| --- | --- | --- |
| ET10 内置行为树 | 官方列有节点、运行时、可视化编辑、参数、执行路径调试和配置代码导出 | 首选候选；优先验证实际制作与服务端运行是否满足 v0.1 |
| NPBehave | 代码式、事件驱动，官方明确没有可视化编辑功能 | 用作机制阅读对照；当前不额外接入其运行时或补建编辑器 |
| 腾讯 behaviac | 含编辑、调试、导出及 C++／C# 运行库；设计器在 Windows 运行 | 完整 AI 制作工具链的备选，需另做 ET 接入评估 |
| BehaviorTree.CPP | C++ 运行库，支持 XML、异步动作和日志，官方主要面向机器人行为 | 机制与 C++ 讨论对照，不作为当前 C#／ET 项目的默认依赖 |

以上方案说明分别见 [ET 官方项目](https://github.com/egametang/ET)、[NPBehave](https://github.com/meniku/NPBehave)、[behaviac](https://github.com/Tencent/behaviac) 和 [BehaviorTree.CPP](https://www.behaviortree.dev/)。没有开展本项目负载下的性能或易用性比较，不据此给出通用优劣排名。

ET10 使用自己的 [ET License](https://github.com/egametang/ET/blob/master/LICENSE)，不能把源码公开理解为 MIT 式自由使用；实施前核对固定版本及所需第三方插件的授权。本文不复制私有工程源码或资产，选型也不改变 Demo 工程私有的边界。

## 3. 静态核对的依据与限制

本轮核对时间为 2026-10-25，范围是 ET10 工作副本中的行为树包及其 `spell` 调用链。该副本的行为树包声明版本为 `4.0.0`；包版本不是完整源码身份，项目尚未锁定正式使用的 ET 提交、依赖和 Unity 组合。以下结论限定于本次所读源码，不推定所有 ET 版本相同。实施实验时需补齐可复现的源码标识与改动记录。

现已整理[最小接入实验设计](cooperative-dungeon-et10-behavior-tree-minimal-experiment.md)：目标源码固定到上游 `743c635dd5b0f6f6bab549c0093382c85f3f8307`，Unity `2022.3.62f3`、SDK `10.0.402`；当前包解析存在差异，必须先通过 E0。这里固定的是待执行的实验目标，不是宣称完整环境已可用或正式产品基线已锁定。

| 检查对象 | 本轮静态观察 | 不能由此推定的能力 |
| --- | --- | --- |
| `ABTHandler`、`BTDispatcher`、Sequence／Selector 处理器 | 核心执行链同步调用，以整数返回码传递结果；Sequence 遇到非零停止，Selector 遇到零停止 | 不能直接套用通用教材的 `Running/Success/Failure` 持续节点模型 |
| `spell` 的周期与协程封装 | 存在 Buff 周期调用树，以及协程取消和停止清理的代码路径 | 不代表任意长时动作都已正确中断，也不代表怪物 AI 必须绑定 Buff |
| 行为树编辑器与导出入口 | 有图形编辑代码；本次核对的具体导出入口仅收集 SpellConfig／BuffConfig | 任意怪物 AI 根节点能否编辑、校验、导出、加载，仍待实际验证 |
| 路径记录与发布 | 检查到的核心路径记录、事件发布使用 `UNITY_EDITOR` 条件 | 独立服务端结果不会因此自动传到 Unity；远程调试链路未确认 |
| `BTEnv` 运行上下文 | 存在数据存取、实体引用及回收逻辑 | 不能把树配置、各怪物运行状态与编辑器调试字段混为一份全局黑板 |

公开项目说明支持“存在这些模块与工具方向”；表中的具体执行语义来自本轮源码静态核对。由于完整实验基线尚未固定，本文不把工作副本观察写成跨版本保证，也不将文件存在写成运行通过。

ET 旧版资料中的“行为机”与 ET10 行为树分别讨论，不把异步行为机、行为树、FSM 或 GoF State 当成同一种机制。

## 4. 近战怪的候选行为树

首版建议采用“周期决策、同步叶子动作”。在服务端规则更新中选择行动，移动由规则更新推进；先不用长时间挂起的追击或等待节点。最小实验选择 50 毫秒周期驱动，具体调度注册及与其他规则更新的调用顺序待实施验证，不能为了少调用树而破坏最近选敌、攻击边界和结束判定。

下面是项目自己的语义草图，不是已导出的 ET 资产，也不是直接可运行的节点代码：

```text
前置生命周期检查：本局运行、怪物存活
  更新最近的存活玩家目标（同距按玩家实例 ID）
  按优先级选择一个分支
    无目标：停止移动
    距离不超过 1.5 米：
      停止移动
      首次等待与攻击冷却均已满足：尝试普攻
      否则：原地等待
    距离超过 1.5 米：直线追击
```

“范围内但冷却未好”是正常的等待决策，必须由该分支处理完成；不能因为攻击未执行就返回未处理，让 Selector 落到追击分支。配置缺失、无效节点或执行异常也不能伪装成普通条件不满足而被后续分支吞掉。具体项目返回码与错误分类需在接入时约定。

每次尝试攻击仍由战斗规则校验本局、施放者、目标、距离与冷却，成功后才扣血和推进冷却。不能以“行为树选中了攻击”代替最终规则校验。

## 5. 状态所有权与规则保持

| 内容 | 建议归属 | 需要保持的不变量 |
| --- | --- | --- |
| 树定义与节点参数 | 只读配置，可供 3 只同类怪复用 | 不写入某只怪物的生命、目标或冷却 |
| 本局、怪物和目标身份 | 当前怪物的业务实体与决策上下文 | 区分配置 ID、实例 ID 与局 ID，旧局消息不能操作新局 |
| 生命、攻击可用时间与首次等待 | 怪物战斗状态 | 换目标、重跑树或切换分支不重置攻击冷却 |
| 本次查询与决策数据 | 各怪物独立的运行上下文 | 不把 M01 的目标、时间或结果写到 M02／M03；实体引用按框架约定管理 |
| 移动与停止 | 当前实体的移动执行逻辑 | 范围内等待时停止移动，倒下和终局不能继续追击 |
| 调度和清理 | 明确的业务生命周期拥有者 | 倒下、测试中止、结束、销毁、重开时停止后续决策并清理资源；重复清理也安全 |

服务端业务身份从业务实体传递，不依赖仅用于 Editor 调试的字段。首个同步实验不引入长期异步节点；如果以后采用已有协程机制，须单独验证取消、回调、上下文所有权及 `await` 后实体有效性，不能把启动协程当成完成动作。

v0.1 参数保持不变：怪物生命 100、移速 2 米／秒、攻击 10 点、射程 1.5 米；首次攻击不早于本局运行满 2 秒，成功后再冷却 2 秒。固定 3 怪、5 个出生点、玩家与技能数值、失败优先和测试徽记规则，均以 [最小玩法规则 v0.1](cooperative-dungeon-minimal-gameplay-rules-v0.1.md) 为准。

## 6. 策划制作与运行观察管线

计划管线为：选择已有节点与参数 → 结构、引用和输入输出校验 → 保存 → 导出完整候选配置 → 服务端采用对应版本 → 单项预览 → 双人流程回归。

先验证已有编辑与 Spell／Buff 导出链路能否覆盖这个最小案例，再决定沿用、增加有限适配或回退直接分支；不预先新增通用图编辑器或一套并行导出框架。用于实验的 Buff 驱动方式不自动变成项目领域模型，也不把怪物 AI 规定为 Buff。

计划提供的能力是：策划可独立组合已暴露节点、调整已支持参数并看到校验与运行结果；新行为能力、根节点类型或当前链路不支持的交互需要程序参与。数据导出成功仍要确认服务端实际采用的版本，失败不能采用半套数据。Luban 的结构化参数与图形配置的权威来源、引用和生成关系需要明确，不维护两份可分别修改的同一规则。

观察分两条验证：Editor 中运行的路径显示，以及独立服务端的日志／轨迹。若需要在 Unity 显示服务端执行路径，单独设计传输与关联方式，记录局 ID、怪物实例、树与配置版本、决策顺序和时间；没有实现前，不标为现成远程调试能力。缺少远程图形显示时，可以先用可关联日志验证服务端规则，但必须明确可视化链路仍未覆盖。

## 8. 采用门槛、回退与教学产出

只有相关制作、导出、服务端规则、实例隔离与生命周期验证有实际证据，且调试覆盖范围明确后，才评审是否把状态从“首选候选”改为“已采用”。代码存在、图能保存、一次 Editor 预览或选型文档发布，都不是采用验收。

若现有导出模型、调度或节点语义需要大量额外建设，记录具体缺口与最小适配成本，再比较直接分支和其他候选；不为了证明已选方案正确而扩充玩法或重建通用工具。保留直接分支作为教学对照和可选回退，实现路径变动不改 v0.1 的预期结果。

教学产出应让读者解释：条件与动作怎样分工；Sequence／Selector 的结果怎样影响后续分支；为何等待不能落入追击；树定义、上下文、战斗状态和生命周期分别由谁持有。组合节点可以用于讨论 Composite，调度与取消可以对照行为机或 FSM，但不能只凭“树”或“状态”名称判定 GoF 模式。

最小树、9 个同步业务节点、配置导出和阶段验证已形成实验设计。下一步先执行 E0 核对环境，再按 E1～E6 实施；结果继续回流 BT01～BT10，不能把实验文档完成当作采用通过。当前待实施、待验证，未修改 ET 工程或运行游戏。
