# 无尽对决：项目整体规划、工种管线与专栏映射

项目名称：无尽对决。以两人合作副本为起点，设计公开，Demo 工程私有。

日期：2026-10-25（Asia/Shanghai）
状态：规划初稿。目标来自本轮讨论；工具、系统和验收要求均为待实施设计，不代表已有能力。
用途：为项目负责人、策划、美术、程序和测试建立共同基线，后续据此拆分设计与实施任务。

## 1. 项目定位与已确定目标

以两人合作副本为起点，持续演进为可上线运营的游戏，并作为 TechStackShow 各专栏共同的工程案例。项目同时交付可玩的内容、可重复的生产流程，以及有源码和实验依据的文章。

### 1.1 已确定的要求

| 项目 | 本轮确定的要求 |
| --- | --- |
| 游戏方向 | 两人合作副本，后续面向上线运营 |
| 技术组成 | Unity、UGUI、ET、Luban、YooAsset、HybridCLR |
| 首阶段 | 先以 Unity Editor 为主要入口，跑通完整游戏流程和内容制作流程 |
| 平台方向 | 从设计之初考虑 Windows、Android、iOS 和小游戏，分别实现和验收 |
| 策划自主能力 | 独立配置技能、怪物、关卡和奖励，修改后在 Editor 验证 |
| 美术自主能力 | 独立替换模型、动画、特效和 UI，修改后在 Editor 验证 |
| 专栏关系 | 同一个项目贯穿玩法、框架、工具、生产、交付、性能及运营主题 |

“独立”指在已提供的行为能力与资源约定范围内，无需程序逐次修改代码或手工绑定。“Editor 验证”指保存、检查、生成或导入、进入预览或运行并确认结果；不预设所有内容能在 Play 中即时刷新。

### 1.2 本文建议与尚未确定事项

建议采用完整内容逐步推进的方式：每轮制作一段可以体验和验收的内容，同时打通相关工种的交接。建议先用状态同步完成副本主线，帧同步另做有边界的对照实验；这项同步方案仍待详细设计确认。

尚未确定：画面维度、视角、操作方式、美术风格、渲染方案、完整战斗规则、具体小游戏平台、技术版本和性能预算。本文的实体名称、字段和工具入口是设计示意，不是现有 API 或最终数据结构。

## 2. 组织方式与取舍

| 方式 | 优点 | 代价与适用边界 |
| --- | --- | --- |
| 分别完成各基础系统，再集中集成 | 可集中研究单个系统 | 较晚发现配置、资源、玩法和多人运行之间的交接问题 |
| 按完整内容逐步推进（本文建议） | 每轮都能观察玩家结果与生产流程，容易形成完整文章案例 | 需要控制内容规模，避免过早扩展通用工具和框架 |

本轮用户要求按已讨论目标形成规划，本文沿第二种方式展开，细节仍供评审。主题实验用于解决明确问题，验证后再进入游戏主线；不要求所有研究方向成为正式运营版本的运行依赖。

首个内容切片建议为：一个可操控角色、一项技能、一类怪物、一段关卡和一项奖励。数量是控制首轮规模的建议，后续再扩展成完整两人副本。

## 3. 玩家流程、制作流程与学习产出

### 3.1 完整玩家流程

启动与内容准备 → 登录 → 大厅 → 组队与准备 → 进入副本 → 合作战斗 → 胜利或失败 → 结算与存档 → 返回大厅 → 再次进入。

详细设计还需确定掉线等待、退出、死亡、复活、团灭、重连、重复领奖和服务端重启等规则。正常流程及对应异常路径都进入验收，避免仅按一次成功通关判断完成。

### 3.2 完整制作流程

提出体验目标 → 约定规则与表现 → 策划配置／美术制作／程序补充能力 → 本地检查与预览 → 提交 → 集成检查 → 双客户端验收 → 构建候选版本 → 发布与反馈 → 修改源内容并复验。

早期由同一人兼任多个角色时，也按这些交接走一遍。角色能够自行发现、定位和修正常见问题，是生产流程的验收内容。

### 3.3 每轮应形成的三类产物

1. 游戏产物：可体验的功能或内容，以及可定位的版本。
2. 生产产物：源数据、源资源、制作约定、工具与检查、交接及验收记录。
3. 学习产物：问题说明、固定版本的源码路线、实验和实际结果，再回写对应专栏。

## 4. 技术职责与系统边界

| 技术或模块 | 计划职责 | 需要另行设计或验证的部分 |
| --- | --- | --- |
| Unity＋UGUI | 表现、交互、场景、界面和 Editor 制作预览 | UI 绑定、生命周期、适配及预览工具 |
| ET | 客户端与服务端组织、通信、实体及业务运行 | 合作副本、战斗、结算、持久化及异常恢复的具体实现 |
| Luban | 配置定义、生成、数据装载相关工具链 | 本项目的数据模型、业务与资源引用检查、策划操作入口 |
| YooAsset | 资源采集、构建、加载、释放、下载和资源更新 | 内容标识映射、分包、资源所有权、失败恢复与多平台配置 |
| HybridCLR | 热更新代码相关运行与加载能力 | AOT 边界、代码组织、版本配套与各目标平台的能力验证 |
| 项目制作工具 | 预览、配置检查、资源检查和本地运行入口 | 依据首个内容切片逐步实现，先复用可用工具 |
| 服务端业务与数据 | 战斗规则、奖励判定、玩家状态、持久化 | 权威边界、幂等、断线与重启后的恢复规则 |

这些组件共同构成技术方向，不等于已经完成集成。Luban 不承担全部玩法编辑能力，YooAsset 不决定游戏规则，HybridCLR 不替代整套发布与兼容设计。

服务端拥有联机战斗与奖励的最终判定权是本文建议的初始边界。客户端预览用于内容调试，不能替代服务端规则和多人一致性验收。

## 5. 各工种职责与交接

| 角色 | 主要职责 | 交付物 | 接收方与验收重点 |
| --- | --- | --- | --- |
| 策划 | 体验、规则、技能、怪物、关卡、奖励和数值 | 规则说明、配置源文件、测试场景与预期 | 程序确认能力边界，美术确认表现要求，测试确认可判定的结果 |
| 美术 | 视觉方向、模型、动画、特效、UI 的制作与替换 | 制作源文件、交换文件、引擎资产、表现配置与预览记录 | 策划确认信息和体验，程序／技术美术确认接口，测试确认完整场景结果 |
| 程序／技术美术 | 系统能力、数据定义、资源约定、工具和运行诊断 | 实现、编辑入口、自动检查、示例、报错与操作说明 | 策划和美术能独立完成规定范围内的日常修改 |
| 测试 | 正常和异常路径、多人结果、数据与平台验收 | 用例、版本与环境、实际结果、复现材料 | 缺陷能回到具体源数据、资源、工具或实现并复验 |
| 项目／发布负责人 | 内容范围、集成、候选版本、验收与发布 | 版本内容清单、制品、检查结果、验收与恢复方案 | 内容和版本配套明确，发布结果可追踪 |

规则、视觉质量、技术可用性和设备性能分别验收。自动检查能发现结构问题，体验、美术质量和合作乐趣仍需要试玩与评审。

## 6. 策划工作管线

### 6.1 独立配置的范围

| 内容 | 首阶段提供的配置能力（建议） | Editor 验证方式 | 仍需程序参与的情况 |
| --- | --- | --- | --- |
| 技能 | 消耗、冷却、目标、范围、已有行为组合、效果与表现引用 | 指定角色／目标的技能测试，查看事件和数值，再做双端检查 | 新的行为类型、目标规则或尚未支持的交互 |
| 怪物 | 属性、已有 AI 行为参数、技能组合、模型表现与掉落引用 | 生成指定怪物，观察状态、施法、受击、死亡和清理 | 新 AI 能力、移动方式或战斗机制 |
| 关卡 | 出生点、怪物波次、已有触发条件、目标、胜负与奖励引用 | 指定关卡启动、测试检查点和重置，最终走完整流程 | 新触发器、新目标类型或尚未支持的场景交互 |
| 奖励 | 奖励组、数量、权重、条件和发放规则参数 | 模拟结果用于检查，再用服务端验证结算、写入和重复请求 | 新奖励类型、新经济规则或发放事务要求 |

关卡的复杂空间编排可以使用 Unity 场景或受约束的编辑数据；具体形式待玩法确定。Luban 承接适合表格或结构化数据的部分，不强行把全部关卡制作压入表格。

### 6.2 日常操作顺序

1. 按字段说明修改配置源文件，选择要验证的技能、怪物或关卡。
2. 执行配置检查：类型与范围、ID 唯一性、引用、循环或业务约束、资源标识和两端可用性。
3. 通过后生成一套完整的候选数据；失败时保留上一套可运行数据，防止半套生成物进入预览。
4. 在本地测试环境中让客户端和服务端采用配套的数据快照，界面显示当前配置版本。
5. 启动对应预览，完成本项检查，再进入副本或双客户端验收。
6. 提交源数据及需要纳管的相关定义与记录；生成物是否入库由后续仓库规则决定。

首阶段允许以重新进入 Play 或重启本地测试服完成数据采用。“保存后直接验证”不要求无条件在线替换数据。若后续实现运行中重载，需要另行定义安全边界、失败恢复与两端一致性。

### 6.3 工具与错误反馈要求

策划至少能发起配置检查、生成并进入预览、指定关卡启动、重置测试状态和查看运行数据版本。入口名称与 UI 待实现设计。

错误应说明源文件、表或记录、字段、错误引用、期望条件和修正方式。例如指出某技能引用了不存在的表现标识，而不是只返回“导出失败”。导出成功后仍需业务和运行验证。

## 7. 美术工作管线

### 7.1 独立替换的范围与约定

| 内容 | 保持稳定的约定 | 允许独立替换的内容 | 检查与预览 |
| --- | --- | --- | --- |
| 模型 | 单位与朝向、根节点、骨骼或重定向要求、挂点、表现组件接口 | 符合约定的新模型、材质、贴图和外观组合 | 静态预览、动作、挂点、受击与死亡；骨骼不兼容时明确报错 |
| 动画 | 动作语义、状态与参数接口、时序配置、位移和打断约定 | 兼容的动画片段及已暴露的表现参数 | 移动、施法、取消、受击、死亡与恢复，核对实际技能时序 |
| 特效 | 挂载位置、触发语义、持续／停止、对象复用与清理接口 | 特效 Prefab、材质、贴图及表现参数 | 播放、提前取消、目标销毁、重复使用和场景退出后的清理 |
| UI | UGUI 视图绑定、必需组件、交互事件、布局与生命周期接口 | 图片、字体、布局、动效和符合视图约定的 Prefab | 指定窗口、模拟数据与状态、多分辨率、重复开关及场景切换 |

“独立替换”依赖已定义的兼容范围。新增骨骼体系、改变技能规则时序、移除 UI 必需绑定或增加交互逻辑，需要协作修改约定和实现。UI 绑定方式、动画编辑与事件表达方式尚未选型，不预设复杂节点改动也能自动兼容。

### 7.2 从制作到运行

1. 按需求和初步规格制作，版本化保存制作源文件与导出设置；具体制作软件未定。
2. 导出交换资源，按约定导入 Unity；通过预设或工具维护导入设置与平台差异。
3. 检查依赖、材质、贴图、组件、骨骼／挂点、资源标识、UI 绑定等。
4. 在资源预览入口确认单项效果，再替换表现绑定并进入实际技能、怪物或关卡预览。
5. 策划检查信息传达与玩法配合，美术检查质量，程序／技术美术检查生命周期和成本。
6. 提交完整依赖及相关 Unity `.meta`，附上预览范围和已知问题，进入集成与副本验收。

源文件、交换文件、Unity 资产和构建制品分别标明归属与生成关系。不能只交付本机可见的 Prefab，遗漏其动画、材质、贴图、字体或 Shader 依赖。

### 7.3 制作预算与质量

按角色、场景、特效和 UI 定义初步规格与检查，但本文不填写尚无设备与玩法依据的面数、贴图或帧率数字。资源单项通过后，还要在两人战斗、技能叠加和真实目标设备上测量，再调整预算。

美术预览不要求使用真实账号或正式奖励数据；测试数据与正式内容分开标识，不能被误当作可发布内容。

## 8. 内容标识、数据版本与质量检查

### 8.1 跨系统连接

建议用稳定的逻辑标识连接技能、怪物、关卡、奖励与客户端表现。例如“技能 → 表现定义 → 模型／动画／特效资源标识”。具体数据结构在详细设计中确定。

逻辑内容 ID、Unity GUID、YooAsset 加载地址和构建内容 Hash 各有用途，不混作同一个标识。资源重命名、迁移、删除和替换要有引用检查；映射既能支持自动校验，也应让使用者定位到实际资源。

服务端消费规则所需数据，客户端消费交互与表现所需数据，公共定义按需要共享。是否将客户端生成数据通过 YooAsset 分发，待配置体积、采用方式和版本关系明确后决定；服务端数据随相应服务端发布流程管理。

### 8.2 检查位置与责任

| 环节 | 检查重点 | 失败后回到哪里 |
| --- | --- | --- |
| 本地编辑／导出／导入 | 格式、ID、资源依赖、绑定、必要规格 | 策划源数据、美术源资源或工具定义 |
| 提交后的集成 | 干净环境可重现、两端生成、编译、跨内容引用 | 本次变更及负责工种；展示具体错误与责任入口 |
| 运行验收 | 规则与表现、多人一致性、数据写入、取消和恢复 | 对应配置、资源、系统或规则设计 |
| 候选版本 | 制品完整、内容范围、版本配套、平台与更新流程 | 构建输入、发布配置或候选内容 |

必须修复的问题与建议优化的问题分别报告。明确的损坏、缺引用或不兼容阻止对应步骤；体验与成本问题按预算和评审处理，避免所有警告都阻塞日常工作。

### 8.3 共同版本记录

一次可运行组合记录代码提交、配置数据版本、资源版本、服务端版本、协议兼容信息、目标平台和检查结果。字段与兼容规则待详细设计。预览应显示实际采用的版本，避免源文件已改而运行环境仍使用旧数据。

出现失败时回到上一套已知可用内容或停止采用新内容；涉及玩家已写入的数据，需要独立的数据兼容与恢复方案，不能假定回退文件即可回退玩家状态。

## 9. Editor 验证与多平台设计

### 9.1 Editor 首阶段的验收

| 验证层次 | 要看到的结果 | 不能据此推定的结果 |
| --- | --- | --- |
| 单项预览 | 指定技能、怪物、关卡、模型、动画、特效或 UI 的修改可见且可定位 | 完整联机和正式平台运行均正确 |
| 完整流程 | 启动至返回重进可重复；失败有反馈，资源和异步工作可清理 | 两名玩家的结果一致 |
| 双客户端会话 | 两个独立客户端会话完成组队、副本和结算，核对一致性与异常路径 | 目标设备的网络、性能和平台生命周期已通过 |
| 更新实验 | 用实际构建制品区分旧、新内容，记录下载、采用和恢复结果 | Editor 模拟加载等同于 Player 的资源和代码更新 |

Editor 作为主要调试入口，独立服务端按需要启动。两个客户端会话采用多 Editor、Editor 配合本地客户端或其他方式，实施时选择并记录；单进程操控两个角色不能替代独立会话验收。需要 Player 才能验证的行为安排专项构建，不把它伪装为 Editor 已验证能力。

### 9.2 从设计起保留的平台边界

输入、视图适配、文件与缓存、网络传输、生命周期、平台账号能力、资源与代码更新、构建参数分别划清职责。Windows、Android、iOS 和小游戏共享可共享的业务定义，平台实现与验收单列。

小游戏具体平台与宿主未定；HybridCLR、网络和资源能力在各平台的组合仍需核实和实验。本文不承诺各平台使用完全相同的实现。移动端触摸操作、切后台、内存和小游戏启动缓存等要求进入设计，不能等 Editor 完成后才开始考虑。

## 10. 项目阶段与完成条件

以下各阶段均为待实施规划，没有承诺日程。采用“待设计／待实现／待验证／已验证”分别记录能力状态，已验证项必须链接到实际证据。

| 阶段 | 玩家或内容结果 | 工种与工程结果 | 完成条件 |
| --- | --- | --- | --- |
| P0 共同设计与基线 | 确定最小合作体验和内容切片 | 盘点现有工程，锁定版本与来源，确定规则／资源／数据约定 | 规则、范围、职责、待定项和验收目标明确，后续拆实施任务 |
| P1 最小制作流程 | 技能、怪物、关卡、奖励和表现形成一段可试玩内容 | 策划与美术完成各自独立操作，错误可定位，可采用一致数据 | 第 11 节的 P1 操作有实际记录；关卡与奖励使用最小测试入口验收 |
| P2 Editor 完整副本 | 两人完成大厅、组队、战斗、胜负、结算、存档、返回重进 | 双客户端验收，重复领奖、断线、清理与重启读取有规则和证据 | 正常循环可重复，已约定异常路径经过验证 |
| P3 内容与版本迭代 | 新内容和修复能够通过实际版本升级交付 | 代码、资源、配置、服务端及兼容规则配套；更新失败可恢复 | 保存旧、新制品与采用回执，完成兼容和失败实验 |
| P4 多平台交付 | 各平台完成同一核心副本体验 | 各平台单独构建、设备与生命周期测试及性能评估 | 每个平台有独立结果；具体小游戏平台明确后单列验收 |
| P5 上线准备与持续运营 | 有稳定的玩家流程及后续内容迭代方式 | 环境部署、账号与数据、监控诊断、备份恢复、运营操作、发布管理 | 有发布条件、职责、故障处理与恢复演练；外部上线要求另行核实 |

状态同步与帧同步的对照研究按学习问题安排，不默认要求正式版本同时维护两套完整战斗实现。商业化方式、支付、社交和复杂成长系统没有在本轮确定，后续按产品目标单独评审。

## 11. 自主制作与集成的验收任务

前提是程序已交付相应能力、工具、示例和字段／资源约定。验收时让操作者从文档入口独立完成，不由程序在后台补绑定或手改生成物。

P1 通过技能、关卡和奖励的最小测试入口验收制作能力，奖励测试使用固定测试玩家。下表除明确标注 P2 的部分外，均为 P1 目标。完整登录、组队、副本循环，以及重新登录和服务端重启后的玩家数据恢复归入 P2，避免把完整游戏系统提前作为 P1 的前置条件。

| 编号 | 操作 | 必须观察和保存的结果 |
| --- | --- | --- |
| D1 技能 | 修改冷却或伤害，再用已有行为组成一项测试技能 | 检查通过、版本采用明确、预览和服务端结果符合规则；无代码修改 |
| D2 怪物 | 创建怪物配置并组合已有技能／AI 参数 | 正确生成、施法、受击、死亡和清理，能定位配置与表现 |
| D3 关卡 | 修改波次、出生位置、目标与奖励引用 | P1：指定关卡启动、胜负、重置与退出重进符合预期；P2：从大厅进入并完成整个玩家循环 |
| D4 奖励 | 修改奖励组及数量，在本地测试环境结算 | P1：服务端结果、重复请求幂等及固定测试玩家的写入／读回正确；P2：重新登录／服务端重启后按规则恢复 |
| A1 模型 | 替换兼容模型及依赖 | 比例、材质、骨骼／挂点和实际动作正确，不需要程序重新接线 |
| A2 动画 | 替换兼容动作 | 开始、打断、恢复和与技能表现的配合正确；规则时序变更需协作 |
| A3 特效 | 替换技能特效 | 触发、挂载、停止、复用和离场清理符合约定 |
| A4 UI | 替换约定窗口的视觉资源、布局或兼容 Prefab | 数据显示、按钮行为、绑定检查、多分辨率与重复开关正常 |
| E1 无效修改 | 分别制造错误配置引用和缺失资源／UI 绑定 | 阻止采用损坏内容，定位源头并给出修正方向；修正后可复验 |
| E2 一致采用 | 修改数据后故意让本地服务端仍使用旧版本 | 能观察版本不一致，并按设计拒绝或纠正；不能悄悄混用 |

测试奖励与测试账号仅用于隔离的本地环境。奖励抽样预览不等于概率分布已经得到统计验证，实际发奖与持久化也必须单独检查。

### 12.1 用共同变更串联文章

“新增一个 Boss”贯穿规则设计、怪物／技能／关卡配置、美术与 UI、双端战斗、资源加载、结算、性能和发布。“修复一个奖励问题”贯穿配置语义、服务端判定、幂等、数据恢复、版本兼容及回归。

每篇只回答自己的核心问题，并链接共同案例与前后环节。项目总览维护整条链路，源码文章解释机制，实验记录提供证据；不把同一篇正文复制到不同专栏。

### 12.2 证据回流

每项工作记录：学习与产品问题、固定版本、源内容与改动、操作者、输入和环境、预期、观测方法、实际结果、失败路径、验证边界及对应文章。分清源码推导、模拟预览、Editor 运行、Player／真机结果和线上结果。

技术栈采用某组件，不等于已获得其全部能力；文章已发布，也不等于本项目已完成对应实现。历史测量和示例需标明来源、版本与实验环境，不直接转写成新项目成绩。

### 12.3 设计模式融入合作副本

2026-10-25 补充：设计模式的应用与验证安排在本项目内，沿用 Unity、UGUI、ET、Luban、YooAsset、HybridCLR 的既定方向。以下是候选研究安排，具体采用哪种模式仍由需求和实验决定；未实现、未运行验证。

教科书保留引擎无关的最小 C# 示例，应用文章回到合作副本的实际变更。可以在同一项目的测试场景或独立实验中保留直接实现与候选实现，正式游戏只维护选定方案。Game Framework、QFramework 等按具体问题作为外部阅读对照，不因设计模式教学增加项目框架依赖。

| 项目中的变化或问题 | 候选设计与比较重点 | 要观察或验证的结果 |
| --- | --- | --- |
| 策划增加技能目标规则或已有行为组合 | 参数化／数据驱动与 Strategy 的边界；新增行为能力由程序提供 | 参数修改能直接预览；增加第二种规则时确认修改范围、旧规则回归及双端结果 |
| 怪物进入施法、受击、死亡，或副本阶段发生转换 | 显式分支、State 对象与 FSM 的适用边界；行为树按实际复杂度另议 | 非法转换、施法打断、死亡后的回调及退出重进有明确结果 |
| 击杀后更新任务、HUD 和表现 | 直接调用与 Observer／事件通知的比较；本地通知与网络消息分开 | 窗口反复开关不重复订阅，场景退出后无残留响应；服务端结算仍独立验收 |
| 玩家发起操作，测试需要记录或延迟执行 | 直接调用与 Command 的比较，区分操作意图、传输协议与服务端校验 | 非法、重复或过期请求按规则处理；命令封装本身不保证幂等、确定性重放或网络撤销 |
| 美术替换 UGUI 外观，策划调整展示数据 | 视图与业务职责拆分，比较 MVP 与现有 ET 组织方式 | 兼容替换无需修改业务规则；绑定缺失可定位，关闭窗口后异步结果不再写入失效视图 |
| 创建怪物、特效和飘字，随后销毁或复用 | 创建职责／Factory 候选、对象池与直接创建销毁的比较 | 重置、取消、回收和再次使用正确；在一致负载下测量收益与成本，不以使用对象池推定更快 |
| 业务使用资源加载与平台能力 | 按真实变化点判断 Adapter、Facade 或直接调用是否更合适 | 加载失败、取消和释放可追踪；封装后仍能表达 YooAsset 句柄所有权及平台差异 |
| 策划检查与生成、美术导入检查、构建任务增加步骤 | 顺序函数、Pipeline 与 Template Method 的比较 | 错误定位到源内容，失败不采用半套产物；有固定骨架与替换步骤时再讨论模板方法 |

所有候选都要先明确状态归属、依赖方向和作用域。ET 实体、组件、消息及异步工作沿所选版本的机制组织，具体行为通过源码和实验核对；需要纯 C# 规则对象时说明其调用边界，不另外复制一套实体生命周期。SOLID、DI、对象池、ECS、Actor、Fiber 与 GoF 模式分别归类；不凭组件名称判定模式。

阶段上，P1 优先覆盖技能规则变化、视图／表现替换和创建清理，服务于策划、美术的独立制作验收；P2 随完整副本补状态转换、事件／消息、异步作用域与失败路径；P3／P4 再随内容迭代和多平台接入研究扩展、适配与生产流程。阶段编号沿用第 10 节，不表示这些模式已经选定，也不要求每个候选都进入正式实现。

每个案例记录“原始需求 → 直接实现 → 新需求或失败 → 候选方案 → 选用或拒绝的理由 → 实际验证与成本”。案例可同时支撑多篇既有文章；篇目与状态仍由设计模式主规划维护，项目规划只登记承载场景。首个案例建议沿 P1 技能制作流程展开，在第二种规则出现时比较配置参数和策略扩展的边界。

### 13.1 现有资料与归属

- TechStackShow 维护本文、学习目标、系列规划和公开文章；本文衔接[既有全栈学习提纲](fullstack-framework-learning-outline.md)，补充产品演进与工种生产要求。

### 13.2 下一轮需要完成的设计

1. 确定视角、操作、合作价值与最小战斗规则，形成第一段可试玩内容的规则说明。
2. 盘点学习工程可复用部分，选择并锁定 Unity、ET 和各组件版本，确认程序集与更新边界。
3. 详细设计技能、怪物、关卡、奖励数据与表现标识，约定程序扩展点和策划可配置范围。
4. 明确模型、动画、特效和 UGUI 的资源与绑定约定，选择最小预览与检查工具。
5. 设计客户端／服务端数据采用、双会话运行、本地测试数据、日志与验收入口。
6. 明确首个小游戏平台和平台能力矩阵，按玩法和目标设备建立可测量的预算。
7. 根据评审后的设计拆解 P1 实施任务，再逐步完善副本、发布与运营要求。

本轮只形成整体规划。上面的待定项可分阶段解决，不以补齐所有远期运营细节为开始最小内容制作的前提；也不把未确定的设计选择写成已经达成的决定。
