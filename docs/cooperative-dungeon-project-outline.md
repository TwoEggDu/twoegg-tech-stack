# 无尽对决：项目整体规划、工种管线与专栏映射

项目名称：无尽对决。以最小两人合作流程承载教学，设计公开，Demo 工程私有。

日期：2026-10-25（Asia/Shanghai）
状态：规划初稿。目标来自本轮讨论；工具、系统和验收要求均为待实施设计，不代表已有能力。
用途：为项目负责人、策划、美术、程序和测试建立共同基线，后续据此拆分设计与实施任务。

## 1. 项目定位与已确定目标

2026-10-25 最新范围：教学优先，简单的游戏过程用于承载并验证各专栏知识。此前上线运营设想放到远期，不作为当前验收条件。每个功能必须有教学目标与验证内容，能复用现有小场景时不扩充玩法规模。

### 1.1 已确定的要求

| 项目 | 本轮确定的要求 |
| --- | --- |
| 游戏方向 | 一张斜俯视场地，两名角色，一种怪物，一种测试奖励；先完成最小教学版本 |
| 技术组成 | Unity、UGUI、ET、Luban、YooAsset、HybridCLR |
| AI 选型状态 | ET10 内置行为树为首选候选，待制作导出、服务端运行与生命周期验证；工程 ET 版本及依赖尚未正式锁定 |
| 引擎分工 | Unity 实际落地并承担项目验收；Unreal、Piccolo 仅讨论对应方案与机制，不纳入项目实施计划 |
| 首阶段 | Unity Editor 先完成单项制作预览，再验证最小双人流程 |
| 平台方向 | 从设计之初考虑 Windows、Android、iOS 和小游戏；平台交付属于按需专项，不是最小版前置条件 |
| 策划自主能力 | 独立配置技能、怪物、关卡和奖励，修改后在 Editor 验证 |
| 美术自主能力 | 独立替换模型、动画、特效和 UI，修改后在 Editor 验证 |
| 专栏关系 | 同一个项目贯穿玩法、框架、工具、生产、交付、性能及运营主题 |

“独立”指在已提供的行为能力与资源约定范围内，无需程序逐次修改代码或手工绑定。“Editor 验证”指保存、检查、生成或导入、进入预览或运行并确认结果；不预设所有内容能在 Play 中即时刷新。

### 1.2 最小规则、教学目标与待定事项

移动、普攻、各一个主动技能；A 施加标记，B 消耗有效标记产生额外伤害。清怪且至少一人存活获胜，全员倒下失败，同一步失败优先；显示一次本局结果和测试奖励，返回后重开。暂不加入复杂 Boss、机关、职业、装备、成长、闪避或救援／复活。

逐项功能编号、教学目标和计划验证统一维护在[引擎无关总览第 3 节](cooperative-dungeon-engine-independent-overview.md#3-功能教学目标与验证内容)的 T01～T18 表。本规划按该表拆阶段与工种交接，不另建一套不同的功能清单。

[最小玩法规则 v0.1](cooperative-dungeon-minimal-gameplay-rules-v0.1.md)已确认，作为本轮玩法基线：自动选取 6 米内目标；A 标记 5 秒、冷却 6 秒；B 优先标记目标，基础 20、额外 30，冷却 4 秒。无目标不进冷却；同一步全员倒下优先失败；胜利两人各 1 枚测试徽记、失败／中止 0。断线中止、同局一次性结算、返回保留内存累计与服务重启清零均已确定。

基础参数与关卡已确认：两人生命 100、移速 4 米／秒，普攻 10 点／1 秒；3 只同类近战怪各生命 100、移速 2 米／秒，攻击 10 点／2 秒、射程 1.5 米，首击等待 2 秒。场地 18×18 米，地面坐标 x／z 均在 -9～9、1 单位=1 米；A／B 于 (-1,-4)／(1,-4)，3 怪于 (-2,0)、(0,1)、(2,0)，距离按地面中心计算。

该文档的 V01～V31 用例细化 T01～T18 中相关规则，不替代资源、美术与全部制作验收。输入映射、镜头具体角度、移动与边界实现、测试入口、美术风格及技术版本仍待设计。所有游戏验证待执行。

### 1.3 行为树候选与验证门槛

[ET10 内置行为树候选评估](cooperative-dungeon-et10-behavior-tree-evaluation.md)记录静态依据、近战怪同步决策设计与 BT01～BT10 待执行计划。行为树只组织现有最近选敌、追击、范围内停止与等待、攻击尝试，不改 v0.1 的数值、出生点、胜负或奖励。

需分别验证编辑保存／导出／加载、独立服务端执行、各怪物上下文隔离、2 秒首击和冷却、生命周期清理及调试可见性。现有具体导出链主要围绕 Spell／Buff，路径记录含 Editor 条件，不能推定任意怪物 AI 导出和服务端远程图形调试已经可用。候选不自动升级为正式依赖；可保留直接分支对照与回退。

## 2. 组织方式与取舍

| 方式 | 优点 | 代价与适用边界 |
| --- | --- | --- |
| 分别完成各基础系统，再集中集成 | 可集中研究单个系统 | 较晚发现配置、资源、玩法和多人运行之间的交接问题 |
| 按完整内容逐步推进（本文建议） | 每轮都能观察玩家结果与生产流程，容易形成完整文章案例 | 需要控制内容规模，避免过早扩展通用工具和框架 |

本轮用户要求按已讨论目标形成规划，本文沿第二种方式展开，细节仍供评审。主题实验用于解决明确问题，验证后再进入游戏主线；不要求所有研究方向成为最小教学版的运行依赖。

首个内容范围固定为两名测试角色、一种普通怪、一张场地和一种测试奖励，以标记与消耗连接技能。单项入口可先用一个客户端预览，双人规则另用两个独立客户端会话验证。复杂内容只在教学问题确有需要时新增。

## 3. 玩家流程、制作流程与学习产出

### 3.1 完整玩家流程

进入 → 清怪 → 简单结算 → 返回 → 重开。测试身份与简化进入入口足够；真实登录、正式大厅、匹配和完整存档另做专项。

最小版固定倒下与结束状态、一次性结算及重开清理，并补齐无效操作和迟到回调验证。完整断线重连、复活救援与服务端重启持久化不属于最小循环前置条件。

### 3.2 完整制作流程

提出教学问题 → 约定规则与表现 → 策划配置／美术制作／程序补充能力 → 本地检查与预览 → 对应阶段验收 → 记录反馈 → 修改源内容并复验。

P1 完成单项制作预览，P2 完成双客户端集成验收。构建候选版本、平台发布及恢复只在对应 X 专项中执行，不要求每轮内容制作都发布 Player 或线上版本。

早期由同一人兼任多个角色时，也按这些交接走一遍。角色能够自行发现、定位和修正常见问题，是生产流程的验收内容。

### 3.3 每轮应形成的三类产物

1. 游戏产物：可体验的功能或内容，以及可定位的版本。
2. 生产产物：源数据、源资源、制作约定、工具与检查、交接及验收记录。
3. 学习产物：问题说明、固定版本的源码路线、实验和实际结果，再回写对应专栏。

## 4. 技术职责与系统边界

| 技术或模块 | 计划职责 | 需要另行设计或验证的部分 |
| --- | --- | --- |
| Unity＋UGUI | 表现、交互、场景、界面和 Editor 制作预览 | UI 绑定、生命周期、适配及预览工具 |
| ET | 客户端与服务端组织、通信、实体及业务运行 | 合作副本、战斗、结算、持久化及异常恢复的具体实现 |
| Luban | 配置定义、生成、数据装载相关工具链 | 本项目的数据模型、业务与资源引用检查、策划操作入口 |
| YooAsset | 资源采集、构建、加载、释放、下载和资源更新 | 内容标识映射、分包、资源所有权、失败恢复与多平台配置 |
| HybridCLR | 热更新代码相关运行与加载能力 | AOT 边界、代码组织、版本配套与各目标平台的能力验证 |
| 项目制作工具 | 预览、配置检查、资源检查和本地运行入口 | 依据首个内容切片逐步实现，先复用可用工具 |
| 服务端业务与数据 | 最小战斗规则、本局状态和一次性测试结算 | 权威边界与重复请求；持久化、重连和重启恢复按需专项验证 |

这些组件共同构成技术方向，不等于已经完成集成。Luban 不承担全部玩法编辑能力，YooAsset 不决定游戏规则，HybridCLR 不替代整套发布与兼容设计。

v0.1 已确定服务端拥有联机战斗与奖励的最终判定权，同步组织和具体实现仍待设计。客户端预览用于内容调试，不能替代服务端规则和多人一致性验收。

| 角色 | 主要职责 | 交付物 | 接收方与验收重点 |
| --- | --- | --- | --- |

| 美术 | 视觉方向、模型、动画、特效、UI 的制作与替换 | 制作源文件、交换文件、引擎资产、表现配置与预览记录 | 策划确认信息和体验，程序／技术美术确认接口，测试确认完整场景结果 |
| 程序／技术美术 | 系统能力、数据定义、资源约定、工具和运行诊断 | 实现、编辑入口、自动检查、示例、报错与操作说明 | 策划和美术能独立完成规定范围内的日常修改 |

规则、视觉质量、技术可用性和设备性能分别验收。自动检查能发现结构问题，体验、美术质量和合作乐趣仍需要试玩与评审。

## 6. 策划工作管线

### 6.1 独立配置的范围

| 内容 | 首阶段提供的配置能力 | Editor 验证方式 | 仍需程序参与的情况 |
| --- | --- | --- | --- |
| 技能 | 标记与消费行为已暴露的持续、冷却、额外伤害和表现引用；以 v0.1 为基线，实验变体注明版本 | 指定角色／目标测试，观察状态、消费和数值，再做双端检查 | 新行为类型、目标规则或尚未支持的交互 |
| 怪物 | 一种普通怪的属性、已有简单行为参数、模型表现引用 | 生成指定怪物，观察行动、受伤、倒下和清理 | 新 AI、移动方式或战斗能力 |
| 关卡 | 同一小场地的怪物数量、出生位置与已有内容引用 | 指定关卡启动，检查清怪／全员倒下、重置与重开 | 新触发器、目标类型或场景交互 |
| 奖励 | 单种测试奖励的数量与已约定的胜负发放条件 | 固定测试玩家验证内存结果、结算一次与重复请求 | 新奖励类型或存储需求 |

技能组合、复杂 AI、波次、触发器、检查点、奖励组和随机权重等进入 X 专项候选；开始前先补教学目标、最小改动和验证内容，不要求 P1 先建通用编辑工具。

关卡先使用场地与生成配置；复杂空间编排在相应专项选择场景或编辑数据。Luban 承接适合的结构化数据，不要求首阶段具备完整关卡编辑器。

### 6.2 日常操作顺序

1. 按字段说明修改配置源文件，选择要验证的技能、怪物或关卡。
2. 执行配置检查：类型与范围、ID 唯一性、引用、循环或业务约束、资源标识和两端可用性。
3. 通过后生成一套完整的候选数据；失败时保留上一套可运行数据，防止半套生成物进入预览。
4. 在本地测试环境中让客户端和服务端采用配套的数据快照，界面显示当前配置版本。
5. 启动对应预览，完成本项检查，再进入副本或双客户端验收。
6. 提交源数据及需要纳管的相关定义与记录；生成物是否入库由后续仓库规则决定。

首阶段允许以重新进入 Play 或重启本地测试服完成数据采用。“保存后直接验证”不要求无条件在线替换数据。若后续实现运行中重载，需要另行定义安全边界、失败恢复与两端一致性。

### 6.3 工具与错误反馈要求

策划至少能发起配置检查、生成并进入预览、指定关卡启动、重置测试状态和查看运行数据版本。入口名称与 UI 待实现设计。

错误应说明源文件、表或记录、字段、错误引用、期望条件和修正方式。例如指出某技能引用了不存在的表现标识，而不是只返回“导出失败”。导出成功后仍需业务和运行验证。

## 7. 美术工作管线

### 7.1 独立替换的范围与约定

| 内容 | 保持稳定的约定 | 允许独立替换的内容 | 检查与预览 |
| --- | --- | --- | --- |
| 模型 | 单位与朝向、根节点、骨骼或重定向要求、挂点、表现组件接口 | 符合约定的新模型、材质、贴图和外观组合 | 静态预览、动作、挂点、受击与死亡；骨骼不兼容时明确报错 |
| 动画 | 动作语义、状态与参数接口、时序配置、位移和打断约定 | 兼容的动画片段及已暴露的表现参数 | 移动、施法、取消、受击、死亡与恢复，核对实际技能时序 |
| 特效 | 挂载位置、触发语义、持续／停止、对象复用与清理接口 | 特效 Prefab、材质、贴图及表现参数 | 播放、提前取消、目标销毁、重复使用和场景退出后的清理 |
| UI | UGUI 视图绑定、必需组件、交互事件、布局与生命周期接口 | 图片、字体、布局、动效和符合视图约定的 Prefab | 指定窗口、模拟数据与状态、多分辨率、重复开关及场景切换 |

“独立替换”依赖已定义的兼容范围。新增骨骼体系、改变技能规则时序、移除 UI 必需绑定或增加交互逻辑，需要协作修改约定和实现。UI 绑定方式、动画编辑与事件表达方式尚未选型，不预设复杂节点改动也能自动兼容。

### 7.2 从制作到运行

1. 按需求和初步规格制作，版本化保存制作源文件与导出设置；具体制作软件未定。
2. 导出交换资源，按约定导入 Unity；通过预设或工具维护导入设置与平台差异。
3. 检查依赖、材质、贴图、组件、骨骼／挂点、资源标识、UI 绑定等。
4. 在资源预览入口确认单项效果，再替换表现绑定并进入实际技能、怪物或关卡预览。
5. 策划检查信息传达与玩法配合，美术检查质量，程序／技术美术检查生命周期和成本。
6. 提交完整依赖及相关 Unity `.meta`，附上预览范围和已知问题，进入集成与副本验收。

源文件、交换文件、Unity 资产和构建制品分别标明归属与生成关系。不能只交付本机可见的 Prefab，遗漏其动画、材质、贴图、字体或 Shader 依赖。

### 7.3 制作预算与质量

按角色、场景、特效和 UI 定义初步规格与检查，但本文不填写尚无设备与玩法依据的面数、贴图或帧率数字。资源单项通过后，还要在两人战斗、技能叠加和真实目标设备上测量，再调整预算。

美术预览不要求使用真实账号或正式奖励数据；测试数据与正式内容分开标识，不能被误当作可发布内容。

## 8. 内容标识、数据版本与质量检查

### 8.1 跨系统连接

建议用稳定的逻辑标识连接技能、怪物、关卡、奖励与客户端表现。例如“技能 → 表现定义 → 模型／动画／特效资源标识”。具体数据结构在详细设计中确定。

逻辑内容 ID、Unity GUID、YooAsset 加载地址和构建内容 Hash 各有用途，不混作同一个标识。资源重命名、迁移、删除和替换要有引用检查；映射既能支持自动校验，也应让使用者定位到实际资源。

服务端消费规则所需数据，客户端消费交互与表现所需数据，公共定义按需要共享。是否将客户端生成数据通过 YooAsset 分发，待配置体积、采用方式和版本关系明确后决定；服务端数据随相应服务端发布流程管理。

### 8.2 检查位置与责任

| 环节 | 检查重点 | 失败后回到哪里 |
| --- | --- | --- |
| 本地编辑／导出／导入 | 格式、ID、资源依赖、绑定、必要规格 | 策划源数据、美术源资源或工具定义 |
| 提交后的集成 | 干净环境可重现、两端生成、编译、跨内容引用 | 本次变更及负责工种；展示具体错误与责任入口 |
| 运行验收 | 规则与表现、多人一致性、数据写入、取消和恢复 | 对应配置、资源、系统或规则设计 |
| 候选版本 | 制品完整、内容范围、版本配套、平台与更新流程 | 构建输入、发布配置或候选内容 |

必须修复的问题与建议优化的问题分别报告。明确的损坏、缺引用或不兼容阻止对应步骤；体验与成本问题按预算和评审处理，避免所有警告都阻塞日常工作。

### 8.3 共同版本记录

一次可运行组合记录代码提交、配置数据版本、资源版本、服务端版本、协议兼容信息、目标平台和检查结果。字段与兼容规则待详细设计。预览应显示实际采用的版本，避免源文件已改而运行环境仍使用旧数据。

出现失败时回到上一套已知可用内容或停止采用新内容；涉及玩家已写入的数据，需要独立的数据兼容与恢复方案，不能假定回退文件即可回退玩家状态。

## 9. Editor 验证与后续专项

Editor 是首个制作与运行入口，单项预览与双客户端验证分别记录。两名角色出现在一个进程里不等于双人网络结果已验证；具体双会话启动方式在实施时选定。

最小循环使用测试身份和隔离的内存奖励，不要求真实账号、正式大厅、复杂匹配、数据库或运营后台。资源下载、HybridCLR Player 行为、持久化、平台生命周期与性能各自设计专项，不将 Editor 模拟结果泛化为 Player 或真机结果。

Windows、Android、iOS 和小游戏仍进入平台边界设计，输入、存储、网络与生命周期分别考虑；只有相关专项开展后才填写验证结果。上线运营不作为当前验收条件。

## 10. 项目阶段与完成条件

所有游戏能力均待实现与验证。先完成教学闭环，后续按问题扩展，不承诺日程。

### 12.1 用共同变更串联文章

“A 施加标记、B 消耗标记”贯穿数据、规则、表现、UI、双端与清理；“修改怪物数量或奖励配置”贯穿源内容、校验、版本采用和结算。“修复重复消费或结算问题”用于规则与生命周期练习。Boss、数据恢复和发布扩展只有在专项需要时引入。

每篇只回答自己的核心问题，并链接共同案例与前后环节。项目总览维护整条链路，源码文章解释机制，实验记录提供证据；不把同一篇正文复制到不同专栏。

### 12.2 证据回流

每项工作记录：学习与产品问题、固定版本、源内容与改动、操作者、输入和环境、预期、观测方法、实际结果、失败路径、验证边界及对应文章。分清源码推导、模拟预览、Editor 运行、Player／真机结果和线上结果。

### 12.3 设计模式融入合作副本

2026-10-25 补充：设计模式的应用与验证安排在本项目内，沿用 Unity、UGUI、ET、Luban、YooAsset、HybridCLR 的既定方向。以下是候选研究安排，具体采用哪种模式仍由需求和实验决定；未实现、未运行验证。

教科书保留引擎无关的最小 C# 示例，应用文章回到合作副本的实际变更。可以在同一项目的测试场景或独立实验中保留直接实现与候选实现，正式游戏只维护选定方案。Game Framework、QFramework 等按具体问题作为外部阅读对照，不因设计模式教学增加项目框架依赖。

| 项目中的变化或问题 | 候选设计与比较重点 | 要观察或验证的结果 |
| --- | --- | --- |
| 策划增加技能目标规则或已有行为组合 | 参数化／数据驱动与 Strategy 的边界；新增行为能力由程序提供 | 参数修改能直接预览；从最近选敌引入 B 标记优先时确认修改范围、旧规则回归及双端结果 |
| 怪物进入施法、受击、死亡，或副本阶段发生转换 | 显式分支、State 对象与 FSM 的适用边界；ET10 行为树已列为首选候选，按 BT01～BT10 待验证；与直接分支、行为机和 FSM 分别对照 | 非法转换、施法打断、死亡后的回调及退出重进有明确结果 |
| 击杀后更新任务、HUD 和表现 | 直接调用与 Observer／事件通知的比较；本地通知与网络消息分开 | 窗口反复开关不重复订阅，场景退出后无残留响应；服务端结算仍独立验收 |
| 玩家发起操作，测试需要记录或延迟执行 | 直接调用与 Command 的比较，区分操作意图、传输协议与服务端校验 | 非法、重复或过期请求按规则处理；命令封装本身不保证幂等、确定性重放或网络撤销 |
| 美术替换 UGUI 外观，策划调整展示数据 | 视图与业务职责拆分，比较 MVP 与现有 ET 组织方式 | 兼容替换无需修改业务规则；绑定缺失可定位，关闭窗口后异步结果不再写入失效视图 |
| 创建怪物、特效和飘字，随后销毁或复用 | 创建职责／Factory 候选、对象池与直接创建销毁的比较 | 重置、取消、回收和再次使用正确；在一致负载下测量收益与成本，不以使用对象池推定更快 |
| 业务使用资源加载与平台能力 | 按真实变化点判断 Adapter、Facade 或直接调用是否更合适 | 加载失败、取消和释放可追踪；封装后仍能表达 YooAsset 句柄所有权及平台差异 |
| 策划检查与生成、美术导入检查、构建任务增加步骤 | 顺序函数、Pipeline 与 Template Method 的比较 | 错误定位到源内容，失败不采用半套产物；有固定骨架与替换步骤时再讨论模板方法 |

所有候选都要先明确状态归属、依赖方向和作用域。ET 实体、组件、消息及异步工作沿所选版本的机制组织，具体行为通过源码和实验核对；需要纯 C# 规则对象时说明其调用边界，不另外复制一套实体生命周期。SOLID、DI、对象池、ECS、Actor、Fiber 与 GoF 模式分别归类；不凭组件名称判定模式。

阶段上，P1 优先覆盖技能规则变化、视图／表现替换和创建清理，服务于策划、美术的独立制作验收；P2 随最小双人循环补状态转换、事件／消息、异步作用域与失败路径；X 专项再按问题研究内容更新、多平台适配与生产流程。阶段编号沿用第 10 节，不表示这些模式已经选定，也不要求每个候选都进入正式实现。

每个案例记录“原始需求 → 直接实现 → 新需求或失败 → 候选方案 → 选用或拒绝的理由 → 实际验证与成本”。案例可同时支撑多篇既有文章；篇目与状态仍由设计模式主规划维护，项目规划只登记承载场景。首个案例建议沿 P1 技能制作流程展开，用最近选敌与 B 标记优先比较配置参数和策略扩展的边界。
