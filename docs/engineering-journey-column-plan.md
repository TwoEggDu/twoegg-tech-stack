## 1. 当前阶段

当前阶段不是写最终正文，而是先回答：

1. 这个页面需要展示哪些内容。
2. 不同内容应该放在什么位置。
3. 每一段还缺什么事实、案例或证据。
4. 哪些内容适合公开，哪些只适合保留在私密履历中。

本轮完成后，公开页应当具备稳定章节结构，但允许具体项目内容仍然不完整。

## 2. 栏目定位

这栏通过工程经历回答六个问题：

1. 进入过哪些类型的项目现场。
2. 项目方向和平台发生变化时，承担的问题怎样变化。
3. 工作重心怎样从具体实现走向完整交付和技术质量。
4. 哪些做法已经在多个项目中复用。
5. FDE 与 RaaS 怎样解释这套实践方式。
6. 下一阶段准备沿哪些方向继续推进。

这不是公开简历、职位说明、项目名单或能力标签页。项目名称只提供背景，代表案例和验证证据才承担主要叙事。

## 5. 职责演进框架

| 层级 | 准备展示的责任 | 可选证据 |
|------|----------------|----------|
| 具体实现 | Unity、C# 运行时、HybridCLR、平台接口与工程问题 | 源码、设计文档、故障复盘、提交记录 |
| 项目交付 | 两个项目出包、内外网构建、资源更新与对外测试 | 构建记录、发布流程、产物、失败处理 |
| 技术质量 | CPU、GPU、内存、启动、包体、崩溃与线上稳定性 | 性能平台、趋势数据、优化方案、回归结果 |
| 项目支持 | 美术资产、策划需求、客户端、服务端和线上问题 | 资产规则、协作流程、跨系统案例 |
| 结果责任 | 调动组内资源、处理取舍、推动最终产品交付 | 决策记录、交付结果、风险与复盘 |
| 公共能力 | 构建、资源、发布、验证和知识沉淀 | 第二项目复用、接入契约、维护机制 |

这一框架不依赖是否存在直属下属。重点是责任边界、影响范围和最终结果。

## 6. 五个代表案例的内容槽

每个案例统一填写下面六项：

```text
项目背景：
真实问题：
约束与风险：
我的判断与动作：
可验证结果：
后来怎样被复用或修正：
```

### 案例 A：PX 的多次方向变化

核心问题：

- 产品方向改变时，哪些工程能力需要保留。
- 哪些旧结构应该退出，哪些公共层不应反复推倒。
- 个人责任是否随着项目阶段发生变化。

当前缺口：方向顺序、品类、平台、关键决策和一次代表性结果。

### 案例 B：Tiny 与 TopHero / DP 的多项目交付

核心问题：

- 怎样同时保障两个项目稳定出包。
- 内网高频构建、周期性外部测试和资源更新分别怎样治理。
- 构建失败、资源错误和发布权限怎样形成反馈。

当前缺口：频率的准确口径、正式发布链、最能代表改进前后的一个案例。

### 案例 C：Zuma 的微信小游戏迁移

核心问题：

- 传统 Unity 项目为什么不能直接视为小游戏项目。
- 平台接口、启动、首包、内存和运行时分别属于哪一层。
- 独立完成平台适配以后，团队怎样持续迭代。

当前缺口：迁移时间、关键阶段、前后数据、真机证据和线上稳定性结果。

### 案例 D：产品技术质量闭环

核心问题：

- 怎样把项目接入公司性能管理平台。
- 数据怎样变成问题优先级和具体优化方案。
- 优化完成后怎样证明没有回退。

当前缺口：平台名称的公开边界、指标基线、典型优化项目、前后结果。

### 案例 E：跨工种推动最终交付

核心问题：

- 美术资产、策划目标、客户端实现和服务端约束怎样互相影响。
- 没有直接汇报关系时，怎样形成共同优先级。
- 怎样让支持工作减少业务开发者的上下文切换。

当前缺口：选择一个跨至少三个工种的真实事件，补齐冲突、判断、协调和结果。

## 7. FDE × RaaS 的证据框架

### 7.1 FDE

采用 `Forward Deployed Engineering` 的工作方法语义：

1. 进入问题实际发生的环境。
2. 同时理解产品目标、工程系统和交付约束。
3. 在真实链路中完成并验证结果。
4. 把现场反馈带回公共工具、平台、知识和方法。

只有临时救火、持续增加项目特例，却没有公共层回流时，不算形成完整 FDE 循环。

### 7.2 RaaS

本站固定使用 `Result as a Service`，即“结果即服务”。进入这一层的能力至少需要：

1. 结果定义与成功条件。
2. 与结果层级匹配的验证证据。
3. 公共部分与项目特例的接入边界。
4. 版本变化、结果漂移和执行失败后的维护方式。
5. 在第二个项目或明显不同场景中的复用。

### 7.3 第一批待验证的跨项目路径

| 候选路径 | 准备验证的内容 | 当前边界 |
|----------|----------------|----------|
| PX -> TopHero / DP | 跨项目资产、构建和运行时经验怎样进入明确契约 | 有仓库证据，仍需确认个人主导范围 |
| Tiny -> TopHero / DP | 多项目出包和发布经验怎样形成统一交付链 | 需要选一个完整案例 |
| TopHero / DP -> Zuma | 构建、HybridCLR、资源和发布机制怎样适应新平台 | 不能把 Android 结果直接当作小游戏结果 |
| 性能平台 -> 多项目治理 | 指标、优化方案和回归怎样变成持续质量能力 | 需要项目级数据和第二场景复用证据 |

候选路径没有补齐第二场景验证前，只写成“正在验证的复用关系”，不写成已经完成的平台能力。

## 8. 证据分层

每个事实要标明它能证明到哪一层。

| 证据 | 可以证明 | 不能单独证明 |
|------|----------|--------------|
| 公开产品页面 | 产品存在、公开名称、平台 | 个人职责和贡献 |
| 仓库源码与提交记录 | 修改范围、技术实现、持续时间 | 构建成功、设备表现、线上效果 |
| 构建日志与产物 | 某次配置能够产出结果 | 真机体验和线上稳定性 |
| 编辑器或自动化测试 | 特定环境中的行为 | 全平台、全设备和生产闭环 |
| 真机与性能数据 | 目标设备上的表现 | 长期线上稳定性 |
| 线上监控与事故记录 | 真实运行结果和质量变化 | 结果完全由单一改动造成 |
| 决策与协作记录 | 判断、协调和责任边界 | 没有结果证据时的最终成效 |

不使用原始提交数量直接证明影响力；自动构建、版本号和生成文件提交要与人工工程改动分开。

## 9. 填充顺序

### 第一轮：补项目边界

每个项目先只补五个字段：

```text
时间范围：
项目类型与平台：
所在团队和角色：
最主要负责的事情：
一个代表性事件：
```

目标是让时间线成立，不追求完整正文。

### 第二轮：补五个代表案例

按优先级：

1. Zuma 微信小游戏迁移。
2. Tiny 与 TopHero / DP 多项目交付。
3. 产品技术质量闭环。
4. PX 多次方向变化。
5. 跨工种推动最终交付。

前三个案例目前证据基础更强，也更容易形成完整的“问题到结果”叙事。

### 第三轮：补数据和验证

优先补：

- 启动。
- 首包和总体包体。
- 内存。
- CPU / GPU。
- 崩溃和线上稳定性。
- 构建与外发频率。
- 故障发现和恢复时间。

没有可靠基线的数据保留 `DATA-TODO`，不使用估算值替代。

### 第四轮：连接公开文章

案例事实稳定后，再把对应文章接入项目时间线。不要为了填满页面先堆链接。

## 10. 边界

### 属于这栏

- 影响工程判断的项目背景。
- 职责范围随项目变化的过程。
- 能够落到真实问题和验证结果的代表案例。
- 已有公开文章与项目经历之间的关系。
- 跨项目复用以后形成的 FDE / RaaS 实践飞轮。

### 不属于这栏

- 完整公司履历、薪资、离职原因和私密项目信息。
- 没有本人确认的项目名称、职责或量化成绩。
- 把团队成果全部改写成个人成果。
- 把仓库存在的代码默认归因给本人。
- 用职位、人数或缩写替代实际责任和结果。
- 把规划中的方向写成已经完成的能力。

## 12. 维护规则

1. 先更新当前 canonical plan，再修改公开页结构。
2. 新增项目时必须说明它在整条路径中承担什么作用。
3. 每个项目至少有一个代表事件以后，才从占位状态进入正文状态。
4. 每个案例优先补问题、判断和结果，再补技术名词。
5. 事实、构建、设备和线上证据分层陈述。
6. FDE / RaaS 必须放在项目和案例之后。
7. 一次方案只有在第二场景复用后，才能标记为 RaaS 候选能力。
8. 修改链接或目录后运行 Hugo 构建。

## 13. 最短结论

`先用项目轨迹说明问题从哪里来，再用代表案例说明怎样对结果负责，最后才用 FDE 与 RaaS 解释这些结果如何跨项目积累。`
