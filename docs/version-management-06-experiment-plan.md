## 验证块 1：分支汇合与提交图

**结论**：在明确策略下，可快进与历史分叉会形成不同的提交关系。

- 最小场景：两个独立仓库，均有干净基线。快进仓库只在 feature 增加一个提交，main 用 `merge --ff-only feature`；分叉仓库两边各修改不同文件，再从 main 普通 merge feature。
- 控制变量：普通分支、不使用 tag；不引入 squash、rebase、cherry-pick 或额外合并策略。两个场景分别初始化，避免前一场景改写后一场景的共同祖先。
- 观测：merge-base、合并前后 HEAD 与 feature SHA、提交数量、父提交、最终文件、`log --graph`。预期快进后 main 等于 feature、没有额外提交；分叉合并有两个精确父提交，双方文件变化存在。
- 验收：使用 `merge-base --is-ancestor` 检查来源可达，再检查目标内容；明确可达性不能单独证明修复行为正确。
- 不符排查：检查基线、实际切换分支、merge.ff、tag 与 squash；不以终端最后一句成功替代提交图。

## 验证块 2：显式文本冲突与结果验收

**结论**：冲突输入与解决后的提交内容可以分别取证。

- 最小场景：第三个仓库，同一行 `damage=100` 在 main 改为 80、feature 改为 90，执行 main 合并 feature。此场景单独约定最终保留 80，不沿用到其他业务。
- 控制变量：两侧输入与共同基线固定，干净工作区，无 rerere 或自定义驱动，源分支合并前后不变。
- 观测：merge 预期非零；HEAD 未前进，MERGE_HEAD 指向来源；`ls-files -u` 有三个 stage，`:1:` 为 100、`:2:` 为 80、`:3:` 为 90；工作文件有冲突标记。
- 解决：依据本场景约定写入 80，显式 add、commit。核对无未合并条目、两父提交、工作区干净及最终内容。没有测试二进制、移动、删除或复杂多祖先冲突。
- 不符排查：检查两侧是否真的改同一行、是否误合入已包含的来源、是否继承驱动或 rerere；不随意选 ours/theirs 来代替业务约定。

## 验证块 3：无文本冲突但行为错误（主案例）

**结论**：文本可自动合并，不保证组合行为满足共同约束。

- 最小场景：第四个仓库。`base.json` 初始伤害 100；`charge.json` 初始倍率 100%；`damage.py` 计算整型原始伤害。事先固定教学规则：最终伤害在 0～150；集成后保留 base=120 与 percent=140，最终按 150 封顶，原始值仍可观察。此规则仅为教学约定。
- 分支：main 只把基础伤害改为 120，feature 只把倍率改为 140%。同一个验收器在基线与两侧均运行通过，输出分别为 100、120、140。
- 合并：两个文件无文本冲突，普通 merge 退出 0、无未合并条目，两侧提交均可达；程序原始/最终值均为 168，同一个验收器预期退出非零。
- 适配：只修改计算程序，保留两个配置与验收器，增加最终封顶。预期 raw=168、final=150，验收通过；修正采用单独可追查的提交，不把已经记录的错误合并伪装成从未发生。
- 接收：本地 clone 新目录，明确 checkout 修正 SHA；程序与原检查器通过，源分支仍停在原 SHA，最终文件散列与目标一致，工作区干净。
- 控制变量：不修改固定上限或验收器，不使用浮点计算，不把检查写在仅一侧新增的测试中，不从源工作目录手工补文件。Python 仅验证教学行为，不证明引擎行为、资源依赖或线上门禁。
- 不符排查：查看配置是否同文件导致文本冲突、是否检查了错误 SHA、是否原工作目录残留污染接收方；若规则本身待决，应保留未通过状态。
