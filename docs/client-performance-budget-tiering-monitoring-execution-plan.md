## 1. 目标与推进原则

本专栏按[性能专栏质量标准](client-performance-quality-standard.md)推进。作者以专家级性能能力为目标；我们用问题模型、测量、因果验证、取舍、预算、系统及持续使用的可复核产物验收，不以术语、篇数或自评总分判定。基础讲解、设备实证和团队采用保持各自证据要求。

最终学会：解释客户端成本与指标，制定预算，建立项目适用的高中低设备分档及画质方案，选择 UI、场景、角色、动画和特效的观测点，设计准确采集，并建设可以持续检查、比较和复验的监测体系。

引擎无关主线、领域模型与具体实现的分工，以及 CPE-01/02 的唯一篇级登记见[专栏主规划](client-performance-engineering-series-plan.md)。A/B/C 的主要判断先用通用模型解释，D 保留领域和实现差异，E/F 先写观测契约再映射实际采集；Unity 是第一条验证路径。通用方法仍注明平台、硬件和实现前提，不将环境差异抹去。

推进分为两个阶段：**先建立知识体系，再开展具体测量与工程实现**。知识阶段按“共同基础 → 预算 → 设备与画质分档 → 五类内容成本与观测 → 测量原理、校准设计与监测方法”展开；达到第 2.2 节的完成条件后，再进行实际采集、预算与设备标定、工具实现和持续回归。预算与分档先用教学推导建立判断，实际数值随后由测量校准。

- 先学原理和判断，再选工具、API 与实现方式；ParticleEffectProfiler 保留为后续特效专项的公开案例。
- 优先复用、审校和补强已有文章。正式新增独立文章前，在对应系列 plan 登记，避免把同一个问题写成多篇。
- 每批推进 1–2 个明确工作单元；按照产物和理解检查推进，不在缺少学习投入与设备条件时预设工期。
- 知识阶段用来源核对、逻辑图、教学推演和理解检查交付，不安排提前实测。实际阈值、设备归档、性能收益与团队采用须另有证据；这些结果留到后续实践阶段取得。
- Unity 是首个具体实现映射；精确版本、渲染管线、包版本、目标平台和设备在进入采集实验前固定，不在计划中擅自指定。
- 首期覆盖五类内容及其组合验收。物理、音频、网络沿原专题按需补齐；线上遥测放在后续扩展。

“首次打开界面并播放特效”是贯穿教学任务：A 定义观测，B 推导候选预算，C 选择候选配置与验证范围，D 解释成本，E 设计证据采集，F 设计回归和处理职责；实际采集与运行在知识阶段完成后执行。它能连接各批，但不能代表所有负载；持续运行、复杂角色与场景组合在各自专项追加。后续实测推翻教学假设时，保留修订依据，更新受影响正文和规则。

首个运行原型只覆盖“测试配置 → 执行 → 有效性判定 → 原始记录 → 报告 → 复跑”所需职责。复用已有采集工具和脚本；公共抽象先经特效与 UI 检验，再决定批量和服务化需求。ParticleEffectProfiler 用于检验其测量边界与可复用实现，具体保留或替换哪些部分由 D1/E 的结果决定。

知识阶段完成后，开始实际实验前集中固定一次环境：可公开的样本工程及版本、Unity/管线/包版本、Player 平台与图形 API、可用设备和测试配置。先检查现有实验材料能否复用；尚缺的产品目标或设备条件再向作者确认。不确定环境不妨碍基础正文与教学推导继续交付，也不能被默认环境冒充。

### 2.2 知识阶段什么时候算完成

完成范围是 A–D、E 的原理与设计，以及 F 的监测方法。复用正文与必要补强共同覆盖这些问题即可，不要求每个单元新增一篇文章，也不要求学完全部硬件、OS 或引擎专题。原文中会影响当前判断的已知缺项须修订或明确限用。

围绕首开界面与特效任务，并加入角色、动画和场景组合的条件变化，完成以下检查：

1. **能解释成本与依赖。** 画出主要执行、等待、资源寿命与反馈路径；说明五类内容各自的成本来源和生命周期，区分共享、独占及重叠部分。
2. **能定义观测与比较口径。** 为目标选择对象、事件、指标、单位、窗口与统计方式，解释工作量和耗时、首次和稳态、帧样本和独立运行的区别，以及代理指标和缺失数据的局限。
3. **能推导候选预算与分档。** 从体验、代表负载和支持范围写出带假设的预算、余量、阈值及超线动作；区分设备能力、画质配置和运行状态，说明代表设备选择、必要体验与待校准项。
4. **能设计测量与校准。** 写出测试条件、采集来源与支持边界、重复和对照方案，说明如何发现漏计、重复、背景混入及采集扰动，哪些结果应判无效或证据不足。此时交付验证设计，不要求已经采集数据。
5. **能迁移判断并设计后续处理。** 当并发、镜头、分辨率、缓存或设备状态变化时，说明哪些假设需要重查；把任务、配置、原始记录、报告、规则版本、异常复验和处理责任连接起来，说明基线更新依据。

检查依据是可阅读的解释与来源、教学图示、可复算例子和作者对理解问题的反馈。沿第 5 节模板保存教学方案，在第 7 节批次记录中定位“正文/补强位置、教学产物、理解反馈与剩余卡点”；已有材料直接复用，不另建一套状态表。教学数值明确标注身份，不冒充已标定预算或机型结论。

材料齐备且作者反馈表明能完成上述判断后，才进入实测准备；有卡点则返回相关单元补桥。AI 写完材料或审稿通过不能代替作者掌握。当前只完成本项标准的制定，知识阶段尚未通过，作者理解仍待反馈；CPE-02 后继续补齐知识，不插入提前实测任务。

## 4. 每批怎样学习与交付

每批按下列顺序推进：

1. 确定本批 1–2 个工作单元及目标问题，列精确文件范围和已有材料。
2. 按[旧文检索与复用判断](article-production-workflow.md#article-reuse-preflight)复读当前正文、必要来源与原 plan；在本批记录中简述“已有覆盖、需调整处、复用决定、本次增量”。选择直接复用、原位补充、修订旧文或独立成篇；新篇先在其唯一 canonical plan 登记。历史审查可复用，但不能把已修问题继续列为缺口，也不能只看标题或待写状态。
3. 先形成原理解释、必要图示/算例与误判说明，再提出采集或验证需求。操作步骤保持服务于解释。
4. 用问题或教学场景检查理解，记录哪里仍缺桥梁；不以“读过”替代能解释或做判断。
5. 需要实验时单列方案、条件、原始证据与待验证项；已有数据不足以支持的结论保持未知。
6. 按[性能专栏质量标准](client-performance-quality-standard.md)记录本批适用条款、证据位置、缺项和处理；回写对应系列的文稿状态，以及本文的任务批次、证据和下一步。公开正文完成后按仓库规范验证；提交和发布按实际授权及结果另记。

作者提供产品意图、实际约束和学习反馈；助手负责材料核对、解释整理、实验设计及授权范围内的实现。项目预算、必要体验与接受责任按真实团队决定，不能由工具默认值代替。

本轮审查已将具体调整定位到[复用记录 R1–R8](client-performance-existing-content-review-2026-11-04.md)。每批先处理会影响本批读者判断的相关问题，再补增量；不要求全站旧文先全部重写，也不把新专栏的更大范围当成每篇旧文的缺陷。

### 4.1 固定每批的交付与退出条件

每批围绕一个读者问题推进，默认同时只有一批正文处于起草和修订；资料核对、独立审稿与实验准备可并行。基础和写作批次应形成读者可见的正文增量，位置可以是已有文章的补节，也可以是登记后的新篇。仅新增内部提纲、指标清单或计划不能算这一批正文完成；实验批次则以可追溯记录为交付，不强求每次实验单独成篇。

每批结束只维护一条接续记录，包含：

`主要问题 / 实际改动文件 / 复用决定和正文增量 / 来源或实验身份 / 适用质量条款及审查结果 / 本地页面检查 / 作者理解反馈 / 未完成项与下一批 / 提交发布状态`

助手负责旧文与来源核对、解释和图表、实验方案、文稿整理及可执行的验证；作者负责实际产品约束、必要体验取舍和学习反馈。涉及设备操作与项目材料时按真实可用条件分工，不在每批重复索取基础信息。审稿至少检查技术与证据、阅读与导航；关键结论可由独立审阅补查，审阅不代替实验复现。

文稿达到适用条款、读者能沿正文完成预定判断且站点检查通过后，就结束本批并回写状态。未回答的延伸问题进入后续单元，避免把最小字典不断扩大成全领域百科。作者是否已经掌握另记为“待反馈／已反馈及卡点”，助手不能代答后认定作者通过。每批给一个改变条件的问题，据反馈调整下一批的补桥深度。

不预设缺乏依据的总工期。P1/P2 完成后，依据实际写作、审稿和作者反馈节奏，再估计后续批次；设备实验另受工程和设备可用性约束。正文、实验、工具、采用及线上发布沿第 6 节分别记账。

### 4.2 固定的专栏写作工作流

2026-11-05 按作者确认固定以下执行顺序。它将[单篇生产流程](article-production-workflow.md)应用到本专栏；写法仍归[文章方法](article-writing-method.md)，篇目仍归[主规划](client-performance-engineering-series-plan.md)，不另建篇级目录。已有有效材料直接复用，局部勘误只走受影响步骤。

| 步骤 | 输入与操作 | 必须留下的产物 | 进入下一步的条件；否则回到哪里 |
| --- | --- | --- | --- |
| W1 确定问题与复用 | 从主规划选一项；阅读相似旧文与前置，确定读者需要作出的决定 | 一句核心问题、文章类型、旧文复用/修订决定、独立增量及文件范围 | 问题和边界明确；旧文已回答则改为链接或补桥，不重复开篇 |
| W2 提纲与证据定位 | 按问题组织解释顺序；从[官方资料索引](client-performance-official-references-2026-11-05.md)查相关章节，记录版本与局限 | 简短提纲；关键主张到资料章节、教学推演或实验记录的对应 | 依据能支持拟写结论；缺依据就缩小结论、补查或登记待验证，不能用官方头衔代替论证 |
| W3 准备最小例子或验证 | 知识阶段设计能复算的教学记录与反例，所需实验登记为方案；第 2.2 节检查完成且环境具备后，实测篇按第 4.3 节运行 | 原始教学输入/计算说明，或实践阶段带配置与失败样本的实验材料 | 例子能说明本篇判断；教学数据明确标注，未完成的实验不写成结果。仅缺实测不阻塞已有依据的基础篇 |
| W4 完成正文 | 沿提纲解释问题、机制、边界与下一步动作；具体工具服务于判断 | 可阅读正文与真实引用；未知项使用 DATA-TODO 等现有标记 | 读者能沿正文作出预定判断；解释跳跃回 W2/W3，范围膨胀回 W1 |
| W5 专家审核与最小修订 | 使用 `col-expert-review`；必要时核对系列一致性或事实风险，复核能改变结论的问题 | 适用条款、关键追问、通过/退修/待补证/阻断及对应依据 | 本篇职责内通过；退修回 W2/W4，证据不足回 W3 或缩小主张。资料核对、AI 编辑审阅和设备实证分别记账 |
| W6 页面验证与状态回写 | 按仓库要求执行模板回归、Hugo、生成页检查；核对导航及图表阅读 | 检查结果、可读预览；先更新系列 plan，再更新必要首页和执行记录 | 本次候选页面与导航通过；失败修对应内容或呈现，不用工作区其他文件的成功替代候选检查 |
| W7 按授权交付 | 每批修改、审核和必要检查完成后，按下述持续授权提交并推送精确范围；需要线上验收时核验对应版本 | 提交 SHA、远端回读及本地未提交项；线上另记核验结果 | 本专栏批次无需逐次确认；范围不清、检查失败或交付受阻时保留进度并报告。提交、推送和线上可读分别记录 |

**Git 交付策略（2026-11-05 人工调整）**：作者已持续授权本聊天的性能专栏每轮修改完成、对应审核与必要本地检查通过后，自动提交并推送现有 `origin/main`，不再逐批等待确认。授权包含本批必要的正文、计划、导航与审校记录，不包含其他专栏或无关工作区修改，也不改变知识先行及实际测量后置的顺序。每次先说明并核对精确文件/部分范围；共享文件仅暂存本批 hunks，保留其他修改与暂存。按 Commit → Fetch → 核对待推送范围 → 按需 Rebase → Push 执行，关闭自动 stash/updateRefs，不强推、不自动清理或捎带其他提交；推送后回读远端 SHA 或核对包含关系。失败时保留已保存的提交并报告；已有本批提交则复用，无改动不创建空提交。此项替代此前“自动任务仅本地、不自动提交”的策略，历史批次中未提交、待确认和快照记录仅描述当时状态。实际交付 SHA 可在聊天与下一批记录补记，不为记录自身 SHA 反复提交。

### 4.3 固定的性能测试与优化工作流

以下是本站结合 Unity、Epic 官方资料和既有测量标准整理的操作协议，**不是两家厂商共同发布的标准，也未在本轮实际跑通**。依据及版本见[参考索引](client-performance-official-references-2026-11-05.md#workflow-evidence)。每次只围绕一个明确任务或性能问题运行，初次基线、优化验证与预算校准共用以下步骤。

知识阶段先学习并推演本流程；实际运行从第 2.2 节检查完成、实验环境确定后开始。T1 中的探索性测量属于实践阶段，不能作为提前跳过知识阶段的入口。

| 步骤 | 输入与操作 | 必须留下的产物 | 通过条件与退回动作 |
| --- | --- | --- | --- |
| T1 定义任务与接受条件 | 确定玩家操作、可见/交互目标、生命周期阶段、必要画质和支持范围；选指标及预算 | 任务卡：对象/请求、起止点、指标口径、接受条件与依据 | 能判断要改善什么。预算未知可先做探索，明确“待校准”，不输出性能合格结论 |
