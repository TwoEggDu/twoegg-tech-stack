## 1. 目标与推进原则

本专栏按[性能专栏质量标准](client-performance-quality-standard.md)推进。作者以专家级性能能力为目标；我们用问题模型、测量、因果验证、取舍、预算、系统及持续使用的可复核产物验收，不以术语、篇数或自评总分判定。基础讲解、设备实证和团队采用保持各自证据要求。

最终学会：解释客户端成本与指标，制定预算，建立项目适用的高中低设备分档及画质方案，选择 UI、场景、角色、动画和特效的观测点，设计准确采集，并建设可以持续检查、比较和复验的监测体系。

引擎无关主线、领域模型与具体实现的分工，以及 CPE-01/02 的唯一篇级登记见[专栏主规划](client-performance-engineering-series-plan.md)。A/B/C 的主要判断先用通用模型解释，D 保留领域和实现差异，E/F 先写观测契约再映射实际采集；Unity 是第一条验证路径。通用方法仍注明平台、硬件和实现前提，不将环境差异抹去。

推进顺序为：**共同基础 → 预算 → 设备与画质分档 → 五类内容专项 → 测量与校准 → 工具与监测体系**。预算与分档需要往返；校准设计可以提前帮助理解基础，具体工具实现依据已经定义的测量需求开展。

- 先学原理和判断，再选工具、API 与实现方式；ParticleEffectProfiler 保留为后续特效专项的公开案例。
- 优先复用、审校和补强已有文章。正式新增独立文章前，在对应系列 plan 登记，避免把同一个问题写成多篇。
- 每批推进 1–2 个明确工作单元；按照产物和理解检查推进，不在缺少学习投入与设备条件时预设工期。
- 概念解释和教学推演可以先完成。实际阈值、设备归档、性能收益与团队采用须另有证据，不以缺少这些证据阻塞其他基础内容。
- Unity 是首个具体实现映射；精确版本、渲染管线、包版本、目标平台和设备在进入采集实验前固定，不在计划中擅自指定。
- 首期覆盖五类内容及其组合验收。物理、音频、网络沿原专题按需补齐；线上遥测放在后续扩展。

| 阶段 | 本阶段要解决的事 | 交付物 | 进入后续阶段所需的最低结果 |

| E 准确测量 | 把指标定义落实为可校准的采集方案 | 采集规格、测试协议、校准样例及有效性报告 | 至少一条链路能识别错误口径、无效样本与采集扰动；设计完成与实验通过分开 |
| F 监测建设 | 将有效测量接成可维护的工程流程 | 系统设计、最小原型、第二领域接入、回归与处理流程 | 实测可复现，报告可定位，失败能处理，规则有版本；各建设步骤逐项验证 |

这些是知识和产物依赖，不要求前一阶段全部旧文都重写完。B/C 可先用明确标注的教学记录练习，随后由 E 的实际数据校准；不能把教学矩阵当作已完成设备标定。

### 2.1 按什么顺序交付给读者

A–F 是学习地图，实际交付按下表推进。共同基础和相关领域机制先行；特效所需知识、指标和协议具备后，就进入一条链路的测量，不以五类专项全部成稿作为实验前置。表内是交付节点，不增加公开篇号，也不要求一个节点在同一批完成。

| 交付节点 | 对应单元 | 读者得到什么 | 转入下一项的条件 |
| --- | --- | --- | --- |
| 共同语言可用 | P1：A1/A2；P2：A3/A4 | 可阅读的旧文补强或独立应用正文，配有首开任务的事件图、最小观测表、统计误判示例 | 能说明测谁、从哪到哪、为何这样统计，以及什么证据尚不足以归因；P1 的明确缺口交给 P2 |
| 预算与分档可推导 | B1–B3、C1–C3，分批展开 | 围绕同一教学任务走完体验目标、代表负载、候选预算、配置与验证矩阵，保留取舍理由 | 教学条件和待校准项明确；能说明场景或设备能力变化时要重查什么，不以假设矩阵宣称实际机型达标 |
| 首条测量链可复验 | D1 → E1–E3 的特效范围 → F1/F2 的必要部分 | 一种明确环境下的特效测量记录、校准结论与最小运行原型；配置、原始记录、分析和复跑相互对应 | 能识别选定的错误口径或无效样本，交代采集扰动；有同条件重复和结论范围，成功读数不能替代校准 |
| 第二领域与优化案例成立 | D2 及其 E 适配、F3；继续 D3/D4/D5 | UI 接入修正公共抽象；角色、动画与场景补齐组合观测；围绕实测现象形成诊断、方案取舍、改动和复验记录 | 共享与独占成本能区分；案例有原始证据及正确性检查，未奏效方案也保留；跨设备结论另按矩阵验证 |
| 回归可运行和维护 | F4，并回校 B/C | 可重复触发的测试、基线比较、异常处理、复验及规则修订记录 | 受控注入的失败能被发现和处理；实际阈值有匹配条件下的标定记录；团队采用另由真实运行记录证明 |

“首次打开界面并播放特效”是贯穿任务：A 定义观测，B 分配预算，C 选择配置与验证范围，D 解释成本，E 收集证据，F 接入回归。它能连接各批，但不能代表所有负载；持续运行、复杂角色与场景组合在各自专项追加。教学假设被实测推翻时，保留修订依据，更新受影响正文和规则。

首个运行原型只覆盖“测试配置 → 执行 → 有效性判定 → 原始记录 → 报告 → 复跑”所需职责。复用已有采集工具和脚本；公共抽象先经特效与 UI 检验，再决定批量和服务化需求。ParticleEffectProfiler 用于检验其测量边界与可复用实现，具体保留或替换哪些部分由 D1/E 的结果决定。

开始实际实验前集中固定一次环境：可公开的样本工程及版本、Unity/管线/包版本、Player 平台与图形 API、可用设备和测试配置。先检查现有实验材料能否复用；尚缺的产品目标或设备条件再向作者确认。不确定环境不妨碍基础正文与教学推导继续交付，也不能被默认环境冒充。

### D. 五类内容专项

按“特效 → UI → 角色 → 动画 → 场景组合”展开；角色单元先建立资源与实例账本，具体动画求值与蒙皮分解由后续单元补齐。此前 A2 的 UI/特效只作共同概念例子，不算完成领域专项。

| 单元 | 重点学习内容 | 产物与验收重点 |
| --- | --- | --- |
| D1 特效 | 发射/模拟、存活量、几何、材质、屏占比、重叠与生命周期 | 特效观测表；解释首放、爆发、稳态、叠加和结束；区分覆盖诊断与原渲染成本，再使用开源工具分析作为实现案例 |
| D2 UI | 数据更新、布局/图形重建、文本与图集、批次、覆盖、资源驻留 | UI 观测表及首开/重开/切页/滚动/关闭协议；区分 uGUI 等实现口径，隐藏与释放分开 |
| D3 角色 | 几何、材质/贴图、骨骼/权重、LOD、换装、阴影与同屏数量 | 角色观测表；记录创建、换装、远近及同屏峰值，共享资源和实例增量分开 |
| D4 动画 | 状态、采样、混合、IK/约束、姿态写回、蒙皮、压缩与更新频率 | 动画观测表；核对过渡、打断、根运动、事件和挂点正确性；与角色父子归因一致 |
| D5 场景与组合 | 镜头、可见集合、灯光/阴影、Streaming、加载和双驻留 | 场景路线与组合账本；把前四类放入代表负载，避免共享阶段重复归账；单机位或单体通过不代替组合验收 |

每份观测表统一包含：对象、阶段、指标定义、成本关系、阈值依据、拟采集方式、数据有效性和超线动作。这里先解释“为什么观察、怎样判断”；具体 API 与准确性实验在 E 集中落实。原文复用位置见[学习路线](client-performance-budget-tiering-monitoring-outline.md)，篇级状态回各原系列。

### E. 测量设计与准确采集

| 单元 | 重点问题 | 产物与验收重点 |
| --- | --- | --- |
| E1 测试条件与播放协议 | 版本、构建、设备、相机/路线、分辨率、种子、缓存、温度和阶段怎样固定或记录？ | 可复现协议；明确空场景/单体/组合、首用/重复/持续运行，以及测试启动、结束、超时和异常 |
| E2 指标到采集方式 | 公开计数器、Profiler、系统/GPU 工具或项目插桩各自能测什么？怎样对齐原始帧和事件？ | 采集适配表：定义→来源→支持版本/平台→单位/范围→延迟→扰动→不支持时处理；先选一种确定环境，不承诺全版本适配 |
| E3 校准与对照 | 怎样发现漏计、重复计数、累计稀释、背景混入和工具扰动？ | 已知答案的小样例、原始记录与误差分析；优先校准特效一条链，再以 UI 检查可复用性；保留失败样本和未验证范围 |

### F. 工具与监测体系

| 单元 | 建设目标 | 验收重点 |
| --- | --- | --- |
| F1 系统设计 | 将领域需求落实为配置、检查、运行、采集、记录、报告、规则和复验职责 | 每个模块能追溯到前面一项实际需求；公共部分与领域适配分清，不预设大型平台或具体 UI 技术栈 |
| F2 最小原型 | 先完成特效的单任务执行、有效性检查、原始数据、报告和复跑 | 一份配置能复现报告；通过、超预算、失败、不支持分别呈现；原始数据到结论可追溯 |
| F3 第二领域与组合 | 接入 UI 验证抽象，再扩角色/动画与场景 | 能复用身份、存储、规则和报告；领域指标和操作不被强行统一；组合统计不重复相加 |
| F4 回归与持续监测 | 批量、取消/超时、基线比较、规则版本、告警、责任交接与复验 | 注入明确故障及回退能被发现和处理；误报、例外、恢复与规则修订有记录；团队运行效果另取证 |

F1 先形成可评审设计，F2–F4 再逐步实现和验证。线上遥测留作后续扩展，另行定义数据需求、采样成本与适用平台；本期以资源检查、受控运行及场景/设备回归形成可用链路。

## 4. 每批怎样学习与交付

每批按下列顺序推进：

1. 确定本批 1–2 个工作单元及目标问题，列精确文件范围和已有材料。
2. 按[旧文检索与复用判断](article-production-workflow.md#article-reuse-preflight)复读当前正文、必要来源与原 plan；在本批记录中简述“已有覆盖、需调整处、复用决定、本次增量”。选择直接复用、原位补充、修订旧文或独立成篇；新篇先在其唯一 canonical plan 登记。历史审查可复用，但不能把已修问题继续列为缺口，也不能只看标题或待写状态。
3. 先形成原理解释、必要图示/算例与误判说明，再提出采集或验证需求。操作步骤保持服务于解释。
4. 用问题或教学场景检查理解，记录哪里仍缺桥梁；不以“读过”替代能解释或做判断。
5. 需要实验时单列方案、条件、原始证据与待验证项；已有数据不足以支持的结论保持未知。
6. 按[性能专栏质量标准](client-performance-quality-standard.md)记录本批适用条款、证据位置、缺项和处理；回写对应系列的文稿状态，以及本文的任务批次、证据和下一步。公开正文完成后按仓库规范验证；提交和发布按实际授权及结果另记。

作者提供产品意图、实际约束和学习反馈；助手负责材料核对、解释整理、实验设计及授权范围内的实现。项目预算、必要体验与接受责任按真实团队决定，不能由工具默认值代替。

本轮审查已将具体调整定位到[复用记录 R1–R8](client-performance-existing-content-review-2026-11-04.md)。每批先处理会影响本批读者判断的相关问题，再补增量；不要求全站旧文先全部重写，也不把新专栏的更大范围当成每篇旧文的缺陷。

### 4.1 固定每批的交付与退出条件

每批围绕一个读者问题推进，默认同时只有一批正文处于起草和修订；资料核对、独立审稿与实验准备可并行。基础和写作批次应形成读者可见的正文增量，位置可以是已有文章的补节，也可以是登记后的新篇。仅新增内部提纲、指标清单或计划不能算这一批正文完成；实验批次则以可追溯记录为交付，不强求每次实验单独成篇。

每批结束只维护一条接续记录，包含：

`主要问题 / 实际改动文件 / 复用决定和正文增量 / 来源或实验身份 / 适用质量条款及审查结果 / 本地页面检查 / 作者理解反馈 / 未完成项与下一批 / 提交发布状态`

助手负责旧文与来源核对、解释和图表、实验方案、文稿整理及可执行的验证；作者负责实际产品约束、必要体验取舍和学习反馈。涉及设备操作与项目材料时按真实可用条件分工，不在每批重复索取基础信息。审稿至少检查技术与证据、阅读与导航；关键结论可由独立审阅补查，审阅不代替实验复现。

文稿达到适用条款、读者能沿正文完成预定判断且站点检查通过后，就结束本批并回写状态。未回答的延伸问题进入后续单元，避免把最小字典不断扩大成全领域百科。作者是否已经掌握另记为“待反馈／已反馈及卡点”，助手不能代答后认定作者通过。每批给一个改变条件的问题，据反馈调整下一批的补桥深度。

不预设缺乏依据的总工期。P1/P2 完成后，依据实际写作、审稿和作者反馈节奏，再估计后续批次；设备实验另受工程和设备可用性约束。正文、实验、工具、采用及线上发布沿第 6 节分别记账。

### P1 的具体执行单

**核心问题：**面对“首次打开界面并出现特效时卡了一下”，应该定义哪些观测对象，什么数据才能支持判断？

**先读与复用：**一帧拆解、帧预算、内存记账、资源就绪和诊断方法；再取 UI 首开与特效生命周期的必要段落。已有源码分析只作后续采集口径的参考，本批不移植或改造 ParticleEffectProfiler。

**动笔前处理：**复核旧文审查 R1 的同帧消费表述并做最小修订；A1 引用一帧已有指标表和统计定义，再接业务对象与事件字段。其余 R2–R8 随预算、分档、测量及对象专项处理，不扩成 P1 的统一前置。

**产物：**一份包含字段定义与反例的最小指标字典；一张请求、资源就绪、创建/激活、首次绘制与反馈的依赖示意；一份“观察到什么、候选原因、还需什么证据”的记录。不预填 CPU/GPU 耗时或设备阈值。

**读者交付位置：**2026-11-04 完成通用主线的复用判断后，独立登记为[专栏主规划](client-performance-engineering-series-plan.md)中的 CPE-01。已有一帧、就绪与诊断文章提供机制定义，新篇负责把多对象、多阶段连成一次操作的观测方案，独立阅读职责明确。以首开界面与特效为教学任务，正文主线保持引擎无关；具体引擎回调、标记与采集实现留后续映射。不能以只留在 `docs/` 的材料代替正文交付。R1 修订留在原文，相关状态回原 plan；首页在正文存在且验收后再接入准确入口。

**首轮范围：**

- 沿现有定义选择应用帧间隔、CPU/GPU 执行范围、请求到 Ready、首次反馈及分层内存等必要观测；每项给对象、单位、边界、来源候选、有效条件及不能推出的结论。数量由任务决定，不填全领域指标目录。
- 事件图按同一次请求关联资源、实例和帧；请求到达、Ready、创建/激活、提交绘制和用户看到反馈分别说明。只有引擎回调时，将其作为代理观测，保留到实际呈现之间的未知区间。
- 至少对比几种可区分的解释，例如资源准备较晚、主线程创建/重建较重、首次渲染准备或 GPU 负载较大；指出区分它们所需的证据，不预判某项就是根因。
- 附字段可填写的观测表与一个改变条件的问题，例如“资源已经驻留，首开仍卡，下一步查什么”。正文提供推理线索；作者反馈单独记录。

**理解检查：**

1. 为什么粒子数少仍可能出现首放长间隔？
2. 为什么 CPU 时间、GPU 时间和加载总时长不能直接相加？
3. 为什么资源已加载与用户已看到反馈不是同一个完成点？
4. 为什么共享纹理、实例内存和对象池保留量要分开记录？
5. 为什么长窗口平均值不能替一次首开事件验收？

**本批完成条件：**正文内能找到完整任务、事件图、观测表、竞争解释与必要来源；字典字段能够描述该任务，示意不混淆时间与归属，五个问题能获得有依据的解释。按 S1–S4 检查适用项，其余条款按内容选用；需要实测的部分明确列出。完成 R1 的最小修订、相关 plan/首页的必要同步、模板回归、Hugo 构建、生成页及阅读检查，记录作者理解反馈状态与尚未执行的验证。随后据此决定 A3/A4 的具体补桥文件，不提前扩写完整五类对象观测表。
