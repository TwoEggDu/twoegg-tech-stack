## 1. 学完后应具备的能力

学习目标是能够解释并做出以下决定：

1. 界定产品必须保住的响应、流畅性、加载、稳定性及视觉信息，选择支持范围和代表场景。
2. 区分 CPU、GPU、内存、加载、呈现与持续性能，理解哪些指标描述工作量，哪些描述实际运行结果。
3. 从体验目标、场景负载与设备条件推导预算，记录余量、阈值依据和超线动作。
4. 建立适合项目的设备能力分档，映射到画质配置，并理解运行时动态调节的适用条件与代价。
5. 解释 UI、场景、角色、动画、特效的成本链与生命周期，选择有意义的观测点。
6. 定义指标，选择采集方式，验证数据范围、准确性、可重复性和采集扰动。
7. 用统一记录连接资源检查、受控测试、设备与场景回归、异常处理和后续运行反馈。

完整覆盖指这些决策都有可解释、可验证的依据，不以收集所有 API、硬件型号或图表为目标。物理、音频、网络等保留原 CP-10 专题入口；先完成已指定的五类内容，再按实际缺口扩展。

## 3. 预算基础应具体展开什么

### 3.1 先定义目标，再分配预算

从支持设备、目标帧率、分辨率、画质和代表性任务出发，明确必须保住的操作反馈与视觉信息。帧节奏 `1000 / 目标 FPS` 是起点；CPU/GPU 分别审视自身工作与依赖，不把两者耗时直接相加。

预算按体验和生命周期分别记录：稳态帧间隔及持续超线、首次使用事件、场景切换或页面就绪、内存常态与峰值、缓存/对象池保留，以及持续运行的性能和热约束。加载总时长可跨 CPU/GPU/I/O 阶段，不能重复加到账本。

### 3.2 自上而下约束，自下而上校准

教学应走完：体验目标 → 代表场景与基线 → 候选分配与余量 → 增加真实内容负载 → 单项变化与组合复测 → 修订资源规格及验收线。

帧预算、对象预算和资源规格属于不同层次。粒子数、骨骼数、DrawCall、纹理尺寸等可形成制作预警，但与时间、内存成本的关系要在适用范围内校准。不能从一个总预算直接按人数等分，或把对象单测结果相加来承诺场景通过。

### 3.3 阈值包含完整的判定条件

每条规则至少保存：对象/场景、设备范围、画质及分辨率、阶段与窗口、指标及单位、统计方式、阈值与依据、适用版本、例外条件、负责人和复验动作。

- 正确性失败：违反明确的引用、生命周期或表现约定。
- 性能验收失败：在指定条件下没有满足经确认的体验或资源预算。
- 预警：命中风险代理或接近预算，需要复核，不能自动当作性能失败。
- 相对回退：与可比基线相比出现退化；需要同时考虑绝对影响、重复结果和测量波动，不能只看百分比。
- 数据无效/不支持：不能获得所需结论，与实际测得的零分开。

平均值、分位数、峰值、超预算事件数与连续超线持续时间分别解释。首放必须有独立事件窗口；长窗口的 P95 不能替首放验收。初始阈值是待校准方案，实际值应带样本、环境和修订条件。

## 4. 机型分档应具体展开什么

### 4.1 三个概念分别建模

| 概念 | 描述什么 | 与其他两项的关系 |
| --- | --- | --- |
| 设备能力档 | 本项目负载下，CPU/GPU、内存、带宽、存储、API/格式支持和持续运行能力 | 为默认策略提供依据；CPU强、GPU弱或内存受限的设备未必能压成同一个标量排名 |
| 画质配置档 | 渲染分辨率、阴影、LOD、后处理、纹理、动画更新及特效等配置组合 | 在预算与体验约束内映射设备能力；名称与设备档可以不同，且要保留生效配置身份 |
| 运行时动态调节 | 根据持续负载、系统状态和用户目标调整允许变化的配置 | 设置上下界、稳定窗口、滞回/冷却与恢复策略；暂时变慢不等于永久降低设备能力档 |

高中低可作为项目沟通入口，背后的维度、配置和测试依据仍需可追溯。档位数量由产品支持范围、区分收益、资产变体和测试维护成本决定，不预设三档或四档必然最好。

### 4.2 分档方法

1. 定义最低支持条件与必须保住的玩法/可读性，区分兼容性不支持与性能不足。
2. 根据实际用户设备范围或明确的目标市场选候选设备；未取得用户分布时说明选择依据。
3. 记录硬件、整机、软件、显示及环境条件。芯片名、RAM、年份和综合跑分可作筛选线索，不能直接决定最终档位。
4. 以覆盖 CPU、GPU、内存、加载和持续负载的代表场景验证；记录冷启动、首用、稳定运行和热状态差异，不只跑一个短场景。
5. 校准可接受的默认画质组合和表现质量；同一 SoC 的不同整机、不同软件配置仍有验证范围。
6. 对边界、未知和异常设备定义保守回退、重测及规则更新；记录最终采用的配置与变更原因。

设备 × 画质 × 场景 × 构建 × 生命周期阶段构成验证矩阵，按风险选择覆盖组合。某档一台样机通过不能证明全部同档设备通过；未覆盖范围单列。用户可选项、资产切换成本、必要体验和动态策略要共同约束，不能用自动降质掩盖异常。

## 5. 五类对象的观测基础

| 对象 | 成本模型与观测点 | 关键操作/窗口 | 容易混淆的边界 |
| --- | --- | --- | --- |
| UI | 数据更新、布局/图形重建、文本与图集、批次、透明覆盖、加载/分配与驻留 | 首开、重开、切页、滚动、刷新、关闭、重新打开 | uGUI/UI Toolkit 等实现口径分别核对；隐藏、不可见、停止更新和释放不是同一状态 |
| 场景 | 可见集合、LOD、材质/Pass、灯光/阴影、Streaming、纹理/Lightmap/RT 与加载峰值 | 固定镜头和路线、进入、跨区域、玩法高峰、退出 | 场景承担组合验收；可见对象数不等于所有实际提交/执行量，单机位不代表整场景 |
| 角色 | 几何、骨骼/权重、蒙皮、材质/贴图、LOD、换装、同屏实例与阴影 | 创建、激活、换装、远近切换、多人同屏、回收 | 共享资源与实例增量分开；角色整体成本已包含的动画/蒙皮不能重复相加 |
| 动画 | 状态推进、采样、混合、IK/约束、姿态写回、蒙皮、片段驻留与压缩误差 | 播放、转场、混合、打断、事件、退屏、恢复 | 源动画采样率、运行求值频率、显示帧率分别解释；减频需验收根运动、事件、挂点及动作信息 |
| 特效 | 发射/模拟、存活粒子、几何、批次、覆盖/重叠、材质、资源与生命周期 | 首放、稳态、爆发、叠加、停止发射、尾部消退、回收 | 覆盖诊断与原材质耗时分开；粒子数或累计平均值不能独立保证性能 |

共同观测与判定表字段：**对象身份 → 事件/阶段 → 指标定义 → 成本关系 → 预算依据 → 采集方式 → 数据有效性 → 超线动作**。每个领域都要说明规模、频率、时机和正确性，不能只复制一张计数器列表。

## 6. 准确采集与监测体系的衔接

先定义指标，再选择公开 API、Profiler 标记、系统工具、GPU 工具或项目插桩。具体可用性按 Unity、渲染管线、构建、设备/API 核对；无可用证据时保留缺失状态。工具实现的职责是满足已定义的测量要求。

测量基础必须覆盖：已知答案校准；重复性与准确性的区别；因果对照与混杂变量；采样/事件时间对齐；不同窗口及聚合方式；冷/热与缓存状态；外部场景负载；额外渲染/读回/插桩扰动；原始数据与报告复现。一次开关差值只证明该组合条件下的变化，不能当作可独立相加的固定对象成本。

| 层次 | 负责什么 | 不足以证明什么 |
| --- | --- | --- |
| 资源静态检查 | 引用、结构、导入与制作规则 | 目标设备上的实际性能合格 |
| 受控实验/单体测试 | 校准指标、理解成本因素、验证明确假设 | 全部场景和并发组合通过 |
| 场景与设备回归 | 原渲染路径下验证组合负载、阶段、预算和正确性 | 所有未覆盖设备和用户环境都相同 |
| 持续监测与反馈 | 跨版本比较、异常取证、复现、修改与复验；线上遥测作为后续扩展 | 仅凭告警自动判定根因或优化效果 |

统一的部分是配置与版本身份、数据定义、存储/报告、规则和复验流程；各领域保留采集适配与测试动作。角色、动画、UI 和场景可能观察到同一执行阶段，统一报告必须保留父子及共享归因关系。

后续体系设计覆盖调度/超时/失败、指标有效性、基线比较、预算版本、报告和责任交接。线上扩展再评估数据需求、采样开销、数据最小化与平台约束；不把线上接入作为基础学习或本地测试的前置。
