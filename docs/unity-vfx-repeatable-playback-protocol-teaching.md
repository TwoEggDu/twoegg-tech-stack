# VFX-T04 准备材料：一次奖励界面与特效的纸面播放协议

> 2026-11-06。本文是 E1 协议、E2 事件/CPU 区间来源及 E3 首批事件校准设计的知识输入，归属[特效测试唯一规划](unity-vfx-testing-series-plan.md)的 VFX-T04；不是新增篇目、完整正文、可运行脚本或已执行实验。所有身份、配置、事件与时间均为虚构教学输入，未选定实际工程、设备和接受阈值。作者理解仍待反馈，实践入口沿[知识阶段出口](client-performance-budget-tiering-monitoring-execution-plan.md#knowledge-stage-exit)。

## 先决定这一次何时算结束

客户端程序和 TA 准备比较首开奖励界面的表现。如果每次只按播放键，看到根粒子消失就重新开始，上一轮的子效果、异步返回或池内状态可能混入下一轮。报告即使有运行编号，也未必记录了同一种任务。

本例只做一件事：应用接受一次打开奖励界面的请求，准备奖励内容并触发一组确认特效，随后结束展示并退出。需要分清三个不同的终点：

| 终点 | 本题怎样认定 | 不能据此认定什么 |
| --- | --- | --- |
| 应用就绪代理 | 本次界面与特效逻辑状态已提交，满足约定后续处理条件；与 CPE-02 定义相同 | 内容首次可见、可交互、GPU 完成或屏幕反馈 |
| 播放组自然结束 | 本次组内所有约定成员都不再存活或继续产生；没有取消或主动清空替代正常收尾 | 整个进程没有工作，或资源内存已经归还 |
| 退出确认 | 本次持有已交接或结束，实例重置/销毁结果和迟到工作去向明确，能够重新核对下一轮初始条件 | 缓存全空、设备降温或下一轮自动成为一次独立首用 |

本批沿用[请求与观测模型](../content/performance/client-performance-task-observation-model.md)的身份、时间域和缺失定义，沿用[CPE-02 草稿](../content/performance/client-performance-test-comparability.md)的可比性与异常保留规则；后者仍是 `draft: true`。本题新增的是怎样按这些定义**开始一次任务、停在正确分支并交出退出记录**，不另建通用工作流。统计与实际采集仍回原篇及后续 E2/E3。

## 开始前，把纸面条件交给下一位执行者

本例选“同进程第一次打开、资源输入已准备、目标实例尚未创建”的组。它既不是全冷启动，也不是同进程重开。以下值足够用于纸面复核；实际执行须先用真实且可核验的身份替换，不能拿 H1 等占位值生成正式报告。

| 条件 | 本题约定 | 实际协议需要交出的依据 |
| --- | --- | --- |
| 候选身份 | 虚构构建 H1、内容 C1、协议 P1；运行 R 各自独立标识 | 仓库/产物与内容身份、引擎/管线/包、平台/图形 API、构建选项和采集配置；实际环境待定 |
| 任务与范围 | 奖励数据 D1；界面 U；特效组 F 含根 F0 和子 F1，均为有限播放；背景 B1 继续运行 | 实际成员清单、挂点/空间、版本和共享持有；本题不含网格尾部、后处理、外部重触发或循环成员 |
| 镜头与输出 | 固定镜头/布局快照 K1、挂点 X1；内部目标与输出均为 1280×720，动态分辨率关闭 | 保存实际相机/视口/布局、目标尺寸和生效画质；不能只写“高档” |
| 随机与推进 | F0/F1 的教学种子分别为 101/102，不自动换种子；输入顺序固定 | 保存每个系统的种子/自动种子状态、模拟时步、时间缩放、暂停及外部输入；同种子不能单独证明逐帧或跨设备相同 |
| 起始状态 | D1 与约定资源输入已就绪；U/F 无存活实例，上一请求无未处理写入；池为空 | 用途就绪、实例/池及在途任务清单，保留不受控的 OS/驱动缓存；“新进程”不等于缓存全空 |
| 运行条件 | 纸面假设背景、供电/热状态、限帧和采集方式一致 | 记录设备/OS、温度/热限制、供电、后台负载、限帧及实际开关；不可控或缺项时标记，不能伪填相同 |
| 观察上限 | 请求后 500 ms，代理或播放组自然结束任一仍未确认便进入相应超时分支；退出另给最多 100 ms 观察 | 两者均为本题便于保留失败的截止值，不是性能预算或获准用于项目的阈值 |

开始检查由执行者保存，采集配置由程序/TA 复核。缺必要身份、上一轮退出不明或观测尚未准备好时，不发出本轮请求；保留未启动的原因，回到执行计划 T1/T2/T3。不能先开始，再从结果挑一个看似稳定的窗口。正式重复顺序和次数需按比较问题与波动设计，本题四条分支不是四次独立实测。

## 一次请求的动作与退出判据

这里的“组”是本题明确列出的 F0/F1，不能靠根对象名字推断成员齐全。每个事件保留运行、请求/代次、实例/成员、发生时间与读取时间、时间域、结果及有效性；准备在请求前完成的输入，直接记录其已有状态，不补造一次加载事件。

```text
核对条件 → 观测先就绪 → 接受请求 q/g → 准备与播放
  ├─ 应用就绪代理：留下时长，继续观察播放组；不是协议直接退出
  ├─ 自然收尾确认：记录组内成员 → 正常关闭 → 退出核对
  ├─ 取消 / 已知业务失败：封闭旧代次 → 按规则停止/清理 → 退出核对
  └─ 到观察上限仍无终点：记超时与最后阶段 → 请求取消 → 退出核对
退出确认 → 归档本轮，再核对下一轮条件
退出超时或不明 → 保留残留与待处理者，禁止直接接成隔离重复
```

| 步骤 | 发出什么、观察什么 | 不满足时怎样留记录 |
| --- | --- | --- |
| 请求前 | 先开启拟用观测并确认能记录；保存背景/初始状态；接受请求时分配 q/g 并记 t0 | 预检查失败记未启动；已接受但起点丢失则记计时缺失，不能把后续第一条日志改作 t0 |
| 准备与开始 | 分别留输入就绪、实例准备、实际开始播放及成员范围；记录本次状态提交的代理事件 | 不能用 Play 调用返回充当首次可见；缺事件只保留最后确认阶段 |
| 正常收尾 | 本例等待全部约定成员自然结束，再按约定关闭界面；留代理终点与播放组终点两条记录 | 根已结束但子仍活跃时继续观察；只有子系统计数不足以证明整个任务成功 |
| 取消或已知失败 | 留触发原因与最后阶段；本题取消规则为关闭展示、请求立即清空本组，并让旧代次无法写入新任务 | 请求停止不等于已生效；已知业务失败保留原错误。没有取消通道的底层工作继续追踪，不写“已中止” |
| 观察超时 | 截止时缺终点，先保存未完成/未观测状态，再按本题规则请求取消；已有代理时长继续保留，另记播放组超时 | 观察超时不等于业务最终失败；截止后的终点另记为迟到，不回改成截止前成功 |
| 退出 | 确认组内尾部、界面/实例、延迟触发、在途返回、订阅和本次资源持有的去向；记录重置或销毁确认 | 未能确认则写未知/退出超时，留责任人及后续记录。共享资源只结束本次持有；回池不等于系统释放内存 |

“封闭旧代次”是业务协议要求：旧工作返回后只能进入旧请求的处理分支，不能更新或结束新请求。底层工作若不能停止，就由原请求负责接收并结束其持有，或明确交给一个继续追踪的拥有者。本例的**隔离重复选择等待旧工作得到处理**；若改成允许重叠，须明确隔离机制和共享负载，另立组合组，不能默认为本协议仍成立。

退出检查也不能无限等待。100 ms 内未确认时，记录最后状态，停止本轮安排，交程序/TA 查残留；保留当前运行证据，重建可确认的环境后再开始新的运行。重启会改变部分状态，仍不能宣称恢复所有缓存/温度。退出阶段的计时和工作单列，不混入请求到应用就绪的代理时长；若实际采集没有覆盖退出，就标未测。

## 用四条合成轨迹复核，而不是先写控制器

每行是一条单独的纸面分支，每次请求接受为该运行单调时钟的 0 ms；只在同一行内相减。列出的时刻是题设确认事件，不是从配置推算的真实结束时间。所有分支的 GPU、呈现与屏幕反馈均未测。

| 分支与原始事件（ms） | 代理结果与样本处理 | 退出与下轮条件 |
| --- | --- | --- |
| N：接受 0；复核输入已就绪 30；本组开始播放 50；应用就绪 60；F0 自然结束 120；F1 自然结束且本组无后续产生 180；正常关闭/退出确认 200 | 代理时长 `60−0=60 ms`；30 只是复核已有状态，不补造加载区间；播放组自然结束为 180，不是 120 | 正常退出在 200；从组结束到退出为 `200−180=20 ms`。重开须新 q/g，并归同进程重开组 |
| C：接受 0；本组开始播放 20；用户取消 30；清空生效确认 40；旧请求的异步回调在 80 到达且按旧 q/g 处理；本次持有/状态核对在 100 完成 | 取消前未到代理终点；代理时长缺失，30 是取消时刻，不能作一次成功时长；40 是强制清空，不是自然结束 | 从取消到退出为 `100−30=70 ms`；不能在 40 就认定可隔离重跑。若 110 再开，须重新核对状态、使用新身份并归重开组 |
| T：接受 0；截止 500 仍无代理或组结束确认；请求取消；退出在 540 确认 | 观察超时；业务在截止时的结果未知。代理时长不填 500 或 0，不丢弃本行；后续结果另记 | 退出处理区间为 `540−500=40 ms`，不因此变成一次成功代理耗时；若到 600 仍无法确认，改记退出超时 |
| M：接受 0；本组开始播放 50；代理记录缺失；事后业务记录能确认本次逻辑状态成功；本组结束 180、退出 200 均有记录 | 业务成功与计时缺失并存；不能把 180 或 200 补作代理终点；不纳入成功代理时长集合 | 退出可以有证据；业务成功不能补齐缺失的计时。若身份也关联不上，连业务结果也应保留未知 |

N 中根结束后还有 `180−120=60 ms` 子成员尾部。若只按根零粒子重启，就把未结束的 60 ms 从正常播放窗口里漏掉了，还可能让下一轮含有旧负载。C 中即使组内已清空，也要处理 80 ms 的旧返回，才能支持本题选择的隔离条件。这两个反例分别检验**播放范围**和**退出范围**，不能用同一个“结束”字段掩盖。

四行里只有 N 提供完整的成功代理时长；M 业务成功但计时缺失，C 取消，T 超时。不能称“平均为 60 ms”来代表全部请求，更不能据这一个合成值估计真实波动。各状态的数量、原始事件和缺失原因需一同交出，分析方式复用 CPE-02。

停止/尾部与活跃量的机制直接复用[特效预算生命周期教学](../content/performance/game-budget-09-vfx-budget.md#vfx-lifecycle-teaching)，不重做其粒子账本。正常/取消与拥有者责任复用[特效制作与接入](../content/delivery-engineering/game-art-production-08-vfx.md)的“时间、空间和结束条件”及预览退出段；其中素材、场景和代码仍待实际验证，不能当成本题已有测试工程。

## E2 首批：事件在哪里取，何时被读到

前面的 N/C/T/M 将事件时刻作为已知题设，便于检查协议。实际记录还需回答：**这个时刻由谁写下，描述的是状态变化，还是观察者后来读到了变化？** 本节只把来源需求映射到候选采集点，尚未接入或验证任何一个事件。

### 业务事件、循环标记与状态查询分开

| 所需观测 | 来源候选与记录点 | 范围、时间和缺项 |
| --- | --- | --- |
| 请求接受 → 应用就绪代理 | 由业务适配在接受本次 q/g、提交本次逻辑状态的两个约定点分别留记录 | 两点必须属于同请求、同已验证时间域；在源点读取时间，另留写入/读取时间。具体函数、执行线程与成功谓词仍待工程定义，不能用 Start/Play 或一个名叫 Ready 的 Marker 自动替代 |
| 应用间隔 | 在同一运行、同一循环阶段的标记点读取时钟，以本采集流连续序号组织相邻读数 | 这是该标记的经过时间，可能含等待；间断保留缺口。frameCount 可作辅助来源字段，不是渲染/GPU/显示身份；后台线程或其他阶段不能混进同一序列 |
| 播放组结束 | 按本题 F0/F1 范围查询 IsAlive，或接入能证明同一范围的结束通知；同时留自然结束/清空原因 | 查询留成员、withChildren、观测时刻和前次有效状态；首次 false 是发现时刻。若根之外还有对象，或旧代次/暂停/重触发关系未明，整个组的终点仍缺证据 |
| 退出确认 | 由拥有者核对本次在途任务、实例/订阅/持有与重置结果，逐项记录；都满足才留本次退出确认 | 对象被销毁不等于清单全部满足。若只采到某个回收/销毁回调，就命名为该局部事件；没有确认记录则保留未知，不用最后一帧或代理终点补齐 |

“源点读取时间”指记录语句执行到约定点时读到的时间。异步日志稍后写盘，写盘时间不能回填成事件时间；如果只能在回调到达时读取，指标就只能叫“回调到达”，源事件时刻仍未知。记录线程与先后关系，不能据同名 Marker 或时间接近跨线程配对；Unity 主线程候选时钟也不自动证明任意线程均可调用或与其他时钟已对齐。

### Unity 6.0 可读出的量，与仍需自行定义的量

以下四份是本轮新读取的公开契约。选择它们是为检验上述候选，不是把接口名直接填成已经有效的来源。

| 来源 | 文档明确的量或条件 | 对本协议的取舍 |
| --- | --- | --- |
| [realtimeSinceStartupAsDouble](https://docs.unity.com/en-us/engine/6000.0/script-reference/unityengine/time/realtimesincestartupasdouble) | 应用开始后的秒数、double；不受 timeScale 影响，一帧内可变化；依赖系统计时器，数个连续帧也可能读到同值。所列桌面/Web/XR/移动平台包含系统休眠时间，主机平台另查 | 可作为选定主线程点的候选秒时钟，差值乘 1000 得 ms；先核精确版本/平台、分辨率、暂停/休眠和误差，不称它已经校准。double 表示精度不等于真实计时精度；相同读数不证明工作零成本 |
| [deltaTime](https://docs.unity.com/en-us/engine/6000.0/script-reference/unityengine/time/deltatime) | 返回帧间隔秒数，但在 FixedUpdate 内返回 fixedDeltaTime，并受 maximumDeltaTime 限制；OnGUI 内不可靠 | 不拿它替代两个业务点的采时，也不默认等同本节同阶段标记之差。若改循环阶段或时序设置，重新核对定义 |
| [frameCount](https://docs.unity.com/en-us/engine/6000.0/script-reference/unityengine/time/framecount) | 在 Update 阶段递增；Awake 中的值未定义 | 只作当前运行的辅助关联字段；请求、采集流序号及 GPU/呈现关系仍分别保留，不能只按帧号拼接 |
| [ProfilerMarker](https://docs.unity.com/en-us/engine/6000.0/script-reference/unity/profiling/profilermarker) | 为脚本代码块加标记，在 CPU Profiler 显示；文档明确 Begin/End 在非 Development 构建中会被条件编译移除 | 用来定位约定代码范围，不能仅凭 Marker 名自动获知业务成功或跨异步等待。真实采集须核对构建/采集开关和记录是否存在；不能把 Begin/End 的说明扩成所有分析接口都同样可用或都消失 |

该时钟页面还注明 **OnDestroy 中返回错误值的已知问题**。这是本轮所读页面的限制提示，不证明所有补丁都存在同一表现；精确补丁、修复状态及替代时钟仍待查。因此退出确认先由上述业务清单定义，不以 OnDestroy 内一次读数作为默认可信终点。若需要覆盖销毁完成后的时刻，要另选可验证的外部观察点与时间域，并注明它与实际销毁之间的范围。

### 两个纸面例子：延迟读取与轮询边界

下面是独立于 N/C/T/M 的合成输入；不是它们的补测或真实 Unity 读数。教学假设同一已对齐时钟、无读时误差或查询耗时，单位原为 s。

| 原始输入 | 可复算判断 | 不能作出的判断 |
| --- | --- | --- |
| 请求接受在 1.000；应用代理源点在 1.060；分析者在 1.120 读到完整记录 | 代理时长 `(1.060−1.000)×1000=60 ms`；代理记录从源点到被读到相隔 `60 ms` | 不能按读取时刻算成 120 ms 代理时长；若 1.060 实际缺失，只剩 1.120，则不能倒推仍是 60 |
| 同一已开始的 F0/F1 组，在 1.104 查询为 true，1.120 首次查询为 false；期间无重启、外部重触发、主动清空或范围变化，之后保持结束 | 整组自然结束时刻只可界定在 `(1.104,1.120] s`，边界宽 `16 ms`；1.120 是发现时刻，理想条件下发现比真实结束晚 `0≤延迟<16 ms` | 不能宣称实际结束恰为 1.120，不能把 16 ms 当实测工具开销；若中途重启或被清空，原自然结束推断不成立 |

```text
源点事件：接受 1.000 ── 代理记录 1.060 ── 分析者读取 1.120
状态轮询：                    true 1.104 ── ? ── false 1.120
                                           只知道转换在两次查询之间
```

轮询增频可以缩短理想观测间隙，也会增加查询/记录工作；事件通知能缩小某些发现延迟，却依赖产生者覆盖范围、触发时机及身份。选择依据是要判断的时间尺度和可接受扰动，不能统一要求每帧检查。真实查询有执行区间、时钟有量化/误差，须保存前后包围时间并放宽上述界限；时钟本身也可能连续返回同值，不能以 double 或每帧读取承诺 16 ms 上界。

本节没有测得任何开销。后续 E3 应在已知输入下检验事件漏记/重复、读取延迟与查询间隙，再分别比较启用/关闭必要采集的同条件记录；记录成本可能改变被测工作，不能先假定采集后的数值减去一个常数就能还原原状。这里只登记校准问题，不运行采集器。

新增理解检查：若两次查询都 false，但其间发生一次外部重触发，能否证明整段没有工作？若把起止点移到 FixedUpdate，或只在 OnDestroy 里记退出，原指标的哪些定义/来源必须重查？若同一时钟连续读数相等，应怎样保留时间分辨率限制，而不是宣称零成本？作者作答待记录。

## E3 首批：给事件采集准备能判错的输入

本节把 E2 的缺项收成三个最小验证块，**全部待执行**。要验证的命题是：给定明确的请求/成员与观测条件，记录能保存身份和结果，暴露缺失/重复，并按来源强度报告时间。已有 CPE-02 负责记录可比性，上文负责候选来源；这里不重做统计，也不承包覆盖率、GPU 或内存采集器的校准。

实际开做时沿原协议固定构建/内容、精确引擎/管线/包、设备平台、采集设置和初始条件；使用独立教学环境与自有最小对象。它们尚未选定，不因本设计落盘而满足运行前置。先准备**输入计划与独立确认账本**，再交给被测采集链；计划发出某动作不等于动作已生效，参考确认怎样取得也必须验证。不能把待验证采集器的同一份输出复制一遍，便称为已知答案。

```text
预置输入 → 参考确认及其有效性 ─────────────┐
         → 被测采集 → 原始记录 → 按身份/范围/时间核对
                                  └─ 通过 / 失败 / 证据不足
```

### 验证块一：同样九行，也可能漏了子成员

先只检验事件传递、归属和重建。下面是锁定的**合成参考账本**，同一运行 R、时间域 C，单位 ms；它不是真实播放记录。本块刻意允许 q1 的工作在 q2 开始后返回，用于挑战旧代次隔离，不能混进 E1 的隔离性能重复。q1/q2 分别使用 O1/O2，F0/F1 是 O2 的明确成员。

| 源事件 ID | 请求/代次 | 对象/范围 | 确认事件 | 源时刻 ms |
| --- | --- | --- | --- | --- |
| E01 | q1/g1 | O1 | 接受 | 0 |
| E02 | q1/g1 | O1 | 取消 | 10 |
| E03 | q2/g2 | O2 | 接受 | 30 |
| E04 | q1/g1 | O1 | 旧准备结果到达，不写入 q2 | 40 |
| E05 | q2/g2 | O2 | 应用就绪代理 | 50 |
| E06 | q2/g2 | F0@O2 | 根自然结束 | 70 |
| E07 | q2/g2 | F1@O2 | 子成员自然结束，组内无后续产生 | 90 |
| E08 | q2/g2 | O2 | 本次退出确认 | 100 |
| E09 | q1/g1 | O1 | 本次退出确认 | 110 |

未来执行顺序为：先冻结此输入/期望及成员清单，确认参考路径有效，再送入被测链；保留传输顺序、源 ID、源/读取时刻和结果，不先汇总。基线应有九个唯一源事件，q1 四个、q2 五个；q2 的代理时长为 `50−30=20 ms`，组结束为 90，退出为 100。q1 取消不产生成功代理时长，E04 不能结束或更新 q2；根在 70 结束不能提前替代 90 的整组条件。

| 单项失败对照（拟构造） | 应被识别的结果 | 通过/失败/证据不足的界线 |
| --- | --- | --- |
| 删除 E07，并再导入一次同源 E05 | 原始仍九行，但唯一事件只有八个；E07 缺失、E05 重复，整组结束证据不足 | 同源 ID 去重但保留重复清单；不能因总数九就通过，也不能补零粒子或以 E06 关闭整组 |
| 把 E04 的请求标签错写成 q2/g2，保留其源 ID 与 O1 | 与独立参考的 q1/g1、O1 归属不符 | 即使九个 ID 齐全也判归属失败；参考归属未独立确认时只能证据不足，不能按时间相近自动纠正 |
| 去掉 E08，留下 E05 与 E07 | 代理与组结束可保留，本次退出仍未知 | 不能由前两项推退出通过；恢复后保留失败记录，按同一输入重核受影响路径 |

有限账本可穷举这几项；未来重复用于检查缓冲、乱序和状态复位，不能用重复次数替代逐项核对。通过只指本输入的记录契约，不证明真实 Unity 事件产生者完整或其他业务都能用同一适配。交接原始记录、参考证据及其来源、缺失/重复/错配清单和重建结果；结束时确认 q1/q2 与采集状态均已处理，残留未知则保留现场，不接下一次隔离运行。

### 验证块二：时间精度不足时，结论也要收窄

保持成员/代次固定，单独改变读取和时钟条件。未来先检验源记录何时产生、何时读到，再检查查询前后包围时间与时间域。沿 E2 的 Unity 6.0 契约复用时钟同值、FixedUpdate、暂停/休眠及 OnDestroy 限制，本轮不新增接口行为断言。

| 已知输入或单项变化（均为教学设计） | 预期记录与判定 | 不满足时先查什么 |
| --- | --- | --- |
| true 查询包围区间 `[104,106]`，false 查询包围区间 `[120,122]` ms；无重启/清空/外部重触发，结束后保持 false，假设每次查询在其区间内有一致读点 | 只能推出结束在 `(104,122] ms`，宽 18 ms；不能沿用点查询的 16 ms 界限。这里尚未加入时钟误差 | 若读点一致性、包围范围或时间域未确认，判证据不足；真实误差需另放宽，不能把这 18 ms 当平台保证 |
| 三个有效源事件，预置时钟读数为 `2.000 / 2.000 / 2.020 s` | 保留三条不同 ID；报告相邻读数差为 `0 / 20 ms`，零差只说明读数相同，真实经过时间仍受分辨率限制 | 按数值去重、宣称首段零成本或用零作除数均不满足契约；真实精度须用另经核验的参考确认，模拟读数不能标定硬件时钟 |
| 循环采集序号由 1 跳到 3；中间记录未取得 | 留缺口与跨缺口区间，不能伪称两个连续完整样本 | 查源点未触发、采集开关、缓冲丢弃或关联失败；原因未知就保持未知，不把序号改连续 |
| 输入 timeScale=0，另分应用暂停/恢复与系统休眠组 | 候选实时钟按已引契约不受 timeScale 缩放；是否继续读取取决于采集生命周期。暂停空窗、恢复阶段和平台支持分别记 | 有空窗时不能宣称持续采样；不能用这项设计推断所有平台的暂停/休眠时钟行为 |

先用预置读数检验数据处理，再用已确认的参考与真实事件检查实际采时；这两层不能互相代替。把源点与读取点混用应在延迟对照中失败，沿 E2 原例核对即可，不重复一组相同算例。交接原始时刻、读数单位、时间域/误差与支持说明、查询包围区间及缺失表；时钟回退、来源不支持或关键记录丢失时停止输出精确时长，保留可确认的业务结果与失败状态。

### 验证块三：关闭采集后，用什么继续比较

待上述记录/时间契约可核对后，再固定任务与原渲染，设计 A（必要参考通道保留）、B（额外采集开启）、A′（恢复设置）的对照。必要参考通道的来源与自身扰动也要说明，不能假定它零开销，或关闭唯一通道后用“没有记录”证明没有成本。按实际波动安排重复与运行顺序；A′ 不会自动还原缓存、温度或后台状态，漂移时回协议重新分组。

每次同时交出请求结果、参考时长/间隔、源/读取与查询设置、丢样/缓冲情况、采集配置和环境状态。开启采集后事件完整性失败就先修复；若记录完整但时间/状态变化，需要区分采集扰动与条件漂移，保留绝对差异和运行间波动，不能直接减去一个假定常数。**扰动可接受的项目标准仍待校准**，本设计不预填百分比，也不把一次差异不明显写成工具无影响。

负对照再检查构建/开关不支持某来源时，报告是否明确“不支持/未采到”。例如上文只确认 ProfilerMarker 的 Begin/End 构建限制，不能把没有该记录写成代码零成本。实际字段缺失原因和支持状态仍须证明，不能一概归给编译。退出时复核恢复后的实际设置和任务残留，保存恢复失败；停止采集、资源清理及再次启动结果都要有记录，不以脚本正常返回代替它们。

三个验证块交程序/TA 复核。实际执行前还缺精确环境、业务成功/退出适配、独立参考的实现与误差、采集支持和扰动接受依据；当前仅设计可审阅。新增理解检查：九行原始记录为什么仍可能漏掉整组结束？若查询区间内没有可确认的一致读点，应保留哪一级结论？关闭采集后唯一参考也没了，应该补什么而不是宣称通过？作者反馈待记录。

## E2 接续：CPU 条形图里，到底量了哪段工作

应用代理较晚时，程序/TA 需要判断下一步补代码区间、线程调度还是依赖证据。已有[任务观测](../content/performance/client-performance-task-observation-model.md)定义 CPU 区间，[诊断方法](../content/performance/game-performance-diagnosis-method.md)解释执行/等待与关键路径，[组合账本](../content/performance/game-budget-07-scene-budget.md#scene-combination-ledger-teaching)说明父子不重复加账；这里不重做总论，只把**一次请求怎样找到对应采样**接到来源与限用。

先给每个所选区间留下运行、请求/代次、对象、线程、起止点/单位/时间域、源应用帧及原始采样位置。父子采样关系与跨线程依赖分别保存；同名 Marker、相近时间或同帧不足以自动关联对象。缺少业务关联时，只能叫“该线程/窗口的区间”，不能改名为本特效独占 CPU 成本。跨帧工作按实际覆盖保留，不能拿一个帧内汇总替代整次任务。

### 一个合成区间：Self 里也可以有未执行的时间

以下是独立教学运行 RCPU、请求 qC/g1 的**虚构完整采样及另给的线程状态答案**，不是 N/C/T/M 或九事件的补测。时间域已对齐，单位 ms，区间左闭右开。题设为同步等待：主线程 M 的 Publish 是本次选定发布范围，内部两个直接子采样 Build/Wait 不重叠；工作线程 W 的 Prepare 与其有关联，但不是 M 的子采样。名称只是教学职责，不是 Unity 内置 Marker 名。

| 原始记录 | 区间或状态 | 这份来源能说明什么 |
| --- | --- | --- |
| M：Publish 采样 | `[10,18)`，含 Build/Wait | 该标记范围经过 8 ms；不是首开全链或整帧 |
| M：Build 子采样 | `[11,13)` | 被父范围包含的 2 ms，不能再加到父的 8 ms 上 |
| M：Wait 子采样 | `[13,16)` | 等待范围 3 ms；名称本身不能证明具体等待对象 |
| W：Prepare 采样 | `[12,15)`，与请求及等待条件有独立关联记录 | 另一线程的 3 ms；不能从 M 的 Self 中扣除，也不能据时间重叠就建立因果 |
| 独立给定的 M 调度状态 | Running `[10,13)`、`[17,18)`；Waiting `[13,16)`；Ready 未运行 `[16,17)` | 在本题状态覆盖完整且对齐的前提下，可区分运行 4、阻塞 3、就绪未运行 1 ms |
| 独立给定的 W 调度状态 | 在 Prepare 的 `[12,15)` 内全为 Running | 本题另给的运行 3 ms；不能仅凭 Prepare 采样推得 |

```text
Publish [10,18) ── 包含同线程 Build [11,13)、Wait [13,16)
       │
       └─ 独立关联记录 → W 的 Prepare [12,15)；不是采样树子项
M 状态：10 ─ Running ─ 13 ─ Waiting ─ 16 ─ Ready ─ 17 ─ Running ─ 18
W 状态：             12 ───────── Running ───────── 15
```

图只示关系，字符宽度不作时间刻度。按完整同线程采样树，Publish 的 `Self=8−2−3=3 ms`，其范围是 `[10,11)` 与 `[16,18)`。其中包含 Ready 的 1 ms，所以 Self 并非纯执行时间；本题 Self 内 Running 只有 `1+1=2 ms`。另一方面，M 的 Running 共 4 ms，还包括 Build 的 2 ms，不能用 Self 替代父范围全部执行。即使 Running 已知，也不能由此区分有效计算与访存停顿。

另一个常见错误是把 M 的 8 和 W 的 3 加成 11 ms 延迟；它们重叠，也不是一棵可相减的同线程树。本题两线程 Running 可按各自覆盖求和为 7 线程毫秒，但这仍不是 7 ms 端到端延迟。若删去调度状态答案，采样范围及 Self 仍可保留，运行/阻塞/就绪的拆分便应改为未知；不能用上述答案补真实采集的空白。
