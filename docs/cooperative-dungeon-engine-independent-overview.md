# 无尽对决设计总览：从共同游玩到共同制作

日期：2026-10-25（Asia/Shanghai）
状态：引擎无关设计正文初稿，待讨论与验证；不是已完成游戏的复盘。
所属：无尽对决公开设计。设计与独立教学材料公开，Demo 工程保持私有。

## 1. 我们准备做怎样的游戏

无尽对决从一段两人合作副本开始：两名玩家组队进入同一个副本，面对共同的战斗目标，完成挑战后获得结算结果，再返回大厅继续游玩。我们希望它逐步成为能够上线、持续制作内容和维护的游戏。

合作体验是玩法设计首先要回答的问题。两名玩家应当需要观察彼此与敌人的状态，选择何时行动、怎样配合，并从共同结果中得到反馈。具体采用分工、互相支援、协同处理机制还是其他形式，需要通过后续规则设计和试玩决定。仅让两个角色同时出现在场景里，还不足以证明合作成立。

本篇先确定游戏流程、系统职责、内容制作和验证之间的关系。画面维度、视角、输入方式、职业、技能数量、成长深度和完整关卡仍是开放问题，不能从本文推定它们已经选定。

项目有三类并行成果：玩家能够体验的内容，各工种可以反复使用的生产流程，以及能够解释设计与实现判断的公开文章和实验。制作能力应随可玩的内容一起验收，避免游戏只有程序在场才能调整。

## 2. 一次游玩的完整流程

启动与内容准备 → 登录 → 大厅 → 组队与准备 → 进入副本 → 合作战斗 → 胜利或失败 → 结算与存档 → 返回大厅 → 再次进入。

这条流程描述业务阶段，并不要求每个阶段都有独立场景、界面、服务或状态对象。实际拆分由实现路线决定。

| 阶段 | 玩家需要理解什么 | 系统必须明确什么 |
| --- | --- | --- |
| 启动与内容准备 | 当前是否可进入游戏，等待或失败后能做什么 | 代码、配置、资源与服务端是否构成兼容组合，准备失败怎样恢复 |
| 登录与大厅 | 自己的身份、当前可用内容及下一步操作 | 玩家会话、数据加载、失效和退出后的处理 |
| 组队与准备 | 队友、所选挑战、准备状态及进入条件 | 两人是否满足条件，准备失效、取消和成员离开怎样处理 |
| 进入副本 | 正在加载什么，何时能开始操作 | 副本归属、两端准备、进入失败与清理，不让旧流程残留到新一局 |
| 合作战斗 | 自己、队友和敌人的状态，操作是否成功及为何失败 | 规则判定、状态同步、表现反馈，以及死亡、打断、掉线等情况 |
| 胜负与结算 | 本局结果、奖励及其是否已保存 | 结束条件、一次结算的身份、重复请求、写入失败和恢复 |
| 返回与重进 | 当前回到了哪里，是否能开始下一局 | 战斗对象、资源、事件和异步工作已结束，持久状态按规则保留 |

两人合作是正式副本的核心体验。单人预览与调试可以用于制作内容，但不替代双人验收。若一名玩家提前退出，继续、等待还是判负属于待定规则，应在实施完整副本前明确。

## 3. 先确定规则的负责人

本初稿建议采用服务端最终判定联机战斗与奖励的边界。客户端负责收集操作、显示可见状态和反馈结果；服务端检查操作是否有效，并决定共享战斗状态和结算结果。需要预测或提前播放哪些表现，留到同步与体验设计中确定。

设计首先维护以下约束：

- 每个副本实例有明确身份，玩家操作和结果属于具体一局，旧局消息不能误作用于新局。
- 技能的请求、通过校验、生效和结束是不同阶段，表现播放不能自动证明规则已经生效。
- 胜负与奖励由受信任的规则判定，一局重复提交结算请求不应重复发奖。
- 玩家已保存的数据与临时战斗状态有明确边界，返回大厅不会顺便清空应保留的进度。
- 取消、离场或销毁后，迟到的消息和异步结果不能继续修改已经失效的对象。
- 客户端和服务端能够识别实际采用的配置与兼容版本，不能悄悄混用不同规则。

这些是设计与验收要求，不是已经实现的保证。奖励幂等、消息失效、并发与数据恢复需要具体方案及实验支撑，也不能只靠某种设计模式名称证明成立。

## 4. 按职责划分系统

系统划分的依据是状态由谁拥有、变化由谁推动、失败由谁处理。下表是逻辑职责，不预设独立进程、网络服务、类或程序集的数量。

| 系统职责 | 拥有或管理的内容 | 与其他部分的交接 |
| --- | --- | --- |
| 身份、会话与玩家数据 | 玩家身份、会话、持久进度及其读取与保存 | 为组队、副本与结算提供身份和数据，处理退出与恢复 |
| 队伍与副本流程 | 队伍、准备条件、副本实例、阶段与胜负 | 将玩家带入同一局，驱动进入、结束和返回，调用战斗与结算 |
| 战斗规则 | 属性、技能、效果、怪物行为、命中与死亡等规则状态 | 消费操作和配置，产出规则结果及可供表现使用的状态／事件 |
| 关卡与目标 | 出生、波次、触发、目标进度与结束条件 | 组织遭遇，连接战斗结果和副本胜负，不自行绕过统一结算 |
| 奖励与结算 | 本局结果、奖励资格、发放记录与数据写入 | 接收可信的本局结果，处理重复与失败，并向玩家数据回写 |
| 客户端交互与表现 | 输入、界面状态、模型、动画、特效和声音 | 表达操作意图，展示业务结果，管理视图与表现对象的生命周期 |
| 内容定义与制作工具 | 配置定义、内容标识、引用关系、编辑检查和预览 | 将各工种的源内容转为可采用的运行数据与资源 |
| 资源与运行支持 | 加载、持有、释放、取消、存储、网络及平台能力 | 支持业务与表现，并保留错误、所有权和平台差异的表达 |
| 构建、交付与诊断 | 版本组合、制品、运行上下文、检查和问题记录 | 证明本次交付包含什么，让故障能够回到源内容或实现 |

例如，技能系统决定某次技能是否命中，表现系统负责显示受击反馈，结算系统负责按本局结果发奖。击杀通知可以连接它们，但各自仍要明确拥有的状态和失败责任。

首轮采用能完成小范围需求的组织方式。第二种规则、重复创建压力或复杂交接出现时，再比较是否需要新的抽象，避免把所有系统都扩展成通用框架。

## 5. 用一项技能连接规则、数据和表现

技能是首个贯穿案例，因为它同时涉及玩家选择、策划配置、美术表现、程序扩展、两端协作与验证。

策划先说明技能的目的、可选目标、消耗、冷却、生效与打断条件。程序提供可以组合的行为能力与数据定义。美术按约定制作动作、特效和界面反馈，三者共同确认时间、空间和生命周期要求。

一次技能可以按以下业务过程观察：

1. 玩家表达操作意图，客户端提交对应角色与本局上下文。
2. 规则负责人检查角色状态、目标、消耗、冷却和当前副本条件。
3. 通过后按规则进入执行，处理生效时点、作用范围和可能的取消或打断。
4. 规则产出状态变化，客户端据此更新界面和表现；提前反馈的范围需另行约定。
5. 技能结束或被取消后，临时状态、表现与相关异步工作按约定清理。

这里描述的是语义，不规定必须分成五个网络消息或五个类。范围、选敌、动画事件与判定时点的具体模型需要下一篇详细设计。

配置用逻辑标识连接技能、效果、怪物、关卡、奖励和表现定义。某个技能的表现标识再映射到实际模型、动作和特效资源。逻辑内容 ID、引擎资产身份与构建内容版本分别管理，不用一种身份承担全部用途。

## 6. 策划怎样独立制作内容

策划的自主范围是组合、调整已有能力。新行为、新目标条件或新关卡交互需要程序先提供实现、定义与检查，再进入可配置范围。

| 制作内容 | 独立操作的目标 | 需要看到的结果 |
| --- | --- | --- |
| 技能 | 调整规则参数、组合已有行为、指定效果与表现 | 在指定角色与目标上验证，能观察规则结果与表现，并回归旧内容 |
| 怪物 | 设置属性、已有行为参数、技能组合与表现 | 生成指定怪物，观察行为、施法、受击、死亡与清理 |
| 关卡 | 编排已有出生、波次、触发、目标和奖励引用 | 指定关卡启动、检查进度、胜负、重置与重新进入 |
| 奖励 | 设置奖励组、数量、权重及已有发放规则参数 | 先检查配置，再验证服务端结算、重复请求和写入／读取 |

日常流程是：修改源配置 → 检查 → 生成完整候选数据 → 客户端与服务端采用配套版本 → 指定内容预览 → 副本验收 → 提交与集成。

错误必须能够回到具体源文件、记录、字段和引用，说明修正方向。生成失败时保留上一套可运行数据，不采用半套产物。运行界面或诊断入口应显示实际采用的数据版本，让“修改了源文件”和“运行时已采用修改”可以区分。

最小制作阶段可以通过测试角色、固定测试玩家和指定关卡入口验证内容。完整登录、组队、奖励持久化与重启恢复在完整副本阶段验收，不提前成为所有制作预览的前置条件。

## 7. 美术怎样独立替换表现

美术的自主替换依赖稳定的交付约定。制作工具应提前检查兼容性，帮助美术自己完成常见修正；视觉质量、反馈是否清楚仍需要共同试玩和评审。

| 制作内容 | 需要共同约定的边界 | 替换后的验证 |
| --- | --- | --- |
| 模型 | 比例与朝向、根节点、骨骼或重定向要求、挂点与表现接口 | 外观、材质、动作、挂点、受击与死亡表现 |
| 动画 | 动作语义、状态接口、位移、时序和打断规则 | 移动、施法、受击、取消与恢复，核对与规则的配合 |
| 特效 | 触发、位置、挂载、持续、停止、复用和销毁 | 正常播放、提前取消、目标消失、重复使用与离场清理 |
| UI | 数据与交互接口、必需绑定、布局适配和开关生命周期 | 模拟状态、实际操作、多分辨率、重复开关与异步返回 |

日常流程是：制作与导出 → 引擎导入 → 检查依赖和约定 → 单项预览 → 实际技能／怪物／关卡预览 → 联合验收 → 完整提交。

替换兼容外观不要求修改业务规则；改变骨骼体系、移除必需绑定、增加交互或改变规则时序时，需要协作调整约定和实现。模型、动画、特效、UI 的具体引擎对象分别在实现路线中说明。

源文件、交换文件、引擎资产和构建制品应能追踪生成关系。提交应包含完整依赖，修正回到源内容，避免只修改某次生成产物而无法重现。

## 8. 各工种怎样完成一次共同交付

以新增一类怪物和一段遭遇为例：策划定义它带来的挑战，程序补充缺少的行为能力，美术制作识别与反馈，测试根据共同规则验证结果。制作过程中先约定角色与怪物标识、动作与特效语义、关卡触发和奖励引用，再并行推进。

| 环节 | 主要负责人 | 交付与接收条件 |
| --- | --- | --- |
| 需求与规则 | 策划牵头，美术、程序、测试参与 | 目标、规则、表现信息、能力缺口和可判定的验收条件 |
| 数据与资源约定 | 程序／技术美术与内容制作者共同确定 | 字段、标识、引用、时序、绑定和兼容边界有说明与例子 |
| 制作与本地检查 | 策划、美术分别执行 | 内容可预览，错误可自行定位，实际采用的版本可观察 |
| 集成与运行验收 | 程序维护集成，策划、美术、测试共同检查 | 规则、视觉质量、多人结果、数据和清理分别有结果 |
| 候选版本与反馈 | 版本负责人组织 | 源内容、制品和版本可对应，发现问题能够明确修正人和复验路径 |

早期可以由同一个人兼任这些角色，但仍按角色入口走完操作。不能由程序在后台补齐资源或绑定之后，宣称策划、美术已经能够独立制作。

检查按环节分层：本地检查提供快速反馈，集成检查验证完整依赖与可重现性，运行验收观察真实行为，设备验收确认目标环境。结构损坏和缺引用可以阻止采用；体验、美术质量与运行成本根据评审和预算判断。

## 9. 让设计模式教学沿真实变化展开

教学与项目一起演进。先让读者看到当前需求下的直接方案，再引入变化或失败，比较真实候选，解释选择理由、额外成本和验证方法。教材负责概念，项目负责应用判断。

| 项目变化 | 候选比较 | 教学应回答的问题 |
| --- | --- | --- |
| 技能增加第二种目标规则 | 配置、分支、函数组合与 Strategy | 隔离的是参数差异还是算法变化，新增规则影响哪里？ |
| 怪物或副本增加阶段与打断 | 分支、转换表、State 对象与 FSM | 状态由谁拥有，非法转换、退出和迟到回调怎样处理？ |
| 击杀需要通知多个界面与功能 | 直接调用、Observer／事件 | 谁订阅，何时取消，通知顺序、重复和失败怎样处理？ |
| 操作需要排队或记录 | 直接调用与 Command | 意图、接收者和执行边界在哪里，哪些能力仍需单独实现？ |
| 对象创建和依赖开始变化 | 直接创建、创建入口与 GoF 工厂候选 | 谁拥有对象，初始化失败和释放由谁处理，抽象是否值得？ |
| 外观替换与业务变化相互干扰 | 职责拆分与 MVP 等 UI 组织方案 | 哪种变化可以局部完成，绑定和异步生命周期如何保持正确？ |
| 多平台接入或资源调用点分散 | 直接调用、Adapter 与 Facade | 包装隔离了什么，是否隐藏了取消、错误和所有权？ |
| 检查与构建步骤需要变化 | 顺序函数、Pipeline 与 Template Method | 是否有稳定骨架，失败怎样回到源内容，继承是否必要？ |
| 高频创建被怀疑产生性能问题 | 直接创建销毁与对象池 | 重置和旧引用是否正确，在可比负载下究竟增加或减少了什么成本？ |

这些都是候选问题，没有要求正式游戏使用所有模式。设计原则、GoF 对象协作模式、UI 架构和运行模型分别归类；对象池、ECS、Actor、Fiber、异步或流水线不统称 GoF 模式。

首个案例建议从技能目标规则开始：原来只有一种规则，增加第二种时先判断数据和算法的变化，再决定是否需要策略抽象。给读者的练习是面对第三种规则，指出谁修改什么，并列出旧技能、非法目标和中途取消的回归条件。

公开教学材料可使用独立伪代码或最小示例，并提供职责关系、方案对比、练习和预期；示例的运行验证状态单独记录。私有 Demo 不公开，也应让读者能够独立理解推理，而不是只能看到模式名称。

## 10. 把游戏、制作能力和教学一起验收

| 层次 | 完成目标 | 需要保留的证据 |
| --- | --- | --- |
| 最小内容制作 | 技能、怪物、关卡、奖励和表现组成一小段可试玩内容，策划与美术能独立完成规定修改 | 操作步骤、源变更、版本、预览与检查结果、错误修正记录 |
| 完整双人副本 | 两个独立客户端会话完成组队、战斗、结算、返回与重进，约定异常路径可处理 | 双端结果、规则与数据记录、资源和异步清理、重复结算与恢复实验 |
| 内容与版本迭代 | 通过实际候选制品交付新内容或修复，能判断兼容与采用结果 | 新旧制品、版本关系、采用回执与失败恢复结果 |
| 多平台与运营准备 | 各目标环境分别完成体验、生命周期、性能与交付验收，形成运行维护能力 | 平台与设备结果、诊断、备份恢复和发布演练等记录 |
| 设计模式学习 | 能比较方案、解释状态与依赖、判断何时不用模式，并应对一次新的变化 | 独立示例、练习与讲解；涉及行为或性能结论时附相应实验 |

首个可试玩内容可以很小，但应包含从源内容到运行结果的完整交接。功能数量、模式数量、接口数量和检查通过率本身不能证明合作好玩或项目可运营。

当前尚无本篇设计对应的完整副本验收。后续逐项区分设计中、待实现、待验证和已验证；源码推导、模拟预览、Editor、Player、真机与线上结果分别记录，历史实验不自动成为新项目证据。

## 11. 怎样连接三条引擎实现与各个专栏

这份共同设计定义规则、职责、内容语义与验收条件。Unity 先实现完整项目，Unreal 和 Piccolo 从同一案例选择关键问题对照，逐步扩展。它们可以使用不同语言、对象模型、工具和方案；共享代码、服务端或资产格式需要另行设计与验证。

Unity 先以 Editor 跑通制作与游戏流程，同时从设计之初考虑 Windows、Android、iOS 和小游戏；各平台仍要单独验收。其他引擎分别定义制作预览入口，不能将 Unity 的工具和热更新方案直接写成共同要求。

阅读时可以沿玩家和制作任务进入既有专栏：

- 为什么这样合作、怎样组织敌人与关卡，进入玩法设计与战斗主题。
- 一次操作怎样到达规则判定、同步和存档，进入全栈框架与服务端主题。
- 策划数据、美术资产怎样成为可用内容，进入内容生产、配置与资源主题。
- 系统怎样承担变化、如何管理对象和依赖，进入设计原则与设计模式教学。
- 加载、对象、动画、界面和渲染机制怎样支持设计，进入各引擎实现与机制研究。
- 如何交付、测量、恢复与继续迭代，进入工程交付、性能及运营主题。

每篇只解释自己的核心问题，引用共同案例与上下游约定。系列目录继续由各自原规划维护，项目总览负责共同上下文与阅读关系。

## 12. 下一步先细化什么

接下来先确定两人合作的核心机制、视角与操作，并把首个技能和最小遭遇写成可判定的规则。随后设计领域对象、状态与所有权、数据与表现约定，形成制作与运行验收方案，再进入 Unity 的具体实现设计。

本文中的合作体验、服务端判定边界和候选模式仍需评审与实验。技术组件、API、界面布局和性能数字留到相应实现设计，不以概念总览替代实际机制与证据。
