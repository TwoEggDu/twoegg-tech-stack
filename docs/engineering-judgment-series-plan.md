# 工程判断与组织领导力系列规划

> 版本：2026-07-30（v1，组织管理方向纳入）
>
> 角色：`工程判断`系列的 canonical 篇级规划。公开索引仍使用 `content/essays/engineering-judgment-series-index.md`，本文件负责系列边界、内容分组、扩写顺序和状态维护。

## 1. 当前决策

组织管理方向不单独建立泛管理学栏目，先并入现有“工程判断”系列，形成一条“从个人判断到组织结果”的子主线。

原因：

1. 现有文章已经覆盖技术评审、Onboarding、跨职能协作、IC 到 Tech Lead、工程健康度和跨项目标准化。
2. 交付工程 V18 已经覆盖 RACI、审批、多团队协作和工程文化等具体治理机制。
3. 工程实践与演进专栏已经预留真实项目、职责变化和代表案例的证据位置。
4. 当前真正缺少的是统一模型，以及模型与真实案例之间的连接，不是更多彼此孤立的管理话题。

本轮只建立规划，不修改现有文章的 `series`、slug 或公开索引顺序。

## 2. 系列定位

### 一句话定位

这组文章回答：技术负责人怎样把个人判断转化为清晰的权责、可运行的协作机制、可验证的反馈闭环和可复用的组织能力。

### 目标读者

- 准备从高级工程师走向 Tech Lead 的个人贡献者。
- 对项目交付、技术质量或工具链结果负责的主程和 Owner。
- 需要推动策划、美术、程序、QA、运营共同完成结果的工程负责人。
- 已经能解决复杂技术问题，但希望扩大稳定影响范围的工程师。

### 核心问题

- 技术负责人的产出为什么不能只按“自己写了什么”衡量。
- Owner 应该同时拥有哪些责任、决策权和升级路径。
- 跨职能协作怎样从临时帮忙变成明确接口。
- 评审、质量门、复盘和工程指标分别承担什么反馈职责。
- 一次有效做法什么时候才能沉淀为跨项目组织能力。

## 4. 系列边界

### 属于本系列

- 技术负责人和工程 Owner 的结果责任。
- 责任、授权、决策权和升级路径。
- 技术评审、跨职能协作、Onboarding 等工程协作机制。
- 质量反馈、复盘闭环、工程健康度和技术债优先级。
- 跨项目标准化、平台化和公共能力维护。
- 上述机制在游戏客户端、工具链、交付和质量场景中的落地。

### 不属于本系列

- 招聘、绩效、薪酬、晋升和劳动关系制度。
- 组织政治、行政管理或泛泛的领导力口号。
- 完整的项目管理方法、排期方法和产品管理体系。
- 交付工程 V18 已经完整展开的流程细节。
- 没有真实约束、责任边界和结果证据的“管理心得”。

### 交叉内容处理

- 涉及发布审批、RACI 和多团队分支时，链接交付工程 V18。
- 涉及个人项目经历时，事实与证据回到工程实践与演进专栏维护。
- 涉及某个具体技术系统时，只讨论组织接口，不吞掉该技术系列。

## 5. 统一模型

组织管理内容统一沿下面五层展开：

```text
定义结果
-> 对齐权责
-> 设计协作接口
-> 建立反馈闭环
-> 沉淀组织能力
```

| 层 | 要回答的问题 | 常见失效表现 |
|----|----------------|--------------|
| 定义结果 | 最终要交付什么，成功怎样验证 | 每个人都完成了任务，但产品结果没有闭环 |
| 对齐权责 | 谁负责、能决定什么、何时升级 | Owner 只有责任，没有决策权或资源 |
| 设计协作接口 | 谁向谁提供什么输入，按什么标准验收 | 依靠临时沟通、反复催促和个人关系推进 |
| 建立反馈闭环 | 怎样尽早发现偏差，怎样确保改进项关闭 | 评审和复盘有会议，没有行为变化 |
| 沉淀组织能力 | 哪些做法可复用，谁维护，怎样接受新边界 | 工具被复制，机制和维护责任没有复制 |

## 8. 总论文章骨架

`EJ-ORG-00` 使用原理篇结构：

1. **问题空间**：复杂项目里，个人技术能力为什么不能自动变成团队结果。
2. **常见误解**：把管理等同于分任务、开会、催进度或拥有直属下属。
3. **抽象模型**：定义结果 → 对齐权责 → 协作接口 → 反馈闭环 → 组织能力。
4. **工程落地**：技术评审、质量门、发布审批、复盘、平台化分别站在哪一层。
5. **边界**：技术负责人、项目经理、职能经理和具体系统 Owner 各自不应吞掉什么。
6. **案例入口**：只引用已经确认责任和结果的项目材料，未确认内容保留为待补。
7. **最短结论**：技术负责人管理的不是“所有人的工作”，而是从判断到结果之间的责任系统。

## 13. 维护规则

1. 新组织管理选题先判断属于五层模型中的哪一层。
2. 能由现有文章修订承接的，不重复建立同题文章。
3. 原理文章必须落回至少一个工程机制；案例文章必须区分团队结果与本人责任。
4. 未确认的项目名称、职责、决策权和数据只保留为待补，不写成事实。
5. 具体流程细节回到交付工程，项目证据回到工程实践与演进，本系列只维护判断模型和组织边界。
6. 每完成或修订一篇，先回写本文件，再更新公开索引。
