## 1. 已确认的定位

研究工程师怎样进入实际工作环境，理解问题与约束，推动工程落地，并把使用反馈转化为可复用能力。

先建立对 Forward Deployed Engineering（FDE）的完整理解，再讨论它怎样用于内部交付工程。需求发现与交付热点识别是应用层重点；基础总论同时覆盖目标定义、范围取舍、实施、采用、结果验证和产品反馈。

## 4. 各篇重点与边界

### FDE-01：先建立完整认知

2026-10-28 初版按六个问题成稿。2026-10-29 根据用户确认的审阅结果收紧为五部分：现场信息如何改变方案、工程实现责任、交付完成条件、公共能力回流和适用条件。保留对象定位的短例，具体走访、核实与方案比较归方法篇，不展开 Missing 的历史过程。

1. 从产品能力与工作现场的距离说明问题空间。
2. 解释观察实际操作、理解领域背景和直接协作的作用。
3. 建立问题、目标、约束、方案、采用与结果之间的关系。
4. 讨论需求发现、范围取舍、工程实施、使用反馈与公共能力回流。
5. 说明责任与权限、协作接口、适用条件，以及定制和复用的取舍。

官方资料用于说明各公司的岗位与工作实践；跨公司的共同特征属于有来源支持的归纳。本站提出的流程明确标为实践框架，不写成统一行业标准，不用个人案例替代基础定义。

### FDE-02：把方法落到交付改进

2026-10-28 初版按五部分结构成稿。2026-10-29 修订保留这一主线，用 P-001、P-002、P-003 三条反馈演示：前两条归入输入辨认热点 H-001，通知未送达单列 H-002；先恢复当前任务，再依据影响、证据和实施条件选择 H-001 试用，并将决定关联拟议能力 C-001。所有反馈、核对结果与排期均为教学推演。

沿“现场观察 → 记录与核对问题 → 识别交付热点 → 选择方案 → 落地与使用 → 复验和回流”展开；这条链路是本站面向交付场景的组织方式。

- **需求发现**：观察谁在什么任务的哪一步受阻，输入与环境是什么，目前怎样绕过，带来什么影响；将表面功能请求与问题假设分开核对。
- **热点判断**：按受阻步骤归类，再用核对结果检验共同工程落点；写清合并、拆分、优先投入及重排条件。事件去重，不用反馈条数代替团队发生率。
- **方案选择**：判断工具、检查规则、文档、培训和交接流程各自能解决哪一部分，明确范围与完成条件。
- **能力沉淀**：让热点关联解决能力、工具入口、操作说明、适用条件、维护责任与验证记录；根据实际复用情况决定抽象范围。
- **使用复验**：区分功能可运行、使用者会使用、问题得到解决和跨场景有效，继续记录误报、绕行办法与未解决的问题。

正文提供填好的问题与能力简例；三份完整模板移入折叠附录，避免读者先理解记录体系才能开始实践。结构与资料边界见[本篇执行提纲](fde-02-delivery-method-outline.md)。

### Missing 案例：最后回到真实过程

2026-10-29 作者逐项确认了历史顺序：QA 先反馈内容缺失，美术本地正常；人工定位困难后补充 Missing 查找工具，最初由作者使用，再到美术本地对照；同样检查在美术本地没有发现问题，随后引入人工 SVN 更新的仲裁机，美术得以复现并自行处理。

检查范围从单资产扩大到全部资源，再收紧到需要进包的内容。检查仍依赖定时安排或 QA 异常后的专人处理，版本日前压力集中，因此接入提交触发并自动 @ 提交者。频繁提醒暴露了依赖识别与手动选择的负担，一个场景可能关联几百个资源，随后才补充依赖提交工具。

正文已据此改成六段因果叙事，配套文档、宣讲和定性结果沿用已知材料。当前源码只用于核对定位与依赖收集能力，不独立证明历史顺序或运行效果；不添加改善比例、增量扫描、自动修复等未确认能力。完整事实与取舍见[执行提纲](production-resource-completeness-outline.md)。
