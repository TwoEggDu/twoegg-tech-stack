## 1. 编辑定位

- 文章类型：原理篇。
- 文章路径：`content/delivery-engineering/fde-01-foundations.md`。
- 读者：希望理解现场问题怎样影响工程决策的工具、交付工程师与技术负责人。
- 核心判断：FDE 将现场理解、直接参与工程实现和使用结果接在一起，让一次交付改善后续工作。
- 前置：了解软件功能、使用者和生产环境的基本含义即可。
- 读后目标：解释现场信息为什么会改变方案；区分开发完成、实际采用与效果验证；判断公共能力回流所需的条件。
- 边界：具体走访步骤、问题记录、方案比较和热点排序归 FDE-02；本文保留定位接口的短例解释工程判断。Missing 历史案例后续补充。

## 2. 贯穿场景

构造一个已上线自动检查系统的团队：检查能发现异常，使用者却无法从内部路径找到编辑对象。以定位接口的对象标识、版本约束和使用入口说明，现场认识怎样改变设计与实现。

场景不是作者历史项目，也不是来源公司的案例。发现、候选方案和验收条件都作为教学推演；不填写虚构部署结果、效率比例或使用人数。

## 3. 结构与论证任务

| 部分 | 论证任务 | 回扣场景 |
| --- | --- | --- |
| 开篇 | 建立功能成立与工作任务完成之间的距离，交代术语与证据身份 | 检查能报错，使用者仍然无法继续 |
| 1. 现场信息 | 说明对象、任务终点和权限的差异怎样改变工程问题 | 从报告异常改为帮助使用者完成处理 |
| 2. 工程实现 | 讲实设计、开发、调试与接入责任，说明技术约束怎样回到产品交互 | 对象关联、快照与过期报告的处理 |
| 3. 完成条件 | 用一张表区分技术成立、实际采用与问题改善，交代维护承接 | 定位功能能运行以后还要确认什么 |
| 4. 能力回流 | 区分共享接口、团队规则和公共产品能力 | 保留差异，按后续场景决定抽象范围 |
| 5. 适用条件 | 说明问题不确定性与必要组织条件，连接内部交付工程 | 使用者、数据、实施、验收和维护安排 |
| 收束 | 给出读者可用于审视自己工作的判断，并连接 FDE-02 | 不把示意目标写成已实现结果 |
