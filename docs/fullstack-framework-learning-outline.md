# 全栈框架：学习目标与产出提纲

本提纲把学习目标转换为文章、实验和总结 Demo 的要求。先确定要解释和验证的问题，再决定 Demo 的功能规模。它是跨系列的执行层路线，不另建 canonical 篇目表；既有文章的范围、编号和状态仍回到原系列计划维护。

## 一、读者与最终产出

面向有 Unity 客户端经验、希望理解完整联网游戏链路的开发者。先以 Unity＋ET 作为工程研究线，再逐步补充 Unreal 实现与对照。

学习完成后，应能沿一次玩家操作解释两端职责、输入输出、状态所有权、资源生命周期与失败处理，并用固定版本的源码、可复现实验和记录支撑判断。

三类产出：

1. **技术文章**：问题空间 → 抽象模型 → 具体实现 → 取舍和适用边界。
2. **主题实验**：明确变量、观测位置、预期和失败条件，记录实际结果。
3. **总结 Demo**：串联已验证的能力；状态同步与帧同步分别实现和验收，小游戏另有平台验收。

## 三、学习目标与产出矩阵

| 主题 | 必须回答的问题 | 文章／学习产出 | 最小验证与完成条件 |
| --- | --- | --- | --- |
| 架构与生命周期 | 模块怎样初始化、协作和销毁，谁持有对象与任务？ | 运行时职责图、一次启动与清理的调用链 | 进场→离场→重进；记录实体、事件、异步任务及资源的创建与清理 |
| 配置与数据工具链 | 策划数据怎样成为两端认可的运行时数据？ | Luban 的定义、校验、生成与消费提纲 | 正确数据能生成并被两端读取；错误引用与版本不兼容有明确反馈 |
| 资源、场景与 UI | 加载完成的边界在哪里，谁负责持有和释放？ | 资源所有权与界面／场景交接说明 | 取消加载、失败重试、重复开关界面与切场景，记录句柄及内存观察 |
| 代码与版本更新 | AOT、热更代码、资源、配置与协议如何配套？ | HybridCLR 机制与跨系统更新链路 | 两个实际版本的制品与更新回执；验证失败、重试与恢复，各平台单独判断支持范围 |
| 玩法系统协作 | 技能、Buff、属性、AI 与表现怎样分工？ | 通用模型、ET 实现与 Unreal 对照 | 跟踪输入→施法→命中→伤害→死亡；区分规则与表现，以记录校验结论 |
| 通信与状态同步 | 哪端拥有权威，另一端如何获得可用状态？ | 会话、RPC、状态同步与恢复的文章 | 两个真实客户端共同战斗；检查技能、血量与死亡一致，覆盖延迟和断线重进 |
| 帧同步 | 输入帧、确定性、预测、回滚与表现怎样衔接？ | 帧同步主线及与状态同步的对照 | 固定输入和初始条件，重放并校验逐帧状态；记录预测错误与回滚结果 |
| 玩家数据 | 什么需要保存，重复请求和进程重启怎样处理？ | 所有权、持久化、奖励幂等与恢复说明 | 奖励写入回执、实际记录、重启后读取三份依据；重复请求不重复发奖 |
| 小游戏平台 | 包体、缓存、网络和平台生命周期怎样改变设计？ | 微信／抖音适配问题提纲，先明确首个目标平台 | 冷启动、分包下载、切后台、网络恢复与内存实测；开发工具与真机分别记录 |
| 构建与反馈 | 如何交付可追溯版本，并把故障带回开发？ | 制品与版本说明、可复现故障案例 | 输入→构建→验收→更新→故障→修复→回归；保留版本、环境和原始结果 |

## 四、专栏组织与已有材料

### 4.1 全栈框架

- **整体运行模型与 ET**：先区分客户端、战斗服、业务服务及共享代码；再追踪 Entity、Fiber、Actor 和消息。复用 [ET 系列计划](et-framework-series-plan.md)、[前置桥接计划](et-framework-prerequisites-series-plan.md)。ET9 既有文章与固定 ET10 研究分轨维护。
- **通信与同步**：会话、请求响应、权威边界、状态同步、输入帧、预测回滚和重放。复用游戏后端与技能系列的相关内容，补独立实验，而非仅比较术语。
- **配置与跨端契约**：Luban 作为独立专题待规划；内容生产与配置管线作为现有前置。计划覆盖定义、引用校验、生成、装载、版本与两端消费。
- **版本配套与综合 Demo**：客户端代码、资源、配置、协议和服务端怎样组成兼容版本；文章对应具体变更与失败恢复案例。

### 4.2 客户端框架

- **执行模型与异步**：复用 [Unity 异步运行时计划](unity-async-runtime-task-to-unitask-series-plan.md)，重点在调度、取消、异常与对象生命周期。
- **资源与场景／UI**：复用 [Addressables／YooAsset 计划](addressables-yooasset-source-reading-series-plan.md)，将所有权、首次可用和释放接到游戏流程。
- **代码热更新**：复用 [HybridCLR 计划](hybridclr-structural-diagnosis-and-bridge-articles-plan.md)，机制与整条更新链分开说明。
- **模块与玩法表现**：复用 [游戏编程模式](game-programming-patterns-plan.md)与[技能系统](skill-system-series-plan.md)；补启动、流程、UI、输入与表现的组合验证。
- **小游戏适配**：先列平台约束和验收目标，再决定适配实现；不由 WebGL 构建成功推定小游戏可用。
- **Unreal 路线**：引用已有引擎架构、GAS、网络主题；逐题补映射，不把 Unity API 当通用模型。

### 4.3 服务端框架

- **会话、RPC 与路由**：请求身份、超时、心跳、错误与生命周期。
- **Actor／Fiber 与地图**：调度、邮箱、并发边界、Location、地图实例与迁移。
- **业务与数据**：玩家状态、背包／任务／装备接入、持久化、幂等与恢复。
- **运行与验证**：双端测试、日志关联、部署与故障回归；交付细节链接原工程与交付专题。

## 五、总结 Demo 的范围由目标决定

暂用两人合作副本作为贯穿场景：登录→组队→进副本→战斗→胜利／团灭→奖励与存档→返回→重进。怪物数量、技能数量和装备深度由验证需要决定。

先做主题实验，再接入完整流程。两种同步实现优先共用内容定义、外围流程与观测口径；战斗逻辑能否共享要验证确定性与生命周期要求，不预设可替换一个网络接口就完成切换。

当前阶段顺序：学习目标与产出→已有材料与官方实现盘点→最小实验→状态同步循环→帧同步对照→小游戏与版本交付→文章收束。每项都区分待设计、待实现、待验证和已有结果。

## 六、知识与证据回流

文章、提纲与阅读入口维护在本站；实验工程、源码研究和原始记录维护在私有实验场。公开页面仅使用允许公开的引用、自主表述及脱敏证据摘要。

每项实验记录：学习问题、固定版本、最小改动、输入与环境、观测方式、实际结果、失败条件、结论适用范围、对应文章。按这些字段保留实验记录，再把版本明确、可公开的结论回写对应文章。

本轮仅准备阅读入口与目标提纲；没有实现新 Demo、运行同步实验、发布小游戏或验证热更新。
