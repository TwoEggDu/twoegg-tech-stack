## 2. 开头与贯穿例子

### 开头骨架

- 情境：程序收到一份法杖模型、一组庭院构件和一个施法圆环，要把它们放进游戏。交付表有面数、贴图尺寸等信息，但还不足以回答运行时应该关注什么。
- 第一段任务：让读者认出自己的接入工作，提出“除了核对资源参数，还需要知道什么”。不虚构项目已经超预算、曾经发生故障或优化成功。
- 第二段任务：指出同一份资源可出现在不同镜头、规模和配置中，引出“资产”和“资产的一次使用”两个观察对象。
- 第三段任务：承诺给出从制作、导入、使用到测量的分析方法，并在后文完整回答核心问题。

### 教学对象与状态

| 对象 | 复用来源 | 在本篇承担什么 | 材料限制 |
| --- | --- | --- | --- |

## 3. 正文五节详细骨架

### 正文一 程序接到的到底是什么

**本节职责：** 先把分析对象拆开，避免把文件、资源和运行实例混在一起。

建议 H3 与展开点：

1. **制作文件保存的内容，与游戏需要的内容有什么关系**：解释 DCC 工程、导出 FBX、纹理原稿/导出图的角色；哪些内容经过转换才能进入引擎。首次解释“导入产物”：引擎根据源文件与导入设置生成的可用数据。
2. **导入后的对象怎样被材质和场景引用**：用法杖说明 Mesh、Material、Texture 的关系；Prefab 保存组装与引用，运行中还会有实例。这里只给最小词义，完整数据结构转到[几何与表面](../content/rendering/unity-rendering-01-mesh-material-texture.md)。
3. **三种大小分别在回答什么**：源文件大小、构建/传输数据量、运行时占用分别定位，不互相替代；共享数据、实例状态与可能副本也要区分。

核心论点：同一个资产名称可能指向多个阶段的不同对象。程序先确认自己看到和测量的是什么，才能把参数与运行行为连接起来。

拟图：**一根法杖的对象关系图**，表示源文件、导入资源、材质引用、Prefab 和实例的关联；将“转换”与“引用”用不同连线表达，不把它画成单一运行时串行管线。

Unity 对照位置：正文一之后放检查卡 A。代码：不安排脚本。

本节结束读者应能判断：磁盘上的 PNG、导入纹理和场景里的显示对象是否是同一种数据；看到“文件很小”时，还缺哪一类信息。

承接下一节：对象身份清楚之后，再追问“它们被使用时究竟做了什么”。

### 正文二 资产参数怎样成为运行工作

**本节职责：** 完整建立成本模型，集中回答核心问题，而不是把答案散成技巧清单。

建议 H3 与展开点：

1. **制作与导入决定准备哪些数据**：几何属性、索引、纹理格式和 Mip、材质功能等，先对应数据和输入，不立即推算帧率。
2. **使用条件决定数据怎样参与工作**：可见对象、绘制组织、顶点处理、片元着色、纹理采样、深度与混合分别用一句定位；首次解释“pass”：为了某个渲染目的组织的一段工作，同一资源可能参与不同用途的绘制。
3. **测量要与问题对应**：把 CPU 准备、GPU 工作、内存驻留和加载列成不同问题；性能受并行、缓存与同步影响，不写成“把几个毫秒直接相加”的预算公式。

正文核心表拟用以下骨架：

| 观察维度 | 先解释什么关系 | 程序应提出的问题 |
| --- | --- | --- |
| 数据与驻留 | 导入资源、共享引用和实例状态 | 当前实际格式是什么？哪些对象共享，哪些另有副本？ |
| CPU 组织 | 可见性、Renderer、材质状态与提交 | 这些使用怎样组织成绘制？是否值得进一步看 CPU 时间线？ |
| GPU 几何 | 顶点/索引、Shader 与绘制用途 | 什么几何参与了哪些用途，哪些属性被处理？ |
| GPU 表面工作 | 投影覆盖、Shader、采样、深度与混合 | 哪些像素区域和功能在参与，是否有叠加？ |
| 加载与转换 | 数据取得到可使用之间的处理 | 当前问题发生在加载、首次使用还是稳定运行？ |

这些行是提问方向，不能仅凭某行参数较大就宣布它是当前瓶颈。纹理、RT 和光照资源可能参与多行，不强制互斥归类。

拟图：**制作—导入—使用—测量的解释图**。每一层都标出“需要的条件”和“能回答的问题”；这张图是全文的抽象骨架。

本节结束读者应能拿一份资源描述，分别提出数据、CPU、GPU 和加载问题。具体格式表、批处理类型与工具指标仍由旧文解释。

### 正文三 同一资产怎样随使用条件改变问题

**本节职责：** 用三个短情境，把第二节模型落回程序能够识别的工作。

建议 H3 与展开点：

1. **法杖从手持近景变成远处的小物件**：资产数据可以相同，投影后可见细节与表面覆盖改变；检查轮廓和细节贡献的理由在这里出现，几何机制留到第二篇。
2. **庭院构件从一组变成重复摆放**：区分共享 Mesh/纹理与新增实例/Renderer 状态；可见范围和绘制方式需要检查。既不把资源内存简单乘以实例数，也不预设实例多一定合批。
3. **圆环从一次反馈变成多次叠加**：分开“粒子数量”“覆盖面积”“叠层”“材质功能”；挑一项改变时，其余条件需记录。叠加可能是目标画面的一部分，重点是判断是否值得其成本。

每个情境按四句骨架写：**保持什么 → 改变什么 → 因此新增哪个问题 → 用什么入口检查**。不提前写“所以必然更慢/更省”。

拟图：三组使用条件对照，优先用原创示意；实际截图具备后再替换并标明条件。不要把旧文的原理图包装成运行截图。

Unity 对照位置：第二/第三个情境后放检查卡 B。不在这里加入完整 Profiler 采样教程。

本节结束读者应能区分：资产本体改变、使用条件改变和当前性能瓶颈改变，是三件需要分别确认的事。

### 正文四 怎样比较一个修改方案

**本节职责：** 把“想到一种优化”转成可讨论的假设与证据需求。

建议 H3 与展开点：

1. **先说想改善什么**：例如驻留量、提交负担、覆盖或首次使用延迟，目标必须具体；画面要求作为约束一同写下。
2. **说清改动会转移哪些成本**：降分辨率、改材质功能、合并资源、增加 LOD 各选一个简短例子；形成“预计减少/可能增加/功能影响”表，不展开为四个教程。
3. **判断当前证据处在哪一层**：公式能算理论字节，Inspector/导入检查能确认数据与设置，Frame Debugger 能看绘制组织；设备性能结论需要进一步采样。将推导、观察和假设分开。

重点例子：提出“为法杖增加 LOD”的候选，列出几何简化、额外网格、切换观感和维护问题，为下一篇埋下主问题；这里不替它做最终选型。

本节只给决定下一步检查的依据。GPU 架构细节、压缩编码参数和完整治理流程链接既有文章。

### 正文五 从资产描述走到检查记录

**本节职责：** 用一份小产物收束，让读者能独立提出下一步问题。

建议 H3 与展开点：

1. **填写一张资产使用与成本关系表**：选法杖，完整走一次“身份—用法—候选问题—检查—当前判断”，示例记录用“待观察”与“由资料可知”标明证据强度。
2. **有证据以后，怎样决定继续查哪一层**：如果只确认源文件大小，下一步看导入格式；如果确认某对象参与额外绘制，下一步判断这些工作是否必要，再按问题进入旧文。不要把这些路径写成自动根因判定器。
3. **把结论带回资源与使用约定**：需要修改哪份数据、材质或配置，以及改变哪些条件时需要重查；完整联合验收流程交给旧系列。

正文模板拟保留：

| 字段 | 内容要求 |
| --- | --- |
| 对象与版本 | 哪份源资产、导入资源、Prefab 和当前实例 |
| 使用条件 | 镜头、规模、显示尺寸、质量设置与绘制用途 |
| 候选问题 | 要确认的数据或工作，避免先填根因 |
| 拟修改变量 | 一次改变什么，预期影响与画面约束是什么 |
| 检查与证据 | 资料、计算、Editor 观察或设备记录的具体入口 |
| 当前判断与下一步 | 已知什么、仍需确认什么、转到哪篇深入 |

文末收束：用总结句方向回答核心问题，然后引导进入几何篇。不要再追加一套通用面数/贴图大小阈值。

## 4. 两张 Unity 检查卡

检查卡均为待执行步骤。建议示例环境为 Unity 6000.0 / URP 17，执行时记录实际补丁与包版本；没有教学工程时，首稿可以先列步骤和待观察项，不填写成功结果。

### 检查卡 A 从场景对象找到它使用的资源

1. 选定一个法杖实例，沿 MeshFilter 或 SkinnedMeshRenderer 的 Mesh、Renderer 的材质槽，再到纹理引用，记录真实对象名与来源。
2. 查看模型与纹理导入设置，记录与当前问题相关的格式、尺寸、材质功能；区分源文件、导入对象和场景实例。
3. 用记录解释“当前看到的是哪一层”；需要占用数据时再进入专门工具，不从资源面板的文件大小推断全部运行内存。

产物：一条引用关系和一张条件记录。限制：不修改导入设置，不提供遍历/导出工具，不宣称已经定位性能瓶颈。

### 检查卡 B 从一个对象找到相关绘制

1. 在能显示目标对象的固定视角打开 Frame Debugger；可用时从 `Window > Analysis` 进入，记录所调试目标是 Editor 还是 Player。
2. 按事件和对象定位它参与的绘制，记录材质/pass/深度或混合等与当前问题相关的信息；具体事件名以版本为准。
3. 回到成本关系表填写“确认了什么工作”；若要知道它花多少时间，将问题转交 CPU/GPU 采样，不把事件数当成耗时。

产物：带说明的事件记录。资料：[Unity Frame Debugger](https://docs.unity3d.com/6000.0/Documentation/Manual/FrameDebugger.html)。完整捕获与性能采样不作为本篇完成要求。

## 6. 证据准备与写作风险

| 要写的内容 | 依据或材料 | 当前状态与使用限制 |
| --- | --- | --- |
| 术语与对象关系 | 上述本地旧文，以及成文时对应版本的官方资料 | 旧文可定位概念；涉及保证的句子继续回到第一手资料 |
| 三个教学情境 | 原创对象关系与使用条件示意 | 可绘制；尚无实际素材/场景观察，不写成经历 |
| 修改方案的收益 | [盘点文档](mobile-art-asset-cost-content-audit-2026-10-26.md) V1—V10 的验证需求 | 本篇只组织检查问题，不实施完整实验，不填设备收益 |
| 两张检查卡 | Unity 对象引用与 Frame Debugger 对照入口 | 步骤待执行；接口/菜单以实际版本确认 |

需要防止的三类写偏：

- 把成本模型展开成所有技术的百科：每类只解释关系和下一步问题，机制链接旧文。
- 把资源参数直接变成性能结论：每次推导写出使用条件，将“需要检查”与“已经证明”分开。
- 让程序读者被 DCC 操作卡住：制作步骤只在帮助理解输入时出现，完整操作沿用美术系列。
