## 1. 系列定位与研究问题

**研究现有游戏交付工具怎样形成可追踪的处理闭环，以及模型判断在什么条件下值得加入。**

首阶段围绕一次资源 Missing 的发现、定位、修正或补交、提交与共享版本复检。以可改造的 Jenkins、SVN、Unity 批处理检查、MissingFind 和依赖提交为设计前提，先建立固定流程基线，再研究证据冲突时的调查与工具选择。

核心问题：**交付工具已有自动化，Agent 还能补上什么？**

研究允许得到三种结论：现有工具已经足够；补齐固定流程即可；某些例外值得引入模型。不能预设引入模型会更快、更准或更省人。

目标读者：

- 维护 Unity 资源检查、构建流水线与编辑器工具的工程师。
- 需要组织策划、美术、程序修正和复检的工具链维护者、QA 与技术负责人。
- 理解基本 Agent 概念，希望判断它在实际交付任务中作用的开发者。

读者应了解提交、工作副本、资源依赖和检查报告；不要求读完 Agent Engineering 全课，不要求先读 DeepSeek Harness 源码。

## 4. 首期范围与贯穿案例

### 已确定的讨论范围

1. 优先组织定位、修正或补交、提交与复检。
2. 假设现有 Jenkins＋SVN 工具可改造；实际接口与源码能力待核对。
3. 固定流程组织常规任务，模型在需要调查或选择处理路径时按需参与。
4. Missing 不自动等于漏提交；正常漏交与证据冲突都需要覆盖。
5. 首页与提纲先行建立，本轮推进 DGA-01 正文；不编写 Agent 服务或修改真实工具。

### 两条贯穿路径

| 路径 | 示例问题 | 研究目的 | 当前证据身份 |
| --- | --- | --- | --- |
| 常规路径 | 共享版本引用缺失，本地存在匹配依赖，形成补交候选，提交后复检 | 建立不调用模型的闭环基线 | 依托历史工具能力的设计推演，未运行 |
| 例外路径 | 本地正常、检查机 Missing、依赖预览未给出可用补交方案；核对预览含义与范围后，进一步调查引用差异 | 观察模型如何选择调查、区分事实与意图、转人工决定，并回到固定流程 | 构造的示意场景，不是真实事故或运行轨迹；没有新增依赖不等于没有场景修改 |

案例中出现的 revision、GUID、对象路径、工具名与输出均须标明示意身份。模型能否取得引用标识、工作副本快照或依赖证据，以实际适配器为准，不假设现有报告已经包含。

首期不扩展到自动发布、线上回滚、服务端运维或完整交付平台；编译与配置检查留作后续候选。不会为了使用 Agent 而把已确定的步骤全部交给模型。

## 7. 证据与实验规划

### 每项结论分别标记来源

| 证据身份 | 可以支持的表述 | 不能替代的证据 |
| --- | --- | --- |
| 历史实践 | 已确认工具做过什么、遇到过什么操作障碍 | 新服务已经实现、当前接口可用或效率提升 |
| 设计推演 | 建议接口、流程与模型输入输出可能怎样组织 | 真正的模型调用或工具执行 |
| 合成回放 | 固定输入、预录工具结果或预设模型输出下的状态处理 | 模型自主工具选择、真实 Unity 与 Jenkins 运行 |
| 真实工具实验 | 指定版本的 Unity、SVN、Jenkins 工具实际行为 | 模型增益与生产可用性 |
| 真实模型实验 | 固定条件下取得的实际请求、工具选择与结果 | 未覆盖场景的可靠性、生产收益 |
| 团队或生产观察 | 在明确范围、时间窗口中的实际处理结果 | 跨项目的普遍保证 |

DGA-06 每轮至少展示：任务目标、版本与状态、已知证据、未知项、可用工具、模型实际输出或标明的拟议输出、工具返回、程序允许的状态迁移。不要把事后解释写成模型真实思维过程。

### 对照原则

后续可比较：已有工具加人工操作、补齐固定流程、固定流程加按需模型判断。三组应尽量使用相同问题样本、工具能力、版本输入和关闭判据；分开记录适配器改进、流程改进与模型带来的贡献。

候选观察项：正确完成处理的情况、误关闭与越界修改、人工介入次数及实际处理时间、总时延与等待时间、重复或无效工具调用、模型成本。具体口径在实验设计中定义，不预填效果比例。

候选样本至少覆盖：普通漏交、本地与共享版本不一致、依赖预览无候选、检查启动失败、重复事件、旧结果晚到、本地通过但未提交、修正后引入另一问题。模型不能访问作者本地文件时，应记录证据缺口，而非假定已取得文件。
