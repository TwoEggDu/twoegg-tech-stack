# 交付预算 14.2：内存预算小节审校记录

2026-11-05 · B1/B2 局部补桥。对象为[交付预算体系](../content/delivery-engineering/delivery-performance-stability-02-budget-system.md)的“内存预算”小节及推导步骤 4，不新增文章或篇号，不重审已经完成的帧预算批次。

## 1. 问题与复用

问题来自[客户端执行计划 B 节](client-performance-budget-tiering-monitoring-execution-plan.md)已经登记的 RAM 到应用额度无条件换算。旧文还把多个分类占比写为建议，并将内存不足后的分配失败与系统终止混为单一 OOM 阈值。

复读[内存记账](../content/performance/game-performance-memory-accounting.md)的指标表、共享记账与完整切场景模型（原文 L77–139），复用其 400/760/440 MiB 教学输入；现有正文已能解释重叠、临时缓冲、释放时机和代价，本篇只接预算判断，不另建同义模型。Android/Apple 预算旧文的固定工程线没有作为本批依据或实际推荐值。

官方资料支持平台行为和诊断边界，不背书本文的候选数值或模型。引擎分类与系统指标的具体映射仍按工具、平台和版本验证。

## 3. 专家追问与回答

| 追问 | 回答与判据 | 本批判断 |
| --- | --- | --- |
| 同为 4 GB RAM，为什么不能自动给同一应用额度？ | 还缺系统/构建、进程状态、统计定义、负载和压力条件；不能用硬件容量替代这些记录 | 基础方法满足，无当前设备达标结论 |
| 稳定点只有 400/440，预算为何还要看 760？ | 交接时新旧资源和临时缓冲同时存在；应覆盖生命周期，三个状态自身仍非完整时间线 | 复用模型满足，真实峰值待实际采集 |
| 一次释放 100 MiB 对象，进程指标一定减少 100 吗？ | 还受共享、持有和分配器/驱动保留影响；按内存记账旧文核对，不直接把对象估算当进程变化 | 归因边界满足，未执行释放实验 |
| 候选线改为 700，是否说明必须增加物理 RAM？ | 教学交接值会高出 60；可评估重叠/临时并发或预载范围及其反馈代价。该模型不足以决定设备支持范围或实际改法 | 条件变化推演满足，未执行优化 |
