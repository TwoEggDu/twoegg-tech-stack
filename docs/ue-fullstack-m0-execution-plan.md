# UE 全栈路线 M0 执行计划：从最小工程到可定位故障的 Windows 包

> 建立日期：2026-09-21。内容状态：**执行计划已建立**；技术证据：**文档依据，工程未执行**；个人能力：**待测、未验收**。
> 上游唯一路线：[UE 全栈工程师成长路线](ue-fullstack-expert-series-plan.md)。本文件只展开 M0，对应 UFS-01/02 的最小测评、UFS-03@M0 和 UFS-09@M0，不新增文章编号。
> 本轮只编写计划，没有检查用户开发硬件、创建练习工程、安装环境、运行下列任务或提交 Git。没有可沿用的 M0 实际执行证据。

## 1. 目标与非目标

M0 要得到一份能完整构建、Cook、打包、脱离编辑器在新进程运行的 Windows 包。本人能解释其中一个自有 C++ 行为与蓝图配置的关系，能把包、符号、源码、配置和运行日志对应起来，并完成一次可控故障的定位、修复与重新构建回归。

最小场景是一张简单地图、一个具有可见行为的自有 C++ Actor、必要的蓝图配置/表现。例如让几何体按配置的角速度旋转，同时记录启动参数与行为状态；它不承担战斗规则，也不要求成为完整客户端可玩切片。输入、镜头、血条、完整动画和客户端基础系统仍由主计划的 UFS-04/05 后续展开，没有被删除。

M0 不要求 Linux DS 实际构建/部署、两客户端联机、身份/匹配/结算/数据库、完整 GAS、完整 UI/动画框架、Android、CI 集群或遥测平台，也不要求读完所有 UObject、GC 或渲染源码。源码合法访问条件需在 M0 确认；实际源码获取/构建安排与 M1 DS 衔接，修改引擎源码不是 M0 前提。

“可重复构建”在这里指输入身份、步骤、工具链/配置可追溯，按相同步骤能再次构建并得到符合预期的功能结果；**不默认要求二进制逐字节相同**。文件校验值用于识别每次真实产物，不能把两次哈希不同直接解释为构建失败，也不能跳过差异说明。

## 3. 工程位置与文件管理

未来执行时采用三处边界，以下只是命名方案，**路径均待确认、未创建**：

| 位置变量 | 保存内容 | 管理边界 |
| --- | --- | --- |
| `DOCS_ROOT` | 当前 `E:\workspace\TechStackShow` 的主计划与本执行计划 | 只存规划和将来经授权整理的脱敏文字记录/必要小型证据索引；不放 UE 工程二进制、引擎源码或商业数据 |
| `PRACTICE_ROOT` | 仓库外的 TwinArena 最小工程、独立 C++ 练习和操作说明 | 实际绝对路径待确认。可用已有合法练习仓库或本地版本管理；本轮不创建本地/外部工程仓库，更不自动推送 |
| `ARTIFACT_ROOT` | 每次 build_id 的包、PDB、日志、manifest、故障记录和校验清单 | 与源码分开，采用不可覆盖的每构建目录；记录实际绝对路径/存储身份和保留策略，不把占位路径写成已存在链接 |

工程输入通常包括 `.uproject`、自有 `Source/`、`Config/`、必要 `Content/`、实际需要的插件声明/版本和构建说明；按资源许可与文件大小选择合适的版本管理方式。引擎源码在独立合法位置，只记录来源/版本；`Binaries/`、`Intermediate/`、DDC、Saved 运行产物、大型包和符号不进入 Hugo 文档仓库，也不作为工程源输入提交。

`Saved` 中需要的原始日志和故障证据要复制到对应构建产物目录后留存，不能笼统忽略后丢失证据。文件管理说明必须区分源码、可再生成缓存与不可丢的执行记录；本计划不提供递归删除命令。重跑使用新的输出目录或隔离工作副本，不能清理原仓库来“验证干净”。

构建身份分三层：工程 revision（含未提交补丁或快照清单）、本次唯一 build_id、本次运行 run_id。build_id 在构建前固定，写入自有启动日志与包内的小型身份文件；包/PDB 的 SHA-256 在产出后记录到外部 manifest，避免把最终包哈希嵌回包自身造成循环。时间戳单独不足以证明符号匹配，还要留调试器的模块/PDB 匹配记录。

### M0-T01｜确认条件与精确构建基线

- **目标**：把第 2 节未知项变成可执行的最小 Windows 方案。
- **前置**：后续工程执行已获授权；能读取本人环境和官方兼容资料。
- **输入**：第 2 节条件表、候选 UE 5.7.x、主计划版本依据与源码访问边界。
- **具体操作**：记录实际硬件/OS/空间；核对 UE 来源、patch/构建标识、插件清单；选择并核实 VS/MSVC/SDK/调试器组合；确认合法源码访问条件与 M1 源码构建安排；提出实践与产物绝对路径及存储余量。缺依赖时只列安装/获取项，按实际授权再执行，不能默认已具备。
- **产物**：环境/基线清单、路径方案、未决条件及解决入口。
- **验收**：每个影响 M0 构建的条件有实际值或明确阻塞原因；工具链兼容依据可追溯；源码访问已由本人确认。没有把待确认写成通过。
- **常见失败**：只记录“UE5”；机器装多套 SDK 却不知实际选哪套；把同名发行版当同一源码 revision；空间估计漏 DDC/符号。
- **需要本人独立完成**：解释为何选择此组合、哪些已确认、哪些要用首次构建验证，说明 M0 与 M1 源码构建的区别。

### M0-T02｜完成最小 C++ 能力测评

- **目标**：证明足以开始最小工程的所有权、编译链接与调试能力。
- **前置**：M0-T01；可用的小型原生 C++ 编译/调试环境。
- **输入**：UFS-02 的拥有/借用、RAII、指针/引用、容器失效、move 与普通模板阅读范围。
- **具体操作**：在隔离练习中编译一个有作用域资源、独占所有者和借用引用的小程序，记录构造/销毁顺序；解释一次容器变更后的引用风险与一次 move 的源/目标状态；设置断点观察；制造并修复一处声明/定义不匹配的链接错误，以及一处可安全观察的生命周期逻辑错误。不要用任意地址写入或破坏环境制造故障；并发/无锁深入到 M4 前再补。
- **产物**：小程序输入身份、编译日志、销毁顺序记录、修复前后差异与解释。
- **验收**：本人能区分编译、链接和运行问题，解释拥有者/借用者及失效条件，修复后重新构建通过；不要求高级模板或并发工程全部毕业。
- **常见失败**：以为 move 必然复制资源；容器地址变化后仍借用；把能运行当生命周期一定正确；只复述 AI 答案。
- **需要本人独立完成**：画销毁顺序，说明修复为什么成立，并在调试器里找到对应变量和栈帧。

### M0-T03｜建立最小 C++ 工程与文件边界

- **目标**：形成有明确输入与版本身份的练习工程。
- **前置**：M0-T02；PRACTICE_ROOT、ARTIFACT_ROOT 的真实路径已确认且不覆盖已有内容。
- **输入**：锁定的 UE/工具链、最小 C++ 项目模板、文件管理方案。
- **具体操作**：在独立练习位置创建最小 C++ 工程；说明 `.uproject`、Source、Config、Content、Game/Editor Target 和模块的职责；保留最少插件；记录源 revision 或不可变源码快照清单；将缓存/生成文件与源输入分离；先完成正常 Editor 目标编译。初版不建立 Server Target、DB 或 CI。
- **产物**：最小工程输入、版本/忽略清单、首次编译日志与操作说明。
- **验收**：源输入可完整找回，工程能以锁定引擎打开并完成常规编译；运行时模块不依赖 Editor 专用模块；没有将大型产物塞入文档仓库。
- **常见失败**：只保存生成的 IDE 项目；插件隐式依赖本机；引擎关联错版；用 Live Coding 成功代替正常编译。
- **需要本人独立完成**：指出每个输入目录的作用和可再生成项，解释 Game 与 Editor 构建用途。

### M0-T04｜完成一张地图、一个自有行为和最小身份日志

- **目标**：让包里有可观察且由本人解释的 C++/蓝图协作行为。
- **前置**：M0-T03；素材来源允许使用。
- **输入**：简单几何地图、自有 C++ Actor、一个可配置参数（例如角速度）、预先写明的预期行为。
- **具体操作**：制作一张可见简单地图并设置游戏默认地图与 Cook 范围；在 C++ 实现一个最小行为，由蓝图子类或实例只配置数值/材质等必要表现；在启动与关键变化记录 build_id、工程 revision、引擎构建标识、配置标识、run_id 和行为参数。修改配置后观察行为变化，说明规则仍由哪段代码负责。此时不深入全部 GC 或网络机制；使用旧文前按主计划 R-03 处理持有风险。
- **产物**：地图/类/配置输入、行为预期、启动日志格式与构建身份文件方案。
- **验收**：本人能从配置追到执行该行为的自有 C++ 函数，解释生命周期入口、单位和结果；无须完整 UI 或 GAS。
- **常见失败**：只改 CDO 而实际实例覆盖了参数；默认地图仅配置在编辑器；C++ 行为实际被蓝图替换；日志缺构建身份。
- **需要本人独立完成**：说明 C++、蓝图和实例各保存什么，预测一次配置变化的结果并验证。

### M0-T05｜完整构建、Cook 与 Windows 打包

- **目标**：得到可独立启动的 Game/Development Windows 包与匹配自有模块符号。
- **前置**：M0-T04；版本、编译器/SDK 与输出目录可用。
- **输入**：固定工程输入、Win64 Game Target、Development 配置、地图/Cook/插件清单、build_id。
- **具体操作**：保存配置并关闭编辑器/Live Coding 会话；使用该版本官方打包流程或核对后的 UAT 流程完成正常 Build、Cook、Stage/Package。设置完整构建与非迭代 Cook，使用新的构建输出；需要排除旧项目编译产物影响时用隔离源副本重建，不删除共享工程。保留各阶段命令或 UI 设置、开始结束时间、退出结果和完整日志；保存实际 exe/模块、依赖、内容包与自有 PDB。记录包和符号清单/校验值，不只保存一张“成功”截图。
- **产物**：Windows 包、匹配符号、输入/工具链/构建配置 manifest、构建与 Cook 日志、校验清单。
- **验收**：所有构建阶段实际成功，默认地图和自有行为进入包；PDB 可保留并追溯到该二进制。完整构建指项目目标的正常构建流程，不要求二进制 UE 用户重新编译整个引擎。
- **常见失败**：Cook 漏地图/资源、错误 Target/平台、Editor 模块依赖、打包未含运行所需依赖、复制了上一次的 PDB。
- **需要本人独立完成**：从日志判断失败属于编译、链接、Cook 还是打包；解释本次确实执行了哪些阶段。

### M0-T06｜新进程启动、身份核对与符号定位

- **目标**：证明包脱离编辑器可用，且能定位到自有源码。
- **前置**：M0-T05；调试器与对应源码、PDB 可读。
- **输入**：实际包路径、启动参数、build_id/run_id、符号和输入清单。
- **具体操作**：关闭编辑器，从包路径启动新的 Windows 进程；留 PID、实际可执行路径、参数、启动/退出时间与日志；核对地图和行为。将调试器连接到实际游戏进程，核查模块与 PDB 的匹配信息，在自有行为处命中断点并观察栈/变量；记录源码 revision 与配置。另做一次不附加调试器的启动/退出，避免只证明调试器宿主能运行。
- **产物**：独立运行日志、进程身份、模块/PDB 匹配与自有断点记录、行为观察。
- **验收**：不是 PIE，也不是编辑器 `-game` 代替打包运行；包/符号/源/配置能交叉对应，日志有本次身份。无需 match_id、DB 结果或网络 Trace。
- **常见失败**：只调到了启动器进程；PDB 与模块错配；优化让行断点行为变化；跑了旧输出目录；日志仍来自编辑器。
- **需要本人独立完成**：确认实际运行的二进制，判断符号是否匹配，从栈定位自有代码并解释所见变量。

### M0-T07｜可控故障定位、修复与重建回归

- **目标**：完成一次有证据的诊断闭环。
- **前置**：M0-T06；保留正常版本和基准行为，使用隔离练习分支/副本。
- **输入**：自有行为、预期结果、故障开关或可还原的小改动，以及独立运行/符号工具。
- **具体操作**：设计一个只影响练习行为的逻辑故障，例如故意把每秒参数按毫秒换算导致运行速度异常；先写触发条件、预期与观测，再以独立坏包复现。根据日志/断点/栈和变量定位自有代码，记录假设与排除过程；修复并以新 build_id 完整构建/Cook/打包，重新执行正常配置、边界配置和再次启动的回归。无需制造系统崩溃、删除文件或破坏任意内存；若选择自有断言，只在隔离 Development 工程内触发并保留匹配栈。
- **产物**：坏版/修复版源身份、包/符号、触发步骤、诊断记录、最小修复差异及回归结果。
- **验收**：能指出失败链条和实际根因，说明修复不只是掩盖症状；好坏包身份不混，修复后重新构建与新进程回归有实际记录。
- **常见失败**：知道练习答案就跳过定位；只改蓝图绕过代码错误；Live Coding 修好却没有新包；覆盖坏包或原日志导致无法复查。
- **需要本人独立完成**：自己操作调试器、解释因果与修复边界、选择并执行回归；可使用资料，但不能仅提交 AI 诊断结论。

这是**自造练习问题**，用于建立诊断技能，不是未预告独立能力考核。主计划 UFS-18@M5 仍须由他人给出未准备答案的问题，完成实现、验证、回归与外评；两者不能合并勾选。

### M0-T08｜重复操作、整理回执与准备 M1

- **目标**：证明说明可重复执行，明确 M0 通过与尚未证明的边界。
- **前置**：M0-T07；修复后的输入已固定，证据可定位。
- **输入**：修复后同一 revision、工具链/配置、构建说明和新的输出路径。
- **具体操作**：本人从记录重新操作，优先在独立源副本进行完整构建/Cook/打包，不拷贝旧项目 Binaries/Intermediate；使用新 build_id/run_id，重做独立启动和故障修复后的回归；核对输入、步骤、配置和功能结果。记录耗时/磁盘与生成产物差异，不要求字节级相同。按第 5/7 节逐项填写实际值和失败项，再列第 8 节 M1 前置补课与源码/Linux 安排。
- **产物**：可重跑说明、第二次构建/运行证据、M0 验收回执与 M1 准备缺口。
- **验收**：第 5 节必做项全部有对应证据；说明无需作者口头补关键步骤。本机第二工作副本通过不宣称第二台机器或他人已复验；外部复验若尚无记录则保持待完成。
- **常见失败**：说明仍含未替换占位符；只复制旧包；修改输入但复用原 build_id；将文件哈希不同直接判失败或完全忽略差异。
- **需要本人独立完成**：按说明复跑，解释两次构建的输入和差异，准确列出自己尚未验证的能力。

## 7. 交付物与证据记录格式

交付物保存在待确认的 PRACTICE_ROOT/ARTIFACT_ROOT：版本化最小工程输入、操作说明、每次完整包与匹配符号、构建/运行日志、故障前后记录、校验清单和 M0 回执。文档仓库只记录必要的产物位置、身份、校验信息与脱敏摘要；大型产物使用受控存储，访问方式不得泄露凭证。

| 字段级别 | 内容 | 判定方式 |
| --- | --- | --- |
| M0 必须：输入/环境 | 工程 revision 或快照 ID、dirty/补丁与输入清单；UE patch/来源/发行构建 ID 或源码 revision；插件、OS/硬件概况、实际编译器/SDK、Target/平台/配置、地图/Cook 设置 | 有具体值与来源；发行版源码 SHA 可记待 M1 确认，但实际 UE 构建身份不能空缺 |
| M0 必须：构建/产物 | build_id、开始结束时间、步骤/实际命令或 UI 设置、退出结果、日志位置；包/模块/PDB 的位置、大小、SHA-256 清单和模块/PDB 匹配记录 | 能从日志追到对应源输入、配置与产物；不同构建不覆盖 |

## 8. 进入 M1 的条件与交接

M0 通过后可以开始 M1 准备；M1 的完整通过仍以主计划为准。交接清单是：

1. M0 的修复后工程、包、符号、说明与证据可重跑，尚未通过项没有被隐藏。
2. 完成 UFS-04@M1前 的**单机**创建/接管/销毁/重生/切图与持有清理，按 R-01/R-03 处理旧文风险；这里不先要求三进程。
3. 完成 UFS-05@M1前 的输入、镜头、基础 UI/动画碰撞可玩切片，并补网络与 Linux 的最小前置。
4. 按已确认合法访问渠道锁定用于 DS 的引擎源码 revision 与构建补丁、对应 Windows/Linux 工具链和目标 Linux 环境，明确 Server Target/Cook/端口安排；实际源码与 Linux DS 构建归 M1，M0 的二进制包不能代替。
5. 在 M1 建成两个独立 Windows 客户端和 Linux DS 后，补 UFS-04@M1 对象存在/权威/所有权矩阵与 UFS-09@M1 进程日志关联；M2 再加业务与数据库，M3 再补重连。M2 不等待完整 GAS。

本文件完成只表示第一个里程碑已有执行方案。当前 Windows/UE 构建、C++ 行为、独立故障诊断、Linux DS、业务后端/数据库、性能与专项深度、外部评审均没有在本轮获得工程验收证据。
