# 游戏研发与持续交付：技术主线提纲

> 本文的十二环节保留为技术范围与问题定位地图；后续按已确认的[工作理念与叙事约定](production-pipeline-writing-principles.md)，重整为一份总览与多篇独立的问题解决文章。环节数量不预设最终篇目数量。

> 2026-10-16 · 第一版提纲。先确定问题顺序与协作关系，后续逐段补充原理、实现、案例和验证。编号表示主线环节，不预设一节对应一篇新文章；篇目与完成状态仍由原系列规划维护。

**主线：产品与资源 → 跨工种生产 → 配置连接双端 → 版本与构建 → 验证和部署 → 投放与运营 → 数据和问题回收 → 修复与下一轮迭代。**

生活模拟与家园建造是贯穿案例之一，多人 RPG 与已有交付实践提供其他语境。通用问题先讲清，再按案例进入技术细节。各环节可以并行；埋点、验收、发布与恢复条件需要提前设计。

## 贯穿主线的主要循环：持续发现问题，持续维护可发布版本

**规范可执行 → 变更有检查 → 结果可追溯 → 候选可验收 → 发布可恢复 → 问题反哺规范与下一轮开发。**

这个循环贯穿下面十二个环节。目标是让日常开发的问题尽早暴露，让性能规范持续生效，并持续维护一个验收证据有效、与当前线上环境兼容的可发布版本。

- **问题尽早暴露**：在资源导入、配置导出、本地开发、提交合入、构建运行和线上灰度各处设置检查；报告包含具体对象、失败原因、责任归属与复现入口。
- **性能规范可执行**：按“指标、预算、场景、设备与环境、测量方法、责任人”定义规则；同时检查绝对预算与相对基线退化，覆盖单资源、场景组合和真机运行。具体阈值后续依据产品目标与实测确定。
- **检查持续在线**：编辑与提交时执行快速检查，候选构建时验证受影响场景，定时覆盖完整设备与场景，灰度及线上持续观测。看板区分通过、不通过、待检查、结果过期和检查执行失败。
- **证据对应版本**：结果关联代码、配置、资源、工具链、测试环境和执行时间；相关输入或线上环境变化后重新判断有效性。未执行、过期或运行失败的检查不能作为通过证据。
- **可发布版本持续维护**：固定并归档通过验收的产物、联合版本清单、已知问题和恢复方案，发布时使用同一批产物。新候选失败时保留最近合格版本，同时重新确认它的兼容性与证据有效性；未完成功能需隔离，协议、配置和存档变更需考虑兼容。
- **问题形成下一轮约束**：线上异常、玩家反馈与业务结果经过定位、修复和复验，沉淀为检查规则、回归样本及需求。例外接受需记录负责人、影响范围和有效期限。

### 接到游戏内容：以新增一件可制作、可摆放的家具为例

以下是待验证的贯穿案例，用来组织后续文章和 ET 实验；尚未表示这些检查已经落地。

| 游戏中的变更或风险 | 尽早暴露的位置 | 检查与反馈方向 |
| --- | --- | --- |
| 美术新增家具模型、贴图和表现资源 | 资源导入 | 检查资源规格、依赖和单资源预算，定位到具体资源并反馈美术／TA |
| 策划配置制作配方、家具 ID 与资源引用 | 配置编辑／导出 | 检查 ID、跨表引用、规则语义及双端导出一致性，定位到表、行、字段 |
| 客户端展示与摆放，服务端扣料并保存家具状态 | 双端集成 | 验证交互、权威校验、重复请求和状态保存，失败信息关联内容 ID 与版本 |
| 配置引用了家具，但更新包未包含所需资源 | 构建产物检查 | 核对配置引用、资源依赖与实际产物清单，阻断不完整候选 |
| 单件家具合格，高密度摆放后出现卡顿或内存峰值 | 场景与真机测试 | 在固定设备、摆放规模与操作路径下检查场景预算及基线退化 |
| 新版本上线后，旧玩家的家具或材料状态异常 | 兼容验收与灰度 | 验证旧存档、配置／协议兼容、部署顺序与恢复条件 |
| 运营投放后转化下降，玩家反馈扣料后家具未出现 | 数据回收与问题处理 | 关联投放批次、业务事件、版本和错误记录，区分展示、加载与保存问题，再补回归样本 |

后续衡量循环是否有效，关注问题从引入到发现的时间、检查反馈耗时、重复问题与线上漏检情况，以及可发布版本的证据新鲜程度；这些指标的口径和目标另行展开。

## 一、理解产品：游戏由哪些内容、资源与状态组成

- 从玩家体验拆出玩法系统：建造、采集、制作、互动、任务等。
- 区分美术源素材、运行时资源、策划配置、程序代码、玩家状态与运营内容。
- 建立内容对象和依赖目录：一件家具、一个角色、一段任务分别关联什么。

## 二、内容生产：美术、策划与程序怎样协作

- 策划提出规则和内容需求，美术交付表现资源，双端明确使用条件。
- 约定标识、命名、尺寸、挂点、时序、预算与依赖，形成可验收的交付契约。
- 资源预览、集成、问题退回与复检；工具与 TA 怎样减少重复沟通。

## 三、配置表：连接策划、资源和客户端／服务端

- 配置字段、类型、单位、ID、跨表引用与规则语义怎样共同定义。
- 编辑、校验、生成和双端导出；共享字段与端侧字段怎样划分。
- 资源引用怎样进入收集与构建；改一行配置会影响哪些资源、代码和验证样本。

## 四、双端实现：内容怎样成为可运行的游戏行为

- 客户端读取配置、定位和加载资源、处理交互与表现。
- 服务端消费配置、校验业务、处理状态与持久化；与客户端约定权威边界。
- 协议、版本、错误与重试怎样衔接；资源定义、玩法定义和玩家实例怎样关联。

## 五、版本协作：多条开发线怎样保持输入一致

- 代码、配置、资源、协议和工具链怎样组成一组可追溯输入。
- 开发、候选发布、线上修复之间的变更传播、冻结与例外处理。
- 变更影响分析、旧配置／旧玩家状态兼容、回退与逐线复验。

## 六、自动化构建：把输入变成可解释的产物

- 检查、导表、资源收集、代码编译、资源构建和打包怎样串联。
- 平台参数、依赖、缓存、增量与并行隔离；产物、报告和符号怎样归档。
- 构建失败怎样定位；节点环境、容量、重建和公共工具怎样维护。
- 变更怎样触发分层检查，检查结果怎样关联固定输入与候选产物，并及时反馈负责人。

## 七、联合验收：各工种怎样确认内容可以交付

- 策划验规则、美术验表现、双端验行为、QA 验完整流程与失败边界。
- 配置／资源／代码兼容、旧状态恢复、多设备表现、性能与更新流程怎样验证。
- 自动检查与人工验收怎样分工，阻断、提醒、例外和问题归属怎样明确。
- 性能预算怎样绑定场景、设备和测量条件；结果过期、未测及检查执行失败怎样影响候选资格。

## 八、部署与热更新：运维怎样把版本送到线上

- 客户端配置、资源和配套更新产物怎样分发，怎样确认获取与应用成功。
- 服务端代码、配置及相关数据怎样部署，怎样确认运行实例实际生效。
- 联合版本清单、部署顺序、灰度、停止与恢复；部署完成和内容开放怎样分别确认。
- 怎样持续维护最近合格且仍兼容的可发布版本，确保验收产物与部署产物一致。

## 九、投放与运营：内容怎样触达玩家并持续运转

- 运营目标、活动节奏、开放条件、展示素材和客服说明怎样准备。
- 广告创意、素材生产、渠道投放与游戏内体验怎样衔接。
- 投放、运营、策划、美术、数据分析与研发之间怎样交换需求和结果。

## 十、数据回收：怎样知道玩家经历了什么

- 业务问题怎样变成事件契约；客户端、服务端和投放渠道各提供什么数据。
- 花费与转化、玩法漏斗、活动参与和留存怎样定义口径、用户群与观察窗口。
- 数据质量、归因与版本关联怎样核对；分析结果怎样形成有依据的改动决策。

## 十一、异常与 Bug：线上问题怎样进入修复流程

- 崩溃、卡顿、下载／加载失败、接口和保存异常怎样发现与聚合。
- 客服、社区和玩家反馈怎样形成可定位、可分派的问题记录。
- 影响评估、止损、复现、跨工种定位、修复、QA 回归、发布后确认与反馈回执。

## 十二、持续迭代：把结果带回下一轮生产

- 业务数据、技术异常和玩家反馈怎样共同影响需求排序。
- 已修复问题怎样转化为配置规则、资源检查、回归样本和发布条件。
- 内容效果、协作成本、构建与恢复效率怎样复盘，并回写知识与工具。
- 怎样用发现延迟、反馈耗时、重复问题和线上漏检评估主要循环，并调整检查位置与覆盖范围。

| 五 · 版本协作 | 研发、内容负责人、QA、发布负责人 | 多线变更 → 固定输入集合、兼容与传播记录 |
| 六 · 自动构建 | 工具／构建、双端、运维 | 固定输入与环境 → 平台产物、清单、报告和符号 |
| 七 · 联合验收 | QA、美术、策划、双端、运营、运维 | 候选版本与验收条件 → 结果、问题与发布约束 |
| 八 · 部署更新 | 运维、构建、双端、QA、运营 | 已验收产物与发布清单 → 部署／更新生效结果与恢复记录 |

## 用两段工程实践补强这条主线

历史项目的资产检查实践与后续多项目交付经验，按工程问题合并取材。历史实践已由作者确认落地；后续材料同时包含运行记录和演进规划，写作时保留各自状态。下面是案例接入位置，不新增一套篇目或进度表。

| 主线位置 | 历史实践切入点 | 后续实践与文章补强方向 |
| --- | --- | --- |
| 二、三 · 内容生产与配置 | 提交检查机器人、Missing 节点定位、依赖提交；配置消费端与资源字段约定 | 配置路径检查保留表、记录和字段来源；通用检查、项目规则与通知分层 |
| 五、六 · 版本与构建 | 独立工作副本检查、资源与整包构建、受控提交及发布核对 | 配置驱动编排、生成物一致性、跨机器产物基线、报告聚合和节点环境维护 |
| 七 · 联合验收 | 资产规格、场景与 Package 检查，策划、美术和 QA 自查 | 用必需 AOT 元数据漏进包的故障说明产物完整性检查；用启动阶段观测连接运行时性能 |
| 八 · 部署更新 | 客户端发布、版本和服务器核对、更新与冒烟流程 | 候选产物与正式清单生效分开；服务端制品、实例切换、运行及登录验证分别交接 |
| 九至十一 · 运营与反馈 | 异常报告、跨工种分派、修正与复检 | SDK 与平台数据来源、业务 BI、日志回收和分析工具，连接版本与玩家运行情况 |
| 十二 · 持续迭代 | 从重复缺失问题形成三个互补工具 | 从故障形成构建检查，从阶段观测指导优化，并把公共机制沉淀到工具链 |

先将资源三工具写入[交付管线实践](../../content/projects/case-build-system-from-zero.md)，再沿[既有阅读路径](game-content-build-delivery-reading-path.md)补配置、构建和验收文章。每个案例保留项目语境与本人职责；概念家具案例继续用于解释经验如何迁移。

其中两条具体线索可以贯穿后续正文：

- **从提交缺失到可处理的检查报告**：独立检查发现问题，本地工具定位和修正；后来进一步将规则问题与检查工具异常分别反馈。历史机器人在问题修正后停止报错，没有单独发送修复完成通知。
- **从构建成功到运行可用**：必需 AOT 产物缺失时，构建曾继续完成而设备启动失败；修复围绕输入来源、生成顺序和缺失即失败展开，再连接设备与 QA 验收。

性能和数据章节采用实际测量范围与数据来源。阶段样本不外推为全平台收益，投放分析工具不等于已取得投放收益。内部素材与源码索引单独保留，公开正文使用脱敏问题、工程判断和可公开结果。

## 后续补充约定

先按本提纲检查遗漏与顺序，再逐段补充。每次只展开一个明确问题，说明：**问题场景、核心模型、参与者、输入输出、具体实现、失败反馈、验证证据**。原理与已有实现优先回到原文章补充；确认存在独立缺口后再安排新篇。

写作先补完整的资源三工具案例，再展开第三部分“配置表”，向前连接美术与策划生产，向后连接双端消费、资源入包和部署。其他部分先保留提纲。概念案例、作者经历和实际实验分别标记；本次新增经历接入方向，未改写各系列正文或执行工程实验。
