# 游戏生产管线：工作理念与叙事约定

> 2026-11-06 补充 D2D 技术组合、提交检查与 DailyBuild 的机制构想，以及运行时问题前移原则。中心思想及当前推进顺序唯一维护在[站点定位](../site-entry-and-audience-plan.md#column-core-principles)；本文展开生产管线的叙事要求，文章写法沿用[仓库写作规范](../article-writing-method.md)，篇目和进度由各原系列规划维护。

## 一、我们要表达的核心理念

**D2D（Design to Delivery，从设计到交付）生产管线服务于最终游戏交付质量：让美术、策划、程序专注各自的专业工作，由管线承接内容转换、集成检查和交付中的共性复杂度，使每一步的产出尽量符合对应标准，进入后续集成与验收。**

本站作者的完整责任视角见[站点中心思想](../site-entry-and-audience-plan.md#column-core-principles)。本主题展开生产工具、检查、交接与反馈怎样支撑这一目标；具体案例按实际覆盖环节与证据说明结果。

对外入口遵循[首页的工作方式原则](../site-entry-and-audience-plan.md#homepage-work-method)：首页讲清目标、分工、持续检查反馈、修正复验与能力沉淀，再引向各专题。下节技术组合保留为深入生产管线时的背景，不放到首页展示。

### 当前 D2D 技术组合与机制构想

2026-11-06，作者明确当前主要采用以下技术组合，作为后续解释具体生产链路的背景：

| 工作部分 | 已明确的技术选择与用途 |
| --- | --- |
| 游戏引擎 | Unity |
| 服务端 | ET |
| 客户端资源与代码更新 | YooAsset 与 HybridCLR |
| 内容配置 | 美术、策划共用 Luban 表达配置；项目根据这些配置确定进入包内的资源 |
| 跨工种协作 | 通过项目管理软件与 Luban 连接美术、策划、程序的工作 |

在这组技术选择上，D2D 的工作机制构想分为两种反馈节奏：

- **每次提交后的及时检查**：各工种提交变更后触发监测机器人，尽早识别能够自动判断的基础错误，将问题反馈给相关工种修正、复验。
- **夜间 DailyBuild 的集成验证**：在夜间构建中安排性能与已落地功能的质量检查，结合对应版本、测试场景和运行环境解释结果，反馈到相关工种继续修正、复验。

性能工程属于这条持续自动化管线的建设范围：围绕明确的质量要求持续检查内容与功能的运行成本，比较变化，将异常反馈到生产环节，并在修正后回归验证。卡顿等问题的专项定位接入这一持续过程；自动执行范围、基线、场景覆盖、目标设备及实际结果按对应专题的实现和验证证据说明。

上述技术组合按作者陈述记录；整条 D2D 管线是建设构想。已实现的局部检查、待建设的触发与反馈、实际执行的功能或性能测试分别说明，不能从技术选型或局部机制推导出完整链路已经自动运行，也不能预填质量与性能收益。各环节随实现与验证补充证据。

### 本主题要写清楚的事

承接站点中心思想，生产管线文章围绕以下问题积累解释与案例，不要求每篇覆盖全部问题：

| 要讲清的环节 | 文章需要提供的解释 |
| --- | --- |
| 生产与交接 | 各工种如何制作、提交、消费和验收资源、配置、代码与版本；谁有权决定内容意图、处理异常和接受结果 |
| 发现卡点 | 从任务观察、反馈与记录找到等待、重复操作、返工或失败的位置；区分用户原话、直接观察、工程假设与待核查项 |
| 理解和排序 | 相关机制怎样解释现象；哪些问题可以归为同一原因，影响、频率、证据和实施条件怎样支持投入先后 |
| 选择改进 | 工具、规范、文档、培训、流程与人工处理各自解决什么；写清未选方案、成本、限制及验证办法 |
| 质量前移 | 哪类运行时问题能够在制作、开发、提交或集成时提前识别；检查依据是什么，怎样定位、修正、复验，哪些条件仍需运行环境验证 |
| 形成可用能力 | 谁实现和维护、使用者从哪里进入、遇到失败怎样处理；说明如何接入原有生产步骤 |
| 复验与回流 | 回到原受阻任务验证，分别记录实现、采用和结果；有效做法进入检查、回归或规范，误报与过时规则怎样调整 |

这张表用于判断文章需要哪些基础与证据，不把理论讨论自动转成采访。先按[执行对照表](../fde-foundations-and-cases-execution-plan.md)复用或补齐相关基础，再选择有材料支撑的案例。讨论“专栏应写什么”时先完成内容判断；需要个人经历支撑的具体段落，再通过 col-voice 取材。

个人表达放在与判断有关的位置：作者为什么在意、怎样选择、当时怎么想、现在怎么看。作者陈述与独立验证区分，材料状态集中在必要位置说明，不在正文每段重复“作者确认”；不把教学情景、设计方案或不同项目的片段拼成一次亲历。

生产管线连接内容制作、配置、双端实现、检查、构建、验证、部署和运行反馈。工程工作的价值体现在业务团队能否顺畅使用这些能力：问题能否及时被发现，使用者是否知道怎样处理，修正后的内容能否经过验证进入交付。

“保质保量”需要落到具体工作：

- **质量**：内容完整，配置和行为符合约定，性能与运行结果满足明确的验收条件。
- **范围与节奏**：约定内容能够按计划交付，重复返工、等待和人工排查中的瓶颈得到处理。
- **持续性**：工具有人维护，规则能够执行，文档可查可用，版本、问题和结果可以追溯。

业务负责人定义内容意图并参与验收，工程负责人将生产中的共性障碍转化为可使用、可维护的能力。方案需要同时考虑技术机制、使用者操作和跨工种交接。

### 将运行时问题前移到生产阶段

遇到运行时问题，继续追问它最早在哪个生产环节已具备可靠识别的条件，再决定将检查放在制作、保存、导出、提交、构建或集成中的哪个位置。前移可以使用静态规则，也可以通过编辑器预览、场景模拟、自动测试或代表设备上的提前运行实现。

1. **交代判断依据与覆盖条件。** 说明检查了哪些对象、规则、版本和环境；例如资源引用检查与实际加载验证分别覆盖什么。
2. **接上使用者的修正动作。** 报告指出问题对象、原因或违反的约定、处理入口与复验方式，让发现、定位、修正和再次检查形成连续过程。
3. **保留完整版本的验证。** 局部产物通过检查后进入后续集成，整体体验、设备表现、真实并发等仍按目标环境验收；制作检查通过不直接代表版本获准上线。

这套原则说明建设目标，不预设现有流程已覆盖全部问题。规则的误报、漏报、维护成本及使用反馈也应进入复盘；经验证有效的检查再纳入日常生产。

## 二、从反复出现的问题出发

文章选题先问：**团队可能在哪些地方反复遇到问题，这些问题为什么值得解决？**

通过实际记录与走访，关注问题的发生频率、影响范围、发现延迟、人工处理成本及交付阻碍。尚未统计的频率作为待核对判断；低频但影响重大的问题单独说明其优先理由。

分析问题后，再决定采用规则调整、操作说明、协作流程、工具开发或自动检查。方案规模应与问题相称，并接上使用者的处理动作。

历史经历提供判断和方案的依据。它们可以说明一种问题如何发生、为什么这样选择方案、团队怎样采用，以及最终观察到了什么结果。篇章由问题组织，经历在对应位置支撑论证。

## 三、两条循环共同支撑落地

### 深入业务的工作循环

**观察受阻任务 → 走访沟通与原因判断 → 工程或协作方案落地 → 回到原任务修正与复验 → 复盘并沉淀能力。**

先了解使用者遇到的实际障碍；上线后继续观察工具是否好用、报告能否理解、修正动作是否顺畅，再依据反馈调整。这是生产管线实践采用的工作循环，可与 FDE 深入现场、推动工程落地的工作方式对照理解；它不单独构成 FDE 的完整定义或行业统一流程。

2026-10-28 已确认将 **FDE 方法与实践**作为“工程与交付”下的独立专栏，按“基础理论 → 交付方法 → 真实案例”推进，篇级安排以 [FDE 系列规划](../fde-methods-series-plan.md)为准。基础篇涵盖目标、约束、范围取舍、实施、采用、结果验证与公共能力反馈；方法篇再展开需求发现、交付热点与工具能力的对应。本文继续维护案例叙事约定，Missing 既有正文保留原归属，走访与设计判断的补充在理论和方法篇之后进行。

文档建设贯穿这个循环：规范解释怎样制作，操作说明解释怎样使用，场景指引解释遇到问题怎样处理，排障与复盘记录为后续判断提供依据。宣讲、试用和跟进帮助方案进入日常工作。

### 持续交付的工程循环

**规范可执行 → 变更有检查 → 结果可追溯 → 候选可验收 → 发布可恢复 → 问题反哺规范与下一轮开发。**

日常问题尽量靠近产生位置暴露；性能规范按资源、场景与设备分层执行；验收对应明确的版本和环境。持续维护可发布版本，需要在输入或环境变化后重新判断结果是否有效。

两条循环相互连接：业务反馈帮助选择要解决的问题，工具和管线提供持续执行能力，运行结果再帮助团队调整下一轮工作。

## 四、阅读结构：一份总览，多篇独立的问题解决文章

### 总览：交代目标、链路与阅读入口

总览首先说明工作理念，再用以下过程连接问题：

**内容生产 → 配置与双端 → 构建验证 → 发布部署 → 数据与问题回收。**

读者通过总览了解生产管线要服务谁、各环节可能有什么障碍，以及应该从哪篇文章继续阅读。环节用于定位问题，篇幅按问题的重要性和材料充分程度安排。

总览可以使用的开篇表达：

> 游戏内容从制作到上线，要经过美术、策划、客户端、服务端、QA、运营和运维的多次交接。资源不完整、配置不配套、设备运行异常和反馈脱节，都可能让团队反复返工。我的工作是沿着这些交接识别共性问题，通过检查、工具、文档和交付流程，帮助团队及时发现、定位和修正问题，并持续维护可以交付的版本。

总览完成后，读者应能回答：这套工作解决什么生产问题，采取什么方法，哪些文章提供更深入的实现与验证。

### 单篇：一个明确问题，一条完整的解决过程

每篇文章能够独立阅读，采用统一的叙事顺序：

1. **问题场景**：谁在什么操作中遇到什么障碍，造成什么影响。
2. **反复发生的原因**：分析机制、信息、依赖和交接方式，说明如何区分可能原因。
3. **解决目标与方案选择**：团队需要具备什么能力，为什么选择这些方法，有哪些取舍。
4. **工具、文档和协作落地**：解释实现、使用入口、职责与反馈，以及使用中推动的调整。
5. **验证结果与复盘**：说明怎样判断有效、实际结果支持什么结论、仍有哪些限制。

开头先让读者看懂问题、影响和核心判断，再逐层进入原理与实现。必要前提在单篇内交代，进一步阅读通过链接提供。

一个问题需要多个工具共同解决时，将它们放在同一篇文章中。多个不同问题使用同一工具时，各篇分别说明该工具解决了哪一部分，公共机制链接到已有技术文章。

## 五、真实经历怎样支撑方案

以资源缺失问题为例，开头先解释“美术本地完整，提交后或手机包中却缺少资源”的矛盾，再说明团队需要主动发现、对象定位和完整提交三种能力。随后引出 Missing 机器人、MissingFind 和依赖提交，说明使用反馈怎样推动工具逐步补齐。

文档、宣讲和跟进出现在使用障碍对应的位置，结果使用作者已经确认的描述。这个案例既呈现技术判断，也呈现方案怎样进入团队日常工作。

材料采用以下表达约定：

- 已落地的工作明确写本人设计、实现、维护、排查或推动的具体部分，并说明协作者及结果。
- 拟议方案写明适用条件、预期解决的问题和验证方法，保持其待验证状态。
- 不同项目保留各自背景、时期和约束；比较可迁移的方法时说明差异。
- 结果区分实现、工具采用、构建、设备运行和业务效果；使用材料能够支持的结论。

公共文章以工程问题和技术判断组织。岗位对应关系、内部材料地址及个人取材待办在 HT 维护。

## 六、下一步怎样重整提纲

先依据本约定整理总览与候选问题，再为每个候选篇目准备四项信息：

| 项目 | 要回答的问题 |
| --- | --- |
| 要解决的问题 | 具体障碍、受影响的人与交付环节是什么？ |
| 单独成篇的理由 | 为什么值得深入展开，与其他篇的边界在哪里？ |
| 核心判断 | 读者理解这个问题时，最需要掌握的因果关系或工程原则是什么？ |
| 支撑材料 | 哪些真实经历、源码、文档或验证结果可以使用，还缺什么？ |

根据问题之间的依赖和材料成熟度确定篇目、合并关系及阅读顺序，再展开每篇细节。现有十二环节用于定位问题，候选问题表用于筛选素材，二者都不直接等同于最终文章数量。

**让读者看到：能够沿着生产过程识别反复阻碍团队的问题，并将解决办法做成团队持续使用的能力。**
