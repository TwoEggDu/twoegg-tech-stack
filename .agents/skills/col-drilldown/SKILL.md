# 技术深挖 — 七个分析视角

输出供写作使用的技术分析稿，区分已知机制、依据与未知项；不以角色设定冒充作者经历，不写最终正文。

## 定位与材料读取

- 接受主题、文章或材料路径、当前对话中的工作单。先读已给材料；缺少主题且无法从材料确定时才询问。
- 需要系列边界时，从[根路由](../../../doc-plan.md)进入相关 canonical plan，再读 `content/` 中直接相关的文章。`docs/` 的 outline、证据卡与实验设计只作为准备材料，`examples/` 的原始记录按需核对，`kb/` 是知识沉淀；不默认扫描全部 Markdown 或归档。
- 读者、目标与基线以本系列和[当前站点定位](../../../docs/site-entry-and-audience-plan.md)为准。分析聚焦本题，不强加 Unity、渲染或源码学习目标。
- 引擎或工具的具体机制、版本差异及变化信息，应查官方资料、可公开引用的源码或原始记录。材料不足时保留问题与查证路径；用户限制资料范围时遵守限制，不补造外部事实。

## 七个视角

保留以下视角作为检查框架，内容按主题展开；不适用的层注明原因，缺资料的层标“待核查”，不为填满层数制造结论。

1. **定义与边界**：一句话定义讨论对象，交代容易混淆的概念及适用语境。
2. **产生原因**：原有问题、核心矛盾、引入这项设计的条件。
3. **内部机制**：输入、状态、数据或控制流、关键对象与因果链。有依据时指出反直觉细节，不强凑陷阱。
4. **成立条件**：相关版本、平台、配置、负载、团队或流程条件。只有材料支持时列差异和替代行为；没有跨平台证据就明确未覆盖。
5. **工程代价**：收益、成本与交换关系。数字需要测量依据；没有测量时讨论可观测指标，不编收益比例。
6. **常见误解**：有依据的错误说法、纠正及原因。不规定数量，不要求归因为“官方没讲清”或“资深开发者也会犯”；证据不足的误区写为待检查的问题。
7. **项目决策**：采用条件、限制、替代方案及停止或重新评估的信号。明确哪些是工程建议，哪些是已验证事实。

## 证据与公开边界

每项重要结论标明证据类型、来源定位与覆盖范围，可合并成表：

| 结论 | 类型 | 来源 / 版本 | 能支持的范围与未验证项 |
|---|---|---|---|
| 本题结论 | 官方规范 / 公开源码静态核对 / 实验观察 / 工程推断 / 待验证假设 | 文档链接、文件行号或实验记录 | 明确环境与限制 |

- 规范描述、静态实现和实际运行结果分别表述，不能互相替代。引用现有实验时说明是材料记载；未独立复跑就不写成本轮实测。
- 本仓的 `docs/` 和 `content/` 均为公开材料。涉及源码级深挖，按仓库双仓约定先确认目标仓库；不把私仓 Unity C++ 函数体、结构定义、内部注释或其改写复制到公仓。函数名、路径可作事实指引，公开 Package 代码按其许可使用。
- 补资料需求用具体待核查项；需要作者真实数据或经验时，沿用仓库的 `DATA-TODO` / `EXPERIENCE-TODO` 标记，不从角色身份推导个人经历。

## 输出

开头列出本轮主题、材料、已有覆盖与本次补充范围；接着给七视角分析和关键结论的证据表，末尾列出影响写作的查证或实验需求。内容具体到可核对的对象、条件和因果，不要求每层都有 API、数字或版本号。

例如分析“单任务提交与保留本地修改”时，若材料只有 Git 教学实验，就区分候选内容与工作区状态；平台差异写未覆盖，不据此编出两条系统差异或生产恢复保证。
