# 最小必要改写

只落地已确认的问题，保留作者表达和未涉及的内容。能补一个有依据的条件就不重写整段，不借修改扩展主题。

## 材料读取与问题来源

- 接受正文或审查记录的文件路径、当前对话审查结果、用户明确的修改清单。用户手工指定修改本身就是有效来源，不要求先运行其他技能。
- 先读当前待改内容，核对记录对应的文章和版本。旧审查与当前文本不一致时重新定位；不能定位的项列为待确认，不盲目套用旧句。
- 需要系列背景时，从[根路由](../../../doc-plan.md)进入 canonical plan，再读相关 `content/` 正文。`docs/` 中的 outline、工作单和审查记录可作依据，`kb/` 按需参考；不把准备材料当发布正文，不全站扫描或改历史归档。
- 定位和读者沿用本篇与系列，写法以[文章方法](../../../docs/article-writing-method.md)为准，不因通用模板改变原有文章类型。

## 可执行的修改依据

1. 用户明确指定的替换、删改或已确认问题。
2. col-risk、col-bridge、col-consistency 等审查的已确认项，或其他来源清楚的审查记录；来源不必在当前聊天。
3. 需要外部事实的修改，必须有相应资料支持。审查建议和用户同意修改并不自动证明某个版本、测试结果或数字为真。

没有已确认问题时，先查用户提供的材料与说明；仍缺依据才询问需要修改的具体项。不要自行把文章全面重审后整篇改写。

## 修改规则

- 逐项对应问题，保留语气和主线；除非用户明确要求，不调整章节顺序、合并小节或补新主题。
- 有来源支持时才增补版本、平台、条件和数字。不用“通常”掩盖无依据结论，不把待填占位符当可直接发布的句子。
- 待核查项单列，说明缺什么以及为何不能改；继续处理不受影响的已确认项。
- 链接、frontmatter 或导航涉及修改时按[呈现约定](../../../docs/article-presentation.md)处理，不手写模板已有的重复导航。
- 用户要求建议时只给替换建议；用户要求修改文件时直接在已授权文件内落地，不额外索要同一授权。只改明确范围并保留无关工作区变更。
- 落盘后检查实际差异；涉及文章、模板或导航时按仓库规定执行相应验证，报告实际执行结果与未核验项。未经授权不提交、推送或发布。

## 输出

建议模式逐处输出：**位置与原句 → 修改后 → 修改理由及问题来源**。可替换句应完整、无需额外猜测；无法确认的项标“待核查”，不伪造替换句。

文件修改模式简述已改范围、对应问题、待核查项和验证结果，不必复述所有未改内容。两种模式都不把审查建议误报为已落盘修改。

例如用户明确要求把某篇的“审查”统一改为“评审”：读取该篇并按指定范围替换即可，不因缺少 col-risk 输出而等待，也不顺带扩写评审平台功能。
