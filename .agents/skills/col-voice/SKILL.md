# 聊天取材与作者表达

先听作者讲真实经历、想法与感受，再把已有材料整理成文章。保留作者的说法、判断和不确定性，不代编经历，不把聊天变成履历包装或问卷。

## 输入与范围

- 先识别任务。“从我的角度打造专栏”“专栏要写清楚什么”“先补哪些基础”属于编辑方向或知识盘点；转读[站点中心思想](../../../docs/site-entry-and-audience-plan.md#column-core-principles)，按请求给判断或落实规划，不以采访问题结尾。需要时使用 twoegg-article-method、col-next 或 col-editor；无需先取得一段个人故事。
- 只有用户明确要求聊天取材、整理亲历与个人表达，或具体成文确实缺少所需亲历时进入以下对话流程。用户说明“我在说规划，暂不采访”就立即切回规划任务，不受上一轮技能惯性影响。
- 接受零散讲述、文章路径、旧笔记、作者自己的原话或当前对话；已有路径就直接读取。只为了解本次话题补读相关材料，不默认扫描所有文章或历史聊天。
- 作者明确更正的内容优先。旧文章或 AI 举过的例子不自动等于作者亲历；来源不明的第一人称叙事先核对，不能用它补全记忆。
- 用户只想先聊时就继续对话；已提供足够材料并要求成文时，可以直接整理，不强迫重走一轮采访。普通技术解释、局部校对不需要强行加入作者故事。
- 把讲述正文与给编辑的指令分开：例如“没有统计过人数和时间，不要写这些”用于约束写作，不自动变成文章中的自述。不同场景或项目的材料也不自动拼成同一次经历。
- 聊天素材默认留在当前对话；本仓的 `docs/` 与 `content/` 都是公开材料，不自动把原始聊天、姓名、内部路径或未确定公开的细节写入仓库。已有明确保存范围时依授权处理。

## 聊天时怎样接住作者

- 每轮围绕作者刚讲的一件事，通常只问一个具体、开放的问题。先简短回应听到的内容，再顺着其中最值得展开的细节问，不一次列出整页问题或让作者填表。
- 可以从为什么在意、当时发生了什么、自己做了哪部分、怎么判断、什么让想法变化、现在怎么看等方向追问；这些是可选方向，不是每次都要完成的清单。
- 用中性问法，不把预设放进问题。不问“是不是终于意识到必须做平台了”，而问“当时你为什么决定做这个工具”。
- 作者说烦、开心、犹豫或好奇，就沿其原话理解；不擅自升级为焦虑、崩溃、使命感等情绪。不替作者猜别人当时的想法。
- “记不清”“没想过”“不想谈”都是有效回答。可换一个有记忆的切口或使用已有材料，不暗示某个细节一定发生过，不逼出完整时间线、挫折或反转。
- 个人感受与偏好不要求日志证明。技术行为、量化效果与协作者贡献仍按实际依据表达；没有数字不妨碍讲一个有边界的经历。

## 留住什么材料

在对话上下文中区分以下内容，不必每轮向用户展示记录表：

| 材料 | 整理时保留的区别 |
|---|---|
| 亲历与具体行动 | 作者说自己做过什么、参与到哪一步，哪些是别人做的；作者回忆与日志核对分别记录 |
| 当时的想法与感受 | 只采用作者讲出的内容，不用现在的理解改写当时的动机 |
| 现在的回望与偏好 | “现在看来”“我更愿意”“我可能”等视角与限定，不推成普遍真理 |
| 有辨识度的原话 | 口头用语、节奏、具体比喻、犹豫或幽默；改述不冒充逐字引语 |
| 未知、矛盾与编辑建议 | 分开标明待问、待核查和助手提议，不写成作者已确认的事实或观点 |

只记得一部分，就围绕这一部分写。没有说过的日期、人物、对话、场景、动机、成果、失败与后续变化，不能为了连贯而补出来。

## 从聊天到文章

1. 当核心经历或观点已有材料、个人表达有着落时，用几句话回放理解与文章方向。用户已授权整理且关键意思明确，就继续写；影响亲历、职责、因果或感受的歧义才需要先问，不循环索要确认。
2. 从作者真正在意的点组织文章。允许写困惑、小发现、未解决的疑问和普通感受，不要求每篇都有事故、成长弧线、成功落地或方法论升华。
3. 用户要片段就写片段，要完整正文就在材料支持的范围内成文，不停在工作单或骨架。缺少关键素材时继续聊；无法确认的内容可省略，或在作者工作备注中列待补，不编造过渡事件。
4. 按 [文章写法](../../../docs/article-writing-method.md)处理技术内容；需要系列归属时从[根路由](../../../doc-plan.md)进入 canonical plan。个人回望可以采用适合的轻结构，不强套技术原理篇的章节，也不另建一份篇级规划。
5. 起草后核对每个“我做过、我当时觉得、后来发生”的来源，并与原话比较：有没有扩大贡献、强化语气、补成因果或改变尚未确定的判断。只在必要处向作者说明改写或待核对项，不把材料审计语言铺满正文。

## 保留作者表达

- 整理顺序、重复和语病可以帮助阅读；有辨识度且不妨碍理解的说法尽量保留，不全部换成统一的技术编辑口吻。
- 作者讲自己的事，用自然的第一人称；合作者的行动照实归属。不反复改成“作者确认”“作者进一步提供”，也不把团队工作全部写成“我”。
- 保留“我觉得”“可能”“现在还不知道”等原有强度。不能把“用的人不多”写成“团队成功采用”，也不能把“现在觉得当时太急”写成“当时就已经认识到问题”。
- 不新增现场对白、心理独白、感官细节、戏剧性冲突或收益数字。需要补充技术解释时与亲历分清，不把助手推导出的理念塞进作者口中。
- 引用原话时保持准确；示例、假设和助手拟句不能在后续稿件里变成真实经历。根据作者反馈改稿时以更正为准，不为维护成稿完整而保留已否认的细节。
- 用户只更正一句或一段时，围绕这次更正局部修改，不顺带补回未提供的行动与前后经过。“于是、就、所以、后来”引出的因果和时间顺序也必须有原话依据，不能仅靠读起来顺畅。

## 对话示例（虚构，仅演示问法）

用户：“那阵子同一个问题老有人来问，挺烦的，先聊聊，别写文章。”

助手：“好，先聊这件事。那时候大家反复问你的是什么问题？”

不要接着替作者补“后来我连夜写了工具，终于让大家摆脱了重复劳动”。

## 产出与后续

聊天阶段输出自然的回应与下一问；阶段回放用简短文字；成文阶段直接给所需文章或片段，可附极少量待核对备注。不要每次都输出完整取材表。

后续需要技术查证、结构审查或落盘时，按 twoegg-article-method 及[呈现与验证约定](../../../docs/article-presentation.md)处理，保留这次谈话中已有的个人表达；审稿不能顺手抹去这些声音。仅在授权文件范围内写入，不自动提交、推送或发布。
