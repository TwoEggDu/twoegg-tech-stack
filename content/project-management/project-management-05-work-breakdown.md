一份培训准备清单写着：“讲师做讲义，组织者通知参加者，规则负责人解答问题。”三个人都有任务，却仍然可能在培训当天发现：讲义用的规则版本不同，练习没有准备，场地也没人确认。

按人列任务能提醒各自眼前的事情，却很难回答一个更早的问题：**为了交出已经承诺的结果，总共需要覆盖哪些工作？** 如果这一步漏了，后面把任务分得再清楚、日期排得再整齐，也只是把不完整的工作安排了一遍。

[PM-04]({{< relref "project-management/project-management-04-goals-scope-acceptance.md" >}}) 已经把培训目标、范围和验收条件写成共同约定。本篇从这份约定出发，用工作分解结构识别需要交付的结果，再把它们连接到可以安排、检查和交接的工作。

> 本文沿用虚构的物品借用登记培训：12 名参加者、90 分钟、600 元直接支出上限均为教学设定。分解结构、角色安排和样表也是教学设计，没有对应的实际实施记录。

## 一、WBS 先说明范围怎样组成

WBS 是 Work Breakdown Structure，通常译为“工作分解结构”。它以交付成果为线索，将项目范围逐层拆成更小的部分。往下一层，应该更清楚这个结果包含什么工作；往上一层，应能解释这些部分怎样组成约定的整体。[1]

这里的成果不限于对外提交的成品。确认过的规则、可用的场地安排、项目跟踪记录和移交记录，也可能是完成项目必需的内部或中间成果。把它们漏掉，工作并不会消失，只会在执行时临时冒出来。

WBS 最底层的组成部分称为**工作包**。工作包需要清楚到能够安排责任、估算投入并检查完成情况；形成它所需的具体动作，可以继续列到活动清单中。[1][2] 例如，“已核对的练习材料包”是一个结果，“编写申请样例、检查答案、修订材料”是产生这个结果的活动。

几种常见安排各自回答不同问题：

| 表达方式 | 主要回答的问题 | 在本例中是什么 |
| --- | --- | --- |
| WBS | 约定的项目范围由哪些结果及其工作组成？ | 材料、培训服务、检查与移交等分支 |
| 责任安排 | 谁执行、谁协调、谁有权确认？ | 讲师准备材料，规则负责人确认内容准确性 |
| 活动清单 | 为完成一个工作包要做什么？ | 编写样例、核对规则、修改问题 |
| 依赖与进度计划 | 哪些工作要等待什么，什么时候能够完成？ | 规则确认后才能完成对应材料的核对 |

这几类信息可以放在同一张表或同一个软件里，但仍要能区分。WBS 编号 `2.1`、`2.2` 表示层级归属，不自动表示先做 `2.1` 再做 `2.2`；把讲师和组织者画成两个分支，也没有自动证明范围已经完整。

## 二、从三类交付物展开，并补上支撑工作

上一章约定的主要交付物是讲义和练习材料、一场含练习的培训、练习与问题记录。先把这些结果摆出来，再检查为了得到它们还需要哪些准备、管理和收尾工作。

下面用缩进目录表达一份 WBS。树图和表格同样可以使用，形式取决于是否方便共同检查。[1] 本例采用成果为主的分组方式，不声称所有项目都必须按这四组拆分。

```text
0  本次物品借用登记培训项目
├─ 1  项目管理
│  ├─ 1.1  已确认的项目约定与变更记录
│  └─ 1.2  准备进度、资源与费用跟踪记录
├─ 2  可用的培训材料
│  ├─ 2.1  本次适用的规则确认记录
│  └─ 2.2  已核对的讲义与练习材料包
├─ 3  培训服务
│  ├─ 3.1  就绪的人员、场地与材料安排
│  └─ 3.2  已实施的讲解、练习与反馈
└─ 4  验收与后续移交
   ├─ 4.1  参加情况与能力检查记录
   └─ 4.2  验收决定与未完成事项移交记录
```

图中的叶子是本例选定的工作包，其他节点用于汇总。本例没有继续把“发送通知”“打印材料”画成叶子：它们可以作为 `3.1` 的活动，不需要为了显示工作认真而无限增加层级。

几个容易重叠的地方，要用文字分清：`1.2` 跟踪资源承诺和费用使用，`3.1` 完成场地确认、通知和物料准备；`3.2` 组织讲解、练习与现场反馈，`4.1` 负责按约定判定并整理每人的检查结果。一次现场活动可能同时产生多个成果，但同一份投入不能因为在两个分支中被提到，就算成两份工作量。

培训活动贯穿这些分支，WBS 却不表示它们必须依次执行。记录准备可以提前开始，能力检查会发生在培训过程中，整体接收则要等相关证据齐备。具体依赖要在活动层另行确认。

还有一个重要区别：`4.2` 的记录完成，不等于整体验收通过。上一章要求三类交付物符合约定，且 12 人全部通过能力检查；如果只有 10 人通过，记录应保留“整体验收未通过”，并明确后续指导、复查的责任、时间与资源。不能因为 WBS 上所有记录都已填写，就把原目标改成完成。

## 三、用范围核对遗漏，也核对多做与重复

WBS 的“100% 规则”要求子层完整覆盖父层所代表的工作，整个结构覆盖约定范围，同时不把范围外工作悄悄加进来。内部成果、中间成果和项目管理工作都在检查之内。[1]

这个百分比描述的是**范围覆盖关系**，并不是“所有未来事情都能提前预测”，也不是“工作完成率已经达到 100%”。只看结构整齐不能证明覆盖完整，仍需回到范围说明、需求与验收条件逐项核对。

本例可以这样检查：

| 已有约定或必要工作 | WBS 中的落点 | 需要核对的边界 |
| --- | --- | --- |
| 目标、范围和条件有共同确认，变化有记录 | 1.1 | 规则的业务内容由 2.1 核对，1.1 维护项目承诺 |
| 准备有人跟进，资源与直接支出有记录 | 1.2 | 不把组织者的协调时间当成零成本；600 元仅为直接支出口径 |
| 讲义与练习采用同一版现行规则 | 2.1、2.2 | 确认现行规则，不包含修订整套管理制度 |
| 12 人能收到安排，场地和材料可用 | 3.1 | 不能只写“发通知”，还要知道参加条件和场地是否落实 |
| 在约定时段提供讲解、独立练习和反馈 | 3.2 | 不默认增加录播、额外专题或超出约定的补训 |
| 每个人的参加情况、能力检查和未掌握项可追溯 | 4.1 | 不用签到或平均分替代每人的能力检查 |
| 有权者作出接收决定，未完成事项有承接安排 | 4.2 | 未通过时如实记录；后续支持另行评估确认，不能用移交掩盖未达标 |

这张表同时可以反向读。若某个工作包找不到对应的约定或必要性，应说明它为什么必须存在；若有人想把录播课程加入 `2.2`，就先讨论范围变化，而不是借着“拆细一点”扩张承诺。

重复也需要处理。假如材料组列了“练习题”，授课组又列一份同样的“练习题”，应决定由哪个工作包生产，另一个工作包只引用和使用。若确实是两种不同用途的材料，就在名称、内容和检查方式上分清。交接双方都需要检查，并不意味着要各自再生产一份同样的交付物。

采购、评审、资料整理、验收、移交等常被漏掉，因为它们没有最终成品那么显眼。检查这些工作是否适用，比机械地为每个项目增加同一套分支更有用。发现原范围已经要求的工作被漏写，是修补分解；增加原范围没有承诺的新成果，则需要确认范围是否改变。两者可能都影响投入和日期，但决定依据不同。

## 四、工作包说明要让另一个人接得住

只写“材料包”仍不足以交给执行者。WBS 给出层级位置，配套说明需要补充含义、边界和检查条件。这类说明通常称为 WBS 字典；小项目不必另建厚文档，可以直接放在工作包旁边。[1]

以下是 `2.2` 的填写示例：

| 字段 | 本例的约定 |
| --- | --- |
| 编号与结果 | 2.2：一套已核对、可用于本次培训的讲义与练习材料包 |
| 输入 | 1.1 的已确认范围及能力检查条件；2.1 的适用规则和版本；12 名目标参加者的已知基础与资料使用条件 |
| 包含的工作 | 编写讲义和两类申请样例，准备空白登记表与检查说明；请规则负责人核对；修订问题并保留确认记录；向组织者交接同一版本 |
| 本包不包含 | 场地、通知、物料发放由 3.1 处理；现场授课归 3.2；实际答卷的判定与人员状态记录归 4.1；制度修订、录播和遗失损坏专题不在本次范围 |
| 完成条件 | 讲义与确认规则一致；包含常规登记及缺必要信息两类情况；独立练习使用未完整演示的新申请；检查说明与 PM-04 的能力标准一致；核对中影响使用的问题已处理 |
| 证据与确认 | 材料版本、对应规则版本、核对意见及处理记录可查；规则负责人确认准确性，组织者确认材料齐备并可获取 |
| 执行与支持 | 讲师负责准备和修订，规则负责人提供解释与核对，组织者协调两者的可用时间；实际执行前落实到具体人员 |
| 估算与检查点 | 先与执行者确认投入，再与 3.1、3.2 约定需要材料的时间；规则未确认时标为输入阻塞，不填成已有可靠工期 |
| 变化处理 | 新要求超出当前范围、规则改变或修改影响使用时间时，说明影响并提交组织者协调；需要改变项目承诺时由有权者决定 |

这份说明没有把“写完文件”作为唯一完成条件。它要求材料可以被下一步实际使用，并留下与规则和检查条件一致的证据。也没有因为标了讲师负责，就默认讲师可以调动规则负责人的时间。

其中的“核对并修订”覆盖为达到已约定条件所必需的工作，但不等于无限追加资源。发现问题超出原估计时，要重新判断影响，协调支持或调整承诺；不能把“工作包里包含修订”解释成必须在原资源下完成任何修改。

如果读者要拿去使用，可以保留最少这些字段：

```text
工作包编号／结果／版本：
从范围说明中的哪项承诺而来：
输入及提供者：
包含的工作／不包含的工作及去向：
完成条件／证据／确认者：
执行者／需要的支持：
投入估算的依据／检查点／当前未确认项：
向谁交接，什么变化需要重新决定：
```

## 五、拆到能够管理，保留必要的判断空间

分解太粗，负责人很难判断还剩什么、哪里卡住；分解太细，计划会花大量时间维护微小动作，执行者也失去调整做法的空间。合适的细度取决于工作复杂度、风险、协作界面和检查需求，而不是固定层数或统一小时数。[1][2]

可以对一个工作包做几项检查：

- 能否说清它交出的结果和完成证据，而不只是“做一下相关工作”？
- 执行者能否解释需要什么输入，估算的依据和未知项是什么？
- 是否跨越了需要分别承诺和交接的责任边界？
- 如果中途出现偏差，能否在仍来得及处理时发现？

本例把讲义和练习合为 `2.2`，是因为假设同一讲师准备、同一规则负责人核对，并按一套材料交接。如果两部分由不同团队制作、有不同交付日期或分别接收，就有理由继续分成两个工作包。反过来，“打开编辑器”“发送第一封邮件”通常不足以成为这个项目的独立管理单位。

对远期或尚需探索的部分，可以先保留较粗的范围说明，写明什么还不知道、由谁在什么检查点补充。不能把一个尚不能估算和分派的大块标成“工作包已准备好”，也不能为了填满层级而编造细节。接近执行时再根据新信息细化，并同步责任、资源与进度安排。

《项目管理之美》第 2 章“分而治之”讨论了将较大的进度安排分为较小片段，并为调整保留机会。[3] 这个思路可以帮助理解为什么不必一次写尽全部细节，但它讨论的是进度组织，不能拿来代替 WBS 的范围分解定义。

## 六、从工作包接到活动、分工与下一步安排

工作包明确以后，再为它识别活动。仍以 `2.2` 为例：

| 活动 | 形成什么可检查的结果 | 主要输入或交接 |
| --- | --- | --- |
| 编写讲义和练习初稿 | 可供核对的完整草稿及问题清单 | 使用已确认的范围、规则和能力检查条件 |
| 核对内容与检查方法 | 逐项核对意见及需修改处 | 规则负责人能够查阅同一版本材料 |
| 修订并确认材料 | 达到工作包条件的材料及确认记录 | 关闭影响使用的问题；有争议时协调决定 |
| 向组织者交接材料 | 组织者能取得并识别正确版本 | 3.1 据此准备发放，3.2 和 4.1 使用同一套材料与检查说明 |

这些活动还要补负责人、投入估算、等待条件和可用时间，才能进入排期。工作包上的一个姓名不能代替各参与者的承诺；活动清单上的几个动作也不能直接给出完成日期。

读者可以拿自己的项目做一个短练习：先写主要交付物，补上为交付所必需的准备、管理和收尾，再选一个最容易扯皮的部分填工作包说明。请执行者检查输入是否拿得到，请接收者检查完成证据是否足够，最后用范围说明查一次遗漏、重复和额外承诺。

例如，把“组织者通知参加者”改成 `3.1` 后，就会发现只发出通知还不能说明准备就绪：目标名单、参加条件、场地和材料也要落实。这不是为了多填几行，而是为了让遗漏在开工前可见。识别清楚这些工作后，下一步才有依据讨论它们怎样互相等待，见 [PM-06 依赖、估算与进度提纲]({{< relref "project-management/project-management-series-index.md" >}}#pm-06)。
