开发说已经做完，测试说还没收到能验证的版本；新需求每天进来，旧任务因为等人确认一直停着。团队有迭代、有看板，也每天开会，却仍然无法说明下一项工作为什么现在开始、哪项结果真正可以交付。

这里需要连接三个问题：**这项需求支持什么结果，什么时候有能力开始，完成后由什么证据确认。** 只给任务加一个日期，或者把卡片移到“完成”，不能替代这些约定。

本篇面向安排需求、开发与测试协作的人。[PM-04]({{< relref "project-management/project-management-04-goals-scope-acceptance.md" >}})提供目标与验收基础，[PM-09]({{< relref "project-management/project-management-09-change-control.md" >}})说明变更与承诺，[PM-20]({{< relref "project-management/project-management-20-measurement-and-variance.md" >}})说明度量口径。这里讨论它们怎样进入软件研发的日常工作，不要求已经使用某种管理软件。

## 一、从需求到工作项，中间不能只剩一个标题

需求说明使用者需要什么，工作项是团队拿来安排、跟踪和验收的一份工作。一个需求可能需要多个工作项，但切分后的项仍要说明它对整体有什么贡献，以及谁接收它的结果。

Berkun第4章把目标作为区分有关与无关工作的依据；第7章进一步区分需求、功能行为、技术方案、工作列表与测试标准。[1] 它们可以写在同一个地方，也可以相互链接，关键是接手者能够找到当前约定，而不是在不同消息中猜哪一条算数。

以下使用一个**独立的虚构教学情境**：一个内部资料检索站点已有可用版本，团队正在改进搜索体验，同时维护下载功能。产品负责人、两名开发人员和一名测试人员共同安排工作；题设中的产品负责人有权排序需求，涉及额外预算或跨团队承诺时仍需升级。它不代表作者经历，也不承接PM-24原型已经成功的结果。

一个搜索工作项可以这样写：

| 信息 | 教学示例 |
| --- | --- |
| 目标与使用场景 | 使用者知道资料标题，需要在有访问权限的资料中找到对应条目；本轮先支持完整标题查询 |
| 结果边界 | 返回匹配且有权访问的条目及入口；没有匹配时明确提示；不扩展到全文检索、模糊匹配或自动纠错 |
| 验收样例 | 给定有权访问的匹配资料，应返回；没有匹配应提示；无权访问的资料不能通过本次搜索泄露标题或入口 |
| 依赖与输入 | 产品负责人确认匹配规则；开发说明权限接口与版本；测试准备有权、无权和无匹配的样例 |
| 工作与交接 | 实现、评审、集成及相应测试在同一工作项下跟踪，交出候选版本、验证记录和已知限制 |
| 排序与未决事项 | 产品负责人说明它相对其他需求为何更优先；接口含义未确认时，先登记问题，不用“高优先级”替代缺失输入 |

这不是一份完整的软件规格，只展示排工作前必须说清的关系。安全要求、数据范围和其他质量约束仍需针对真实系统补齐。验收样例也只是该工作项的部分检查，不能据此声称已覆盖整个权限体系。

拆工作时，尽量让一项结果能够被检查。例如可以先交付边界明确的完整标题查询，再讨论其他检索能力；而“后端完成”“前端完成”往往只是内部子任务，还要有人负责把它们集成为可用行为。跨团队确实需要分项时，保留共同验收对象和依赖，不把几个局部“完成”直接相加为功能完成。

如果连规则或技术路径都还不清楚，可先安排[PM-24的探索任务]({{< relref "project-management/project-management-24-exploration-estimates-and-checkpoints.md" >}})，交出有限问题的证据，再决定是否进入实现。探索项和功能项的完成信号不同，应明确标记。

## 二、周期与流动回答不同的问题

固定周期帮助团队定期检查一个阶段目标、检视结果并调整下一段安排。持续流动则强调每个工作项从开始到完成怎样前进，以及何时有能力接入下一项。两者可以结合，不能只凭日历或看板外观判断团队采用了什么方法。

| 安排 | 什么条件下值得采用 | 需要付出的代价 | 应重新考虑的信号 |
| --- | --- | --- | --- |
| 以固定周期组织目标和反馈 | 一组工作共同支持阶段目标，使用者能定期参与检查，团队能形成可验证的结果 | 需要共同规划与反馈；不能把所有临时请求无限加进本轮 | 周期末始终只有半成品，或持续性紧急工作反复打散目标 |
| 按可用能力持续拉入工作 | 请求持续到来，工作可以较独立地完成，排序和交接规则明确 | 要主动维护队列、处理老化和阻塞，不能只等下一次计划会 | 每项都要等待同一个大批次才能交付，或频繁改序使长期目标无人负责 |
| 固定目标复查，加上周期内的流动控制 | 产品改进需要共同方向，日常维护又持续发生 | 两套节奏要共享人员容量、完成口径与变更决定 | 功能与维护各占满同一组人，紧急项变成不受约束的第二条队列 |

Berkun第2章将较长计划拆成有限片段，片段内仍包含设计、实现和测试，再根据新信息调整。[2] 本文保留这个结构，不把书中的三分时间或任务天数当作比例标准。缩短周期本身不会生成反馈；如果关键使用者始终不在，先解决反馈来源。

本例假定使用者代表每周可以参加一次结果检查，因此可以试用一周的共同目标复查，同时限制周期内已经开工的任务。这个“一周”是教学安排。若反馈条件改变，就应调整；也不意味着每周只能发布一次，或每天来的请求都必须等到周末才能处理。

Scrum Guide 2020中的Sprint是一个月或更短的固定时长事件，期间不得作出危及Sprint Goal的变化，质量不得下降；随着学习，范围可以与Product Owner澄清和重新协商。[3] 这说明“周期内绝不能改任何任务”并非指南原意。但Scrum有完整的职责、事件与工件要求，本例的每周安排不因此成为完整Scrum实践。

## 三、先定义工作流，再画列

The Kanban Guide（May 2025）把工作流定义放在核心位置：工作项是什么，何时开始与结束，中间经过哪些状态，怎样控制在制品，以及各状态怎样流转。[4] **在制品（WIP）就是已经开始、尚未完成的工作项。** 它包括等待和阻塞，不能只数当前有人正在敲代码的项。

本例把“开始”定义为团队正式拉入实施，把“结束”定义为满足下节共同完成标准、形成可交付候选。工作流约定如下：

| 状态 | 进入与离开的条件 |
| --- | --- |
| 待澄清 | 记录请求来源、目标与疑问；缺规则或决定时交给相应负责人，不默认为已接受承诺 |
| 可选择 | 目标、边界、验收样例和必要输入已足以支持当前实现，实施者已参与核对；等待排序和容量 |
| 实施中 | 团队有可用能力且按排序拉入；含必要设计、编码和评审，记录开始时间 |
| 待验证 | 交出可验证的候选版本、变更说明与必要材料；等测试也是在制品 |
| 验证中 | 在约定环境中检查行为和集成；不符合标准就回到相应处理环节，保留历史与原开始时间 |
| 可交付 | 达到共同完成标准，记录完成时间与证据；是否已发布、是否被使用另行记录 |

进入条件是团队的工作约定，不是为了把所有设计在开工前定死。发现新信息可以继续澄清；真正影响原承诺时按权限处理。这里也不把“准备就绪”包装成Scrum官方规定的额外工件。

题设先用**总在制品上限3项**试行，覆盖“实施中、待验证、验证中”以及这些状态中的阻塞项。3只是初始教学参数：需结合任务大小、协作方式和可用能力复查，不能按人数直接推出最优上限。不是每人都必须占一张卡，也不是一位成员空下来就自动新开任务。

当验证前堆积时，可以先帮助准备复现材料、修正失败项、解除依赖，再决定下一项是否能开始。帮助必须符合能力与权限，不能为了让数字下降，就由未具备条件的人代替必要的独立核验。Berkun第14章对在做什么、被什么阻塞、下一项输入是否明确，以及上项是否真正完成的追问，可用于这种日常检查。[5]

阻塞是附在工作项上的状态信息：写清等什么、找谁、何时再次核对及升级条件。可以把它显示成单独区域，但既然已经开始，它仍计入本例的总在制品。若真正取消工作，应记录取消决定及遗留处理，不能把取消当作成功交付；移到“暂停”也不会让已投入和未完成责任消失。

## 四、共同完成标准要跨过编码结束

工作项的验收条件说明这个功能具体应做什么；共同完成标准说明团队对这类交付物一致要求什么质量状态。前者不能只写“按需求实现”，后者也不能只写“开发自测通过”。

本例约定进入“可交付”前，至少具备：

- 约定行为与相关失败路径通过检查，变更经过评审；本次修改影响的权限边界有对应验证。
- 已合入共同的候选版本，与既有功能一起验证，结果能定位到版本、环境、输入和记录。
- 必要的配置、使用说明、发布与恢复安排已经准备并核对；未解决事项明确，阻止交付的缺陷未被掩盖为普通备注。
- 产品负责人能按已约定范围核对结果，测试与开发对证据和限制有共同理解；正式接收权限仍按组织约定执行。

这些是教学情境中的质量约定，真实项目需要结合产品风险制定。若组织已有最低标准，不能为了赶周期临时降到它以下。Scrum Guide用Definition of Done表达增量所需的质量状态，未达到它的工作不能算入增量；指南也明确Sprint Review不是发布价值的闸门。[3]

因此，**编码完成、形成可交付候选、实际发布、使用者采用是不同状态。** 本例的流动计时在“可交付”结束，但发布等待仍需单独可见；如果要回答用户从提出请求到真正可用等了多久，就必须使用更长的起止边界。不能用较短的开发周期替代用户等待时间。

到周末仍在验证的项继续显示真实状态：说明已具备什么、还缺什么和后续决定，不把它打勾后再开一个名字叫“补测试”的任务来美化完成率。固定周期的复查可以如实讨论未完成工作，不能把未达到质量要求的半成品宣传为可交付成果。

## 五、变化先经过判断，再改变正在做的工作

新信息到来时，先区分它改变了哪一层：

| 输入 | 处理方式 | 决定边界 |
| --- | --- | --- |
| 澄清既定行为 | 例如确认无匹配时的提示措辞；核对是否改变范围、质量与工作量，更新当前说明 | 不因称作“澄清”就免于影响评估；涉及承诺变化时升级 |
| 实现中发现缺陷 | 保留原验收要求，安排修正和复验，更新剩余预测 | 不能通过删除验收条件让工作看起来完成 |
| 新增能力 | 例如增加全文检索或自动纠错；进入待澄清与排序，再比较代价 | 产品负责人决定优先次序；实施者确认容量和方案，超出权限的承诺另行批准 |
| 紧急中断 | 先核实影响、严重性及临时处置，再由约定有权者决定响应和工作调整 | “有人催”不能自动取得最高级；安全恢复步骤仍须遵守相应权限与检查 |

周期内新增能力可以替换原计划中的低优先级工作，但应说明移出什么、阶段目标是否仍成立、谁受到影响。已经开工的工作暂停后仍要跟踪，不能假装没有发生。实际采用Scrum时，Sprint Goal过时才涉及取消Sprint，且只有Product Owner有权取消；这条框架规则不能偷换成“任何经理都可中途加任务”。[3]

用一个离散的看板推演说明紧急插入。下面只有状态变化，没有真实执行结果，也没有推断完成速度：

| 时点 | 已开始但未完成的项 | 数量与决定 |
| --- | --- | --- |
| T0 | A：标题查询实施中；B：搜索结果显示更新时间，待验证；C：帮助页修正，因文本确认阻塞 | 在制品3项，达到上限；新请求先入队，不直接开工 |
| T1 | 原A、B、C仍未完成；另有D：已有下载功能不可用，题设假定已核实需立即恢复 | 产品负责人按预先约定的应急权限批准一次例外，开发与测试确认响应安排；暂停A，把相关能力转给D。D实际开始后在制品是4项，不能把暂停A或阻塞C藏掉后声称仍为3 |
| T2 | D达到共同完成标准，恢复发布还须按应急安排核验；A、B、C仍未完成 | 本例工作流的在制品回到3，仍未获得普通新项的空位；恢复情况另行跟踪 |
| T3 | B也达到共同完成标准；A、C仍未完成 | 在制品降为2；先核对C的依赖、D恢复工作的占用与实际可用能力，再决定能否拉入下一项 |

这里的例外不是给团队永久加一个名额。例外记录要写批准人、影响、临时上限、恢复常态条件和复查时点。本例约定最多同时一个应急例外，临时上限4；D离开在制品后恢复3。若又来一个紧急事项，必须重新比较响应安排并升级，不能自动叠加额度。暂停A会影响它的预测日期，要及时通知依赖方。

例外减少了规则对即时响应的阻碍，却提高了同时未完成工作的数量。是否值得，要看实际影响；频繁使用例外说明原容量或维护安排需要调整，不能以“灵活”为理由长期绕过限制。

## 六、用流动数据找下一步，不给成员排名

The Kanban Guide列出四项必要的流动指标。[4] 先固定工作项单位和开始／结束边界，再讨论数字：

| 指标 | 本例口径 | 能帮助提出的问题 |
| --- | --- | --- |
| 在制品 WIP | 已拉入实施、尚未达到可交付的项数，含等待和阻塞 | 是否同时开了过多工作？是否在验证前积压？ |
| 吞吐量 Throughput | 一个观察窗口内达到可交付的工作项数量 | 系统在这段时间完成了多少项？任务大小与类型是否变化？ |
| 工作项年龄 Work Item Age | 未完成项从开始到当前的经过时间 | 哪项长期没有前进，需要查依赖、返工或等待？ |
| 周期时间 Cycle Time | 已完成项从开始到完成的经过时间 | 完成项经历了多长时间，长尾集中在哪些条件？ |

例如，另设一个时间口径练习：某项在11月3日10时开始，11月5日10时完成，按连续日历时间计为48小时，包含夜间和等待；另一项从11月2日10时开始，到11月5日10时仍未完成，年龄为72小时，不能把它排除后宣布所有任务都在两天内完成。这不是前面T0—T3的时间线，更不是开发人员有效工时。

吞吐量按“项”计数，不能直接等同于用户价值或不同团队生产率。工作项切得更碎就可能让数字增加，未必交出了更多可用结果。除了这些流动指标，还要结合失败、返工、发布等待及用户反馈；定义与分母的检查接PM-20。

该指南还要求工作流明确服务水平预期（SLE）：用经过时间及对应概率表达完成预测，通常基于历史周期时间；没有历史数据时，可以先用明确标注的初步判断，之后再校准。它是预测，不是保证。[4] 本例没有真实历史数据，不编造百分位或承诺“某比例必在几天内完成”；本文演示的是流动规则与状态推演，尚不是已经运行、满足全部要求的Kanban系统。

观察应接到动作。例如，B类项反复等待验证，要检查候选版本、材料、验证能力和到达节奏；C类项长期等确认，则找规则与决定责任。给所有人再开更多任务，通常不能直接修复这些缺口。调整上限、状态或交接约定后，需要同口径继续观察；单次队列下降不足以证明效率改善。

## 七、把安排压成一页，试用后再改

读者可以用本篇形成一份最小工作约定：

| 要约定什么 | 本例的起点与复查问题 |
| --- | --- |
| 目标与反馈 | 每周检查共同目标与可交付结果；使用者代表是否实际参与，反馈有没有进入下一步？ |
| 进入条件 | 目标、验收样例、必要输入可查，实施者理解；是正常学习，还是长期缺输入却被迫开工？ |
| 同时开工 | 总在制品暂定3，阻塞与等待计入；遇到堆积先查原因，是否需要改变工作组织？ |
| 完成口径 | 达到共同质量标准才进可交付；发布与使用状态分别记录，是否存在隐藏的下游队列？ |
| 变化与例外 | 产品排序、团队确认容量；应急例外按明示权限决定并保留影响，是否已经成为常态？ |
| 观察与修订 | 按约定边界观察四项流动指标及质量、使用反馈；到每周复查或重大条件变化时，决定保留、修改或停止试用 |

先用一小组真实工作检查这些约定是否可执行，再调整。不要把每张卡填满当作成功；要看接手者能否知道下一步、等待是否有人处理，以及交出的结果是否满足约定。跨团队如何共同确认这些交接，接[PM-26提纲]({{< relref "project-management/project-management-series-index.md" >}}#pm-26)。

## 来源与延伸阅读

1. Scott Berkun，《项目管理之美》，机械工业出版社，2009，ISBN 9787111259527，第4章“编写好的远景文档”中的目标驱动与统一，第7章“撰写优秀的规格说明书”中的“决定需要撰写什么”。用于连接目标、需求、工作项和验证依据，不照搬固定目标数或文档规模。
2. 同书第2章“进度表的原理”，重点为“分而治之（大进度表＝许多小进度表）”及相邻的设计、实现、测试讨论。用于有限范围内安排与反馈，不将三分时间模型或早期方法分类作为现行规范。
3. Ken Schwaber、Jeff Sutherland，[The Scrum Guide](https://scrumguides.org/scrum-guide.html)，November 2020，核对The Sprint、Sprint Backlog、Commitment: Sprint Goal、Increment、Definition of Done。本文只解释相关边界，没有宣称教学安排符合完整Scrum。
4. [The Kanban Guide](https://kanbanguides.org/the-kanban-guide/2025.5/)，May 2025，核对Defining and Visualizing the Workflow、Actively Managing Items in a Workflow、Improving the Workflow、Flow Metrics。用于工作流、在制品、拉动、例外、SLE及四项指标；本文上限和规则是教学设计。
5. Berkun同书第14章“中盘战略”，重点为“编码管道”“追踪进度”。用于识别阻塞、准备下一项输入、检查完成质量和整体状态，不把编码视为唯一产出，也不采用固定缓冲项数或任务天数。
