## IL2CPP 是什么、为什么贵

一次 Jenkins 构建失败，可能发生在 Unity 编译之前，也可能在产物签名或上传时。首先要区分整个交付任务与其中的 IL2CPP 代码构建链。

Unity 2022.3 的 IL2CPP 构建会经历托管程序集编译、托管代码裁剪、生成 C++、调用本机编译器等步骤。示意如下；平台上的导出工程、链接和打包过程还需结合实际构建日志识别。[Unity 2022.3 IL2CPP 概述](https://docs.unity3d.com/2022.3/Documentation/Manual/IL2CPP.html)

```text
C# 与所需包代码
    → 托管程序集
    → 托管代码裁剪
    → IL2CPP 生成 C++
    → 平台本机编译与链接
    → 对应平台的二进制，再进入必要的打包与签名
```

代码生成量、优化设置和平台工具链都会影响工作量。不能用 C# 行数直接推导编译时间，也不能把每个泛型实例都理解为一份独立生成代码：IL2CPP 存在泛型共享，生成方式受类型和设置影响。[Unity 2022.3 脚本限制：泛型](https://docs.unity3d.com/2022.3/Documentation/Manual/ScriptingRestrictions.html)

某阶段失败后哪些结果能复用，由构建系统的依赖判断和缓存状态决定，不等于整条链必然从头执行。

## 构建时长特征：每阶段耗时分布

先固定 Editor 完整版本、目标平台与架构、SDK/NDK/Xcode 或编译器版本、构建选项、源码与资源版本、缓存条件和同机任务。否则，“这次比上次慢”可能比较的是两种不同构建。

| 阶段 | 建议核对的记录 |
|------|----------------|
| Unity 资源处理 | 是否发生导入、资源构建或重复后处理，不把它们记成 IL2CPP 转译 |
| 托管编译与裁剪 | 处理哪些程序集，是否出现编译或保留规则变化 |
| IL2CPP 转译 | 实际输入、代码生成设置与输出变化 |
| 本机编译 | 编译任务数量、实际并发、CPU 和内存使用 |
| 链接 | 链接器身份、优化选项、输入与资源使用 |
| 打包、签名与交接 | 平台工具耗时、产物检查及上传等待 |

`BuildReport` 提供构建概要与步骤信息，可与 Editor 日志和平台工具日志对齐。步骤可能有父子层级，不能将所有步骤时间直接相加当成墙钟时间；外部 Jenkins 阶段也要单独记录。[Unity BuildReport API](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Build.Reporting.BuildReport.html)

### C++ 编译为什么慢

先确认当前慢的是哪些编译任务，再看是否存在可并行工作、内存压力或 I/O 等待。增加 CPU 核数能否获益，要比较固定输入下的结果；不能承诺核数增加四倍，时间就缩短到四分之一。

旧稿关于生成文件数量和各阶段占比没有样本依据，已撤下。后续若补表格，应同时提供测量范围与构建条件。

### 链接慢的根因

应先确定本次使用哪个链接器及哪些参数。LLVM LLD 的官方资料明确展示了多线程支持，因此不能把所有链接器写成“单线程、加 CPU 没用”。这也不意味着某个 Unity 项目一定使用 LLD，或能获得官方示例中的收益。[LLVM LLD 官方说明](https://lld.llvm.org/)

链接输入、调试信息、优化方式、CPU、内存与存储都可以列为待查因素。只有观测到对应的等待或资源压力后，才适合决定调整哪一项。

## 内存特征：峰值与持续

### 阶段性内存使用

本篇不再画带具体 GB 和分钟数的曲线，因为没有对应采样。需要分别记录：

- 发生峰值时运行的阶段、进程与子进程。
- 使用的指标口径，例如进程驻留内存、提交量或系统可用内存。
- 同一时刻的其他构建，以及容器或作业的资源限制。
- 错误时间、退出原因和系统记录。

编译任务叠加也可能造成内存压力，不能预设峰值一定在链接阶段。不同进程峰值发生在不同时间时，也不能简单相加当作整机峰值。

### Mono / Bee 增量构建

Unity 2022.3 的增量构建适用于 Mono 与 IL2CPP，按输入变化复用可用结果；项目构建结果与跨项目缓存有不同存储范围。构建回调及其输入的变化可能需要 clean build 验证。[Unity 2022.3 增量构建管线](https://docs.unity3d.com/2022.3/Documentation/Manual/incremental-build-pipeline.html)

具体哪些任务重跑、是否重新链接，要看该次日志。不能把“链接内部是否支持增量”和“上层构建系统能否跳过链接任务”混为一谈，也不能给出修改一行代码后的固定最低耗时。

### 进程数控制

需要区分 Jenkins executor 数量、同机 Unity 构建数量，以及单次构建内部的编译并发。调整其中一层，不保证其他层跟着变化。

旧稿的 `UNITY_IL2CPP_PARALLEL_JOBS` 未找到可核对的适用版本与官方接口依据，已撤下可执行示例；这不构成该名字在所有工具中都不存在的断言。实际调节应先确认固定工具版本支持的入口，再从进程与日志确认生效。不能仅凭环境变量设置成功就声称并发已改变。

## 磁盘 I/O 特征：中间产物的体积爆发

### 中间产物体积

分别盘点项目缓存、生成代码、本机编译产物、导出工程、包与符号文件。目录结构取决于 Unity、平台工具和构建方式，旧稿的 iOS 路径与容量表不能作为跨平台模板。

记录构建前、峰值附近和结束后的占用，并避免将嵌套目录重复相加。最终包大小也不能代替构建所需的临时空间。

### I/O 密集时段

转译和本机编译都包含文件读写；存储是否限制本次构建，需要结合设备延迟、吞吐、队列与进程活动判断。Unity 官方将较快存储列为改善构建时间的方向，但并未为本项目证明固定加速倍数。[IL2CPP 构建时间说明](https://docs.unity3d.com/2022.3/Documentation/Manual/IL2CPP.html#OptimizingBuildTimes)

不从一个 IOPS 值或固定延迟阈值推断所有设备，也不把所有慢构建归因于磁盘。

### 清理时机

清理前确认构建及后处理已经结束，交付物和所需诊断材料已经保留，候选目录没有其他任务使用。删除缓存后是否重跑、重跑多少，仍要由下一次构建核对。

具体保留与清理边界见 [203 Workspace 与产物的磁盘治理]({{< relref "delivery-engineering/delivery-jenkins-ops-203-disk-governance.md" >}})。本篇撤下按猜测目录名删除中间产物的建议。

## Agent 配置基线

按代码行数给出 CPU、内存和固定构建时长，会忽略平台、泛型共享、优化设置、资源处理和并发。旧配机表已撤回，改用下面的评估顺序；它是待执行的验证设计。

| 顺序 | 记录什么 | 用来决定什么 |
|------|----------|--------------|
| 固定一条代表性构建 | 输入、工具链、目标与交付物 | 确认比较的是同一类工作 |
| 区分干净构建与增量构建 | 实际复用内容、分阶段耗时与产物检查 | 确认缓存收益与失效成本 |
| 从单任务观察开始 | 整机与进程的内存、CPU、磁盘峰值 | 找到容量约束和测量缺口 |
| 再增加同机负载 | 同时构建时的资源使用、排队、耗时和失败 | 确定可接受的并发，而非假定两任务必然 OOM |

验收要同时考虑结果正确性、资源余量和交付等待时间。一次单任务成功，不足以承诺某个并发数长期稳定。

### 配置陷阱

宿主 OS、平台工具链和产物形式要一起记录。例如，iOS 导出工程后的 Xcode 构建与 Android 的工具链不是同一种测量。不要把 Linux 的内存诊断或某个平台的中间目录套到所有 Agent 上。

Jenkins controller 存储与 Unity 工作目录也应分别评估。网络存储是否适用，要核对一致性、延迟、吞吐和工具约束，本篇不作统一禁止。Unity 的 `Faster (smaller) builds` 提供构建工作量与运行时表现的取舍，调整后仍需目标设备验证，不能当作无代价优化。[Unity 2022.3 IL2CPP 设置说明](https://docs.unity3d.com/2022.3/Documentation/Manual/IL2CPP.html#OptimizingBuildTimes)

## 五类故障与诊断

### 故障 1：疑似内存不足 {#故障-1oom链接阶段}

`Killed`、退出码或界面进度只能作为定位线索，不能单独证明 OOM，更不能确定是链接器耗尽了内存。

先对齐失败时刻与进程身份，再查系统或容器记录。在 Linux cgroup v2 中，`memory.events` 的 `oom_kill` 可以观察该组及子组进程被 OOM killer 终止的次数；只查本组时需区分 `memory.events.local`。应比较本次任务前后的变化，并结合内核记录定位，不能把历史累计值当成这次构建的原因。[Linux cgroup v2 内存事件](https://docs.kernel.org/admin-guide/cgroup-v2.html)

确认原因后，再区分单任务超限与多任务叠加，验证减少并发、调整已支持的选项或扩容是否有效。本篇不再提供“对象文件体积除以二就是峰值”的公式。

### 故障 2：磁盘空间相关错误 {#故障-2磁盘满编译中段}

根据实际写入失败的路径定位存储卷，并核对剩余容量、inode 或配额等限制。不要用“构建到 50%”确定阶段，也不要直接清理推测中的 iOS 目录。

释放空间应遵循已核对的保留策略。修复后重跑时检查实际重建步骤及产物，不预先认定所有中间结果都能复用或全部失效。

### 故障 3：卡死（无明显错误）

长时间没有日志，不足以判断 clang 死锁。先查进程是否仍存在、子进程在做什么、是否等待 I/O、锁、交互输入或外部服务，再决定是否需要堆栈或系统调用观察。

诊断工具应匹配操作系统与权限条件。只有取得复现、工具版本和已知问题的对应证据后，才把升级或代码调整作为修复；不能默认小版本升级一定解决。

### 故障 4：编译错误（IL2CPP 失败）

先找到第一条有意义的错误，区分托管编译、裁剪、IL2CPP 转译、本机编译和链接失败。SDK、原生插件或工具链不匹配，也需要在对应阶段核对。

`link.xml` 用于声明托管代码保留规则；它不是任意 C++ 编译或链接错误的通用修复。只有证据指向裁剪误删时，才围绕需要保留的类型或成员调整，并验证运行结果。[Unity 托管代码裁剪说明](https://docs.unity3d.com/2022.3/Documentation/Manual/ManagedCodeStripping.html)

### 故障 5：单纯慢（无错误）

先比较输入、缓存条件和各阶段耗时，再检查实际慢段。CPU 使用率低可能是等待，也可能是并行工作不足；内存接近限制是否出现换页，需要额外观察，不能直接等同。

旧稿所称 `Library/Bee/Stats/` 缓存命中数据入口未核实，已撤下使用步骤。以当前版本真实日志和工具输出为准；缓存失效可以列为假设，但需要重跑记录支持，不能预设为最常见根因。

## 全系列总结

本系列从流水线组织、稳定性运维与 Unity 集成三个方向讨论交付。查某个故障时，应先确定所在环节，再进入对应文章；文章中的方法仍需结合目标版本和实际记录验证。

### 写给技术负责人 {#写给-l3-面试官线读者}

评估一种方案时，关注输入、责任边界、观测结果和恢复条件。具体数字与事故故事需要来源，不能仅凭叙述细节把它们认作作者项目成果。

### 写给 L1 / L2 读者

把故障现象与原因拆开，用日志、进程、资源和产物记录逐步缩小范围。每次改动后核对它解决了哪个问题，以及有没有改变交付物。
