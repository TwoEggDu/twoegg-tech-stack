> 贯穿案例：把第 05 篇冻结的 R17 分阶段交给客户端 100，通过第 06 篇的启动回执确认采用情况；随后发布 R18 活动内容与客户端 101 的 R19。组合定义统一见[第 04 篇]({{< relref "delivery-engineering/unity-game-update-release-04-version-binding.md#release-examples" >}})。

## 1. 发布器接收什么，哪些状态仍未完成

- 接收冻结组合、文件身份、兼容条件、构建与验收回执，以及恢复候选和未验证项；发现内容发生变化时重新生成组合身份。
- 分别记录构建完成、组合验收、文件上传、发布策略生效、客户端实际采用、平台上线和内容开放。
- 在写操作前固定平台、渠道、环境和目标客户端人群；不能把测试上传或 CI 成功当成玩家已可用。

## 2. 先准备完整组合，再切换发布入口

1. 上传 R17 新增文件，核对继承的 Res 12 以及所有 Manifest 和依赖也在目标环境完整可取。
2. 发布冻结的 R17 组合记录，保留 R16 与其文件；生产人群策略暂时仍可指向 R16。
3. 在目标渠道与设备上核对 R17 的内容解析、基线、启动和恢复条件，形成发布决策依据。
4. 用新 `policyRevision` 更新人群到组合的完整映射，避免逐个 Package 切换 latest；并发发布要检查原策略修订，冲突时重新核对。
5. 读取远端实际策略，并检查客户端回执中的策略与组合身份，再决定扩大范围。

- 版本化内容文件与可变策略入口分别设计缓存规则；不在同一个内容身份下覆盖不同字节。
- 完整映射的切换不等于所有 CDN 节点或在线玩家同时生效；本次启动冻结组合，后续请求按缓存与准入规则重新选择。
- 可以对照 CCD Release/Badge 解释“快照与入口”，但业务兼容、跨 Package 准备和进程采用仍需项目实现。

## 3. 让三种发布流程使用同一个契约

| 场景 | 发布对象 | 生效前需要确认 |
|---|---|---|
| 首次 Full | 客户端 100、B100、R16 | 客户端可取得，首包与远端内容配套，首次启动可走通 |
| 已有客户端补丁与内容更新 | R17，之后的 R18 | 支持范围仍覆盖 100，完整组合已验收；R18 的活动开放条件另行满足 |
| 新客户端 Full | 客户端 101、B101、R19 | 对应渠道的新客户端可取得并能运行 R19，再决定是否停止支持 100 |

- 单类 Res、HotCode、Data 与 HotUpdate 都进入相同的组合验收和发布步骤；R17 中依赖 HotCode 8 的 Data 21 不能提前单独生效。
- 核对现有发布工具是否支持这些范围并保留完整版本映射；构建选项存在不代表公网发布工具已经支持。
- 发布 101 时可继续保留 100 的兼容内容路由；`latestAvailableClient` 更新不自动意味着提高 `minSupportedClient`。

## 4. 最小灰度闭环怎样运转

| 阶段 | 观察与决策 | 需要留下的依据 |
|---|---|---|
| 试投 | 固定平台、渠道与稳定的人群归属，少量玩家采用 R17，其余仍用 R16 | 策略修订、目标人群、兼容范围、负责人 |
| 观察 | 按客户端与组合对照下载失败、启动失败/崩溃及修复目标的业务表现 | 样本范围、观察窗口、分母与失败阶段 |
| 放量或暂停 | 达到本次预设条件再扩大；异常时暂停扩大并判断是否需要撤回 | 判断依据与决策人，不虚构通用数值门槛 |
| 恢复 | 核对旧组合与当前服务端、数据仍兼容，再调整路由；否则关闭相关功能或准备向前修复 | 恢复条件、新策略修订与客户端采用结果 |

- 发布前定义本次门槛和负责人；同一个玩家在相同策略下的分组应稳定，避免反复下载不同组合。
- R18 的资源已就绪不代表活动已开放。活动开关需要结合组合能力、服务端准备和开放人群；关闭入口不等于撤销玩家已经发生的业务状态。
- 已实现的活动参数或开关可以通过服务端/远端配置调整；这类运营配置变更单独记录，不假定每次都需要构建 Data 包。

## 5. 回退到底恢复哪一层 {#rollback-layers}

| 恢复对象 | 可以采取的动作 | 仍需满足的条件 |
|---|---|---|
| 发布入口 | 新策略重新指向保留的 R16 | R16 文件完整，当前准入与服务端仍允许它 |
| 客户端采用的内容 | 在下一次安全启动中按 R16 整体选择、校验与加载 | 不能把 R16 的 Data 与已采用的 R17 HotCode 混用 |
| 当前进程代码与对象 | 普通 HybridCLR 路径按重启恢复设计 | 远端指针回移不能撤销已经加载的程序集与业务副作用 |
| 存档、数据与服务端状态 | 按迁移兼容、补偿或向前修复方案处理 | 新字段、新英雄状态等未必能由旧代码理解 |
| 已安装客户端 101 | 为 101 提供兼容组合或后续修复包 | 降低强更要求不会自动把已安装客户端变回 100，也不能让它默认采用 R16 |

- 示例：策略修订 40 指向 R16，41 让试投人群采用 R17，42 扩大到目标人群；若允许恢复，则用修订 43 指回 R16。策略修订继续前进，内容组合可以回到旧版。
- R17→R16 的恢复必须验证旧逻辑、数据与服务端仍能协作；若 R17 是当前不可撤销的准入要求，先明确新的允许策略，不能由客户端擅自忽略它。
- R18 上线后玩家可能已获得新英雄，R19 又涉及新的基线和数据格式；不能直接套用 R17 的恢复结论。
- 旧文件清理需要同时考虑仍被客户端使用的组合、允许恢复的组合与保留周期。

## 6. 如何证明发布与恢复真的生效

- 核对输入修订、构建回执、远端内容身份、`policyRevision`、`releaseId` 与实际启动结果。
- 验证新装、旧包、冷热缓存、试投与普通人群、发布期间中断，以及渠道目标客户端不可得的情况。
- 对恢复分别记录入口已改、客户端已重新采用、业务恢复和状态处理结果；某一层完成不代替其他层。
- 将未覆盖的设备、观察窗口与恢复条件写入回执，未做实验的步骤保持待验证。
