假设你正在修改角色技能。工程里有三项工作：已经修复的伤害重复结算问题、尚未完成的蓄力技能，以及刚接入的新特效。现在 QA 只需要验证伤害修复。

你在本地测过修复，也知道改过哪些文件。但“把修改提交一下”仍然不够具体：同一个脚本可能混着两个任务，新特效可能带入额外文件，而本地运行还可能用到了没有进入仓库的配置。

真正需要回答的是：**这次交付哪些修改，其他工作留在哪里，别人怎样准确取得并核对这次内容？**

下面用这个教学场景建立共同模型，再看 Git、SVN、P4 分别从哪里进入。它不对应某次真实项目事故；文末给出验证设计，并区分已经完成的 Git 文本文件实验与尚未验证的范围。

## 同一个目录里，为什么会混着不同任务

开发目录首先服务于当前工作。为了修一个问题，你可能临时修改配置；为了验证一个接口，又提前接入了下一项功能。几项任务逐渐叠在一起，目录里的内容也就不再对应一次明确的交付。

假设现在有这样的修改：

| 文件 | 本地包含的工作 | 本次希望交付什么 |
| --- | --- | --- |
| `Damage.cs` | 修复重复结算，同时加入未完成的蓄力逻辑 | 只包含伤害修复 |
| `SkillConfig.json` | 调整蓄力技能参数 | 暂不交付 |
| `CastEffect.prefab` | 接入新特效 | 暂不交付 |

这张表暴露出两个不同的范围：**哪些文件变了，以及哪些内容属于这次任务。**

即使只选中 `Damage.cs`，也可能夹带蓄力逻辑。反过来，如果伤害修复依赖一个新增配置字段，只交脚本又可能漏掉必要内容。选文件只是表达提交范围的一种方式，还需要核对文件内部的修改与文件之间的依赖。

保存文件只改变了当前目录。版本控制进一步把文件随时间的变化记录下来，使人能够定位过去的内容、比较差异和追查修改。[Pro Git 对版本控制的介绍](https://git-scm.com/book/en/v2/Getting-Started-About-Version-Control)从这些能力展开。

任务为什么这样划分、哪些依赖必须一起交付，则需要开发者结合工程判断。工具可以展示差异，却不能仅凭“这个文件改过”就判断它属于哪个需求。

## 先认识工作区、变更集合、历史与基线

先把刚才的目录拆成四个概念：

| 概念 | 它回答什么问题 | 在伤害修复里的对应 |
| --- | --- | --- |
| 工作区 | 我现在实际编辑和使用什么内容？ | 同时包含修复、蓄力逻辑和新特效的目录 |
| 变更集合 | 这次准备一起交付哪些修改？ | 伤害修复及其必要配套修改 |
| 历史 | 已记录过哪些版本，它们有什么关系？ | 可以追查修复前后内容的版本记录 |
| 基线 | 这次比较和讨论从哪份内容开始？ | 双方约定的修复前版本 |

这里的“工作区”是通用称呼，各工具的正式术语与管理方式会有差异。“变更集合”也只是分析概念，不假定工具里一定有同名对象。

**基线让“改了什么”有明确参照。** 例如，将修复前内容记为 V0，只加入伤害修复后得到候选 V1。V1 相对 V0 的差异，才是这次准备交付的变化。V0、V1 是示意名称，实际交接需要能准确定位的版本标识。

如果另一人从更早的版本开始比较，看到的还会有其他修改；如果直接把你的整个工作区当成 V1，又会把蓄力逻辑混进来。比较对象一变，同一句“这次改了这些”就可能表达不同的事情。

历史则让这些参照能够被重新定位。它可能包含多条并行关系，不必是一条从旧到新的直线；“最新”还需要说明是哪条工作线。一个可定位的版本也未必经过测试，版本身份与可用性需要分别判断。

在同一基线下，可以把例子画成这样的关系：

```text
基线 V0
  ├─ 开发工作区 A：伤害修复 + 蓄力逻辑 + 新特效
  │      ├─ 选择伤害修复及必要依赖 → 候选内容
  │      └─ 蓄力逻辑与新特效留在本地继续工作
  │
  └─ 候选被记录并共享 → 可定位的版本 V1
                              └─ 工作区 B 取得 V1 并核对
```

这张图表达内容关系，不表示所有工具都必须提供一个独立的“候选区”。图中也没有要求从 A 的整个目录复制出 V1：当同一个文件混有多项任务时，还需要借助工具和隔离环境把候选内容组织清楚，具体办法留到[任务提交篇]({{< relref "delivery-engineering/version-management-05-task-submission.md" >}})。

## 修改怎样被选择、记录、共享和接受

顺着这张图，可以把交接拆成四个动作。它们各自回答不同的问题，具体工具可能把其中几个合在一次操作里。

**选择修改，确定这次的内容范围。** 先相对 V0 看差异，确认伤害修复需要什么，再排除蓄力逻辑。若两项工作已经相互依赖，便需要调整实现或扩大本次范围，不能只靠取消勾选一个文件来解决。

选择之后要检查的是候选内容。当前开发目录仍有其他修改，在 A 中运行通过，可能依赖这些额外内容；因此它不足以证明候选 V1 可以独立工作。

**记录版本，为内容留下可追查的身份。** 记录应当让人知道内容在哪里、发生了哪些变化，并能关联修改说明。历史中出现“修复重复结算”的描述，仍要与实际内容核对：说明表达意图，差异展示做过的修改。

一项任务可以包含多次记录。是否合并整理，需要结合工具与团队流程决定；任务边界不必机械等于一次提交。

**共享内容，让协作者能够取得它。** 只保存在本机的记录，别人可能无法访问；内容进入共享仓库后，对方的已有目录也未必随之变化。交接因此需要同时说明仓库或服务位置、工作线及版本标识，以及需要取得的路径范围。

只说“拉最新的”容易使对象漂移：QA 取内容之前，别人可能又提交了新修改。若需要验证某次修复，就应固定本次候选，再核对实际取得的内容。

**确认接受，决定这份修改能否进入团队约定的工作线。** 这一步可能涉及审查、自动检查、测试和合入权限。它们回答修改是否满足约定条件；保存历史和成功上传本身不会替团队完成这些判断。

这些动作也不必永远按同一顺序发生。有的流程先将修改共享给审查者，批准后再正式集成；有的流程先提交到开发线，再组织验证。无论采用哪一种，都需要说明检查和接受针对的是哪一份内容。后续若再修改候选，原有结论是否仍适用，也要重新核对。

## 将共同问题映射到三种工具

理解这些动作后，再看工具名会更容易找到重点：

| 工具 | 先认识哪些对象 | 本篇最需要保留的区别 |
| --- | --- | --- |
| Git | 工作区、暂存区、本地提交与远端 | 本地记录版本和向远端共享修改是可以分开的动作 |
| SVN | 工作副本、仓库路径与修订 | 提交将修改记录到仓库，其他人的已有工作副本仍需取得相应内容 |
| P4 | Depot、Workspace、待提交 Changelist 与 Shelf | 可以组织待提交修改，并在正式提交前搁置内容供交接 |

Git 官方模型区分工作区、暂存区和本地仓库；暂存内容用于组织下一次提交，本地提交之后还可以继续安排共享。[Git 的对象与状态说明](https://git-scm.com/book/en/v2/Getting-Started-What-is-Git%3F)

SVN 的工作副本与仓库是不同对象。其文档明确区分提交和更新：你提交了修改，另一位协作者的已有工作副本仍保留原内容，直到对方请求更新。[SVN Book 1.7：工作副本交互](https://svnbook.red-bean.com/en/1.7/svn.basic.in-action.html)

P4 用 Changelist 组织修改；搁置可以在正式提交前将工作保存到共享服务器，支持他人审查或交接。因而，“服务器上已有这份内容”和“它已成为正式提交”也需要分开理解。[P4 2026.1：Changelist 与搁置](https://help.perforce.com/helix-core/server-apps/cmdref/current/Content/P4Guide/basic-tasks.recurring-other.changelist.html)

这里引用 SVN 1.7 的基础模型和 P4 2026.1 的说明，不据此推定其他版本的全部细节；各工具篇会继续核对采用版本。暂存区、工作副本和 Changelist 也不应直接画等号，它们承担的职责与保存的状态需要分别解释。

## 拟验证：换一个干净目录取得指定内容

可以用两个独立工作区检验前面的模型。下面是完整验证设计，先用普通文本表示脚本与配置，版本控制机制核对清楚后，再扩展到引擎资产。

1. **准备基线 V0。** 在 A、B 中取得相同内容，记录工具版本、取得范围和版本身份，确认两边没有额外本地修改。
2. **只在 A 中开展多项工作。** 在同一文本文件里分别加入伤害修复和未完成逻辑，再增加无关配置修改。保留操作前后的内容作为对照。
3. **组织修复候选并记录、共享。** 只纳入伤害修复及必要依赖，记下实际生成的版本标识，检查 A 中尚未交付的修改是否保留。
4. **让 B 明确取得该版本。** 不从 A 手工补文件，也不依赖 A 的目录残留。将 B 的内容与候选逐项比较，检查修复存在、未完成逻辑未混入、必要文件没有遗漏。

其中的一个 Git 文本文件子集已在[第 02 篇]({{< relref "delivery-engineering/version-management-02-git.md" >}})实测：先暂存伤害修改，再继续编辑同一文件中的蓄力开关，接收方取得指定提交后只包含已提交内容，开发方仍保留后续编辑。23 项检查通过；这没有覆盖已经混合的任务拆分、额外配置依赖、故障恢复或引擎验证，完整设计仍待补齐。

如果 B 缺少某个配置，A 却可以运行，就沿这个差异追查：候选漏了依赖，还是 A 使用了未记录的本地输入？这种对照比反复说“我这边正常”更能缩小问题范围。

最后把检查结果分三层记录：**文件内容是否与候选一致，任务所需依赖是否齐全，修复行为是否正确。** 文本比较或文件散列可以帮助核对第一层，依赖检查负责第二层，构建和功能测试继续验证第三层。后续若要固定工具链与完整构建输入，再进入[构建基线篇]({{< relref "delivery-engineering/version-management-09-build-baseline.md" >}})。
