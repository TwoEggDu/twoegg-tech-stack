## 这篇解决什么问题

前五篇讲了资源线和配置线的生产管线。但有一个问题在单端开发时不存在，多端交付时会突然暴露：**同一份源资产在不同平台上需要不同的运行时格式和质量参数。**

这一篇讲清楚差异在哪、谁来管、管理策略怎么设计。

> 版本与证据范围：Unity 映射参考 6000.0 文档。下文是配置与交付方法，没有实际三端产物、小游戏能力测试或设备收益；平台配额需按选定宿主、SDK 与当前规则核对，配置候选不作为已验证标准。

## 为什么这个问题重要

多端资源差异管理出问题的典型场景：

- 产物使用了目标设备不支持的纹理格式，发生了非预期回退或加载问题
- 微信小游戏的主包、分包和按需资源边界没有对齐目标环境的交付要求
- 设备分档使用了超出当前预算的资源，出现内存压力
- 三端资源分开维护，更新时漏掉了某一端，导致内容不一致

这些是待检查的情境，不是本项目事故记录；它们都需要沿**生产规则、导入配置、构建产物与运行用法**定位，不能只在构建末尾临时调参数。

## 本质是什么

多端资源差异管理的本质是：**一份源资产 → 多份运行时产物**，由导入设置和构建配置决定产物形态。

```
源资产（一份）
    ↓
导入设置 × 平台 × 质量档位
    ↓
运行时产物（多份）
```

管理的对象不是"三套不同的资源"，而是"一套源资产 + 一组平台差异规则"。

## 三类核心差异

### 纹理差异

纹理是多端差异最大的资源类型：

| 差异维度 | iOS | Android | 微信小游戏 |
|---------|-----|---------|-----------|
| 格式候选 | 按目标设备与数据类型核对 ASTC 等支持 | 按设备/API 能力选择 ASTC、ETC2 等候选 | 按宿主/SDK 暴露的格式能力确认，不能仅凭 WebGL 2.0 判断 ASTC |
| 格式不支持时 | 选择受支持格式或显式交付回退 | 明确受支持格式与资源路由 | 准备可用格式或受控回退，并检查占用；降低尺寸不等于获得格式支持 |
| 最大分辨率 | 由镜头、画质和占用预算确定 | 结合镜头与设备分档比较 | 按实际宿主与设备预算比较，不预设统一上限 |
| Alpha 与通道 | 先确认使用语义与目标格式 | 区分 RGB、二值/完整 Alpha 等格式需求 | 按实际可用格式比较透明边缘与参数误差 |
| 法线贴图质量 | 比较法线和高光误差 | 比较候选格式及其设置 | 在目标后端与设备上比较，不预设固定块大小 |

WebGL ASTC 有独立的[扩展与 profile 查询规范](https://registry.khronos.org/webgl/extensions/WEBGL_compressed_texture_astc/)。微信宿主是否暴露相应能力还需实际确认；改用 ASTC 8x8 也不能解决不支持 ASTC 的问题。格式、Alpha 与存储细节见[带宽优化]({{< relref "performance/gpu-opt-02-bandwidth.md" >}})，本表不再复制一套固定规格。

管理策略：

**优先复用源贴图**。可通过导入设置表达的差异，用 TextureImporter 平台覆盖管理；需要不同内容时仍可维护显式变体。平台覆盖不自动建立多格式资源包、能力检测与运行时地址路由。

**导入设置模板化**。按贴图用途（漫反射 / 法线 / UI / 特效 / 光照贴图）定义导入模板，模板中包含每个平台的压缩格式和最大尺寸。新贴图导入时自动匹配模板。

**设备分档叠加**。平台能力与同平台内的质量档需要分别记录。若准备不同尺寸或内容版本，应明确实际产物、资源映射和加载选择；Quality Settings 不会自动替项目产出并交付多套资产。候选配置见[资产规格]({{< relref "performance/device-tier-asset-spec-texture-and-package.md" >}})。

### 模型与动画差异

模型的多端差异相对较小，但在极端情况下仍然需要管理：

| 差异维度 | 高端设备 | 中端设备 | 低端设备 / 微信小游戏 |
|---------|---------|---------|-------------------|
| 几何候选 | 依据近景等目标保留必要细节 | 比较可接受的简化版本 | 比较更简化版本或替代表现，不预设某一级一定适合 |
| 骨骼与层级 | 保留必要蒙皮、挂点与驱动关系 | 确认消费者后再比较精简 | 同样需要功能对照，不按档位直接删骨骼 |
| 动画精度 | 定义画面与玩法接受条件 | 比较误差与运行表示 | 按使用条件比较，不只按档位提高压缩 |

管理策略：

**LOD 系统**。可用 LOD 管理不同细节版本的选择，仍需维护相应网格、引用、配置与回归。Unity LODGroup 的阈值以相对屏幕高度为基础，不能统一理解成固定世界距离；级数与切换需要结合对象和镜头比较，见[几何与 LOD 成本]({{< relref "performance/mobile-geometry-cost-vertices-screen-triangles-lod.md" >}})。

**动画压缩参数化**。导入设置可控制压缩策略与允许误差，但它们不是固定压缩率。按实际片段、Rig 类型和玩法检查结果，再决定是否需要不同候选；本篇没有已接受的分档压缩结果。

### 音频差异

音频的多端差异主要体现在编码格式和质量上：

| 差异维度 | iOS | Android | 微信小游戏 |
|---------|-----|---------|-----------|
| 编码候选 | 以目标导入器/后端支持为准 | 以目标导入器/后端支持为准 | 以宿主/SDK 实际支持为准 |
| 采样率 | 44100Hz | 44100Hz | 22050Hz（节省体积） |
| 声道 | 立体声 | 立体声 | 单声道（节省体积） |
| 压缩质量 | 高 | 中-高 | 中-低 |

表中的采样率、声道和质量仅是待比较的参数示例，不是各平台默认值、最优值或强制降级规则。应按声音用途、频率内容、空间/立体声需求和加载策略比较，并确认目标支持；本篇没有听感与并发播放结果。字段含义参考 [Audio Clip Import Settings](https://docs.unity3d.com/6000.0/Documentation/Manual/class-AudioClip.html)。

## 差异管理的三种策略

### 策略一：导入时分平台配置

最常见的方式。在引擎的资源导入设置中，按平台配置不同的参数。

**优点**：一份源资产，构建时自动产出不同平台的运行时资源。管理简单，美术无感知。

**缺点**：所有差异都必须能通过导入参数表达。如果某个平台需要完全不同的资源（比如微信小游戏需要特制的低面数模型），导入参数无法覆盖。

**适用场景**：纹理压缩格式、分辨率限制、音频编码格式——这些差异可以通过参数化控制。

### 策略二：资源变体

为同一个逻辑资源准备多个物理文件，构建时根据目标平台选择对应的变体。

```
Assets/Characters/Hero/
    hero_body_d.tga         (通用源贴图)
    hero_body_d_mini.tga    (微信小游戏专用低分辨率版本)
```

**优点**：可以处理导入参数无法覆盖的差异（不同平台使用完全不同的资源文件）。

**缺点**：增加了资源管理的复杂度。美术需要维护多份资源，容易遗漏更新。

**适用场景**：微信小游戏需要特制资源、PC 端需要高清贴图而移动端使用标准贴图。

### 策略三：运行时动态加载

不在构建时区分，而是在运行时根据设备能力动态选择资源。

```
// 伪代码
if (DeviceTier == High)
    LoadTexture("hero_2k");
else if (DeviceTier == Medium)
    LoadTexture("hero_1k");
else
    LoadTexture("hero_512");
```

**优点**：一个包适配所有设备。可以通过远程配置动态调整。

**缺点**：所有档位的资源都要打进包里（除非配合按需下载），包体增大。运行时加载逻辑更复杂。

**适用场景**：设备分档差异（同一平台内的高中低端设备），配合 Addressables 或按需下载使用。

### 实际项目中的组合

大多数项目会组合使用三种策略：

- **平台差异**（iOS vs Android vs 微信小游戏）→ 策略一（导入时分平台配置）
- **极端差异**（微信小游戏专用资源）→ 策略二（资源变体）
- **设备分档差异**（同平台高中低端）→ 策略三（运行时动态加载）

关键是：**差异规则在生产段定义，不在构建段临时处理。**

## 微信小游戏的特殊性

微信小游戏的资源差异不只是"格式不同"，而是整体资源策略都需要重新设计：

**主包与分包约束**。先按选定宿主、SDK、类目与当前规则核对各包限制，再决定安装/首进与追加下载边界；本篇不保留未经本轮核对的统一配额数字，也不假定所有内容都能采用同一远程交付方式。

**宿主与设备预算**。实际内存上限、驻留与峰值需要在目标环境检查，不能把所有宿主与设备合成一个固定低档。源文件或包体变小，也不保证运行内存按同一比例下降。

**图形后端约束**。核对目标后端、扩展和 Shader 支持，再比较功能与成本；不能只凭 WebGL 版本或宿主名称推导所有图形能力。

这意味着微信小游戏不能简单地"用同一套资源换个格式"。它可能需要：
- 专门的贴图分辨率上限（比原生端低一档）
- 专门的模型面数预算
- 专门的 Shader 变体（去掉 WebGL 不支持的特性）
- 专门的加载策略（按场景按需下载，不预加载）

在本专栏的 V06（包体管理与分发）和 V07（多端构建）中会详细展开微信小游戏的工程化处理。

## 小结与检查清单

- [ ] 三端资源差异是否通过导入设置统一管理（而非手动维护三套资源）
- [ ] 导入设置模板是否按资源用途分类定义
- [ ] 微信小游戏是否有独立的资源预算（分辨率、面数、内存）
- [ ] 设备分档差异是否与平台差异分开管理
- [ ] 变体资源（如有）是否有自动化的同步检查（更新源资产时变体是否同步更新）
- [ ] 三端的资源质量是否在 CI 中分别验证
