## 这篇解决什么问题

版本号看起来是最简单的工程决策之一——不就是 1.0.0 改成 1.1.0 吗？

但在多端交付场景下，团队说的“版本”可能分别指用户看到的发行版本、某次构建、安装包、协议或一组资源。只有先分清这些对象，才能讨论更新选择、兼容验收和问题追溯。

> 范围与证据：SemVer 按 2.0.0 规范，Apple／Android 字段按 2026-10-31 查阅的官方资料核对。下文编号、清单与公式为教学设计和算例，没有上传商店、安装升级、真实构建或双端兼容实测。平台接受规则仍需按目标应用、发布轨道与提交时条件核验。

工作区、候选和提交的关系复用[版本控制模型]({{< relref "delivery-engineering/version-management-01-model.md" >}})；兼容矩阵、候选清单与实际消费的验收复用[跨端版本协调]({{< relref "delivery-engineering/delivery-server-versioning-01-coordination.md" >}})。本篇解释怎样命名、关联与判断这些身份，不重复展开版本控制操作或完整发布管线。

## 为什么这个问题重要

下面是需要防止的教学情景，不是同一次项目事故：

- 发布器用展示版本代替内容身份，两端显示同号却各自拿到不同资源。
- 服务端只比较版本号大小，没有确认协议、数据格式与能力，误把不兼容组合放行。
- 同一个 1.2.0 生成了多次安装包，报告却只有展示版本，无法找到对应产物和符号材料。
- 把原生安装包的编号规则直接用于小游戏，忽略宿主发布状态和游戏实际加载的内容。

## 本质是什么

先把标识符理解为**对某个对象的引用**。号码可以表达约定，也可以帮助检索记录，但不能单独证明内容相同、来源正确或组合兼容。

| 对象 | 示例与职责 | 还需要关联什么 |
| --- | --- | --- |
| 展示／发行版本 | `1.2.3`，帮助用户与团队辨认一次发行 | 适用平台、应用与渠道；同号不保证同字节 |
| 源码修订 | 仓库位置与明确 commit／修订 | 资源、配置、依赖及工具链；提交号不是完整构建输入 |
| 内部构建身份 | 项目／流水线／运行号／尝试号／目标，定位一次构建执行 | 实际输入、参数、日志及各输出角色 |
| 产物身份 | 安装包、服务端制品、符号文件的记录与校验值 | 输出之间的配套关系、存放位置与构建来源 |
| 协议与内容组合 | 协议／数据格式标识，以及确切资源和配置集合 | 支持条件、兼容检查与实际加载证据 |
| 发布策略 | 选择何时向哪些用户提供哪个已验收组合 | 当前环境、准入与恢复条件，不等同于内容本身 |

一次构建可以输出多个平台或多个文件，所以运行号不能天然唯一标识某一个安装包。构建号的唯一性必须限定命名空间；重试、并行任务、不同 CI 实例也要区分。产物哈希用于核对内容，不能独立证明它由哪些输入生成，也不能证明业务兼容。

可以将这些对象连成一份小的交接记录：发行版本 → 构建执行与实际输入 → 安装包／符号材料 → 允许采用的内容组合与兼容记录。QA 和运行报告再回报实际使用的身份。清单应来自实际输入与产物，不能只给所有文件贴同一标签。

## 版本语义与构建身份 {#版本号的四段结构}

`1.2.3 (456)` 可以作为团队的展示约定：前三段表达发行语义，括号内指向内部构建记录。它不是所有平台要求的四段格式，也不是 SemVer 的标准拼写。

```
展示约定：1.2.3 (456)
SemVer 示例：1.2.3+build.456
```

若采用 [SemVer 2.0.0](https://semver.org/spec/v2.0.0.html)，先声明所管理的公共 API，再按变化赋予 Major／Minor／Patch 含义。预发布与构建元数据另有规则；`+build.456` 的构建元数据不参与 SemVer 优先级比较，不能用它自动推导平台更新顺序。

### Major：不兼容的 API 变更 {#major大版本}

针对已声明 API 的不兼容变更提升 Major。赛季变化、资源更新与 API 不兼容不是同一个概念；若项目采用其他发行语义，应明确它不是在逐项遵循 SemVer。

是否要求玩家更新，要看旧端能否通过适配、路由或能力降级继续工作，以及目标平台允许的交付方式。Major 标签本身既不执行强更，也不证明一定需要重新下载商店安装包。

### Minor：功能版本

按 SemVer，Minor 表达向后兼容的 API 功能新增。它不承诺所有旧客户端都能消费新配置、资源或业务规则；还需检查默认值、未知字段、可选能力和实际操作。

服务端保留哪些历史版本由兼容成本与业务条件决定，不存在统一的“必须支持 Minor 和 Minor−1”规则；也不能由 Minor 推导一定走商店更新或一定不强更。

### Patch：修复版本

按 SemVer，Patch 表达向后兼容的 API 缺陷修复，不等于“静默热更”。修复若涉及已安装客户端不具备的原生能力、接口或数据条件，仍需评估客户端升级；仅更新内容也要验证其与消费程序配套。

选择整包、内容更新或其他受支持路径，应先回答“改变了什么、谁有能力消费、怎样分发并确认采用”。版本标签记录意图，兼容矩阵和验证记录负责说明接受条件。

### Build：构建号

内部构建身份定位执行记录，平台构建版本满足分发系统的要求，两者通过映射关联，不要求使用同一个裸整数。失败与重试也保留执行身份；是否分配平台编号、在什么阶段分配，由项目的分配规则决定。

自动化有助于减少手工遗漏，但不能只写“CI 自动递增”就假设并发、分支和重试都不会重号。记录分配范围、唯一性与发布顺序；已发布身份不应被换成不同内容。崩溃调查还要关联实际二进制与配套符号，不能只靠版本文字选择文件。

## 三端版本号：统一还是独立

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **统一发行语义** | 各端共享发行名称，各自登记平台字段与产物 | 便于共同沟通 | 端内独立修复仍需明确映射 |
| **独立编号** | 各端按发布节奏编号，映射到受支持组合 | 允许独立交付 | 要维护跨端兼容与追溯关系 |
| **发行语义 + 目标维度** | 内部记录另列平台、渠道、环境与内容身份 | 避免把所有信息塞进一串号码 | 需要生成并核对记录，不能只维护命名约定 |

先根据独立发布需求和消费者约束选择规则。相同版本号不证明兼容，不同版本号也不自动证明不兼容；协议、数据格式、资源依赖与功能条件仍需单独表达。详细取舍和候选验收沿用[跨端版本协调]({{< relref "delivery-engineering/delivery-server-versioning-01-coordination.md" >}})，不预设所有项目必须三端 Major.Minor 相同。

内部记录可将平台作为独立字段。若写成 `1.2.3-ios`，在 SemVer 中连字符后属于预发布标识，不是平台字段；完整字符串也未必能写入平台版本键，不能直接用于通用大小比较。

## 版本号与平台商店的对应

平台字段和内部标识之间需要显式映射。以下只列本次核对的 iOS／Android 字段，不把同一个字符串直接填到所有平台：

| 平台 | 展示版本 | 内部版本 | 格式约束 |
|------|---------|---------|---------|
| iOS | `CFBundleShortVersionString` | `CFBundleVersion` | 前者为三段点分整数；后者按官方定义为一至三段点分整数，不是任意字符串 |
| Android | `versionName` | `versionCode` | 前者为展示字符串；后者为正整数，升级／分发顺序需按其规则管理 |

Apple 的 [ShortVersionString](https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundleshortversionstring)与 [BundleVersion](https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundleversion)文档区分发行与构建版本，均限制为数字和点；不要直接写入括号、`-ios` 或 `+build.456`。字段格式通过不代表上传或上架已接受，实际发布还应检查对应提交规则与回执。

按 [Android 官方版本说明](https://developer.android.com/studio/publish/versioning)，系统使用 `versionCode` 防止降级，但不会因此替游戏验证服务端与内容兼容。Google Play 允许的最大值为 `2100000000`，已用于先前版本的编号不能重复上传；多 APK 的范围分配有专门条件，不能压成跨应用、跨轨道的一个简单全局顺序。

微信等小游戏的宿主上传、审核发布与运行内容也应区分。本篇不预填通用的 `version` 字段或“无格式限制”结论；具体字段与接受条件按所用宿主和上传接口核对，不照搬原生端编号。游戏自己的内容组合记录仍应明确所选资源与配置。

### Android 编号公式：先证明范围，再谈编码

原来的十进制打包式可以作为教学算例，但不能在没有字段范围时直接推荐：

```
C = M * 10000000 + m * 100000 + p * 100 + b
1.2.3 (b=1) → 10200301
1.2.3 (b=101) → 10200401
1.2.4 (b=1)   → 10200401  // 不限制字段范围就会碰撞
```

例如，**仅为这套教学编码**规定 `0≤M≤99`、`0≤m≤99`、`0≤p≤999`、`0≤b≤99`，并排除全零：各字段不会侵入相邻字段，最大编码为 `999999999`，低于上述 Play 上限。可用整除与取余反解，再与原元组核对；`b=100`、负数与超范围输入必须拒绝，不能截断、取模或靠溢出继续分配。

无碰撞只证明限定范围内的编码关系，不保证实际发布顺序。分支、旧版本修复、预发布到正式版及重试都可能使下一次语义元组不大于上次已发布元组。还要核对候选编号是否已使用、是否满足目标发布路径的顺序要求；分配需避免并发重号，并在发布回执中保留对应身份。

若不需要从编号反解语义版本，可采用独立分配的单调平台序号，并保存到发行版本、内部构建与产物的映射。这也是项目方案，需要处理分配范围、并发、失败与重试；它不是 Android 强制采用的算法，也不能只看单个 CI 任务的计数。

最小核对包括：正常元组的往返、最大边界、全零／负数／越界拒绝、上述碰撞反例，以及“编码合法但低于既有发布编号”的反例。算术检查与目标商店接受、安装升级、运行兼容分别验收。

## 常见错误做法

**只有编号，没有生成与核对规则。** 手工填写和自动生成都可能出错。为发行、平台与构建身份分别定义来源、分配范围和检查，再读取实际包内字段，与构建回执对照。

**一个展示版本指向多份产物，却没有映射。** 同号重建、不同平台与不同输出需要可追溯的构建与产物记录。不能用“都是 1.2.3”选择安装包或符号材料。

**只改文件名，没固定内容身份。** `update.zip` 这个名字本身不决定正确与否，关键在于清单能否定位确切内容、核对文件并记录实际采用组合。反过来，文件名带版本号也不能证明没有被原地覆盖。

**把编号检查当作兼容验收。** 平台接受上传、客户端安装成功、协议握手成功与目标玩法正确是不同结论。静态定义与运行验收的分工复用已有跨端协调文章，不靠多加一段版本号免除验证。

## 小结与检查清单

- [ ] 每个标识对应的对象、命名空间、生成者和消费者是否明确
- [ ] 采用 SemVer 时是否声明 API，并把兼容意图与更新方式分开
- [ ] 展示版本、平台编号、源码修订、构建执行和产物是否可以关联
- [ ] 编号是否检查范围、碰撞、历史使用与目标发布顺序
- [ ] 兼容矩阵和本次实际采用组合是否分别记录并验收
- [ ] 接收者能否据实际安装／加载身份找到产物、来源和符号材料
