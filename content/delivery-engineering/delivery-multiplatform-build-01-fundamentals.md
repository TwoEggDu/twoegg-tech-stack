## 这篇解决什么问题

构建系统连接内容、资源、配置、代码与下游验证和发布。若实际输入已经漂移，团队即使沿用同一个版本号，也不能直接沿用上次的验收结论。

但很多团队对构建系统的理解停留在"点 Build 按钮"。这一篇用四段模型把构建系统拆开，让每一段的职责和失败模式都可管理。

> 范围与证据：可复现性的定义参考 Reproducible Builds；Unity 例子按 2022.3 LTS 手册，Android 产物形态按官方 App Bundle 文档核对。本文没有执行 Unity／Unreal 工程构建、签名、商店上传或设备验收，后面的对照是待执行设计，不是作者项目测试结果。

标识符与映射复用[版本号设计]({{< relref "delivery-engineering/delivery-version-management-01-versioning.md" >}})；脚本、环境、缓存与归档操作复用[构建自动化]({{< relref "delivery-engineering/delivery-cicd-pipeline-03-build-automation.md" >}})。本篇负责输入边界与验证结论，不以邻篇已有正文代替目标版本的工具核对。

## 本质是什么

任何构建系统都可以拆成四段：

```
输入（Input）→ 变换（Transform）→ 产物（Output）→ 验证（Verify）
```

### 输入段：构建的原料

构建的完整输入，是**所声明构建过程实际依赖的内容、工具、参数与环境条件**。不能只列顶层仓库，然后让生成器从某个“最新目录”或本机残留中补材料。

| 输入 | 最少需要固定与记录什么 | 仍需核对什么 |
| --- | --- | --- |
| 代码、脚本及构建配置 | 仓库、明确修订、取得范围、工作区额外修改 | 构建真正读取的文件是否来自该集合 |
| 资源与导入设置 | 源文件、身份／导入元数据、外部对象及依赖 | 路径存在不等于内容正确，指针也不等于实际资源已取得 |
| 配置与生成代码 | 源输入、导出器／模板版本、参数、生成集合 | 预生成物与现场生成物选择明确，不能混用旧代码和新数据 |
| 引擎与包依赖 | 引擎补丁版本、所需模块、包声明与解析结果、实际包内容 | 本地包、外部下载和可变引用是否固定，所需内容能否取得 |
| 平台工具链 | 编译器、SDK／构建工具、插件与目标架构 | 声明版本与实际调用路径、工具身份是否一致 |
| 构建参数 | 平台、配置、后端、裁剪／宏定义、目标内容与版本分配结果 | CI 默认值、隐式设置与本地参数是否参与结果 |
| 相关环境条件 | 实际影响输出的 OS、路径、语言／时区、环境变量等 | 哪些被固定，哪些已证明不影响指定产物，哪些尚未确认 |
| 签名与外部服务 | 签名身份、受控材料引用、远程输入的确切身份与取得方式 | 授权与可取得性另验；清单记录引用，不复制密钥秘密值 |

**输入段先做到身份明确、实际可取得、消费可核对。**一份版本清单只描述输入，不会自动保全外部对象、补齐访问条件或证明工具已经使用它。记录缺失与未固定项，比拿一个总版本号掩盖未知更有用。

Unity 2022.3 的 [包锁文件](https://docs.unity3d.com/2022.3/Documentation/Manual/upm-conflicts-auto.html)保存依赖解析结果，用于稳定后续解析；这不是整套构建环境快照，也不自动归档本地包或外部文件。其他包管理器按各自机制核对，不把一个 lock 文件当成全部输入。

[Reproducible Builds 的环境记录说明](https://reproducible-builds.org/docs/recording/)要求定义或记录相关环境信息；具体记录形式随生态而异。本篇建议让清单关联实际取得与消费记录，不规定一个通用 JSON 就能覆盖所有引擎。完整输入的工具取得方法仍由版本管理专题维护。

输入段的常见失败模式：
- 构建环境漂移——CI Agent 升级了 OS 或 SDK 版本，构建行为改变
- 依赖版本不锁定——构建时拉取了最新版 SDK，和上次不同
- 构建参数遗漏——漏传了某个关键参数，产物和预期不同

### 变换段：从原料到产物

变换段执行实际的编译、打包、签名等操作。对游戏项目来说，变换通常包括：

```
脚本编译／代码生成（按引擎、后端与目标）
    ↓
资源导入（源文件 → 引擎格式）
    ↓
资源打包（引擎格式 → AssetBundle / 资源包）
    ↓
平台构建（代码 + 资源 → 平台产物）
    ↓
签名（产物 + 证书 → 签名产物）
    ↓
归档（签名产物 + 元信息 → 归档包）
```

**变换段的工程要求：可追溯。**每一步的输入和输出都应该被记录，构建失败时能定位到是哪一步出了问题。

上图仅示意职责，不规定所有引擎都按该顺序串行执行，也不表示所有 C# 后端都先转成原生代码。实际步骤可并行、增量复用或插入后处理；生成工具与回调同样有输入和依赖，不能因为不在主仓就从记录中消失。

变换段的常见失败模式：
- 编译错误——某个 asmdef 引用了不存在的类型
- 资源导入失败——某个资源的导入设置和引擎版本不兼容
- 打包范围或依赖错误——约定需要的内容未进入产物，或运行时无法按预期取得依赖
- 签名失败——证书过期、Provisioning Profile 不匹配

### 产物段：构建的输出

构建的最终产物因平台不同：

| 平台 | 产物形态 | 主要组成 |
|------|---------|---------|
| iOS（Unity 路径） | Xcode 工程，再经平台工具构建／分发 | 工程导出与可安装／分发产物分别确认 |
| Android | Gradle 构建输出 APK 或 AAB 等 | AAB 是发布格式，不能直接等同于设备安装的 APK 集合 |
| Web／小游戏适配 | Web 构建输出或经宿主适配的代码与资源包 | 具体引擎和宿主条件另查，WebGL 目录不自动等于宿主可接受包 |

按 [Unity 2022.3 iOS 构建说明](https://docs.unity3d.com/2022.3/Documentation/Manual/iphone-BuildProcess.html)，生成 Xcode 工程与随后构建应用是不同步骤，后者需对应的 Xcode／macOS 环境。按 [Android App Bundle 说明](https://developer.android.com/guide/app-bundle)，Google Play 可由 AAB 生成并签署面向设备的 APK；应区分上传产物与实际分发产物。Unity 的 [WebGL 构建输出](https://docs.unity3d.com/2022.3/Documentation/Manual/webgl-building.html)也不能据此推定微信或其他宿主适配已完成。

**产物段的工程要求：可归档、可追溯。**

每次构建的产物应该：
- 关联输入清单、构建执行与目标，分别标识安装包、资源、符号等输出角色及校验依据。
- 保存实际使用的工具、参数、日志和检查结果；失败、未执行与例外也有记录。
- 按发布支持、恢复需求和存储条件约定归档范围与保留时间，核对材料可取得；没有统一的 N 个版本或固定月数适用于全部项目。

构建输入、签名前输出、签名后包、外层归档与实际安装内容是不同的比较对象。运行日志和带时间的回执可以单独保存；它们不必都被纳入字节可复现的主产物集合。归档成功也不证明能重建，重建成功更不能替代保存当时实际发布的产物。

### 验证段：产物是否合格

构建成功不等于产物正确。验证可分阶段自动执行，也可包含需要设备或人员接受的项目；检查必须指向确切候选。下面是验收设计方向，不是已部署门禁：

| 检查项 | 方法 | 接受条件怎样确定 |
|--------|------|---------|
| 输入与产物身份 | 清单、实际文件与构建回执对照 | 缺失或错配如何拒绝，谁负责补齐 |
| 包体与资源完整性 | 预算、关键内容与依赖检查 | 阈值来自目标与基线，不预填通用“超 20%” |
| 编译与签名 | 工具结果及对应平台校验 | 区分错误、警告、未检查及例外，不只看进程返回成功 |
| 启动与关键功能 | 在指定环境运行并验证目标操作 | 明确设备、步骤和预期；模拟器结果不覆盖所有真机条件 |
| 指定产物比较 | 固定集合与比较边界后核对字节 | 另说明它是否属于字节可复现目标，不代替功能验收 |

验证段是构建系统的"质量门"——V01 讲的交付飞轮中的第一道门就在这里。

## 构建的可重复性

为了避免“可重复”一词混用，本篇分开报告以下结论：

| 结论 | 至少需要什么证据 | 不能自动推导什么 |
| --- | --- | --- |
| 版本可定位 | 仓库与输入记录能指向明确对象 | 外部资源仍可下载，或本地残留已排除 |
| 输入可取得 | 接收环境按记录取得所需内容与工具，缺项可见 | 构建一定成功或结果正确 |
| 构建可重跑 | 在声明环境按说明重新执行并成功产生约定输出，另记失败条件 | 产物一定与原包逐字节一致 |
| 功能验收通过 | 对指定候选、环境与操作完成实际验证 | 所有设备正确，或二进制字节相同 |
| 指定产物字节可复现 | 固定源码、相关环境和构建指令，重建得到声明产物集合的逐字节一致副本 | 整个目录、日志和签名包都已纳入承诺，或功能已免测 |

最后一项沿用 [Reproducible Builds 定义](https://reproducible-builds.org/docs/definition/)。因此，仅有同一个 commit 和部分参数不够：还需明确相关输入、环境、指令和要复现的产物集合。一次同机成功重跑，也不证明任意机器或所有后续构建均满足条件。

破坏可重复性的常见因素：

| 因素 | 表现 | 调查与处理边界 |
|------|------|------|
| 时间与归档元数据 | 包内容相同但容器或附加信息不同 | 查明进入哪些字节；按目标固定、移出比较集合或用声明方法处理 |
| 路径与环境差异 | 不同工作副本或 Agent 的输出不同 | 核对实际相关变量与工具，不以“机器配置一样”代替记录 |
| 遍历／并行顺序与生成器 | 输出顺序或生成内容不稳定 | 查明依赖和排序，不能把关闭并行当作所有问题的统一修法 |
| 缓存或后处理依赖遗漏 | 增量与隔离重建结果不同 | 记录缓存层、来源和依赖，保留证据后选择适用对照 |
| 依赖或外部输入漂移 | 同 commit 得到不同输入 | 记录解析结果并核对实际内容与可取得性，不只固定版本文字 |

[时间戳专题](https://reproducible-builds.org/docs/timestamps/)说明生成工具与归档元数据可能引入差异；统一时区不等于统一时间戳，工具也不必支持同一种固定时间机制。不能未经核对就删除所有时间或改写可执行内容。

[嵌入签名专题](https://reproducible-builds.org/docs/embedded-signatures/)讨论签名给字节复现带来的额外条件。如果只比较签名前产物，就明确结论只覆盖该阶段；若使用专门的签名处理或比较工具，应说明被排除的范围及其依据。不能先剥离不一致的部分，再宣称原始分发包已逐字节一致。签名有效性和平台接受结果仍需另验。

Unity 2022.3 的[增量构建手册](https://docs.unity3d.com/2022.3/Documentation/Manual/incremental-build-pipeline.html)区分增量路径、缓存与 Clean Build；自定义构建回调及其输入改变时，可能需要 clean build 来重建受影响结果。这不等于所有缓存都已清空，也不是完整输入的替代品。其他 Unity 版本、AssetBundle／资源框架或 Unreal 构建缓存按各自工具核对，不照搬一条全局删除命令。

### 最小正反对照：从干净副本重跑一次

以下方案尚未执行。先选一个自有的小型教学工程、一个目标平台与一条可验收功能，约定输入清单、构建指令和主产物集合；需要签名时单列相应阶段。干净工作副本指不借用作者目录里的未记录材料，不意味着删除公共缓存或禁止所有已声明依赖。

| 对照 | 只改变或隔离什么 | 记录与预期判断 |
| --- | --- | --- |
| A：原基线 | 按声明输入完成一次构建 | 保存实际输入、工具、参数、输出集合、日志和功能结果，不能只有 commit |
| B：正对照 | 在另一个隔离工作副本按同一记录取得输入并执行 | 分别报告取得、重跑、功能与字节比较结果；成功构建不替代后两项 |
| C：输入缺失／漂移反例 | 保持代码修订不变，单独遗漏或替换一个外部配置／导出器输入 | 检查前置核对能否拒绝或显示差异；若未被发现，不预填系统具备防护能力 |
| D：缓存对照 | 维持逻辑输入，按所选工具隔离或重新建立一个明确的缓存层 | 比较产物与功能、记录命中和重建范围；差异是调查线索，不直接证明缓存是唯一根因 |

反例中的替换只作用于独立教学副本，保留 A 的原材料；若该输入并未被实际消费，输出不变不能证明检查充分。恢复原输入并复测，核对差异是否随之消失；未发现问题也只报告本次覆盖范围。缓存命中不能让缺失的源材料被悄悄认作“已经取得全部输入”。

比较前列明文件集合、相对路径、大小与校验值。字节不同时先定位具体文件和阶段，再检查是否属于声明范围；功能相同不能把差异直接忽略，哈希相同也不能代替运行验收。保存失败、未执行及工具条件，不能只挑一次成功记录或按目录里文件数相同就接受。

## 构建系统与交付链路的关系

```
V02 内容生产  ─┐
V03 工程基建  ─┤→ V07 构建系统 →┬→ V08 热更新构建
V04 版本管理  ─┤                ├→ V09 平台发布
V05 资源管线  ─┤                └→ V13 验证与测试
V06 包体分发  ─┘
```

构建系统是汇聚点——前面六卷的工程决策最终都在构建系统中落地。构建系统的质量决定了后面所有环节的基础。

## 常见错误做法

**依赖个人目录的未记录材料。** CI 便于共享执行、留存记录和安排检查，但“在 CI 运行”本身不保证输入完整或结果确定。受控本地环境也可用于重建验证，关键是接收者能按明确条件执行并核对。

**修复了 Agent，却没有留下变化。** 诊断中可能需要手动处理环境；保留失败证据、记录干预范围，再将有效修法进入环境或脚本管理并复测。只修业务代码不能解决所有工具、凭据或基础设施故障，也不能靠反复重跑掩盖漂移。

**只留包或只留构建脚本。** 回溯实际交付与重新构建需要不同材料。按支持与恢复目标保留产物、符号、输入记录和必要工具取得条件，检查可读、可取得与配套关系；存了一个目录不代表这些能力已经验证。

## 小结与检查清单

- [ ] 构建是否摆脱未记录的个人目录和隐式环境依赖
- [ ] 输入身份、取得方式、实际消费及缺失项是否明确
- [ ] 可重跑、功能验收与指定产物字节复现是否分别报告
- [ ] 构建失败是否能定位到具体步骤（可追溯性）
- [ ] 输出角色、构建执行、输入与归档是否可关联并取得
- [ ] 正反对照、缓存／签名边界和失败结果是否有实际记录
