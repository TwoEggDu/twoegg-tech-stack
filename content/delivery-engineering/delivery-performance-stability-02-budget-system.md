## 这篇解决什么问题

V14-01 讲了性能工程的四阶段循环，Budget 是第一步。但"定预算"不是拍一个帧率目标就完事——需要三个维度的拆解才能变成可执行的约束。这一篇讲预算怎么定、按什么维度拆、每个类目怎么分配。

## 三维预算矩阵

性能预算是三个维度的交叉：

```
维度一：系统（角色、场景、UI、特效、音频、脚本）
维度二：场景类型（大厅、战斗、过场、加载）
维度三：设备档位（高档、中档、低档）
```

**每个交叉点都有自己的预算值。** 比如"低档设备 + 战斗场景 + 角色系统"的 CPU 帧时间预算可能是 4ms。

不需要把每个交叉点都精确定义——先定最关键的（低档设备 + 战斗场景），再逐步覆盖。

## 预算类目

### 帧时间预算

目标帧率 `f` 对应的节奏参考为 `T = 1000 / f` ms。CPU 与 GPU 可以并行处理不同帧，不能把各自耗时相加作为输出间隔；只取两者的较大值，也不足以推断单次反馈延迟或保证实际呈现节奏，还需检查依赖、排队、限帧与呈现。

Unity 6.0 的 [Highlights 说明](https://docs.unity.com/en-us/engine/6000.0/manual/analysis/profiler/visualizing-data/highlights)以 CPU/GPU 并行工作解释各自预算。该模块的 CPU Active Time 有特定的线程与等待扣除规则，不能把所有 CPU 指标视为同一口径；通用定义见[一帧拆解的指标表]({{< relref "performance/game-performance-frame-breakdown.md" >}})。

下表是**未校准的教学候选**，没有设备实测。先假设项目为波动和内容变化预留空间，再选择各侧工作预算；14/28 ms 及余量均不是通用推荐值。

| 目标帧率 | 节奏参考 T | CPU 侧候选预算 | GPU 侧候选预算 | 各侧预算到 T 的名义余量 |
| --- | --- | --- | --- | --- |
| 60 FPS | 约 16.67 ms | ≤14 ms | ≤14 ms | 各约 2.67 ms |
| 30 FPS | 约 33.33 ms | ≤28 ms | ≤28 ms | 各约 5.33 ms |

余量按 `T − 该侧预算` 分别计算，不能把 CPU 与 GPU 的余量相加后再分配一次。是否足够，后续要按目标设备、实际配置、代表负载与持续状态校准。VSync 或限帧等待可能是正常节奏控制，不能将其统一视为额外损失，再套一个固定的 2–3 ms 扣减。

**按系统提出配额（30 FPS 教学情形）**：下面假设各行是同一选定 CPU 线程上的互斥工作段；数值是计划分配，没有测量这些系统。共享渲染提交只记在一行，其他行不再包含它。

| 工作段 | 候选配额 | 本题的计账边界 |
| --- | --- | --- |
| 渲染提交 | 6 ms | 统一记录 Draw 提交、裁剪和排序 |
| 角色逻辑 | 4 ms | 动画、AI、技能的 CPU 更新，排除统一渲染提交 |
| 物理 | 3 ms | 独立的物理模拟工作段 |
| UI | 3 ms | 布局和状态更新，排除已记的渲染提交 |
| 特效 | 3 ms | 粒子等 CPU 更新，不含 GPU 后处理或统一渲染提交 |
| 其他脚本逻辑 | 4 ms | 网络、事件等未计入前述段的工作 |
| GC 与其余工作 | 3 ms | 该线程上未计入前述段的工作 |
| **配额合计** | **26 ms** | 距 28 ms 候选线还有 2 ms；距 T 约 7.33 ms |

这只是约束提案。真实实现若有父子区间、并行任务或共同依赖，先重建计账关系，再判断是否能相加；CPU 配额表也没有覆盖 GPU 和呈现。不能按对象平均分预算，或用单体耗时乘数量承诺场景通过，参见[帧预算拆账]({{< relref "performance/game-budget-06-frame-budget-breakdown.md" >}})。

**分项分位数同样不能直接求和。** 另构造 20 个帧的同线程教学记录，每帧分项互斥：

| 帧编号 | 基础工作 | UI 增量 | 特效增量 | 同帧总工作 |
| --- | --- | --- | --- | --- |
| 1 | 10 ms | 6 ms | 0 | 16 ms |
| 2 | 10 ms | 0 | 6 ms | 16 ms |
| 3–20，各帧 | 10 ms | 0 | 0 | 10 ms |

采用 nearest-rank，P95 取升序后第 `ceil(0.95×20)=19` 个值。分项 P95 之和为 `10+0+0=10 ms`，同帧总工作 P95 却为 `16 ms`。因此要先按帧关联互斥分项、形成总工作记录，再计算总量的分位数；多个分项各自 P95 达标不能代替组合检查。这些合成帧只演示算法，不估计独立运行的波动。

### 内存预算

设备物理 RAM 是支持范围的一项条件，不能直接乘一个比例得到应用可用额度。系统内存压力、进程状态、平台限制和所选统计指标都会影响判断；分配失败与进程被系统终止也要分别记录，不能统称为越过一个固定阈值后的 OOM。

[Android 内存管理说明](https://developer.android.com/topic/performance/memory-management)介绍了内存回收和 LMK 的进程选择；[Apple 的 jetsam 报告说明](https://developer.apple.com/documentation/xcode/identifying-high-memory-use-with-jetsam-event-reports)要求结合终止原因分析内存压力和进程限制。这些资料不提供本项目的通用安全额度。

先为目标设备、系统与构建配置写明下面的约定，再提出候选线：

| 预算项 | 应先约定什么 | 校准与复验重点 |
| --- | --- | --- |
| 进程常态占用 | 指标、单位、统计来源，以及任务结束后何时取值 | 在代表负载和运行条件下比较；RSS、PSS、footprint 与引擎 Used/Reserved 不能互换或混加 |
| 生命周期峰值 | 首开、切换、后台恢复等窗口，以及采样能覆盖什么 | 检查新旧资源重叠、临时缓冲和在途工作；稀疏采样的最大值不证明真实峰值已被捕获 |
| 内容分类账 | 纹理、Mesh、音频、脚本及共享资源的归属和持有者 | 同口径互斥项才可求和；共享资源计一次，引擎分类账与进程指标的差额保留待定位 |
| 返回与保留量 | 关闭界面或卸载后仍保留什么，何时允许保留 | 对象池、缓存、分配器或驱动保留量需解释；释放对象不保证进程指标立即等量下降 |

可复用[内存记账的切场景模型]({{< relref "performance/game-performance-memory-accounting.md" >}})：三个教学状态的同口径合计为 400、760、440 MiB，其中交接状态含新旧资源和临时缓冲。若另行假设候选线为 800 MiB，已列交接状态的名义余量只有 `800−760=40 MiB`。800 是本题假设，没有从某档物理 RAM 推出；三个状态也不能证明中间没有更高峰值。

这说明分配预算要考虑资源寿命和同时发生的工作，而不是给纹理或脚本先套一组固定百分比。真实项目还要保留指标定义、全窗口记录、压力/异常退出和必要表现的验证，才能决定是否接受候选线。

### 包体大小预算

包体预算先区分平台可接收的产物和项目希望达到的下载体验。构建上传大小、设备实际下载量、安装占用及首次任务必需资源是不同对象，不能合成一条“推荐首包大小”。下载量也不能独自证明转化率变化。

[Apple 最大构建文件大小](https://developer.apple.com/help/app-store-connect/reference/app-uploads/maximum-build-file-sizes)列的是构建限制；[Google Play 大小限制](https://support.google.com/googleplay/android-developer/answer/9859372?hl=en)说明其限制按 Play Console 计算的压缩下载大小，并区分 base module、feature module 和 asset pack。两者不能直接横向抄成项目预算。微信小游戏还需分别核对主包、分包及适用能力的现行规则，本篇不预填额度。

| 要建立的规则 | 必须先写清什么 | 通过后仍不能推出什么 |
| --- | --- | --- |
| 平台硬限制 | 渠道、产物/模块类型、压缩口径、适用规则及核对日期 | 被平台接收不等于下载体验可接受 |
| 首次任务下载预算 | 从哪个起点到哪个就绪点、必须取得哪些内容、缓存及网络条件 | 安装包变小不等于首次任务需要传的字节减少 |
| 版本更新预算 | 从哪个旧版本更新到哪个候选、设备配置及差异内容 | 上传产物大小不等于每名用户的更新下载量 |
| 磁盘与缓存预算 | 安装、解包、补丁、新旧副本及缓存的生命周期和峰值 | 磁盘字节不能替代运行内存或 GPU 占用 |

用一组教学账本说明边界：假设从开始取得应用到首个任务就绪，冷缓存、无重试，必要下载集合互斥，暂不计协议开销。A 的商店下发为 80 MiB，另需资源 20 MiB；B 将其中 20 MiB 移到后续资源下载，商店下发变成 60 MiB，任务就绪前仍必下 40 MiB。两者的必要传输量都是 `100 MiB`。

这只能说明本例没有减少该任务前的必要字节，不能证明耗时相同：连接、并发、安装校验和资源准备仍需单独观察。决定内容能否延后，应先确认它是否为该任务必需，并核对延后后的功能与反馈；分层定义继续复用[包体预算]({{< relref "performance/game-budget-02-package-budget.md" >}})。

### 加载时间预算

加载预算先写清“从哪里开始，哪些条件满足才结束”。字节取得、资产加载成功、界面出现和任务可操作是不同终点；首屏出现也不说明必要内容与交互都已就绪。具体边界复用[任务与反馈观测]({{< relref "performance/client-performance-task-observation-model.md" >}})，不把一个加载回调改名为用户等待时间。

| 任务 | 应先约定的起止点 | 影响预算解释的条件 |
| --- | --- | --- |
| 冷启动 | 明确的启动请求观测点 → 分别约定的首屏、必要内容及可交互终点 | 进程与缓存状态、构建/设备、数据与网络；应用内起点未覆盖的启动前等待须注明 |
| 首次打开界面或释放技能 | 应用接受本次请求 → 本次内容满足必要的可见/交互条件 | 资源与实例起始状态、必要效果与允许延后的装饰；首开与重开分开 |
| 场景切换 | 接受切换请求 → 目标场景达到约定的控制与表现条件 | 过场结束不等于可以操作；同时检查切换窗口的帧尖峰与新旧资源重叠 |
| 下载或预加载 | 接受准备请求 → 必要内容按约定取得、校验并交给消费者 | 后台工作仍可能竞争带宽、CPU 和内存；必需资源未赶上用途时仍会产生等待 |

例如，[Addressables 1.21 操作句柄文档](https://docs.unity3d.com/Packages/com.unity.addressables@1.21/manual/AddressableAssetsAsyncOperationHandle.html)的示例在资产加载成功后另外实例化；它没有把加载成功定义为业务或画面完成。预算记录还要约定设备/配置、窗口、单位、统计方式、候选时限依据及超时动作，不能直接套用一组高低档秒数。

用两条**教学记录**说明终点为什么会改变结论，不是设备实测。任务仍是打开奖励界面；本例要求奖励可见、控件可交互、确认特效可见，三者缺一不可。各条件一旦满足就保持有效，所有时刻均相对各自请求被接受的起点，使用同一教学时间域，单位为 ms：

| 教学候选 | 资产加载成功回调 | 奖励内容可见 | 控件可交互 | 必要确认特效可见 |
| --- | --- | --- | --- | --- |
| A | 120 | 200 | 260 | 300 |
| B | 80 | 180 | 240 | 360 |

在这些前提下，整体就绪取必要条件共同成立的时刻：A 为 `max(200,260,300)=300 ms`，B 为 `max(180,240,360)=360 ms`。加载回调从 120 提前到 80 ms，不能证明任务等待缩短，也不能据表认定读取、激活或 GPU 是原因。若**仅为本题假设**候选时限为 350 ms，A 留有 50 ms 名义余量，B 超出 10 ms；这不是实际项目的推荐线，两条教学记录也不能估计实际分位数、成功率或证明机型通过。若允许确认特效延后，需在比较前同步修改两组任务约定，并单独保留该反馈的完成要求。

提前准备或分帧可能把代价转到驻留、资源竞争或最终就绪时间，需一起检查任务完成时长、相关帧时间和内存；机制与失败收尾复用[资源就绪链]({{< relref "performance/game-performance-read-does-not-mean-ready.md" >}})。已知超时/未完成与观测缺失分开记录，不能以零代填或静默删除；只有回调证据时，只报告到该回调的代理区间，实际反馈保持未知。

## 预算推导方法

预算不是拍脑袋定的，是从设备能力倒推的：

```
1. 确定目标设备（最低支持到什么设备）
2. 确定目标帧率（低档 30 FPS / 高档 60 FPS）
3. 从帧率得到节奏参考（30 FPS → 约 33.33ms），再提出有依据、待校准的各侧预算与余量
4. 按设备/系统/构建、内存指标与生命周期提出候选线，再由代表负载和压力条件校准；不从物理 RAM 直接换算应用额度
5. 从帧时间和内存总预算分配到各系统
6. 各系统 Owner 认领并确认可行性
7. 不可行的 → 调整分配或降低该系统复杂度
```

**关键步骤是第 6 步**——预算必须由执行者确认，否则就是一纸空文。

## 预算作为 CI 约束

预算进入 CI 前，先定义检查对象、有效证据与超线动作。每份报告要绑定候选/内容、规则与基线版本、任务、设备及实际配置，并能回到原始记录；一次静态检查或一次流水线成功，只支持其实际覆盖的结论。

| 预算对象 | 可以安排的自动检查 | 结论边界 |
| --- | --- | --- |
| 构建包体 | 按渠道和产物类型解析构建报告或文件大小 | 构建字节不能替代设备下载量、首次任务下载或安装占用 |
| 纹理规格与估算 | 扫描目标平台的导入尺寸、格式、Mipmap 等规则 | 规格合规或同口径估算不能证明运行时同时驻留的纹理占用达标 |
| Shader 变体 | 记录指定平台/API 的构建变体集合及变化 | 变体数变化不能直接证明 GPU 耗时变化 |
| 帧时间与加载 | 在约定设备、任务与窗口采集，按预算及同口径基线判定 | CPU/GPU/反馈指标分开；缺必需观测不能记零或默认通过 |
| 内存 | 按指定指标、生命周期窗口与采样方式检查 | 已采样最大值不保证覆盖真实峰值，分类估算也不能代替进程指标 |

[Unity 6.0 的采集说明](https://docs.unity.com/en-us/engine/6000.0/manual/analysis/profiler/profiling-applications/profiling-collect-data-introduction)区分 Editor 中快速迭代与回到目标设备验证。将检查接进自动流程，没有消除构建、设备、内容与采集条件的差异。性能接受还需核对必要画质与玩法表现，不能为压低数字省去必需反馈。

聚合时先核对必需项、候选匹配、规则/基线适用性和数据完整性，再应用告警或阻断策略。已确认超线、采集异常、跳过与过期分别保留；缺证据不等于已知性能失败，也不等于通过。执行异常交检查维护者处理，超线交对应代码/内容负责人定位；例外须记录范围、理由、批准者、补验责任与到期条件，不能改写原检查事实。具体协议直接复用[质量门自动化]({{< relref "delivery-engineering/delivery-cicd-pipeline-04-quality-gates.md" >}})。

再构造一份**教学判定表**，不是实际跑测。假设同一候选、同一任务协议下计划三轮，每轮一次打开请求，任务终点沿用前节的三个必要条件；每轮都需在题设的 350 ms 内完成，三轮均为必需证据。三轮仅是本题规模，不是通用重复次数：

| 教学运行 | 证据状态 | 请求到任务终点 | 按题设判定 |
| --- | --- | --- | --- |
| R1 | 有效且条件匹配 | 320 ms | 未超线，名义余量 30 ms |
| R2 | 有效且条件匹配 | 370 ms | 超出 20 ms，保留失败事实 |
| R3 | 未取得终点，任务结果未知 | 不填数值 | 证据不足，需补验 |

这份清单有 3 轮计划、2 轮有效计时、1 轮已确认超线和 1 轮缺证据，不能判为通过；缺测也不能抹去 R2 的超线。即使已有计时均未超线，仍需补齐缺少的必需证据。复跑须说明原因并保留原记录，不能反复挑选通过结果；这些合成记录不估计真实成功率或证明设备达标。

**预算要有可复验的检查入口和处理责任。** 按风险与成本安排静态检查、目标设备跑测及必要的人工反馈验收，逐步自动化；人工验收也应绑定候选、规则、覆盖与证据。规则是否有效、工具是否运行、性能是否接受和团队是否持续使用分别验证，不以自动化脚本的存在替代这些结论。

## 小结与检查清单

- [ ] 性能预算是否按三个维度拆解（系统、场景、设备）
- [ ] 帧时间预算是否从目标帧率倒推并分配到各系统
- [ ] 内存预算是否按类目设定并区分设备档位
- [ ] 包体大小是否区分渠道设定上限
- [ ] 加载预算是否明确起止点、必要内容、统计方式及超时/缺失处理
- [ ] 预算是否由各系统 Owner 确认可行性
- [ ] 预算是否有匹配证据范围的检查入口，并保留缺失、超线、例外与复验责任
