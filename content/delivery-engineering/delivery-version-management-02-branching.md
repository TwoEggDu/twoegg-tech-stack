## 这篇解决什么问题

分支策略决定了代码怎样从开发流向发布。选错策略，团队会陷入合并冲突、发布阻塞或版本混乱。

## 为什么这个问题重要

分支策略出问题的典型场景：

- 所有人都往 main 分支直接提交，某次提交引入了崩溃 Bug，所有人的工作都被阻塞
- Release 分支拉出后，有人在 Develop 上修了一个紧急 Bug 但忘记 Cherry-Pick 到 Release，发版后 Bug 仍然存在
- 三个团队各自有 feature 分支，合入 Develop 时冲突量巨大，每次合入像一场战役
- Hotfix 分支修复了线上问题，但修复没有合回 Develop，下个版本又把同样的 Bug 带了回来

## 本质是什么

分支策略的本质是回答：**代码从写完到上线，经过哪些阶段，每个阶段在哪个分支上完成。**

### 四种角色分支

以下是 GitFlow 风格的一种角色分工，用来解释后面的例子。采用主干开发的团队可以用短期分支、版本标记和发布配置承担其中的职责，不必建立同名的四条长期分支：

| 分支角色 | 职责 | 生命周期 |
|---------|------|---------|
| **主干（Main/Master）** | 始终代表最新的已发布状态 | 永久 |
| **开发线（Develop）** | 集成所有已完成功能，是下一次发布的候选 | 永久 |
| **发布线（Release）** | 从 Develop 拉出，只接受 Bug 修复，准备发布 | 版本周期 |
| **热修复线（Hotfix）** | 从 Main 拉出，修复线上紧急问题 | 天级 |

加上按功能拆分的 **Feature 分支**（从 Develop 拉出，功能完成后合回 Develop），这就是经典的 GitFlow 模型。

### 三种主流策略

| 策略 | 适用场景 | 复杂度 | 发版节奏 |
|------|---------|--------|---------|
| **GitFlow** | 需要独立发布准备与维护线的项目 | 高 | 按团队约定的版本周期 |
| **GitHub Flow** | 主干可持续集成，发布另有控制的项目 | 较低 | 合入节奏与发布节奏可分开 |
| **简化 GitFlow** | 希望减少长期分支，同时保留发布隔离的项目 | 中 | 按测试与交付安排 |

#### 简化 GitFlow（本文的示例模型）

是否需要发布分支，要看同时维护的版本、测试窗口、客户端与服务端兼容要求。渠道审核影响发布时机，但不能单独决定代码分支模型，也不应把审核时长写成固定承诺。

以下用简化模型说明分工：

```
main ──────●─────────────●────────────── (已发布版本)
           ↑             ↑
release ───┼──●──●──●────┘              (发布准备 + Bug 修复)
           │  ↑  ↑  ↑
develop ───┼──┼──┼──┼──●──●──●──●────── (日常开发集成)
           │     │
feature/A ─┘     │                       (功能开发)
feature/B ───────┘
```

规则：
- Feature 分支从 Develop 拉出，完成后合回 Develop
- Release 分支从 Develop 拉出，只接受 Bug 修复（不接受新功能）
- Release 测试通过后合入 Main，打 tag，发版
- Release 的 Bug 修复同时合回 Develop
- Hotfix 从 Main 拉出，修复后合入 Main + Develop

## 三个版本并行时，怎样交付同一套输入 {#parallel-release-lines}

假设团队正在维护线上版本 N、测试待发布版本 N+1，同时开发更远期功能。这是用于讨论的场景，不是作者项目的实录。重点是每条线能接受什么变更、如何交付和追溯；分支叫什么由团队决定。

| 工作线 | 当前目标 | 可接收的变更 | 交接对象与凭据 |
| --- | --- | --- | --- |
| 线上 N 的维护线 | 修复已发布版本的问题 | 经影响评估的修复及必要配置、资源变更 | 运维与测试拿到固定版本组合、兼容范围和回退条件 |
| 待发布 N+1 | 收敛测试结果，形成发布候选 | 冻结范围内的修复；新增内容需重新评估 | 测试拿到确定的候选构建身份与变更说明 |
| 后续功能线 | 持续集成更远期内容 | 尚未进入 N+1 的功能及依赖改动 | 开发验证结果；不能自动混入发布候选 |

### 不只记录代码分支

一次交付要保存可重建的版本组合：客户端和服务端代码的固定提交、资源版本、配置源表版本与导出格式、协议版本或兼容范围、构建脚本及工具链版本，以及目标平台和环境。不同仓库可以分别标记，但交付清单必须把这些标记对应起来；单独写“来自 release 分支”无法重建一个包。

配置导出物还应能回溯到源表、导出工具和校验规则。资源路径、配置引用、客户端与服务端协议需要交叉检查；各仓库分别编译成功，不能证明这一组输入能一起运行。

### 一个线上修复怎样传到后续版本

修复 N 的问题时，先确定 N+1 与后续功能线是否也受影响。为每条受影响的工作线记录“需要修复 / 不受影响及原因 / 修复提交 / 验证结果 / 负责人”。不能用“已合回 develop”代替逐线确认。

代码未分化时可以评估移植同一修复；实现已变化时，可能需要重新实现等价修复。不要机械 Cherry-Pick 后便认为问题消失。资源和配置依赖也应随修复一起核对，避免只搬代码。

### 冻结的是候选输入，环境也要隔离

测试开始后，分支仍可能前进，但一个候选构建使用的输入清单应固定。修复后生成新的候选身份，并注明哪些测试结论需要重跑。不同工作线的配置、缓存、导出目录和归档位置需要能区分，避免 N+1 读到远期功能线的资源。

回退也要检查配置格式、资源内容、协议和服务端状态是否兼容；能检出旧代码不等于旧包仍能连接当前服务。具体兼容策略归对应系统维护，本篇只定义交接时必须回答的问题。

### 交接前的验收问题

- 仅凭交付清单，能否定位客户端、服务端、资源、配置及工具链的准确版本？
- N 的修复是否在每条受影响工作线上有独立结论？
- 测试验收的是哪一个候选构建，随后修改了什么？
- 旧包、新服务和配置变化的兼容范围是谁确认的，回退条件是什么？

具体触发、排队与产物保留策略见 [Jenkins 多分支流水线]({{< relref "delivery-engineering/delivery-jenkins-ops-104-multi-branch.md" >}})。该篇负责执行映射，本篇维护版本协作规则。

## 多团队分支协作

当团队规模从一个团队扩展到多个团队时，分支策略需要额外的协调机制：

### 命名规范

多团队的 feature 分支必须有命名规范，否则分支列表变成一团乱麻：

```
feature/{team}/{ticket-id}-{short-description}
例：feature/combat/PROJ-1234-skill-cooldown-fix
    feature/ui/PROJ-5678-new-shop-layout
```

### 合入节奏

多个 feature 分支合入 Develop 时的冲突管理：

**方案一：每日合入**。每个团队每天至少合入一次 Develop。冲突小、频率高。适合团队间代码耦合度低的项目。

**方案二：周合入窗口**。每周固定一个合入窗口（如周三下午），所有团队在窗口期集中合入。有人值班处理冲突。适合团队间代码耦合度高的项目。

**方案三：集成分支**。每个团队有自己的集成分支（team/combat-develop），先在团队内集成，再定期合入总 Develop。增加了一层缓冲，但也增加了管理成本。

### 代码所有权

多团队场景下，必须明确哪些目录/模块归哪个团队负责：

```
# CODEOWNERS 文件
/Assets/Modules/Combat/    @team-combat
/Assets/Modules/UI/        @team-ui
/Assets/Core/              @team-platform
```

跨团队修改需要明确审核归属。CODEOWNERS 可声明审核人；是否强制审核，还需要对应托管平台的保护规则或 CI 配置。仅存在这个文件不等于审核已经执行。

## 分支策略与发版节奏的关系

分支策略和发版节奏必须匹配：

| 发版节奏 | 推荐策略 | Release 分支存在时间 |
|---------|---------|-------------------|
| 每周发版 | 简化 GitFlow，Release 分支存在 2-3 天 | 短 |
| 双周发版 | 简化 GitFlow，Release 分支存在 3-5 天 | 中 |
| 月度发版 | 完整 GitFlow，Release 分支存在 1-2 周 | 长 |
| 按需发版 | GitHub Flow 变体，main 即 release | 无 |

Release 分支存在时间越长，合回 Develop 时的冲突越大。缩短 Release 分支的生命周期是减少合并痛苦的关键。

## 常见错误做法

**发布候选没有固定输入和准入规则**。无论使用发布分支还是主干开发，都需要隔离未验收内容、固定构建身份并保存验证结果。是否设置 Release 分支是实现方式之一，不能仅凭分支名称判断交付质量。

**Hotfix 只合入 Main 不合回 Develop**。线上紧急修复通常在 Hotfix 分支上完成后合入 Main 发版。但如果不同时合回 Develop，下个版本的 Release 分支就会再次包含这个 Bug。

**Feature 分支存在太久**。一个 feature 分支开发了两周不合入，和 Develop 的差距越来越大，最终合入时的冲突量爆炸。Feature 分支的生命周期应该控制在 3-5 天内。如果功能需要更长时间，用 Feature Flag 分段合入。

## 小结与检查清单

- [ ] 是否有明确的分支策略文档（不是"大家都知道"）
- [ ] Feature 分支是否有命名规范
- [ ] Feature 分支的生命周期是否控制在一周以内
- [ ] Release 分支的 Bug 修复是否同步合回 Develop
- [ ] Hotfix 是否同时合入 Main 和 Develop
- [ ] 多团队场景是否有 CODEOWNERS 和跨团队 Review 流程
- [ ] 分支策略是否和发版节奏匹配
