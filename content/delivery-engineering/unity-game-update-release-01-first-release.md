> 贯穿案例：客户端 100 首次交付，建立基线 B100，采用初版内容组合 R16。

## 1. 先拆开一款可运行游戏的组成

- 程序、业务代码、配置数据和美术资源分别提供什么能力。
- 客户端与服务端各自交付什么，哪些内容必须配合才能运行。

| 术语 | 本系列中的含义 |
|---|---|
| Player | 客户端程序，提供已随包交付的运行能力 |
| Res | 游戏资源，如模型、界面和音效 |
| HotCode | 可热更新的业务代码 |
| Data | 客户端读取的运行数据 |
| 内容 | Res、HotCode、Data 三类逻辑内容的合称 |

## 2. 哪些内容进入安装包

- 区分 Player、原生库、启动器、业务程序集和内置资源。
- 区分随包交付、运行时加载与运行时驻留，避免把它们混为一谈。

## 3. 哪些内容可以远程交付

- 说明远程资源、热更 DLL 和运行数据的职责及所需加载能力。
- 说明首次安装、首启下载与后续更新之间的关系。
- 将更新对象（Player 或三类内容）与策略分开：是否必须完成、是否建议升级、哪些内容按需下载分别描述准入要求、提示和下载时机，可以组合使用。
- 本系列的“客户端强更”指整包升级拦截；必须安装的内容补丁另行描述。

## 4. 第一次为什么要建立完整基线

- 让客户端、资源清单和配置格式形成一套可运行组合。
- 记录平台、渠道、环境、代码版本和热更基线，供后续更新复用。

## 5. 首包内置与远程下载怎样取舍

- 比较包体、首启下载量、弱网体验和离线能力。
- 分别按 Android 渠道、浏览器 WebGL 与具体小游戏平台核对分发、下载和重启约束，再决定内置、首启或按需下载。

## 6. 走通客户端 100 的首次交付

- 画出安装包、资源服务和游戏服务之间的连接。
- 分别检查产物完整、下载成功、进入游戏和设备体验，保留未验证项。

## 系列案例：从客户端 100 到 101 {#series-case}

1. **首次交付客户端 100。** 建立基线 B100，采用初版组合 R16。
2. **为 100 修复线上问题。** 配套发布修复组合 R17，客户端整包号保持不变。
3. **上线新英雄与活动。** 准备内容组合 R18，协调服务端规则，再决定开放时机。
4. **构建客户端 101。** 新底层能力要求基线 B101 与组合 R19，再决定旧玩家何时必须升级。

整包号和各内容版本独立表达。示例均在同一平台、渠道、环境空间内讨论；Android / demo / prod 是教学值。完整版本表与兼容契约统一见[第 04 篇：版本如何绑定]({{< relref "delivery-engineering/unity-game-update-release-04-version-binding.md" >}})。

版本号、英雄和故障用于教学，不代表线上发布记录。正文会分别标明源码核对、工程建议和实验结果；涉及 API 与平台机制时固定适用版本。
