> 教学优先的最小版本设计初稿。以下是计划规则与验证要求，游戏尚未实现和验收；设计与独立教学材料公开，Demo 工程保持私有。

## 1. 项目首先服务教学

无尽对决用一个简单的两人合作副本，串联玩法规则、框架、配置、资源、UI、网络、内容制作和设计模式教学。首要成果是能够解释问题、比较方案、复现实验并判断结果；游戏过程保持小而完整。

此前设想的上线运营放到远期扩展，不作为当前验收条件。每增加一个功能，都先写清要教什么、需要观察什么，以及现有场景是否已经足够承载它。

已确定采用斜俯视，强调技能搭配、释放时机和队友配合，操作保持简单。首版用一张小场地、两名角色、一种普通怪和一种测试奖励。两名角色各有移动、普攻和一个主动技能；模型、动画、特效与 UI 可以先用可替换的占位资源。

复杂 Boss、双装置机关、职业、装备、成长、救援／复活和闪避暂不进入最小版本。第二种规则或表现可以作为教学对照样例，不自动扩展正式玩法规模。

## 2. 最小玩法与合作规则

**进入 → 清怪 → 简单结算 → 返回 → 重开。**

进入测试时准备两名测试角色与本局配置，不要求先实现真实账号、正式大厅或完整匹配。两客户端如何连接、测试身份怎样分配，在 Unity 实现设计中落实；单项制作预览允许只启动一个客户端。

| 内容 | 最小规则 |
| --- | --- |
| 场地与镜头 | 一张小场地，斜俯视；具体角度、移动输入映射和目标选择细节待实现设计，不增加精确瞄准或复杂连招要求 |
| 玩家动作 | 移动、普攻、各一个主动技能；两名角色采用共同的基础能力与可区分的技能配置 |
| A 的主动技能 | 对有效敌人施加标记，提供可观察的状态与表现 |
| B 的主动技能 | 消耗目标上的有效标记，造成额外伤害；没有有效标记时不产生额外效果 |
| 普通战斗 | 两人均可通过普攻参与清怪；技能衔接用于展示合作效果，不以强制机关阻止单项调试 |
| 敌人 | 一种普通怪，数量、位置、属性和已有简单行为参数可配置 |
| 胜负 | 清空本局怪物获胜；两名角色全部倒下失败；结束后停止接受本局战斗操作 |
| 结算 | 显示本局结果和一种测试奖励，同一局只执行一次结算 |
| 返回重开 | 清理本局临时状态，准备新局，再次运行相同流程 |

标记持续时间、重复施加的刷新方式、技能冷却、目标选择、奖励数量及失败奖励、同时满足胜负时的优先级，仍须在实施前固定。它们应支持验证规则边界，不需要先做复杂平衡。断线后的恢复策略也需明确；首轮可采用显式终止并重开测试的简化方案，恢复到战斗中途留作后续实验，这一处理方式仍待实现设计确认。

## 3. 功能、教学目标与验证内容

下面是最小教学版本的计划验证表，不是已有测试结果。制作阶段通过单项入口先验证内容；双人一致性到双客户端阶段验收。所有记录都注明环境、版本、输入、预期、实际结果和限制。

| 功能 | 教学目标 | 计划验证内容 |
| --- | --- | --- |
| T01 一张场地与斜俯视镜头 | 区分世界状态、相机与表现，保持观察方式简单 | 两名角色、目标与技能反馈可辨认；镜头变化不改变规则判定 |
| T02 两名测试角色进入同一局 | 理解角色身份、局身份、客户端与规则权威方的职责 | 两个独立客户端会话看到相同角色和同一局结果；单客户端预览单独记录 |
| T03 移动 | 理解输入意图、状态更新和表现同步 | 各自只能操作所属角色；倒下或结束后不继续移动；非法与迟到输入有明确处理 |
| T04 普攻 | 理解目标、攻击条件、伤害、冷却和死亡归属 | 有效攻击按规则扣血，无效目标不生效；重复消息不重复结算同一次命中 |
| T05 A 的标记技能 | 理解配置、效果状态、施加者与目标的关系 | 正确目标获得可观察标记；失效或结束后清理；持续和刷新规则按最终约定检查 |
| T06 B 的消耗技能 | 理解条件组合、状态消费、事件与额外伤害的衔接 | 有标记时消费并产生额外伤害；无有效标记时没有额外效果；同一标记不重复消费 |
| T07 一种普通怪 | 理解属性、简单行为与生命周期，比较分支和状态组织 | 按配置生成、行动、受伤和倒下；倒下后停止行为，退出重进不残留旧怪物 |
| T08 最小关卡配置 | 理解内容标识、生成清单与关卡目标 | 改怪物数量、出生位置或属性能观察结果；空配置、错误引用有约定反馈 |
| T09 胜负状态 | 理解状态转换、状态所有者及结束条件 | 清空本局怪物获胜，两名角色都倒下失败；结束只触发一次；并发胜负按确定后的优先级验收 |
| T10 一种测试奖励与简单结算 | 理解结果对象、一次性发放和 UI 反馈 | 同一局只结算一次；重复请求不重复计数；失败是否有奖励按约定检查；先用隔离的内存数据 |
| T11 返回与重开 | 理解局作用域、初始化、销毁与异步取消 | 新局有新身份；角色与怪物临时状态、标记、订阅、任务和表现清理；旧回调不写入新局 |
| T12 策划修改配置 | 理解数据定义、校验、生成与两端一致采用 | 独立修改技能、怪物、关卡、奖励；正确数据可预览，错误定位到源记录；不采用半套数据 |
| T13 替换模型 | 理解资源身份、依赖与表现接口 | 兼容模型替换后比例、朝向、挂点和材质正确；缺失依赖或不兼容有反馈 |
| T14 替换动画 | 理解规则时序与表现时序、取消和恢复 | 普攻、主动技能、受伤和倒下反馈符合约定；换动画不擅自改变规则；退出后不继续回调 |
| T15 替换特效 | 理解加载、触发、停止、复用和所有权 | 标记与消耗特效触发正确；提前结束、目标消失和重开后无残留 |
| T16 替换 UI | 理解视图与业务分工、绑定、事件订阅和异步作用域 | 血量、技能状态和结算正确显示；兼容外观替换不改规则；缺绑定可定位，重复开关无重复响应 |
| T17 加载与释放 | 理解资源请求、持有、取消和清理 | 按当前加载模式记录请求与释放；失败可观察；反复进入／返回可追踪资源生命周期；下载缓存另做实验 |
| T18 诊断与复现 | 理解实验输入、版本与可观察结果 | 保存局身份、配置／代码／资源版本、步骤与事件；能够区分规则失败、资源失败和错误配置 |

结算首轮可使用内存中的测试计数或结果记录。真实账号、背包经济、数据库事务、重启持久化和正式运营数据不作为最小循环的前置条件；演示一次性结算也不能推定生产级数据可靠性。

## 4. 系统按教学职责划分

| 逻辑职责 | 最小承担范围 | 可以由此研究什么 |
| --- | --- | --- |
| 测试进入与局流程 | 测试角色、本局身份、进入、运行、结束、返回与重开 | 身份、状态机、作用域与清理 |
| 战斗规则 | 属性、普攻、标记与消耗、受伤和倒下 | 数据驱动、规则组合、变化边界与双端权威 |
| 关卡与怪物 | 生成一种怪物、维护剩余目标与简单行为 | 创建、生命周期、状态与配置 |
| 结果与测试奖励 | 生成结果、一次性结算、显示测试计数 | 幂等问题、职责分工与数据边界 |
| 交互与表现 | 输入、镜头、模型、动画、特效、血量与技能状态、结算 UI | 规则／表现分离、视图与异步生命周期 |
| 内容制作与运行支持 | 配置、资源映射、检查预览、加载释放与日志 | 策划／美术交接、错误反馈、资源所有权与复现 |

这些是逻辑职责，不要求拆成六个服务或六个类。双人实验建议由服务端统一判定规则与结算，客户端提交意图并显示结果；具体同步组织仍需设计和验证。直接实现足以说明问题时就保持简单。

## 5. 用标记与消耗串起一项技能

策划定义标记和额外伤害的规则参数，程序提供对应行为与字段定义，美术按约定提供标记和消耗反馈。先描述输入、状态、规则结果和清理，再选择引擎对象与 API。

1. A 对有效目标发起技能，规则负责人校验本局、角色、目标和技能条件。
2. 通过后建立目标标记，并显示能辨认的反馈；无效操作不建立标记。
3. B 发起技能，规则检查有效标记；满足条件时消费一次并产生额外伤害。
4. 标记失效、目标倒下或本局结束时，按已确定的规则清理状态与表现。
5. 验证无标记、失效标记、重复消费、无效目标、旧局消息和退出后的回调。

这条链路同时解释“源配置已经改动”和“运行环境已经采用改动”的区别，以及“特效播放”和“规则生效”的区别。初期不承诺所有配置都能在 Play 中即时刷新，允许生成后重新进入测试或重启本地测试服。

## 6. 策划工作管线

策划在程序已提供的能力内独立配置技能、怪物、关卡与奖励。新行为类型仍由程序扩展，不要求配置系统承担任意编程能力。

流程为：修改源配置 → 检查与生成 → 两端采用配套版本 → 指定技能／怪物／关卡预览 → 最小双人流程验收。

先用标记参数、额外伤害、怪物属性、数量和出生位置、测试奖励配置完成独立操作。检查包括格式、范围、唯一标识、引用和业务约束。失败应定位到源文件、记录和字段，并保留上一套可运行数据，避免采用半套产物。

教学与验收对应 T05～T12：操作者应能解释配置如何变成规则数据，展示正确修改的结果，并独立发现和修正一个无效引用。单项预览不承担正式账号与存档系统的建设。

## 7. 美术工作管线

美术在稳定的兼容约定内独立替换模型、动画、特效和 UI。每类资源先做一个能看到结果的占位样例，再验证替换能力。

流程为：制作与导出 → 引擎导入 → 依赖与兼容检查 → 单项预览 → 标记／消耗技能和清怪流程验证 → 提交完整依赖。

模型约定比例、朝向、骨骼或重定向及挂点；动画约定动作语义、规则与表现时序；特效约定触发、持续和清理；UI 约定数据、交互、绑定和开关生命周期。更换不兼容骨骼、移除必需绑定或增加业务交互，需要程序参与调整。

教学与验收对应 T13～T17：展示一次兼容替换、一次缺失依赖或绑定报错，以及一次退出重开后的清理。源文件、交换资源、引擎资产和运行制品的生成关系要可追踪。

## 8. 各工种共同验收一个小过程

策划说明规则与预期，美术说明表现与交付范围，程序提供数据与资源约定、工具和运行能力，测试按同一版本记录步骤、结果与失败。早期可以兼任角色，但验收独立制作时不能由程序在后台手动补齐配置或绑定。

共同交付至少包括：源内容、实际采用的版本、操作入口、预期与实际结果、问题和修正记录。规则正确、美术反馈、工具可用、双端一致性和清理分别检查，自动结构检查不替代运行结果。

## 9. 让设计模式教学沿真实变化展开

沿“直接方案 → 需求变化或失败 → 候选比较 → 选择理由 → 实现验证 → 迁移练习”教学。所有模式都是候选，最小版本不要求使用全部模式；设计原则、GoF 模式、UI 架构和执行模型分别说明。

| 教学案例 | 候选与学习问题 | 计划验证 |
| --- | --- | --- |
| 标记／消耗能力与参数变化 | 先比较配置、分支、函数；第二种目标规则出现时再讨论 Strategy | 修改范围、旧规则回归、无效目标与重复消费；只改数值时不必引入新策略 |
| 本局与怪物的阶段 | 分支、转换表、State 对象与 FSM | 非法转换、结束一次、迟到回调与重开清理；不把所有状态机判作 GoF State |
| 血量、技能状态和结算 UI | 直接调用、Observer／事件、MVP 等职责拆分 | 视图开关和退出后无残留订阅，换外观不改规则；本地通知与网络消息分开 |
| 操作、创建和资源交接 | 按变化需要比较 Command、工厂候选、Adapter 或 Facade | 明确接收者、所有权、失败和取消；封装本身不保证幂等或确定性重放 |
| 检查步骤或创建成本的专项 | 顺序函数、Pipeline、Template Method；直接创建与对象池 | 只在具体变化或测量问题出现时开展；记录失败定位、重置和成本，不作为最小版必做清单 |

首个内容案例先解释 A 与 B 为什么产生不同效果，分清配置参数与行为能力；第二种目标规则作为后续迁移练习，不增加第二种正式玩法。公开独立示例与练习并给出预期，读者无需私有 Demo 也能判断方案；实验未执行时明确标注。

## 10. 分阶段验收，扩展按教学问题选择

| 阶段 | 需要完成的事 | 验收范围 |
| --- | --- | --- |
| P0 规则与基线 | 固定最小规则、字段与资源约定，选择版本与观察入口 | 规则可判定，未定细节与各功能教学目标清楚 |
| P1 内容制作与单项预览 | 同一小场地中的基础行为、标记与消耗；配置与资源独立替换 | T01、T03～T08、T12～T18 的单项部分；本地预览按实际模式记录 |
| P2 最小双人教学流程 | 两独立客户端进入同一局，清怪、胜负、一次性测试奖励、返回与重开 | 全部 T01～T18；完整双人结果有证据，不要求真实账号、数据库持久化或运营后台 |
| X 按需专项实验 | 资源／代码更新、持久化与重启恢复、平台适配、性能或更复杂同步 | 每次选择一个问题，在相同小流程上实验，记录输入、结果和限制，不扩充必做玩法 |

当前只有设计文档与网站页面，游戏能力均待实现与验证。Unity 先在 Editor 跑通最小教学流程；跨进程验证需要独立会话，资源与代码更新需要专项 Player 验证时单独构建。

Windows、Android、iOS 和小游戏保留为设计考虑与按需实验方向，各平台单独验证。上线运营、正式账号、匹配、成长经济、完整持久化、运营工具和帧同步完整版本均非最小版前置条件。

## 11. 四部分设计与各专栏的关系

引擎无关设计定义最小规则、内容语义、教学问题和验收目标。Unity 作为项目的实际落地引擎，沿用 ET、Luban、YooAsset、HybridCLR、UGUI 的方向；其中更新等能力按专项接入，不要求先用齐所有组件再验证一次清怪。

Unreal 与 Piccolo 仅用于讨论相同设计的落地方案与机制差异，当前不安排对应项目实现或验收。讨论围绕 Unity 的实际案例展开，说明对象组织、内容流程、生命周期和能力缺口；区分已核对的机制、设计推导与待验证假设，不将方案讨论写成运行结果。T01～T18 的实施与验收由 Unity 路线承担。

- 玩法主题解释标记与消耗为什么形成配合，以及最小规则的取舍。
- 框架与网络主题追踪双人操作、状态、结算和局生命周期。
- 配置与生产主题解释策划、美术的源内容如何进入运行与反馈。
- 设计模式主题解释变化、方案、成本与迁移练习。
- 资源、UI、运行时和引擎主题解释实现机制及失败边界。
- 交付、性能与运营主题选择受控专项，用现有小流程承载实验。

## 12. 下一步与证据要求

下一步细化标记持续与消费、目标选择、冷却、胜负优先级和测试奖励规则；确定输入映射、版本与制作预览入口，再拆最小实现任务。暂不追加 Boss、机关、职业或成长需求。

每个实验记录：功能编号、教学问题、固定版本、输入和操作、观察位置、预期、实际结果与验证范围。源码推导、单项预览、Editor、双客户端、Player 与真机结果分开，教学示例通过不替代游戏验收。
