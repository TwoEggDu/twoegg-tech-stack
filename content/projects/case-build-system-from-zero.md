## 一句话总结

这条工作线把提交后的错误反馈给能处理它的人：美术能定位资源节点上的 Missing，策划能看到导表时的路径与依赖错误，程序能收到编译问题；构建完成后，机器人将包的下载地址发给 QA。

## 第一阶段：0→1，在第一个项目里搭起最小可用管线

本节沿用原有章节位置。“从零”和“第一个项目”仍待核实；目前确认的是下面这些工具与反馈环节。

### 接手时的状态

作者遇到的交付问题包括：客户端提交后编译报错、云端代码编译报错、配置表解析不通过、美术资源 Missing、策划配置与实际提交路径不匹配，以及客户端和服务端协议不匹配。

这些问题来自不同输入，处理者也不同。只告诉团队“构建失败”，还需要有人再去定位是代码、配置还是资源出了问题。这个案例关注怎样把反馈定位到具体对象；没有材料证明这些问题都已经被同一种自动检查覆盖。

### 我搭建的第一版管线

已确认的环节如下。表格按问题的处理顺序组织，不表示所有工具必须由同一个 Job 串行执行。

| 环节 | 已确认的做法 | 谁可以据此处理 |
| --- | --- | --- |
| 美术提交前 | 作者实现了依赖提交工具，用于减少资源依赖遗漏 | 美术 |
| 资源定位 | Unity 编辑器工具支持拖入资源，显示具体资源的哪个节点存在 Missing | 美术与相关资源维护者 |
| 本地导表 | `xlsx → bin`；路径不匹配、配置表依赖错误会在导表时反馈 | 策划 |
| 提交后检查 | 机器人检查每次提交中的 Missing、路径不匹配和编译问题 | 对应的美术、策划、程序 |
| 构建后交接 | 机器人将包的下载地址推送给 QA | QA 获取待测包；下载与测试结果仍需另行确认 |

依赖提交工具与提交后检查承担不同职责：前者帮助提交者带上依赖，后者让已进入协作流程的问题可见。编辑器里的定位工具则缩短了从“报错”到“找到具体资源节点”的距离。这里没有把依赖提交描述成能杜绝所有 Missing。

### 两类通知怎样进入协作流程 {#build-and-check-notifications}

作者提供了构建完成与 Missing 检查两类群消息。这里保留信息结构，替换任务名、人员、版本值、时间和所有内部地址；下面的占位内容不是另一次真实构建记录。

```text
[项目 A / 目标平台 / 测试环境] 构建完成 #<构建号>
触发人：<已脱敏>
开始时间：<构建开始时间>
源码版本：SVN r<版本号>
参数摘要：<构建范围、目标环境、热更新、SDK、调试与发布开关>
下载：<受控的包下载入口>
预览二维码：<目标平台的预览入口>
有效期：<截止时间与预计剩余时长>
详情：<对应构建任务的详情入口>
```

构建通知不仅告诉 QA “包好了”，还给出查找这次构建的线索。源码版本和参数帮助确认拿到的是什么包，详情入口供失败追查，有效期提醒接收者及时获取；过期后怎样重新获取、通知是否包含资源与配置版本，仍需补充。

```text
请修复检查中发现的 Missing 资源
报告：<本次检查报告的 JSON 入口>
```

Missing 通知样例提供了报告链接。具体资源与节点如何定位，目前依据作者对编辑器工具的描述；本轮没有打开原报告，不能声称已核对 JSON 字段、错误数量或修复结果。检查报告与构建包属于不同交付物，不能用一条消息代替另一个环节的验收。

参数中配置了自动发布，也不等于已核验发布成功。通知发送、下载可用、预览可用、安装启动与 QA 测试结论应各有记录；本轮材料仅证明所提供通知包含这些入口与字段。

### 检查结果需要区分问题类型

作者进一步提供了导入设置检查消息，以及另一条“缺失资源”的报告链接。下表只复述消息中的差异，资源名与路径已替换，不是对项目资源执行检查的结果：

| 脱敏对象 | 报告中的检查字段 | 项目规则期望值 | 报告实际值 |
| --- | --- | --- | --- |
| 资源 A（纹理） | `TextureImporter.mipmapEnabled` | `False` | `True` |
| 资源 B（纹理） | `TextureImporter.streamingMipmaps` | `True` | `False` |
| 资源 B（Android 设置） | `TextureImporter.PlatformTextureSettings.overridden` | `True` | `False` |
| 资源 C（Android 纹理格式） | 消息中的 `TextureImporter.PlatformTextureSettings.Format` | `ASTC_RGB_6x6` | `ASTC_8x8` |

这类消息给出“哪个对象、哪个字段、期望什么、实际是什么”，接收者可以据此找到设置差异。后续样例还包含 @ 接收者与序号标记，但责任人如何映射、消息怎样分段尚未核实。格式名称按消息原样记录，不作为当前 Unity 版本枚举或推荐压缩格式的说明。是否应修改为期望值，仍取决于该规则的适用资源范围、平台和版本；本例不意味着所有纹理都应关闭 mipmap 或开启 streaming。

另一条通知把“缺失资源”报告作为单独入口，但本轮没有读取报告内容，不能确认它检查的是文件存在性、配置路径还是资源引用。后续取材应把导入设置差异、资源节点 Missing 与引用目标不存在分别核实，明确各自的定位信息、处理人和修复后复检方式。

### 群通知和本地诊断各自承担什么

作者提供的一条导表失败消息包含 `author`、`FilePath` 和 `Error`。脱敏后，其信息关系是：

| 字段 | 样例中提供的信息 |
| --- | --- |
| `author` | 一名相关人员，公开稿不保留姓名或账号 |
| `FilePath` | 某张源配置表的位置，公开稿不保留构建机路径 |
| `Error` | 与 `FilePath` 相同的路径，没有进一步原因 |

仅看这条群消息，详细原因不可见。作者进一步确认：同事收到通知后，可以在本地工具中查看更详细的报错。因而这里是两层反馈：群消息提示相关人员处理哪个文件，本地工具承担深入定位；不能仅凭消息简短就认定整套诊断信息不足。

后续取材应补一例“收到通知 → 本地定位 → 修正 → 复检”的过程，说明怎样找到对应文件、确认本地输入与被检查版本一致，以及修正后如何知道问题已消除。详细报错究竟包含 sheet、行列、字段或依赖链中的哪些信息，仍需看获准公开的样例。本轮不要求把全部诊断搬进群消息，也没有修改导表工具或通知系统。

### 搭建过程中最难的部分

目前能确认的设计目标，是让美术、策划、程序各自快速知道哪里出了问题，并处理自己负责的输入。作者反馈这些工具让定位和修正更直接；这属于经历中的定性观察，尚无错误率、等待时间或效率提升的量化记录。

关于规则由谁制定、是否阻断后续构建、误报和豁免怎样处理，以及作者与其他维护者的具体分工，本轮尚未补齐。不能据现有材料把整条管线都归为作者独立设计与维护。

## 结果和反思

这个案例目前可以解释一个工程判断：**检查结果需要把问题指向可处理的对象，而不只是返回一个失败状态。** 资源节点、配置路径与依赖、编译错误分别对应不同的修复入口；机器人把问题和包地址送到协作流程中。

后续取材优先补四项：

1. 一条经过脱敏的 Missing 报告：对象、节点、错误类型与修正后的结果。Missing 的具体分类待确认。
2. 一条导表失败及修复的摘要：源表、依赖与资源路径如何对应，修复后怎样复核。
3. 一次提交到 QA 通知的版本对应关系：提交身份、检查结果、构建产物身份、通知内容。公开材料不用真实下载地址或原始日志。
4. 客户端与服务端协议不匹配：目前确认遇到过此问题，自动检测方式、覆盖范围和验收方法尚未确认。

若要补效率数字，需另有可比样本、时间窗口与采样定义。QA 通知发送成功、实际下载成功、安装启动成功和测试通过分别记录，不能互相代替。
