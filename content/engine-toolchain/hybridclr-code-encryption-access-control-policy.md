> 代码加固影响别人读取和分析 DLL 的成本；访问控制约束加载后的代码能调用哪些能力。两者需要分别设计和验证。

这是 HybridCLR 系列第 29 篇。热更 DLL 既是可分发文件，也是即将执行的程序。文件被拿到后能否直接反编译，和程序执行后能否访问文件系统，是两个不同的问题。

> 资料范围：商业功能依据 2026-10-25 查阅的官方 9.x 文档。本文没有商业加固包或对抗测试，不推断私有解析器继承关系、密钥存储布局或访问检查的完整内部实现。

## 先确定保护的对象

标准 .NET DLL 通常能被 ILSpy 等工具解析，metadata 与 CIL 可以帮助恢复程序结构和接近源代码的表达。但反编译结果不是原始 C# 文件的完整还原，注释、部分局部名称及编写形式不一定保留。

项目需要区分三类目标：

| 目标 | 可以采用的手段 | 不能替代的工作 |
|---|---|---|
| 降低离线解析与直接反编译的便利性 | 格式变换、混淆、加密 | 运行时对抗和实际安全评估 |
| 限制第三方模块调用宿主能力 | 访问策略、模块 API 设计 | 完整沙盒边界与异常路径验证 |
| 维持更新来源与内容完整性 | 发布鉴别、完整性验证 | 不能仅靠“文件打不开”判断可信 |

客户端加固也不能让支付或对战关键结果自动可信。若相关决策本来需要服务端校验，加密 DLL 只是附加保护。

## 官方加固说明能确认到哪一层

[官方代码加固文档](https://www.hybridclr.cn/docs/business/basicencryption)介绍了全局 metadata 保护、元数据混淆／加密、结构与加密虚拟化、延迟解密等方向。这些方向对应不同的攻击面，不能当作一套经本项目验证的固定“七级安全等级”。

特别是该页面的功能表中，指令虚拟化没有和前六项一样标记“已经实现”。不能仅因后文介绍了原理，就写成所有商业包都已提供、可以全部开启；应核对实际购买的版本与高级加固功能文档。

可确认的运行时契约是：匹配的商业 runtime 可以加载相应加密 DLL，普通热更程序集仍使用 `Assembly.Load`。这不等于已确认其内部一定替换了 `RawImageBase` 的某个子类，或者解密后所有步骤都与社区版相同。

社区版加载器接收标准 DLL，并不推出“开源意味着不能加密”。加密的安全性不能建立在算法源码保密这一条假设上；开源算法同样可以提供密码学保护。社区版项目自行加密传输文件后再解密加载，与商业 runtime 内建的格式和延迟处理能力，是不同的工程方案。

## 构建参数为什么必须有版本归属

官方公开参数里，`vmSeed` 用于生成进入主包 native 代码的加密虚拟机，生成更新 DLL 时需要与主包一致；`metadataSeed` 和 `key` 则允许按更新调整。

这给发布系统带来一个明确要求：加密配置必须能够追溯到目标主包。不能只保存“本次用了什么参数”，还要知道客户端使用哪套主包实现。配置不一致属于不兼容输入，可能造成加载失败；具体错误形式应实测，不能保证一定以某种异常或崩溃表现出来。

更换动态参数可以改变后续产物，但不代表已经泄露的客户端能力或明文因此失效。参数轮换与密钥保护、版本适配、撤回旧更新是不同问题。

### 延迟解密降低的是暴露便利性

延迟解密把部分数据的解码推迟到使用时，能够降低在单一加载入口取得完整原始数据的便利性。不能据此断言“任何时刻都不存在完整明文”或“无法通过多次运行和观察恢复信息”。

实际缓存保留多久、哪些数据仍可通过反射取得、不同运行路径会暴露多少信息，需要对应版本的实现或测试。本文不将“逆向成本指数级增加”作为可测结论。

## 加固应该怎样进入构建流水线

在可审查的工作流里，先得到已验证的程序集，再应用匹配的混淆与加固步骤，最后把对应产物送入发布系统。对于需要输入标准 IL 的混淆工具，应在改变 DLL 文件格式之前执行，并检查两套工具的兼容性。

DHE 还需要保持变化数据与 DLL 一致。官方提供联合生成加密 DLL 与 DHAO 的工具入口，但不能由此推断任何版本都只允许一种内部执行顺序。应使用所选工作流的受支持入口，避免自行组合不匹配产物。

构建后至少要验证加载结果、关键调用、反射与泛型用法，而不是只检查文件不能被普通反编译器打开。商业加固能力没有在本系列社区版实验中被验证。

## 访问控制策略具体限制什么

[官方访问控制策略](https://www.hybridclr.cn/docs/business/accesspolicy)描述了类粒度的调用限制。它约束受限程序集对目标类型方法的访问，不等于可以从一段配置推导出完整的进程隔离或资源配额能力。

当前配置结构为 `AccessPolicy` 下的 `Rule` 与 `Target`。前者定义目标 API 范围，后者把规则绑定到受限程序集。下面是一个结构有效的示例，用于演示限制 `ThirdPartyMod` 访问部分系统类型：

```xml
<AccessPolicy>
  <Rule id="RestrictSystemApis">
    <assembly fullname="mscorlib">
      <type fullname="System.IO.*"/>
      <type fullname="System.Reflection.*"/>
    </assembly>
  </Rule>
  <Target assembly="ThirdPartyMod"
          accessAssemblyNotInRules="0"
          rules="RestrictSystemApis"/>
</AccessPolicy>
```

这是策略格式示例，不是可直接覆盖所有 UGC 风险的完整配置。`mscorlib` 等程序集归属需要按实际目标程序集核对；宿主 SDK、反射包装和允许调用的 API 都需要单独设计。`accessAssemblyNotInRules` 控制规则未涉及的程序集访问，不能漏掉这一层。

同一 assembly 中类型规则按官方匹配次序生效；多个 Rule 汇总为限制集合。允许例外、通配范围和默认行为都应通过配置校验确认，不能用自造的 `AllowClass / DenyClass` 标签替代产品格式。

### 把“能读取配置”和“限制生效”分开验收

官方流程包括 XML 转二进制、配置名字检查、程序集离线调用检查及 `RuntimeApi.LoadAccessPolicy` 运行时装载。普通 `Assembly.Load` 本身不会提前验证所有非法调用。

文档说明调用检查与首次调用相关，也允许运行时更新策略。它没有完整公开已转换方法、缓存失效与动态更新的所有细节，因此不能直接断言“检查一次后永远不再检查”，更不能据此承诺更新策略对所有已执行代码立即生效。

应用应准备允许调用、拒绝调用、间接调用以及更新策略后的用例，核对实际阻止行为。对非预期路径的处理也要纳入测试，不能仅以加载返回成功作为访问隔离成立的证据。

## 加固与混淆的关系

混淆主要改变可读符号或 IL 表达，加固可以进一步改变分发格式及运行时处理方式。二者可能组合，但具体收益不满足简单的“每多一层就按固定倍数增长”。

项目选型时，先记录保护哪些代码、面对哪种访问能力的攻击者，再测量包体、加载、首次使用和运行开销。对于第三方代码，还要单独验证访问策略。没有明确威胁模型时，堆叠功能数量不能说明保护已经充分。

加固与访问控制的有效性，需要由各自的输入契约和验证结果支撑。
