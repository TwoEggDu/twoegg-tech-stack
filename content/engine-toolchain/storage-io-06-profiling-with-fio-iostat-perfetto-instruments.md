> 如果只先记一句话，我建议记这个：先说清楚哪一次加载、慢在哪个阶段，再选能回答这个问题的工具。`fio`、`iostat`、Perfetto 和 Instruments 各有观测范围，不必每次按固定顺序跑一遍。

> 阅读范围：本文核对工具官方文档，给出观测模型与排查建议；配置和事件字段是教学示例，没有设备压测、项目 trace 或优化收益实测。命令适用条件随各节说明，不能直接跨平台照搬。

前面几篇我们已经把底图立住了：

- 存储设备在怕什么
- 文件系统会在哪些地方替你先结账
- OS I/O 请求怎样流动
- 为什么移动端会把同一个问题换一种方式放大

再往下走，就该进入很多团队真正会卡住的一步：

`那我到底怎么测？`

因为项目里“像 I/O 的症状”其实很容易长得像同一件事：

- 首载卡一下
- streaming 边界抖一下
- 某些低端机就是慢
- 明明异步读了，还是在关键帧掉下来

但这些外观看起来很像的现象，背后可能完全不是同一个根因：

- 真的是底层设备太慢
- 是访问模式把请求打得太碎
- 是 `open / close`、元数据和页缓存先在前面结账
- 是 I/O 回来后解压、反序列化、依赖解析和 GPU 上传在后面收口

所以这篇文章想解决的，不是“教你背几个命令”，而是先把这件事说清楚：

`当你怀疑游戏 I/O 有问题时，哪一个工具该先上，它到底回答什么，不回答什么。`

## 先定义观测口径：谁的耗时，从哪里算到哪里

“读取用了很久”至少可能指四本账。每个数字都要带上**对象、起止事件、单位、窗口和聚合方式**，才能拿来比较。

| 观测对象 | 本文采用的口径 | 不能直接推出什么 |
| --- | --- | --- |
| 一次应用读取请求 | 从进入读取接口到应用观测到结果的墙钟耗时，单位 ms；另记实际返回字节数与状态 | 不全是设备服务时间，也不保证已读满所需内容 |
| 承载工作的线程 | 在任务窗口内分开看 on-CPU、就绪未运行、阻塞／等待 | 逻辑任务跨线程；线程上的全部活动不都属于它 |
| 一个块设备 | 指定采样区间内全部负载的请求、吞吐、平均延迟与队列统计 | 不直接归属于本进程，更不能归属于某个资源 |
| 一次资源加载任务 | 从业务触发到约定的 Ready 条件成立的墙钟耗时 | 读取返回、上传命令提交、首次可见不是同一个终点 |

设备的平均 `await`、fio 某类请求的 P99、任务到 Ready 的 P99，分母和起止边界都不同。不能把它们相加，也不能把设备一秒平均值当成某个卡顿帧的读取延迟。分位数应注明成功样本数、采样轮次和条件；少量样本里的最高值也不能包装成稳定的尾延迟结论。

这里复用已有机制，不再展开一套底层课程：

- 路径、元数据和缓存的区别，读[文件系统基础]({{< relref "engine-toolchain/storage-io-03-filesystem-path-directory-metadata-page-cache.md" >}})。
- 应用请求与设备请求为何不一一对应，读 [OS I/O 机制]({{< relref "engine-toolchain/storage-io-04-os-io-sync-async-dma-mmap-read-ahead-queue-depth.md" >}})。
- 等待结束与获得执行机会的区别，读[线程调度与等待]({{< relref "performance/game-performance-thread-scheduling-waits.md" >}})；缺页与读盘的区别，读[内存记账]({{< relref "performance/game-performance-memory-accounting.md" >}})。
- 从字节到对象，再到渲染与交互，沿[资源可用链]({{< relref "performance/game-performance-read-does-not-mean-ready.md" >}})定义终点。

## 先把四个工具放回它们真正的位置

如果把这四个工具压成一张判断表，我会先这样记：

| 工具 | 它最擅长回答什么 | 它不适合回答什么 |
| --- | --- | --- |
| `fio` | 指定文件／设备路径、engine、缓存与负载条件下，合成请求的吞吐和延迟 | 游戏关键路径或不受软件栈影响的硬件绝对上限 |
| Linux `sysstat iostat` | 采样窗口内，选定设备的汇总负载、请求粒度、延迟与队列变化 | 具体是哪一个资源、哪一段代码在发 I/O |
| Perfetto | Android 上已采集的应用 marker、线程调度与系统事件如何对应 | 自动还原未打点的加载阶段，或无条件得到全部 I/O 因果 |
| Instruments | Apple 目标上可用的文件事件、CPU 采样与任务 signpost 如何对应 | 用文件活动直接证明物理介质耗时或 GPU 已完成 |

这张表最值钱的地方不是“工具介绍”，而是：

`不要让一个工具回答它根本不该回答的问题。`

比如：

- 拿 `fio` 跑得很快，就说“项目 I/O 没问题”
- 看见 `iostat` 没打满，就说“肯定不是 I/O”
- 在 Perfetto 里看到线程阻塞，就直接认定“底层盘不行”
- 在 Instruments 里看到很多文件操作，就立刻断言“必须合包”

这些判断都太快了。

## 开始测之前，先把实验条件锁死

I/O 分析最容易被污染的，不是工具本身，而是实验条件。

正式开始前，我更建议至少先锁住这几件事：

### 1. 分清冷缓存和热缓存

要明确这次测的是：

- 冷启动第一次进场
- 第二次热命中
- 长时间运行后的重进场

如果这三种情况混在一起，后面任何数据都很难解释。

还要写清“冷”的对象：进程重启只说明应用重启，不能证明 OS 页缓存或设备缓存已冷；第二次快也可能包含对象复用、依赖已就绪等变化。记录缓存准备方法与可验证范围，没有控制住的部分标“未知”，不把“首载”直接改名为“冷盘”。

### 2. 固定触发动作

尽量让每次都触发同一条加载链，比如：

- 首次进入同一个场景
- 同一个角色第一次出现
- 同一个 streaming chunk 进视野

不要一边测一边改内容路径，否则 trace 只会越来越花。

固定构建与资源版本、输入资源集合／内容哈希、读取范围、压缩格式和 Ready 验收条件。对照必须完成等价工作；少读了依赖、取消了部分任务或显示了占位资源，不能算同一次加载变快。

### 3. 固定设备状态

尤其在移动端，要尽量知道当前是：

- 冷机还是热机
- 前后台切过没有
- 是否有下载、同步、录屏这类后台活动

设备型号、OS／文件系统、工具版本、剩余空间、供电和温度条件也随记录保存。一次只改一个待验证因素，重复采样；采集本身可能改变负载，必要时比较开关采集的差异。

### 4. 先定义你到底想证伪什么

更稳的问法通常不是：

`是不是 I/O 慢？`

而是：

- 这是不是设备本身的极限问题
- 还是访问模式问题
- 还是后处理问题
- 还是只有某个平台 / 档位 / 热状态才会爆

只要问题先问准，后面的工具顺序就会清楚很多。

## 把同一加载任务的证据接起来

仅有 `ReadChunk`、`Decompress` 这些名字还不够：两次加载重叠时，你可能把 A 的读取接到了 B 的解压上。建议由资源加载器保留一份任务关联记录，以下字段是设计示例，不是某个引擎的内置接口：

| 字段 | 用途 |
| --- | --- |
| `run_id`、构建／资源版本、输入哈希 | 区分采样轮次与输入，避免把两次运行拼成一条链 |
| `task_id`、父任务与依赖 ID | 从一次业务加载追到子任务；共享依赖保留多个消费者的关联 |
| `request_id`、资源标识、offset、请求／返回字节数 | 标明具体读取及重试；一次任务可有多次读取，不能用文件名代替请求身份 |
| 阶段、时间戳与时钟域、PID／TID | 关联阶段与承载线程；跨进程时显式传播关联 ID |
| 结果状态、错误／取消、trace 文件与配置 | 解释短读、失败和过期结果，并能回到原始证据 |

先给阶段约定名字，再放到同一条任务链里：

```text
LoadBegin(task_id)
  ├─ 应用排队、打开与元数据操作
  ├─ ReadEnter(request_id) → ReadResult(request_id, bytes, status)
  ├─ ConsumeBegin → 解压／反序列化／依赖处理／对象创建
  └─ 渲染提交及所需后续工作 → Ready(task_id, criterion)
```

这是排查模型，不是固定串行调用栈。读取可能同步完成；分块消费、解压和后续读取可以重叠。`ReadResult` 指应用实际观测到读取结果的时刻；如果它在 continuation 内打点，就已经包含恢复执行前的等待。没有额外系统事件时，不能倒推出“设备恰在此刻完成”。只有累计拿到所需字节且状态有效，才能把对应字节标为可消费；失败与取消单列，不混进成功加载耗时。

`Ready` 要约定为对象可用、可交互或首次正确显示中的具体一个条件。若只采到了 GPU 上传命令提交，就记录“已提交”；不要把它填成 GPU 完成或首次显示。子阶段墙钟时间有重叠，不能简单累加来解释总耗时；应找阻止 Ready 推进的依赖和等待。

时间关联也要分精度。应用阶段优先进入同一份 trace；外部日志用单调时钟，并记录与 trace 时钟的同步点／转换关系。不同设备、不同 trace 的时间戳不能直接相减。[Perfetto 的时钟同步文档](https://perfetto.dev/docs/concepts/clock-sync)说明了多时钟域需要显式映射。`iostat` 的采样窗口只能与任务窗口做粗粒度对照，不能因此获得逐请求身份；多层块设备的统计也不能直接相加。

判断时保留三句话：**观察到了什么；它支持哪个假设；还缺哪一项对照。** 比如“任务等待窗口与设备平均延迟上升重叠”支持调查存储争用，但还要确认设备映射、后台负载和该任务的等待对象，才有资格说它拖慢了关键路径。

## `fio`：比较指定条件下的合成 I/O 负载

`fio` 最适合做的，是先回答一个非常基础但很重要的问题：

`这个测试路径在指定 I/O 模式下，吞吐和延迟大概是什么量级？`

它适合检验由真实访问特征引出的假设。结果仍包含文件系统、内核、engine、CPU 和设备状态的影响，不是“裸硬件天花板”；也不必作为每次加载排查的第一步。

### `fio` 最适合什么时候上

通常是你想先知道：

- 指定路径在顺序读负载下能到什么量级
- 小块随机读会不会非常差
- 队列深度拉起来后设备有没有明显改善
- 目标机器对不同访问模式的差异是否支持进一步做设备对照

### `fio` 不适合回答什么

它不适合直接回答：

- 你的游戏线程为什么在某一帧卡住
- 哪个 bundle 或哪个对象在发 I/O
- 为什么读完以后还是卡

因为 `fio` 测的是指定测试负载，不会替游戏执行相同的依赖解析、解压和激活。

### 跑 `fio` 时最重要的一个意识

先决定要比较 direct 路径还是 buffered 路径。fio 的 `direct=1` 请求 non-buffered I/O，通常使用 `O_DIRECT`；平台、文件系统与 engine 支持不同，还需满足对齐条件。它不能清空所有层的缓存，也不会把普通文件测试变成纯硬件测试。若真实应用走 buffered I/O，direct 结果只是另一种条件，不能直接替代应用表现。参数契约见 [fio 官方手册](https://fio.readthedocs.io/en/latest/fio_doc.html#i-o-type)。

### 一组够用的 `fio` 最小实验矩阵

如果只想先建立最小直觉，可以按真实请求特征选择三种候选负载：

1. 顺序读，大块，比如 `128k`
2. 随机读，小块，比如 `4k`
3. 随机读，中等块，比如 `64k`

如果你还怀疑设备是不是特别吃队列深度，再加一组：

4. 同样的随机读，对比 `iodepth=1` 和更高 `iodepth`

下面限定为 **Linux、fio 3.x、支持 direct I/O 的本地普通文件**，使用同步 `psync` engine，深度固定为 1。先在专用测试目录准备一份至少 2 GiB、已经实际写入内容的测试文件，替换 `filename`；不用稀疏文件，不指向原始块设备或生产资源。创建与写入准备不放进读测试，以免把准备开销误算进去。

保存为 `read-matrix.fio`。`stonewall` 让后一项等前一项结束，并分开报告；否则同一 job file 的作业可能并发，测到混合负载。

```ini
[global]
filename=/path/to/fio-test.bin
allow_file_create=0
size=2G
runtime=20
time_based=1
ioengine=psync
iodepth=1
numjobs=1
direct=1
group_reporting=1

[seqread_128k]
rw=read
bs=128k

[randread_4k]
stonewall
rw=randread
bs=4k

[randread_64k]
stonewall
rw=randread
bs=64k
```

在该 Linux 环境中执行：

```bash
fio --version
fio --enghelp
fio --readonly --output-format=json --output=read-matrix.json read-matrix.fio
```

`--readonly` 拒绝写／trim 工作负载，`allow_file_create=0` 让文件不存在时失败；先核对路径、文件大小与本机版本选项，不能把自动建文件当成读取的一部分。direct 不支持或对齐报错时记录条件并调整实验，不悄悄退回 buffered 后继续当作同一组。这里的 `k` 按 fio 默认设置为 KiB，`20` 秒只是教学采样窗口，不是足以覆盖所有设备稳态的保证。参见 [readonly](https://fio.readthedocs.io/en/latest/fio_doc.html#cmdoption-readonly)、[文件创建](https://fio.readthedocs.io/en/latest/fio_doc.html#file-creation)与[作业串行](https://fio.readthedocs.io/en/latest/fio_doc.html#cmdoption-arg-stonewall)。

专门比较队列深度时，另选目标平台支持的异步 engine、固定其他条件。同步 engine 下把 `iodepth` 调高不会得到预期并发；Linux `libaio` 的 buffered 路径也可能达不到目标深度。要核对输出中的实际深度分布，且 fio 深度不等于设备硬件队列深度。见 [fio I/O depth](https://fio.readthedocs.io/en/latest/fio_doc.html#i-o-depth)。

也就是说：

`不要看到自己写了 iodepth=32，就默认设备真的被你喂到了 32。`

### 看 `fio` 输出时，先别贪多，先盯三件事

#### 1. `bw`

它更适合回答：

- 该条件下顺序大读的吞吐量级
- 在当前条件下吞吐是否仍随负载变化

#### 2. `IOPS`

它更适合回答：

- 该条件下每秒完成多少次测试 I/O
- 小随机读是不是天然就弱

#### 3. 延迟，尤其尾延迟

平均值当然有用，  
但如果你关心的是运行时抖动，我更建议看：

- `clat` / `lat` 的定义与显示单位
- 以及更高分位的尾延迟

因为游戏最怕的不是“平均有点慢”，而是：

`偶尔特别慢，而且刚好发生在关键时刻。`

fio 的 `clat` 是完成延迟；异步 engine 下到 fio 收割完成为止，`lat` 还包含提交延迟。它们都不是游戏到 Ready 的耗时。将 engine、块大小、实际深度、请求数、运行时长和分位数一起保存，跨配置比较前先确认口径，见 [fio 输出说明](https://fio.readthedocs.io/en/latest/fio_doc.html#interpreting-the-output)。

### 怎么用 `fio` 结果做第一轮判断

如果你看到：

- 顺序读很好
- 但 `4k randread` 很差

它支持的判断是：

`在这组测试条件下，小块随机负载比大块顺序负载更受限制。`

这不是随机性单因素的结论，因为块大小也变了。若要分离原因，就固定块大小只改访问顺序，再与游戏的实际请求分布比较。

如果你看到：

- `iodepth=1` 很一般
- 队列拉高后明显变好

它支持的判断是：

`增加在途请求提高了这组负载的吞吐。`

还要同时看延迟、内存与关键请求的完成时间；吞吐提高不保证首屏更快，不能直接把游戏并发设成压测峰值对应的深度。

如果你看到：

- 顺序和随机都很差

那就要先怀疑：

- 设备档位本身就低
- 当前环境有争用
- 或者你的测试路径本身不干净

如果你看到：

- `fio` 跑得很好
- 但游戏里还是卡

那也别急着开心。  
这通常只能说明：

`这组测试负载表现好，尚不能排除游戏实际路径中的存储、缓存或后处理问题。`

## `iostat`：看真实运行窗口中的设备汇总负载

`iostat` 适合在真实复现窗口里回答：

`我真实复现问题的时候，设备到底忙不忙，排队重不重，请求长什么样。`

### 最常用的一条命令

以下是 **Linux sysstat 的 iostat**，不是 macOS 上同名工具的参数约定。先确认已安装 sysstat、本机 `iostat -V`／man page 与内核统计可用，再在复现前启动：

```bash
iostat -x -y -t -k 1 30
```

这些参数分别约定：

- `-x`：看 extended stats
- `-y`：跳过“开机以来平均值”那一屏，只看当前采样窗口
- `-t`：输出报告时间；`-k`：吞吐采用 KiB/s；`1 30`：每秒一份，共 30 份区间报告

`iostat` 手册也明确写了这一点：默认第一屏是 since boot，`-y` 才会把它省掉。  
如果不加 `-y`，很多人第一眼就会被旧历史值带偏。

字段与选项见 [sysstat 官方 iostat 手册](https://github.com/sysstat/sysstat/blob/master/man/iostat.in)。保存原始表头、版本、时区和采样起止；报告时间不能替代与应用单调时钟的对齐。先确认资源路径对应哪个挂载点、分区与底层设备，容器、device mapper、虚拟盘或远端文件不能只凭设备名猜。拿不到目标设备统计时换证据来源，不用宿主机／另一块盘的数字顶替。

### 真正值得盯的列，不需要太多

不同 distro / kernel / `sysstat` 版本，列名会有一点变化。  
但如果只想做判断，先盯下面这些就够了：

- `r/s`、`w/s`
- `rkB/s`、`wkB/s` 或对应单位列
- `areq-sz`
- `await`
- `aqu-sz`
- `%util`

### 这些列各自更像在回答什么

#### `r/s` / `w/s`

看的是：

`所选设备每秒完成多少个合并后的读／写请求。`

如果请求数很高，但吞吐不大，  
通常就要怀疑：

`是不是很多小请求在 storm。`

#### `areq-sz`

看的是：

`发给设备的 I/O 请求平均有多大，当前手册单位为 KiB。`

旧版 `avgrq-sz` 以扇区计，不能沿用数值直接对比。这个平均粒度不是应用每次 `Read` 的大小，也不是文件平均大小；请求拆分、合并与其他负载都会影响它。

#### `await`

`iostat` 手册对 `await` 的定义很清楚：  
它是 request 被服务的平均时间，里面既包括排队时间，也包括真正被设备处理的时间。

也就是说：

`await` 高，不一定只是设备慢，也可能是队列先堆起来了。

#### `aqu-sz`

它更接近在看：

`采样窗口内发给设备的请求平均队列长度；不是某时刻只等待、尚未服务的请求数。`

它和 `await` 一起升高支持调查该设备负载与延迟，但不自动说明游戏任务正在等这块设备。

#### `%util`

很多人会把它直接理解成“盘满了”。  
这也不完全对。

`iostat` 手册里对 `%util` 的解释是：  
设备在采样窗口里有 I/O request 被发给它的时间占比。  
而它也专门提醒了：对可以并行服务请求的现代 SSD / RAID，这个数字并不总是准确代表极限。

所以：

- 在串行服务请求的设备上，接近 100% 可提示饱和
- 在现代并行 SSD 上，它更像一个参考信号，不是绝对上限

### `iostat` 最容易帮你看出来的三种图景

#### 图景一：设备延迟与队列一起上升

你会看到：

- `await` 高
- `aqu-sz` 高
- `%util` 很高

这时更像：

`所选设备承受了更重的在途负载或服务变慢，需要确认与任务关键路径的关系。`

#### 图景二：小请求 storm

你会看到：

- `r/s` 很高
- 吞吐不一定高
- `areq-sz` 很小

这时更像：

`设备层完成了许多小请求，需要再查它们的进程、文件与发起路径。`

不能据此断言游戏打开了很多小文件；一个大文件的随机读或后台程序也可能产生这种统计。

#### 图景三：看起来像 I/O，但设备并不忙

你会看到：

- 游戏卡
- 但 `%util` 不高
- `await` 也不高

可以继续检查这些候选方向：

- CPU 计算、同步点或主线程收口是否阻止任务继续
- I/O 在这次任务中是否位于关键路径

这些仍是候选方向。低平均值也可能掩盖短突发、串行依赖和单次长尾，或说明看错了设备；一秒采样不足以排除某个短帧内的 I/O 等待。`await` 是平均值，不能从这张表推算逐请求 P99。

### 一个特别容易踩坑的地方：别把 `%iowait` 当磁盘利用率

`iostat` 手册对 `%iowait` 的解释是：

`CPU 空闲、同时系统存在 outstanding disk I/O request 的时间占比。`

所以它说的是 CPU 状态，不是设备状态。  
它不能直接替代 `%util`、`await` 或队列指标。

## Android：用 Perfetto 接任务、线程与系统时间线

如果问题是“哪一帧在等什么、读取结果之后为什么仍未 Ready”，可以直接从时间线开始，不要求先跑 fio 或拿到 iostat。

Perfetto 在 Android 上最有价值的地方，就是它能把：

- app 自己的切片
- 线程调度
- CPU 状态
- 系统 trace

收进同一张时间图里。

前提是所需数据源确实启用并成功采集；“能打开 trace”不等于拥有完整调度、文件或块 I/O 事件。

### Perfetto 最适合回答什么

它最擅长回答的是：

- 这一帧或这一段加载期里，线程到底在干什么
- 主线程是在等 I/O、等 future，还是在自己做解压 / 反序列化
- 有相应 marker／事件时，worker 在什么时候进入读取、观测到结果
- 所需字节有效返回以后，任务何时达到 Ready

### 最低成本的起步方式

按 [Perfetto 官方系统采集教程](https://perfetto.dev/docs/getting-started/system-tracing)，UI 录制起步条件是 Android 11（R）及以上、USB 连接、开发者选项与 USB 调试，并完成设备授权。然后：

1. 打开 [Perfetto UI](https://ui.perfetto.dev)，进入 Record New Trace，确认目标设备。
2. 按问题启用 CPU 调度／频率与应用 ATrace，指定本应用；先检查任务 marker 能被采到。
3. 在覆盖触发前后的一段短窗口里只做固定动作，保存 trace、配置和本轮 `run_id`。

脚本化时优先复用官方 `record_android_trace` 与显式配置，记录脚本版本、包名和可用数据源。官方对旧系统另有说明：Android 9／10 可能需要启用 tracing service，早于 Android 9 的设备不能直接套用 on-device perfetto 命令；配置路径和拉取权限也有版本差异。具体条件见[高级 Android 采集](https://perfetto.dev/docs/learning-more/android)。不要假定所有零售机都能采到全部内核事件，也不要求为每次定位先取得 root。

### 真正让 Perfetto 变得好用的一步：给加载阶段打 marker

如果你能控制 Android app 或 native 层，  
我非常建议给关键阶段补 trace marker，比如：

- `RequestBundle`
- `ReadChunk`
- `Decompress`
- `Deserialize`
- `UploadTexture`

应用／原生层可使用 `android.os.Trace` 或 NDK `ATrace_*`。同步 section 必须在同一线程正确嵌套、成对结束；不能在提交线程 begin，再在完成线程 end。同一次异步加载跨线程时，改用异步事件配对，begin/end 使用相同名称与 cookie，并避免与进程内其他在途事件的 cookie 冲突。Java `Trace.beginSection` 从 API 18 可用，`beginAsyncSection` 从 API 29 可用；其他接口按 SDK／NDK 版本检查，不能把这些版本视为所有 Trace API 的统一门槛。见 [Android Trace API](https://developer.android.com/reference/android/os/Trace)与 [Perfetto ATrace 插桩说明](https://perfetto.dev/docs/getting-started/atrace)。

把 cookie／事件参数映射回前文的 `task_id`／`request_id`，阶段名只表达工作类型。Unity、Unreal 或自研加载器需核对实际打点是否进入本次系统 trace；引擎 Profiler 里的同名 marker 不自动构成跨工具关联。

因为只要没有 marker，  
你看到的就更像“线程在忙”，  
但有了 marker，才会更容易回答：

`它到底在忙哪一笔账。`

### 在 Perfetto 里，我最先会看什么

#### 1. 主线程 / 渲染线程是不是在等

先区分主线程是阻塞、就绪未运行，还是在执行未标记代码。应用切片的空白本身不说明原因。再沿同一任务查等待对象和依赖生产者：worker 同时读文件或解压，只是时间相关；确认主线程确实在等它，才接得上因果。状态解释复用前文链接的线程调度篇。

#### 2. 读什么时候结束，CPU 什么时候才真正放过你

如果同一任务的 `ReadResult` 已出现，但 Ready 尚未到来，就继续核对：

- 解压
- 反序列化
- 依赖解析
- 激活

这些阶段可能是下一步调查方向，但应先排除尚未完成的其他读取和依赖。只有一条读取结束，不能代表整次任务的 I/O 全部结束。

#### 3. 问题是不是只在某种状态下才出现

比如：

- 冷机没事，热机后开始糟
- 冷缓存第一次差，第二次明显好
- 前后台切回来以后路径变样

在输入、版本与窗口相同的前提下比较各阶段，再判断差异来自哪里；仅凭热机后慢，不能把原因限定为闪存。

### Perfetto 最常帮你排除掉的误判

一个值得检验的情况是：同一任务在读取结果之后仍有较长 CPU 阶段，并且该阶段阻止了 Ready。

这时候优化方向就会完全变掉：

- 针对解压、反序列化、依赖收口和主线程同步设计单因素对照
- 检查改动后 Ready 是否提前，以及帧耗时和内存峰值是否出现代价

先检查采集是否覆盖完整任务、marker 是否配对、必要数据源是否存在，以及是否丢事件或被缓冲区覆盖。Perfetto 的[缓冲与丢失说明](https://perfetto.dev/docs/concepts/buffers)给出了诊断方式；有缺口时，“没看到事件”不能写成“没有发生”。

## Apple：用 Instruments 对照文件活动与任务阶段

在 Apple 生态里，我更建议把 Instruments 理解成：

`看 app 自己到底在怎样碰文件系统，以及这些文件活动是不是刚好和 CPU 卡顿重叠。`

### Instruments 最适合从哪几个模板切

不同 Xcode 版本、目标平台和模板命名会有些差异。  
按需要选择文件活动、CPU 与任务标记相关 instrument，不要求一次全开：

- `File Activity`
- `Time Profiler`
- `os_signpost` 或当前工具中的对应任务区间视图

Apple 归档的 [Mac 应用 I/O 指南（2016）](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/MinimizingIO.html)列出了 `File Activity` 的 open／close／stat、`Reads/Writes` 的字节读写、`File Attributes` 的属性修改和 `Directory I/O` 的建目录／链接／移动等活动。它支持这些分类的解释，不保证当前 Xcode、iOS 或其他目标拥有同名模板及相同覆盖。

这对定位“小文件 storm”和“名字 / 目录 / 属性操作过多”特别有用。

实际采集前确认 Xcode／Instruments、OS、目标真机或模拟器、应用构建配置和附加权限，先录短 trace 验证需要的事件与符号。真机缺少某项 instrument 时，保留已获得的应用阶段证据，并记录缺口；模拟器的文件路径与宿主机存储表现不能作为手机闪存实测。

用 signpost 标出本轮任务和阶段。多个同名区间可能同时在途，需要独立 signpost ID，并将它映射到应用任务记录；使用 `OSSignposter` 时将 begin 返回的 interval state 传给对应 end，不能按“时间上最近”配对。接口可用性随目标 SDK／OS 检查，见 [Apple Recording Performance Data](https://developer.apple.com/documentation/os/recording-performance-data)与 [beginInterval](https://developer.apple.com/documentation/os/ossignposter/begininterval(_:id:))。

### 我在 Instruments 里最先看什么

#### 1. `open / close / stat` 是不是在狂刷

如果你看到：

- bytes 并不夸张
- 但 file open / close / stat 非常多

那通常更像：

`该窗口文件事务很多，值得核对同一任务的路径、调用来源和耗时。`

计数多不等于关键路径成本高；先确认归属和影响，再比较减少重复打开或改变资源布局的效果。

#### 2. `Directory I/O` 是不是异常多

先看工具实际记录的事件类型。归档指南中的 Directory I/O 包括建目录、链接与移动，不能直接将其计数解释成路径查找次数；File Attributes 的修改记录也不能替代所有元数据读取。要调查查找成本，还需核对相关调用、路径、缓存条件和时长。

这和前面讲的路径解析、目录项和元数据那一层正好能对上。

#### 3. `Reads/Writes` 和 `Time Profiler` 的时间关系

最值钱的不是单看 file activity，  
而是把它和 `Time Profiler` 的 CPU 时间线一起看。

在同一任务区间内对照文件事件、signpost 和 CPU 栈：若所需字节已有效返回，后处理标记仍持续，且该阶段延迟了 Ready，才支持调查后处理。文件活动没有出现也可能是缓存路径、采集范围或事件缺失，不能单凭图上空白宣告 I/O 完成。

Time Profiler 是 CPU 调用栈采样，不能独自精确给出每次函数调用的起止和次数；阶段墙钟耗时由任务区间测量，需要分析等待时另取调度证据。参见 [Apple Instruments 教程：执行次数与采样边界](https://developer.apple.com/tutorials/instruments/determining-execution-frequency)。

### Instruments 最适合帮你确认什么

它特别适合帮你确认：

- 问题是不是“大量独立文件事务”
- 是不是目录和属性操作被低估了
- 读取行为是不是过碎
- app 卡顿是不是主要发生在文件活动之后

这些都是需要关联与对照的问题；建立固定输入的 baseline，改变一项因素后复测，而不是把看到的计数直接翻译为优化结论。

## 按问题选择入口，再决定需要补哪层证据

工具次序取决于当前缺什么证据。Android 与 Apple 的时间线走各自路径；没有必要在一次排查中凑齐四个工具。

| 当前问题 | 首先取得的证据 | 下一步何时补工具 |
| --- | --- | --- |
| 某帧卡住，尚不知道在读、算还是等 | 同一任务的阶段、Ready 与线程状态；Android 用 Perfetto，Apple 用可用的 Instruments 组合 | 确认等待涉及存储后，再补设备／文件证据 |
| 读取窗口是否受到设备争用 | Linux 上核对目标设备映射，用 iostat 对照采样窗口与后台负载 | 需要归属到进程、文件或请求时补时间线；iostat 本身不能完成归属 |
| 哪些文件事务过多、请求是否零碎 | 应用请求记录与可用文件事件，先定位路径、资源和调用来源 | 想检验对应访问模式的敏感性时，再设计 fio 负载；设备平均粒度不能替代应用记录 |
| 指定块大小／深度／缓存路径差异多大 | 隔离环境中的 fio 对照，记录路径、engine 与实际深度 | 结论回到游戏的同一任务复测，不能用压测吞吐代替 Ready |
| 首次慢、热后慢或仅某档设备慢 | 固定输入，分开应用缓存、OS 缓存、温度、频率与后台状态 | 根据变化发生的阶段补文件、调度、CPU 或设备证据，不凭现象指定根因 |

## 把观察变成可验证的修改，而不是套结论

下面是排查建议，不是本项目已经获得的实测结论。

| 观察 | 仍需补的关联或反证 | 可以尝试的对照 |
| --- | --- | --- |
| fio 小随机负载较弱，复现时设备延迟也升高 | 两者负载条件是否接近；该任务是否真的等待该设备；是否有其他进程争用 | 保持输出一致，只改变局部性／请求组织，比较 Ready 与尾延迟 |
| 设备层小请求多 | 请求属于谁，来自一个文件还是多个文件；文件事务是否占关键路径 | 减少重复打开或重组 chunk，连同读放大、解压量和更新粒度一起检查 |
| 读取结果之后 CPU 阶段很长 | 所需读取是否都结束；CPU 栈是否属于本任务；是否还有依赖与等待 | 只调整已确认的后处理阶段，复测帧耗时、Ready 与内存峰值 |
| 热机或某机型恶化 | CPU／GPU 频率、内存压力、缓存、后台负载与存储条件分别怎样变化 | 固定输入分组重测；若尝试提前加载或并发调整，同时记录多读数据和内存预算 |

一次修改成立，至少要能回答：完成了相同内容吗，目标任务是否更早 Ready，关键帧是否改善，是否把代价转给了内存、后台带宽或后续任务。失败、取消和退化路径也要保留，不能只挑成功样本。

值得沉淀进生产管线的，是稳定的任务关联字段、可重放输入、采集配置、设备条件和复测口径。把已确认问题连到相应加载阶段、资源／代码责任位置，再决定形成资源布局约束、运行时预算、工具检查或人工评审项；阈值应由目标设备基线决定。这是工程建议，本文没有已验证的自动化检测效果或项目收益。

## 这一篇最该带走的结论

`I/O 分析真正值钱的，不是“会不会用 fio / iostat / Perfetto / Instruments”，而是知道每个工具只应该回答哪一层。`

沿同一任务把证据接起来，才有依据区分：

- 是指定条件下的设备路径限制
- 是访问模式太碎
- 是文件系统和缓存行为
- 还是 I/O 后面的那条加载链

最后用等价输入和同一 Ready 条件复测，才能判断改动是否真正帮助了玩家等待的那条路径。
