> **读这篇之前**：先用[线程调度与等待唤醒]({{< relref "performance/game-performance-thread-scheduling-waits.md" >}})区分运行、就绪与阻塞，再用[虚拟内存与游戏内存预算]({{< relref "performance/game-performance-memory-accounting.md" >}})理解映射、驻留与统计口径。本文以本地普通文件的缓存读取为主，分别用 Windows、Linux 与 .NET 的公开资料说明边界；不是某个 Unity 版本的完整调用栈，也没有设备性能实测。

> 如果只用一句话概括这篇文章，我会这样说：`ReadAsync`、`mmap`、DMA、预读和队列深度，不是几组互不相关的名词，它们共同决定了“你的读取请求是怎样穿过操作系统到达设备、又怎样回到内存和应用线程”的。

前两篇我们已经把两层底图立住了：

- 底层设备怕什么
- 文件系统会在哪些地方替你先结账

再往下走，就会来到很多人最容易混的一层：

`操作系统到底是怎样处理一次 I/O 请求的？`

尤其是当应用层写的是：

```csharp
using var stream = File.OpenRead(path);
int bytesRead = await stream.ReadAsync(buffer, 0, buffer.Length);
// 这里只展示一次读取；后续只能消费 buffer 中前 bytesRead 个字节。
```

`OpenRead` 打开文件，`ReadAsync` 才请求读取字节。这段代码没有证明底层使用了内核异步 I/O。一次读取也不保证填满缓冲区；完整读取需要累计返回长度，并处理 EOF、异常和取消，不能把短读后的剩余区域当有效数据。[FileStream.ReadAsync 的返回值约定](https://learn.microsoft.com/en-us/dotnet/api/system.io.filestream.readasync)

很多讨论会把中间这一大段都省略掉，  
最后只剩一个过度简化的直觉：

`CPU 去硬盘里把数据读到了内存。`

这句话太粗了。

先把它看成一张有分支的教学模型：

```text
应用层 API
-> 运行时 / native 封装
   -> 运行时缓冲已有数据：可能直接返回
   -> 需要 OS 读取：系统调用进入内核
      -> 所需数据已在文件缓存中：从缓存满足
      -> 需要设备取数：文件系统 / 块层 -> 驱动 / 控制器
         -> 设备传输（例如 DMA）-> 内核处理完成
-> 读取结果交给应用（实际字节数或错误）
-> 按完成方式继续执行，或等待线程 / continuation 获得执行机会
-> 应用按资源格式继续解压、解析、创建等后处理
```

运行时缓冲与 OS 文件缓存是两层不同的缓存；并非每次高级 API 调用都会进入内核，也并非每次系统调用都会访问设备。Windows 的默认文件缓存路径见 [File Caching](https://learn.microsoft.com/en-us/windows/win32/fileio/file-caching)。直接 I/O、网络文件系统和特殊文件另有条件，不能把这张图当所有平台的固定流水线。

这篇文章要做的，就是把这条链拆开。

前一篇已经把路径、目录项、元数据和页缓存的“文件系统账”单独立住了。  
所以这一篇不再展开名字查找和目录结构，重点看读取怎样经过缓存、设备与完成通知，并回到应用的等待和预算决策。

## 第一层：一次 `Read` 到底经过了什么

沿着上面的缓存读取模型，逐步看每一层在承担什么；缓存命中时会跳过设备路径。

### 1. 应用层发起请求

比如：

- `FileStream.Read`
- `FileStream.ReadAsync`
- 引擎自己的异步加载接口

这时你在用户态表达的是：

`我要这个文件的某一段字节。`

打开文件是前置步骤，也可能产生元数据访问；引擎加载 API 还可能拆成多次读取和后处理，不能与一次 `Read` 等同。

### 2. 运行时进入系统调用

运行时自己的缓冲若能满足请求，可以不发起新的读取系统调用。例如 .NET 6 的 `FileStream` 缓冲正是为了减少这类调用；这是该运行时的实现说明，不能直接代替 Unity 的 Mono／IL2CPP 路径。[.NET 6 File I/O 说明](https://devblogs.microsoft.com/dotnet/file-io-improvements-in-dotnet-6/)

需要进入 OS 时，关键动作是：

- 从用户态进入内核态
- 把“读哪个文件、从哪读、多大、放到哪”这些参数交给系统

用户态进入内核态不等于切换到了另一个线程。是否阻塞、是否被调度出去，是另一层问题。

### 3. 内核先看页缓存

这是最容易被漏掉的一步。  
操作系统通常不会先问设备，而会先问：

`这段文件页是不是已经在内存里？`

如果已经在：

- 这次读取可能主要是内存复制和状态管理
- 甚至异步接口也可能很快就完成

如果所需数据还没就绪，可能需要发起读取，也可能等待已经在途的读取；不能按一次缓存未命中就计作一个新的设备命令。

所以“第二次突然变快”可以先检查缓存，但只凭耗时不能证明究竟命中了运行时缓冲、OS 缓存还是别的缓存。

### 4. 内核把未命中的请求交给块层和驱动

在确实需要从本地块设备取数的路径上，文件系统会组织底层请求。

这一步通常会涉及：

- 计算需要哪些块或页
- 合并或拆分请求
- 排队
- 交给块层和设备驱动

到这里，你的“读文件”已经不再是抽象 API，  
而是变成了面向设备的请求。Linux 的 blk-mq 还区分软件暂存队列和硬件派发队列，并可合并相邻请求；应用请求与块层请求并非一一对应。[Linux blk-mq 文档](https://docs.kernel.org/block/blk-mq.html)

### 5. 控制器和设备真正去取数据

这时设备端会按自己的物理特性工作：

- HDD 可能在寻道和等待转盘位置
- SSD / UFS 可能在做地址翻译和 flash 页读取
- NVMe 盘可能在并发处理多个命令

### 6. DMA 把数据搬回内存

真正搬字节的那部分，通常不是 CPU 一字节一字节去 copy，  
而是设备通过 DMA 把数据写进内存中的目标缓冲区或页缓存页。

这描述的是设备与内存之间的传输；缓存读取把数据交给用户缓冲区时仍可能需要 CPU 复制。第三层会再拆开这两段。

### 7. 内核收到完成信号

设备请求成功或失败后，系统会通过中断、轮询等完成机制获知结果：

`这个设备请求有结果了。`

然后它会：

- 更新状态
- 成功时使相应数据可供使用，失败时传递错误
- 唤醒同步等待线程
- 或者触发异步完成路径

底层命令完成、应用读取完成、线程真正恢复执行是不同的时刻。唤醒只让等待线程有机会被调度；应用还必须检查实际读取长度和错误。Linux `read` 也允许成功返回少于请求的字节数。[read(2)](https://man7.org/linux/man-pages/man2/read.2.html)

### 8. 应用层继续往后走

这里很多人会误以为“读完了”。  
但对游戏来说，这一步往往只代表：

`字节到内存了。`

后面通常还有：

- 解压
- 反序列化
- 依赖解析
- 运行时对象创建
- GPU 上传

所以 I/O 机制讲清楚之后，你会更容易理解：

`为什么读完不等于 ready。`

## 第二层：同步 I/O 和异步 I/O 到底差在哪

很多讨论里，“同步 / 异步”被说得像“慢 / 快”。  
这其实是最容易带偏判断的地方。

更准确的区别是：

- 同步 I/O：调用返回时给出读取结果；等待期间这条调用栈不能继续。线程可能正在执行内核工作，也可能阻塞，不能把整段耗时都算成 CPU 忙碌。
- 异步 I/O：允许操作尚未完成时返回，之后用回调、事件、future、task 或完成队列取得结果；也可能在调用期间已经完成。

所以“同步 / 异步”首先描述的是：

`调用方怎样等待结果。`

它不是在说：

- 底层设备一定怎样工作
- 有没有页缓存
- 有没有 DMA
- 数据会不会被预读

### 一个最容易踩坑的误解

❌ 误解：`ReadAsync` 就意味着“磁盘会在后台慢慢读”。  
✅ 更准确的说法：异步接口描述结果怎样交付，不说明数据来自哪里，也不保证没有线程阻塞。

这里至少有三层，不能混成一个“异步”：

| 层次 | 要核对什么 |
| --- | --- |
| 应用的 `await` | 等待未完成任务时可挂起异步方法；任务已完成时可以继续执行，后续代码在哪个线程还要看运行时与上下文 |
| 运行时的文件接口 | 使用内核异步请求，还是把同步读取放到工作线程；句柄打开选项和运行时版本都会影响实现 |
| OS 的完成机制 | 请求是否待完成、何时报告结果、怎样通知；不由方法名中的 `Async` 决定 |

例如微软对 **.NET 6 的 Unix 文件 I/O 实现**说明：异步文件操作会将同步操作调度到线程池。这里有线程在等待，只是调用方不必占着原线程等。这个例子不表示 Unix 没有其他异步 I/O 接口，也不证明 Unity 使用同一路径。[.NET 6 的实现说明](https://devblogs.microsoft.com/dotnet/file-io-improvements-in-dotnet-6/)

Windows 的异步文件句柄也不保证每次调用立即返回；官方明确保留同步表现的情形。因此需要分别测调用本身的耗时与之后的等待。[Windows 同步与异步 I/O](https://learn.microsoft.com/en-us/windows/win32/fileio/synchronous-and-asynchronous-i-o)

### 为什么异步 I/O 仍然可能卡你

因为它提供了不同的完成方式，却不保证：

- 打开文件、提交请求和缓冲管理没有同步成本
- 工作线程或完成队列没有排队
- 后续解析不在主线程
- continuation 不回到关键线程
- 依赖收口不在关键帧
- 请求粒度已经合理

所以即使观察到下面的现象，也不能直接归因为磁盘：

- 资源“异步读”了
- 但某一帧还是很卡

需要继续区分提交、等待和恢复执行，再检查：

- 主线程 continuation
- 解压
- 反序列化
- 激活和 GPU 上传

还有一个容易漏掉的代价是生命周期：请求没完成，缓冲区就不能提前复用。以 Windows 为例，`ReadFile` 要求缓冲区保持有效直至完成；`CancelIoEx` 只是请求取消，不等待操作完成，取消也可能与正常完成竞争。工程上应在确认最终结果后释放或归还缓冲区，并丢弃已经过期的资源结果。[ReadFile](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-readfile)、[CancelIoEx](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-cancelioex)

## 第三层：DMA 为什么重要

DMA 让设备可以在驱动安排后直接访问内存，减少 CPU 亲自执行设备数据搬运的需要；它不保证整条读取链没有复制，也不能单凭是否使用 DMA 推断延迟。

你可以先把 DMA 理解成：

`设备在 CPU 设置好规则后，自己把一段数据搬到内存指定区域。`

CPU 在这件事里主要负责的是：

- 建立请求
- 告诉设备目标地址和长度
- 处理完成通知
- 在数据回来后继续做高层逻辑

这里的“目标地址”不是把应用中的指针原样交给设备。Linux DMA 文档区分 CPU 虚拟地址、物理地址和设备使用的 DMA 地址；IOMMU 等机制可以在设备地址与物理内存之间建立映射。[Linux DMA 地址说明](https://docs.kernel.org/core-api/dma-api-howto.html)

再看两处仍可能发生的复制：

- 普通缓存读取可能先把数据放入 OS 缓存，再复制到应用缓冲区。
- 如果设备不能直接访问目标内存，Linux 的 SWIOTLB 可以使用中转缓冲区，再由 CPU 在中转与目标之间复制；不是所有设备都需要这一步。[DMA 与 SWIOTLB](https://docs.kernel.org/core-api/swiotlb.html)

### 这就是为什么“CPU 去硬盘里读数据”不够准确

更准确的说法通常是：

- CPU 发起并描述请求
- 操作系统和驱动安排请求
- 设备把数据 DMA 到内存
- CPU 再处理后续逻辑

这层理解很重要，但不能把 DMA 完成当成“OS 工作结束、应用开始解析”的分界线。完成处理、可能的复制、线程调度和应用队列都还会产生时间。排查时要沿实际记录区分设备服务、完成交付与后处理，不能只看一个读请求总耗时。

## 第四层：`mmap` 到底在帮你做什么

`mmap` 很容易被说成“更底层、更快”的黑科技。  
这也不精确。

更准确地说，`mmap` 做的是：

`把文件内容映射进进程虚拟地址空间，让程序像访问内存一样访问文件页。`

它的关键影响有两点：

- 程序不一定要先显式 `read` 到独立用户缓冲区
- 访问尚未建立有效页映射的地址时，可能触发缺页异常；文件页若已在缓存中，可以建立映射而不读取设备，需要取数时才进一步走 I/O

缺页异常不等于程序出错，也不等于一定访问磁盘；已有映射的页被回收后，后续访问仍可能再次付出缺页成本。Linux 的普通文件映射与缓存读取共享页缓存这一层，建立映射不代表整份文件已驻留。[Linux 内存概念与页缓存](https://docs.kernel.org/admin-guide/mm/concepts.html)

### `mmap` 什么时候很有吸引力

通常是在这些场景里：

- 大块只读数据
- 结构清晰、可直接解析的数据布局
- 需要随机访问文件内部不同区域
- 希望少一层显式复制和缓冲管理

这也是为什么一些大数据结构、数据库、或可直接映射的运行时文件格式会偏爱这条路。

### 但 `mmap` 不是默认更稳

它的代价也很明确：

- 第一次触碰页时，页错误可能发生在你最不想卡的线程上
- 必须保证所有访问结束后才解除映射，并管理文件版本和有效范围
- 如果文件本身还要解压、解密或二次解析，它就不一定适合直接映射

例如 Linux 明确规定，访问超出映射文件末尾的整页可能产生 `SIGBUS`；运行中截短文件尤其需要处理这类风险。只读映射也不能替代格式、偏移和长度校验。[mmap(2)](https://man7.org/linux/man-pages/man2/mmap.2.html)

所以 `mmap` 更像：

`把文件页接到虚拟地址访问上，让部分读取成本在访问页面时发生。`

它可以省去“复制到独立用户缓冲区”这一环，但不是端到端零复制：解压、解密、对象构建和 GPU 上传仍要分别核对。选择它的理由应是文件布局和访问方式合适，并且能接受缺页与寿命管理的代价。

## 第五层：Read-Ahead 怎样用额外读取换取更少等待

预读的核心直觉很简单：

如果系统发现你在顺序读文件，它就会猜：

`你大概率还会继续往后读。`

于是系统的预读策略可能提前把后面的页读进来；具体窗口与触发条件依实现而定，不是每次顺序读都有相同效果。

这件事的价值非常高，因为一旦猜对了：

- 下一次读可能直接命中页缓存
- 有机会以较大的连续逻辑范围组织读取
- 请求更容易被合并

### 这也是为什么顺序访问特别“吃系统优化”

因为顺序访问天然给了操作系统三个信号：

- 访问是可预测的
- 相邻数据很快会被用到
- 现在多读一点，大概率不会浪费

但“装在同一个大包里”不等于程序真的按相邻偏移访问，文件逻辑相邻也不能直接证明设备上的物理连续。先看实际的偏移、长度和访问顺序，再判断是否有局部性。

所以当程序的访问模式是：

- 文件跳来跳去
- 每个只读一点
- 没有清晰线性趋势

自动顺序预读就未必能有效预测。若应用提前知道将用到哪些区域，仍可按具体平台提示访问范围；例如 Linux 的 `posix_fadvise` 提供访问模式与 `WILLNEED` 提示，但提示不是完成保证，内核也可根据内存压力减少预取量。[posix_fadvise(2)](https://man7.org/linux/man-pages/man2/posix_fadvise.2.html)

预读猜错时，会消耗读取带宽和缓存容量，还可能挤掉近期需要的页。工程上应限制预取窗口，并观察提前读入的内容有多少在有效期内被使用；不能只报告预读后的热缓存速度，而不算额外流量与内存压力。

## 第六层：队列深度为什么常常决定“理论性能”和“项目体验”的落差

讨论队列深度之前，先说清楚看的是哪一层：

| 观测层 | 计数对象 | 为什么不能直接换算 |
| --- | --- | --- |
| 应用 | 已发起、尚未完成的读取操作 | 可能还在运行时排队，也可能由缓存满足 |
| OS 块层 | 正在排队或处理的块请求，依工具口径区分 | 文件读取可能拆分、合并或带出预读，还混有其他请求来源 |
| 设备命令队列 | 已提交但未完成的设备命令，需说明单队列还是聚合 | 取决于驱动派发、设备资源和其他负载 |

Linux blk-mq 的软件队列、硬件派发队列与设备完成机制说明了这些中间层。因此，应用的并发数是可以控制的输入，设备队列深度则要在相应层观测。[blk-mq 队列机制](https://docs.kernel.org/block/blk-mq.html)

它为什么重要？

因为很多现代存储设备，尤其是 NVMe，不是靠“单个请求特别神奇”取胜，  
而是靠：

- 控制器能并行处理很多请求
- 协议能承载更深的队列
- 设备可以在队列里调度和重排

### 串行小读取为什么可能限制吞吐

如果你的程序总是：

```text
发一个 32 KB 读
等它回来
再发下一个
```

这只能说明这段逻辑同时至多有一个应用读取尚未完成，不能推出设备 `QD=1`：缓存命中可能不发设备请求，预读或拆分可能产生更多请求，其他线程与进程也可能正在访问设备。

如果实际观测确认设备需要更多并行请求才能提高吞吐，逐个等待的小读取才是候选限制。反过来，低延迟需求本来就可能只需少量在途请求；不能用没达到宣传峰值证明加载设计有问题。

### 但队列深度也不是越高越好

在设备或后处理已经接近饱和时继续加请求，可能带来：

- 更多内存占用
- 更复杂的调度
- 更大的尾延迟波动
- 碎访问 storm 被一次性放大

队列也可以给调度器重排的机会，所以延迟并不是随深度单调恶化；实际拐点要按负载测。游戏关心的是关键资源多久可用、较慢请求的等待和帧时间，而不只是总 MB/s。

应用侧建议同时限制**在途请求数、尚未释放的缓冲字节数和后处理队列长度**。读取已经完成但还在等解压的缓冲也要算入预算；只限制“正在读”的数量，不能阻止后处理积压。相关占用口径接[游戏内存预算]({{< relref "performance/game-performance-memory-accounting.md" >}})，不要再把进程驻留与系统文件缓存直接相加。

## 把这几层重新串成一条“从 C# 到资源可用”的链

如果把前面所有东西收成一条更接近项目排查的图，可以这样看：

```text
资源请求与依赖规划
-> 打开文件 / 取得句柄（若未打开）
-> 一次或多次读取：运行时缓冲 / OS 缓存 / 设备路径
-> 收到每次读取的结果并处理长度、错误与取消
-> 解压、解析、依赖准备、对象创建等后处理
-> 需要的主线程提交 / GPU 上传与同步
-> 满足该资源约定的可用条件
```

这是排查阶段图，不是 `AssetBundle.LoadFromFileAsync` 的固定内部顺序；不同格式和引擎会合并、拆分或交叠阶段。资源可用的定义接[读盘完成，为什么还是不等于资源可用]({{< relref "performance/game-performance-read-does-not-mean-ready.md" >}})。

这条链的价值在于：

当你以后再看到“加载卡顿”，你不会再只剩一句：

`是不是磁盘慢了？`

而会开始问：

- 卡在页缓存之前还是之后
- 是同步等待卡住了线程，还是异步完成收口在关键帧
- 设备负载低，是缓存已经满足、上游没发出需求，还是串行依赖限制了并行
- 真正贵的是 I/O 还是 I/O 回来后的后处理

## 工程上最容易拿去就用的结论

### 同步 I/O 适合什么

- 有明确延迟预算、允许等待的少量读取；“初始化阶段”也可能影响首屏，不能自动视为安全
- 明确不在关键帧上的预处理
- 调试和工具链

在受控工作线程里使用同步读取可以简化逻辑，但等待仍占着工作线程的处理名额，需要避免线程池耗尽或优先任务排在长读取之后。

### 异步 I/O 更适合什么

- 运行时补读
- Streaming
- 能提前发请求、稍后收结果的资源链

但前提是：

- 后续解析不要都压回主线程
- 请求粒度和批量化已经做过设计
- 有并发与缓冲预算、完成队列处理预算，以及错误、取消和过期结果的释放路径

### `mmap` 适合什么

- 大块只读
- 数据布局天然适合按页访问
- 团队能接受页错误语义和映射生命周期管理
- 提前验证文件范围和格式，且关键线程的首次触页成本可测、可安排

### Read-Ahead 最吃什么

- 顺序读取
- 稳定局部性
- 实际按相邻范围访问的 chunk；合包本身不保证这一点

### 队列深度最怕什么

- 小请求串行化
- 高并发但无局部性的随机 storm

调节应用并发时，要同时看吞吐、关键资源可用时间、尾延迟与内存峰值；达到资源目标后，不必继续追设备峰值。

### 怎样验证这些取舍

下面是验证设计，尚未在本文执行，不代表某种接口已经测得更快：

1. 固定文件内容、访问偏移、请求大小和输出校验，记录 OS、运行时、文件系统、设备与文件打开选项。先确保短读、EOF、失败与取消都正确收口。
2. 分开记录首次访问与重复访问的缓存条件。仅重启应用不能证明 OS 文件缓存已清空；不知道条件时，就标注缓存状态未控制。
3. 一次只改变读取方式、请求大小、预取范围或应用并发中的一个因素。比较 `mmap` 时必须包括实际触页与消费数据，不能只计建立映射的时间。
4. 分别记录请求提交耗时、提交到读取完成、完成到后处理开始、最终可用时间，同时采样帧时间、缓冲峰值和应用队列。具备权限与工具时，再用 OS 记录核对设备请求和线程等待，不能用应用任务数冒充设备 QD。
5. 若吞吐增加而关键资源更晚可用，或读完待处理的数据不断堆积，应减小并发／预取窗口、调整优先级或后处理预算；只有定位到相应阶段，才把收益归因于 I/O 改动。

具体观测工具接[IO 性能分析]({{< relref "engine-toolchain/storage-io-06-profiling-with-fio-iostat-perfetto-instruments.md" >}})；本轮只核对本文机制，不表示相邻工具文章的所有命令和平台条件已经复验。

## 这一篇最该带走的结论

`OS I/O 机制真正决定的，不只是“文件能不能被读到”，而是“请求怎样进入内核、怎样命中缓存、怎样交给设备、怎样回到内存，以及应用线程最后在什么时机继续付账”。`

同步 / 异步 I/O、DMA、`mmap`、Read-Ahead 和队列深度，本质上都在回答同一个问题：

`这次读取到底是怎样流动的。`
