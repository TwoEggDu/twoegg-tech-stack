> 版本说明：本篇依据 Unity 6.6（6000.6）公开资料，核查于 2026-10-22。性能数字注明官方测试环境；分析模型与实验方案不代表本仓已有测量结果。

“Content Directories 比 AssetBundle 更快”，首先需要补上一个宾语：什么更快？

是改完一张贴图之后更快出内容，还是进入场景更快，或者退出场景后更容易回收不再使用的内容？这些现象可以同时出现，但背后的原因不相同。

[上一篇]({{< relref "engine-toolchain/unity-content-directories-02-vs-assetbundle.md" >}})比较了边界。本篇继续往下拆：**性能收益来自少做了哪些工作，或者哪些工作可以更好地重叠。**

## 1. 先给性能问题建立坐标

| 观察结果 | 可能变化的工作 | 需要查看的证据 |
|---|---|---|
| 内容增量构建缩短 | 重建范围、缓存命中、构建并行度 | 构建报告、变更资产与变更产物 |
| 加载耗时缩短 | 依赖准备、读取、解压、反序列化的关键路径 | Player 时间线与分阶段计时 |
| 内存峰值降低 | 重复对象、依赖范围、阶段重叠方式 | 对象数量、原生与图形内存快照 |
| 退出后剩余内容减少 | 不再需要的内容能否独立释放 | 引用所有者与退出后的对象变化 |

只比较最后一列总耗时，很难区分原因。下面每条机制都应当能对应到一种观察。

## 2. 构建侧：减少一次修改影响的工作范围

把一个大容器里的一小部分内容改掉，发布时通常要重新处理受影响的容器。内容粒度更细时，构建系统有机会复用更多未变化产物。

这是理解增量收益的最小模型：

```text
修改范围 → 失效范围 → 真正重做的工作 → 本次构建耗时
```

Unity 的 6.6 手册明确说明 Content Directory 构建支持增量复用，并且内容可以独立于 Player 重新构建。[增量构建说明](https://docs.unity.com/en-us/engine/6000.6/manual/assets-and-media/assets-managing-runtime/content-directories/introduction)

但不能把这写成“AssetBundle 没有缓存”。旧方案同样有增量构建能力。真正要对比的是：**同一次修改，在两套布局下各自使多少工作失效。**

比如只改角色的材质参数，检查产物变化；再改公共 Shader，重新检查。两次修改的影响面不同，不应该用第一次的收益推算第二次。

### 稳定 ID 为什么重要

如果 A 的二进制数据直接保存 B 的内容哈希，B 一变，A 中记录的哈希也要变，变化可能沿引用链向上传播。

Content Directories 在 Content File 之间使用稳定标识，由 manifest 映射到实际内容哈希。这样可以减少“目标内容变化，仅因为标识跟着变化而重写引用者”的情况。[Unity 工程师对 ID 与哈希的解释](https://discussions.unity.com/t/new-unity-6-6-contentdirectory-good-and-bad-q-a/1732493/5)

这里要把两种失效分开：

- 只因内容地址变化产生的连锁改写，可以通过间接映射减少。
- 因目标平台、导入设置、Shader 或真实构建依赖变化产生的失效，仍可能需要重新构建。

这项设计减少的是不必要的变化传播，不能推导成“修改任何依赖都只重建一个文件”。

## 3. 加载侧：少准备无关内容，并让流水线更充分重叠

先看一个概念模型：

```text
依赖准备 → 读取/解压 → 反序列化 → 对象完成初始化 → 可供业务使用
```

实际工作会重叠，并不是简单相加。但这条链可以帮助解释两类不同的优化。

### 第一类：缩小需要准备的依赖范围

如果管理层按 Bundle manifest 加载容器依赖，目标资产会受到所在 Bundle 汇总依赖的影响。Content Directories 的依赖信息更细，可以减少由同包其他内容引入的牵连。

这不代表目标资产的真实依赖消失了。一个 Prefab 真正需要的材质和贴图，仍要进入可用状态。对照时应该检查依赖图，而不是把少加载了内容一概归为“磁盘变快了”。[AssetBundle 的依赖追踪层次](https://docs.unity3d.com/6000.6/Documentation/Manual/AssetBundles-Dependencies.html)

### 第二类：提高多阶段的并行与重叠

Unity 官方介绍指出，新构建基础复用了资产导入框架，支持独立资产构建、缓存与多进程工作；运行时采用任务化的读取与反序列化流水线。

可把差别理解成生产线：若多个独立产物能够同时读取，后续阶段就有机会在前一批完成后提前开始，而不必把所有内容串成一个长队。**这里改善的是关键路径和吞吐，不是把所有工作成本清零。**[官方构建与加载架构说明](https://unity.com/blog/content-directories-beyond-the-assetbundle)

需要同时保留两个边界：

- AssetBundle 也有异步 API，不能把比较简化为旧方案同步、新方案异步。
- 内容读取与反序列化的改进，不能推出任意业务脚本、实例化与 GPU 工作都能无条件并行。

如果最慢的部分在场景激活或业务初始化，加载后端缩短一部分耗时后，那些成本仍然存在。

### 一个上限模型

假设总等待时间中，只有比例 `p` 的工作能被新后端改善，该部分加速 `s` 倍。在先忽略阶段重叠的简化模型里：

```text
新的总时间 / 原来的总时间 ≈ (1 - p) + p / s
```

这个模型不是 Unity 的性能预测器，只用来提醒读者：能优化的部分占比有限，总收益就有上限。

## 4. 内存侧：减少被一起留下的内容

内存收益需要另外一条解释，不能直接从加载耗时推导。

假设大厅保留一张预览图，关卡曾经加载过大量其他纹理。若它们受同一套粗粒度容器生命周期管理，预览图的长期存在可能让回收策略变得困难。

更细的内容与加载引用关系，使不再被使用的内容有机会单独结束生命周期。Loadable 的释放以加载引用为依据，多个实例持有同一目标时，需要等待最后一份引用结束。[Release 契约](https://docs.unity3d.com/6000.6/Documentation/ScriptReference/Unity.Loading.Loadable_1.Release.html)

但释放加载引用、销毁 Unity 对象、图形驱动回收、进程向操作系统归还内存，是不同的观察层。不能要求一次 `Release` 后任务管理器数字立刻下降相同的字节数。

循环直接引用也会破坏理想的独立加载边界。UnityDataTools 文档区分了 6.6 与后续版本对循环的产物处理方式；共同需要警惕的是，循环中的内容可能被作为关联单元加载。不要把“每个资产都能完全独立”作为无条件前提。[内容粒度与循环引用说明](https://github.com/Unity-Technologies/UnityDataTools/blob/main/Documentation/contentdirectory-format.md)

所以内存测试至少要问：留下的到底是必要共享内容，还是已经结束业务使用却没有释放的对象。

## 5. 官方案例能证明什么

Unity 在 Slime Rancher 2 的官方介绍中给出了以下结果：

| 指标 | Addressables / AssetBundle | Addressables / Content Directories |
|---|---:|---:|
| 增量构建 | 32 分 16 秒 | 3 分 4 秒 |
| 干净构建 | 58 分 6 秒 | 37 分 13 秒 |
| Player 构建大小 | 4 GB | 2.88 GB |
| 启动到菜单再到游戏 | 45 秒 | 30 秒 |

环境为 **Unity 6000.6.0b10、MacBook Pro M5 Max**。这些是官方特定项目结果，不是本文复测，也不是正式版全平台承诺。[官方数据及环境](https://unity.com/blog/content-directories-beyond-the-assetbundle)

这组数据说明不同指标的收益可以不同。它没有提供把每一秒变化精确分摊到缓存、并行或依赖粒度的完整归因证据，不能仅凭总数倒推出各机制贡献。

## 6. 怎样做一个能解释原因的对照实验

下面是实验设计，结果留待实际项目填写。

### 固定可比条件

固定 Unity 补丁、Addressables 包、内容提交、平台、Player 配置与设备。记录两边的压缩和归档设置；压缩方式不同，就把它列为独立变量。

冷缓存与暖缓存分开，干净构建、无修改重建、单资产增量构建也分开。重复运行，记录每次原始值及统计口径；不要只保留最快的一次。

### 按机制拆实验

| 实验 | 改变什么 | 用什么判断机制 |
|---|---|---|
| 单材质增量 | 只改一个参数 | 失效任务、重建产物与总耗时 |
| 公共依赖修改 | 改公共 Shader 或导入设置 | 真实依赖造成的影响面是否扩大 |
| 角色预览 | 只显示一个角色 | 准备了哪些容器、内容与对象 |
| 场景加载 | 同一场景、相同激活条件 | 请求到可用耗时及主线程时间线 |
| 退出但保留预览 | 保留一份小内容引用 | 哪些已不用的资产仍驻留 |
| 循环引用对照 | 直接引用环与按需引用断环 | 构建布局、加载关联范围和内存 |

再给 AssetBundle 基线一个合理布局。拿一个明显不适合业务的巨型共享包对比新系统，只能证明那份布局的问题；需要同时比较维护成本，才能讨论迁移价值。

在 Player 上验证尤其重要：编辑器通过 AssetDatabase 加载项目资产的路径，与已构建内容的引用计数路径不同。[编辑器与构建内容的行为区别](https://docs.unity3d.com/6000.6/Documentation/ScriptReference/Unity.Loading.Loadable_1.html)

## 7. 哪些条件会让收益缩小，甚至出现反效果

以下是需要通过测试排除的工程条件：

- 内容本来总是一起使用，细化后减少不了实际工作。
- 第一次构建由 Shader 编译等工作主导，增量缓存优势尚未体现。
- 大量散文件增加文件操作成本，归档与压缩策略没有适配目标设备。
- Root Asset 的普通直接引用过重，注册时就带入大量内容。
- 常驻缓存、对象池或未释放的 Loadable 持有内容，加载边界细化也无法替项目结束所有权。
- 总等待主要来自业务初始化，内容后端改善的比例很小。

官方手册本身也保留了干净构建可能慢于 AssetBundle 的限制说明。因此应把“为什么可能更快”写成一条条可验证的因果链，而不是升级版本后的默认结论。

回看[原理与最小流程]({{< relref "engine-toolchain/unity-content-directories-01-model-and-workflow.md" >}})时，可以用这四个问题检查接入方案：重建了什么、加载了什么、哪些工作能重叠、哪些内容仍被持有。

**Content Directories 的性能潜力来自缩小工作与驻留范围，并改善流水线利用率；实际收益仍由项目关键路径决定。**
