> 函数注入主要控制的是变化向调用方扩散的范围；不注入不等于这个函数从此不能热更。

这是 HybridCLR 系列第 26 篇。[上一篇]({{< relref "engine-toolchain/hybridclr-dhe-internal-dhao-format-diff-algorithm-function-routing.md" >}})解释了主包与变化数据的对应关系。这篇只讨论其中一个变量：入口检查会怎样改变调用链的执行选择。

> 资料范围：以下行为与配置依据 2026-10-25 查阅的 HybridCLR 官方 9.x [函数注入策略](https://www.hybridclr.cn/docs/business/ultimate/injectrules)。图中的函数是说明模型用的自有样本，不是商业源码或实测生成物；本篇没有商业性能验收。

## 为什么没有改动的调用者也可能需要解释执行

设同一个 DHE 模块内存在普通非虚调用链：

```text
A → B → C → D
```

现在只修改 D。如果 C 的旧 AOT 实现仍直接进入 D 的旧 AOT 函数，单独保存一个“D 已变化”的标记并不能保证调用自动改道。

一种保持正确性的办法，是让 C 也解释执行，用最新的运行时调用路径访问 D。但 B 又可能直接调用旧的 C，于是变化继续向上游传播。这里的“脏”不只表示源代码被编辑过，还可能表示它不能继续沿用当前 AOT 调用路径。

因此要区分两个集合：

- **直接变化**：方法自身或相关判定输入发生了变化。
- **间接传播**：为了让调用到达正确版本，未直接编辑的调用者也需要切换执行方式。

这个模型说明为什么“只改了一个函数”不保证“只有一个函数解释执行”。实际传播范围还要结合类型变化、调用形式和工具生成的结果检查。

## 入口检查怎样截断传播

DHE 默认在函数入口注入检查。对前面的样本，可以理解为：

```text
C 的 AOT 实现进入 D 的原生入口
  → D 的入口检查当前执行方式
    → 未需要重定向：继续原始 AOT 逻辑
    → 需要重定向：转入最新解释执行
```

这样，C 可以保留原有调用入口，而由 D 决定后续执行方式。只考虑这个调用关系时，D 的变化就不必继续迫使 C、B、A 解释执行。

这是公开的行为模型。它不要求业务代码手工修改方法指针，也不能推出所有虚调用、内联或其他边界具有完全相同的实现。

### 不注入后发生变化，仍需保证执行正确

官方明确说明：一个函数被配置为不注入后，后续修改它不会因此执行旧逻辑或导致运行错误；代价是直接调用它的函数可能被标记为脏，继续产生传播。

例如 D 不注入、C 注入：D 改变后，C 可能需要解释执行；C 的入口检查则可以防止同一传播继续向 B 扩大。最终应检查工具产物，不能只凭这幅简图预测所有方法的状态。

所以“不注入”是传播范围与运行开销之间的取舍，不是承诺该函数永远不再修改。

## 注入规则与主包属于同一份契约

入口检查是在构建 AOT 代码时形成的。生成变化数据时，需要知道原主包哪些函数具有检查，哪些没有。

如果主包按规则甲构建，热更新却按规则乙计算传播，工具对旧代码的假设就可能不成立。这类错配与“不注入函数被正常修改”不同，确实可能影响正确性。

规则文件应随每个主包快照一起保存。生成 DHAO 或 MetaVersion 时，使用该工作流要求的配套规则与快照，不能拿当前工作目录中的最新规则直接代替旧主包规则。

## 一个可审阅的配置样本

以下 XML 使用官方的 `rules / assembly / type / method` 结构，类型名为示例项目自有名称：

```xml
<rules>
  <assembly fullname="GameLogic">
    <type fullname="GameLogic.SmallValue">
      <method name="get_Value" mode="none"/>
      <method name="set_Value" mode="none"/>
    </type>
    <type fullname="GameLogic.ModuleEntry">
      <method name="*" mode="proxy"/>
    </type>
  </assembly>
</rules>
```

`none` 关闭匹配函数的入口注入；`proxy` 使用检查。没有提供策略文件时，产品采用默认注入行为；匹配多条规则时，官方规定后面的匹配规则生效。修改前应核对具体包版本和生成结果。

这里不把 `Mathf`、Unity 模块或任意第三方 API 当成项目可随意配置的 DHE 函数。注入规则作用于实际参与对应 DHE 构建的程序集。

## 成本应怎样判断

官方报告指出，注入可能增加生成的 C++ 文件体积，短函数也可能因附加检查或内联变化出现性能下降。文档中的约 30% 是相应生成代码的体积观察，**不是所有项目安装包一定增加 30%**；最终二进制还受编译、链接和裁剪影响。

不能因为 getter 很短，就默认全部设成不注入。应先找到目标设备上的热点，再同时比较：

| 比较项 | 为什么需要 |
|---|---|
| 稳定版本的耗时 | 注入是否确实影响这个热点 |
| 修改叶子方法后的解释执行范围 | 减少入口检查是否带来更大传播 |
| 生成 C++、最终二进制与安装包大小 | 三种大小的变化不能混用 |
| 规则、快照与发布材料的一致性 | 性能调整不能破坏版本契约 |

本系列没有执行这些商业对照，不能把厂商数字作为本项目的收益。

## 哪些情况下值得调整默认行为

默认策略更容易维护。只有当固定设备、固定构建的测量表明注入开销影响目标预算时，才值得缩小注入范围。

对短函数取消注入后，应补一组“以后真的修改这个函数”的用例。它检验的不只是结果是否正确，还包括会把多少调用者带入解释执行。如果这个范围不可接受，可以恢复注入，或重新划分稳定 AOT 与频繁变化模块。

函数注入控制的是变化传播的成本，主包与规则一致性负责让这种取舍成立。
