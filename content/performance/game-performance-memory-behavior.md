> 容量是否足够、访存是否受限、分配和回收是否集中在关键帧，需要分别判断。总量没有超预算，仍可能存在内存相关的帧时间问题。

> 读这篇之前：如果还分不清分配、驻留与工具统计，先读[内存到底占在哪里：从虚拟地址、物理页到游戏内存预算]({{< relref "performance/game-performance-memory-accounting.md" >}})。本文聚焦生命周期与排查方法，UI 场景为教学示意，没有项目发生率或优化收益统计。

前面几篇文章，我一直在往同一个方向收：

- 为什么某些操作会慢
- 一帧到底是怎么完成的
- 什么事不能在什么时候做
- 为什么大整文件通常比很多小散文件更稳
- 为什么读盘完成不等于资源可用

如果顺着这条线继续往下走，接下来最该讲的一层，就是内存。

但这里有一个很常见的误区：

很多团队一提到内存，脑子里第一反应只有一个问题：

`够不够。`

这个问题当然重要。  
如果真的不够，进程会被系统回收、崩溃、OOM，或者被迫进入非常糟糕的回收状态。

即使没有确认容量不足，仍然需要解释这些现象：

- 明明总量看起来还行，为什么还是会卡
- 明明场景不是特别大，为什么切场景时总会抖
- 明明一次分配不大，为什么长玩后越来越不稳
- 明明资源压下来了，为什么首次打开 UI、首次进战斗还是会掉帧

这些问题的共同点是：

`它们值得检查内存行为，但这些现象本身不能证明内存就是瓶颈。`

所以这篇文章我想讲透的是：

`除了容量，还要观察当前需要访问的数据，以及分配、访问和释放的时间分布。`

本文将“活跃数据集合”用于描述业务在一个时间窗口内需要的数据；Windows 的 Working Set 则是特定 OS 指标，不能把它与资源持有列表、托管堆或 RAM 总量互换。

真正影响体验的，往往不是“仓库有没有装满”，而是你是不是在用一种混乱、波动很大、会打断帧预算的方式搬运和管理这个工作区。

## 先把一个概念摆正：RAM 更像工作台，不像仓库

磁盘、SSD、UFS 更像仓库。  
它们擅长长期存放数据。

RAM 在游戏运行时扮演的角色更像工作台：

- 当前帧要访问的对象在这里
- 正在运行的系统状态在这里
- 资源数据中当前驻留的部分由物理内存承载
- GPU 上传前的很多准备数据也在这里

工作台和仓库最大的差别在于：

- 仓库更怕装不下
- 工作台更怕一直乱

如果工作台总是在这些状态里来回切换：

- 突然堆很多东西上来
- 刚放上来又立刻扔掉
- 一会儿清空一大片，一会儿又塞满
- 刚准备好的内容下一秒又被换走

那即使容量预算仍有余量，也可能因分配、初始化或回收成本影响帧时间；是否出现尖峰，需要测量。

内存相关行为可能影响下面这些体验，但它们也可能来自计算、同步、I/O 或热状态等其他原因：

- 帧时间抖动
- 场景切换尖峰
- UI 首开卡顿
- 长玩后变差
- 某些设备上明显更容易出事

## 很多卡顿，真正伤人的不是“占了多少”，而是“怎么进、怎么出”

如果只看内存占用截图，很容易有一种错觉：

`内存总量没爆，应该没啥问题。`

但运行时更敏感的常常是下面这些事：

- 分配发生得太频繁
- 释放发生得太集中
- 生命周期边界太剧烈
- 临时对象太多
- 资源常驻和淘汰策略来回抖
- 页面缺失和缓存失效在关键时刻出现

也就是说，内存问题最危险的地方，很多时候不是“占用高”，而是：

`行为不平滑。`

如果每帧都在做很多小分配与释放，或者在关键节点集中激活和销毁对象，应检查这些成本是否落在帧的关键路径上；总次数、单次代价和并发关系共同决定影响。

这里不能把 `memory bound` 当作“工作集管理不稳定”的同义词。它讨论执行受内存子系统限制，例如访存延迟或带宽；[Intel VTune 的 Memory Bound 定义](https://www.intel.com/content/www/us/en/docs/vtune-profiler/user-guide/2024-0/cpu-metrics-reference.html)描述的是 load/store 相关的流水线停顿口径。容量压力、GC 时间、对象寿命与访存瓶颈可能同时存在，但需要分别取证。延迟与带宽的区别见 [F04]({{< relref "performance/hardware-cpu-f04-memory-bandwidth.md" >}})。

## 临时对象为什么这么容易变成性能问题

很多程序员第一次踩内存坑，通常不是踩在“超大资源”上，而是踩在看起来不起眼的临时对象上。

因为临时对象从业务语义看太无害了：

- 临时拼一段字符串
- 临时组一份列表
- 临时构建一棵 UI 数据
- 临时生成一批特效参数

单次看起来都不大。  
但一旦这些事发生在高频路径里，比如：

- 每帧
- 每次输入
- 每次角色更新
- 每次 UI 刷新

它就会慢慢变成一类特别典型的问题：

- 分配频率高
- 回收压力高
- 分配器工作量可能增加
- 可能触发 GC 或分配器扩容；具体时机依运行时而定

短命对象不天然意味着缓存局部性差；布局、访问顺序与复用距离要另外分析。

这类问题最容易骗过人的地方在于：

`每一处都不大，但总量和节奏很糟。`

所以很多时候，真正危险的不是“大对象”，而是：

- 高频临时对象
- 短命对象风暴
- 热路径里习惯性地产生中间结果

对运行时来说，这就像你在工作台上不停地扔下小纸片、揉掉、再扔、再揉。  
每张纸都不大，但整个台面会变得非常乱。

## 生命周期集中变化，需要与帧时间对齐

这件事和前面“什么事不能在什么时候做”那篇是连着的。

除了单个大对象，也要检查：

`很多对象在同一个时刻一起活过来，或者一起死掉。`

比如这些高风险时刻：

- 进战斗
- 切场景
- 打开大 UI
- 一波敌人同时生成
- 大量 streaming 内容一起进场

这些时刻里，系统常常会同时发生：

- 分配内存
- 初始化对象
- 建立引用
- 激活组件
- 触发生命周期回调
- 将来再在另一个节点集中释放

这类问题特别难受，因为从业务角度看你只是做了一个“切换状态”的动作。  
但从运行时角度看，你其实在一个很短的时间里制造了一整波内存行为尖峰。

因此，切场景或 UI 首开时，应把分配、初始化、回调和渲染准备标记对齐到同一时间线；不能把这一整段都计为分配器或 GC 成本。

## GC 成本需要同时看分配来源与回收时间

GC 负责托管对象的回收，不代表所有资源都会随一次 GC 释放。以 Unity 6.0 为例，托管堆中的空闲块可以保留供后续使用，原生对象还有独立寿命；归还 OS 的时机也不能由业务假定。依据见 [Unity 托管内存说明](https://docs.unity.com/en-us/engine/6000.0/manual/analysis/performance-memory/managed-memory/introduction)。

因此，观察到 GC 时间后，需要继续问：

- 哪些调用产生了托管分配，分配量如何随场景变化？
- 对象是否仍被引用，哪些空间可以复用？
- 回收阶段是否与加载、初始化或 UI 更新重叠？
- 工具显示的是单帧 GC 时间、分配流量，还是当前堆大小？

GC 成本还受堆状态、存活对象与运行时策略影响，不能只用“垃圾多”解释。对象池可以减少某些创建与分配，但也会保留对象及其引用；只有同时核对池上限、回收时机和占用，才能判断是否值得。

## 长玩后的卡顿，怎样检查缺页与资源反复进入

“刚进入正常，切几次场景后开始卡”只是现象。可以沿三条不同的线调查：

- 业务是否在反复卸载、重载或构建同一资源；
- OS 页面是否发生缺页，以及处理时是否涉及后备存储 I/O；
- CPU 数据访问是否受到 Cache Miss、延迟或带宽限制。

这三层不能互相代替。Windows 的软缺页可以不访问后备存储，硬缺页才需要读取分页文件或映射文件；工作集被裁剪不等于引擎卸载了资源。具体定义见 [Microsoft Working Set](https://learn.microsoft.com/en-us/windows/win32/memory/working-set)。

只有把缺页类型、I/O、资源请求与关键线程时间线对齐，才可以判断它们是否解释了这次卡顿。长玩后的增长还应检查未释放引用、缓存策略和内容变化，并保留热状态、其他进程压力等候选原因。

## 常驻与淘汰，不是越省越好，而是要避免来回抽搐

很多团队讲内存策略时，容易把目标说成：

`尽量少常驻。`

这句话对一半。

因为如果你什么都常驻，内存压力肯定会越来越大。  
但如果你什么都不敢常驻，系统又会在关键时刻不停追资源、追对象、追上传。

真正的问题不是“常驻多还是少”，而是：

`常驻和淘汰是不是在服务实际访问模式。`

最怕的是一种很常见的策略失败：

- 这个资源刚被淘汰
- 过几秒又要用
- 用完又被淘汰
- 再过一会儿又得重新拉回来

这种来回抽搐式的管理，往往比单纯“占用略高一点”更伤体验。

因为它意味着：

- I/O 反复发生
- 解析反复发生
- 对象和 GPU 资源准备反复发生
- 帧时间波动被放大

所以从游戏体验角度看，更成熟的目标通常不是“极限省内存”，而是：

`在可接受总量内，让工作集尽量稳定。`

## CPU 缓存局部性和 RAM 行为，为什么会一起变成帧时间问题

很多人一说内存问题，就只想到 RAM 总量。  
但 CPU 视角下，还有另一个很现实的层面：

`你访问内存的方式，决定了 CPU 跑这段逻辑到底顺不顺。`

如果数据布局很乱、访问模式跳来跳去、对象分散得很碎，那即使总量不大，CPU 也会：

- 更难命中缓存
- 更频繁地去更慢的层级取数据
- 更容易在热路径上浪费时间

这类问题为什么重要？

因为它会让很多人产生一种错觉：

`逻辑明明不复杂，为什么 CPU 还是会抖？`

除了算法工作量，也可以检查这些候选因素：

- 数据太碎
- 布局太乱
- 访问太散
- 生命周期太频繁变化，导致局部性持续被破坏

所以内存行为问题并不只属于“资源管理”，它也深深影响着纯 CPU 侧的帧时间。

## 用一个大 UI 首开的例子，把内存行为问题串起来

这类场景特别适合说明问题。

玩家看到的现象是：

`第一次打开背包或商城时，会顿一下。`

真实系统里可能同时发生的是：

1. UI 资源首次读取或访问相关页面
2. 图集、字体、配置、脚本数据被解析
3. 节点树和运行时对象被创建
4. 布局和绑定开始计算
5. 一批临时对象和字符串处理中间结果被制造出来
6. 某些纹理和材质状态第一次上传 GPU
7. 回调、动画、音效和脚本逻辑一起启动

如果只把这件事叫成“UI 有点重”，你就会什么也优化不明白。

只有把它翻译成：

- 首次资源进场
- 生命周期尖峰
- 临时对象风暴
- GPU 首次成本

这几层，你才知道该怎么拆：

- 哪些资源可以提前准备
- 哪些节点可以延迟创建
- 哪些子页面可以按需展开
- 哪些字符串和列表不该在热路径里反复构造

## Unity 和 Unreal 里，可以沿哪些阶段取证

### Unity 的调查入口

Unity 项目里，内存行为问题常常会长成下面这些样子：

- GC 尖峰
- `Instantiate / Destroy` 高频触发
- UI 首开、切页、列表刷新时明显抖动
- 某些逻辑路径每帧产生大量短命对象
- Addressables / AssetBundle 读完以后，激活和运行时构建阶段卡顿

调查时可以检查这些候选因素，再用对应采样判断是否成立：

- 临时对象多
- 生命周期波动大
- 收口时机太集中
- 资源反复加载、释放或重新构建

### Unreal 的调查入口

在 Unreal 中，也可以沿线程与对象生命周期阶段调查，例如：

- Game Thread 在对象激活和初始化阶段有尖峰
- 流送、激活和渲染准备在同一时间窗口收口
- 某些对象链条第一次进入场景时成本很高
- 常驻和 streaming 内容切换时工作集波动明显

这些是沿引擎阶段取证的线索，不能仅凭 Game Thread 尖峰认定内存问题。需要把分配、对象构建、脚本执行、同步和图形准备分别测量。

## 平台差异要落实到目标设备和指标

开发机的容量余量不能代表低档设备。同样的资源策略，在目标设备上需要分别检查进程占用、切换峰值、后台压力和长期重复操作；不能只按“PC”或“手机”推定哪种问题一定先发生。

Android 的系统回收与共享页记账可从[内存管理文档](https://developer.android.com/topic/performance/memory-management)进入；Apple 的内存压力终止应结合 [jetsam 报告](https://developer.apple.com/documentation/xcode/identifying-high-memory-use-with-jetsam-event-reports)。系统终止、分配失败与程序崩溃是不同调查方向，返回桌面并不自动证明 OOM。

平台策略影响取证方式，产品预算仍要通过具体设备与场景校准，不设一个所有设备通用的 RAM 比例。

## 一套更实用的内存行为排查问题

如果你现在面对的是“总量看起来没爆，但体验还是不稳”的问题，我建议先问下面这些问题。

### 1. 容量、访问与时序分别有什么证据

先确认进程指标与采样窗口，再分别检查：

- 峰值是否超出项目预算，是否有分配失败或系统终止记录
- 关键路径是否受访存延迟或带宽限制
- 分配、回收、缺页或资源构建是否与坏帧重叠

这些因素可以同时存在，不能仅靠总量截图二选一。

### 2. 高风险时刻有没有生命周期尖峰

切场景、开 UI、进战斗、首播技能时，是否有大批量对象同时创建或销毁。

### 3. 热路径里有没有很多短命对象

如果每帧、每次输入、每次 UI 刷新都在反复分配临时对象，先盯这里。

### 4. GC、回收或分配器尖峰是不是踩在关键帧

如果是，就不要只盯“GC 花了几毫秒”，要回头找前面是谁制造了垃圾。

### 5. 常驻与淘汰策略是不是在来回抽搐

如果同一批资源不断进出场，问题通常不在“某次加载”，而在策略本身。

### 6. CPU 侧数据访问是不是太碎

如果逻辑不复杂却 CPU 抖动明显，要怀疑数据布局和局部性。

### 7. 这类成本能不能前置、池化、分帧、降波动

前置可能提高重叠峰值，池化可能增加常驻容量，分帧可能延长完成时间。改动后要同时复验峰值、帧时间、可操作时间和释放正确性。

## 我的结论

如果把这篇文章压缩成一句话，我会这样总结：

> 内存优化既要约束容量和峰值，也要解释访问、分配、回收与资源重建在关键时间窗口内的成本；每一项判断都应对应指标和证据。

理解这一点之后，你再去看 GC 尖峰、UI 首开抖动、切场景顿、长玩后变差、对象生命周期波动，很多问题就不再会被粗暴地归类成“内存不够”。

你会更容易开始问：

- 是谁在制造短命对象
- 是谁在关键时刻拉起大量生命周期变化
- 是谁让资源反复进入、退出和重新准备
- 是谁把可前置的准备拖到了当前帧

当这些问题开始被持续追问时，内存优化才真正从“省一点 MB”变成了“让运行时稳定下来”。

下一篇我会先把这条线落到 Unity 的现场上：

`Unity 里，这些性能问题通常怎么显形。`
