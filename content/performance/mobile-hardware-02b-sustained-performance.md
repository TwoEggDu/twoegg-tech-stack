> **阅读说明**：标题提出的是需要验证的问题，不是“高端机必然更持久”的结论。本篇保留硬件差异视角；信号、降载与恢复策略见[硬件 03：功耗与发热]({{< relref "performance/mobile-hardware-03-power-thermal.md" >}})。原稿缺少来源的机型留存率、温度／帧率对照和固定内存额度已移除，本篇没有设备实测结果。

比较设备时，除了刚启动时的峰值表现，还需要观察同一产品在持续负载下能维持怎样的体验。更强的芯片、不同的热设计和更大的内存容量可能改变余量，但售价或“旗舰”标签不能代替实际验证。

## 峰值性能 vs 持续性能

峰值描述特定条件下短时可达到的能力；持续表现需要同时说明负载、目标、环境、初始状态和运行窗口。固定跑到第 30 分钟不是定义本身，也不能只用一个留存百分比比较所有设备。

例如，一台设备在更高分辨率运行，另一台设备降低了效果，二者帧率接近并不表示能力相同。锁定帧率后，“帧率没掉”也不直接证明内部频率或热状态没变。Android 官方将可持续负载与设备热设计、环境及近期使用联系起来，见 [Thermal API 指南](https://developer.android.com/games/optimize/adpf/thermal)。

比较持续能力至少记录：

| 条件 | 为什么需要 |
| --- | --- |
| 相同或明确不同的内容、画质、分辨率与帧率目标 | 避免把工作量差异当作硬件能力差异 |
| 设备、系统／固件、驱动与构建 | 说明结果属于哪个运行组合 |
| 环境、亮度、供电、初始热状态与测试顺序 | 说明热和能耗条件是否可比 |
| 帧时间／呈现、质量变化、平台信号与观测窗口 | 分开体验、主动降载与系统限制 |

## 散热硬件：从部件名称回到整条传热路径

多数常规手机依赖被动散热，也存在带主动风冷或外接散热器的产品。热量需要从发热部件经封装、接触界面和扩散结构传到外壳，再散到环境；某个部件面积大，不代表整条路径的热阻一定更低。

### 均热板（Vapor Chamber）

均热板利用密闭结构内工质的相变与回流扩散热量。简化逻辑是：

```text
热端吸热并蒸发 → 蒸汽到较冷区域冷凝 → 工质回流
```

它帮助扩散热量，并不把热量消除。厚度、接触、布置、工作条件与整机散热都会影响效果。本篇不再用未注明条件的“比铜片强若干倍”、面积范围或机型标签推导持续帧率。

### 热管与导热片

热管可以把热量沿其布置传递到其他区域；片状导热材料可以帮助扩散。石墨片、石墨烯相关材料和金属的名称、结构与方向性需要按具体材料规格区分，不能把宣传名称直接换成一组固定导热系数。

选型数据应来自对应材料与整机资料；仅凭“有无均热板”不能推出设备温度、降频时间或档位。没有风扇也不等于没有散热设计，均热板和热管本身并不是主动制冷。

## 内存发热与持续带宽

内存访问也有能耗，CPU、GPU 与其他消费者可能竞争共享内存系统。但不能从“机身变热”直接推出某款 LPDDR 在某个温度降到指定带宽，更不能按芯片名固定分配 GPU、CPU、NPU 各用多少 GB/s。

先区分标称传输能力、实际访问带宽和等待。温度、刷新、控制器策略、频率及工作负载之间的关系，需要具体器件或平台资料及观测；本篇没有足够证据给出通用降速表。访问成本与带宽判断沿[移动端与 PC 的差异]({{< relref "performance/mobile-hardware-04-mobile-vs-pc.md" >}})继续核对具体条件。

## 制程效率对持续性能的影响

制程是芯片设计条件之一，不能单独决定产品的能效与持续帧率。架构、工作电压／频率、软件负载、目标画质和整机热策略共同参与结果；不同代芯片的工艺名称或理论算力不足以证明某个游戏的持续表现。

因此这里不保留无来源的“某制程几瓦实现多少 TFLOPS”算例，也不据此推出旗舰机长时间无需降载。真正有用的比较是相同体验目标下，设备能否持续满足要求，以及为此付出了什么画质与能耗代价。

## 内存容量对持续体验的影响

长时间运行后变慢或退出，需要分别调查资源驻留、缓存增长、泄漏、系统压力与退出原因。容量可能提供更多余量，但整机 RAM 不是进程可使用的保证额度，也不能据机型档次推算几分钟后一定 OOM。

缓存过大与泄漏要分别处理。定期强制 GC 不会自动修复仍被持有的资源，也可能引入成本；先检查持有与卸载，再考虑具体回收策略。口径和峰值见[内存预算基础]({{< relref "performance/game-performance-memory-accounting.md" >}})。

切后台再回来时，组件重建、进程重启与游戏状态恢复也不由 RAM 容量单独决定。原来的“低端必重启、旗舰瞬间恢复”对照不能作为设计依据。恢复责任接[Android 专项]({{< relref "performance/mobile-unity-android.md" >}})，iOS 压力与后台约束接[iOS 专项]({{< relref "performance/mobile-unity-ios.md" >}})。

## 对开发者的设计启示

设备分档可以作为初始配置入口，最终要用实际能力与运行结果校准。不要按“旗舰／低端”直接承诺 120fps、固定纹理内存上限或统一关闭全部后处理，也不能默认高端机不需要恢复与降载策略。

建议按以下问题做对照，而不是填一张未经测量的档次体验表：

1. 初始档位是否满足必要画面、响应与内存目标？
2. 在约定持续窗口内，内容、帧与平台状态怎样变化？
3. 降载后保住了什么，牺牲了什么，切换本身是否引入卡顿？
4. 回到较低负载或恢复前台后，状态能否正确重建并逐步恢复？
5. 失败样本是否有足够信息区分内容成本、系统限制和资源寿命问题？

观察到后段帧率下降时，不用一个固定留存比例判定“散热设计不好”。先保证输入和口径可比，再调查原因。把信号与团队动作连接起来的责任表、策略和教学场景，统一放在[硬件 03]({{< relref "performance/mobile-hardware-03-power-thermal.md" >}})，本篇不重复建立第二套控制策略。
