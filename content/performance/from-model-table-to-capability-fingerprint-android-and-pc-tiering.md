很多团队第一次做机型分档时，最自然的实现方式会是：

- 看到一台机器
- 查到型号名
- 在表里找它应该进哪一档

这套思路在一些平台上并不是完全错的。

例如：

- 硬件代际非常稳定的平台
- 团队手里只有少量固定设备池
- 产品只面向非常窄的设备范围

但只要场景一放到 `Android` 和 `PC`，这套做法很快就会变得越来越脆。

因为真正决定体验的，经常不是机型名本身，而是：

- `GPU` 家族
- 图形 API 路径
- 分辨率和刷新率
- 内存和存储状态
- 驱动版本
- 热状态
- 玩家自己设置的目标帧率与画面偏好

所以这篇文章真正要讲的，不是"型号表还有没有用"，而是：

`在 Android 和 PC 这种开放环境里，分档判断怎样从型号名单升级成能力指纹。`

如果说 [手机和 PC 为什么要用不同的性能直觉]({{< relref "performance/game-performance-mobile-vs-pc-intuition.md" >}}) 解释的是"为什么两个平台的问题长得不一样"，那这篇更像是在把那个判断框架压回到一个具体工程动作里：

`默认分档规则到底该看哪些信号。`

## 为什么型号表在 Android 和 PC 上很快会失真

先把问题说清楚：

型号表最大的问题不是"维护麻烦"，而是它默认了一个前提：

`型号名 = 设备能力。`

这个前提在 Android 和 PC 上都很容易失真。

### 在 Android 上，问题是同名设备不等于同样表现

常见原因包括：

- 同一代际芯片的散热设计差异很大
- 同品牌不同市场版本的存储、内存和屏幕规格不同
- 系统版本与驱动更新会改变图形路径表现
- 用户后台环境、电池状态和老化程度差异大

也就是说，型号名能提供线索，但它远远不等于真实预算。

### 在 PC 上，问题是你甚至没有一个稳定的"机型名"

用户真正带来的差异通常是：

- 不同 `GPU`
- 不同 `VRAM`
- 不同显示分辨率和刷新率
- 不同驱动
- 不同电源模式
- 不同后台环境

在这种环境里，继续沿用"型号表思维"，很容易把一套分档系统做成一堆难以解释的特殊判断。

所以更稳的目标不是完全抛弃型号信息，而是把它降级成：

- 少量黑白名单
- 少量已知风险覆盖

而把真正的默认判定，交给能力指纹。

## 什么叫能力指纹

如果把这件事压成一句话，我会这样定义：

`能力指纹不是设备名字，而是一组真正决定当前运行预算和风险面的信号组合。`

这里的“指纹”是用于判断和回溯的一组记录，内部仍要分开四类信息。否则同一台机器切换目标帧率或暂时发热后，就像变成了另一种硬件。

| 类别 | 记录什么 | 用来决定什么 |
| --- | --- | --- |
| 兼容性与支持边界 | 项目必需 API、格式、特性、最低资源条件，以及具体驱动/路径的阻断记录 | 是否存在允许运行的路径；无路径时是不支持、阻断或待核查 |
| 设备能力 | CPU/GPU、内存容量与组织、存储能力、整机散热设计；绑定 OS、驱动与构建条件下的能力证据 | 哪些配置值得成为候选；硬件名和容量只是线索 |
| 目标与配置 | 目标帧率、内部渲染与输出分辨率、阴影/LOD/特效方案、玩家选择 | 本次想承担多少工作、保留什么体验；记录请求值和实际生效值 |
| 当前运行状态 | 热信号及有效性、功耗/电源模式、后台负载、可用内存和存储空间 | 当前是否需要临时限载，何时复核或恢复；不据一次状态永久改写设备档 |

后三类共同影响表现，但不能用一个总分互相抵消。显存或关键特性不满足某配置的约束时，GPU 得分再高也不能补齐；当前可用内存也不等于设备总容量。记录整机持续能力时，要同时保留负载、配置和初始状态，不能从一次热机结果外推所有场景。

在这份记录之上，判定顺序仍可分成三层。

### 第一层：硬能力门槛

这层解决的是"能不能"：

- 是否支持目标图形 API
- 是否满足最小内存 / 显存
- 是否支持某些关键格式或特性

如果项目必需条件不满足，结果应是“不支持”；命中明确的禁用规则，应记录“阻断”。这两者都不能写成“低画质可运行”。只有项目确实提供并验证过兼容替代路径时，才选择该路径及适用配置；没有证据时保留待核查。API 的选择也不表示能在运行中随意切换，切换时机与重启要求由具体引擎和平台决定。

### 第二层：性能与预算信号

这层解决的是“在指定目标下，先验证哪些配置”：

- CPU/GPU 的能力线索与不均衡情况
- 内存、显存和存储能力的证据及适用条件
- 相同或相近负载下的首次与持续运行记录

然后把能力证据与本次目标帧率、渲染分辨率和内容配置匹配，得到候选配置。某设备被标为“高档”，不证明它在任意分辨率、任意场景都能使用最高配置。

### 第三层：风险修正信号

这层解决的是"理论上可以，但现在要小心"：

- 某驱动版本已知有问题
- 某 API 路径稳定性差
- 某组机型在历史版本里反复出现异常

这样一来，分档系统就不再是：

- 看到型号表，直接给档

而会变成：

- 先看硬门槛
- 再看预算信号
- 最后再做风险修正；硬阻断规则优先于性能偏好

## Android 分档最值得看的信号是什么

Android 是最容易让型号表失真的地方，所以也最适合先讲。

我更建议 Android 的默认分档至少看下面几类信号。

### 1. GPU 家族与代际

对于以图形负载为主的候选配置，GPU 家族是值得先查的线索。

原因不是它万能，而是它最接近图形预算本身。

例如：

- `Adreno` 不同代际
- `Mali` 不同代际
- 某些长尾 `GPU` 的 API 支持差异

它比单看机型名更便于组织图形能力与风险证据。但角色逻辑、动画求值或资源准备可能受其他路径限制，GPU 家族不能代替 CPU、内存及任务证据。

### 2. 图形 API 路径

同一设备在：

- `Vulkan`
- `OpenGL ES`

两条路径上的表现与稳定性，可能完全不是一回事。

所以默认分档至少要知道：

- 当前实际跑的是哪条 API
- 该 `GPU` 在这条 API 上是否稳定

遇到路径风险，先明确是禁用该路径、采用已验证的替代路径，还是限制某项配置；降低画质不能自动修复 API 或驱动兼容问题。

### 3. 分辨率与刷新率

要分别记录屏幕刷新率、目标渲染帧率、内部渲染分辨率和输出分辨率。120 Hz 屏幕可以承载以 30 FPS 生成的内容，不能直接把 120 代入工作量；目标值也不能代替实际帧与呈现记录。Android 的 [Frame rate 文档](https://developer.android.com/media/optimize/performance/frame-rate)说明了应用期望帧率与显示刷新率的关系。

例如内部渲染目标保持 `1280×720`，从 30 FPS 改为 60 FPS，每秒对应的目标像素数从 `27,648,000` 变为 `55,296,000`，名义每帧时间从约 `33.33 ms` 缩为 `16.67 ms`。这是**教学算例**，只说明目标改变；多 Pass、覆盖、着色器、CPU 与等待都可能改变成本，不能据此断言 GPU 耗时翻倍。若只把面板从 60 Hz 换成 120 Hz，而目标和实际配置不变，也不能推导渲染工作量翻倍。

### 4. 内存与存储状态

很多机型不是纯 GPU 不够，而是：

- 内存紧
- 存储慢
- 可用空间低

要把容量/存储能力与本次剩余空间、可用内存分开记录。这些条件可能影响：

- 首载
- 切场景
- 热更资源挂载

### 5. 热状态与持续运行表现

Android 上同型号设备的热差异很大。

短时 Benchmark 只能提供对应条件下的线索，持续表现还要结合相同负载、配置、初始状态与运行窗口。一次会话发热可触发已验证的临时限载，恢复也需满足稳定条件；不要因此永久写低设备能力档。

Android [Thermal API](https://developer.android.com/games/optimize/adpf/thermal)用于观察平台热状态并辅助调节负载，支持性和信号有效性需要检查。没有热信号不代表设备处于冷态，长帧也不能单凭这一现象归因为发热。持续表现的条件和解释沿[硬件 02b]({{< relref "performance/mobile-hardware-02b-sustained-performance.md" >}})复用；具体降载、恢复与防振荡在动态策略中校准。

## PC 分档为什么更像能力指纹，而不是"机器识别"

如果说 Android 还能勉强靠"机型名 + `GPU`"维持一层近似，那 PC 基本就不适合继续走这条路。

因为 PC 环境的本质更像：

`开放硬件组合 + 开放用户目标 + 开放后台环境。`

所以 PC 分档更适合围绕下面几类信号。

### 1. GPU 与 VRAM

这通常是第一层。

但即便如此，也不应只问"显卡型号是什么"，还要结合：

- `VRAM`
- 驱动版本
- 是否为移动版 / 低功耗版

### 2. 目标分辨率与帧率

PC 最容易被低估的一点，是：

- 同一块显卡
- 不同显示目标

预算可以差非常多。

所以 PC 默认分档最好不是"这块卡永远高档"，而是：

- 这块卡在当前目标分辨率和帧率下，更适合哪档

显示器刷新率另记，实际渲染目标与生效配置按前面的边界核对。

### 3. CPU 与后台环境

有些 PC 问题并不是图形档位本身，而是：

- 后台录屏
- 浏览器标签页
- 杀毒或同步工具
- 笔记本电源模式

这些因素可能改变本次表现；调查时保留 CPU 能力、当前负载与电源状态各自的记录，不因为一次后台繁忙就永久重写设备能力档。

### 4. 玩家目标与手动覆盖

PC 和移动端另一个明显差别是，PC 用户通常更能接受：

- 自己选画面与帧率取舍
- 自己关某些昂贵效果

所以 PC 分档的意义通常不是替玩家做最终决定，而是：

`给出一个有证据边界的默认起点，再允许玩家在支持范围内手动调。`

手动选项不能越过兼容阻断和必要体验约束。日志要同时保留默认建议、玩家请求、会话限制和实际生效配置，才能解释“选了高档，为什么现在不是高档效果”。

## 一个更实用的规则模型：兼容路径 + 候选配置 + 风险规则

如果把 Android 和 PC 的默认分档规则统一抽象，我更喜欢下面这种结构：

1. **检查兼容路径。** 核对必需条件和硬阻断；有已验证替代路径才采用，没有就明确不支持、阻断或待核查。
2. **形成候选映射。** 将设备能力与目标帧率、分辨率和内容方案匹配；CPU、GPU、内存等约束分别保留，不假设高低之间处处是同一顺序。
3. **应用有依据的例外。** 风险规则限定到构建、驱动、路径及配置；白名单不能越过硬约束，也不自动证明更高配置通过。
4. **处理玩家选择与会话限制。** 在允许范围内接受请求，再按已验证策略临时限载；记录实际生效值与原因。

下面只示意职责和返回状态，类型与方法均为**教学伪代码，未实现、未运行**，候选表也不是已标定结果。这里不提供未校准的分数门槛；若项目采用评分，必须先定义维度、权重与标定集，再检查边界和误判，不能直接套用分数。

```csharp
public static TierDecision Decide(
    DeviceCapability capability, Target target, RuntimeState state)
{
    // 包含版本化硬阻断和已验证替代路径；选择时机由平台适配负责。
    var path = Compatibility.SelectValidatedPath(capability);
    if (path.IsUnsupported) return TierDecision.Unsupported(path.Reason);
    if (path.IsBlocked) return TierDecision.Blocked(path.Reason);
    if (!path.IsConfirmed) return TierDecision.NeedsValidation("path_unknown");

    // 映射包含对应版本的配置约束与软风险修正。
    var mapping = CandidateRules.Find(capability, path.Id, target);
    if (mapping == null)
        return TierDecision.NeedsValidation("mapping_unknown");

    var requested = PlayerChoice.OrDefault(mapping.DefaultConfig);
    if (!mapping.Allows(requested))
        return TierDecision.NeedsValidation("config_outside_support");

    // 只使用映射中已验证的限制与恢复策略，不把热状态写回设备能力。
    var session = SessionPolicy.ApplyValidatedLimits(requested, state, mapping);
    if (!session.IsResolved)
        return TierDecision.NeedsValidation("session_policy_unknown");

    return TierDecision.Candidate(
        path.Id, mapping.RuleVersion, requested, session.EffectiveConfig);
}
```

`Candidate` 只表示按规则选出的候选，不是验收通过。未知设备可以采用项目已验证的保守配置，但前提是兼容路径和该配置的适用边界都有证据；单凭“未知”不能一律标为 Low 并放行。没有适用证据时，保留待验证与明确的产品处理路径。

### 用同一个首开任务检查这套划分

以下全是**教学条件，没有设备实测**。沿用“首次打开界面并播放特效”的任务，假设 D0 在路径 P0 下已有 Q0 的支持证据，Q0 的内部渲染目标为 `1280×720 / 30 FPS`；本表不指定真实芯片，也不推出其他配置已通过。

| 条件变化 | 应保留的判断 | 应重新检查什么 |
| --- | --- | --- |
| 面板为 120 Hz，仍请求并生效 Q0 | D0 能力和 Q0 候选不因 120 Hz 自动改变 | 记录目标/实际帧与呈现条件；不能把 120 当作渲染帧率 |
| 同一设备改为 60 FPS 目标 | 设备能力不变，目标改变 | 重新匹配候选，并验证首开、组合和持续负载；Q0 的 30 FPS 证据不能直接复用为 60 FPS 通过 |
| 本次出现有效热限信号 | 保留设备能力证据，记录会话限制 | 仅采用已验证的限载方案并保留必要信息；恢复条件另验，无效信号不填为正常 |
| 必需 API 不支持，且无已验证替代路径 | 不支持，不生成低档运行结论 | 修改支持范围或准备并验证替代路径；命中禁用规则则另记阻断 |

理解检查：若同一台 120 Hz 设备请求 60 FPS，热机后实际运行在一套限载配置，哪些字段属于能力、请求和实际状态？能否把这一条记录用于证明“设备永久为低档”或“60 FPS 配置通过”？分别指出还缺的证据。

真正校准映射时，要按 CPU/GPU/内存等差异选代表设备，再选配置可行边界附近、路径/驱动风险及未知组合做复核。绑定构建、规则、实际配置和任务阶段，分别检查首用、重复与持续运行，同时验收必要视觉/玩法信息。改目标、内容规模、驱动/API 或策略后重查受影响范围。这里交付的是校准设计，详细指标、缺失处理及首用/持续窗口接[分档验证矩阵]({{< relref "code-quality/device-tier-validation-matrix-baseline-and-visual-regression.md" >}})；实际采集与设备校准仍待开展。

这种分离也能对应到引擎：Epic 的 [Android Device Profiles 文档（UE 5.8）](https://dev.epicgames.com/documentation/en-us/unreal-engine/customizing-device-profiles-and-scalability-in-unreal-engine-projects-for-android?application_version=5.8)区分设备规则匹配与运行时 Scalability 设置。它支持我们分别记录默认选择和实际生效配置，不证明本篇候选表已经校准。

## 把能力矩阵用于选样，而不是再造一个总分

能力矩阵把设备信息、条件和证据按维度列开，用来发现差异并选择待验证组合。CPU 较强、GPU 较弱，与 CPU 较弱、GPU 较强的设备，不一定存在统一的高低顺序；换成首开、持续渲染或内存峰值任务，优先调查的约束也会改变。Epic 的 [Scalability and the Developer（UE 5.8）](https://dev.epicgames.com/documentation/en-us/unreal-engine/scalability-and-the-developer-for-unreal-engine?application_version=5.8)就用低内存但较快、GPU 快但 CPU 慢等组合说明硬件差异，并建议 QA 分别覆盖 CPU/GPU/内存维度。本节的具体表和选样练习是教学设计，不是 Epic 给出的通用设备标准。

实际矩阵的一行要能定位设备/整机、OS、驱动与图形路径；任务、构建、目标配置和阶段另作关联。每个能力值注明来源、适用版本及证据状态：可核对的硬件规格、匹配条件的运行证据、待验证假设和未知分别记录，不能混成一个“已知”。容量不等于带宽、延迟或当前剩余量，内存与存储的访问表现需要对应证据；共享内存的不同报告值也不能直接相加当作额外容量，定义沿[内存记账]({{< relref "performance/game-performance-memory-accounting.md" >}})复用。

### 同一任务，先选哪些能力差异

继续使用首开界面并播放特效的任务与 Q0 候选目标。必要体验先约定为：关键信息可读、按钮在约定就绪点可用、特效反馈的必要形状/颜色/时序保留，业务结果不因档位改变。具体接受条件需由项目确认；不能把删掉整个反馈当作性能通过，保护目标沿[体验一致性]({{< relref "performance/device-tier-experience-consistency.md" >}})展开。

下表是**完全虚构的候选样本和待验证假设，没有设备测量**。“边界”“较宽”只描述题设中的选样方向，不表示已测得剩余毫秒、已接受某档配置或推荐真实芯片。A/B/C/U 是四份候选样本记录，不是通用的设备数量要求。

| 候选样本 | CPU/GPU 线索（题设） | 容量与加载线索（题设） | 兼容与持续条件（题设） | 本轮优先安排的问题 |
| --- | --- | --- | --- | --- |
| A | CPU 侧边界候选，GPU 侧相对较宽 | 内存峰值边界候选；首开读取与激活分查 | P0 可运行性已作为题设给定，持续能力未定 | CPU：首开 CPU/等待；MEM：内存峰值与驻留 |
| B | CPU 侧相对较宽，GPU 侧边界候选 | 容量不是本轮优先差异，加载仍需记录 | P0 可运行性已给定，驱动差异的行为仍待复核 | GPU：渲染负载；PATH：路径/驱动风险 |
| C | 与 B 同 GPU 家族，不能据此继承全部结论 | 内存与加载条件仍单列 | P0 可运行性已给定；整机/电源条件与 B 不同，持续表现未知 | GPU：渲染负载；SUSTAIN：持续状态、限载与恢复 |
| U | CPU/GPU 信息或匹配证据不齐 | 容量/加载证据不齐 | 必需路径尚未确认 | UNKNOWN：未知组合的补证与处理分支；不进入未确认兼容的性能路径 |

A 不能因 GPU 线索较强就自动判高；B 也不能因 CPU 线索较强就绕过 GPU 约束。C 与 B 即使同 GPU 家族，也可能需要独立的整机、驱动和持续条件记录。反过来，同一台设备的冷/热状态是测试阶段，不应伪装成两个独立硬件样本。

U 首先处理兼容补证；确认不支持必需路径且无已验证替代时，结果是不支持。取得可用路径及配置的适用证据后，才进入相应性能验证；不能为了凑齐“低档代表机”把它直接归 Low。对于 A/B/C，本表也只安排调查重点，真实数据可以推翻这些假设，非重点项并不自动通过。

### 可复算的选样练习：数量够了，问题未必排齐

仅在这道题内，把本轮计划回答的问题限定为六个符号：CPU、GPU、MEM、PATH、SUSTAIN、UNKNOWN，含义见上表。候选记录拟安排的集合为：

```text
A = {CPU, MEM}       B = {GPU, PATH}
C = {GPU, SUSTAIN}   U = {UNKNOWN}
```

集合只统计“哪项问题已安排验证”，不统计通过项、独立运行次数或真实硬件覆盖率。

- 只选 A+B，安排了 `{CPU,MEM,GPU,PATH}` 四项，缺持续问题 SUSTAIN 和未知处理 UNKNOWN。
- 换成 A+C，仍是四项，缺路径/驱动 PATH 和未知处理 UNKNOWN；不是增加一次 GPU 检查就能补上。
- A+B+C 的并集为 `{CPU,GPU,MEM,PATH,SUSTAIN}` 五项，未知分支仍没有安排。
- 再补 U，才把**本题预先定义的六项问题**排齐；这不证明四台设备足够，也不证明六项已经通过。U 可以先是待补证的组合记录，不能据此虚报一台已完成性能测试的设备。

实际选样还要考虑用户分布、已知故障、最低支持范围与维护成本。一个样本可以承担多个问题，同一设备也可跑多个配置/路径；这些不是多个独立设备。若资源不足以补齐，保留未覆盖问题及影响，由负责人决定补样、收窄支持结论或承担有期限的风险，而不是降低记录要求来制造“矩阵完成”。

```text
目标与必要体验 → 能力/风险问题 → 选样与验证计划
                                      ↓
                               有效记录与未覆盖项
                                      ↓
                            补样、改配置或缩小支持结论
```

理解检查：若只能保留 A+B，能否宣布“已覆盖高中低档”？新增一份与 B 完全同条件、仍只安排 GPU/PATH 的记录，会补上哪个缺口？如果把目标改为 60 FPS，哪些能力记录仍可复用，哪些候选和验证计划必须重新检查？

能力矩阵给出的是选择依据；具体分辨率、阴影、动画、UI/特效与资源方案仍需形成独立的候选配置矩阵，再按前面的指标与窗口验证。不要从这张表直接生成真实机型的高中低推荐名单。

## 怎么避免规则表越写越脏

只要分档系统真的上线，规则一定会增长。

所以真正需要设计的，不是"如何永远不加规则"，而是：

`如何让新增规则不会把系统拖进一团无法解释的例外。`

我更建议至少守住下面三条。

### 1. 型号表只做例外，不做主体

默认判断一定优先走能力指纹。

型号表应该只承担：

- 已知严重风险黑名单
- 已知稳定白名单
- 少量市场特殊机型修正

### 2. 规则必须版本化并可回滚

只要某条规则会影响线上档位，就必须：

- 有版本号
- 能灰度
- 能回滚

否则你很快就会遇到这种状态：

- 大家都知道"最近好像加过一条规则"
- 但没人能说清到底是哪条导致了线上变化

### 3. 规则来源必须能回溯到证据

更稳的规则，不该来自：

- "感觉这机子不太行"

而应该来自：

- 遥测数据
- 崩溃与卡顿聚类
- 固定 baseline
- 边界机复核

也就是说，规则的来源最好是证据，而不是印象。

## 一条最小可执行路径

如果项目现在还停留在型号名单分档，我会建议先从下面这五步升级：

1. 先把当前规则拆成"主体规则"和"例外规则"
2. 先分开兼容路径、CPU/GPU/内存等能力记录、目标配置和会话状态，再形成候选映射
3. 先保留少量黑白名单，只处理已知高风险例外
4. 先把线上遥测和问题归因切到能力指纹维度
5. 先让玩家请求、实际配置、限制原因、有效性和规则版本都进入日志

这五步能让判断来源和异常分支更清楚；配置是否适用，仍由匹配条件下的验证决定。

如果把这篇文章压成一句话，我会这样收：

`先确认可运行路径，再用设备能力和目标配置选候选，以会话状态作有条件的临时限制；型号表保留有证据的例外，候选配置仍需验证。`
