> 看一帧，先说清楚在看哪次更新、哪份渲染结果、哪个显示时刻，再追踪它依赖的工作和等待。一个线程上的长条，不能独自解释整条反馈链。

本文先讲共同模型；Unity 标记以 Unity 6.0 官方文档为参照，Unreal 只作线程职责映射。平台资料在对应段落注明。教学时间线为人为设定的依赖算例，没有设备 trace、输入延迟测量或优化收益实测。

上一篇我先立了一套判断框架，重点讲的是：

- 为什么某些操作会慢
- 为什么很多问题不是“不能做”，而是“不能在那个时机做”
- 为什么掉帧、加载慢、首次卡顿和内存波动，常常是同一条链上的不同表现

但如果要把这些判断真正用起来，还缺一张更具体的地图：

`一帧到底是怎么走完的？`

很多性能误判，都是因为开发者脑子里的一帧太简单了。

最常见的简化版本大概是这样：

`Update -> Render -> Present`

这当然不算错，但它粗到几乎没法支撑工程判断。

因为一份画面所依赖的工作可能包括：

- 输入采样
- 游戏逻辑和状态推进
- 动画、AI、物理、UI 更新
- 任务系统调度
- 资源查询和依赖准备
- 文件读取、解压、反序列化
- 可见性和绘制列表构建
- 渲染命令提交
- GPU 执行
- Present 和屏幕显示

这些工作不一定每次更新都发生，也不一定在同一帧开始、结束。资源可以早已驻留，物理更新可以使用独立步长；下面的阶段编号用于解释职责，不是所有引擎固定执行的串行清单。

很多时候：

- CPU 在准备这一帧
- GPU 还在画上一帧
- 屏幕上显示的甚至是更早之前的一帧

所以这篇文章的目标很明确：

- 把一帧拆回真实链路
- 解释一帧里最常见的工作分工
- 解释卡顿最容易发生在哪些交界处
- 帮你把 Unity 和 Unreal 里看到的线程、时间轴、Profiler 现象，对应到这张地图上

## 先分清逻辑帧、渲染帧与显示刷新

日常说的“一帧”，至少可能指三个不同对象：

| 对象 | 在追踪什么 | 不能默认的关系 |
| --- | --- | --- |
| 逻辑更新／模拟步 | 哪一次输入消费和状态推进 | 不必与物理步、渲染次数一一对应 |
| 渲染帧 | 为某份状态生成并执行的一批绘制工作及其输出 | 命令提交不等于 GPU 完成，也不保证输出最终被显示 |
| 显示刷新／呈现事件 | 屏幕刷新时采用哪份图像，或系统报告的呈现时刻 | 一份图像可能重复显示；应用帧也可能被丢弃 |

Android 的固定刷新率示例会在新帧迟到时重复旧图像；DXGI flip 模式的官方队列示例则说明部分排队帧可能被丢弃。两者提示我们：记录时必须注明“帧”属于哪一层，不能只拿一个递增编号把它们强行对应。具体行为仍由平台与呈现模式决定。见 [Android Frame Pacing](https://developer.android.com/games/sdk/frame-pacing) 与 [DXGI Present](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/nf-dxgi-idxgiswapchain-present)。

以均匀输出为目标时，60 FPS 对应约 `16.67 ms` 的输出间隔，30 FPS 对应约 `33.33 ms`。这是节奏目标，**不是一次输入从发生到屏幕反馈的总时限**。多帧可以处于流水中的不同阶段；即使输出间隔稳定，排队也可能增加反馈延迟。

因此，要分别问：单位时间完成多少帧、相邻画面何时更新、这次输入多久得到可见反馈。优化其中一项，不自动证明另外两项也改善。

## 一张指标表：数字到底测了哪一段

以下是本文采用的记录口径；实际工具的同名字段必须再核对定义、单位和平台支持情况。

| 指标 | 对象与起止点 | 用途与限制 |
| --- | --- | --- |
| 应用帧间隔 | 同一个应用循环标记的两次相邻时间戳之差，ms | 看应用推进节奏；可能含等待，不等于 CPU 纯执行时间或屏幕更新间隔 |
| CPU 阶段耗时 | 指定线程／任务上某段工作的开始到结束，ms | 插桩墙钟区间可含阻塞、抢占；线程实际运行时间要结合调度数据。父子区间、并行区间不能直接相加 |
| GPU 区间耗时 | 工具关联到该渲染帧或 pass 的 GPU 起止时间，ms | 标明所含队列、上传与同步范围；CPU 调用绘制 API 的时间不能代替它 |
| 呈现间隔 | 两份相邻新图像的呈现时间戳之差，ms | 看画面更新节奏；注明是系统报告的呈现事件还是实际屏幕观测，重复刷新与丢帧怎样统计 |
| 输入到可见反馈延迟 | 约定的输入事件到对应画面变化，ms | 硬件输入、OS 事件、游戏消费是不同起点；软件呈现时间戳也不等于像素发光时刻，端到端测量需相应观测手段 |
| 加载可用时间 | 一次请求到指定用途满足就绪条件，ms | 必须说明是数据、运行对象还是首次显示可用；不能拿读盘完成代替 |

例如，Unity 6.0 的 Highlights 模块将 CPU Active Time 定义为主线程与渲染线程扣除指定等待后的较长区间；它并不是所有 CPU 核心执行时间的总和。文档也明确用 CPU/GPU 并行工作解释各自预算，不能把两根条直接相加当作输出间隔。见 [Highlights 的统计定义](https://docs.unity.com/en-us/engine/6000.0/manual/analysis/profiler/visualizing-data/highlights)。

### 平均值、分位数和卡顿事件要一起读

对于同一对象的 `N` 个连续、无遗漏间隔 `dᵢ`（ms），覆盖时长为它们的和；对应平均速率是 `1000N / Σdᵢ`。不要先对每个间隔取倒数再平均，冒充同一个统计量。应用循环计数得到的速率也不能冒充屏幕新图像的呈现速率。

P95／P99 描述所选样本的尾部，须注明分位数算法、样本数和采样窗口；它们不能替代最大值与事件记录。若用阈值定义长间隔，还要说明连续超阈值样本算一个事件还是多个、事件持续多久。低于某个 P95 阈值不能证明没有首次长卡顿。

先按“首次技能／稳定战斗／切场景／持续运行”分窗口，再保存版本、设备、API、质量档、刷新率、限帧、缓存和热状态。诊断采集与低扰动复测分别记录；工具开关、Editor／Player 和构建模式变化时，不把数字直接并入同一基线。加载完成条件见[资源可用链]({{< relref "performance/game-performance-read-does-not-mean-ready.md" >}})，持续条件见[功耗与发热]({{< relref "performance/mobile-hardware-03-power-thermal.md" >}})。

## 只看一条线程，还看不完整条反馈链

很多人刚开始看 Profiler 时，会下意识把“一帧”理解成主线程上的一段时间条。

这种理解不够，因为主线程只是整条链中的一段。

真实的一帧至少有三条时间轴值得同时放在脑子里：

- CPU 主线程和任务线程在做什么
- GPU 在做什么
- 显示系统正在把哪一帧送到屏幕

下面只示意工作可以重叠。每列不是固定时间槽，标签也不规定 GPU 必须落后一帧、显示必须落后两帧：

```text
时间 ->

CPU:  [准备 Frame N] [准备 Frame N+1] [准备 Frame N+2]
GPU:      [执行 Frame N-1] [执行 Frame N] [执行 Frame N+1]
显示:         [显示 Frame N-2] [显示 Frame N-1] [显示 Frame N]
```

实际相位取决于依赖、队列深度、限帧与显示策略。Android Frame Pacing 文档区分 pipeline 与 non-pipeline 模式，正说明流水深度需要在吞吐和延迟之间取舍，并非越深越好。见[模式说明](https://developer.android.com/games/sdk/frame-pacing#supported-operating-modes)。

这张图最重要的不是固定偏移，而是一个认知：

`你在 CPU 上“正在做的这一帧”，和玩家“正在看到的这一帧”，往往不是同一帧。`

这件事一旦理解了，很多现象就不会再显得玄学：

- 为什么某次输入延迟看起来比一帧更长
- 为什么 GPU 明明很忙，CPU 还在继续跑
- 为什么某个依赖延误会传到后续提交与呈现

## 一帧的第一步：输入并不是你按下去的那一刻

站在玩家角度，一帧往往从输入开始。

比如：

- 按下攻击键
- 拖动镜头
- 点开 UI
- 手柄摇杆转向

但从程序角度看，“输入发生”不等于“这一帧已经处理了输入”。

以一种常见的事件处理路径为例，输入可能经过：

- 输入设备与系统产生、传递输入事件
- 引擎在某个时机拉取输入
- 游戏逻辑在 update 阶段消费输入
- 角色状态机、动画或 UI 再把这次输入转成世界状态变化

这就意味着一个很重要的现实：

`输入延迟不能只看渲染。先明确起点，再看事件传递、消费、执行与显示各段。`

如果输入晚采样、逻辑晚消费、结果晚提交、显示又被后面的链路拖住，玩家就会觉得“按下去了，但游戏反应慢半拍”。

如果工具从游戏消费事件才开始计时，它就没有测到此前的输入设备和系统传递延迟。

## 第二步：主线程先把“这一轮世界状态”算出来

对于大多数游戏来说，主线程或者 Game Thread 这一层仍然是世界状态推进的核心。

它要负责的事情通常包括：

- 游戏规则更新
- 状态机推进
- 动画驱动
- AI 决策入口
- 物理结果整合
- UI 状态更新
- 场景对象的启用、禁用和生命周期变化

这一层最重要的职责不是“做最重的计算”，而是：

`把这一轮世界到底发生了什么，结算出一个稳定结果。`

需要共享结果的系统必须在约定边界保持状态一致，但不要求所有工作都在同一个主线程结束。哪些结果本轮必须可见、哪些能延后，由玩法和系统契约决定。

这里也是最容易发生卡顿放大的地方之一。

因为一旦你在主线程上做了下面这些事，风险会立刻升高：

- 阻塞等后台结果
- 大量创建和销毁对象
- 首次加载关键资源
- 触发整条依赖初始化链
- 在高交互时刻做重度 UI 刷新

这些工作集中出现时，应核对其实际成本和依赖期限；只有延误了目标关键路径，才能据此解释对应的超预算。

## 第三步：任务系统不是魔法，它只是帮你重新安排预算

任务系统允许把满足并行条件的工作移到其他执行线程。

动画计算、剔除、路径搜索、资源处理、批量数据准备，很多都会通过任务系统、Job System 或 Task Graph 分散出去。

这一步带来的好处很直接：

- 更能利用多核 CPU
- 把可并行工作和主线程收口分开
- 降低单一线程被压爆的概率

但这里也有一个常见误区：

`把工作扔到后台，不等于问题已经解决。`

结果即使在同一帧消费，也可以因并行而更早就绪。关键在于后台工作与其他工作重叠了多少，以及调度、同步、访存争用是否抵消收益；“同帧收口”本身不是失败条件。

最常见的误判就是：

- 后台线程在读资源
- 后台线程在解压
- 后台线程在准备数据

如果主线程派发后立即等待，没有可重叠工作，端到端耗时就未必缩短；即使重叠了一部分，结果尚未就绪时仍需等待。还要区分任务没轮到执行、正在执行和阻塞等待外部条件，见[线程调度与等待唤醒]({{< relref "performance/game-performance-thread-scheduling-waits.md" >}})。

所以评估任务系统时要问：

- 数据与依赖是否允许并行
- 结果最晚何时必须被消费，之前有什么工作可重叠
- 调度、同步和共享资源争用后，关键路径是否缩短

把消费推到以后也有代价：可能增加反馈延迟、跨帧状态或资源驻留。是否接受这些代价，需要同时核对玩法正确性和预算。

## 第四步：资源系统决定这一帧到底能不能拿到它想用的东西

很多开发者脑子里的一帧，会下意识忽略资源系统，仿佛资源总是已经在内存里等着用。

现实不是这样。

当一帧需要新的贴图、网格、动画片段、音频、特效或 UI 资源时，中间往往会经过一整条准备链：

- 定位资源
- 解析依赖
- 读文件
- 解压
- 反序列化
- 创建运行时对象
- 上传 GPU

这些阶段可以命中缓存、跳过、重叠或跨帧发生；上传主要针对需要图形资源的用途。只有对应依赖在本轮必须完成，才进入这次反馈的关键路径。完成条件和失败退出详见[资源可用链]({{< relref "performance/game-performance-read-does-not-mean-ready.md" >}})。

除了资源体积，还要检查：

- 资源首次出现
- 访问方式很碎
- 依赖层级过深
- 这一帧必须马上用

切场景、首放技能、首开 UI 的尖峰可以从资源准备链调查，但现象本身不能证明根因；也要排除独立的逻辑、渲染负载和调度变化。

更准确地说，是：

`资源系统在这一帧开始追账了。`

## 第五步：可见性和绘制准备并不是免费前菜

当世界状态确定、资源也基本准备好之后，渲染系统还要回答另一个问题：

`这一帧到底要画什么？`

这里通常会包含：

- 相机相关计算
- 可见性判断
- LOD 选择
- 阴影相关对象筛选
- 绘制列表构建
- 材质和 pass 归类
- render graph / render pass 准备

很多人会把这部分笼统地叫“渲染前准备”，但它并不只是前菜。

在 CPU 预算紧的时候，这一层经常就是大头之一。尤其是：

- 场景对象很多
- 可见性变化剧烈
- UI 和 3D 内容一起波动
- 需要构建很多 pass
- 资源状态变更频繁

所以不要把“渲染卡”简单理解成“GPU 太忙”。在进入 GPU 之前，CPU 端已经可能花了不少时间去决定“到底怎么画”。

## 第六步：提交渲染命令，不等于 GPU 已经完成

这是一个特别适合讲清楚的边界。

CPU 构建渲染命令、调用图形 API、准备 command buffer、切换状态，并不等于画面已经被画出来了。

在这一阶段，CPU 更像是在做这些事：

- 告诉 GPU 用哪些资源
- 告诉 GPU 以什么顺序做哪些 pass
- 告诉 GPU 这一批 draw 或 dispatch 的状态是什么
- 把命令组织成底层能执行的形式

如果把它说得更直白一点：

`CPU 在这一层做的，是交办工作，不是完成工作。`

这也是为什么你会看到一些常见现象：

- CPU 端提交很快，但 GPU 端还是晚了
- CPU 明明没满，帧时间还是被 GPU 拖住
- 某些资源上传或状态切换会让提交流水变得很碎

这一步最怕的不是“命令多”本身，而是：

- 命令组织过于零碎
- 状态切换过多
- 上传与绘制挤在一起
- 需要立刻同步确认某个结果

同步会约束依赖它的工作何时能继续，并不必然停止所有 CPU／GPU 并行。要检查等待范围，区分保证正确性的依赖与不必要的全局等待。

## 第七步：GPU 终于开始做它真正擅长的事

这里展开 GPU 的工作职责，不表示它要等所有 CPU 帧工作结束才启动。命令与依赖就绪后，GPU 可以与 CPU 的其他工作重叠。

这时 GPU 可能在做的包括：

- 顶点处理
- 光栅化
- 像素着色
- 计算 pass
- 阴影 pass
- 后处理
- 资源拷贝和上传消化

沿 GPU 时间线还要区分工作与依赖，检查限制是否来自：

- 等资源就绪
- 等某个上传完成
- 等 CPU 提交足够多的命令
- 被过重的 pass 或过宽的带宽压力拖慢

所以 GPU 问题虽然经常表现成“掉帧”，但根子未必只在 GPU 算力本身。

有证据支持时，可以评估这些调整：

- 本来能提前上传的东西没有提前上传
- 本来能拆开的 pass 没有拆开
- 本来能前置命中的状态拖到了首帧使用

GPU 当然会为这些决策买单，但这些决策未必是在 GPU 这层做的。

## 第八步：Present 请求、完成绘制与屏幕显示要分开

Present 类接口把图像交给呈现流程；调用返回不应被当作玩家已经看到了新画面的时间戳。例如 Vulkan 的 `vkQueuePresentKHR` 排队呈现请求，渲染完成依赖通过信号量衔接；接口允许阻塞，呈现请求与后续队列工作也有明确的执行边界。见 [Vulkan 呈现契约](https://docs.vulkan.org/refpages/latest/refpages/source/vkQueuePresentKHR.html)。

从绘制完成到屏幕变化，还要考虑排队、合成、显示策略及扫描输出。不同平台可能把反压体现为取交换链图像、提交、Present 或限帧等待；不能要求所有时间都出现在一个 Present 标记下。

等待也可能是有意控制节奏。Android Frame Pacing 就通过安排等待抑制过度排队；削掉等待不一定让画面更快出现，也可能只是让队列更深。见 [Frame Pacing 的长帧与排队说明](https://developer.android.com/games/sdk/frame-pacing#long-game-frames-lead-to-stuttering-and-latency)。

看到 Present 附近的长条，先查目标帧率、刷新率、GPU 完成时间与相邻呈现事件，再判断是正常节奏等待、GPU 工作未完成，还是提交与显示之间的积压。**等待占比不能独自证明故障，也不能证明 GPU 过载。**

## 教学时间线：关键路径怎样决定完成时刻

沿用技能场景，假设资源已经就绪，本次只追踪一次输入产生的视觉反馈。以下是人为设定的算例，不是任何设备的默认行为或实测数据。

约定一个简化显示模型：固定 60 Hz，在 `0、16.67、33.33 ms` 选择最新的已完成图像；没有额外队列与合成成本，选择截止点就在上述时刻。此处“选图”不等于屏幕全部像素已经改变，实际系统的合成截止点、扫描与像素响应需要另测。

| 时间（相对同一时钟，ms） | 主线程 | Worker | GPU／显示 | 依赖解释 |
| --- | --- | --- | --- | --- |
| 1 | 输入事件到达 | — | 显示旧图像 | 起点是软件事件，不含输入硬件此前延迟 |
| 2–4 | 消费输入、准备技能数据 | — | — | 到 4 才能派发任务 |
| 4–8 | 执行与任务独立的工作 | 4–11 计算技能表现数据 | — | 两条分支可以重叠 |
| 8–11 | 等任务结果 | 继续计算到 11 | — | 这是等待区间，不再记成主线程计算 3 ms |
| 11–13 | 合并结果并提交本次绘制 | 已完成 | — | 必须等两条分支都结束 |
| 13–20 | 可继续做其他允许的工作 | — | 执行本帧绘制 | 假设该批绘制在 13 开始，没有其他排队 |
| 16.67 | — | — | 新图像尚未完成，继续用旧图像 | 本次错过选图点 |
| 20–33.33 | — | — | 新图像就绪，等待下一次选图 | 不把此区间算成 GPU 计算 |
| 33.33 | — | — | 选择包含反馈的新图像 | 算例的软件事件到选图为 32.33 ms |

这里关键路径的含义是：**在给定依赖与调度下，限制目标完成时刻的那条链**。先确定目标是“命令提交”“图像就绪”还是“反馈呈现”，再追查它依赖什么；只找最宽的函数条，未必找到限制目标的工作。

在这个简化模型中，合并开始时刻为 `max(8, 11) = 11`。因此图像就绪时刻是 `11 + 2 + 7 = 20 ms`；不能把主线程的独立工作、Worker 工作和等待再全部相加。

- 若只把主线程 `4–8` 的工作缩到 `4–6`，Worker 仍在 11 完成，图像仍在 20 就绪。局部工作减少，目标完成时刻不变。
- 若只把 Worker 改成 `4–7`，主线程独立工作仍到 8，合并和提交在 `8–10`，GPU 在 `10–17`；图像提前 3 ms 就绪，但在本模型中仍赶不上 16.67 的选图点，所以对应呈现时刻未变。
- 若改为下一轮才消费任务结果，则改变了依赖期限，可能减少本轮等待，也可能推迟技能反馈。须先确认玩法能否接受，不能只用主线程条变短宣布优化成功。

这些结论只由表中假设推出。真实设备还要核对调度、GPU 队列及显示截止点；显示模式改变后，不能照搬这里的选图结果。预算怎样分项记录而不重复计时，接着看[帧预算拆账]({{< relref "performance/game-budget-06-frame-budget-breakdown.md" >}})。

## 真正危险的地方，往往都在交界处

如果把一帧拆到这里，你会发现一个很明显的规律：

真正容易出事的地方，很多都不是纯粹的单层内部，而是层与层的交界。

最典型的几类交界问题是：

### 输入到逻辑的交界

输入采样晚、消费晚、状态机更新晚，就会拉长输入到反馈的链。

### 主线程到任务系统的交界

同帧收口可以受益于并行，也可能等待尚未完成的依赖；要看目标完成时刻是否被推迟。

### 资源系统到运行时对象的交界

文件读完不等于资源可用，中间还有解压、反序列化、初始化。

### 资源准备到 GPU 上传的交界

CPU 侧觉得“都准备好了”，GPU 侧却还要吞上传成本。

### CPU 提交到 GPU 执行的交界

检查同步范围是否超过实际依赖，是否阻止了本来可以重叠的工作。

### GPU 执行到显示系统的交界

Present、交换链和显示节奏决定完成的图像何时被采用；需要与计算成本分别观测。

也就是说，真正成熟的性能判断，不是只会盯某一层，而是能看见交界。

## 为什么“后台加载了”还是会卡

这是项目里非常常见，也非常值得专门点出来的一个问题。

很多人会说：

`我已经异步加载了，为什么主线程还是卡？`

因为所谓“异步加载”，常常只异步了其中一段。

比如：

- 文件读取在后台
- 解压在后台
- 一部分解析在后台

但下面这些环节往往仍然可能回到主线程或者关键路径：

- 创建引擎对象
- 绑定依赖
- 激活组件
- 触发 Awake / BeginPlay / 生命周期回调
- 上传 GPU
- 第一次命中 shader / pipeline

如果上述依赖落在首次使用的关键路径上，后台读取完成后仍可能出现尖峰；哪个阶段最贵需要测量，不能预先指定。

可评估的调度动作包括：

- 后台准备
- 主线程错峰激活
- GPU 分帧上传
- 尽量提前预热首次命中

这些是候选动作，不是每个引擎都允许自由拆分的接口。提前准备会增加驻留，分帧可能延长就绪时间；应按[资源可用链]({{< relref "performance/game-performance-read-does-not-mean-ready.md" >}})核对用途期限、内存与取消清理。

## 为什么第一次进场景慢，第二次就快了

这个问题也很适合用“一帧链路”来解释。

首次与再次存在差异时，可以检查哪些准备被复用，而不是假定整条链只运行一次：

- 资源第一次读到内存
- 文件页是否命中系统缓存
- 解压第一次发生
- 运行时对象第一次创建
- GPU 资源第一次上传
- shader / PSO 第一次命中

第二次快，不一定是因为“游戏突然更优化了”，而是因为很多准备已经完成了。

所以当你看到“第一次卡、第二次好”的问题时，不要只记一个现象描述，而要立刻把它翻译成工程判断：

`优先怀疑首次成本，而不是稳定瓶颈。`

这条直觉对 Unity 和 Unreal 都非常重要。

## Unity 和 Unreal 里，这条一帧链路分别怎么映射

如果只讲原理，不讲引擎映射，很多人看完之后还是不知道该去哪里找问题。

### Unity 里更容易看到的，是主线程收口感

Unity 中可以从这些已插桩位置进入调查：

- Update / LateUpdate 阶段的逻辑和生命周期波动
- GC 尖峰
- Instantiate / Destroy 的集中成本
- 资源首次加载后的激活
- 渲染提交前的准备和同步

这会让很多 Unity 问题看起来像“主线程又炸了”。  
但真正的根子，未必只在主线程代码本身，往往是：

- 资源准备时机不对
- 生命周期变化太剧烈
- 一部分后台工作最终同帧收口

以 Unity 6.0 为例，`Gfx.WaitForPresentOnGfxThread` 需要结合渲染线程和 GPU 观察；`WaitForTargetFPS` 在不同上下文下可能关联限帧、VSync 或 GPU 尚未完成。标记是调查入口，不能仅凭名字认定原因。官方还区分 Editor 与 Player 的观测开销，见 [Profiler markers reference](https://docs.unity.com/en-us/engine/6000.0/manual/analysis/profiler/markers)。

### Unreal 里更容易看到的，是线程边界感

Unreal 则更容易让你直观看到：

- Game Thread
- Task Graph
- Render Thread
- RHI Thread
- GPU

这里列的是观察维度，不保证每种平台与配置都启用独立的同名线程。Epic 的[线程化渲染说明](https://dev.epicgames.com/documentation/en-us/unreal-engine/threaded-rendering-in-unreal-engine)解释 Game Thread 与 Rendering Thread 的职责和状态交接；本文只复用这个边界，不把文中的历史 API 或帧偏移当作所有 UE 配置的固定规则。

典型现象包括：

- Game Thread 太慢
- Render Thread 等待
- RHI 侧提交流水被打断
- PSO 首次创建或流送时序不合理

但你会发现，底层判断其实还是同一套：

- 工作发生得太晚
- 工作堆得太密
- 工作在交界处发生了阻塞

## PC 和手机在一帧上的风险点为什么不同

从一帧链路角度看，PC 和手机的差异不是“哪边更强”，而是“哪边更容易在哪些环节翻车”。

### PC：记录配置与运行环境

比如：

- 部分设备仍然用慢盘
- 后台软件影响 I/O 和调度
- 驱动版本和显卡架构差异放大某些提交或 shader 问题
- 用户配置太多，质量档位不合理时某些 pass 会突然过重

这些条件需要随采样保存，不能仅因某次 PC 表现不同就归因于代码。

### 手机：记录持续条件与生命周期

比如：

- 热和功耗导致 CPU/GPU 预算动态变化
- 前后台切换让生命周期变复杂
- 首次读取与缓存命中的状态不同
- 进程内存压力与资源驻留、淘汰影响后续准备

两组检查不是平台专属原因或发生率排序。持续变慢时，用[功耗与发热]({{< relref "performance/mobile-hardware-03-power-thermal.md" >}})的热信号和帧时间分别核对；内存用[内存记账]({{< relref "performance/game-performance-memory-accounting.md" >}})统一统计对象，不能从运行时长或设备类别直接推断瓶颈。

## 一份更实用的“一帧排查表”

如果你现在就要排查某个掉帧或卡顿问题，我更建议用下面这套问题先过一遍。

### 1. 这次变慢是输入晚了，还是显示晚了

玩家觉得“卡”，并不总是因为 GPU 慢。  
也可能是输入消费晚、逻辑推进晚、主线程收口晚。

### 2. 这是稳定瓶颈，还是偶发尖峰

稳定瓶颈和偶发卡顿的采样窗口与调查重点不同，也可能共享同一个原因。
稳定瓶颈更像长期超预算。  
偶发尖峰更像首次命中、同步边界、生命周期波动。

### 3. 是 CPU 在准备阶段就超时了，还是 GPU 在执行阶段超时了

这一步是最基础也最容易被跳过的。

### 4. 这一帧有没有在追资源账

如果这帧里发生了首次加载、首次解压、首次初始化、首次上传，就要优先怀疑资源链。

### 5. 有没有后台工作在本帧被强制收口

很多所谓后台任务，真正卡人的地方不是“在后台跑”，而是“这一帧必须等它跑完”。

### 6. 有没有错误的同步边界

检查等待是否限制了目标关键路径，或使图像错过呈现期限；不要把正常限帧等待当作必须删除的成本。

### 7. 这是不是平台预算变化导致的问题

在手机上尤其要问这句。因为有些问题的根本不是代码突然变差，而是设备不再给你原来的预算了。

## 我的结论

如果把这篇文章压缩成一句话，我会这样总结：

> 一帧不是一个函数调用，也不是一条线程上的时间条，而是一条从输入、逻辑、资源、提交到 GPU 和显示系统的接力链；真正容易让体验出问题的，往往是这条链路里那些被放错时机的重操作，以及层与层之间被忽略的等待边界。

理解这一点之后，再去看掉帧、加载慢、输入延迟、首次卡顿和移动端抖动，很多问题就会开始变得更容易拆。

因为你会知道自己不该只问：

- 这一帧慢不慢

而应该继续往下问：

- 慢在哪一段
- 是谁在等谁
- 这段工作为什么会落到这一帧
- 这件事能不能更早做、更晚做、分帧做，或者根本不要在关键时刻做

下一篇我会继续往最实用的一层收：

`什么事不能在什么时候做。`
