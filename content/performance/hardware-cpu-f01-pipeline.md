写游戏逻辑时，一个 `if(entity.isActive)` 是否值得优化，不能由它出现了多少次直接判断。它可能跳过大量无用工作，也可能因难以预测而让 CPU 反复执行错误路径。要区分这两种情况，需要看生成代码、输入模式和热点的实际瓶颈，再从流水线解释原因。

> 范围与证据：本文以超标量、乱序 CPU 的简化模型讲解机制，不把某款芯片的周期数推广到所有 x86 或 ARM。数值算例均标明假设，不是设备实测；Unity 查询部分按 Entities 1.0 文档说明语义，伪代码不代表已运行的项目实现。

## CPU 流水线：一条指令的旅程

CPU 不是“执行一条指令，再取下一条”。流水线（Pipeline）让多条指令的不同阶段重叠，就像汽车装配线上同时有多辆车在不同工位上作业。

下面是典型乱序核心的逻辑阶段示意，不是所有处理器共用的七级物理流水线：

```text
取指 (Fetch) → 译码 (Decode) → 重命名 / 分配 (Rename / Allocate)
    → 调度 / 发射 → 执行 (Execute) → 结果就绪 / 回写
    → 退休 (Retire，也称提交 Commit)
```

**一条指令的延迟**和**连续指令的吞吐**不是同一件事。只考虑单发射、每级一周期、没有停顿的教学模型，填满流水线后可以每周期完成一条指令，但一条指令仍需要经过多个阶段。超标量处理器还可能每周期完成多条，不能把 `CPI = 1` 当成所有现代 CPU 的理想上限。

这里按同一测量区间、同一线程与周期口径定义：

```text
IPC（Instructions Per Cycle）= 退休的架构指令数 / 周期数
CPI（Cycles Per Instruction）= 周期数 / 退休的架构指令数
```

加深流水线可以把部分组合逻辑拆到更多阶段，为提高频率创造条件，但也引入级间开销；具体频率与恢复代价不能只由级数推算。具体芯片可能有不同的取指、译码和执行路径，讨论级数时也要明确口径；后面的误预测估算不能只依赖这个数字。

## 超标量与乱序执行：怎样利用指令级并行

**超标量**（Superscalar）提供同周期处理多条指令的能力。前端供给、重命名 / 分配、执行端口和退休各有宽度限制，不能只挑一个数字就推导实际 IPC。

尤其要区分**架构指令**和处理器内部的 **micro-op（微操作）**。一条架构指令可能拆成多个微操作，也存在融合等处理；不同阶段的计数口径未必相同。例如 Intel 对 Skylake Client 的说明中，“6 uops/cycle”指 DSB（已解码微操作缓存）向 IDQ（指令解码队列）的供给能力，不是“每周期退休 6 条指令”，也推不出程序 IPC 必然达到 4～5。见 [Intel 优化手册 248966-049，§2.6.1～2.6.2](https://cdrdv2-public.intel.com/814198/248966-Optimization-Reference-Manual-V1-049.pdf)。

**乱序执行**（Out-of-Order Execution，OoO）则在可见的在途指令中选择操作数已就绪、且执行资源可用的工作先执行。寄存器重命名可以消除部分仅由寄存器名字复用造成的依赖，但不能消除“必须使用上一条计算结果”的真数据依赖。

ROB（Reorder Buffer，重排序缓冲区）是这套机制的重要部分，用来跟踪在途工作的状态，配合重命名、调度器等结构支持按序退休与异常处理。执行完成不等于已经退休；较后的工作即使先完成，也可能要等前面的指令满足退休条件。

```text
程序顺序：A → B → C → D
依赖关系：C 使用 A 的结果；B、D 与 A、C 独立

如果 A 的输入尚未就绪：B、D 可以在资源允许时先执行
A 的结果就绪后：C 才能继续
退休顺序：A → B → C → D
```

按序退休维护架构要求的程序语义，不表示所有核心按源码顺序观察到所有内存访问，也不意味着错误路径留下的微架构影响全部消失。并发可见性仍要遵守语言和 ISA 内存模型，见 [F05：内存序与并发正确性]({{< relref "performance/hardware-cpu-f05-multicore-false-sharing.md" >}})。乱序调度与退休的结构说明可参照 [Intel 早期架构优化手册，§2.1.2](https://cdrdv2-public.intel.com/821614/356477-Optimization-Reference-Manual-V2-050.pdf)。

**指令级并行**（ILP，Instruction-Level Parallelism）描述可重叠推进的独立工作。更多独立工作能给调度器更多选择，但在途窗口、端口、取指与访存资源都是有限的；一条长依赖链也不会因为“CPU 支持乱序”就自动消失。

IPC 是诊断指标，最终目标仍是更快完成同样的任务。删掉无用工作或使用 SIMD 后，指令数和 IPC 都可能下降而耗时改善；相反，多做独立但无用的计算也可能抬高 IPC。因此应一起看指令数、周期数、频率口径和耗时，不能单独追求“IPC 拉满”。见 [Intel VTune CPU 指标说明](https://www.intel.com/content/www/us/en/docs/vtune-profiler/user-guide/2024-2/cpu-metrics-reference.html)。

## 分支预测：CPU 怎样提前选择路径

前端要继续取指时，条件分支的结果可能还没算出来。若一直等到结果确定才取后续指令，就会错过本可重叠执行的工作；等待多久取决于条件的依赖链和机器状态，不是固定十几个周期。

**分支预测**（Branch Prediction）在结果确定前预测控制流，让后续工作推测执行。预测正确时，可以避免这次误预测恢复，但分支仍可能占用前端和执行资源，不能等同于零成本。预测错误时，处理器丢弃需要回滚的推测工作并转向正确路径。

可以把预测问题拆成两部分：

- **方向预测**：条件分支这次是否跳转。
- **目标预测**：如果跳转，应从哪个地址继续取指。BTB（Branch Target Buffer）用于提供缓存的分支目标信息；间接跳转和返回还可能使用历史相关预测、返回栈等结构，不能把它们统一描述为“记住上次跳去了哪里”。Intel 的 [控制流推测说明](https://www.intel.com/content/www/us/en/developer/articles/technical/software-security-guidance/technical-documentation/hardware-behavior-related-to-speculative-execution.html) 区分了这些情况。

**2-bit 饱和计数器**可用来解释一个基础方向预测模型。下面约定 T 为实际跳转、N 为实际不跳转，遇 T 加一、遇 N 减一，在两端饱和：

| 当前状态 | 预测 | 实际为 N 后 | 实际为 T 后 |
|---------|------|------------|------------|
| 00 强不跳 | N | 00 | 01 |
| 01 弱不跳 | N | 00 | 10 |
| 10 弱跳 | T | 01 | 11 |
| 11 强跳 | T | 10 | 11 |

它能对偶发的反向结果保持一定稳定性，但这只是教学模型，不代表每款现代 CPU 都给每个分支独占一个计数器。实际预测器可以利用更长的历史，有限的预测表也可能出现容量和别名干扰。

所以不能给“现代 CPU”指定统一的 95%～99% 命中率。需要说明测量的是哪个负载、哪些分支，以及如何计数；整个程序的总体命中率也可能掩盖某个热点分支的高失误率。

## 预测失败的代价：先明确估算口径

发生误预测时，可以用以下过程理解代价：

1. 分支实际结果可用，发现方向或目标与预测不符。
2. 丢弃错误路径上的较新推测工作，恢复必要状态。
3. 从正确路径重新供给指令，继续执行。

这不意味着把所有更早的有效工作一起清掉。错误路径浪费的执行资源、恢复和重新供给的开销，以及它们与其他工作的重叠，都会影响最终耗时。**误预测代价不等于流水线深度乘以时钟周期**，也不是每次固定的 15 cycles。Intel 手册本身就按具体微架构和取指路径讨论代价差异，见 [优化手册 248966-049，§B.5.6.1](https://cdrdv2-public.intel.com/814198/248966-Optimization-Reference-Manual-V1-049.pdf)。

若只是做一阶预算，可以明确采用下面的模型：

```text
误预测次数 ≈ 该分支动态执行次数 × 误预测率
估算额外时间 ≈ 误预测次数 × 平均暴露代价（cycle/miss）÷ 频率（cycle/s）
```

这里的“平均暴露代价”是模型中未被其他工作掩盖的平均额外周期，需要在指定负载与测量方法下估计；不能直接拿某条指令的延迟替代。假设它为 15 cycles、频率恒定为 3 GHz，一条分支执行 10,000 次，则：

| 假设的误预测率 | 估算误预测次数 | 模型中的额外时间 |
|---------------|---------------|------------------|
| 10% | 1,000 | 5 微秒 |
| 50% | 5,000 | 25 微秒 |
| 100% | 10,000 | 50 微秒 |

这张表是单位换算和敏感性分析，**不是 Skylake、ARM 或某个游戏的实测**。50 微秒约占 16.67 ms 的 0.3%，但多个热点之间若有重叠或瓶颈转移，也不能把单独测得的损失无条件相加。

实际定位还应结合分支执行数、误预测事件、周期数和总耗时。计数器事件是否包含条件分支、其他分支或推测执行，需按设备文档核对。`Bad Speculation` 一类指标可能统计浪费的流水线槽位，并且还包括其他错误推测，不能直接当成分支误预测率。ARM 的代价也应按具体核心验证，不能仅因架构名称就断言比桌面更小。

## 数据模式怎样影响预测命中率

预测器利用过去的行为预测未来，所以输入的排列方式很重要；但生成代码、历史相关性、预测器容量和训练状态同样会影响结果。

**稳定模式——通常容易建立一致预测：**

```c
// 示意：假设最终机器码保留了这条条件分支，arr 全为正数
for (int i = 0; i < N; i++) {
    if (arr[i] > 0) process(arr[i]);
}
// 条件结果稳定；这不表示整个循环没有分支或其他成本
```

源码条件为 true 不等于机器码分支一定是 taken：编译器可能生成“条件不成立则跳过”的形式，分析时要看实际跳转方向。

**不可预测模式——需要把概率前提写清：**

```c
// 示意：正负结果等概率，且与预测器可用历史没有可利用的相关性
for (int i = 0; i < N; i++) {
    if (arr[i] > 0) process(arr[i]);
}
// 理想独立模型下，长期预期误预测率约为 50%，不是每轮都失败
```

若每次结果与预测器已知信息独立且等概率，无论根据历史猜哪边，下一次猜错的概率都是 1/2。这是概率模型的结论；固定伪随机数组反复遍历，并不自动满足这个前提，较短的重复模式可能被学到。相同的 true 占比也可以对应“全部 true 集中在前面”或“到处交错”等不同顺序。

有序与随机数组的对比适合设计实验，但不能据此给所有平台一个固定的 3～4 倍加速：编译器可能把条件转换成选择指令或 SIMD 掩码，测试时甚至没有那条逐元素条件跳转。Arm 的 [条件选择指令说明（§9 Program flow）](https://developer.arm.com/-/media/Arm%20Developer%20Community/PDF/Learn%20the%20Architecture/Armv8-A%20Instruction%20Set%20Architecture.pdf?revision=818c7869-3849-4e5d-bde2-710e69defb57) 展示了同一 `if` 的不同实现方式。

做对照时至少控制以下条件：

- 使用相同的数据集合、元素数和处理结果，只改变排列；先确认业务不依赖顺序。
- 查看热点汇编，确定是否有目标条件分支，以及编译器是否向量化或消除了计算。
- 把数据生成、排序和编译预热与内核计时分开；若要评估“排序是否值得”，再把排序与维护成本计回总账。
- 记录编译器与优化选项、目标 CPU、工作集、重复次数、分支事件和耗时，避免把缓存或处理工作量的变化全部归因于预测。

也不应无条件把分支改成无分支代码。选择、掩码或同时计算候选结果可能增加指令、访存和数据依赖；当分支可预测，或能跳过昂贵工作时，保留分支可能更划算。

## 游戏循环里的分支问题：一个教学算例

设想一个按对象列表遍历的逻辑，以下代码仅示意筛选过程，省略类型定义和上下文：

```csharp
// 对象列表遍历示意
void UpdateAll(List<Entity> entities) {
    foreach (var e in entities) {
        if (!e.isActive) continue;       // 分支 1
        if (e.health <= 0) continue;     // 分支 2
        if (!e.hasAIComponent) continue; // 分支 3
        e.AIComponent.Tick(deltaTime);
    }
}
```

假设场景里有 10,000 个 Entity，其中：
- 活跃率 30%（3,000 个 isActive == true）
- 活跃的里面 80% 血量 > 0（2,400 个）
- 其中 90% 有 AI 组件（2,160 个需要真正执行逻辑）

因为 `continue` 会提前跳过后续判断，并不是每个 Entity 都执行三道判断。在上述假设中，源码层面的评估次数是：

| 判断或工作 | 次数 |
|-----------|------|
| 检查 isActive | 10,000 |
| 检查 health | 3,000 |
| 检查 hasAIComponent | 2,400 |
| 执行 Tick | 2,160 |

三项判断合计 15,400 次，真正执行 Tick 的实体占 21.6%。这只能说明候选与有效工作量的比例，**不能说明 78.4% 的执行时间都浪费在筛选上**；一次 Tick 可能远比几次检查昂贵。

活跃率 30% 也推不出第一道分支的预测命中率。即便活跃状态在列表中混杂，仍要看它是否与位置、历史或其他分支相关。只有最终机器码、各分支的动态执行次数和误预测率明确后，才能使用上一节的估算模型。不能从三个人数比例直接得出“每帧损失 20 微秒”。

对象列表还可能包含指针解引用与非连续字段访问，但是否形成随机访存、是否 cache miss，都取决于实际对象布局与缓存状态。应把访存和分支分别定位，相关机制见 [F02：Cache 与访问局部性]({{< relref "performance/hardware-cpu-f02-cache.md" >}})。

## ECS 如何减少重复筛选，以及它的边界

把符合条件的对象组织成可直接遍历的工作集合，可以减少反复筛选。这种方法也能用于普通对象列表；ECS 的组件组织和查询机制为其中一部分条件提供了系统支持，但不会自动移走所有业务分支。

以 **Unity Entities 1.0** 为例，`EntityQuery` 可以按组件类型匹配 Archetype，并结合其支持的过滤条件确定参与处理的数据。一个查询可能涉及多个 Archetype 和多个 Chunk，不能统一描述成“调度前生成一个只含目标实体的连续内存块”。Chunk 内按组件类型存放数组，也不意味着所有结果或组件内部字段全局连续，见 [Archetype 与 Chunk](https://docs.unity3d.com/Packages/com.unity.entities@1.0/manual/concepts-archetypes.html)。

三种条件需要分别建模：

| 原判断 | 可以怎样组织 | 仍需负责什么 |
|-------|-------------|-------------|
| 是否有 AI 数据 | 查询要求存在相应组件 | “有组件”是否真的等于业务上的“参与 AI” |
| 是否活跃 | 由业务维护 ActiveTag，或使用 enableable 组件表达状态 | 状态更新、查询选项及依赖必须正确 |
| health > 0 | 在循环里检查数值，或另行维护 Alive 状态 / 候选集合 | 有 Health 组件不等于其值大于零；生命值变化时必须同步状态 |

组件存在性查询不是普通字段的任意数值谓词。Shared component filter 和 change filter 也有各自语义，不能替代通用 `health > 0` 筛选。参见 [创建查询](https://docs.unity3d.com/Packages/com.unity.entities@1.0/manual/systems-entityquery-create.html) 与 [查询过滤器](https://docs.unity3d.com/Packages/com.unity.entities@1.0/manual/systems-entityquery-filters.html)。

下面用逻辑伪代码说明查询与业务条件的分工：

```text
query 要求：ActiveTag、AI 数据、Health 组件

for each 匹配的 chunk / entity:
    if entity.Health.Value <= 0:
        continue
    TickAI(entity)
```

这里能减少对组件存在性的逐实体判断，**血量判断仍然存在**。如果希望核心 AI 循环连血量判断也不做，就需要另外维护正确的可执行集合：

```text
状态变化时或单独筛选阶段：
    更新 Active / Alive / AI 资格
    处理对应的组件状态或工作集合

AI 处理阶段：
    遍历满足已维护条件的实体
    执行 TickAI（内部仍可能有分支）
```

成本被改变或转移，并没有消失。添加、移除普通组件会涉及结构变化；enableable 组件能在不做结构变化的情况下切换状态，但查询仍需要处理启用状态，相关数据访问仍需正确依赖。具体约定见 [Enableable components](https://docs.unity3d.com/Packages/com.unity.entities@1.0/manual/components-enableable-intro.html)。

工程上要比较“状态维护 + 查询遍历 + 实际工作”的总成本。如果每帧先扫一遍全量数据才能维护资格，或状态频繁切换，未必比直接判断更快。还需保证执行顺序、随机数消费和状态变化的时点符合业务语义。

因此，查询缩小工作集合、组件数组提高局部性、Burst 向量化和 Job 并行应分别观察。不能由“使用 ECS”推出热循环无分支、流水线满载、IPC 接近上限，更不能据此承诺数量级收益。向量化条件与布局取舍分别见 [F03：SIMD]({{< relref "performance/hardware-cpu-f03-simd.md" >}}) 和 [F06：数据布局]({{< relref "performance/hardware-cpu-f06-data-layout.md" >}})。

## 小结

| 机制 | 能解释什么 | 不能直接推出什么 |
|------|-----------|------------------|
| 流水线 | 指令不同阶段可以重叠 | 流水线级数就是误预测罚时 |
| 超标量与乱序 | 在资源允许时并行推进独立工作 | micro-op 吞吐就是架构 IPC；真依赖自动消失 |
| 分支预测 | 在结果确定前继续推进控制流 | 预测正确零成本；所有负载共用一个命中率 |
| 输入模式 | 结果顺序和历史相关性影响预测 | 随机就每轮失败；排序固定快几倍 |
| IPC / CPI | 帮助定位执行效率变化 | IPC 更高就一定更快完成任务 |
| ECS 查询与状态分组 | 减少部分重复筛选、改变数据组织 | 自动筛选 Health 数值；维护和遍历没有成本 |

理解流水线不是为了消灭源码里的 `if`。它帮助我们把问题落到可验证的因果链上：实际生成了什么指令，哪些工作受依赖或错误推测限制，改写又引入了哪些额外成本。最终用相同任务的结果与耗时确认优化，而不是用分支数量或单个硬件指标代替判断。
