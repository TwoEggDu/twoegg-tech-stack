切换场景以后，旧对象数量已经下降，系统监控里的内存却没有降回原位。另一个工具又给出不同的数字：引擎显示的已用量、进程的驻留量、图形资源估算，看起来都在回答“游戏占了多少内存”，却无法直接对上。

此时，先增加一次 GC、缩小对象池，或者把预加载全部关掉，都可能改错地方。要判断是否泄漏、是否超过预算，首先需要弄清楚：**谁在统计什么对象，处于哪一层，统计的是哪个时刻？**

> 阅读范围：本文建立通用分层，再用 Windows 普通可分页内存、Linux 6.8 的 proc 口径、Android 和 Apple 文档说明平台差异；引擎映射采用 Unity 6.0 文档。场景数字是教学算例，没有设备采样、引擎运行或项目收益实测。具体 GC、驱动与 OS 回收算法留给专项。

## 一个对象，为什么会出现在几本账里

游戏代码看到的是对象、数组、纹理和资源句柄；分配器看到的是分配块、空闲块与池；OS 管理地址映射、物理页及后备数据；硬件则执行地址转换与数据访问。同一份资源可以同时出现在这些观察里，不能把它们都相加。

```text
业务寿命：场景、对象、资源引用 —— 谁还需要这份数据？
分配管理：托管堆、原生分配器、池 —— 哪些块在用，哪些可复用？
虚拟内存：地址区间、映射与权限 —— 这些地址允许怎样访问？
物理与后备：驻留页、文件内容等 —— 当前数据在哪里，怎样恢复？
```

这不是四份独立存储，也不是每个对象都单独向 OS 申请一页。小对象通常可以共用分配器取得的页面；一个资源也可能有文件字节、解码缓冲、运行时对象和 GPU 数据等不同表示。

因此要分别问两件事：同一份分配是否被多个工具重复统计，以及同一资源是否真的同时保留了多份表示。前者要统一口径，后者才可能是减少峰值的机会。

## 虚拟地址是访问位置，物理页是映射的承载

进程中的普通指针使用虚拟地址，不能直接把指针值理解成 RAM 上的位置。OS 维护页表，把虚拟页映射到物理页并记录访问权限；不同进程可以拥有相同数值的虚拟地址，却访问不同的数据，也可以通过受控映射共享页面。参见 [Microsoft 虚拟地址空间](https://learn.microsoft.com/en-us/windows/win32/memory/virtual-address-space)。

可以把普通分页访问抽象成“虚拟页号 + 页内偏移”：找到对应物理页后，再定位页内的数据。于是，一段连续虚拟地址并不要求背后所有物理页连续；反过来，地址空间足够大也不能证明有足够物理内存承载当前访问。

MMU 负责地址转换，TLB 缓存转换结果，减少重复查页表的开销。**TLB Miss、数据 Cache Miss 与缺页异常是不同事件**：前者查不到缓存的转换，不必然缺页；数据没命中某级 CPU Cache，也不意味着 OS 要从磁盘恢复它。Linux 的[页表说明](https://docs.kernel.org/mm/page_tables.html)解释了这些职责。页大小和转换结构依架构与配置而异，本文不固定为 4 KiB。

硬件层的延迟和带宽问题，可回到 [F04：内存带宽]({{< relref "performance/hardware-cpu-f04-memory-bandwidth.md" >}})。这里关心的是：地址能否访问、数据是否驻留，以及工具怎样记账。

## 分配成功、已经驻留、可以复用，是三个不同阶段

先用 Windows 的 `VirtualAlloc` 建立一个具体模型。下表只讨论普通可分页私有内存，不覆盖大页、锁页等特殊机制。

| 操作或状态 | 改变了什么 | 不能据此认定什么 |
| --- | --- | --- |
| 保留地址区间（Reserve） | 占住一段虚拟地址供后续使用 | 整段 RAM 已经分配给进程 |
| 提交页面（Commit） | 计入系统提交记账，使页面可按权限使用 | 所有物理页已经驻留，或已写入分页文件 |
| 实际访问页面 | 可能需要建立物理页与映射，再完成访问 | 首次访问成本已经包含在分配调用里 |

`MEM_COMMIT` 的契约与物理页按需取得的区别，见 [VirtualAlloc 文档](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualalloc)。这里的提交会消耗系统提交额度，后备能力与 RAM、分页文件有关，而不是提前把这些字节写进分页文件。例如先保留一大片地址、只提交其中一部分，是合法的管理方式；这个例子不能直接套成 `new byte[]` 的时间线，因为运行时还会处理分配、初始化等工作。

Linux 则有可配置的 overcommit 策略，不能把 Windows 的提交语义逐项搬到 `malloc` 或 `mmap` 上。分配返回成功不等于所有页面已驻留；后续是否能满足访问，还受策略和资源限制影响。参见 [Linux Overcommit Accounting](https://docs.kernel.org/mm/overcommit-accounting.html)。

释放也需要分层。业务解除引用，不等于 GC 已完成回收；分配器把块标为空闲，不等于整页都空了，更不等于它立即把页面归还给 OS。池化还会主动保留容量，换取后续复用。

Unity 6.0 的[托管内存说明](https://docs.unity.com/en-us/engine/6000.0/manual/analysis/performance-memory/managed-memory/introduction)明确区分堆内可复用空间和归还 OS，并说明归还时机不能依赖；托管 GC 也不负责回收全部原生资源。这里的工程判断是：**占用没有马上下降，只是调查入口，不能单凭它认定泄漏或认定没有泄漏。** 应继续查对象可达性、原生持有者、池容量和多轮操作后的增长趋势。

## 缺页为何不总是读盘，文件映射为何不等于资源可用

Windows 的 Working Set 指当前驻留的可分页页面集合，不包含 AWE、大页等非可分页分配。缺页处理有时不需要读后备存储，例如首次访问需求零页；硬缺页才需要从分页文件或映射文件读取数据。工作集被裁剪，也不表示业务对象已销毁。参见 [Microsoft Working Set](https://learn.microsoft.com/en-us/windows/win32/memory/working-set)。

所以，“发生了缺页”不能直接翻译成“从 swap 读回来了”，缺页计数上升也不能单独证明某一帧的卡顿来自磁盘。需要把事件类型、I/O 和关键线程时间线对齐；访问没有权限或无效映射，还可能以访问错误结束，不能把所有异常都当作可恢复加载。

接着区分页面的数据来源：普通文件映射可以从文件内容恢复；匿名内存没有这样一份可直接重读的普通文件原件。干净文件页在适当条件下可丢弃后重读，已经修改且需要保留的数据则不能随意丢弃，如何回收、写回或压缩取决于映射类型和平台。

Linux `mmap` 建立的是地址映射；`MAP_PRIVATE` 的修改采用写时复制，不写回原文件。一个最初共享文件内容的页面，写入后可能变成私有副本。这解释了为什么“映射了多大的文件”和“当前私有占用”不是同一个数。具体契约见 [mmap 手册](https://man7.org/linux/man-pages/man2/mmap.2.html)。

对游戏而言，即使文件页已经可读，压缩数据仍可能需要解码，资源还可能需要构建对象和上传 GPU。这些新表示可能与原文件页同时存在。映射可以改变读取路径，但不能凭 API 名字推出零拷贝、零峰值或不卡顿。加载阶段的衔接可读[资源可用链]({{< relref "performance/game-performance-read-does-not-mean-ready.md" >}})，I/O 机制继续进入 [OS I/O]({{< relref "engine-toolchain/storage-io-04-os-io-sync-async-dma-mmap-read-ahead-queue-depth.md" >}})。

## 比较内存数字之前，先写出指标的定义

以下指标提供不同视角，不构成统一的“总量公式”。

| 指标或观察层 | 回答的问题 | 使用边界 |
| --- | --- | --- |
| 虚拟地址区间大小 | 进程映射或保留了多大地址范围 | 不直接表示 RAM 占用 |
| Windows Commit 与 Working Set | 提交记账多少；可分页页面当前驻留多少 | 两个指标有重叠，不能相加；文件映射与特殊分配要另核对 |
| Linux/Android RSS 与 PSS | 驻留页计数；按共享关系分摊后的驻留量 | RSS 会在多个进程中重复计共享页，PSS 不是独占内存 |
| Apple memory footprint | 系统如何计入应用的内存负担 | 不等于全部驻留页的简单总和，按 Apple 工具定义解释 |
| 引擎 Used／Reserved／对象分类 | 引擎跟踪到哪些分配、池容量和对象 | 不等于 OS 的同名统计，也不保证覆盖驱动和插件 |

以普通页面的理想模型说明共享记账：进程 A 有 80 MiB 私有驻留页，再与 B 共享 40 MiB，且这 40 MiB 只由两者等份分摊，则 A 的 RSS 为 120 MiB，PSS 为 100 MiB。A 不做任何新分配，共享者改变也可能改变 PSS。实际字段与特殊页的例外要按内核版本核对，见 [Linux 6.8 proc 文档](https://www.kernel.org/doc/html/v6.8/filesystems/proc.html)。这些数也不能代替对象引用关系。

Android 文档还区分 RSS、PSS、USS，以及 RAM、zRAM 与存储：zRAM 使用 RAM 保存压缩页，并不是额外增加的物理 RAM。不要将 Java 堆上限当作 Unity 整个进程的预算，原生、图形和系统侧仍有自己的占用。参见 [Android 内存分配说明](https://developer.android.com/topic/performance/memory-management)。

Apple 的 [WWDC22 游戏内存讲解](https://developer.apple.com/videos/play/wwdc2022/10106/)区分 clean、dirty 以及压缩／交换相关记账：可重读的干净文件页可能驻留却不计入该讲解中的 footprint；被压缩或换出的脏页仍可能按原始大小计入。因此 footprint 与驻留量不能互换。在 Apple silicon 上，相关 CPU/GPU 资源共享物理内存，也不能把系统 footprint 再加一遍引擎图形资源估算。具体字段应随工具和平台版本记录，不从一个平台的名词推算另一个平台的数值。

Unity 6.0 的 [Memory Profiler 模块](https://docs.unity.com/en-us/engine/6000.0/manual/analysis/profiler/visualizing-data/memory/memory)区分 tracked、reserved 与 untracked，部分插件、驱动等内存可能不在引擎跟踪范围内。Unity 的 Reserved 描述其管理和池分配，不能直接当作 `VirtualAlloc(MEM_RESERVE)` 的地址总量；图形统计也可能是估算。比较时应记录 Player／Editor、引擎与工具版本、平台和采样时刻。

由此得到一个操作原则：**用 OS 指标约束进程，用引擎和分配记录寻找归属。两者需要对照，不要求它们天然相等。** 无法解释的差额保留为待定位项，不能统一塞进“泄漏”或“驱动”。

## 用切场景模型，把统计口径变成预算取舍

下面是人为设定的预算模型，单位为 MiB。假设每行都是同一时刻、按同一种规则计入的成本，分类互斥，公共资源只计一次；它不是把 RSS、PSS、Commit 和纹理估算混加，也不是任何设备的真实 footprint。

| 分类 | A 场景稳定时 | A 与 B 交接时 | B 场景稳定时 |
| --- | ---: | ---: | ---: |
| 公共运行时与共享资源 | 160 | 160 | 160 |
| A 独有资源 | 220 | 220 | 0 |
| B 独有资源 | 0 | 260 | 260 |
| 本阶段临时缓冲 | 20 | 120 | 20 |
| 同口径合计 | 400 | 760 | 440 |

只看两个稳定点，会以为预算只需覆盖 440 MiB；交接点却出现 760 MiB。若这只是三个采样点，它也只能称为“已观察到的最高值”，不能证明中间没有更高峰值。真实采样应覆盖整个交接窗口。

在这个模型里，可以比较三种改法：

- **提前释放 A 的 100 MiB 独有资源。** 若同一峰值时刻其余项不变，模型变为 660 MiB。但前提是旧画面、回调和在途任务不再使用它；分配器或驱动保留内存时，OS 指标未必立即同幅下降。
- **将临时缓冲并发量从 120 限到 60 MiB。** 模型变为 700 MiB，代价可能是准备时间更长。应按在途字节和缓冲寿命控制，单纯限制任务数量未必约束不同大小任务的峰值。
- **减少 B 的预加载范围。** 可以缩小重叠，但也可能把读取、解码或首次使用成本推迟到玩家操作期间，需要同时验收体验。

这些方案不是只由程序一方决定。内容负责人需要给出哪些资源会同时出现；客户端明确持有者、并发上限与取消后的释放责任；渲染侧核对 GPU 在途使用；QA 用相同切换路径验证峰值和交互结果。这样，预算才从一张总量表变成各方可以执行的约定。

## 预算要约定观察窗口，也要约定超出以后怎么办

建议为每个目标设备档位维护一份足够小的记录：

| 要记录的内容 | 它支撑的判断 |
| --- | --- |
| 程序／内容版本、设备、OS、图形 API、工具和构建方式 | 这次数字与上次是否可比 |
| 冷启动、首次进入、稳定运行、切换、重复进入等阶段 | 优化是否只是把成本挪到别处 |
| 选定的进程指标、分配归属、峰值和操作后的残留趋势 | 超的是哪个预算，谁有能力改变 |
| 采样频率、快照时机、工具扰动与未覆盖项 | 有没有漏掉短暂重叠，数字还缺什么 |
| 预算线、余量、超出时的降档／限流／阻断规则 | 发现问题后怎样处理和复验 |

项目预算线来自目标设备验证与产品取舍，不是系统承诺的终止阈值，更不能用标称 RAM 减一个固定常数获得。一次低占用也不证明所有后台压力和内容组合都安全。

如果发生退出，先区分分配失败、系统终止和程序错误。Apple 的 [jetsam 报告说明](https://developer.apple.com/documentation/xcode/identifying-high-memory-use-with-jetsam-event-reports)提供系统内存压力终止的调查入口；“回到桌面”本身不足以定因。帧时间变差时，则同时查看[线程运行与等待]({{< relref "performance/game-performance-thread-scheduling-waits.md" >}})，不要用一张内存截图替代耗时证据。

本篇尚未执行的最小验证可以分两步：先观察一块缓冲从分配、触碰到释放时各层指标的差异，记录平台、分配方式与采样误差；再对同一场景切换重复采样，只改变一项驻留或并发策略，比较峰值、残留、帧时间、可操作时间与资源正确性。第一步解释机制，第二步才可能支持产品优化结论。
