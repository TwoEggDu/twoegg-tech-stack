> 跨平台时，要重新核对设备能力、运行状态和产品目标。平台名称帮助选择调查条件，不能替代对当前问题的取证。

本文与[性能工作流]({{< relref "performance/game-performance-methodology-summary.md" >}})共同讨论诊断的归因和比较边界。文中场景是调查候选，不是跨平台发生率统计；本文没有设备对照实测，也不认定 PC 必然稳定、手机必然持续降频。

前面这一组文章，我一直在做一件事：

- 先把性能问题拆成 `CPU / GPU / I/O / Memory / Sync / Thermal`
- 再把一帧、加载链、生命周期、内存行为和引擎现场分别讲清楚

到了这一步，有一个很重要、也很容易被低估的问题必须单独拿出来讲：

`为什么同样一套游戏、同样一个问题，在手机和 PC 上经常完全不像一回事。`

很多团队在跨平台开发里最容易踩的坑，不是完全没做适配，而是：

- 还在用 PC 的直觉理解手机
- 或者反过来，用手机的直觉误判 PC

这会导致一些特别常见的错误判断：

- 觉得手机只是“配置差一点的 PC”
- 觉得 PC 只是“不会发热的高性能手机”
- 觉得同样一套资源组织、加载时机和渲染策略应该天然可通用

这些理解都太浅。

因为真正决定性能问题长相的，往往不是芯片名字，而是下面这些现实条件：

- 预算是不是稳定
- 功耗和温度会不会动态收缩预算
- 存储和内存路径是不是足够宽松
- 用户环境是不是可控
- 应用生命周期是不是稳定
- 用户是否接受你用画质设置、硬件分档和后台环境去换性能

所以这篇文章的目标很明确：

- 解释跨平台时需要重新核对哪些条件
- 解释同一现象为何仍需按具体设备与运行状态取证
- 帮你知道什么时候该怀疑平台预算，什么时候该怀疑环境差异

## 先拆一个最常见的误区：手机不是“弱 PC”，PC 也不是“强手机”

如果只看算力表面，很容易把两者理解成同一条坐标轴：

- 手机是低端
- PC 是高端

这当然不是完全错误，但它太粗了。

真正的差异不是简单的强弱，而是：

`它们面对的约束类型不同。`

可以先列一份共同的条件表，再按目标设备补充平台特有证据：

| 条件 | PC 调查示例 | 手机调查示例 |
| --- | --- | --- |
| 执行与图形路径 | CPU／GPU、驱动、图形 API、渲染尺寸与刷新率 | SoC／GPU、驱动、图形 API、质量与实际渲染尺寸 |
| 运行条件 | 供电、电源策略、散热、后台负载 | 供电、电源策略、散热、后台负载 |
| 内存与内容 | 系统及进程口径、驻留、缓存、首次准备 | 系统及进程口径、驻留、缓存、首次准备 |
| 生命周期 | 焦点变化、最小化、设备或窗口状态 | 前后台、进程寿命、Surface／界面及游戏会话状态 |

同一行是可核对条件，不是两边采用相同策略的保证。Windows 的[处理器电源管理说明](https://learn.microsoft.com/en-us/windows-hardware/customize/power-settings/configure-processor-power-management-options)也包含性能状态和平台约束；Android 的[Thermal API 指南](https://developer.android.com/games/optimize/adpf/thermal)则提供热约束调查入口。两份资料不能用来排列所有设备的问题发生率。

## 在 PC 上，记录硬件与运行环境

调查跨机器差异时，先保存具体配置和运行状态。

同一款游戏在 PC 上可能面对：

- 不同 CPU
- 不同 GPU
- 不同驱动
- 不同存储介质
- 不同分辨率和刷新率
- 不同后台软件
- 不同电源模式

这就意味着一件事：

`PC 上的很多性能问题，本质上不是你的一套代码能不能跑，而是它在多少种用户环境下还能稳定地跑。`

这会直接改变你的性能直觉。

在 PC 上，你更需要习惯去想这些问题：

- 某个问题是不是只出在部分硬件组合上
- 某个问题是不是被某类驱动放大
- 某个问题是不是在开发机上不明显，但在低配盘、慢盘、后台复杂环境里就会出事
- 某个渲染方案是不是需要给更多画质档位和回退路径

所以 PC 上很多时候真正重要的不是“榨干硬件”，而是：

- 兼容性分层
- 配置分档
- 回退策略
- 对环境差异的容错

## 在手机上，检查持续运行条件

短时间满足目标不代表持续窗口也满足；但持续变慢本身不证明热限制。保持操作负载和内容可比，再核对平台热状态、帧时间、资源驻留与后台活动。

如果有证据支持执行能力受到约束，再评估降载、质量恢复与产品接受条件。运行时长、温度与频率各有不同口径，不规定“玩几分钟后一定降频”。具体模型复用[功耗与发热]({{< relref "performance/mobile-hardware-03-power-thermal.md" >}})。PC 同样需要按设备和供电、散热状态验证持续表现。

## 同样的 CPU 问题，在 PC 和手机上为什么经常不是一回事

### 在 PC 上

PC 上可调查的 CPU 路径包括：

- 某些配置下主线程顶不住
- 某些场景在高刷新率和复杂逻辑下持续 CPU bound
- 某些后台环境让 CPU 调度变得更差

这类问题更像：

- 逻辑预算不够
- 环境复杂度在放大问题
- 某些机器的持续性能比开发机差很多

所以 PC 上的 CPU 直觉更偏向：

- 做配置分档
- 做逻辑热点治理
- 看不同机器上的主线程预算

### 在手机上

手机上的 CPU 调查也要区分执行、调度与等待；若已有持续约束证据，还可以检查：

- 热起来以后主线程余量没了
- 本来还能接受的生命周期尖峰开始变成明显卡顿
- 解压、解析、对象初始化在持续运行后更危险

所以手机上的 CPU 直觉更偏向：

- 不要假设当前频率永远在
- 不要让高风险收口发生在热机后的关键帧
- 不要把“勉强能跑”当成“长期安全”

两类设备都要检查执行能力与运行环境；这些候选不构成平台专属的原因分类。

## 同样的 GPU 问题，在 PC 和手机上为什么也不是一回事

### 在 PC 上

PC 上可调查的 GPU 负载包括：

- 分辨率太高
- 后处理太重
- 阴影和透明太贵
- 某些材质太夸张

这些是候选负载，需通过时间线与对照确认。

但 PC 上更有意思的一点是：

很多 GPU 问题你可以通过这些办法去换：

- 提供更多画质设置
- 降分辨率或用不同 upscale 策略
- 给不同配置分层
- 允许用户自己在画面和性能之间取舍

设置项提供哪些取舍由产品决定；可调设置不能替代默认路径的验收。

### 在手机上

手机 GPU 调查中也应按具体硬件与采样检查：

- 带宽敏感
- overdraw 敏感
- 后处理和大 render target 更危险
- 热和功耗会持续改变 GPU 预算

针对“画面太重”，除调设置外，还可以检查：

- 这套渲染思路本身是不是就不适合这个预算
- 某些 pass 是不是应该从设计上减少
- 某些透明、特效、全屏效果是不是本来就不该这么铺

两边都可以评估分档、回退或减少工作量；选择依据是目标与证据，而非设备类别。

## 同样的 I/O 和加载问题，在两个平台上为什么主因经常不同

### 在 PC 上

PC 读取调查可先记录：

- 用户存储介质差异非常大
- 有人是 NVMe SSD
- 有人是 SATA SSD
- 甚至还有人是 HDD
- 后台软件可能随时影响磁盘访问

所以 PC 上的加载直觉必须很早就把“环境差异”纳入考虑。

某个在开发机 NVMe 上看起来没有问题的方案，到了慢盘用户那边，可能会直接暴露出：

- 小文件海量访问问题
- 首次加载尖峰
- streaming 边界抖动

### 在手机上

手机虽然通常没有 HDD，但不代表 I/O 问题会自动消失。

手机上的加载调查同样要记录：

- 所需驻留是否接近目标设备的实际预算
- 资源重进场更敏感
- 热机后 CPU 解压和解析更危险
- 前后台切换后，原资源状态是否仍有效

所以手机上的 I/O 直觉不该只看“UFS 很快”，而应该看：

- 这条读取之后的链会不会在关键帧收口
- 工作集策略会不会让资源频繁重进场
- 热机后解压和解析还能不能扛住

这里列出的解压、解析、对象初始化是读取之后的阶段，不能都称为 I/O 瓶颈。跨平台差异应按同一请求与用途就绪点调查，见[资源可用链]({{< relref "performance/game-performance-read-does-not-mean-ready.md" >}})。

## 同样的内存问题，在两个平台上为什么体感差这么大

### 在 PC 上

如果只凭开发机的标称 RAM 作判断，可能产生这样的假设：

- 觉得多放一点没关系
- 觉得某些对象先常驻着也还好
- 觉得临时对象和工作集波动不是第一优先级

这会让一些原本不够健康的行为，在开发阶段被放过去。

可一旦到了：

- 低配机器
- 背景环境复杂
- 长时间运行

问题就会暴露出来。

这里需要警惕的假设是：

`你以为内存足够大，所以开始不尊重工作集。`

### 在手机上

手机应按实际系统、进程状态和内存统计核对压力；不能把标称 RAM、引擎分配和进程驻留当作同一数字。PC 也需要同样的口径约束，见[内存记账]({{< relref "performance/game-performance-memory-accounting.md" >}})。

例如：

- 工作集来回抽搐
- 资源常驻与淘汰策略不稳定
- 某些内容刚淘汰又立刻要用
- 高频生命周期尖峰

调查这些行为时，可关联以下目标事件：

- 切场景抖
- 大 UI 首开卡
- 长玩后更差
- 切后台回来又要重新结一遍账

所以手机上的内存直觉必须更强调：

- 行为稳定
- 生命周期平滑
- 工作集可预期

## 同样的 sync 问题，在两个平台上也会呈现不同形状

### 在 PC 上

PC 同步调查需要记录：

- 用户环境复杂
- 驱动和图形路径差异大
- 某些等待只在特定配置和特定负载下明显

只在特定机器出现是触发条件线索，不能独自证明同步边界有错。

所以 PC 上看同步问题时，要特别警惕：

- 这是稳定问题，还是某些环境才触发
- 这是你的同步边界设计问题，还是环境差异在放大它

### 在手机上

若已确认持续能力变化，还应核对：

- 原本还可接受的等待，在预算缩小后会更痛
- 首次上传、首次准备或任务收口是否因执行能力变化而延后目标

因此同步调查也需要关联：

- 首次成本
- 热预算
- 生命周期切换

缠在一起。

这会让很多问题表面上看起来不像“同步”，而像：

- 怎么突然就抖了
- 为什么一段时间后才开始抖

## 热／功耗条件怎样进入两个平台的调查

PC 和手机都要记录供电、电源策略、散热、内容负载与运行窗口。不要预设 PC 的持续能力固定，也不要把手机长期变慢直接称为降频。

若平台提供热状态或其他约束信号，将其与任务、执行和显示指标关联；缺少信号时保留未知。降载本身也减少工作量，即使结果变快，也不能单独证明原问题由热限制造成。降载、恢复及接受责任沿[功耗与发热]({{< relref "performance/mobile-hardware-03-power-thermal.md" >}})展开。

显示与限帧也要记录。Android 的[Frame Pacing 文档](https://developer.android.com/games/sdk/frame-pacing)说明排队与有意安排等待的关系；它支持检查呈现节奏，不支持把所有等待都判为 GPU 超载或错误同步。

## 用户预期也在改变你的性能直觉

除了硬件和系统差异，用户预期其实也会改变你应该如何判断问题。

### 在 PC 上

产品可以提供这些选择，但是否适合目标用户需要验证：

- 自己调画质
- 自己换分辨率
- 自己在性能和画面之间权衡

这意味着 PC 上你可以更多地把问题转化成：

- 分档
- 选项
- 回退路径

### 在手机上

可以把以下项目列为产品接受目标，再与实际使用需求确认：

- 打开就顺
- 玩一段时间也顺
- 不发热太夸张
- 不耗电太离谱

默认路径与可选设置均需验收；是否开放选项、哪些质量可退，由产品目标与用户证据决定。

## 一套更实用的平台判断清单

如果你在做跨 PC 和手机的性能判断，我建议至少把下面这些问题变成固定习惯。

### 1. 两份结果是否可比

同一程序与内容身份、操作路线、指标起止点和采集条件是否一致？目标帧率、刷新率、实际渲染尺寸与自动质量策略是否被记录？不同设备做不了完全相同条件时，先说明不可比部分。

### 2. 初次、重复与持续窗口分别测了吗

缓存、首次准备、驻留和热状态是否可区分？不能用一次开发机采样代表全部设备，也不能把冷机与持续窗口直接混在一个平均值中。

### 3. 哪份证据支持原因，哪份只是相关

执行、等待、内存与平台信号是否属于同一任务和时间域？缺失数据保留未确定。详细分类与对照沿[诊断方法]({{< relref "performance/game-performance-diagnosis-method.md" >}})回查。

### 4. 分档和默认策略的代价由谁接受

画面、玩法反馈、加载、内存与持续条件分别如何验收？同一策略在两平台上都需要对应证据，不能默认 PC 交给用户设置、手机交给自动降级。

### 5. 结果不符合预期时回到哪里

条件变化返回基线，证据不足返回采集，目标或质量不接受返回方案取舍。实际交接与教学例见[性能工作流]({{< relref "performance/game-performance-methodology-summary.md" >}})。

## 我的结论

如果把这篇文章压缩成一句话，我会这样总结：

> 手机和 PC 的比较要落到设备、系统、内容和运行条件。环境差异与持续约束都应进入调查，用同一目标下的证据判断原因，再选择合适的分档、调度或回退。

理解这一点之后，你再去看同样的掉帧、加载慢、首次卡顿、长玩后变差，就不会再轻易把它们当成“跨平台同一个问题”。

你会更容易开始问：

- 这是环境差异，还是热预算收缩
- 这是可以靠分档和回退解决的问题，还是默认路径本身就不该这样设计
- 当前产品需要哪些可调策略，持续表现又覆盖了哪些条件

当这些问题开始成为默认思路时，你的跨平台性能判断才真正开始成熟。
