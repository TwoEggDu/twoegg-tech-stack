> 如果只用一句话概括这篇文章，我会这样说：性能优化里最贵的错误，不是“改得不够快”，而是“根本没判断清楚慢在哪，就开始动手改了”。

前面这个系列已经把几条最重要的线铺开了：

- 为什么某些操作会慢
- 一帧到底是怎么完成的
- 什么事不能在什么时候做
- 为什么大整文件通常比很多小散文件更稳
- 为什么读盘完成不等于资源可用
- 为什么内存不是够不够，而是行为稳不稳
- 这些问题在 Unity 和 Unreal 里通常怎么显形

到了这一步，最自然的下一篇就不该再补一个零散原理点，而应该把前面的内容收束成一套更能落地的东西：

`当你面对一个真实卡顿、掉帧、首次抖动、长玩后变差的问题时，到底该怎么判断。`

因为在开发现场，最危险的情况通常不是“不知道任何原理”，而是：

- 看见掉帧就先怪 GPU
- 看见切场景卡顿就只怪磁盘
- 看见 GC 尖峰就把一切都归结成内存不够
- 看见线程等待就立刻重写任务系统

这些动作都可能对，但如果顺序不对，最后就会变成一种很贵的假勤奋：

`改了很多，问题还在。`

所以这篇文章集中回答：

`把 CPU bound、GPU bound、I/O bound、memory bound、sync bound、thermal / power bound 变成一套能用来排查的判断方法。`

> 范围与版本：本文讲诊断方法，Unity 字段与采集条件按 2022.3 LTS 文档核对，Unreal 工具入口参考 UE 5.6 的 Unreal Insights 文档；不把两者的计数器逐项等同。下文对照方案是未执行的验证设计，没有目标工程 trace、设备采样或优化收益实测。

阶段与关键路径复用[一帧链路]({{< relref "performance/game-performance-frame-breakdown.md" >}})和[帧预算拆账]({{< relref "performance/game-budget-06-frame-budget-breakdown.md" >}})；CPU／GPU 计时、显示间隔和输入反馈的口径复用[帧时序与显示技术]({{< relref "rendering/unity-rendering-supp-i-frame-timing.md" >}})。本篇负责把这些证据组织成可以继续验证的判断，不再展开一套机制或工具教程。

## 先确定目标，再选择优化动作

优化动作本身当然重要。  
但在大多数项目里，真正稀缺的不是“会不会写快一点的代码”，而是：

- 能不能先把问题分对类
- 能不能先确定瓶颈在哪条链上
- 能不能先区分稳定瓶颈和偶发尖峰
- 能不能先判断这是代码问题、资源问题、时机问题，还是平台预算问题

很多人一上来就进入“解决问题”的状态。  
但在性能问题里，一个常见现实是：

`你以为自己在解决问题，其实只是换了一个地方继续花预算。`

比如：

- 以为自己在做异步，结果只是把阻塞从读盘换成了等待后台结果
- 以为自己在做内存优化，结果只是压低了总量，却让资源重进场更频繁
- 以为自己在做 GPU 优化，结果真正的问题其实是首次上传和首次命中

所以这篇文章的第一原则非常简单：

`先诊断，再优化。`

而“诊断”不是一句空话，它要能落到具体判断上。

## 从线索到结论，中间还差什么

先固定要解释的目标：是应用帧间隔超预算、一次资源迟迟不可用、显示没有新内容，还是某次输入反馈变晚？它们可以互相影响，但不能用同一个“卡”字替换全部测量边界。

| 当前掌握的材料 | 可以怎样表达 | 还不能怎样表达 |
| --- | --- | --- |
| 直接观察或用户反馈 | 同一操作首次出现长间隔，后续较短 | 已确认磁盘慢或需要对象池 |
| 候选假设 | 首次读取、解压、对象创建或首次渲染准备可能延后目标 | 这些阶段都是 I/O 瓶颈 |
| 可关联的证据 | 同一请求／内容帧的某项依赖迟到，并阻止目标继续 | 同时出现的所有尖峰都是根因，或最长的条必然是瓶颈 |
| 对照与复测 | 在说明条件与重复结果后，某项改动支持或削弱了指定假设 | 一次 fps 上升就证明全部原因和所有设备的收益 |

这里的“瓶颈”要带上**目标、负载、设备和窗口**：是哪项资源、执行能力、依赖或系统约束限制了目标完成。它不要求所有 CPU 核都满载，也不要求某个汇总利用率达到固定百分比。稳态输出节奏与单次反馈的关键路径还可能不同。

先把同一任务的开始、依赖完成、恢复执行与目标完成关联起来，保留请求、源帧、线程、构建和时间域。时钟未对齐、样本缺失或 GPU 数据不可用时，结论可以停在“尚未确定”。这比给一个没有证据支持的 bound 标签更有用。

六类名称也不是六个互斥时间桶：访存受限可以发生在 CPU 或 GPU 工作内，I/O 可以导致线程等待，热约束可以改变 CPU／GPU 可用能力。同一段时间不重复加账，具体边界随下面各节说明。

## 先学会判断：你面对的是哪一类“慢”

在进入六类 bound 之前，先做一个更基本的分类。

很多项目一上来就问：

`这是 CPU 还是 GPU？`

这当然重要，但还不够。  
更早一步的问题其实是：

- 这是稳定慢，还是偶发抖
- 这是首次慢，还是每次都慢
- 这是长玩后变差，还是冷启动就差
- 这是某个交互点才出现，还是整场景都慢

这几个维度会直接改变你后面的诊断方向。

下面四种描述用于选择采样窗口和调查方向，不是根因分类，也不代表候选原因的发生率排序。首次与再次、持续运行前后必须核对实际内容和运行条件。

### 稳定慢

如果每次进入场景都慢、每帧都偏慢、整体表现长期压不住预算，这更像稳定瓶颈。

可以先调查：

- CPU bound
- GPU bound
- 持续的 memory / bandwidth 压力

### 偶发抖

如果大多数时候正常，只有个别帧突然爆，这更像尖峰问题。

可以先调查：

- 首次命中
- 生命周期尖峰
- sync bound
- GC / 分配器尖峰
- 某段后台工作在错误帧收口

### 首次慢

如果第一次进场景、第一次开 UI、第一次放技能慢，第二次明显变好，可以检查：

- I/O 链
- 依赖展开
- GPU 上传
- shader / PSO 首次命中

### 长玩后变差

如果刚开始还好，玩一段时间以后变差，可以检查：

- thermal / power bound
- 工作集波动
- 资源淘汰与重进场策略
- 长时间运行导致的分配行为劣化

这一步看起来很朴素，但非常关键。  
因为它能帮你避免一种常见浪费：

`明明是首次尖峰，结果你按稳定瓶颈去优化。`

## 一套更实用的总排查顺序

如果你现在面对一个真实问题，我建议先按这个顺序来，而不是直接扑向某个具体系统。

### 第一步：先固定复现场景

不要在模糊印象上诊断。

至少先把问题压缩成一句话：

- 什么时候发生
- 多稳定
- 第一次还是每次
- 在 PC 还是手机
- 是战斗、切场景、UI、流送边界，还是长玩后

同时固定构建／内容版本、目标设备、图形 API、操作路线、缓存与运行状态。低频或暂时无法稳定复现的问题，也可以保留事件记录、成功与失败样本，逐步缩小触发条件；不能因为复现不稳定，就把相关性升级成原因。

### 第二步：先区分稳定瓶颈和偶发尖峰

这一步会直接决定后面的工具和思路。

- 稳定瓶颈更适合先看持续时间和整体预算分布
- 偶发尖峰更适合先找首次命中、同步边界和生命周期波动

### 第三步：关联 CPU、GPU 与目标完成时刻

先核对 CPU／GPU 数字的对象、区间与源帧，再判断哪项工作或等待延后目标。

先回答这些：

- CPU 区间包含哪些执行、就绪未运行或阻塞；GPU 计时是否受支持，是否对应同一批工作
- 降低实际渲染分辨率时，相关 GPU 工作与目标节奏是否一起变化
- 单独改变一个画质因素后，哪些区间变化，哪些没有变化
- 主线程、渲染线程、Worker 与 GPU 的依赖中，谁阻止了目标继续

不能直接比较两个名字里都有“frame time”的总量就定案。Unity 2022.3 的 [Frame Timing Manager](https://docs.unity3d.com/2022.3/Documentation/Manual/frame-timing-manager.html)中，CPU 帧时间包含等待与开销，GPU 数据也有平台支持与准确性限制；最近返回值不必属于当前应用帧。

降低分辨率有效，只说明这次配置对某些成本敏感，不单独证明 ALU、带宽或某一个 Pass 就是唯一原因。若限帧使显示节奏不变，也不能据此认定 GPU 工作量完全没变。记录动态分辨率、同步与目标帧率，分别比较工作区间和目标指标。

### 第四步：沿依赖调查读取、内存、同步与持续条件

很多问题不是纯 CPU 或纯 GPU，而是：

- I/O 链让 CPU 在关键帧收口
- memory 行为让帧时间波动
- sync 边界打断了原本的流水
- thermal / power 把原本勉强安全的方案放大成事故

所以前面的 CPU / GPU 分类，只是第一层，不是终点。

## CPU bound 怎么判断

### 典型现象

可优先检查 CPU 路径的线索包括：

- 主线程或 Game Thread 明显长
- 降分辨率帮助不大
- 关闭后处理或降低渲染质量帮助有限
- 某些交互点、对象激活点、系统更新点容易出尖峰

它常见的外观包括：

- 一整段逻辑、UI、对象激活拉长
- 切场景收口时 CPU 明显爆
- CPU 侧准备迟到，但尚需查明是执行、调度还是等待依赖

### 优先看什么

先看这些问题：

- 主线程 / Game Thread 时间是不是稳定偏长
- 哪段 update、tick、生命周期回调在拉长
- 是否有大量对象在同帧被创建、激活或销毁
- 是否有后台工作最终回到这一帧收口
- 数据访问模式是否很碎，缓存局部性是否很差

### 常见误判

CPU bound 最常见的误判是：

`看见主线程长，就以为一定是某段纯逻辑算法太慢。`

很多时候不是。  
它也可能是：

- 生命周期尖峰
- UI 刷新
- 资源激活
- 后台任务收口
- 大量短命对象导致的后续成本

所以 CPU bound 不是“只看代码”，而是看：

`CPU 这一帧到底在替谁结账。`

进一步要分开：是 CPU 侧关键工作执行太久、任务依赖未满足，还是线程已经就绪却迟迟未获调度？主线程墙钟条长不等于它一直在计算，整机 CPU 占用不高也不能排除单线程关键路径受限。Windows 的 [WPA CPU 分析](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/cpu-analysis)分别讨论 Running、Ready、Waiting 与关键路径；其他系统按各自轨迹解释，不硬套 Windows 状态字段。

能支持 CPU 执行限制判断的，是目标路径上的执行工作与迟到关联，且有针对性的减负在对照中使该路径和目标指标按预期变化。若主要时间在等 GPU、读取或正常限帧，继续追被等待对象；模型见[线程调度与等待]({{< relref "performance/game-performance-thread-scheduling-waits.md" >}})。

### Unity / Unreal 里常见落点

Unity 中可检查的入口包括：

- Main Thread 尖峰
- `Update / LateUpdate`
- `Instantiate / Destroy`
- UI 刷新和生命周期回调

Unreal 中可检查的入口包括：

- Game Thread 压力
- 对象激活链
- Tick 体系
- Streaming 收口时的主线程工作

## GPU bound 怎么判断

### 典型现象

可优先检查 GPU 路径的线索包括：

- GPU frame time 明显长
- 降分辨率有效
- 降低特效、阴影、后处理、透明度或画质后明显改善
- 某些视角、某些镜头、某些高分辨率路径特别容易出问题

### 优先看什么

先看：

- GPU 工作是否延后目标所需图像就绪，而不只是数值高于含等待的 CPU 区间
- 降分辨率是否立刻有效
- 问题是否和画面复杂度、像素成本、后处理强相关
- 是否有高开销 pass、overdraw、带宽压力、复杂 shader
- 是否有大规模 GPU 上传或首次资源准备撞到关键帧

### 常见误判

GPU bound 最常见的误判是：

`看起来像渲染问题，就一定是场景画得太重。`

很多时候也未必。  
它还可能是：

- 首次纹理 / mesh 上传
- 首次 shader / PSO 命中
- CPU 提交和 GPU 执行节奏没对齐
- 某个关键帧把“资源准备 + 渲染执行”一起堆给了 GPU

所以 GPU bound 也要继续分：

- 是稳定的渲染负担过高
- 还是首次成本在关键时刻显形

首次 shader／PSO 准备也可能涉及 CPU 编译、驱动或管线创建，不能因为名称与渲染有关就算成 GPU 执行。需要把准备、提交、GPU 工作、队列和显示采用分开。

一个尤其容易误判的线索是 Present 等待。按 [Unity 2022.3 Profiler 标记说明](https://docs.unity3d.com/2022.3/Documentation/Manual/profiler-markers.html)，`Gfx.WaitForPresentOnGfxThread` 需要同时检查渲染线程；相关等待可能包含 VSync，渲染线程也可能忙于 CPU 侧命令准备。等待长不能单独证明 GPU 计算超预算，等待短也不能单独排除其他瓶颈。

### Unity / Unreal 里常见落点

Unity 中可检查的入口包括：

- 某些 pass 很重
- overdraw
- shader variant 首次命中
- 资源首次上传

Unreal 中可检查的入口包括：

- pass 和材质开销
- Render / RHI 路径压力
- PSO 首次命中
- GPU 侧资源准备撞上首次使用

## I/O bound 怎么判断

### 典型现象

可优先调查读取链的线索包括：

- 首次进场景慢
- 切场景或传送边界抖
- 第一次开 UI、第一次放技能、第一次看到某类资源时卡
- 第二次进入明显变好

这类问题经常带着一种很强的“首次感”。

### 优先看什么

先看：

- 这是第一次慢，还是每次都慢
- 问题是否和资源首次读取或 streaming 边界强相关
- 是大整块资源读，还是海量小文件碎访问
- 读盘之后是否还叠着解压、反序列化、依赖解析

### 常见误判

I/O bound 最常见的误判是：

`把所有首次卡顿都粗暴地叫成磁盘慢。`

这通常不够。  
更准确的判断要继续往后拆：

- 真的慢在读盘吗
- 还是慢在读盘之后的解压和解析
- 还是慢在对象创建和 GPU 上传

本篇将 I/O 受限限定为：

`目标依赖的读取路径延后了所需字节就绪，并限制了目标继续。`

应用请求耗时还可能包含排队、缓存与系统等待，不全是设备服务时间；设备汇总吞吐也不直接归属某个游戏任务。字节已就绪之后的解压、反序列化、对象创建和上传分别归到实际执行或依赖阶段，不能统称磁盘瓶颈。第二次变快也可能来自其他首次准备成本消失，不能只归功于文件缓存。

按同一请求关联读取、后处理与 Ready 条件，先用[OS I/O 机制]({{< relref "engine-toolchain/storage-io-04-os-io-sync-async-dma-mmap-read-ahead-queue-depth.md" >}})区分应用请求、缓存与设备工作，再选工具。工具和观测边界复用 [IO 性能分析]({{< relref "engine-toolchain/storage-io-06-profiling-with-fio-iostat-perfetto-instruments.md" >}})及[资源可用链]({{< relref "performance/game-performance-read-does-not-mean-ready.md" >}})。不要把请求等待、设备统计和加载总时长相加，或用 fio 结果替代这次业务请求的证据。

### Unity / Unreal 里常见落点

Unity 中可检查的入口包括：

- Addressables / AssetBundle 首次卡顿
- UI 首开
- 首次技能和首次场景进入

Unreal 中可检查的入口包括：

- Asset Streaming 边界
- 首次进入 streaming 区域
- 首次资源使用前的准备链

## memory bound 怎么判断

### 典型现象

这一节沿用 memory 作为排查入口，但先区分三类问题：

| 问题 | 要观察的材料 | 不足以证明什么 |
| --- | --- | --- |
| 容量／驻留压力 | 明确口径的进程或引擎内存、资源持有、缺页／回收及目标受影响的时间关系 | 总量高不自动等于泄漏或访存带宽耗尽 |
| 分配、回收与生命周期成本 | 分配调用、GC 工作、对象创建销毁及所在关键路径 | 有分配不等于该帧发生 GC；GC 发生也不等于系统内存耗尽 |
| 访存延迟／带宽限制执行 | 对应 CPU／GPU 工作、架构适用的计数器和针对数据访问的对照 | 一张内存占用截图不能证明 memory-bound 执行 |

硬件性能分析里的 memory-bound 关注访存对执行的限制。例如 [Vulkan profiling 指南](https://docs.vulkan.org/guide/latest/profiling.html)把 GPU 的内存带宽利用与相关瓶颈联系起来；具体计数器仍须按芯片与工具核对，不能跨厂商套一个阈值。容量问题与 GC 成本不因此都变成同一种硬件瓶颈。

以下现象可以触发上述调查，但本身不能区分三类原因：

- 总量不一定立刻爆，但帧时间越来越不稳
- 切场景、开大 UI、进战斗时明显抖
- GC 尖峰
- 长玩后变差
- 同一批资源反复进出场

### 优先看什么

先看：

- 是容量逼近极限，还是行为不稳定
- 有没有高频临时对象
- 有没有生命周期尖峰
- GC、分配器尖峰是不是踩在关键帧
- 常驻与淘汰策略是不是来回抽搐
- 工作集变化是不是和体验恶化强相关

### 常见误判

memory bound 最常见的误判是：

`总量没爆，所以内存没问题。`

很多时候真正的问题不是“放不下”，而是：

- 分配过碎
- 释放过猛
- 工作集来回波动
- 生命周期变化集中发生

原来的“仓库满了／工作台太乱了”比喻可以提醒我们关注行为，却不能替代分类。内存口径复用[内存记账]({{< relref "performance/game-performance-memory-accounting.md" >}})，分配与对象寿命的取舍复用[内存行为]({{< relref "performance/game-performance-memory-behavior.md" >}})。

Unity 2022.3 的 [GC 文档](https://docs.unity3d.com/2022.3/Documentation/Manual/performance-garbage-collector.html)区分分配跟踪与回收模式；增量 GC 可把回收工作分布到多帧。报告时写出模式、分配与回收的实际时间线，不用单个 `GC.Alloc` 数字推算停顿，更不把 Unity 的托管 GC 机制直接搬到 Unreal。

### Unity / Unreal 里常见落点

Unity 中可检查的入口包括：

- GC
- 高频 `Instantiate / Destroy`
- UI 首开和切页抖动
- 临时对象风暴

Unreal 中可检查的入口包括：

- 对象激活链上的工作集波动
- streaming 内容进出场
- 长玩后的资源重进场和初始化波动

## sync bound 怎么判断

### 典型现象

sync bound 最典型的表现不是“谁特别忙”，而是：

`谁在等谁。`

但等待存在不等于需要删除同步。锁、fence、readback 或任务收口是否限制目标，要看等待对象何时完成、线程何时恢复、目标期限在哪里；正常限帧与无任务时的休眠需要单独解释。忙等也不总显示成线程阻塞，应结合调用栈、依赖与执行状态判断。

常见现象包括：

- 某个线程本来不重，但某些帧会突然停住
- CPU、GPU 都没明显长期过载，但帧还是会爆
- Present、fence、readback 或某个等待点附近异常明显

### 优先看什么

先看：

- 某一帧是不是在等待后台任务结果
- CPU 是否在等 GPU
- GPU 是否在等资源准备
- 有没有主线程必须同帧拿到的异步结果
- 有没有不必要的同步点把原本可并行的链条串起来

### 常见误判

sync bound 最常见的误判是：

`只看哪个线程长，却不看它是不是在等。`

等待和执行是两回事。  
有些尖峰不是“做了很多”，而是“被迫停住了”。

这类问题如果被误当成纯 CPU 或纯 GPU 负担去优化，常常会越改越偏。

### Unity / Unreal 里常见落点

Unity 中可检查的入口包括：

- 主线程等异步结果
- 资源准备和首次显示撞在一起
- 看起来像主线程尖峰，但实际是等待边界

Unreal 中可检查的入口包括：

- Game Thread / Render Thread / RHI 节奏被打断
- Streaming 与首次使用之间的等待
- CPU / GPU 流水被同步边界串起来

移除等待、推迟消费或增加并发都会改变依赖、资源寿命或响应时机。对照实验必须保持所需正确性，再判断目标是否变早；不能以主线程等待条变短作为唯一成功条件。

## thermal / power bound 怎么判断

### 典型现象

可优先调查热／功耗约束的线索包括：

- 刚开始正常，玩一会儿以后变差
- 冷机和热机表现差异明显
- 同样场景，刚启动时能稳住，持续运行后开始掉帧和抖动

移动设备和 PC 都需要核对持续条件；本篇没有跨平台发生率数据。

### 优先看什么

先看：

- 问题是否和运行时长强相关
- 是否只在热机状态下明显
- 平台是否报告热约束，执行能力与目标指标怎样变化；频率、功耗、温度各自来自什么测量
- 是否存在“原本勉强安全”的路径，被热限制放大成明显卡顿

### 常见误判

thermal / power bound 最常见的误判是：

`代码没变，所以问题应该不在平台预算。`

在工作量和其他条件已核对，并有热／功耗约束证据时，才可以形成这样的解释：

- 代码没变
- 预算变了

所以你看到的是同一段逻辑在不同温度、功耗和持续运行状态下，突然显得完全不像一回事。

长玩后变差还可能来自内容规模、内存增长、后台工作、缓存策略或帧率设置变化。温度、频率与耗时一起变化提供线索，不能单独完成归因。Android 的 [PowerManager](https://developer.android.com/reference/android/os/PowerManager)中，热状态查询从 API 29、thermal headroom 从 API 30 提供；后者可能不受设备支持并返回 `NaN`，不是所有设备通用的摄氏温度。未知值不能写成“没有热限制”。

固定操作负载、初始状态、供电和环境，记录平台状态与目标指标，再用降载及恢复过程复核解释；不要规定所有设备跑固定分钟数后一定降频。具体模型与责任复用[功耗与发热]({{< relref "performance/mobile-hardware-03-power-thermal.md" >}})。

### Unity / Unreal 里常见落点

两个引擎都可调查这样的现象：

- 起初正常，持续运行后同一任务的指标变差
- 首次成本、工作集波动、资源上传在热机状态下被明显放大

先核对工作量、运行状态与平台约束，再判断引擎调度或内容策略如何参与变化。

## 不要只诊断单一 bound，要学会看主矛盾和次矛盾

真实项目里，纯净的单一瓶颈并没有想象中那么多。

更多时候你看到的是这种结构：

- 主矛盾是 I/O / 首次资源准备
- 但它最后显在主线程尖峰

或者：

- 主矛盾是内存工作集波动
- 但它最后显在 streaming 边界的 CPU 和 GPU 同时抖动

又或者：

- 原本只是轻度 GPU 压力
- 但在热机状态下被 thermal / power 放大成稳定掉帧

所以诊断时要尽量形成两层结论：

1. 现在帧爆掉时，表面上是谁在超预算
2. 更底层的主导因素到底是什么

这两层不分开，结论就很容易半对半错。

报告应落到可检查的句子：**在什么设备、构建、任务与窗口中，哪项依赖／工作延后了哪个目标；哪些证据和对照支持它，还剩哪些替代解释。** 改掉当前限制后，新的瓶颈可能出现；这不自动否定前一次判断，也不允许把局部收益外推到全部场景。

## Unity 和 Unreal 的诊断入口为什么不一样，但方法论还是同一套

Unity 和 Unreal 的专项文章提供各自的调查入口。

两个引擎的现场入口确实不一样：

- Unity 往往更容易先看到主线程、GC、Instantiate / Destroy、Addressables、UI
- Unreal 往往更容易先看到 Game Thread、Render Thread、RHI、Streaming、PSO

但真正的诊断方法没有变。

你仍然要回答这些：

- 稳定慢还是偶发抖
- 第一次还是每次
- 谁在超预算
- 谁在等待
- 工作集是否在波动
- 平台预算是否在收缩

共同方法可以复用，具体阶段、线程和计数器仍以对应引擎版本为准。

工具操作复用[性能诊断工具选择指南]({{< relref "performance/mobile-tool-09-performance-diagnosis-tool-selection.md" >}})，按本次缺的证据选择工具，不要求每次走同一条工具链。该文中的入口也要回到实际平台、版本与支持范围核对，不能因列出工具名称就认定拿到了可用 GPU 数据。

按 [Unity 2022.3 采集说明](https://docs.unity3d.com/2022.3/Documentation/Manual/profiler-profiling-applications.html)，连接 Player 的 Unity Profiler 使用 Development Build；Editor、Development 与发布配置的成本要分别报告，Deep Profile 等采集开销也要记录。定位时可按需要启用更细采样，收益验收还应在目标交付配置用适用方法复测，不把采集配置的结果直接当发布表现。

UE 5.6 的 [Unreal Insights 文档](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-insights-in-unreal-engine?application_version=5.6)说明其事件、记录与分析分工，采集工作流取决于构建和 OS。这里仅映射职责，不给跨版本通用启动命令；实际启用的事件、丢失情况、计时范围与平台能力都应随 trace 保存。

## 最小对照验证：让假设能够被支持或推翻

### 六类入口各需要哪份证据

下表是验证设计，不是已执行实验。每一行都要关联同一个目标、版本、负载和时间窗口；支持一项解释后，仍需保留尚未排除的替代原因。

| 调查方向 | 要检验的假设与证据 | 可选择的对照，以及结论限制 |
| --- | --- | --- |
| CPU 执行／调度 | 目标依赖的工作执行太久，或已就绪却未获调度；关联执行区间、调用栈、任务流及调度状态 | 对一项已定位工作减负，观察该路径与目标是否同时提前；仅有主线程条缩短，不能证明呈现或反馈改善 |
| GPU 工作 | 目标图像所需 GPU 工作迟到；核对源帧、GPU 区间、CPU 提交、队列与呈现关系 | 降低实际渲染比例并核对联动设置；只能先检验像素相关负载敏感性，不能直接认定带宽或某个 Shader 是唯一原因 |
| 读取路径 | 所需字节迟到，后续用途等待这份输入；关联请求、缓存条件、字节就绪与后处理 | 在明确条件下比较读取路径或预取时机；第二次更快可能同时改变缓存、管线与对象准备，不能作为单独的磁盘证据 |
| 内存三类问题 | 容量压力、分配回收成本、访存限制分别取证；统一统计对象并关联阶段与资源寿命 | 只调整一项持有、分配或访问策略；同时核对重载、生命周期、画面和目标指标，不能用总量下降替代所有结论 |
| 同步依赖 | 目标被某项尚未满足的依赖阻止；保留被等待对象、完成及恢复执行时间 | 在正确性允许下缩小等待范围或调整派发／消费时机；记录新增驻留与反馈延迟，同帧收口也可能已有效重叠 |
| 热／功耗约束 | 同一负载下平台约束与执行能力变化参与了退化；关联状态信号与任务指标 | 控制并记录初始条件，比较降载与恢复过程；降载本身也降低工作量，单次变快不能独自证明热约束就是原因 |

若某份必要数据缺失，先写“需要什么证据”，再选择下一项能区分候选原因的采集或对照。不要为了把六类填满而给一个任务同时认定六个根因。

### 固定一项假设，保留可比条件

先写假设，再选改动。假设要包含预期与反证：如果原因成立，哪段应变化、目标应怎样变化；如果只缩短内部区间而目标不变，可能是限制已转移、呈现被限速，也可能原假设并未解释目标。

一份足够小的验证记录可以这样组织：

| 环节 | 最少记录什么 |
| --- | --- |
| 目标与基线 | 程序／内容身份、设备／OS／API、任务路线、指标起止点、预算与正确性条件 |
| 可比条件 | 缓存与首次准备状态、热／供电状态、同步／刷新／画质、后台活动和采集方式 |
| 假设与改动 | 候选原因、预期证据、只改变的一个因素，以及随之联动的设置 |
| 重复与采样 | A 基线、B 改动及必要的 A 恢复复测；轮次、顺序、窗口、有效／缺失样本和异常 |
| 结果与边界 | 对应区间与目标的变化、分布与波动、视觉／交互／内存／功耗代价，以及未排除原因 |

A／B／A 是排查漂移的一种设计，不保证热状态或缓存已复原。可按问题安排交错或分组重复；冷启动、首次使用与稳态分别比较，先定义各自条件。不要为了“冷测”在用户设备上随意清空全局缓存或修改系统策略。

下面以**拟验证的固定战斗镜头**为例，不填实测数字：

1. 假设是“GPU 像素相关工作参与限制稳态输出节奏”。固定镜头、内容和操作路线，记录实际渲染尺寸、动态分辨率、目标帧率与同步状态。
2. A 保留原尺寸，B 只降低渲染比例；确认没有同时改变材质、LOD、后处理或其他质量策略。若引擎自动联动了设置，记录后拆开验证，不能宣称已隔离唯一变量。
3. 比较同口径 GPU 工作、CPU 执行／等待、目标间隔与显示证据。GPU 工作变短且目标同步改善，可支持“像素相关负载参与限制”的解释；仍不足以区分 ALU、采样和带宽，需要进一步证据。
4. 若 GPU 工作变短但显示间隔不变，检查限帧、队列和其他关键路径；GPU 数据缺失就报告未确定。若只是视觉内容少了、交互错误或功耗转移，也不能按原质量目标验收成功。
5. 恢复 A 并重复，检查结果是否随条件漂移；保留失败与反例，不只挑最好的一轮。这个对照只回答所选镜头的稳态问题，不替代首次加载、长玩、其他设备或输入延迟验证。

统计前沿用帧时序篇的去重与窗口口径：应用、GPU、显示和任务延迟分开，说明均值／分位数算法与样本数；缺失不填零，短窗口不外推整局游戏。不要用固定“改善百分比”代替对重复性、波动和产品验收条件的判断。

结论不足时，记录下一项最能区分候选原因的证据；结论成立后，再把触发条件、责任人、复现路线与测量口径沉淀到回归或预算。基础机制成立、一次对照有效、检查被接入、团队持续使用是不同状态，不用一份诊断记录宣称持续性能门禁已经运行。

## 一张更实用的快速判断表

如果你想把这篇文章压成一张脑内清单，我建议记下面这些“第一反应”。

这些问题用于选择下一份证据，不是可直接套用的判定表。

### 看起来像 CPU bound 时

先问：

- 是纯逻辑，还是主线程在收系统总账
- 有没有生命周期尖峰
- 有没有后台任务这一帧收口

### 看起来像 GPU bound 时

先问：

- 降分辨率有没有用
- 是稳定渲染压力，还是首次上传 / 首次命中
- 是场景真的重，还是关键帧把准备工作堆给了 GPU

### 看起来像 I/O bound 时

先问：

- 是第一次慢，还是每次都慢
- 真慢在读盘，还是慢在读盘后的链条
- 是大块顺序访问，还是碎访问

### 看起来像 memory bound 时

先问：

- 是容量问题，还是行为问题
- 是否另有访存延迟／带宽限制执行的证据
- 有没有短命对象风暴
- 有没有工作集来回抽搐

### 看起来像 sync bound 时

先问：

- 谁在等谁
- 等待是必要的吗
- 原本可并行的链条是不是被串起来了

### 看起来像 thermal / power bound 时

先问：

- 热机和冷机差异多大
- 是代码变了，还是预算缩了
- 哪条原本勉强安全的链在高温下最先失控

## 我的结论

如果把这篇文章压缩成一句话，我会这样总结：

> 性能诊断真正值钱的地方，不是背出 CPU / GPU / I/O / Memory / Sync / Thermal 这些名字，而是能在一个真实问题面前，先区分稳定瓶颈和偶发尖峰，再找出谁在超预算、谁在等待、谁在放大问题，以及这条链为什么偏偏在那个时机收口。 

理解这一点之后，你再去做优化，很多动作就不会再是“凭经验盲改”，而会变成一套更有胜率的工程判断。

你会更容易知道：

- 这个问题先该抓哪条链
- 这个现象更像哪一类 bound
- 这个尖峰到底是执行问题，还是等待问题
- 这个退化到底是代码问题，还是平台预算问题

当这些判断开始稳定下来之后，优化才真正从“救火”变成了“有秩序地减灾”。
