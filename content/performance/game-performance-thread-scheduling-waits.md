一项场景准备工作从发起到返回用了很久，但 CPU 总占用并不高。把它挪到后台之后，主线程最后仍然卡了一下。此时，继续增加 Worker、把方法改成 `async`，或者提高线程优先级，都需要先回答同一个问题：**这段时间里，工作到底停在哪一层？**

可能是线程一直在执行一条很长的依赖链；可能是线程已经能运行，却迟迟没有获得 CPU；也可能在等资源，而恢复后的逻辑还要排到主线程的某个处理时机。它们都表现为“还没完成”，需要改变的机制却不同。

> 前置知识：理解函数调用、局部变量和基本共享数据即可阅读；无需先学完整内核、异步 API 或全部 CPU 微架构。

> 阅读范围：本文使用通用的简化状态模型，再分别引用 Windows、Linux/POSIX 与 Unity 6.0 文档解释具体边界。时间线和场景准备链均为教学示例，没有设备采样或项目优化实测。虚拟内存、内核调度算法和具体 I/O 实现留给专项。

## 进程持有资源，线程承载执行

磁盘上的可执行文件描述程序的一部分；运行起来以后，系统需要为它组织地址空间、资源和执行状态。以 Windows 为例，进程提供虚拟地址空间和系统资源，线程是进程内可以被调度执行的实体。一个进程可以有多条线程，它们共享该进程的地址空间，同时各自保有栈、寄存器上下文等执行状态。见 [Microsoft：进程与线程](https://learn.microsoft.com/en-us/windows/win32/procthread/about-processes-and-threads)。

地址空间让进程中的代码能够访问内存，线程的执行上下文则回答“接下来从哪条指令继续、局部调用进行到哪里”。线程切换时要保存与恢复必要上下文，才可以让不同执行流轮流使用 CPU。线程各有自己的栈，并不意味着其他线程在语言和访问规则允许时绝对无法通过地址访问其中的数据；栈上对象的寿命仍需由程序负责。

游戏里还有第三种对象：任务。一次寻路、一项资源请求、一个 `Task` 或 Job 描述的工作，并不天然对应一条专属 OS 线程。它可能先待在应用队列里，由某条 Worker 取走；也可能分成多段，先后在不同执行现场推进。

```text
游戏／引擎：一项逻辑任务 → 依赖满足 → 进入可执行任务队列
运行时：   Worker 或主循环取得任务 → 执行其中一段
操作系统：对应线程具备运行条件 → 被调度到逻辑 CPU
硬件：     推进这条线程的指令
```

这张图画的是职责关系，不是所有任务固定经过的四次排队。任务可以立即开始，continuation 也可能直接执行；关键在于不要把各层的状态混成一个“正在跑”。

如果任务还在引擎队列里，OS 不会替它识别“这是首屏关键资源”；OS 调度的是承载工作、且满足调度条件的执行实体。反过来，即便 Worker 已取到任务，它也不因此独占某个物理核心。多核、硬件线程和运行时任务的对应，可继续读[“线程”这个词的三层含义]({{< relref "engine-toolchain/unity-async-runtime-extra-01-thread-three-layers.md" >}})。

## 没有完成的线程，至少有三种不同处境

为了讨论等待，可以先用三个状态建模：

| 状态 | 本文中的含义 | 下一步由什么决定 |
| --- | --- | --- |
| 运行（Running） | 线程当前被调度在逻辑 CPU 上 | 它执行的代码、硬件资源与接下来的调度事件 |
| 就绪（Ready / Runnable） | 已具备运行条件，但此刻没有在 CPU 上执行 | 调度策略、其他可运行线程、CPU 可用性与亲和性等约束 |
| 阻塞／等待（Blocked / Waiting） | 当前继续执行所需的条件尚未满足，线程停止占用 CPU 等待 | 锁、事件、I/O、计时器等条件及相应通知机制 |

不同 OS 的实际状态名和细分不同。例如 Linux 的 runnable 概念可包含当前正在运行的任务；表里为了分析耗时，将“就绪但未运行”单独列出。它也没有画出创建、退出、显式暂停等全部状态，不能直接当作某个内核的状态枚举。

```text
就绪 ──被调度──→ 运行 ──需要等待且条件未满足──→ 阻塞
 ↑                │                              │
 └──被抢占等───────┘                              │
 └────────────条件变化／超时等使其可运行───────────┘
```

抢占让系统能够把 CPU 交给另一条可运行线程；运行线程主动等待，也会让出执行机会。具体时间片、优先级和选择规则属于系统策略，不能用一个固定毫秒数概括所有设备。Windows 的[上下文切换说明](https://learn.microsoft.com/en-us/windows/win32/procthread/context-switches)给出了保存上下文、选择就绪线程和恢复执行的模型。

这里尤其容易混淆三种“停”：

- **Cache Miss 或指令依赖造成的停顿**发生在硬件执行层。它不直接等于 OS 把线程置为阻塞；线程可以仍处于 on-CPU 状态。其成本由 [F01 的流水线与依赖模型]({{< relref "performance/hardware-cpu-f01-pipeline.md" >}})和 [F02 的缓存模型]({{< relref "performance/hardware-cpu-f02-cache.md" >}})解释。
- **循环检查条件的自旋**仍在执行指令。它可能没有业务进展，却占用 CPU；看到 on-CPU 时间不能直接认定那都是有效计算。某些锁会先短暂自旋再休眠，不能仅凭 API 名称推断整段等待方式。
- **系统调用**是应用请求内核服务的接口。进入内核执行与切换到另一条线程是两个概念：调用可以在当前线程上下文中完成，也可能因等待而触发调度。Linux 的[系统调用说明](https://man7.org/linux/man-pages/man2/syscalls.2.html)定义了这一接口边界。

因此，CPU 总占用低并不能排除关键线程已经占满一个执行上下文，也不能直接证明 I/O 慢。总占用只是聚合结果；需要回到关键线程、任务依赖和相同的时间窗口。

## 从阻塞到继续执行，中间发生了什么

考虑一条线程等待资源准备完成。它要先检查条件：如果结果已经可用，可以直接继续；如果不可用，才需要进入相应的等待机制。Windows 的[等待函数](https://learn.microsoft.com/en-us/windows/win32/sync/wait-functions)就区分条件已满足、继续等待与超时等情况。不是每次调用等待 API 都一定睡眠或切换线程。

“检查后去睡，另一边完成后叫醒”看起来很简单，却有一个关键竞态：生产者恰好在消费者检查以后、真正挂起以前完成并发送通知，消费者会不会错过这次变化？正确实现必须协调**条件状态、等待登记与通知**，不能用一个普通布尔变量加任意 `Sleep` 拼出通用同步协议。

以 POSIX 条件变量为例，等待操作会原子地释放关联互斥锁并等待，返回前重新取得锁；返回后仍要重新检查谓词，因为存在伪唤醒，条件也可能被其他消费者改变。概念结构如下，具体错误处理省略：

```text
消费者：
    持有关联互斥锁
    while 工作队列为空 且 尚未要求退出:
        等待条件变量（释放锁并等待；返回时重新持锁）
    检查退出条件，或取出一项工作
    释放锁

生产者：
    在同一锁保护下放入工作，按同步协议通知等待者
```

这只是条件变量的示意，不是信号量、事件和完成对象的统一写法。规则依据见 [POSIX 条件变量契约](https://man7.org/linux/man-pages/man3/pthread_cond_wait.3p.html)。使用库原语时，应遵守它的谓词、锁、通知与内存可见性约定，而不是自行猜测唤醒行为。

条件变化后，等待线程可以重新获得运行资格，但**唤醒不等于马上执行，也不等于已经拿到资源**。它可能还要等 CPU，或者在重新竞争锁时再次等待。I/O 完成、通知被处理、线程恢复、业务结果被消费，也可能是不同时间点。

超时同样只说明某次等待到达了它的返回条件，不自动取消生产者正在进行的工作。此时释放 buffer、销毁请求对象或离开场景，需要另有取消与寿命协议。Linux 内核的 [completion 文档](https://docs.kernel.org/scheduler/completion.html)专门提醒：等待提前返回后，仍须保证后续完成通知不会访问已经释放的对象。这是一个内核机制例证，游戏用户态代码需要遵守自己使用的 API 契约。

## 方法经过的时间，不等于线程执行的时间

下面只讨论一条线程从请求开始到返回的简化时间线。所有数字均为人为设定，用来检查分析口径，不代表某台设备：

| 区间 | 状态 | 假设发生的事 |
| --- | --- | --- |
| 0～2 ms | 就绪但未运行 | 等待获得 CPU |
| 2～4 ms | 运行 | 提交请求并进入等待 |
| 4～18 ms | 阻塞 | 等待条件满足 |
| 18～21 ms | 就绪但未运行 | 已被唤醒，尚未获得 CPU |
| 21～24 ms | 运行 | 消费结果并返回 |

在这个完整、互斥分类的模型中：

```text
经过时间 24 ms = on-CPU 5 ms + 就绪等待 5 ms + 阻塞等待 14 ms
```

它没有告诉我们 14 ms 全是磁盘传输，也没有证明 5 ms on-CPU 全是有用工作。要解释阻塞，需要继续追依赖方；要解释运行时间，需要调用栈、采样或硬件指标。对于真实 trace，采集缺口、中断和工具记账规则还会影响分类，应保留未知时间，不能强行凑平。

假如该线程在 18 ms 被唤醒，优化它之后的计算，对前面的阻塞没有直接解释力；假如主要损失在 18～21 ms，提高设备读盘速度也不直接解决这段调度等待。这里的价值是把候选方案放回它能影响的区间，而不是先套一个优化开关。

异步任务还要多考虑一层。它的 continuation（后续执行逻辑）可能正在应用队列里，而承载它的主线程一直在运行其他工作。此时 OS trace 里没有一条名为“这个任务”的阻塞线程。多个线程并行推进一项任务时，各线程 CPU 时间相加也不是该任务的经过时间；应找出决定完成时间的依赖路径。

## await、后台线程和分帧，各自改变哪一段

`await` 等待未完成操作时，可以挂起当前异步方法，把控制权交还调用方；对已经完成的操作，它可以直接取得结果而不挂起。它本身不要求阻塞当前线程。这是 [C# await 的语言行为](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/operators/await)，不等于底层操作完全没有线程成本。

例如，包装器可能把一个同步、会阻塞的 SDK 调用放到 Worker 上，再返回可等待对象。调用方可以不阻塞，但 Worker 仍会等待。若 SDK 没有合适的非阻塞接口，用**有界的专用 Worker 隔离阻塞**可以是合理取舍；需要承认其线程占用、排队、超时和退出成本。这补充了“异步优先”的适用边界。

同样，CPU 密集型工作放到后台不等于总完成时间必然缩短。它可能让主线程及时响应，但也增加数据交接，或与其他任务竞争核心、缓存和带宽。若主线程立刻同步等待后台结果，原来的关键依赖仍然存在。

Unity 是这种分层的具体例子。Unity 6.0 文档说明多数 Unity API 不具备线程安全性，需要在主线程调用；continuation 还受到 Unity 同步上下文和所用 awaitable 的规则影响。因此“资源后台准备完成”不等于“场景对象已经更新”，还要安排合法的主线程提交。具体行为见 [Unity 6.0 continuation 文档](https://docs.unity.com/en-us/engine/6000.0/manual/scripting/programming-distribute-work-threads/async-await-support/async-awaitable-continuations)，不要把某种恢复方式推广到所有版本与异步类型。

## 把机制放回一项场景准备工作

设想一个教学链路：请求资源字节 → 解压与解析 → 发布准备结果 → 主线程创建并挂接对象。这里假设解析只访问线程安全的独立数据，最后的对象创建必须由主线程完成；真实引擎 API 的约束需要另行核对。

如果最后一步很重，只把读文件改成异步，主线程整合仍可能集中发生。如果一次性启动大量后台请求，结果也可能集中涌回主线程；任务虽然更早排出去了，排队位置和内存峰值却发生了变化。

| 观测支持的原因 | 候选改动 | 需要一起检查的代价 |
| --- | --- | --- |
| 可拆分计算占据关键路径 | 减少工作量，或将独立部分并行／后台执行 | 数据复制、依赖、同步、带宽竞争和结果正确性 |
| 关键线程长时间就绪但未运行 | 检查竞争者、过量并发和亲和性约束，限制非关键工作 | 吞吐可能下降；不能仅凭该现象直接决定绑核 |
| 等待共享数据或锁 | 缩小临界区、调整持有关系、使用快照或消息交接 | 快照寿命、复制成本、状态一致性与允许的延迟 |
| 等待外部完成 | 使用合适的异步接口；必要时隔离同步阻塞调用 | 取消、超时、资源寿命与有界队列 |
| 结果已就绪，但主线程提交积压 | 设置提交预算、按可用单元分批消费 | 可见的半完成状态、完成时间与峰值驻留 |
| 首次使用前准备不足 | 在有依据的时机预加载／预计算 | 提前占用内存、预测错误产生的无用工作与取消 |

线程优先级只影响相应调度策略下的机会分配，不能让未满足的依赖自动完成。高优先级消费者如果依赖低优先级生产者，还要分析整条依赖链；不能期待所有 OS 和锁都自动消除优先级反转。Windows 的[优先级说明](https://learn.microsoft.com/en-us/windows/win32/procthread/scheduling-priorities)也提醒高优先级工作应保持短暂，避免妨碍其他必要工作。

亲和性则限制线程可以在哪里运行，可能用于特定约束，也会减少调度选择。具体核心能力、系统负载和移动设备热状态都会改变结果，本文不提供通用绑核或优先级配方。

设计可验收的任务接口，比仅仅规定“改成异步”更具体。例如：输入是否为不可变快照，后台结果由谁持有，允许几个请求在途，队列满了如何处理，场景退出后结果是否失效，主线程每次消费多少，以及失败与取消怎样回收资源。读盘后的阶段继续见[读盘完成与资源可用的区别]({{< relref "performance/game-performance-read-does-not-mean-ready.md" >}})；I/O 内部机制由[OS I/O 专题]({{< relref "engine-toolchain/storage-io-04-os-io-sync-async-dma-mmap-read-ahead-queue-depth.md" >}})承接。

## 怎样取得足以选择方案的证据

先固定一次用户可感知操作的起止点，例如“请求进入场景”到“允许操作”，再为关键任务记录请求、开始执行、外部完成、结果入队、主线程开始提交和真正可用等事件。多线程日志需要关联同一请求，并采用可对齐的时间基准。只在某个函数外围放计时器，通常只能得到区间耗时，不能自动分出运行与等待。

接着把任务标记与 OS 调度信息对齐。Android/Linux 可用 [Perfetto 调度事件](https://perfetto.dev/docs/data-sources/cpu-scheduling)观察切换、唤醒及线程状态；Windows 可从 [WPA CPU Analysis](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/cpu-analysis)的采样和精确调度分析入手。只有函数采样时，容易看到 on-CPU 热点，却缺少线程未运行时的完整原因。采集权限、事件覆盖和符号可用性都需要记录；空白区不能一律当作阻塞。

最小验证可以先设计两组对照，以下尚未执行：

1. **区分计算与等待。** 给相同起止标记之间分别放入确定的 CPU 工作和受事件控制的等待，在可控条件下比较 elapsed、on-CPU 与状态轨迹。预期是解释各自时间构成，不承诺固定耗时或固定切换次数。
2. **区分外部完成与业务完成。** 后台发布带请求 ID 的准备结果，主线程在指定处理点消费；分别标出发布、消费和可用时间。然后改变消费批次，检查响应性、总完成时间、结果一致性和中间状态，而不是只比较后台方法耗时。

真正用于优化结论时，应固定程序与内容版本、输入、设备与 OS、构建方式、Worker 配置、冷热与功耗状态、采集工具和窗口，重复观察分布与异常样本。改变并发或分帧后，还要检查取消、退出、重复请求以及高负载下队列是否有界；不能拿单次更短的函数时间替代整个场景的验收。
