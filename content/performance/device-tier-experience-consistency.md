如果分档验收只是在低档设备上跑一遍，然后说“能跑，没问题”，检查就还不完整。

但有一个更重要的问题没有被问到：**低档的玩家感觉这还是同一款游戏吗？**

这里关心的是：低档方案满足预算时，核心感觉还在吗？色调、角色辨识与打击反馈是否仍符合目标？具体哪些参数需要下降，应由使用条件与运行比较决定。

需要防止的一类问题是：参数都在预算内，关键辨识线索和反馈却丢了，让人觉得“这个游戏变味了”。

> 证据范围：本文提出体验接受条件和待比较方案，不提供玩家容忍度、耳机/外放占比、性能收益或盲测结果。文末 ARPG 是教学情境，参数不是机型推荐；Unity 映射参考 6000.0 文档，尚未执行设备、画面、听感或玩法验证。

## 视觉质量 vs. 视觉身份

先把两个概念分开。

**视觉质量**（Visual Quality）：可记录的画质参数与表现，例如 Shadow Map 分辨率、粒子数量、Render Scale、贴图尺寸。它们可列为分档候选，但参数下降会影响哪些内容、玩家能否接受，都需要对照，不能由机型档位推定。

**视觉身份**（Visual Identity）：让这款游戏具有辨识度的核心元素，如色调风格、角色轮廓、标志性的特效和 UI 反馈。这里把它们列为优先保护的接受条件，具体实现仍可以比较和替换。

这两个维度并不独立：降低分辨率也可能损失辨识度。本文不预设玩家更容忍哪一种改变，应先列出要保护的线索，再用目标画面和体验检查确认。

## 找到你游戏的视觉身份元素

不同游戏的视觉身份来自不同的地方。在做低档配置之前，应该先问：

**这款游戏靠什么让玩家一眼认出它来？**

几个常见的来源：

### 色调与氛围

如果游戏依赖明确的色调特征，就应先列出要保护的颜色与明暗关系，再检查 Color Grading 或其他实现怎样参与这些目标。

操作：可把预制 LUT、较低精度的颜色分级或其他色调方案列为候选，比较目标色调和实际渲染工作。预制 LUT 不等于零运行成本；URP 的 LUT 大小、分级模式及相关后处理仍有质量和开销取舍，见 [URP Asset](https://docs.unity3d.com/6000.0/Documentation/Manual/urp/universalrp-asset.html)。本篇未取得目标设备上的增量结果。

### 角色辨识度

如果角色是当前玩法和镜头的核心，角色主贴图、面部特征和轮廓可以列为优先检查对象；不能仅凭游戏类型推定所有玩家的关注点。

操作：固定目标镜头、UV 与渲染分辨率，比较尺寸和格式候选是否保住必要特征，不设统一的角色最低尺寸或 ASTC 块大小。场景中的导航、交互和叙事线索同样要检查，不能一律替角色承担降级，见[资产规格]({{< relref "performance/device-tier-asset-spec-texture-and-package.md" >}})。

### 技能特效风格

如果技能依赖蓝色流光、特定粒子形状等标志性特征，可先把这些特征列为辨识检查对象。

操作：比较粒子密度时，同时检查技能的形状、颜色、出现时序和危险范围提示。减少数量可能影响这些线索，保留某个百分比也不能保证效果；本篇没有两种密度的辨识测试。

### 打击感与反馈

打击反馈可能由音效、屏幕抖动、命中粒子和受击位移共同构成，需要把各项与实际命中时序对应起来。

操作：把命中时序、受击反馈和可辨识提示写进接受条件，再比较屏幕抖动、命中粒子或替代实现。粒子覆盖、叠层、材质与并发会改变成本，不能把命中粒子统一称作低代价，也不能预先比较感知损失与 GPU 收益。

## 身份不只是视觉：听觉和动画也在传达"是不是同一款游戏"

低档配置在讨论时容易被收成"画质讨论"，但玩家感知"同一款游戏"时，画面只是其中一层。**音效和动画的降级同样能把游戏感觉做没**。

### 听觉身份

降采样率、减少音轨层数或关闭空间处理，改变的工作并不相同。采样率影响可表达的频率内容，层数影响同时参与的声音，空间处理涉及定位与后端工作；具体 CPU、内存和听感变化还取决于编码、Load Type、并发和输出条件，不能先认定收益极小或感知损失很大。

| 音频元素 | 优先保护的接受条件 | 可比较方案与检查 |
|---------|--------|------|
| 标志性音效（技能、命中、击杀、胜利）| 提示意义、时序与辨识 | 编码/表示可比较，不预设与视觉记忆等强 |
| BGM 完整度 | 当前编排需要的旋律、节奏和动态变化 | 比较不同分层或混音版本，不保证少一层就损失身份 |
| 环境音 layer 数量 | 环境与玩法线索 | 可比较精简，但须查混音与并发，不宣称多数玩家听不出 |
| 3D 空间音效 | 定位、距离与玩法提示 | 按目标后端和耳机/外放分别检查，不由机型推定输出习惯 |
| 音频采样率 | 必要频率内容与最终混音的辨识 | 按素材比较候选，不能只凭人声或主音效分类断言影响 |

操作要点：层数、采样率、声道、编码与加载策略分别比较，不设“先砍层数”的通用顺序。听感比较需匹配音量并说明输出设备，同时观察首播、循环和并发；不能用文件变小代替运行成本。字段与加载边界见 [Audio Clip Import Settings](https://docs.unity3d.com/6000.0/Documentation/Manual/class-AudioClip.html)及[内存音频节]({{< relref "performance/cpu-opt-05-memory-budget.md" >}})。

### 动画身份

动画承载动作节奏与辨识。源采样、压缩误差、运行求值/更新频率和显示帧率是不同变量，不能合成一个“动画帧率”；插值与状态更新也会影响最终表现。骨骼或层级精简则要确认蒙皮、挂点、脚本和重定向等消费者。

| 动画元素 | 优先保护的接受条件 | 可比较方案与检查 |
|---------|--------|------|
| 主角战斗动画更新 | 起手、命中、响应与混合时序 | 分别比较压缩/更新策略，不由采样数字推定卡顿 |
| 主角骨骼 LOD | 姿态、轮廓、挂点与驱动关系 | 先列消费者，再比较候选，不能仅按主角身份禁止或允许 |
| NPC 动画更新 | 屏幕贡献及战斗/交互提示 | 按镜头和用途比较，无通用的远景更新率 |
| NPC 骨骼 LOD | 必要蒙皮、挂点与玩法功能 | 不规定减半，也不保证远处一定无影响 |
| 镜头运镜节奏 | 叙事、瞄准和操作反馈 | 比较替代实现后确认关键时序 |
| 布料 / 头发解算 | 轮廓、运动线索与必要互动 | 比较模拟、预制变形或静态替代；额外数据与运行工作另查 |

核心原则：按功能列出必须保留的节奏、辨识和绑定关系，远处或次级对象同样需要接受条件。不能预设玩家统一更在意更新率而不在意形变，也不能把 Optimize Game Objects 等层级优化等同于删除蒙皮骨骼，相关边界见 [Rig Import Settings](https://docs.unity3d.com/6000.0/Documentation/Manual/FBXImporter-Rig.html)。

## 按游戏类型的视觉身份清单

下面按类型列的是待讨论的保护目标与候选，并非该类型的统一验收表；角色、场景或特效的重要性仍需结合实际玩法判断。

### 动作 / ARPG

| 视觉元素 | 保护目标 | 可比较方向 |
|---------|--------|------|
| 角色主贴图 | 对应镜头的必要特征 | 尺寸/格式候选，不设统一最低尺寸 |
| 核心技能特效 | 形状、颜色、时序与范围提示 | 比较密度或其他表示，逐项确认 |
| 打击反馈（Camera Shake / 命中粒子）| 命中与响应线索 | 比较实现和并发成本，不预设低代价 |
| 实时阴影 | 落地关系及必要提示 | 比较实时、Blob 或其他方案，不要求固定替代 |
| 场景背景贴图 | 导航、交互与氛围线索 | 在目标镜头下比较简化 |
| SSAO | 当前场景需要的接触/层次关系 | 比较开关与替代，不按游戏类型判断感知弱 |

### 开放世界 / MMO

| 视觉元素 | 保护目标 | 可比较方向 |
|---------|--------|------|
| 整体光照色调（黄昏/黎明等）| 需要的时段与氛围辨识 | 比较色调实现，不要求固定保留 LUT |
| 地形和建筑细节 | 目标镜头下的轮廓与交互线索 | 按投影和用途选候选，不规定统一米数 |
| 角色外观（装备高光、皮肤细节）| 已确认的重要外观特征 | 用目标展示和玩法镜头比较 |
| 植被密度 | 场景构图、遮挡与必要功能 | 比较密度/表示，不给统一百分比 |
| 远处场景质量 | 轮廓、地标和必要动态提示 | 比较简化，不能只按距离忽略 |
| NPC 同屏数量 | 任务、交互、战斗和场景需求 | 区分显示、模拟与玩法实体，不直接按档位删对象 |

### 卡牌 / 回合制 RPG

| 视觉元素 | 保护目标 | 可比较方向 |
|---------|--------|------|
| 角色立绘 | 实际展示需要的特征 | 按显示尺寸比较，不设全档统一尺寸 |
| 卡牌动效 | 状态、操作与角色提示 | 按功能比较简化，不能由主角/NPC 分类直接决定 |
| 战斗特效的颜色和风格 | 关键提示与表现目标 | 可比较 Flipbook 与粒子；覆盖、采样和资源成本仍需检查 |
| 背景场景 | 构图、交互及叙事线索 | 按实际镜头比较简化 |
| UI 动画 | 状态切换与操作反馈 | 比较简化或替代，不一律保留全部动画 |

### 休闲 / 超休闲

| 视觉元素 | 保护目标 | 可比较方向 |
|---------|--------|------|
| 整体色彩 | 当前游戏的必要风格与辨识 | 按目标画面比较实现，不预设统一饱和风格 |
| 核心 Gameplay 反馈特效 | 消除、速度等玩法反馈 | 先列接受条件，再比较替代实现 |
| 背景细节 | 导航、障碍和构图线索 | 按玩法比较，不假设背景没人关注 |
| 角色精细度 | 目标镜头的轮廓与必要特征 | 比较尺寸/几何，不给通用“够用”数字 |

## 一个教学对比：通用削减与体验保护目标

下面是教学对比，用来说明两种方案该检查什么。配置尚未实现；没有目标设备、构建体积、帧率、社区反馈或收益结果。数字只帮助区分候选，不是推荐值。

**背景**：假设一款主打“红蓝流光剑气”的 ARPG，需要为目标设备设计低档候选。具体设备、图形能力与帧预算仍待选定，不用机型名称代替能力验证。

### 方案 A：按通用规则砍

假设团队直接套用这样一份“低档配置模板”：

- Color Grading 关闭（"LUT 计算贵"）
- 所有实时阴影关闭（"Shadow Map 代价高"）
- 粒子密度统一砍到 30%
- 贴图全部降到 512 ASTC 8x8
- 关闭 Bloom 和 Camera Shake

对方案 A 应提出以下检查问题，这些不是已取得的玩家反馈：

- 剑气的流光、形状与危险范围提示是否仍可辨识？
- 匹配镜头后，高低档是否保留相同的关键角色和场景线索？
- 命中反馈与实际命中时序是否仍一致？
- 原本设定的蓝紫色调是否被不合预期地改变？

这些问题用于识别是否误伤关键体验；检查前不把风险写成已经发生的结果。

### 方案 B：按身份清单砍

围绕保护目标提出另一组待比较配置：

| 配置项 | 方案 A 候选 | 方案 B 候选 | 需要确认 |
|-------|-----------|-----------|------|
| Color Grading | 关闭 | 比较预制 LUT 方案 | 色调是否符合目标，实际后处理成本 |
| 主角实时阴影 | 关闭 | 比较 512 Shadow Map、15m 距离候选 | 落地关系、遮挡、清晰度与成本，不保证该值可用 |
| 远处实时阴影 | 关闭 | 对适合的静态内容比较烘焙 | 动态对象和时间变化能否接受，额外数据成本 |
| 剑气特效粒子密度 | 保留原数量的 30% | 比较 40%，以保住形状和颜色为目标 | 必须看目标画面，比例不保证形状保留 |
| 背景装饰粒子 | 保留原数量的 30% | 比较关闭 | 有无承载必要提示或氛围 |
| 主角贴图 | 尺寸 512 | 比较 1024、ASTC 6x6 | 格式支持、使用镜头与误差 |
| 远景贴图 | 尺寸 512 | 比较 256、ASTC 8x8 | 地标和轮廓线索、实际占用 |
| Bloom | 关闭 | 若实现支持，比较低分辨率路径 | 流光目标、阈值/强度、实际缓冲和 pass；不把“1/4”当统一选项 |
| Camera Shake | 关闭 | 比较保留或调整 | 命中反馈与舒适度、实际更新工作 |

两组候选应在相同设备、路线、镜头和负载下比较，再分别记录画面、CPU/GPU、内存和产物。多个设置同时改变时，不能把总差值直接归因给其中一项；此处没有“额外成本很小”或稳定帧率结果。

**待确认的目标**：候选应保住红蓝流光、角色辨识和命中反馈，并满足预算。两者都通过后才能接受方案 B，不能仅因它按身份清单设计就称为正确或有收益。

这个对比强调：选择低档方案时，除预算外还应明确要保护的体验。通用模板可以提供候选，具体接受条件仍需项目设计和目标体验检查。

## 一个检验方法：截图盲测

可以用截图比较初筛静态风格问题；它不能单独验证完整视觉身份、动作、声音或操作体验。本篇尚未执行这项检查：

1. 固定镜头、角色状态、光照时段和输出条件，截取匹配的高低档画面，记录版本与配置。
2. 隐去档位标签并打乱呈现顺序，请未参与配置的人比较；记录受试范围，不将小样本当成全体玩家。
3. 问是否有共同风格、丢了哪些辨识线索，并记录具体位置；动态反馈、动画、声音和操作另用匹配路线检查。

“像两款游戏”是复查线索，需要定位色调、细节、时段或状态差异；“同一款但画质不同”也只支持当前截图条件，不能据此宣布整个分档方向正确。

截图检查可帮助定位色调、角色细节或特效静态形状的差异；通过后仍需检查目标设备运行预算及完整体验。

## 分档配置里需要复查的操作

| 待复查的操作 | 可能损失什么 | 比较方向 |
|---------|------------|---------|
| 低档关掉 Color Grading | 既定色调或层次 | 比较 LUT、分级精度或其他实现的效果与成本 |
| 统一降低角色主贴图尺寸 | 必要特征与边缘细节 | 按目标镜头比较，不规定统一最低尺寸 |
| 核心技能特效全部关掉 | 形状、范围和时序提示 | 比较简化或替代表示；Flipbook 也不保证低成本 |
| Camera Shake 关掉 | 部分命中反馈 | 连同其他反馈、舒适度和实际实现比较 |
| LOD 切换过激 | 轮廓或必要细节的连续性 | 按屏幕贡献、镜头和切换表现比较，不指定近景保留层数 |
| 光照色温改变 | 时段与氛围辨识 | 按既定目标比较替代照明，不先判定所有色温调整违规 |

## 在开发期检查：让设计带着低档候选

一种需要防范的工作流风险是：**低档设备没有进入设计评审**。如果只在开发机上评审，到接近发布才做低档候选，发现问题时可能需要返工；本篇不据此推定多数团队都采用这种流程。

更稳的做法是把低档放进日常工作流：

### 1. 在提需求阶段讨论目标档位的表现

TA 和美术合作定效果时，除了高档目标，应该同时回答：

- 各目标档位需要保留哪些体验条件
- 哪些参数或实现可以作为比较候选
- 现有实现无法满足预算时，可以比较什么替代方案

如果暂时回答不了“低档的这个效果长什么样”，应把它登记为待确认风险，明确比较方案和负责人，再决定是否进入下一阶段。

### 2. 美术 review 有一轮在低档机上过

新角色、新场景、新特效评审时，从项目支持范围选代表设备和固定路线，不用一个 GPU 型号证明覆盖足够。检查必要体验的同时记录预算，不能仅因看起来符合目标就忽略性能。

评审频率按改动风险与版本节奏安排，记录本次覆盖和未覆盖的内容，不设“每周一次足够”的通用保证。

### 3. 截图自动化：每次提交构建都存一组低档截图

可在 CI 中为选定构建、配置和路线留存截图，供美术和 TA 比较版本变化；自动截图环境还需检查可重复性。它有助于提前发现差异，但不保证提前多久，也不能替代目标设备和动态路线。本篇尚未接入该流程。

### 4. 标志性效果单独挂 owner

色调、主角、标志性技能特效、打击感——这四类身份元素应该有明确的 owner（不是每个都同一人）。任何人想改这四类的低档配置，必须过 owner 这一关。

负责人需要审查保护目标、替代方案和验证记录；明确责任有助于减少未经审查的降级，但不能保证问题不再发生。

---

## 结论

分档的目标不是让低档设备玩到一款"降级版游戏"，而是让他们玩到**同一款游戏的轻量版本**。

区别在于：前者是不同的产品，后者是同一个产品在不同硬件上的表现。

每次降质前，先写清要保护的体验，再比较实现与预算；方案只有同时满足接受条件和目标设备约束，才有依据采用。
