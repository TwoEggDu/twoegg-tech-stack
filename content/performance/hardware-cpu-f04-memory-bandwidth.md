一段“计算不多”的代码跑得慢，可能是访问链太长，也可能是单位时间要搬的数据太多。这分别对应延迟和带宽问题，优化方向并不相同。在共享内存系统中，还要考虑 CPU、GPU 和其他单元的并发流量。

本篇先建立计算口径，再讨论数据布局能减少哪部分流量。文中的数值推导都是标明前提的模型，不是设备实测结果。

---

## 两个不同的指标：带宽与延迟

延迟和带宽描述不同维度，但会相互影响，例如请求排队会增加负载下的访问延迟。

**延迟（Latency）**：在指定测量边界内，从发出访问到所需数据可用的时间。单位是纳秒（ns）或 CPU 周期（cycle）。必须说明测的是 DRAM 时序、某级缓存，还是 CPU 端到端访问。

**带宽（Bandwidth）**：单位时间内能够传输的数据总量。单位是 GB/s。

用水管来类比：延迟是水源到水龙头的管道长度，带宽是水管的直径。管道很长，水从源头流到你手里要等一段时间——这是延迟。水管很细，即便等到了，每秒流过的水量也有上限——这是带宽。

对游戏代码的影响截然不同：

- **延迟**影响依赖该数据的后续工作何时能继续。L1 miss 可能由 L2、末级缓存或其他核心缓存满足，不必然访问 DRAM；乱序执行和多个独立请求也可能隐藏部分等待。指针追逐这种“拿到地址才能发下一个请求”的代码，通常更难隐藏延迟。
- **带宽**约束大量数据搬运的持续吞吐。连续遍历可能形成足够多的在途请求，逐步接近带宽上限，但数据在缓存中、计算较重或并行度不足时，瓶颈会不同。

仅作单位换算：**假设**某次测量延迟为 80 ns、CPU 实际频率为 3 GHz，则对应 240 个周期；这不代表整条流水线必定停顿 240 周期，也不是本文给出的设备延迟。

## 内存规格：先算清理论带宽

接口峰值的基本换算是：

```text
理论带宽（GB/s，十进制）
= 数据传输率（MT/s）× 总数据位宽（bit）÷ 8 ÷ 1000
```

以下只是**给定传输率与总位宽后的算例**，并非各类设备的默认配置：

| 假设配置 | 计算 | 接口理论带宽 |
|---------|------|-------------|
| DDR4-3200，总数据位宽 128 bit | 3200 × 128 / 8 / 1000 | 51.2 GB/s |
| DDR5-6000，总数据位宽 128 bit | 6000 × 128 / 8 / 1000 | 96 GB/s |
| LPDDR5-6400，总数据位宽 64 bit | 6400 × 64 / 8 / 1000 | 51.2 GB/s |

MT/s 已经是传输率，不能因为 DDR 再乘一次 2。通道、子通道的叫法随内存代际变化，核对**总数据位宽**比只写“双通道”更明确。这里的 GB 是十进制单位，不能直接与 GiB 混用。

这些数字还不能告诉我们三件事：

1. **CPU 访问延迟**。CAS 等 DRAM 时序只描述命令过程的一部分，不能拿十几 ns 的器件时序代替 CPU 端到端访问；缓存、互连、控制器与排队都可能参与。
2. **应用可持续带宽**。读写切换、刷新、访问模式、控制器利用率以及并发负载都会影响结果，持续读、持续写和混合读写也不是同一测试。
3. **两类设备的固定倍数差距**。只有传输率、总位宽、频率策略和测量口径都明确，才有可比较的规格或实测结果。

工程中应同时保留“设备规格的上限”和“匹配负载的持续测量值”，不把规格表直接填进帧预算。

## UMA：共享内存如何改变预算

应按具体内存拓扑区分，不能把“桌面 / 主机”统一画成独立显存，也不能把 UMA 当成手机独有的设计。

### 独立显卡 PC 示例：系统内存与显存分开

```text
CPU ── 系统内存控制器 ── 系统 DRAM
 │
 └──── PCIe 等主机互连 ── 独立 GPU ── 显存控制器 ── 显存
```

GPU 的显存访问与 CPU 的系统 DRAM 访问使用不同内存接口；PCIe 位于主机与独立 GPU 之间，不是 GPU 访问本地显存的通道。但资源上传、下载或访问主机内存仍可能使用系统内存带宽与互连，因此也不能说两者完全互不影响。

### UMA 示例：多个单元共享物理内存资源

```text
CPU / Cache ─┐
GPU / Cache ─┼─ 片上互连与仲裁 ── 内存控制器 / 多通道 ── 共享 DRAM
其他单元 ────┘
```

CPU 与 GPU 同时产生到 DRAM 的流量时，可能竞争公共资源。但这不是一根固定速率的管道：缓存命中、多个通道、访问时序、仲裁和频率策略都会改变可用吞吐。不能用“规格峰值减去 GPU 某个估计数”算出 CPU 保证能用的带宽。

游戏中 CPU 逻辑和 GPU 渲染可能重叠，因此要在代表性并发场景下测量；不能只用 CPU 空载基准代表整机运行时的条件。UMA 也存在于桌面级平台，例如 Apple Silicon 的 CPU 和 GPU 共享内存，但资源可见性和同步仍要遵守 API 约定，见 [Apple GPU 存储模式说明](https://developer.apple.com/documentation/metal/choosing-a-resource-storage-mode-for-apple-gpus)。

## 带宽瓶颈如何出现：Roofline 模型

判断一段代码的性能上限，有一个经典工具：**Roofline Model**（屋顶线模型）。它把算力与数据搬运放在同一个模型里。

先指定流量的测量边界，例如 DRAM，而不是把 L1 流量与 DRAM 带宽混在一起。令算术密度 `I = 浮点运算数 / 该边界传输字节数`，计算上限为 `C`，带宽上限为 `B`，则：

```text
性能上限 P ≤ min(C, B × I)
转折点 I = C / B

性能（FLOP/s）
  │           ┌──────────────── 计算上限 C
  │          /│
  │         / │  带宽上限线 B × I
  │        /  │
  └───────────┼────────────────→ 算术密度（FLOP/byte）
              C/B（转折点）
```

转折点左侧的屋顶由带宽约束，右侧由算力约束。**落在左侧不等于实际运行已经打满带宽**：依赖链、访存并行度不足、分支或调度开销，可能使性能远低于屋顶。模型与测量方法见 [Berkeley Lab 的 Roofline 说明](https://amcr.lbl.gov/departments/computer-science-department/ppan/roofline-performance-model/)。

以三维位置更新 `position += velocity * dt` 为例，忽略标量 `dt` 的重复装载，按算法语义计数：

| 项目 | 每个实体的工作量 |
|------|----------------|
| 浮点计算 | 3 次乘法 + 3 次加法 = 6 FLOP |
| 输入读取 | position 12 bytes + velocity 12 bytes |
| 输出写入 | position 12 bytes |
| 语义数据量口径下的比值 | 6 / 36 = 1/6 FLOP/byte |

这个推导揭示了计算与搬运的比例，但 **36 bytes 并非已经测得的 DRAM 流量**。缓存复用、缓存行粒度、预取、写分配和回写会改变流量；只有把分母换成相应层级的实际或明确建模的字节数，才能与那一层的带宽上限比较。

同样不能仅凭“碰撞检测”“PBR”“FFT”的名称判断瓶颈。比较和整数操作也不能直接计成浮点运算；具体算法、数据规模与复用方式才决定模型是否合适。

## 数据导向在带宽受限下的实际意义

这里用一个限定条件的模型说明 AoS（Array of Structures，结构体数组）与 SoA（Structure of Arrays，按字段组织数组）的区别。

假设 `float` 和 `int` 都为 4 bytes，下面的 `Float3` 紧凑存储，**缓存行为 64 bytes，数组首地址按 64 bytes 对齐**：

```cpp
#include <cstddef>

struct Float3 { float x, y, z; };
struct Quaternion { float x, y, z, w; };

struct alignas(64) Entity {
    Float3 position;      // offset 0，12 bytes
    Float3 velocity;      // offset 12，12 bytes
    Quaternion rotation; // 16 bytes
    float health;        // 4 bytes
    float energy;        // 4 bytes
    int flags;           // 4 bytes
    char padding[204];
};
static_assert(sizeof(Float3) == 12, "example assumes packed float3");
static_assert(offsetof(Entity, velocity) == 12, "check hot-field offset");
static_assert(sizeof(Entity) == 256, "check example stride");

// 10000 个实体占 2,560,000 bytes，即十进制 2.56 MB
```

如果只读写 `position` 和 `velocity`，热点范围是每个实体开头的 24 bytes。**结构体占 256 bytes，不代表每轮必须把全部 256 bytes 读进缓存**：按上述布局，热点只落在一条 64-byte 缓存行里。

用字段级拆分布局存放相同热点数据：

```cpp
alignas(64) Float3 positions[10000];
alignas(64) Float3 velocities[10000];
// 两个数组各占 120,000 bytes；冷字段另外存放
```

比较一次遍历触及的**不同热点缓存行足迹**，忽略预取额外流量，不统计回写：

| 布局 | 10000 个实体的热点缓存行数 | 热点行覆盖字节 | 有效热点数据 / 行覆盖字节 |
|------|--------------------------|---------------|-------------------------|
| AoS，实体步长 256 bytes，热点均在首行 | 10000 | 640,000 | 240,000 / 640,000 = 37.5% |
| AoS，实体步长 64 bytes，热点位置相同 | 10000 | 640,000 | 37.5% |
| 两个连续 Float3 数组 | 3750 | 240,000 | 100% |

`Float3` 元素可能跨行，不是“一行固定装 5 个完整元素”；这里按整个连续数组的字节范围计算。100% 也只指这个特定遍历需要全部热点字段，不代表所有 SoA 工作负载。

这个模型说明拆分可以降低热点足迹，却**不能推出等比例加速**。实际 DRAM 读写还受缓存初始状态、预取与脏行回写影响；若数据已驻留缓存，变化也不一定表现为 DRAM 带宽减少。更多布局条件见 [F06：数据布局]({{< relref "performance/hardware-cpu-f06-data-layout.md" >}})。

## NUMA：节点位置会改变访问成本

NUMA（Non-Uniform Memory Access，非均匀内存访问）表示不同处理单元到不同内存节点的访问成本并不相同。多路服务器是常见例子，但 NUMA 不仅由插槽数决定，应以 OS 暴露的拓扑为准。

```text
CPU / 节点 0 ── 跨节点互连 ── CPU / 节点 1
     │                             │
   本地内存                       本地内存
```

若线程运行在节点 1，而所需页面位于节点 0，未被缓存满足的请求可能需要经过远端链路。远端延迟、可用带宽与竞争情况要实测，不能统一写成“延迟翻倍、带宽减半”。

实践时同时检查**线程放在哪里**和**页面放在哪里**。只绑定线程不一定改变已有页面的位置；Linux 的内存策略、首次触页以及 cpuset 限制也会参与分配，见 [Linux NUMA Memory Policy](https://docs.kernel.org/admin-guide/mm/numa_memory_policy.html)。

按房间或 World 分区、配置线程亲和性与内存策略，可以作为对照方案；但把所有线程固定在一个节点也可能造成负载不均或限制可用资源。应比较吞吐、尾延迟和跨节点流量后再决定，不把“一 World 一节点”写成通用要求。

## Non-Temporal 写入：减少写分配的特定场景

在常见的 write-back、write-allocate 缓存策略下，普通写入冷数据可能需要取得缓存行及写权限，再修改并最终回写：

```text
普通写入未持有所需缓存行 / 权限
→ 获取该行及写权限（可能涉及 Read-For-Ownership）
→ 修改缓存中的数据
→ 脏行在之后回写
```

这解释了为什么只写新结果也可能伴随读流量，但不能把它写成“每写 4 bytes 必定从 DRAM 读 64 bytes”。数据可能已在缓存，也可能由其他缓存提供，具体 CPU 还可能优化某些整行写模式。

x86 的 `MOVNTPS` / `MOVNTDQ` 等 non-temporal store 可用于流式输出，减少部分写分配与缓存污染。但它们涉及对齐、写合并和顺序要求，不是同步地直达 DRAM；把结果交给其他线程或设备时，仍需按指令和发布协议处理必要的排序，例如适用情况下的 `SFENCE`。指令细节见 [Intel 架构手册](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html)。

ARM 的 `VSTMIA` 与普通 `ST1` 不能当作对应的 NT 写入。AArch64 有 [STNP 非临时提示指令](https://developer.arm.com/documentation/ddi0487/mb/-Part-C-The-AArch64-Instruction-Set/-Chapter-C6-A64-Base-Instruction-Descriptions/-C6-2-Alphabetical-list-of-A64-base-instructions/-C6-2-412-STNP)，但提示不是所有实现上都绕过缓存的保证，也不等于与 x86 有相同效果。

适合考虑的条件是：输出大、访问连续、很快不再由 CPU 读取，并且普通写入已被证实受流量或缓存污染影响。小缓冲区、立即复读的结果可能不适合。不能仅凭使用 Job System 就断言编译器自动选用了 NT 指令，应检查生成代码和真实负载。

## 回到原点：移动端 DOD 的带宽压力更大还是更小

不能仅靠“手机”或“桌面”的分类给出固定答案。更有用的是依次检查三个条件：

**第一层：持续可用带宽。** 从具体设备的传输率和总位宽识别规格上限，再用匹配访问模式的负载测量。桌面同样可能带宽受限，移动端也可能先受延迟或计算约束。

**第二层：共享资源竞争。** 在 UMA 上比较 CPU 单独运行与代表性 CPU / GPU 并发场景，关注双方的耗时和流量变化。不要把一次空载测量当成所有场景的固定预算。

**第三层：持续功耗与温控。** 减少无用数据搬运有机会减少相关能耗，但是否改善整机功耗、温度和持续帧时间，需要控制设备状态并运行足够长时间验证。

DOD 的实际价值在于：围绕具体访问模式提高热点数据密度和复用率，减少不必要的搬运。能释放多少预算、是否改善帧时间，要由目标负载回答。

## 小结

- **延迟与带宽**是不同指标；访问链等待与持续吞吐受限需要不同证据。
- **规格峰值**由传输率和总位宽计算，不能替代应用持续带宽或端到端延迟。
- **UMA**使多个单元共享内存资源，竞争程度取决于实际访问与缓存行为。
- **Roofline**给出指定流量口径下的上限，不证明应用已达到那个瓶颈。
- **布局分析**按触及的缓存行与读写行为计算，不能把 `sizeof(Entity)` 当成每次访问流量。
- **NUMA 与 NT 写入**都有拓扑、访问模式和正确性条件，应在目标平台验证收益。
