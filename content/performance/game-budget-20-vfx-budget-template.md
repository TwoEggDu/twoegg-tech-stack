特效预算最容易写成“一个技能最多多少粒子”，但这很快就会失真。

更有用的写法，是让每个技能或一组战斗表现都有一张组合验收表。

## 模板字段

每张表先绑定规则 ID/版本、任务与内容版本、设备/实际画质配置、镜头和并发条件；再引用指标规格，写清单位、对象/子系统范围、窗口/统计量、采集来源，以及首次、稳态、停止/回池后的阶段。候选上限与实际记录分开填；未采集、不支持或缺失须明记，不能填零或通过。规则、依据、负责人和复验约定可沿用[同任务预算记录]({{< relref "delivery-engineering/delivery-performance-stability-02-budget-system.md" >}})，不必把所有关联信息塞进这张表。

| 字段 | 数值 / 等级 | 备注 |
|------|------------|------|
| 发射器数量 |  | 注明根/子系统、实例及启用范围 |
| 最大活跃粒子数 |  | 注明计数范围、采样窗口及漏采风险；与发射量分开 |
| 最大屏占比 |  | 注明相机、目标/视口、分母及覆盖判定；峰值对应哪个窗口 |
| 透明叠层风险 |  | 注明 Pass、材质和层数口径；诊断图不代替原渲染计时 |
| 是否使用 RT / 扭曲 |  | 记录规格、共享/实例归属、启用阶段和释放条件 |
| 贴图 / 网格资源量 |  | 文件字节与运行分配分开；共享分配去重，实例缓冲另计 |
| 是否需要预热 |  | 记录预热条件、首次反馈与驻留代价，保留未预热对照 |
| 对象池策略 |  | 分记活跃/保留数、容量上限、实际分配、重置/退役及持有者 |
| 出现时机 |  | 绑定首次/稳态/尾部和组合任务；资源峰值按同一时刻、同口径合计 |
| 最低支持档位 |  | 引用已验证的设备/配置/任务记录；只有候选时标待校准 |

覆盖、生命周期和共享/实例的填写口径见[特效预算的教学账本]({{< relref "performance/game-budget-09-vfx-budget.md#vfx-resource-ledger-teaching" >}})及前两节。结构计数、资源量和任务净增耗时分别记录，不能由单体总量乘并发数代替组合验证。

## 为什么这些字段必须一起看

因为特效最容易同时打爆：

- CPU 模拟
- GPU overdraw
- 内存和对象池
- 关键时机的帧预算

## 怎么用

1. 先按技能或特效簇建表。
2. 再按目标设备档位写允许版本。
3. 验证时固定：
   - 单独释放
   - 战斗高峰叠加
   - 首次命中

这些是需要分别固定条件的观察场景，不是共用一个窗口取最大数。表格填齐只提供制作预警和验收输入；性能接受仍需匹配规则的有效观测、完整必要反馈及副作用检查。没有实际验证记录时，不能把最低候选档位写成已支持，也不能把未知结果变成通过。

## 最短结论

特效预算模板的价值，不是限制创作，而是让团队在做强反馈时知道：

`这次表现到底在花哪几笔账。`
