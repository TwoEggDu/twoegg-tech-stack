> 性能判断要能回答：当前知道什么，凭什么做这个改动，结果不符合预期时回到哪里继续查。把这些问题和交接责任连起来，方法才有机会被团队重复使用。

本篇收束前面的基础与诊断文章，解释如何从一个使用障碍走到可复查的决定。它提供工程建议和教学推演，不代表某个项目已运行这套流程，也没有设备 trace 或优化收益实测。具体计时、平台和工具契约继续由相应基础篇维护。

## 从一个具体任务开始

“某个技能第一次放的时候顿一下”，仍然不足以决定采用对象池、预加载还是降低特效。首先要知道：谁在什么构建、设备和操作中遇到了什么障碍，这次需要改善的是哪一个结果。

例如，同一句“技能卡”可能指输入到动作反馈晚、首个特效出现晚、应用长间隔，或画面更新不均匀。这些对象可以相互影响，却需要不同的起止点和证据。先与提出问题的人确认具体受阻任务，再选择测量入口。

前面的[一帧链路]({{< relref "performance/game-performance-frame-breakdown.md" >}})区分逻辑、渲染、呈现与输入反馈，[诊断方法]({{< relref "performance/game-performance-diagnosis-method.md" >}})区分现象、假设、证据与结论。本篇在它们之上组织决定与交接，不再建立第二套指标定义。

## 一条可以回退的工作流

可以把一次调查组织为：

**定义目标与条件 → 保存观察 → 提出候选解释 → 取证与对照 → 选择改动 → 复测与接受 → 沉淀及跟进。**

箭头表示信息如何交接，不是必须一次走完的审批流水线。可以先做小范围探索；新证据否定解释、测试条件变化或结果缺失时，要返回对应步骤，保留原假设和失败记录。

### 1. 定义目标与条件：先约定改善什么

固定程序与内容身份、设备／OS／图形 API、质量与渲染尺寸、目标帧率与刷新率、操作路线、缓存及热／供电状态。首次使用、重复使用、稳定战斗和持续运行分别划定窗口。

同时写清正确性和体验要求：什么反馈不能推迟，哪些视觉元素必须保留，允许增加多少加载等待或资源驻留。接受条件应由项目目标与实际设备条件确定，本篇不提供通用数值门槛。

若连“动作先响应但特效稍后到达能否接受”都未约定，就先回到产品与表现要求；代码局部变快不能替代这个决定。

### 2. 保存观察：把原话与测量分开

使用者反馈、复现操作、直接观察、工具数据分别记录。保留正常与异常样本、采集方式、缺失字段和未覆盖窗口。复现不稳定时先收集触发条件，不把偶然相关认作原因。

诊断采集可能改变运行开销。Unity 2022.3 的[应用采集说明](https://docs.unity3d.com/2022.3/Documentation/Manual/profiler-profiling-applications.html)规定连接 Player 的 Unity Profiler 使用 Development Build；因此采集配置和目标交付配置要分别报告。详细采样帮助定位，最终收益仍需按实际交付条件用适用方式复验。

若没有能关联到本次任务的证据，下一步产物是采集设计，不是瓶颈结论。计时对象不一致或时钟未对齐时，返回指标定义和采样步骤。

### 3. 提出候选解释：沿依赖寻找限制

把这次任务的输入、资源就绪、对象与生命周期、提交、GPU 工作及所需反馈对应起来。它们不是每次都顺序执行：任务可以提前准备、命中缓存或与其他工作重叠，Present 请求也不等于画面已经显示。

六类名称用于选择证据，不是六个互斥时间桶：

| 调查入口 | 本次真正要追问什么 |
| --- | --- |
| CPU | 目标依赖的执行工作太长，还是线程就绪未运行、正在等待依赖？ |
| GPU | 哪批 GPU 工作何时就绪，是否限制所需图像，而非仅看到一个长等待标记？ |
| I/O | 哪次读取延后所需字节就绪？字节之后的解压、对象创建和上传分别在哪里？ |
| 内存 | 容量／驻留压力、分配回收成本、访存延迟／带宽限制，当前证据支持哪一种？ |
| 同步 | 谁等谁，等待范围和期限是什么，是否推迟了目标？ |
| 热／功耗 | 工作量与其他条件是否可比，平台约束信号是否参与了执行能力变化？ |

详细条件沿[诊断方法的六类证据表]({{< relref "performance/game-performance-diagnosis-method.md" >}})回查；执行与等待看[线程调度]({{< relref "performance/game-performance-thread-scheduling-waits.md" >}})，内存看[内存记账]({{< relref "performance/game-performance-memory-accounting.md" >}})，加载看[资源可用链]({{< relref "performance/game-performance-read-does-not-mean-ready.md" >}})。

先写两个或几个仍有可能的解释，以及各自需要什么证据，数量按问题决定。不因首次发生就认定磁盘慢，不因长玩后变差就认定热降频。平台、引擎与构建条件从调查开始就进入记录，不应到最后才补；跨平台比较见[平台直觉]({{< relref "performance/game-performance-mobile-vs-pc-intuition.md" >}})。

### 4. 取证与对照：让解释有机会被否定

对每个准备验证的假设写出预期：原因成立时，哪项依赖或工作应改变，目标应怎样改变；什么结果会削弱这个解释，什么情况下仍无法判断。

按需设计 A 基线、B 单项改动与恢复复测，记录重复顺序、有效与缺失样本、异常及自动联动设置。恢复代码不保证缓存或热状态复原；条件不可比时重新建立基线，不能只挑最好的样本。

内部阶段缩短但目标不变，可能是呈现被限速、另一条依赖接管了关键路径，或假设没有解释原问题。回到时间线检查，不能直接增加更多改动。数据不足就保留未知，选择下一份最能区分候选解释的证据。

### 5. 选择改动：同时接受收益和代价

有针对性的改动可以是减工作量、前置准备、异步或分帧、调整资源组织、平滑生命周期、质量分档与平台回退。它们是候选方案，必须说明所针对的依赖和代价。

例如，预热可能增加进入阶段等待与驻留；分帧可能延长就绪；推迟任务消费可能改变反馈；减特效可能改变技能辨识。用[帧预算拆账]({{< relref "performance/game-budget-06-frame-budget-breakdown.md" >}})记录重叠与分项，别把同一段加载成本重复加账。

先做足以检验解释、且能恢复的改动。若新方案改变了玩法或表现要求，返回目标步骤，由相应负责人接受新取舍，再建立对照；它不能沿用旧目标直接宣布成功。

### 6. 复测与接受：回到原来的受阻任务

同时检查原目标、相关内部阶段及功能／画面、加载、内存和持续条件。统计对象、采样窗口、样本数、均值与分位数算法保持可比，缺失数据不填零。局部场景或单台设备的结论按实际覆盖范围表述。

结果反复不一致时检查条件漂移；功能或画面退化时修正或撤销改动；目标没有改善时返回假设和依赖调查。修复一种原因后出现新的限制，也需要重新取证。

验收通过后才判断哪些条件值得进入资源规范、预算、回归场景或自动检查。方法设计、单次有效对照、检查接入和团队持续采用分别记录，不能互相替代。持续运行的信号与取舍复用[功耗与发热]({{< relref "performance/mobile-hardware-03-power-thermal.md" >}})。

## 决策交接表：每一步留下什么，谁接着处理

下表为建议分工，表示责任而非固定组织编制；小团队可以一人承担多项职责。技术负责人协调目标、优先级和跨项代价，内容意图与体验接受仍需对应负责人参与。

| 决策点 | 留下的材料 | 交接与接受条件 | 不满足时返回哪里 |
| --- | --- | --- | --- |
| 问题与目标 | 使用者原话、操作路线、版本设备、指标边界与接受要求 | 程序／QA 与问题提出者确认任务；策划、产品或表现负责人确认语义底线 | 目标和条件定义 |
| 观察与假设 | 正常／异常样本、事件关联、候选解释、缺失证据 | 程序／TA 按实际阶段认领调查；QA 核对复现和采集条件 | 采样或指标口径 |
| 对照决定 | 单项改动、预期与反证、恢复办法、重复安排 | 实施者与复测者能够按记录重做；联动变量已说明 | 假设与实验设计 |
| 方案取舍 | 依赖影响、加载／驻留／画面／交互代价及替代方案 | 程序说明实现限制；策划、TA／美术接受对应表现取舍，负责人协调范围 | 产品目标或方案 |
| 结果接受 | 同条件复测、失败与反例、功能／画面检查、覆盖限制 | QA 核对结果，内容负责人接受体验；技术负责人记录通过、待补或退回 | 条件、假设或改动 |
| 后续复用 | 适用场景、执行入口、维护者、触发与失效条件 | 使用者知道何时执行、失败交给谁；有执行和修正记录才报告已采用 | 调整规则、补说明或退出过时规则 |

通知已发、代码已提交、包能启动，都不是这张表最后一行的完成证据。交接材料要让接收者能继续处理；不必为每个小问题搭一套新平台。

## 让一份报告能回到原始记录

交接责任明确以后，还要让记录沿途保持含义。只交一张“本次通过”的截图，接手者仍然不知道任务是否完成、哪些指标有效、应用了哪版规则。持续监测首先需要这条可以回查的数据流；一份配置、原始文件和报告索引就能起步，不必先建设数据库或调度平台。

```text
任务/指标规格 + 候选/实际配置 → 执行与领域采集 → 原始记录/缺失状态
                                                     ↓
规则/基线及分析版本 ────────────────→ 有效性/可比性核对 → 报告与处理
                                                     ↑       ↓
                                                   新记录 ← 复验
```

下面是职责设计建议，不是一套已经运行的系统。每一环要交出足够让下一环复核的材料；几项职责可以由同一个程序或同一个人承担。

| 环节 | 交出的材料 | 守住的边界 |
| --- | --- | --- |
| 任务与配置 | 任务/协议、指标定义、候选构建/内容、计划设备与画质、规则适用范围 | 启动后另记实际生效配置；计划为高档不证明实际使用高档 |
| 执行与领域适配 | 运行/请求/对象身份、开始/阶段/退出事件、正常/取消/超时结果 | 特效成员和退出协议归特效适配；UI 的用途就绪条件另定，不能共用一个未经定义的 Ready |
| 采集 | 原值、单位、来源/版本、采时或查询区间、事件/帧关联、可用性依据 | 未启用、不支持、未取得及原值为零分开；全局值与任务关联不等于对象独占 |
| 记录保存 | 上述原始记录、配置快照、失败/缺失原因及稳定引用 | 汇总前先保存；复跑另立运行身份并关联原记录，不覆盖失败记录 |
| 分析与报告 | 覆盖范围、逐项有效性、可比性、聚合方法/版本及规则判定 | 执行结束、数据可用、规则满足分别报告；基线不适用时不生成回退百分比 |
| 处理与复验 | 问题与责任、原报告引用、拟改动、复验任务和新结果 | 执行异常交检查维护者，已确认超线交对应程序/内容负责人；接收通知不等于修正通过 |

共同部分是身份、记录引用、有效性、规则及复验关系；领域适配负责把业务操作和领域指标接进来。复用这条数据流，不表示角色、动画、场景、UI 和特效具有相同生命周期，也不要求把所有原始数据压成同一张表。对象/事件怎样定义，沿[任务观测模型]({{< relref "performance/client-performance-task-observation-model.md" >}})；规则与配置怎样绑定，沿[预算总表]({{< relref "performance/game-budget-16-budget-master-sheet-template.md" >}})。

采集设置也属于证据。Unity 6.0 的[采集说明](https://docs.unity.com/en-us/engine/6000.0/manual/analysis/profiler/profiling-applications/profiling-collect-data-introduction)明确只为已启用的 Profiler 模块采集数据；这支持检查开关，不能反过来把所有缺失都解释为未启用。需要按精确来源区分支持、配置、执行和记录完整性，更不能用一条进程退出成功的结果替代这些检查。

### 三次任务结束后，为什么不能只数绿色项

以下**全部是虚构教学输入**。教学规则 T0 为每次奖励任务要求两项有效记录：请求至应用就绪代理不超过 25 ms，约定范围的 GPU 时间不超过 10 ms。两条线只为推演设置，不是项目预算或建议阈值；代理也不等于屏幕反馈。每行是独立状态输入，分别给定其来源/环境依据和 T0 适用性，不构成同条件设备快慢对照，不对应一次 API 实测。

| 任务记录 | 执行结果 | 代理记录 | GPU 记录 | T0 下应怎样交接 |
| --- | --- | --- | --- | --- |
| J-A | 正常退出 | 24 ms，有效 | 本来源在该环境不支持，依据已给定 | 代理满足此教学线；必需 GPU 项不支持，整体接受条件未满足，不能填 0 通过 |
| J-B | 正常退出 | 28 ms，有效 | 8 ms，有效 | 保留代理超线与 GPU 满足两项事实；按代理范围定位，不扩大成实际屏幕反馈结论 |
| J-C | 执行超时 | 缺终点，时长未知 | 未取得，原因待查 | 执行异常与指标缺失分别保留；复核超时/采集/退出，不把未取得直接改成不支持 |

计划执行是 3 次，正常退出是 2 次，超时是 1 次。按 T0 每次两项计，共有 `3×2=6` 个必需指标位置；有效数值是 3 个，不支持是 1 个，缺失/未取得是 2 个，`3+1+2=6`。三个有效值中有两个满足教学线、一个超线；只显示“2/3 满足”会遮住另外三个必需位置，也不能作为三次任务的通过率。`3/6=50%` 只描述本题必需位置的有效数值覆盖，不代表测量准确度或真实项目健康程度。

报告应能从每项结论回到 J-A/J-B/J-C、实际配置、原始值/状态及 T0，接手者才能区分“查环境支持”“查采集完整性”和“查代理超线”。若 GPU 后来被决定为可选项，先记录理由、责任人与新任务/规则版本，再形成新判定；不覆盖 T0、原记录和原报告，也不把例外写成性能成本为零。规则变化后哪些数据可重算、哪些必须复测，要看原始覆盖与可比条件，不能只换一条预算线就宣布修复。

理解检查：如果 J-A 的 GPU 项后来改为可选，哪些旧事实仍应保留？J-C 后来业务成功但代理终点始终缺失，哪些字段可以补、哪些仍未知？这份纸面记录用于检验交接与报告设计，尚无实际采集、工具运行或团队采用证据。

## 规则或基线变了，旧记录还能回答什么

一份报告变绿，可能只是判定条件变了。沿上节的记录链，先问：现在要评价的候选、任务和指标是什么，旧记录是否覆盖这个问题？[预算体系]({{< relref "delivery-engineering/delivery-performance-stability-02-budget-system.md" >}})已把规则依据、检查事实和接受决定分开；[质量门]({{< relref "delivery-engineering/delivery-cicd-pipeline-04-quality-gates.md" >}})规定基线更新要有可比性依据、理由和接受责任。本节把它们落实为重算与补证的判断方法，不另设一套放行规则。

这里有三个不同层次：**可重算**表示已有记录足以按新定义形成派生结果；**证据不足**表示当前材料不能支持所问结论；**需复测**表示要取得新的运行证据。它们不互斥：旧候选可重算，新候选仍可能证据不足并需复测。能算出数值，也不等于已有可比基线或已获接受。

```text
新问题/候选 + 新规则/基线
           ↓
核对原始覆盖、指标定义与实际条件
  ├─ 足够 → 按声明的分析版本重算 → 另存派生报告 → 核可比性与接受范围
  └─ 不足 → 保留已有事实及未知 → 查找缺失原件/说明 → 必要时设计新运行
                                                     ↓
                                        新运行另立身份，关联旧报告
```

重算前至少能追到原候选/内容、实际配置、对象/事件、原始值及有效性、采集与分析版本；若涉及比较，还需两边的样本、窗口和条件可比依据。旧报告仍保留当时的规则、基线与判定，新报告说明改变了什么、由谁接受和仍缺什么。原始数据不完整时，不因格式能够导入就补零、插值或静默删除异常。

### 五种变更，分别查哪一份证据

下表及后面的数字**全部为教学假设**，没有运行设备、采集器或回归工具。每行独立给定变更条件；沿用 J-B 的地方只复用上节已给定的有效记录，不把不同任务混成一组对照。T1 也只是题设规则，不是建议阈值。

| 本次改变 | 已有证据与可做的处理 | 仍不能宣称什么／下一步 |
| --- | --- | --- |
| 只把代理上限从 T0 的 25 ms 改为 T1 的 30 ms；GPU 要求和其他条件不变 | 题设接受人已给出理由、范围并确认 T1 适用于 J-B 原候选；J-B 的 28 ms 与 8 ms 可按 T1 另出判定，原 T0 代理超线保留 | 28 ms 没有变快，未证明修复；只能说 J-B 在 T1 的这两项满足，不能推广到未覆盖的候选或必需项 |
| 由均值改为指定算法的 P95 | 若对象、窗口、有效性和所需原始样本齐全，可重新聚合；若只存均值，不能唯一恢复 P95 | 缺样本时先查原件，找不到则为新要求设计采集；不能把旧均值改名为 P95 |
| 由应用就绪代理改为屏幕可见反馈 | 旧记录没有屏幕终点或对应时钟/事件关联，对新指标证据不足；原代理事实仍可保留 | 不能在代理上加一个常数冒充屏幕结果；先定义终点和关联/校准方案，再补所需观测 |
| 要评价新的构建、画质或并发，而旧记录只覆盖旧条件 | 旧值只能回答其覆盖的问题；对新条件需另立运行并记录实际生效配置及必要体验 | 重算不会生成新条件下的运行成本；旧结果不能填入新候选的必需证据位置 |
| 规则不变，只把 B0 基线换成 B1 | 两边定义、聚合和条件有可比依据时才重算差值；缺依据先保留“不可比/待补”，必要时重建对照 | 选了较慢基线不证明候选改善；不自动采用“最近一次成功”，也不因重算成功就批准更新 |

### 复算：改变算法或分母，报告为什么会变

为第二行另给合成记录 K：同一指标/单位/窗口约定下，四次任务各有一个有效代理时长，依次为 `18、22、28、32 ms`，原件及条件完整。均值为 `(18+22+28+32)/4=25 ms`。若新规格采用 nearest-rank：升序后取第 `ceil(0.95×4)=4` 个值，不插值，则该组 P95 为 `32 ms`。四次仅用于检验算法，不能证明尾部分布已估准、重复次数足够或真实设备达标；分位数与事件的使用边界沿[一帧拆解]({{< relref "performance/game-performance-frame-breakdown.md" >}})。

反过来，只知道均值为 25 ms，就无法判断原组是上述 K，还是 `25、25、25、25 ms`；后者按同算法 P95 为 25 ms。两组的均值相同，尾部不同。缺少原始覆盖时，要求重算并不能补回信息。

再为第五行独立给定一组**定义、统计方式及条件已对齐的教学汇总**：B0 为 20 ms，候选为 24 ms，拟用 B1 也为 24 ms。相对 B0 是 `24−20=4 ms`、`4/20=20%`；换成 B1 后是 `24−24=0 ms`、`0/24=0%`。候选始终为 24 ms，变化来自比较分母与参照值。这不证明真实退化的原因或显著性，也不构成抬高基线的理由；缺可比依据时，这两个百分比都不应出现在正式结论中。

### 把新判定交回处理链

检查维护者说明是规则、分析、记录完整性还是运行条件变化，关联原报告与新派生报告；QA/复测者补齐所需条件与覆盖，程序/内容负责人接收仍成立的超线。指定接受人审阅基线或规则更新理由、影响范围和回退依据。临时例外仍须有批准者、补验责任和到期条件，沿质量门处理，不改写成“测量通过”。

新运行保留正常、超时、缺失和异常结果；修复后用新记录回应原问题，不覆盖旧失败，也不无限重跑挑一次绿色。若只是规则获准放宽，应写“接受条件已变更”，而非“性能已修复”。这些是处理设计，尚无真实告警闭环或团队采用证据。

理解检查：只剩 K 的均值和样本数，能否补出 P95，为什么？J-B 按 T1 满足后，能否关闭“代理已变快”的问题？B1 缺少实际画质记录时，该保留哪些事实、暂停哪种比较、由谁补什么证据？作者反馈待记录，不以本题答案或纸面重算代替实测。

## 告警有人接了，何时才能说恢复

重算和复测的去向明确后，还要区分四件事：报告记录了什么、通知怎样送达、谁正在处理、当前允许接受什么。收到消息只证明送达；有人接单只证明有人承担下一步。临时接受风险、暂停重复通知和完成修复各有条件，不能共用一个“已解决”状态。

例如，Prometheus 的 [Alertmanager 概念文档](https://prometheus.io/docs/alerting/latest/alertmanager/)说明，分组把同类告警组织为一条通知，静默按匹配条件在给定时间内停止发送对应通知。这是通知处理能力的例子，不能据此推出检查通过或例外已经批准。本节只借用这个区别，不预设选用该系统、它的部署版本或已经接入运行。

```text
原始报告/规则事实 → 问题与责任记录 → 处理/补验 → 接受人核对 → 按覆盖范围记录恢复
       │                 │              │
       └→ 通知分组/重投   └→ 接单/升级    └→ 临时例外及到期重判
          保留原引用        不改检查事实       不覆盖旧失败或新候选
```

重复送达可以合并通知，但仍须看到原报告身份、受影响候选/配置/规则、发生次数与最新证据时间。新的运行、候选或指标异常要追加事实，不能因为标题相同就吞掉。指定处理人还需知道下一步、复查时间与无人响应时交给谁；时限由影响和处理条件约定，本篇不提供通用分钟数。

### 一条带到期条件的教学时间线

以下**全部是独立的虚构教学输入**，不沿用前节 T1。`t` 是从本题起点算起的分钟，仅方便复算，不是响应 SLA。规则 P0、候选 C-A/C-B、问题 P 和报告 R0/R1/R2 均为本题标识；P0 不是告警级别。报告的指标/来源/适用性在题设中给定，不对应引擎采集或实际通知。

| t（分钟） | 新事件与已知事实 | 此时怎样处理 |
| --- | --- | --- |
| 0 | C-A 的 R0 执行完成、证据有效；按适用的 P0 已确认一项超线 | 建问题 P，引用原件、规则及实际配置，交对应程序/内容负责人；保留超线 |
| 2 | 同一 R0 被重投，报告身份和内容未变 | 在 P 下记重复送达，可合并通知；没有增加一次独立跑测或第二份失败证据 |
| 4 | 处理人接单，给出调查与复查安排 | 状态为处理中；不是修复或接受通过，无人接单则按事先约定升级 |
| 6 | 题设有权限的接受人批准例外 X，写明理由/风险、措施、补验责任；仅适用 C-A/P0/指定范围，有效区间为 `6≤t<16` | 临时接受只限 X 覆盖的风险；原事实不变，通知静默须另有受控记录，不能互相代替 |
| 12 | 拟修正候选 C-B 的 R1 超时，必需终点未取得 | 保留执行异常和证据不足，交检查维护者查原因；X 即使尚未到期，也不覆盖 C-B，不能继承旧候选的接受决定 |
| 16 | 没有足以关闭 P 的新证据，X 到达期限 | 停止援引 X，按原必需项和接受策略重判；指定负责人核对到期处理，不默默续期或把没有新报告当恢复 |
| 18 | C-B 的补验报告 R2 有效；题设给定条件/规则适用、完整复验集合与必要功能/画质及相关代价均满足原约定，R1 原因/处置和受影响分支补验也已留证 | 把完整材料交接受人审阅，关联 R0/R1；单个指标变绿或一次正常退出不能替代这些题设条件 |
| 20 | 接受人核对上述证据，批准在题设覆盖范围内关闭 P | 记录恢复范围、接受依据与后续触发；保留 R0 超线、R1 超时、X 及原决定，不推为所有设备或监测链长期可靠 |

X 的题设时长为 `16−6=10` 分钟；在 `t=12` 时虽处于这个时间区间，C-B 仍不匹配 X 的候选范围；`t=16` 则已经不在有效区间。这里只演算授权范围，没有证明任何工具会自动失效。质量门已有[豁免与维护责任]({{< relref "delivery-engineering/delivery-cicd-pipeline-04-quality-gates.md" >}})：实际到期检查、策略生效和通知恢复需要实现及验证，暂未自动化时也须安排明确的人工核对。

本题发生四次报告送达（R0 两次、R1/R2 各一次），只有三份报告身份；接单、批准例外和关闭问题均不是额外测量样本。这样既能减少重复通知，又不删除历史或伪造重复次数。若只有 R2 的某个数值满足，而缺少完整复验集合、正确性或相关代价证据，就应停在待补/待接受，不能直接走到 `t=20` 的结论。

### 恢复通知仍需回到证据

通知不再出现，可能是静默、路由变化、规则停用、上报中断或确实不再触发；需要查相应记录才能区分。保留最新有效结果的时间和本轮应有的覆盖，采集空窗记为未知或过期，不自动沿用上次绿色。这里的恢复指原受阻任务在约定条件下得到复验和接受，不能只按“告警消失”判断。

关闭后还应写明何时重新打开：候选/规则/配置越出已验范围、新有效结果再次超线，或既有证据失效时，回到对应核对和处理步骤。回滚或降低配置也需要核对实际生效条件、必要表现与相关代价；仅提交修复、撤销静默或恢复旧设置，都不足以宣称任务恢复。这些是治理设计，没有实际告警发送、故障注入、放行或团队采用记录。

理解检查：R0 重投为什么不增加独立失败样本？X 在 t=12 和 t=16 分别因什么不能使用？若 t=18 只有代理指标满足、功能检查缺失，谁还需补什么，能否记录 t=20 的恢复？作者反馈待记录，不以本题推演代替真实响应和复验。

## 教学推演：首次技能反馈迟到，怎样回退与选择

以下是假设的调查过程，用来演示方法，没有测量数字、真实 trace 或项目改善结果。

### 从反馈到候选原因

QA 描述“技能第一次按下去顿一下”。程序先问清楚：是角色动作迟到、特效出现晚，还是整个画面停住？策划要求命中语义和动作反馈保持，TA／美术确认特效中需要保留的辨识元素。记录目标设备、构建、路线和首次条件，先把输入事件至动作反馈、特效用途就绪、应用间隔分开。

此时保留两个候选解释：H1 为资源用途尚未就绪；H2 为资源已就绪，但对象激活或其他必需工作迟到。第一次慢、第二次好是观察，不负责替 H1 或 H2 定案。

### 一次无法定案的采样

假设首轮材料只有“读取完成”日志与主线程长条，无法把请求、实例和反馈对应起来。这里应返回采样步骤，补请求身份、阶段就绪与调用区间，不能把整根长条都算成磁盘耗时。若没有屏幕观测，结论也不能覆盖实际输入到可见反馈延迟。

后续若材料显示目标实例所需数据已就绪，而对象激活在反馈依赖上迟到，就提高 H2 的调查优先级；H1 的“读取迟到”解释被削弱。仍要检查激活区间内是执行、调度还是等待，不能仅凭阶段名称认领根因。

### 选择一个可恢复的改动

候选方案 A 是在可控制的进入阶段准备并持有实例；候选方案 B 是拆分激活工作。先核对引擎接口和依赖是否允许，再比较新增驻留、进入时间、首次反馈与维护复杂度。不能为了平滑特效把影响命中语义的工作随意推迟。

若选择 A 做对照，只改变这一项准备策略，保存原配置与恢复办法；用同一路线比较进入阶段、首次技能、后续使用及退出。准备提前了，但资源增加多少、退出是否释放、持续运行是否受影响，都仍是待测项。

### 结果怎样改变下一步

| 拟观察的结果 | 可以怎样继续 | 不能怎样收尾 |
| --- | --- | --- |
| 激活区间缩短，但原目标不变 | 回查新的限制、帧关联和呈现；必要时补下一份证据 | 仅凭主线程条缩短宣布问题解决 |
| 首次反馈改善，但进入等待或驻留不满足要求 | 回到方案取舍，限制准备范围、尝试 B，或撤销改动后重做 | 把代价隐藏在另一个阶段 |
| 结果随轮次漂移或恢复后无法重现 | 检查缓存、初始状态、自动策略与采集开销，重建可比条件 | 挑最好一轮当稳定收益 |
| 目标和正确性均满足已约定条件 | 按覆盖范围形成结论，再讨论对应内容规范和回归路线 | 推成所有技能、设备均有效或团队已有持续门禁 |

这个推演的交付物是一条可复查的决定链：反馈如何限定目标，证据怎样改变假设，方案为何被接受或退回。真实案例需要填入同一次事件的版本、原始样本、改动与复验材料后才能成立。

## 让方法回到团队日常使用

一次调查可能只需要一份短记录。有效做法进入共同工作时，还需明确入口、触发、维护人、失败处理和适用范围：哪些属于资源制作规范，哪些需要场景组合验证，哪些只能在设备上判断。

这与[游戏研发 FDE]({{< relref "delivery-engineering/fde-methods-series-index.md" >}})的连接在于：从使用者受阻的任务进入，用技术机制选择方案，再回到原任务验证是否可用。真实实践可从[客户端生产体系]({{< relref "engineering-journey/production-pipeline-overview.md" >}})阅读；其中[持续性能 05]({{< relref "engineering-journey/production-continuous-performance.md" >}})仍为提纲，后续需用完整优化对照充实。

方法是否值得保留，要看它是否帮助团队继续处理问题。出现误报、条件过期或维护成本过高时，规则也应调整或退出。留下清楚的依据、取舍和回退路径，比给每个问题都贴上一个最终标签更有用。
