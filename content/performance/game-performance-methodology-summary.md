> 性能判断要能回答：当前知道什么，凭什么做这个改动，结果不符合预期时回到哪里继续查。把这些问题和交接责任连起来，方法才有机会被团队重复使用。

本篇收束前面的基础与诊断文章，解释如何从一个使用障碍走到可复查的决定。它提供工程建议和教学推演，不代表某个项目已运行这套流程，也没有设备 trace 或优化收益实测。具体计时、平台和工具契约继续由相应基础篇维护。

## 从一个具体任务开始

“某个技能第一次放的时候顿一下”，仍然不足以决定采用对象池、预加载还是降低特效。首先要知道：谁在什么构建、设备和操作中遇到了什么障碍，这次需要改善的是哪一个结果。

例如，同一句“技能卡”可能指输入到动作反馈晚、首个特效出现晚、应用长间隔，或画面更新不均匀。这些对象可以相互影响，却需要不同的起止点和证据。先与提出问题的人确认具体受阻任务，再选择测量入口。

前面的[一帧链路]({{< relref "performance/game-performance-frame-breakdown.md" >}})区分逻辑、渲染、呈现与输入反馈，[诊断方法]({{< relref "performance/game-performance-diagnosis-method.md" >}})区分现象、假设、证据与结论。本篇在它们之上组织决定与交接，不再建立第二套指标定义。

## 一条可以回退的工作流

可以把一次调查组织为：

**定义目标与条件 → 保存观察 → 提出候选解释 → 取证与对照 → 选择改动 → 复测与接受 → 沉淀及跟进。**

箭头表示信息如何交接，不是必须一次走完的审批流水线。可以先做小范围探索；新证据否定解释、测试条件变化或结果缺失时，要返回对应步骤，保留原假设和失败记录。

### 1. 定义目标与条件：先约定改善什么

固定程序与内容身份、设备／OS／图形 API、质量与渲染尺寸、目标帧率与刷新率、操作路线、缓存及热／供电状态。首次使用、重复使用、稳定战斗和持续运行分别划定窗口。

同时写清正确性和体验要求：什么反馈不能推迟，哪些视觉元素必须保留，允许增加多少加载等待或资源驻留。接受条件应由项目目标与实际设备条件确定，本篇不提供通用数值门槛。

若连“动作先响应但特效稍后到达能否接受”都未约定，就先回到产品与表现要求；代码局部变快不能替代这个决定。

### 2. 保存观察：把原话与测量分开

使用者反馈、复现操作、直接观察、工具数据分别记录。保留正常与异常样本、采集方式、缺失字段和未覆盖窗口。复现不稳定时先收集触发条件，不把偶然相关认作原因。

诊断采集可能改变运行开销。Unity 2022.3 的[应用采集说明](https://docs.unity3d.com/2022.3/Documentation/Manual/profiler-profiling-applications.html)规定连接 Player 的 Unity Profiler 使用 Development Build；因此采集配置和目标交付配置要分别报告。详细采样帮助定位，最终收益仍需按实际交付条件用适用方式复验。

若没有能关联到本次任务的证据，下一步产物是采集设计，不是瓶颈结论。计时对象不一致或时钟未对齐时，返回指标定义和采样步骤。

### 3. 提出候选解释：沿依赖寻找限制

把这次任务的输入、资源就绪、对象与生命周期、提交、GPU 工作及所需反馈对应起来。它们不是每次都顺序执行：任务可以提前准备、命中缓存或与其他工作重叠，Present 请求也不等于画面已经显示。

六类名称用于选择证据，不是六个互斥时间桶：

| 调查入口 | 本次真正要追问什么 |
| --- | --- |
| CPU | 目标依赖的执行工作太长，还是线程就绪未运行、正在等待依赖？ |
| GPU | 哪批 GPU 工作何时就绪，是否限制所需图像，而非仅看到一个长等待标记？ |
| I/O | 哪次读取延后所需字节就绪？字节之后的解压、对象创建和上传分别在哪里？ |
| 内存 | 容量／驻留压力、分配回收成本、访存延迟／带宽限制，当前证据支持哪一种？ |
| 同步 | 谁等谁，等待范围和期限是什么，是否推迟了目标？ |
| 热／功耗 | 工作量与其他条件是否可比，平台约束信号是否参与了执行能力变化？ |

详细条件沿[诊断方法的六类证据表]({{< relref "performance/game-performance-diagnosis-method.md" >}})回查；执行与等待看[线程调度]({{< relref "performance/game-performance-thread-scheduling-waits.md" >}})，内存看[内存记账]({{< relref "performance/game-performance-memory-accounting.md" >}})，加载看[资源可用链]({{< relref "performance/game-performance-read-does-not-mean-ready.md" >}})。

先写两个或几个仍有可能的解释，以及各自需要什么证据，数量按问题决定。不因首次发生就认定磁盘慢，不因长玩后变差就认定热降频。平台、引擎与构建条件从调查开始就进入记录，不应到最后才补；跨平台比较见[平台直觉]({{< relref "performance/game-performance-mobile-vs-pc-intuition.md" >}})。

### 4. 取证与对照：让解释有机会被否定

对每个准备验证的假设写出预期：原因成立时，哪项依赖或工作应改变，目标应怎样改变；什么结果会削弱这个解释，什么情况下仍无法判断。

按需设计 A 基线、B 单项改动与恢复复测，记录重复顺序、有效与缺失样本、异常及自动联动设置。恢复代码不保证缓存或热状态复原；条件不可比时重新建立基线，不能只挑最好的样本。

内部阶段缩短但目标不变，可能是呈现被限速、另一条依赖接管了关键路径，或假设没有解释原问题。回到时间线检查，不能直接增加更多改动。数据不足就保留未知，选择下一份最能区分候选解释的证据。

### 5. 选择改动：同时接受收益和代价

有针对性的改动可以是减工作量、前置准备、异步或分帧、调整资源组织、平滑生命周期、质量分档与平台回退。它们是候选方案，必须说明所针对的依赖和代价。

例如，预热可能增加进入阶段等待与驻留；分帧可能延长就绪；推迟任务消费可能改变反馈；减特效可能改变技能辨识。用[帧预算拆账]({{< relref "performance/game-budget-06-frame-budget-breakdown.md" >}})记录重叠与分项，别把同一段加载成本重复加账。

先做足以检验解释、且能恢复的改动。若新方案改变了玩法或表现要求，返回目标步骤，由相应负责人接受新取舍，再建立对照；它不能沿用旧目标直接宣布成功。

### 6. 复测与接受：回到原来的受阻任务

同时检查原目标、相关内部阶段及功能／画面、加载、内存和持续条件。统计对象、采样窗口、样本数、均值与分位数算法保持可比，缺失数据不填零。局部场景或单台设备的结论按实际覆盖范围表述。

结果反复不一致时检查条件漂移；功能或画面退化时修正或撤销改动；目标没有改善时返回假设和依赖调查。修复一种原因后出现新的限制，也需要重新取证。

验收通过后才判断哪些条件值得进入资源规范、预算、回归场景或自动检查。方法设计、单次有效对照、检查接入和团队持续采用分别记录，不能互相替代。持续运行的信号与取舍复用[功耗与发热]({{< relref "performance/mobile-hardware-03-power-thermal.md" >}})。

## 决策交接表：每一步留下什么，谁接着处理

下表为建议分工，表示责任而非固定组织编制；小团队可以一人承担多项职责。技术负责人协调目标、优先级和跨项代价，内容意图与体验接受仍需对应负责人参与。

| 决策点 | 留下的材料 | 交接与接受条件 | 不满足时返回哪里 |
| --- | --- | --- | --- |
| 问题与目标 | 使用者原话、操作路线、版本设备、指标边界与接受要求 | 程序／QA 与问题提出者确认任务；策划、产品或表现负责人确认语义底线 | 目标和条件定义 |
| 观察与假设 | 正常／异常样本、事件关联、候选解释、缺失证据 | 程序／TA 按实际阶段认领调查；QA 核对复现和采集条件 | 采样或指标口径 |
| 对照决定 | 单项改动、预期与反证、恢复办法、重复安排 | 实施者与复测者能够按记录重做；联动变量已说明 | 假设与实验设计 |
| 方案取舍 | 依赖影响、加载／驻留／画面／交互代价及替代方案 | 程序说明实现限制；策划、TA／美术接受对应表现取舍，负责人协调范围 | 产品目标或方案 |
| 结果接受 | 同条件复测、失败与反例、功能／画面检查、覆盖限制 | QA 核对结果，内容负责人接受体验；技术负责人记录通过、待补或退回 | 条件、假设或改动 |
| 后续复用 | 适用场景、执行入口、维护者、触发与失效条件 | 使用者知道何时执行、失败交给谁；有执行和修正记录才报告已采用 | 调整规则、补说明或退出过时规则 |

通知已发、代码已提交、包能启动，都不是这张表最后一行的完成证据。交接材料要让接收者能继续处理；不必为每个小问题搭一套新平台。

## 教学推演：首次技能反馈迟到，怎样回退与选择

以下是假设的调查过程，用来演示方法，没有测量数字、真实 trace 或项目改善结果。

### 从反馈到候选原因

QA 描述“技能第一次按下去顿一下”。程序先问清楚：是角色动作迟到、特效出现晚，还是整个画面停住？策划要求命中语义和动作反馈保持，TA／美术确认特效中需要保留的辨识元素。记录目标设备、构建、路线和首次条件，先把输入事件至动作反馈、特效用途就绪、应用间隔分开。

此时保留两个候选解释：H1 为资源用途尚未就绪；H2 为资源已就绪，但对象激活或其他必需工作迟到。第一次慢、第二次好是观察，不负责替 H1 或 H2 定案。

### 一次无法定案的采样

假设首轮材料只有“读取完成”日志与主线程长条，无法把请求、实例和反馈对应起来。这里应返回采样步骤，补请求身份、阶段就绪与调用区间，不能把整根长条都算成磁盘耗时。若没有屏幕观测，结论也不能覆盖实际输入到可见反馈延迟。

后续若材料显示目标实例所需数据已就绪，而对象激活在反馈依赖上迟到，就提高 H2 的调查优先级；H1 的“读取迟到”解释被削弱。仍要检查激活区间内是执行、调度还是等待，不能仅凭阶段名称认领根因。

### 选择一个可恢复的改动

候选方案 A 是在可控制的进入阶段准备并持有实例；候选方案 B 是拆分激活工作。先核对引擎接口和依赖是否允许，再比较新增驻留、进入时间、首次反馈与维护复杂度。不能为了平滑特效把影响命中语义的工作随意推迟。

若选择 A 做对照，只改变这一项准备策略，保存原配置与恢复办法；用同一路线比较进入阶段、首次技能、后续使用及退出。准备提前了，但资源增加多少、退出是否释放、持续运行是否受影响，都仍是待测项。

### 结果怎样改变下一步

| 拟观察的结果 | 可以怎样继续 | 不能怎样收尾 |
| --- | --- | --- |
| 激活区间缩短，但原目标不变 | 回查新的限制、帧关联和呈现；必要时补下一份证据 | 仅凭主线程条缩短宣布问题解决 |
| 首次反馈改善，但进入等待或驻留不满足要求 | 回到方案取舍，限制准备范围、尝试 B，或撤销改动后重做 | 把代价隐藏在另一个阶段 |
| 结果随轮次漂移或恢复后无法重现 | 检查缓存、初始状态、自动策略与采集开销，重建可比条件 | 挑最好一轮当稳定收益 |
| 目标和正确性均满足已约定条件 | 按覆盖范围形成结论，再讨论对应内容规范和回归路线 | 推成所有技能、设备均有效或团队已有持续门禁 |

这个推演的交付物是一条可复查的决定链：反馈如何限定目标，证据怎样改变假设，方案为何被接受或退回。真实案例需要填入同一次事件的版本、原始样本、改动与复验材料后才能成立。

## 让方法回到团队日常使用

一次调查可能只需要一份短记录。有效做法进入共同工作时，还需明确入口、触发、维护人、失败处理和适用范围：哪些属于资源制作规范，哪些需要场景组合验证，哪些只能在设备上判断。

这与[游戏研发 FDE]({{< relref "delivery-engineering/fde-methods-series-index.md" >}})的连接在于：从使用者受阻的任务进入，用技术机制选择方案，再回到原任务验证是否可用。真实实践可从[客户端生产体系]({{< relref "engineering-journey/production-pipeline-overview.md" >}})阅读；其中[持续性能 05]({{< relref "engineering-journey/production-continuous-performance.md" >}})仍为提纲，后续需用完整优化对照充实。

方法是否值得保留，要看它是否帮助团队继续处理问题。出现误报、条件过期或维护成本过高时，规则也应调整或退出。留下清楚的依据、取舍和回退路径，比给每个问题都贴上一个最终标签更有用。
