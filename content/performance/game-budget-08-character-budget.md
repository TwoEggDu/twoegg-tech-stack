角色预算最容易被误写成一张表：

- 主角 3 万面
- NPC 1 万面
- 骨骼不超过多少

这当然比完全没有好。  
但它仍然不够。

因为角色从来不是只有面数这一笔账。  
它同时会吃：

- GPU 几何和材质账
- 动画求值与蒙皮计算账（执行位置和统计范围按引擎版本、平台与配置核对）
- 内存常驻账
- 包体和贴图账
- 同屏组合与参与范围

所以角色预算真正值钱的地方，不是“给一个数字”，而是建立：

`单体规格、同屏组合、目标设备与实际配置、使用阶段`

这些共同约束维度。它们不是四个可直接相乘的数：档位和时机需要落实为具体条件，单体结果也不能乘人数后就承诺整个场景达标。

## 角色预算首先在管什么

一套真正能用的角色预算，至少要同时看下面这些对象：

- 面数
- 材质球数量
- 骨骼数量
- 蒙皮影响数
- 动画片段和状态机复杂度
- 主贴图、法线、遮罩和次级贴图
- 同屏数量

## 判断依据是什么

### 1. 角色通常是玩家最在意的内容对象

所以角色预算和场景预算不一样。  
很多场景细节可以降，角色主贴图、轮廓和关键识别信号通常更应该保。

### 2. 单个角色不重，不代表多角色同屏不重

角色预算需要同时说明实例规模和实际参与范围：

- 一个角色过线，不代表十个角色还能过线
- 同屏人数增加会改变负载，但资源共享、可见性、LOD、材质状态和绘制用途会改变增量，不能把每一项都按人数线性放大

应在目标镜头、实际配置和组合负载下分别观察相关工作及必要反馈。共享一份 Mesh 或材质，不代表多个角色的变换、蒙皮和绘制都只执行一次；反过来，多了一个实例也不证明所有资产都复制了一份。

### 3. 角色很多时候同时吃 CPU 和 GPU

例如：

- 骨骼更多，CPU 或 GPU 蒙皮更重
- 材质更多，提交和绘制更碎
- 贴图更高，显存和包体更贵

所以角色预算本质上是典型的多桶预算对象。

## 同屏人数相同，为什么资源账仍会改变

角色美术的[近景优先级与换装取舍]({{< relref "performance/game-performance-character-art-budget-priority.md" >}})已经说明应保护哪些识别信息；[内存记账]({{< relref "performance/game-performance-memory-accounting.md" >}})则区分分配、持有和系统占用。这里把它们接到同一个角色组合：先看实际引用了哪些资源，再看保留了哪些实例。

```text
角色实例 I1…I4 ──引用──→ 共享基础资源 K
       └────────引用──→ 当前外观 A 或 B
实例自己的分配另列；换装交接/缓存仍持有的旧外观也另列
```

### 四个教学快照：人数与外观种类分别记录

以下是**虚构的内存记账题，不是 Unity 采样、资源规格建议或预算阈值**。选定同一种内存口径，K、A、B 是按分配身份归并、互不重叠的三组分配，分别为 8、12、20 MiB；它们不是资源文件或 AssetBundle 的磁盘大小。每个保留实例另有 2 MiB 独占分配，不重复包含前三组；题设各实例没有材质副本或其他临时分配，回池后该分配仍完整保留。表中列出的分配在对应快照确实存在，其他背景成本排除在本表范围外。

| 快照与阶段 | 展示/保留实例及共享分配状态 | 同口径合计（MiB） |
| --- | --- | --- |
| C0：四个 A 角色创建完成 | 4 个展示实例；K、A 各一份 | `8 + 12 + 4×2 = 28` |
| C1：一人换成 B，其余三人仍是 A | 仍为 4 个展示实例；K、A、B 各一份 | `8 + 12 + 20 + 4×2 = 48` |
| C2：四人都已换成 B，缓存仍持有 A | 4 个展示实例；K、B 使用中，A 分配仍在 | `8 + 12 + 20 + 4×2 = 48` |
| C3：两人退出展示并回池，A 分配已确认退出 | 2 个展示、2 个池内实例；K、B 各一份，A 已不在此口径分配集合 | `8 + 20 + 4×2 = 36` |

若把一个 A 实例的 `8+12+2=22 MiB` 乘四，会得到 88 MiB，重复计算共享分配；C0 应为 28。C0→C1 人数不变，但外观种类增加，表内增量为 B 的 20 MiB；不能只检查“同屏四人”便沿用同一资源结论。C1→C2 已无人展示 A，分配却没有因此消失。C3 的四个实例仍被保留，不能只按两个展示者计算实例分配；减少的 12 MiB 来自题设已确认退出的 A，不是“少画两人就省出这些内存”。

这些是同口径、同一时刻的集合求和，**不是 CPU/GPU 时间公式，也不是进程内存总量**。48 只是四个已给快照中的最高值，不能证明换装中途没有旧新资源、临时准备或在途使用形成的更高峰值。若实际引擎、池或加载方式保留了别的分配，须加入记录，不能继续照抄本表。

### 回到 Unity：资源身份不能只看名字

Unity 6.0 的 [SkinnedMeshRenderer.sharedMesh](https://docs.unity.com/en-us/engine/6000.0/script-reference/unityengine/skinnedmeshrenderer/sharedmesh)给出该组件使用的蒙皮网格入口；[Renderer.sharedMaterials](https://docs.unity.com/en-us/engine/6000.0/script-reference/unityengine/renderer/sharedmaterials)说明多个对象可以使用同一个材质，返回的是材质数组副本，修改其中共享材质的内容会影响其他使用者。因此，读取到两份数组不证明其中的材质也复制了，资源名相同也不证明引用身份相同。这里说明的是引用与共享入口，没有核验角色的实际分配大小或共享路径。

还要防止调查本身改变状态。[Renderer.material](https://docs.unity.com/en-us/engine/6000.0/script-reference/unityengine/renderer/material)文档说明该属性会实例化材质；原材质被其他 Renderer 使用时，会克隆共享材质供当前 Renderer 使用，并有相应销毁责任。不能把遍历角色时读取该属性当作无副作用的身份查询，也不能据此假定所有角色从创建起就各有一份材质。实际副本若存在，应作为新身份和持有责任进入账本；具体加载、换装及释放策略另按项目契约确定。

### 给资源账留下哪些观测

| 对象与阶段 | 拟保存的记录 | 能支持与不能支持的判断 |
| --- | --- | --- |
| 创建及组合变化 | 构建/资源版本、角色/实例身份、外观组合、实际 Mesh/材质/纹理身份与共享者、对应分配口径 | 区分人数变化与外观多样性；引用关系不是字节数，未知大小不填零 |
| 换装交接 | 请求/数据代次、旧新外观的准备/交接、必要画面和挂点、持有者及实际分配退出；失败/缺失单列 | 发现旧新重叠和迟到结果；资源回调不代正确画面，当前无人展示不代释放 |
| 退出与复用 | 展示、参与更新、池内保留的集合分别记录，关闭后及再开窗口、持有责任与同口径状态 | 解释保留代价与复用机会；池内数量不等于全部停止更新，解除持有不代系统占用下降 |

这些是后续采集需求，尚未映射成已支持/校准的 API。几何与执行账还要关联实际相机、LOD 和绘制用途；[几何与 LOD]({{< relref "performance/mobile-geometry-cost-vertices-screen-triangles-lod.md" >}})已解释导入顶点、屏幕三角形、级别选择与驻留的区别，不由上述资源总量推耗时。保留更多外观或池容量，可能换来后续准备机会，同时增加驻留和失效管理；减少保留则需复验换装/再开时的准备与正确反馈。规则和接受条件仍须绑定目标设备、实际配置和完整组合负载，不能因这张表算对就判场景通过。

**理解检查**：C0 为什么不是 88 MiB？C1 为什么人数没变却多了 20？C2 无人展示 A，能否宣布它已释放？C3 能否只计两个实例，或把 36 当成进程总占用？若给每个角色新增了独立材质副本、换了 LOD 或增加阴影用途，分别应重查哪份账？

## 一套更稳的角色拆法

### A. 几何规格

至少写清：

- 主角 / Boss / 精英 / 路人 NPC 各自的面数范围
- LOD 层级、选择依据与过渡条件；不预设所有引擎都按固定距离切换

### B. 蒙皮规格

至少写清：

- 骨骼数
- 每顶点影响数
- 是否允许复杂次级骨骼

### C. 材质与贴图规格

至少写清：

- 材质球数量
- 主贴图尺寸
- 法线和遮罩是否保留
- 是否允许高价材质分支

### D. 动画与运行时规格

至少写清：

- 同时激活的动画层数
- 角色是否允许复杂 IK / 程序化修正
- 同屏最大角色数

## 从单体规格到主画面、阴影与 LOD 过渡

角色规格表中的面数、材质槽位和 LOD 是输入。判断同屏工作时，还要知道：哪些实例、哪一级几何，在什么相机和用途下参与。资源账中的“共享一份”与执行账中的“使用几次”不能互换。

### 先把对象、子网格和绘制用途接起来

```text
角色实例/外观 → 实际 Renderer 与所选 LOD → Mesh 的子网格/材质对应
                                            └→ 主画面、阴影等实际用途/Pass/目标
```

Unity 6.0 的 [Mesh.subMeshCount](https://docs.unity.com/en-us/engine/6000.0/script-reference/unityengine/mesh/submeshcount)说明子网格对应 Renderer 中的材质，各有三角形列表，顶点可以跨子网格共享。因而，要分别保存整个 Mesh、子网格索引范围和实际材质，不能把整份 Mesh 的三角形数再乘材质槽位；统计顶点时也不能把每个子网格引用的顶点数直接相加，当成唯一顶点数。实际绘制还要看管线、Pass、批处理/实例化和状态；材质槽位数不是 DrawCall 的统一公式，相关边界沿[几何与绘制用途]({{< relref "performance/mobile-geometry-cost-vertices-screen-triangles-lod.md" >}})复用。

LOD 选择也不只是世界距离。[Unity 6.0 LODGroup](https://docs.unity.com/en-us/engine/6000.0/manual/analysis/graphics-performance-profiling/simplifying-distant-meshes-with-level-of-detail-lod/class-lodgroup)以对象屏幕空间高度相对屏幕高度的比例描述阈值；实际相机、对象参考范围、LOD Bias 与 Fade 配置需要一起保存。文档还说明，Cross Fade 过渡会分别渲染相邻两级，再交叉淡化，表现需有相应 Shader 支持。因此，远处稳定使用低级别，不证明过渡期间只处理这一级，也不证明不用的级别已从资源账退出。

### 教学用途表：相同人数，参与范围不同

以下是**纸面计数模型，不是帧捕获、硬件计数或性能预算**。三个角色记 I1/I2/I3，某 LOD 的 Mesh 各有身体和装备两个三角形不重叠的子网格，对应两份材质。L0 身体/装备分别 6000/2000 个三角形，L1 分别 1500/500。只讨论一个主画面用途和一个明确命名的阴影用途 S；本题人为给定各用途的实例、级别与子网格集合，不声称 Unity 会自动这样选择阴影 LOD。

每个所列子网格在该用途中计一次“逻辑三角形输入”；重复用于另一个用途就另列。模型不模拟裁剪、顶点复用、批处理、硬件执行、像素覆盖或其他未列 Pass。P0 为稳定状态，P1 仅将 I2 的主画面改为 L0/L1 两级过渡，其他所列参与条件不变。

| 快照与用途 | 题设参与集合 | 逻辑三角形输入 |
| --- | --- | --- |
| P0 主画面 | I1 的 L0 身体+装备，I2 的 L1 身体+装备；I3 不参与 | `6000+2000+1500+500 = 10000` |
| P0 阴影 S | I1/I2/I3 各用 L1 身体，不含装备 | `3×1500 = 4500` |
| P1 主画面 | I1 仍用 L0；I2 同时用 L0 与 L1 的身体+装备 | `8000+8000+2000 = 18000` |
| P1 阴影 S | 与 P0 的 S 相同 | `3×1500 = 4500` |

P0 所列两用途合计 `10000+4500=14500`，P1 为 `18000+4500=22500`，差 8000 来自题设新增的 I2/L0 主画面用途。主画面若只数可见两人，会漏掉 S 中 I3 的工作；若统一按三人、每人 L0 算，又会忽略用途和级别差异。I1 的整份 L0 已含两个子网格，共 8000，不能再因“两份材质”乘二。

这里的两级参与只是逻辑计数，不能说 GPU 时间增加了 `22500/14500` 倍，也不能推出绘制调用数。S 只有一个是题设，不可推广到多光源、级联或其他相机。Unity 的 [ShadowsOnly](https://docs.unity.com/en-us/engine/6000.0/script-reference/unityengine/rendering/shadowcastingmode/shadowsonly)提供“只投影、对象本身不显示”的配置契约，足以说明主画面与阴影可有不同参与集合；它不证明本例已运行，或所有主相机外角色都必定投影。

### 下一份证据应能还原参与集合

后续记录至少应关联运行/帧、角色与 Renderer 身份、实际 Mesh/子网格/材质、相机/目标/Pass，以及稳定或过渡时的 LOD 集合。记录字段是采集需求，尚未实现；规格、实际选择、渲染事件与 CPU/GPU 时间各自保留边界，没有对应证据就写未确认，不能凭 Inspector 槽位补齐批数。

材质和贴图还要对齐实际 Shader/变体、启用特性、绑定纹理及有效尺寸/格式、Mip 和显示覆盖；“同为两份材质”不足以断定工作相同。具体着色机制继续读[Shader 优化]({{< relref "performance/gpu-opt-03-shader.md" >}})，不由本教学三角形输入估算像素时间。换装、降 LOD 或调整阴影时，复查轮廓/装备识别、必要投影和过渡连续性，连同上一节的驻留与再准备代价比较；减少逻辑计数本身不完成接受。

**理解检查**：为什么 P0 不是“三人 × L0 × 两份材质”？P1 增加的 8000 属于哪份几何和用途，能否换算毫秒？如果新增一盏参与投影的灯、改变 LOD Bias，或同样两个槽位换用其他 Shader/纹理，哪些输入和证据需要重建？

<a id="character-task-observation-record"></a>

## 把角色规格接到阶段观测和接受规则

现在可以回答更具体的问题：同样四个角色，换装后资源保留增加、LOD 过渡时绘制参与增加，应该交哪份证据，才能判断是否需要处理？不能只在规格表里勾选“人数没变”。

这里复用[任务观测方法]({{< relref "performance/client-performance-task-observation-model.md" >}})的指标定义，以及[预算规则记录]({{< relref "delivery-engineering/delivery-performance-stability-02-budget-system.md" >}})中依据、检查事实与接受决定的区分。下表是角色领域的记录要求，**不是已实现的采集协议或已校准的阈值**；共用定义按 ID/版本引用，不再另造一套“角色帧时间”。

| 字段 | 角色记录要关联什么 | 判断边界 |
| --- | --- | --- |
| 对象 | 构建/内容版本、运行、请求与数据代次；角色类型、实例及共享资源身份，实际 Renderer/Mesh/子网格/材质、相机/用途/Pass | 名称相同不证明资源相同；同屏、后台和池内集合分开，实例复用不继承旧请求结果 |
| 阶段 | 创建、换装、远近稳定/LOD 过渡、同屏峰值、退出/复用；每段的起止、反馈条件及前后背景 | 首次与已有准备状态分开；离散快照不能代连续窗口，配置变化要分段 |
| 指标定义 | 引用指标 ID/版本、单位、范围、事件/帧与时钟关联、窗口、聚合及预期样本；骨骼/权重是规格，资源、工作规模与 CPU/GPU 区间各列 | 写清整个 Mesh 或子网格、哪个 LOD/用途、哪层内存；规格不推出执行位置或耗时，求值/蒙皮另查对应范围 |
| 成本关系 | 按前两节保留共享分配、实例独占与用途参与集合；角色父区间与动画/渲染子区间保留包含关系 | 不重复乘共享项或材质槽位，不把父子区间相加；整帧差异不直接归给单个角色 |
| 阈值依据 | 规则 ID/版本、体验要求、代表组合与设备；实际画质、LOD/Fade、阴影、Shader/变体及纹理尺寸/格式/Mip | 档位名不代实际配置；标明项目目标、待校准候选或已有验证依据，口径/条件不匹配就不能套线 |
| 拟采集方式 | 业务事件/对象与资源引用、引擎时间线、渲染事件及平台工具的候选来源；附工具/版本、Player 支持范围、配置和扰动核对方案 | `sharedMesh/sharedMaterials` 只帮助找身份；`material` 读取可能实例化，不能为了查询改变被测对象。当前未验证来源覆盖率或准确性 |
| 数据有效性 | 每项分别记有效、缺失、不支持、未启用或关联不明，保留原始记录位置、最后确认阶段与盲区 | 任务成功/失败/超时/取消另记；换装未反馈不等于零耗时，GPU 未关联也不能由 CPU 数据补齐 |
| 超线动作 | 采集/协议负责人补缺失或修关联；角色/渲染负责人查参与集合与资源持有，动画子项转对应负责人；规则负责人记录接受、退回或有期限例外 | 保留旧规则、失败与处理理由；改资源保留、LOD、阴影或 Shader 后，复验必要画面、反馈、驻留及再准备代价 |

### 阶段不能只写一个名字

同一套记录定义要落到下面这些不同条件。具体起止与必要反馈由任务约定，不能把任意一帧“看到了角色”当作全部条件已满足。

| 阶段 | 要留下的条件与边界 | 用来区分什么 |
| --- | --- | --- |
| 创建 | 请求前的资源就绪/缓存、实例池与管线准备状态；请求到约定外观、挂点和可用状态，关联附近帧与分配 | 输入就绪、实例创建和首次反馈分别何时成立；首次/复用不能只按点击次数分类 |
| 换装 | 同一请求/代次的新旧资源、交接持有和实际生效外观；覆盖重叠期间直到约定收尾，保留超时/取消 | 新外观显示不证明旧资源已退出；迟到结果不能记到下一次换装 |
| 远近与过渡 | 镜头/屏幕占比、实际选择依据、LOD Bias/Fade、参与级别、用途与过渡前后区间；材质/Shader 条件一起存 | 稳定低级别与两级过渡、主画面与阴影各做了什么；资源是否退出另查持有/分配 |
| 同屏峰值 | 按玩法定义组合窗口，记录展示/后台/池实例、外观多样性、VFX/UI/场景背景及各用途参与者 | 最高人数、最高资源量和最长工作区间可能不在同一时刻，不能拼成一帧或“单角色成本” |
| 退出与复用 | 退出展示、回池/销毁、结束本次持有及后续复用分别记录；约定时点和期间样本保留共享消费者 | 不显示、保留实例和资源退出不是同一动作；再次使用仍需按新代次核对外观、反馈与旧结果清理 |

前两节的教学记录可以检查这份表是否够用：C2 的四人已全换 B，但 A 仍在，不能因新外观正确就填“旧资源已释放”；P1 的两用途合计 22500 只支持题设参与范围，不能填“GPU 超预算”。二者分别属于资源快照和逻辑工作输入，也不能因都列在角色表里，就认作同次运行或相同窗口的证据。

只有指标定义、来源和有效条件成立，记录才可用于对应判断；还要有适用且获准的规则，才能决定接受。若规格符合制作线，却缺首次反馈或目标组合证据，应保留“规格符合、性能接受证据不足”。材质副本、额外灯光、镜头或实际配置改变时，按受影响的身份、用途和规则重新核对，不自动沿用旧结论。具体配置与来源要求继续复用[分档验证口径]({{< relref "code-quality/device-tier-validation-matrix-baseline-and-visual-regression.md" >}})，可填写的规格与引用放在[角色预算模板]({{< relref "performance/game-budget-19-character-budget-template.md" >}})。

**理解检查**：四人全部换装成功、旧资源是否退出未知、GPU 来源不支持时，哪些事实可以报告，哪些接受结论不能填？若只改阴影用途或把实例留在池里，哪些证据可复用、哪些需要补验，分别交给谁？

## 最常见的误判

### 1. “角色预算就是面数预算”

不对。  
如果一个角色面数不高，但：

- 材质球很多
- 骨骼太多
- 法线和遮罩贴图很多
- 阴影投射和后处理参与太多

它仍然会很贵。

### 2. “主角过了预算，就把主角削掉”

很多时候更合理的做法是：

- 优先压非核心材质分支
- 压次级贴图
- 调整同屏数量
- 调整低档 LOD 和阴影策略

而不是先动最影响感知的核心识别信息。

### 3. “单体检测通过就行”

角色预算一定要看：

- 主角单独
- 小队同屏
- 群怪同屏
- Boss 战高特效叠加

因为玩家真正玩的不是“一个角色在空场景里”。

## 角色预算应该落成什么规则

我建议至少直接写出四张表：

- 主角 / Boss 规格表
- NPC / 小怪规格表
- 贴图与材质表
- 同屏数量与档位联动表

这样角色预算才会从“美术感觉差不多”变成工程规则。

## 结尾

所以如果只用一句话收束这篇，我会这样说：

`角色预算需要共同约束单体规格、同屏组合、实际配置与使用阶段；共享资源、实例和执行工作分别记账，再由目标组合负载的证据决定是否接受。`
