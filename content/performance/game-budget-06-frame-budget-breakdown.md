很多团队会说：

`这一帧超了。`

这句话当然成立。
但如果项目里只剩这句话，通常就还不够。

因为从预算管理角度看，一帧不是一个数字，而是一串不同的人在结的不同账：

- 逻辑时间
- 渲染提交时间
- GPU 时间
- 加载尖峰
- 同步等待

把它们混在一起，会直接导致责任不清和误判。

这些分项是调查与协作视角，不是可以直接相加的五个互斥时间桶。本文同步[一帧拆解]({{< relref "performance/game-performance-frame-breakdown.md" >}})的口径：先区分执行、等待、呈现与反馈，再给对应工作安排预算。下面的账本是工程建议，没有项目收益或持续门禁实测。

## 一帧为什么一定要拆账

如果你不拆，一帧所有的问题最后都会被翻译成同一句空话：

- "优化一下 CPU"
- "GPU 太满了"
- "加载有点卡"

但真实项目里更像下面这样：

- 主线程逻辑本身还行，真正超的是首次挂接和对象激活
- GPU 稳态也还行，真正出事的是切场景后的上传和 RT 重建
- 加载线程已经异步了，但主线程等结果的同步点把一帧打穿了

所以帧预算真正值钱的地方，不是告诉你"这一帧超了"，而是告诉你：

`谁在超，在哪超，为什么总是在这个时刻超。`

## 一帧账本最少要拆哪几项

### 1. 逻辑时间

这笔账管的是：

- Update / Tick
- AI
- 动画
- 物理
- UI 更新
- 常规系统推进

它更偏"世界状态推进"。

### 2. 渲染提交时间

这笔账不是 GPU 真正在画，而是 CPU 这边在：

- 做可见性和列表构建
- 设置状态
- 提交 Draw
- 收口渲染相关工作

很多人把它和 GPU 时间混成一件事，其实不是。

### 3. GPU 时间

这笔账关注 GPU 工作区间，先确认工具是否计入队列等待、上传和同步，以及覆盖哪些队列，再分析：

- 几何
- 光照
- 阴影
- 后处理
- 透明
- RT 读写

### 4. 加载尖峰

加载是跨阶段的事件维度，可能同时包含 CPU 解压、对象创建、GPU 上传与依赖等待。它可在下面这些节点出现，不能在已记录各阶段耗时后再加一次“加载总耗时”：

- 首次资源命中
- 场景切换
- 热更解压
- 后台切回

### 5. 同步等待

这笔账最容易被漏掉。

阻塞等待不等于 CPU 持续空转；线程也可能被挂起。以下等待会延长所测墙钟区间，但只有沿依赖限制目标完成时刻时，才能解释对应的反馈延误：

- 等后台结果
- 等 GPU
- 等资源准备
- 等统一收口

限帧或 VSync 等待还可能是正常节奏控制。先查目标是否按时完成，不以“等待越少越好”作为统一验收条件。

## 分项记账，不重复累计

| 记录维度 | 应写清什么 | 如何避免算错 |
| --- | --- | --- |
| CPU 阶段 | 线程、起止标记、墙钟／实际运行时间、是否含子区间 | 父区间已含子调用时不再相加；并行任务用依赖与重叠关系解释 |
| GPU 阶段 | 渲染帧身份、时间戳范围、队列与工具支持 | CPU API 调用时间不是 GPU 执行时间；多队列区间不能未经分析相加 |
| 加载事件 | 请求身份、用途就绪点、各阶段与线程 | 作为事件标签关联 CPU／GPU／等待，不再作为额外一笔总成本 |
| 同步等待 | 等谁、何时满足、是否阻止目标继续 | 等待与被等待任务往往重叠；限帧等待与依赖迟到分开 |
| 呈现与体验 | 新图像呈现间隔、输入反馈起止点、窗口与样本数 | 保留系统事件与屏幕观测的区别，不能由某个内部耗时直接推算体验 |

一帧拆解的教学例中，任务在 `4–11 ms` 运行，主线程独立工作到 8，等待到 11，再花 2 ms 合并提交；GPU 随后运行 7 ms。图像在 20 就绪，不应把任务、独立工作、等待全部累加。主线程独立工作提前结束，也未必让任务依赖更早满足。

同样，稳态吞吐与单次延迟要分开：CPU／GPU 可以处理不同帧，不能直接相加各自耗时作为输出间隔；单次反馈则要沿自身依赖追踪等待、排队和呈现。Unity 6.0 的 [Highlights 定义](https://docs.unity.com/en-us/engine/6000.0/manual/analysis/profiler/visualizing-data/highlights)也以 CPU／GPU 并行工作解释各自预算；具体计数器的范围仍应按工具核对。

## 判断依据是什么

### 1. 一帧是链路，不是单点

前面那篇 [一帧到底是怎么完成的：游戏里一个 Frame 到底在做什么]({{< relref "performance/game-performance-frame-breakdown.md" >}}) 已经讲过，一帧从来不是 `Update -> Render -> Present` 这么简单。

预算视角下，它更像一条接力链。

### 2. 不同分项帮助选择调查与改动

- 逻辑时间超了，可能要减常驻系统、分帧、换时机
- GPU 时间超了，可能要调分辨率、阴影、RT、后处理
- 加载尖峰超了，可能要预热、拆阶段、换交互时机
- 同步等待超了，可能要改结果收口和调度方式

这些动作只是候选：先判断它是否影响关键路径，再核对正确性、反馈延迟、内存和画面代价。分项能帮助分工，但同一根因也可能影响多笔预算。

### 3. 玩家感知的是整帧结果，不是内部归因

玩家不会关心你是逻辑超了还是等待超了。
但团队必须关心，因为不同的超法需要不同责任人来处理。

## 最常见的误判

### 1. "这帧卡了，所以一定是 CPU 太重"

有时候并不是算得太多，而是在等。

### 2. "GPU 没超，所以渲染不是问题"

如果提交侧和资源准备侧很重，渲染相关问题仍然可能是主因。

### 3. "已经异步了，所以加载不该再伤帧"

很多时候真正伤帧的是主线程最后的挂接和激活。

## 帧预算怎样进入日常规则

真正能用的帧预算，不该只停在一次 Profiler 观察。

它至少要落实成：

- 关键场景固定口径
- 逻辑 / 提交 / GPU / 等待的分项记录
- 首次技能、切场景、首开 UI 的专项样本
- 冷机 / 热机、低档 / 高档的对照

每份记录还应保留包与内容版本、设备／OS／API、构建与采集配置、场景操作、限帧与刷新率、冷热与缓存条件。平均值、P95／P99、最大值和长间隔事件使用同一对象与明示窗口，不混入不同运行条件；若工具没有呈现数据，就保留“呈现未测”，不要用 CPU 时间代填。

分工也以工作对象为准：程序核对依赖和时间戳，TA／美术核对表现成本与画面，策划确认可延后或降级的反馈，QA 保留可重复路线与条件，技术负责人协调目标及跨项代价。角色可以由同一人承担；只有同条件复测及功能／画面接受后，才讨论是否更新基线。

这样你才能回答：

- 稳态是谁超
- 尖峰是谁超
- 哪笔账最容易在版本里反复回来

## 结尾

所以如果只用一句话收束这篇，我会这样说：

`帧预算真正值钱的地方，不是告诉你"这一帧慢了"，而是把逻辑、提交、GPU、加载尖峰和同步等待分别记账；只有这样，团队才可能知道该由谁处理、该怎么处理，以及为什么某些问题总会在同一种时机里反复出现。`
