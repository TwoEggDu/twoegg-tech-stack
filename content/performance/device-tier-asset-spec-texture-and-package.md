分档系统在代码层落地之后，真正影响玩家体验的是资产层——贴图用什么压缩格式、分辨率压到多少、LOD 怎么分层、不同档位的设备是否下载不同的包。

这篇用教学配置展示规格表和分层交付怎样组织。下文分辨率、距离、密度和帧率都是待校准的示例，不是项目实测、行业标准或某类设备的最优配置；具体预算要从目标镜头、内容规模与设备验证推导。

> 版本与证据范围：本轮按 Unity 6（6000.0）纹理格式资料修订；没有四档代表机 A/B 结果。Addressables 片段仅示意标签依赖预下载，未执行编译、分包或下载验收。

## ASTC 格式选法

ASTC（Adaptive Scalable Texture Compression）是支持设备上的 GPU 压缩候选。LDR/HDR、API 和具体 GPU 能力应分别确认。二维 ASTC 每块固定 128 bit，位率按 `128 / (块宽 × 块高)` 计算；相同块大小的质量仍取决于内容和编码器。

| 格式 | 位率（bpp）| 需观察的误差 | 候选比较对象 |
|------|------------|---------|---------|
| ASTC 4x4 | 8 bpp | 法线、高光、透明边缘与细线 | 对误差敏感的内容 |
| ASTC 6x6 | 约 3.56 bpp | 与 4x4 对照细节损失 | 角色/场景的候选 |
| ASTC 8x8 | 2 bpp | 块状、梯度和遮罩变化 | 可接受更大误差的内容 |
| ASTC 12x12 | 约 0.89 bpp | 对高频与透明边缘尤其谨慎 | 仅在画质比较通过后采用 |

**ETC2 / PVRTC 的使用场景**：
- ETC2：按真实设备池和所用 API 判断是否作为构建/分发候选，不凭未经统计的市占判断省略兼容路径。
- PVRTC：旧项目可能保留；是否需要由实际支持设备和格式能力决定。

Unity 可以按平台设置导入格式，但这不自动生成多格式资源包或运行时选择逻辑。使用 ASTC/ETC2 多套产物时，需要显式设计构建、能力检测、地址映射与分发；不支持格式时也要确认是否发生解压回退。见 [Unity 纹理格式](https://docs.unity3d.com/6000.0/Documentation/Manual/texture-compression-formats.html)与 [TextureFormat](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/TextureFormat.html)。

## 各档贴图规格

### 通用规则

1. **角色主贴图**：按实际镜头和屏幕贡献决定保留细节，不固定要求所有档位同尺寸。
2. **法线贴图**：检查高光和法线误差，与颜色贴图分别比较；没有统一的保护优先级。
3. **远景贴图**：观察投影尺寸、过滤和移动时的质量；不能只按 30m 等世界距离宣布压缩差异不可见。
4. **UI 贴图**：按目标像素尺寸、边缘、文字与透明需求选择运行时格式。PNG 是源文件形式，不等于 GPU 中的无损格式；UI 是否分档也由项目需求决定。

## LOD、密度与渲染预算

下表继续沿用教学候选；级联为 0 表示关闭阴影的语义，不代表应向所有 URP API 写入数值 0。

| 配置项 | 高档 | 中档 | 低档 | 极低档 |
|--------|------|------|------|--------|
| Render Scale | 1.0 | 0.85 | 0.75 | 0.65 |
| LOD Bias | 1.0 | 0.8 | 0.6 | 0.5 |
| 植被 / Crowd 密度 | 100% | 70% | 40% | 0%（关闭） |
| VFX 粒子发射量 | 100% | 70% | 40% | 20% |
| Shadow Distance | 80m | 50m | 30m | 10m（或关闭） |
| Shadow Map 分辨率 | 2048 | 1024 | 512 | 关闭 |
| Shadow Cascade | 4 | 2 | 1 | 0 |
| SSAO | 开 | 关 | 关 | 关 |
| Bloom | 开 | 开（降分辨率）| 关 | 关 |
| Color Grading | LUT 完整 | LUT 完整 | 预烘焙 LUT | 预烘焙 LUT |
| 目标帧率 | 60fps | 30–60fps | 30fps | 30fps 锁帧 |

**Color Grading 也需要比较**：预计算 LUT 可以减少部分运行时运算，但查表、应用颜色和相关 pass 仍有成本。是否保留、与其他处理合并或关闭，取决于视觉需求与当前管线，不能概括成接近零成本。

## 按游戏类型的差异调整

上面的表格是教学起点。下面按游戏类型列出候选观察方向，不能仅凭类型确定瓶颈；数字也不具有跨项目推荐效力。

### 动作 / ARPG

**核心压力**：角色特效密度、实时阴影、屏幕空间效果。

| 调整项 | 说明 |
|--------|------|
| 检查角色贴图的屏幕贡献 | 比较主镜头和近景的误差，不固定保留 2048 |
| 比较实时阴影与 Blob | 检查落地感、地形适应、覆盖和混合成本 |
| 分开检查特效模拟与覆盖 | 减粒子数或降低覆盖是不同变量，不固定删到某个百分比 |
| 比较帧率档 | 根据操作体验、功耗与持续性能确定目标 |

### 开放世界 / MMO

**核心压力**：场景复杂度、Draw Call、角色同屏数量、Terrain。

| 调整项 | 说明 |
|--------|------|
| 分别看场景与角色的驻留 | 根据可见范围和流送行为分配贴图预算 |
| Crowd 密度分档控制 | 同屏数量同时影响逻辑、动画、剔除与绘制，分别测量 |
| 比较 Terrain Detail | 检查几何和透明覆盖；降低密度与完全关闭分别观察 |
| 比较 LOD 切换 | 检查轮廓、跳变、额外网格与实际执行收益 |

### 卡牌 / 回合制 RPG

**核心压力**：UI 层复杂度、全屏角色立绘、特效叠加。

| 调整项 | 说明 |
|--------|------|
| 立绘按显示尺寸验收 | 是否分档取决于缩放、镜头与内存，不能统一指定 2048 |
| 场景按实际可见内容分配 | 静态画面与复杂 3D 战斗不能共用未经验证的规格 |
| 比较实时特效与 Flipbook | 后者仍可能有大纹理、采样和透明叠层成本 |
| 验证交互与帧节奏 | 30fps 是否可接受需要具体操作与体验判断 |

### 休闲 / 超休闲

**核心压力**：覆盖尽量多的设备，极低档也要有完整体验。

| 调整项 | 说明 |
|--------|------|
| 比较较低纹理规格 | 按具体画风、显示尺寸和压缩误差判断，不预设 512 足够 |
| 极低档和低档合并也可以 | 如果底线设备不需要太多区分，极低档配置直接复用低档 |
| 根据目标设备池确定底线 | 用户设备分布需要实际资料，不由游戏类型推断 |

## 包体分层：高中低档下载不同的东西

**是的，不同档位的设备可以下载不同的资源包**。这不是 trick，而是移动端资源交付的基本能力。

### 分层逻辑

```
Base 包（所有设备必下）
├── 极低档 + 低档贴图（512/256 分辨率）
├── 低 LOD Mesh
├── 核心逻辑和 UI
└── 极低档配置所需的全部资源

高档差异包（仅高档设备下载）
├── 2048 分辨率贴图
├── 高 LOD Mesh（可选）
├── 高分辨率天空盒
└── 高质量特效贴图

中档差异包（可选，按需设计）
├── 1024 分辨率贴图升级版
└── 中 LOD Mesh（如果 base 包只包含低 LOD 的话）
```

### 实现方式：Addressables + Content Catalog

Addressables 可使用标签查询资源并预下载依赖，但标签不等于独立分包边界，也不自动按性能档替换引用。需要同时设计 Group/打包规则、依赖和档位地址映射；下面仅演示标签依赖下载入口：

```csharp
// 标签示例：给高档专用资源打上 "high-tier" 标签
// 启动时根据档位决定是否下载该标签的内容

public static async Task DownloadTierContent(QualityTier tier)
{
    var labels = new List<string> { "base" };

    if (tier >= QualityTier.Mid)
        labels.Add("mid-tier");

    if (tier >= QualityTier.High)
        labels.Add("high-tier");

    foreach (var label in labels)
    {
        var handle = Addressables.DownloadDependenciesAsync(label);
        await handle.Task;
        Addressables.Release(handle);
    }
}
```

### 常见踩坑

**坑 1：低档设备下载到了高档资源**

候选检查：不同档位是否打入同一 bundle，或 base 资源是否依赖高档专用内容。
处理：检查构建报告和真实下载依赖，调整分组、打包与引用；仅改 label 不保证隔离。

**坑 2：包体降了，但运行时仍然引用高档资源**

候选检查：当前档位解析到的 AssetReference/地址是否仍指向高档资源，依赖是否可取得。没有预下载并不自动等于加载必然 missing reference，加载路径也可能触发下载。
处理：建立明确的档位资源映射；直接引用与 label 都能成为实现的一部分，关键是解析结果和依赖正确。

**坑 3：档位切换后包体版本不一致**

候选检查：Catalog/资源版本是否一致，切档时的新引用是否可用、旧引用是否正确释放。缓存中同时存在高低档数据，本身不能证明版本不一致。
处理：可以选择仅在进入场景前切换，或实现有验证的运行时替换；两者需明确加载、失败回退与生命周期。

**坑 4：中档设备下载了 base 包之后，发现分辨率不够，想升档但没有触发中档包下载**

原因：分层下载逻辑只在首次安装时跑，后续档位调整没有触发补包。
修复：在每次档位判断结束后、正式进游戏前，检查当前档位需要的 bundle 是否已完整下载，缺失则补下。

## 极低档的资产策略

极低档的目标应由当前实际支持设备、内容需求和产品体验确定；旧设备型号不能自动定义今天的支持底线，也不能保证某个开关组合达到 30fps。

内存压力需要按真实设备和进程可用预算观察，先分清理论纹理数据与实际分配：

- 一张 2048×2048 ASTC 4x4 基础层为 `(2048/4)² × 16 bytes = 4 MiB`；保留 GPU 压缩格式时，不需要常规解压为完整 RGBA32 后再采样。
- 如果实际回退到 RGBA32，同尺寸基础层为 16 MiB。两者均未计完整 Mip、CPU 副本和分配开销；要检查实际格式，不能假设每张都会回退。
- 不给出未经设备验证的统一 150–200 MB 贴图预算；合计角色、场景、UI、光照与共享资源的实际驻留，再确定项目余量。

下面仍只是待校准的教学配置候选：
- 所有贴图走 base 包，512 以下 ASTC 8x8
- 关闭动态阴影，改用静态 Lightmap + Blob Shadow
- 关闭所有后处理（Bloom、SSAO、Depth of Field 全部关）
- 特效粒子减少到 20% 以下，或改用 Flipbook 帧动画
- Render Scale 降到 0.65，减少像素填充压力

开关、额外 LOD、低分辨率副本或替代表现都可能产生制作与维护成本。需要哪些资产取决于差距和复用条件，不能预设极低档只要关闭功能即可。
