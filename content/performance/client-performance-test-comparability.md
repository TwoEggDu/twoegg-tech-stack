第一次打开奖励界面时，特效晚了一拍。修改后，两份报告的 P99 都是 16 ms，平均应用间隔只差约 1%。有人认为优化没有价值，另一个人却指出：首次就绪时间缩短了十几毫秒。

这两个判断首先需要回答一个更基础的问题：**两份报告各自在比较什么，记录是否足以支撑这个比较？**

[上一篇]({{< relref "performance/client-performance-task-observation-model.md" >}})定义了一次请求需要哪些对象、事件和观测边界。本篇继续处理记录拿到之后的判断：什么时候可以描述差异，什么时候需要重新分组，什么时候还得补证据。

> 以下两组记录全部由教学假设构造，时间单位为 ms，没有运行引擎或设备实验。算例不提供真实优化收益、通用阈值或已校准采集器。均值、帧间隔和分位数的基础定义复用[一帧拆解]({{< relref "performance/game-performance-frame-breakdown.md" >}})，本篇把它们放进具体比较。

## 先写比较问题，再选择报告里的数字

“B 比 A 快”至少可能指三件不同的事：

| 要回答的问题 | 最少需要什么 | 结论能走到哪里 |
| --- | --- | --- |
| 这两份记录有什么差异？ | 对象、单位、事件、窗口与算法明确，原始输入可检查 | 描述这两份记录 |
| 同一种任务和条件下，B 的结果是否更好？ | 指标相同，初始状态、负载、环境和采集条件可比，并保留重复结果 | 比较指定条件下的表现及波动 |
| 可以接受这项优化吗？ | 改动与证据能支持预期解释，目标和正确性达到约定，新增代价可接受 | 接受已验证范围内的改动 |

第一层有答案，不意味着后两层也有答案。两份数据都可能是真实记录，但一份测首开，一份测重开；它们能描述两种状态，却不能直接回答同条件优化带来了多少收益。

可比性因此总要带着问题。例如，降低分辨率可以用于调查像素相关负载，也可以作为画质方案的一部分；若要评估“相同画质下创建实现的收益”，这项变化就需要拆开。先约定比较目标，再决定哪些条件必须保持一致、哪些变化本来就是方案的一部分。

本篇的教学任务是：应用接受打开奖励界面的请求，准备本次界面内容，并触发特效。只提供两种观测：

- **应用间隔**：同一个应用循环标记的两次相邻时间戳之差，可能包含等待。
- **请求到应用就绪**：请求接受后，到本次界面和特效的逻辑状态已经提交、满足约定后续处理条件的时长。

这里的应用就绪是业务代理终点，不能替代特效首次可见或界面可交互。GPU、呈现和屏幕反馈没有数据时，保持“未测”。每次运行使用自己的单调时钟，只在该运行内相减；跨运行比较同定义的时长，不相减绝对时间戳。

## 第一组：同一个 P99，为什么仍有首次问题

先给一组条件充分明确的教学记录。A/B 仅改变创建实现；任务内容、逻辑完成条件、必要表现、相机、背景、实际分辨率、画质和采集方式相同，作为本题前提。

两个候选各启动一轮新进程。资源输入已按相同协议准备好，目标实例尚未创建。“首次”只指该进程第一次打开本界面，不指所有磁盘、驱动和系统缓存都为空。其他状态在本题中假设一致；实际项目需要核对它们，不能仅靠相同的“高画质”标签证明配置相同。

| 原始输入 | A：`A-run-1` | B：`B-run-1` |
| --- | --- | --- |
| 应用循环起始边界 `t0` | 0 | 0 |
| 第 1 个应用间隔 | 64 | 48 |
| 第 2–100 个应用间隔 | 每个 16，共 99 个 | 每个 16，共 99 个 |
| 首次请求 `q1`：请求 / 应用就绪 | 0 / 90 | 0 / 74 |
| 同进程重开 `q2`：请求 / 应用就绪 | 2000 / 2018 | 2000 / 2018 |

应用统计窗口是从 `t0` 起的前 100 个完整间隔。请求则逐次保留起止点，`q2` 发生在这段应用窗口之外，不并入首开请求。上表可以完整展开：`t_i = t_(i-1) + d_i`，`i=1..100`，共需 101 个边界时间戳。

本例采用 nearest-rank 分位数：将 `N` 个值升序排列，`Pp` 取第 `ceil(p×N)` 个值，位置从 1 开始，不插值。工具算法不同时，应先对齐定义。

| 汇总项 | A | B |
| --- | --- | --- |
| 100 个间隔的覆盖时长 | `64+99×16=1648` | `48+99×16=1632` |
| 平均应用间隔 | 16.48 | 16.32 |
| P95 / P99 | 16 / 16 | 16 / 16 |
| 最大应用间隔 | 64 | 48 |
| 首次请求到应用就绪 | 90 | 74 |
| 重开请求到应用就绪 | 18 | 18 |

升序后的前 99 个值都是 16。P95 取第 95 个值，P99 取第 99 个值，都没有选中唯一的最大值。因此，两个 P99 相同，仍然允许首次附近出现不同的最长间隔。

平均应用间隔只相差 0.16 ms，相对变化约为 `0.16/16.48=0.9709%`；首次代理时长相差 16 ms，相对变化约为 `16/90=17.7778%`。它们的对象、分母和窗口不同，不能压成一个“性能提升百分比”。

若把应用窗口扩到 1000 个间隔，新增的都为 16，均值就变成 16.048 和 16.032，差值进一步缩小到 0.016 ms。首次请求的 90 和 74 没有因此改变：改变汇总窗口并没有重新测量该事件。

这也是首次使用必须保留独立事件记录的原因。长窗口有助于描述持续输出，但稀少事件可能被大量普通样本稀释。反过来，首次变快也不能代替持续运行验收。

本组可以描述：在这些明示条件和记录内，首次代理时长、最大应用间隔分别有 16 ms 差异，重开记录相同。它还不能证明屏幕反馈改善，也不能因为两个差值都为 16，就认定最长间隔解释了全部就绪差异；后者仍需同次请求的依赖和时间线支持。

## 一百个间隔，为什么不是一百次独立验证

第一组每个候选只有一轮运行。100 个应用间隔来自同一进程、同一段状态演进；它们增加了对该窗口的观察，没有增加到 100 次重新开始的测试。

至少区分三层身份：

| 层次 | 用来组织什么 | 常见误用 |
| --- | --- | --- |
| 运行 | 一次启动及其环境、初始化和状态演进 | 把一轮长记录当成大量独立重复 |
| 请求 | 同一运行内一次首开、重开或其他操作 | 把预热后多次重开当成多次首次使用 |
| 帧或事件 | 请求附近的应用、渲染、GPU 或呈现记录 | 不带来源地混合编号，或重复导入同一记录 |

同一运行里的帧还可能存在时序相关，例如状态逐步变化或一串连续的延迟。不能仅凭样本数量给出独立重复的可靠性结论。即使重新启动多次，也仍需检查共同的热状态、后台负载或运行顺序是否引入漂移。

因此要保留各次运行的结果与波动，再决定是否汇总。若几轮运行长度不同，合并所有帧会让较长运行占更大权重；这可以用于描述所采帧总体，却不自动等同于“每次运行权重相同”的结果。权重应服务于比较问题。

去重也依靠身份。可用“运行 + 事件来源 + 帧/请求编号”检查同一记录是否被重复导入。连续出现两个 16 ms 完全可能是两条有效记录，不能按数值相同去重。

本例不足以估计运行间波动，也没有实际接受条件、画面与资源代价。下一步应设计相同阶段和条件下的重复，分别保存首次、重开和后续窗口。重复多少次取决于波动与要作出的决定，本篇不规定统一的三次或十次，也不用这些单轮数据计算收益置信区间。

## 第二组：报告更快，为什么还需要重新比较

再看另一组教学记录。这次先不看均值，先看它们的条件：

| 条件 | A | B |
| --- | --- | --- |
| 请求结构 | 四轮新进程各一次首开 | 同一进程预热后四次重开 |
| 资源和实例 | 目标实例未创建，资源状态按首开协议记录 | 资源保留，实例池可复用 |
| 实际渲染尺寸 | 1920×1080 | 1280×720 |
| 采集方式 | 详细诊断模式 | 仅业务事件的较少插桩模式 |
| 热状态与背景 | 缺少足以对齐的记录 | 缺少足以对齐的记录 |

假设报告保留了下面这些请求。时间均从各自请求时刻算起，终点仍是同定义的应用就绪事件。

| 记录 | 已观测时长 | 结果与有效性 |
| --- | --- | --- |
| A，第 1 轮首开 | 90 | 成功，两个端点齐备 |
| A，第 2 轮首开 | 94 | 成功，两个端点齐备 |
| A，第 3 轮首开 | 不填精确值 | 观察到 500 时测试超时，期间未见就绪事件，业务最终状态未知 |
| A，第 4 轮首开 | 缺失 | 事后检查业务成功，但就绪事件丢失 |
| B，同一轮内第 1–4 次重开 | 18、19、20、21 | 均成功，计时完整 |

只算可观测成功样本，A 的均值是 92，B 是 19.5。这个计算描述了两个被选中的样本集合，**没有计算 A 四次请求的总体均值**。它也不能回答 B 在相同首开条件下的表现。

这里有三个问题。

首先，测量的阶段不同。B 复用了资源和实例，回答的是准备后重开的结果。若优化方案就是提前准备，应把准备阶段及新增驻留也纳入评价；不能把准备成本移到窗口外，再把首开和重开直接当作同一负载。

其次，渲染尺寸和采集方式也变了。即使结果差异稳定，也无法单凭这份记录把差额归给创建实现。降低分辨率可作为独立诊断或配置选择，但应说明它改变了什么，并验证必要表现。

最后，A 的完整性不同。两次计时完整，一次测试超时，一次业务成功但计时缺失；这四次尝试都必须留在记录里。删除后两次，只能得到“计时完整且成功”的条件样本，不能代表全部尝试。

## 超时、业务结果和计时缺失分别记录

第二组中的 500 ms 是教学观察截止约定，不是推荐阈值。若观测在截止前连续有效，记录能支持“截至 500 仍未观察到应用就绪”，不能填成“恰好 500 完成”。若事件以后才发生，具体时长仍需后续证据。

这种情况可以保留观察下界及删失标记：知道观察到了哪里，不知道准确完成时间。若截止前已有丢样，就连这个下界也未必成立，应先检查证据有效性。

业务成功但计时缺失是另一回事。功能检查可以确认任务后来成功，缺少的时间戳却无法因此恢复。它不能填零，也不应自动算成业务失败。

一份报告至少要能回答：发起多少次、业务结果怎样、多少次计时可用、不可用的原因是什么。第二组 A 的四次尝试分别是：

- 2 次业务成功且计时完整。
- 1 次测试超时，业务最终状态未知。
- 1 次业务成功但计时缺失。

保留这层清单后，再对合适的子集作统计，并说明分母。业务结果和证据有效性是两条不同的记录维度，沿用[上一篇的请求记录]({{< relref "performance/client-performance-task-observation-model.md" >}})。

## 采集越详细，为什么不能直接替代接受配置

详细采集能帮助区分解释，但采集本身也要占用资源，并可能改变执行与调度。记录更多细节和取得适合验收的数字，是相关但不同的目标。

Unity 6.0 的 [Deep Profiling 文档](https://docs.unity.com/en-us/engine/6000.0/manual/analysis/profiler/deep-profiling)说明，全方法插桩会增加资源使用并影响运行。这里能推出的是“采集配置需要记录和检查”；它没有提供一个适用于所有调用形状、构建和设备的固定开销，不能把两份报告相减后统一扣掉。

范围也影响解释。[Unity 6.0 的采集说明](https://docs.unity.com/en-us/engine/6000.0/manual/analysis/profiler/profiling-applications/profiling-collect-data-introduction)说明只收集已启用模块的数据；[Unreal Insights Reference（UE 5.8）](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-insights-reference-in-unreal-engine-5?application_version=5.8)说明相关通道未启用时，事件不会进入 trace。没有某条数据，可能是采集配置、支持条件或记录完整性的问题，不能直接推成该项工作为零。

可以先用满足判断所需的较少观测建立记录，再围绕候选解释增加细节；对难以重现的问题，预先保留更多线索也可能值得。代价是开销、数据量和分析成本。选择依据是当前问题和复现条件，不能机械地把“细节最多”作为默认验收配置。

当详细采集支持了一种解释后，需要回到与接受目标匹配、扰动已经检查的配置复核；诊断数据保留自己的身份，不能混入原基线。这里先建立方法，实际采集器的校准留给后续实践。

## 最后交出可比性判断和下一份证据

判断不必给整份报告贴一个永久标签。可以按主张分别写：

| 本例的主张 | 当前判断 | 接下来需要什么 |
| --- | --- | --- |
| 第一组两份记录的首次代理时长不同 | 明示教学条件下可描述，差 16 ms | 实际应用中保留同次事件和起止定义 |
| 第一组因此改善了真实玩家反馈 | 证据不足 | 对应的可见/交互终点、重复结果和接受条件 |
| 第二组支持同条件创建优化的收益 | 当前条件不满足该比较 | 对齐任务阶段、初始状态、配置和采集，保留运行层次 |
| 第二组 A 的四次请求总体平均时长是 92 | 证据不足 | 处理超时与缺失的记录方案；不能用成功子集均值代替 |

在知识阶段，这些补证项形成测试设计即可。进入实际测量时，再按条件准备、有效性检查、基线、假设、改动和复测运行。[性能诊断方法]({{< relref "performance/game-performance-diagnosis-method.md" >}})继续承担从证据走向具体原因和方案的工作。

可以用一个条件变化检查自己是否理解：**第一组只把汇总窗口从 100 个间隔扩到 1000 个，为什么均值差距缩小了，却不能据此说首次收益消失？** 回答时需要分别指出窗口、事件终点与样本层次，并说明真实优化仍缺哪些证据。
