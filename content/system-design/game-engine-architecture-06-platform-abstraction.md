同一份渲染逻辑在开发机正常，到了另一台设备却无法创建需要的纹理。项目明明使用了统一图形接口，为什么差异还会露出来？

平台抽象首先要统一请求和结果的表达，使上层不用到处直接调用平台 API。但具体环境能否完成请求、需要什么条件、失败后怎么办，仍要明确处理。**一个有用的平台边界，应同时说明操作语义、能力范围和失败协议。**

> 阅读位置：运行时位置见 [00A 职责与依赖图]({{< relref "system-design/game-engine-architecture-00a-layers-dependencies-resource-boundaries.md" >}})，产物装配见 [05 资产与发布]({{< relref "system-design/game-engine-architecture-05-asset-and-delivery.md" >}})。实现对照依据 Unity 6.0（6000.0）与 Unreal Engine 5.6 官方资料；下面的适配与回退例子是设计示例，未作设备或引擎运行验证。

## 先拆开两个都叫平台的问题

构建机器需要知道“准备给什么目标生成产物”；运行中的程序需要知道“当前环境能完成什么请求”。两者互相关联，但发生在不同时间，也可能发生在不同机器上。

| 维度 | 运行时平台与设备适配 | 离线目标平台描述 |
| --- | --- | --- |
| 使用者 | 运行中的框架、专业系统和资源服务 | 导入器、编译器、Cook 与构建工具 |
| 主要输入 | 文件、窗口、线程或设备操作请求 | 目标平台、架构、格式、配置与工具要求 |
| 主要输出 | 操作结果、能力信息、完成或失败状态 | 目标规则与加工配置，供工具生成产物 |
| 典型状态 | 文件句柄、窗口、设备和命令资源 | 构建配置、工具链/SDK 描述、目标格式集合 |
| 不能替代的事情 | 不替玩法和画质策略决定如何降级 | 不证明某一台玩家设备实际具备全部能力 |

“平台抽象层”可以作为这些平台职责的总称；画运行时依赖图时，应把离线工具与目标描述另放一侧，不能将所有平台相关 API 画成同一帧内的调用链。

下面两段图示分别描述两种关系：

```text
运行时接口调用：
框架 / 专业系统 / 资源服务 → 平台契约 → 当前后端 → OS / 设备

离线产物交接：
目标描述 + 源内容 + 代码 → 加工与构建工具 → 平台产物 → 交给运行程序
```

例如，桌面工具可以为移动平台构建内容。它运行时查询到的桌面 GPU 能力，不能直接当作目标移动设备的能力清单。

## 运行时适配应统一什么

### 请求的含义，而不只是函数名字

用 `ReadFile` 包装几个平台 API，只有在调用方知道返回的数据归谁、何时完成、失败怎样表达时，才形成可使用的契约。

文件适配可以将平台错误转成约定的失败类别，并保留诊断信息；资源服务再决定是否重新定位或重试。平台实现不应因为一次文件读取失败，就自行跳转游戏场景。

窗口、计时和线程也存在相同问题：句柄何时有效，回调在哪个环境执行，关闭时如何结束未完成请求，都属于接口语义。通用数学和容器则无需因此依赖整个窗口或文件系统。

### 能力，以及能力成立的条件

“支持某种纹理格式”通常还不够，使用者需要说明打算把它用于采样、渲染目标还是其他用途。尺寸、采样数和组合限制也可能影响请求是否成立。

能力查询应尽量表达这些条件。无法满足时，返回可理解的失败，比悄悄接受请求却改变语义更容易维护。即使能力检查通过，实际创建也仍可能失败，例如当前可用资源不足；调用者不能省略结果检查。

## 设计示例：设备不支持期望的渲染目标

假设某渲染效果希望写入高精度颜色目标，再在后续阶段采样。项目允许低档位关闭这个效果，但不允许任意改变其他 Pass 的输入含义。

这里至少有四个负责方：

| 负责方 | 具体决定 |
| --- | --- |
| 产品与画质策略 | 该效果是否必需，允许哪些降级结果 |
| 渲染系统 | 需要什么格式、用途和 Pass 组合，如何实现已批准的降级路线 |
| 平台 / 图形后端 | 当前设备能否满足请求，实际创建是否成功 |
| 离线工具 | 构建对应 Shader、配置和资源，保证允许的路线确实可用 |

可以用下面的伪代码表达协作。这不是 Unity 或 Unreal 的实际 API，也不代表某种格式在所有设备上可用。

```text
preferred = 渲染系统描述完整的目标用途
if 后端支持(preferred) and 创建成功(preferred):
    使用高档效果路径
else if 画质策略允许关闭效果 and 低档路径所需内容已随产物交付:
    检查并创建低档路径需要的资源
    成功则切换到低档路径，否则报告失败
else:
    向应用初始化流程报告该能力不可用
```

这里的回退由渲染系统与画质策略共同决定。后端只知道资源请求，不能自行断言把高精度目标替换成低精度目标后，所有光照、曝光和后处理仍然正确。

降级路线还要真的存在。发布产物没有对应 Shader 或配置时，运行时不能仅靠一个 `if` 分支凭空补出实现。反过来，离线工具生成了高档路线，也不代表玩家当前设备一定能使用它。

一份有用的诊断应能回答：当前后端是什么，请求了哪些用途，能力检查或创建停在哪里，最后选择了哪条路径。它比“某平台不支持”更接近可以处理的问题。

## 哪些差异适合留在边界内

平台实现可以吸收不影响调用契约的细节，例如原生句柄类型、系统调用方式和错误码转换。会改变上层行为或内容需求的差异，则应通过能力、结果或明确配置暴露。

这条原则也限制了抽象的范围：

- 平台文件接口负责读写语义，资产系统负责路径解析和依赖，应用负责内容缺失时的用户流程。
- 图形后端负责设备操作及能力，渲染系统负责 Pass 与资源用途，画质策略负责可接受的视觉变化。
- 目标描述负责告诉工具生成什么，构建系统负责执行加工与装配，运行时再核对当前环境。

条件编译可以用来选择实现和裁剪代码，但不能回答所有运行时能力问题。一个目标平台可能覆盖多种设备；只检查编译目标，会丢失设备与驱动带来的差异。

## 在 Unity 与 Unreal 中怎样找对应落点

### Unity：构建配置、后端选择与当前能力分开看

Unity 6.0 的 Build Profile 是面向指定平台的一组构建配置，同一平台可以保存多份配置。它属于生成应用的工具侧入口，不能当成当前设备能力测试。[Unity 6.0：Build Profiles](https://docs.unity3d.com/6000.0/Documentation/Manual/build-profiles.html)

图形 API 配置决定候选后端。官方文档以 Windows、macOS 和 Linux 的设置为例，说明自动选择及手动列表顺序；这说明“产物允许哪些后端”与“运行时实际采用哪个后端”需要分别观察。不能据此推断所有平台都有相同回退行为。[Unity 6.0：Graphics API 配置](https://docs.unity3d.com/6000.0/Documentation/Manual/configure-graphicsAPIs.html)

`SystemInfo.IsFormatSupported` 则按格式与指定用途回答支持情况。这种查询比“当前是哪个平台”更贴近渲染系统实际需要的契约；它仍不替项目决定视觉降级策略。[Unity 6.0：IsFormatSupported](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/SystemInfo.IsFormatSupported.html)

### Unreal：运行时图形模块与目标产物各有入口

UE 5.6 的官方 API 将 RHI 标为 Runtime 模块，其中包含动态后端接口、资源和命令相关类型。这个入口用于理解运行时渲染请求怎样抵达图形实现，不应扩张成整个操作系统适配的同义词。[Unreal Engine 5.6：RHI](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/RHI?application_version=5.6)

另一侧，Packaging 文档明确说明目标平台、相应 SDK/组件要求，以及将代码和资产加工为目标产物的过程。这属于离线目标与构建问题；“已经为目标完成 Cook”不能替代运行时设备能力检查。[Unreal Engine 5.6：Packaging 与目标平台](https://dev.epicgames.com/documentation/en-us/unreal-engine/packaging-your-project?application_version=5.6)

这些例子说明两台引擎都需要连接离线目标与运行环境，但具体配置项、模块边界和支持范围不能直接互换。这里也没有据此推断后端的实际性能、内部线程模型或所有平台的兼容性。

## 用两条线定位跨平台问题

如果产物连目标环境都无法加载，先追目标、架构、内容格式和工具要求；如果产物能运行而某项请求失败，再追当前后端、请求条件、能力结果与创建错误。两条线会在产物与运行契约处交汇，排查时却不能相互代替。

平台抽象的价值，是让上层用明确契约处理差异，并把回退决定留给真正理解行为要求的系统。
