打开一台引擎的代码，通常能找到 Render、Physics、Scene、Resource、Editor、Platform 等名字。知道这些词的含义，还不足以回答一个工程问题：修改角色外观时，为什么编辑器、资源加载和渲染表示都要参与，而文件系统不应该理解“角色换装”？

本系列用一张职责地图回答这类问题。先辨认谁生产内容、谁组织世界、谁提供执行机制和专业能力，再追接口、状态和生命周期。**职责分类帮助我们找问题，依赖关系帮助我们判断设计；两者不能互相替代。**

> 本文的分类是作者用于阅读引擎的参考模型。Unity 2022.3、UE 5.6 和 Godot 官方资料提供具体概念的例子，不证明所有引擎采用统一层数或相同目录。本文没有进行引擎源码依赖审计或运行测试。

## 先画职责地图，不急着排上下层

可以从下面六组问题进入一台引擎。表格按阅读顺序排列，**不表示调用顺序，也不表示只能依赖相邻一行**。

| 职责范围 | 它回答的问题 | 典型输入与输出 | 后续文章 |
| --- | --- | --- | --- |
| 内容生产 | 人怎样制作、修改、预览和保存内容？ | 编辑动作、源文件 → 内容描述与加工请求 | [01]({{< relref "system-design/game-engine-architecture-01-content-production.md" >}}) |
| 世界与游戏框架 | 对象怎样存在、关联、更新和退出？ | 场景描述、玩法操作 → 世界实例与生命周期通知 | [02]({{< relref "system-design/game-engine-architecture-02-gameobject-vs-actor.md" >}}) |
| 运行机制 | 代码、类型、内存和任务怎样获得执行支持？ | 程序与任务、类型契约 → 执行与管理能力 | [03]({{< relref "system-design/game-engine-architecture-03-runtime-foundation.md" >}}) |
| 专业系统 | 模拟、姿态、声音和图像怎样计算？ | 专业描述、世界变化 → 专业结果与表示 | [04]({{< relref "system-design/game-engine-architecture-04-professional-subsystems.md" >}}) |

还有两类问题会横穿这张表。数学、容器、内存等 **Core 基础能力**被多处复用；数据导向则会改变世界存储、任务组织和专业系统交接，不能只把它画在表格最底部。后者由[07：DOTS 与 Mass]({{< relref "system-design/game-engine-architecture-07-dots-and-mass.md" >}})展开。

这张表比单列“渲染、物理、动画”多考虑了制作、世界组织和交付，但它仍然只是职责索引。一个模块可能覆盖多行，一行也可能分散在几个模块里。对照目录时，应先找实际契约，再判断是否值得拆分。

## 这些职责怎样放进分层参考模型

[00A：职责、依赖与资源服务的边界]({{< relref "system-design/game-engine-architecture-00a-layers-dependencies-resource-boundaries.md" >}})进一步提出“应用与工具—引擎框架—专业系统—平台后端”的主要接口使用方向，同时把资源服务和 Core 画成共享能力。它与上表可以这样对齐：

| 本文的观察角度 | 在00A中怎样定位 |
| --- | --- |
| 内容生产 | 主要在工具侧；预览可以使用运行时框架和专业系统 |
| 世界与游戏框架 | 框架管理身份、场景关系、生命周期与推进策略；具体玩法归应用 |
| 运行机制 | 通用机制放在共享基础或专门运行模块；接入对象生命周期的部分在框架 |
| 专业系统 | 各自维护领域数据、算法和表示，通过契约协作 |
| 资产与交付 | 离线加工在工具链；运行时身份、依赖与加载协作由资源服务承担；类型处理留给相应实现 |
| 平台与设备适配 | 运行后端承接环境操作；离线构建工具使用目标平台信息，两条线分别讨论 |

例如，资产构建和运行加载都涉及“资源”，却不会因此成为同一个模块。一个运行时只读内容包的程序，不应被迫携带完整模型导入器；一套离线加工工具，也不一定需要活动游戏世界。

同样，不能根据表格行序，推断内容生产、世界建立、运行机制与专业系统之间的先后关系。实际装配与初始化顺序取决于依赖；内容生产工具也可能调用运行时能力完成预览。

## 用一次角色外观修改检查交接

假设团队把守卫角色的金属盔甲改成皮甲。下面是**教学设计例子**，箭头表示产出与消费的数据关系，具体引擎可以合并、并行或跳过其中的步骤。

```text
工具修改模板与材质引用
    → 加工或取得对应资产产物
    → 资源服务解析标识、协调依赖与加载
    → 世界中的守卫实例绑定新的外观
    → 渲染/动画系统更新自己的专业表示
    → 设备后端执行需要的上传与绘制工作
```

这条路径上的每个交接，都有比模块名字更具体的问题。

**工具侧要区分改了谁。** 修改模板，还是只改一个场景实例？撤销和保存记录针对哪份数据？Unity Prefab 提供可复用模板与实例覆盖，是一个可以核对的实际例子；它不能替其他引擎规定模板机制。[Unity 2022.3：Prefabs](https://docs.unity3d.com/2022.3/Documentation/Manual/Prefabs.html)

**世界侧要区分身份与共享内容。** 守卫实例的位置和动画状态属于该实例，网格或材质可能由多个对象共享。Unity GameObject 以组件组合能力，说明“对象身份”和“具体功能”可以分别讨论；组件布局仍不能直接推导渲染器内部的数据布局。[Unity 2022.3：GameObjects](https://docs.unity3d.com/2022.3/Documentation/Manual/GameObjects.html)

**资源与专业系统要协商完成条件。** 找到资产标识、读完文件、建立 CPU 数据、上传到设备、发布新的场景表示，是不同的状态。只写“加载完成”会掩盖谁还能等待、谁可以消费，以及旧表示何时释放。

**平台边界要保留通用语义。** 文件接口接受读取请求，图形后端接受资源创建和执行请求。它们可以报告失败、限制或完成信息，但不负责决定“这个守卫现在应穿皮甲”。这个决定属于工具意图或游戏规则。

如果只更换材质引用，却需要修改文件系统的角色判断代码，说明上层语义已经扩散。如果删除一个守卫就释放其他守卫仍在使用的网格，说明实例寿命和共享资源寿命没有分清。这两种错误都无法靠重命名目录解决。

## 三种箭头要分开看

分析刚才的例子时，至少需要区分：

1. **代码依赖**：资源管理器是否引用具体纹理实现，还是只认识加载器接口？看类型、模块规则和接口归属。
2. **运行调用**：谁注册加载器，谁调用它，回调在什么条件下触发？看装配、调用路径与完成协议。
3. **数据与时间**：谁发布新的材质表示，谁仍持有旧版本，怎样确认设备使用结束？看所有权、队列与同步条件。

运行时“通用管理器调用专业加载器”，可以通过由通用侧定义的接口实现，并不自动意味着编译依赖也指向专业实现。反过来，把调用藏进回调，也不会自动消除对具体类型和寿命的依赖。00A会用加载器注册展开这个区别。

读主循环时还需要另一张时间图。初始化、帧调度和退出不是这张职责地图的上下移动，相关模型见[初始化、帧循环与退出]({{< relref "engine-toolchain/game-engine-foundations-02-startup-frame-shutdown.md" >}})。

## 官方资料能支持什么，不能支持什么

Godot 的架构文档把 Scene、Servers、Drivers/Platform、Core 和 Main 分别说明，可以作为“世界组织、专业能力、平台适配和共享机制能够分开讨论”的例子。但它的 Core 包含 Object、ClassDB 和文件 I/O，范围并不等于本文参考图中较窄的 Core。[Godot：Engine architecture](https://docs.godotengine.org/en/stable/engine_details/architecture/godot_architecture_diagram.html)

UE 5.6 的 Packaging 文档说明了构建、Cook、Stage、Package 等交付操作。它支持把面向目标平台的内容加工和发布纳入引擎工程视野，却不意味着这些步骤都是运行时架构中的一层。[UE 5.6：Packaging projects](https://dev.epicgames.com/documentation/en-us/unreal-engine/packaging-your-project?application_version=5.6)

因此，本系列会把结论写在证据实际覆盖的范围内：某个文档可以说明一个对象或工具的职责，不能仅凭文档目录、产品名称或包名，推出整台引擎的依赖图。讨论 Unity 与 Unreal 时，优先对照相同任务中的状态、接口和变化传播，而不是给两台引擎预设“更轻”或“更框架化”的标签。

## 怎样使用这张地图

第一次读，可以按00、00A、01—07认识完整范围；有具体问题时，直接跳到对应专题：

- 编辑属性不能正确保存或预览：从01的编辑事务和运行表示交接开始。
- 对象、组件、资产引用混在一起：从02区分身份、组合与关系。
- 不清楚反射、GC、任务系统应放哪里：从03分开机制与框架策略。
- 一个游戏事件牵动多个系统：从04追生产者、消费者与完成条件。
- 内容本地可用，发布后不可用：从05追目标产物、依赖和交付分支，再到06看平台条件。
- 想批量处理大量对象：从07比较数据布局、更新组织与表现桥接。

读完一篇，选一个真实变化，写下它的输入、持有者、输出和清理责任，再回代码找证据。能追通这条路径，比记住固定的层数更接近读懂一台引擎。
