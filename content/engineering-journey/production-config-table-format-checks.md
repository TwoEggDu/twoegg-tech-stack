策划修改配置表以后，如果其他人导不出来，或者运行时才发现引用不对，这次修改就会变成下游的等待。我在项目中遇到过配置解析不通过的问题，也逐步把检查接到日常修改与提交环节。

项目使用**鲁班（Luban）导表，并通过 TortoiseSVN 提交前的客户端钩子接入本地检查**。它把检查放在策划准备交出修改的时候：先取得反馈，回到源表处理，再继续交接。代码编译走另一条路径，由 Jenkins Job 在提交后检查并在群里提醒，见[编译错误处理]({{< relref "engineering-journey/production-client-compile.md" >}})。

这里要回答两个问题：怎样让检查进入日常工作，以及一次通过究竟能证明配置在哪些方面正确。

## 把“配置是对的”拆成可以判断的条件

源表能导出，是后续使用的起点。业务含义、跨表关系和实际加载结果还需要各自的规则与验证。

| 层次 | 要判断什么 | 由什么支撑判断 |
| --- | --- | --- |
| 可解析与类型 | 输入是否满足定义，字段能否按声明类型读取并生成输出？ | 导表工具、表结构与字段定义 |
| 已声明的约束 | 数值范围、引用目标或资源路径是否满足项目规则？ | 配置的校验器、被引用的数据与明确的检查上下文 |
| 业务含义 | 单位、默认值、配方或奖励关系是否符合设计？ | 策划与程序约定的契约、业务规则和相应测试 |
| 实际消费 | 代码、数据与资源是否配套，游戏是否读到了这次修改？ | 产物核对与受影响功能的运行验证 |

例如，某字段无法转换成声明的整数，是解析问题；引用了不存在的物品 ID，是需要相应规则的引用问题；奖励 ID 有效但选错了奖励，则可能通过前两层。这些是说明检查边界的示例，不是本项目的事故记录。

因此，工具通过支持的结论应当是：**在这组输入和已启用规则下，检查没有发现对应错误。** 不能把它扩大成所有业务内容已经验收。

## 鲁班负责导出与规则检查，规则仍要由项目定义

鲁班根据配置定义处理源数据，并生成程序需要的数据或代码。它提供引用、范围、路径等校验能力；使用哪些能力，需要在项目定义中明确配置。可对照官方的[数据校验器说明](https://www.datable.cn/docs/quality/validators)。该页当前为 5.x，本文未确认历史项目所用版本，不照搬其中的命令行开关，也不推定项目已启用所有校验器。

工具不会自动知道一个字段的业务单位，或者哪些空值是合法的。策划与程序先约定含义，工具维护者再把稳定、可执行的条件落实为规则。新增检查要同时准备“应该通过”和“应该报错”的样例，避免把有效内容挡住。

跨表关系需要相应的上下文。只给导表工具一张修改过的表，可能不足以判断它引用的目标；检查范围应由依赖关系与规则决定。路径检查也依赖所使用的资源目录及规则配置，不能仅凭某个校验器名字，就认为打包收集与设备加载已经检查过。

## TortoiseSVN 钩子把检查放到提交前

本地入口的价值，是让策划不用等另一位同事更新工程后再发现导表错误。钩子负责触发，鲁班与项目规则负责判断；两层需要分别排查。

1. 策划修改源表与相关定义，准备通过 TortoiseSVN 提交。
2. 提交前客户端钩子调用本地检查，鲁班按项目定义导出与校验。
3. 查看结果与诊断；有错误时回到源表、规则或环境修正，再运行检查。
4. 检查通过后核对提交范围，继续交接。

这四步说明检查与修正的处理路径。**钩子失败是否强制阻止提交，还取决于实际脚本和客户端设置；本文目前确认的是使用了提交前客户端钩子，没有把强制阻断写成已验证结果。**

TortoiseSVN 的客户端钩子有等待脚本完成、错误处理等配置。它运行在本机，不能当作服务端对所有客户端的统一准入。要设计阻断行为，应核对等待与错误传播，并以失败样例实际验证提交结果，见 [TortoiseSVN 客户端 hook 设置](https://tortoisesvn.net/docs/release/TortoiseSVN_en/tsvn-dug-settings.html#tsvn-dug-settings-hooks)。

## 收到报错以后，怎样让策划自己继续处理

我已有的导表反馈经验是：通知先指出相关配置文件，详细原因再通过本地工具查看。把检查前移后，仍然需要让使用者从结果找到输入，而不只是看到“导表失败”。

下面是组织诊断信息的建议，不是鲁班某个版本的原始日志格式，也不表示这些字段已经全部接入：

| 应提供的信息 | 帮助使用者完成什么 |
| --- | --- |
| 源文件、表与可定位的记录／字段 | 找到应该修改的输入；能够取得行列信息时一并显示 |
| 违反的规则、预期与实际值 | 理解为什么错误，避免盲目试填 |
| 详细日志和重新检查入口 | 查看简短提示之外的原因，修正后执行同一检查 |
| 工具或环境失败的具体阶段 | 区分数据错误与工具无法正常工作 |

处理时先回到真正维护的源表或定义，修正后重新导出。不要只修改生成的二进制或生成代码，否则下一次生成可能覆盖修正，源输入仍然有问题。

如果是工具未能启动、依赖缺失或规则定义不合理，应由工具维护者参与恢复；让策划反复改正确的数据，只会增加往返。若错误涉及业务含义，策划和消费这份配置的程序需要共同确认规则。

## 本地通过以后，还要核对交出去的内容

本地工作副本可能有尚未提交的源表、定义或资源。本地检查能找到它们，其他人同步版本库时却可能拿不到。因此，导出成功后还要核对提交范围，确保该次修改所依赖的输入一起交接。

历史实践中也有提交后触发配置格式检查，以及策划在本地把 `xlsx` 导出为游戏使用的 `bin` 的入口。它们说明两个检查时机的价值：本地尽早反馈，共享版本再次检查。这里分别记录已有做法，不将不同历史材料拼成一条已完成端到端验证的流水线。

复查时要看检查是否实际执行、输入是什么、结果是否通过。没有新通知不能单独证明恢复；本地生成了新数据，也不能证明客户端和服务端已经取得它。接下来按[配置与双端一致性]({{< relref "engineering-journey/production-config-consistency.md" >}})核对定义、生成代码、数据、资源与实际消费，再对受影响功能进行验证。

**配置检查成为生产能力，靠的是规则能够表达、错误能够处理、交出去的内容能够复查。**
