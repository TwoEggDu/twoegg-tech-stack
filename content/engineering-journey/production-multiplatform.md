同一个项目要交付微信和 TikTok，两边都走 Web 构建，但各自的平台库不能因此混在一起。问题可能在编译阶段就出现，例如两套平台代码有重复的类名；也可能把 TikTok 的平台库带进微信包，交付内容与目标平台对不上。

我实际负责过 Windows、iOS、Android、微信小游戏和 TikTok 等平台的交付。通常每个平台会配置一个或多个 Jenkins Job。上面的 Web 平台差异，是我们在这套工程里重点处理的一类问题。

我们的做法是：**将平台专属材料放在工程外，通过参数化构建选择目标平台，实际打包时再把对应内容拷入工程。** 这些准备工作封装在构建工具内，业务侧使用相应的打包入口，最终各平台分别出包进行测试。

本篇根据这套实际流程，说明平台差异怎样从使用者的手工准备，转成构建工具负责的输入选择。具体报错、文件名与内部脚本不在这里展开。

## 同样是 Web，仍需要区分实际交付平台

在我们项目中，Windows、Android 和 iOS 的构建方式比较成熟，日常主要选择对应的平台设置。这里的成熟是对该项目使用情况的描述，具体工程仍有各自的依赖与配置。

微信与 TikTok 带来了另一层区别：引擎侧同属 Web 构建，实际接入的宿主与平台材料不同。只选了 Web 目标，还没有回答本次应该使用哪一套平台库。

从 Unity 的通用机制看，`UNITY_WEBGL` 表达的是 WebGL 构建平台。Unity 也支持自定义编译符号，见[官方条件编译说明](https://docs.unity3d.com/2022.3/Documentation/Manual/PlatformDependentCompilation.html)。在本案例里，微信与 TikTok 的选择还需要项目自己的构建输入来表达；上面的通用平台符号本身不能替代这项选择。

可以把需要对应的信息分成三层：

| 层次 | 需要确定什么 |
| --- | --- |
| 引擎构建目标 | 本次使用哪种引擎构建方式，例如 Web 构建 |
| 实际交付平台 | 本次交付微信还是 TikTok，应该选择哪套专属材料 |
| 工程实际输入 | 真正进入编译和打包过程的文件，是否对应本次选择 |

这样排查时，就能把“选了哪个平台”继续追到“哪些材料实际进了工程”。

## 平台库混在一起，可能在不同阶段暴露问题

这类问题需要分别看两个阶段。

**编译阶段的冲突。** 两套平台代码如果在同一编译范围内声明了冲突的类型，就可能因为重复定义而失败。此时需要核对的是工程里有哪些代码、为什么它们同时参与编译，而不只是重复点一次构建。

**构建内容与目标不符。** 即使没有在编译阶段报错，也需要检查是否准备了错误的平台材料。微信包里混入 TikTok 专属库，就是输入选择需要避免的情况。编译成功本身不能说明所有平台材料都已选对。

这里整理的是作者确认的冲突与混入风险，以及实际采用的准备方案，不拼成某一次有完整堆栈和修订记录的事故。两种现象共同指向的是：需要控制平台专属内容何时、按什么条件进入工程。

## 将平台专属材料放在工程外，构建时再选择

在这套方案中，微信与 TikTok 的专属材料先分别准备在工程外。构建工具接收目标平台参数，选择对应内容，在实际打包时拷入工程中的相应目录，再继续构建。

```text
工程外的平台材料
    ├─ 微信材料
    └─ TikTok 材料
           ↓ 按目标平台参数选择
工程中的平台目录
           ↓ 构建
目标平台的包
           ↓
对应平台的测试
```

这张图只说明组织关系，不对应内部目录名。工程外的材料区与参与构建的工程目录承担不同职责：前者存放可供选择的平台内容，后者承接本次构建需要的内容。

把材料放到工程外，只完成了存放位置的区分。真正接回日常交付的是参数化准备：打微信包时由工具选择微信材料，打 TikTok 包时选择 TikTok 材料，让这项选择进入构建流程。

因此，平台选择会影响工程实际收到的输入。排查出包问题时，也有了可以继续追查的位置：本次传入什么目标，工具选择了什么材料，拷入后工程使用了什么内容。

## 对业务提供打包入口，把准备细节封装进工具

每个平台通常有一个或多个 Job。它们可以作为业务侧取得相应平台产物的入口，而平台材料怎样选择、从哪里准备、何时拷入工程，由构建工具统一处理。

业务侧不必在每次出包前理解和执行这些目录操作。复杂性进入工具以后，维护者仍需能沿构建目标查到准备过程，工具才能持续维护；使用者则围绕本次要取得哪个平台的包继续工作。

本篇中的平台维度，与[版本范围与合并协作]({{< relref "engineering-journey/production-parallel-versions.md" >}})中的分支维度需要一起看：

- **分支与修订**决定本次交付哪些功能、修复、配置和资源。
- **平台选择**决定本次采用哪组平台专属材料。
- **Job 与构建记录**帮助定位是哪次执行产生了这份包。

同一个分支可以向多个平台出包，同一平台也可能有不同用途的 Job。核对时需要把这些选择对应起来，才能判断问题出在版本范围、平台准备，还是后续构建与运行阶段。

## 最终出包测试，让平台准备接回交付

这套流程最终会为各平台打出包，再进行测试。工具封装准备细节，使用者取得对应产物，QA 或其他测试者继续检查实际表现，构建工具因此接入了日常交付过程。

如果需要把这类方案复验得更完整，可以按下面的对象分别保留记录：

| 检查对象 | 要回答的问题 |
| --- | --- |
| 构建入口 | 本次 Job 选择了哪个平台，使用哪个源码修订？ |
| 材料准备 | 选中了哪套材料，工程实际使用了什么内容？ |
| 编译与产物 | 是否完成构建，产物是否对应目标平台？ |
| 运行测试 | 在目标平台测试了哪些操作，结果怎样？ |

这是组织后续复验的方法。本篇已确认的是参数化材料准备、工具封装，以及分别出包进行测试的工作方式；没有在本轮重跑五个平台的构建，也不把测试流程的存在扩写成五端所有功能均已验收。

包通知、QA 取包和运营发布怎样衔接，见[怎样持续维护一个可发布版本]({{< relref "engineering-journey/production-release-readiness.md" >}})。构建环境、工作目录与维护的进一步问题，留在[构建环境与维护（提纲）]({{< relref "engineering-journey/production-build-infrastructure.md" >}})中展开。

## 将平台差异变成可以维护的构建输入

这次实践留下的，是一条相对清楚的职责分工：平台专属材料分别准备，构建工具根据目标选择并拷入工程，业务使用平台对应的入口，最终通过实际包继续测试。
