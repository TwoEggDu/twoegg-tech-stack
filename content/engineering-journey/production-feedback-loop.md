一次新版本上线后，制作人发现转化偏低。我开始到 Firebase 后台查看崩溃日志，沿着异常信息排查，将方向收敛到客户端 JSON 库 CatJson 的浮点数处理与语言、区域设置的关系。据我回忆，当时出问题的是俄语环境。

我将这个猜想和解决方向交给客户端主程。后续客户端侧修改了 JSON 库并推送修复，该语言环境下没有再出现这项问题；QA 随后也将该语言纳入每次发布的测试。

这次我的工作是从业务反馈切入技术排查，形成猜想与修复方向，再交给对应负责人处理。我也提供了固定区域设置的数值转换工具方法；客户端主程推进库侧修复，QA 把已发现的问题转成后续回归条件。这里能够确认的是这项故障得到解决和测试范围得到补充，不据此判断整体转化变化或买量收益。

在[可发布版本]({{< relref "engineering-journey/production-release-readiness.md" >}})一篇中，交接已经走到运营发布与数据回传。这篇先展开上面的实际经历，再连接日志回收和分析工具中的其他做法，说明反馈怎样进入下一轮生产。业务反馈与修复后的表现依据本人回忆整理，工具方法及 CatJson 格式化适配已经核对历史提交；事故的准确日期、原始堆栈与故障包版本仍待补充。

## 从转化反馈，收敛到可以交接的技术问题

### 先从具体异常寻找线索

“转化偏低”是需要调查的现象。它可能与技术故障、用户群、流量来源、玩法流程或统计口径有关，不能收到这个反馈就直接归因。

这一次，我选择先查看 Firebase 后台的崩溃信息，检查客户端有没有具体的失败线索。后续排查提出了 JSON 浮点解析与语言环境有关的猜想，而不是仅把“转化有问题”继续转交给其他人。

### 把语言环境当成运行条件检查

JSON 数字的小数部分采用点号格式，见 [RFC 8259 的数字定义](https://www.rfc-editor.org/rfc/rfc8259.html#section-6)。而在 .NET 中，一些未显式指定格式提供者的浮点解析调用会使用当前区域设置；数值默认转成字符串时也会使用当前区域的格式。参见 [Single.Parse 官方说明](https://learn.microsoft.com/en-us/dotnet/api/system.single.parse)与 [Single.ToString 官方说明](https://learn.microsoft.com/en-us/dotnet/api/system.single.tostring)。

因此，要同时检查两个方向：读取 JSON 数字时是否按数据格式解释，写出 JSON 数字时是否意外采用了面向用户显示的本地格式。只盯着报错处的“解析失败”，可能会漏掉上游已经写错格式的情况。界面语言和运行时区域设置也需要分别确认，不能只凭“俄语”推定某个具体 Culture 值。

继续验证这类猜想时，可以对照相同输入在不同语言与区域设置下的表现，检查解析是否遵循数据格式约定。具体输入、异常与对比结果应来自复现记录，不用一个相似的公开示例替代。

### 把解决方向落到转换工具与库的格式化入口

回查历史记录，可以看到两组相关改动：

| 时间 | 已核对的改动 | 解决哪一层的问题 |
| --- | --- | --- |
| 2023 年 6 月 | 我新增字符串到 `float`、`double` 的转换工具，显式使用 `CultureInfo.InvariantCulture`，随后补充可选的错误日志与抛出异常行为 | 让调用这些工具的数值转换使用固定格式，并提供失败诊断入口 |
| 2024 年 1 月 | 客户端同事为 CatJson 注册 `float`、`double` 自定义 Formatter，在 `ToJson` 中显式使用 `NumberFormatInfo.InvariantInfo` | 固定浮点数写入 JSON 时的格式，避免输出跟随当前区域设置 |

前一组提交核实了我提供工具方法的工作；后一组核实了客户端侧通过 CatJson 扩展入口完成格式化适配。它们有不同的提交日期，不能据此确定线上事故发生在哪一天。

这里也有一个容易混淆的细节：后一组改动重写的是 `ToJson`，直接处理的是**序列化输出**，不能将它描述成重写了 `ParseJson`。工具方法使用固定区域设置，也不等于 CatJson 已调用该工具；这条调用关系尚未在历史记录中确认。

这个转换工具本身也不是完整的 JSON 数字校验器。其历史实现采用较宽松的数值样式，且默认失败时返回零，可按参数选择记录错误或抛出异常。若某处必须区分合法的零与转换失败，调用方还需要明确处理失败，而不能只检查返回值。

### 交给能修复这一层的人，再把条件留下来

我交给客户端主程的是问题猜想和解决方向，由客户端侧继续修改 JSON 库并推送修复。修复以后，该语言环境下不再出现原问题；QA 将该语言加入后续每次发布测试，避免以后只在常用语言环境下验证。

这一轮既解决了一项客户端问题，也留下了来自真实故障的回归条件。后续版本需要再次经过这项检查，修复经验因此进入持续交付过程。

## 先问需要判断什么，再选择数据

“看看数据有没有问题”还不够具体。我会先将它改写成可以继续查证的问题：哪个版本、什么操作或环节出现差异，影响哪些用户，需要谁作出什么判断。

不同来源承担的角色也需要先分开：

| 来源 | 可以帮助回答什么 | 还需要核对什么 |
| --- | --- | --- |
| 技术日志与异常记录 | 哪个阶段报错，调用或加载停在哪里？ | 包版本、设备、时间、操作与相关上下文 |
| 客户端行为事件 | 客户端声明发生过什么操作或流程节点？ | 触发位置、身份、漏报补报及版本覆盖 |
| 服务端业务记录 | 服务端受理了什么，业务处理结果是什么？ | 处理对象、结果语义、记录范围与重复情况 |
| 运营或渠道数据 | 特定窗口与用户群的触达、行为或结果怎样变化？ | 指标分母、归因口径、时间与平台差异 |
| 玩家反馈与工单 | 玩家在什么条件下遇到了什么现象？ | 复现步骤、发生时间、版本及可关联的记录 |

例如，客户端上报了购买按钮点击，不能直接当成服务端购买成功；一个行为同时出现在两类记录中，也不能把两条记录相加计为两次业务结果。日志采到错误信息，同样不能单凭日志条数判断受影响人数。

已有客户端 BI 材料还区分了认证身份、断线队列和服务端记录。队列中接受了一条事件，不等于已经送达；服务端记录了客户端声明，也不会自动把它变成服务端权威业务结果。先说清这些含义，后面的统计和诊断才有对应对象。事件设计可继续看[事件契约与版本上下文]({{< relref "code-quality/game-analytics-integration-event-schema-and-privacy.md" >}})。

## 日志回收：先把检查范围固定下来

上面的案例使用了 Firebase 后台查看崩溃。下面的日志回收与数据整理属于另外已有的工具实践，用来说明怎样准备可查材料，不表示它们都参与了同一次排查。

现有日志回收流程提供了按环境和时间窗口取得材料的入口，并支持定时执行。一次任务中的各来源共用冻结的窗口，避免因为排队或采集耗时，让每个来源实际查询的起止时间不断变化。

结果按照来源整理、归档，再提供通知与下载入口。服务端业务日志、应用日志与独立客户端观测资料分别呈现，接收者可以继续核对某个来源是否完整，以及这次实际取到了什么。

这里有三个状态值得分别保留：

- **采集执行状态**：任务有没有真正完成准备、获取和归档。
- **各来源状态**：完整、部分缺失或失败，不能被一个总状态掩盖。
- **通知状态**：报告是否已经可取得，通知是否被接口接受；它与报告中的事件是否正确是不同判断。

一份历史回收记录就保留了这种差异：部分来源缺失，其他来源仍有有效产物，最终任务按不完整状态呈现。现有核对到的是回收元数据和清单，不能因此推断缺失来源没有玩家活动，也不能把其余产物存在写成所有业务数据都已验收。

所以，“没有查到”需要继续拆开看：可能确实没有发生，也可能来源缺失、筛选范围不对、目标版本没有记录这个事件，或采集本身失败。把这些状态保留下来，比给一张看起来全部完成的总表更有用。

## 数据整理：让同一问题能够按同一口径重查

已有分析工具可以读取导出的 JSON Lines 数据，合并多份来源，设置时间范围，选择版本，并按平台与版本输出分析表。启动漏斗、教程步骤与任务等结果由工具整理成后续可以查阅的形式。

这类工具接手的，是重复导入、筛选、合并和导出工作。它仍需要使用者确认输入覆盖范围与统计定义。

### 文件范围和时间范围分别确认

一份按天导出的文件未必覆盖问题发生的完整区间，多份导出也可能相互重叠。先看实际数据的起止范围，再按约定窗口筛选；不能只凭文件名判断覆盖到了哪一天。

时间字段的含义也需要明确。以 GA4 / Firebase 的 BigQuery 导出为例，官方区分了报告时区下的 `event_date` 与以 UTC 表达的 `event_timestamp`。不能直接把日期字段视为每位玩家的设备本地日期；使用前应确认目标数据源的定义。参见 [Google 官方字段说明](https://support.google.com/analytics/answer/7029846)及[界面与导出数据差异说明](https://developers.google.com/analytics/blog/2023/bigquery-vs-ui)。

### 去重规则和统计对象分别确认

现有工具在合并时会按既定事件字段组合处理重复记录。这可以帮助处理重叠导出，但规则仍需与实际事件定义对应：漏掉重复记录会抬高次数，把不同事件合并则会丢掉有效行为。

同时，事件次数、应用分析标识数、游戏账号数和角色数是不同对象。统计表中的“人数”应说明按哪个字段去重，不能把一个设备或应用实例的分析标识直接当成游戏账号。

一份能继续使用的分析结果，除了数值，还应带上数据源、版本与平台、观察窗口及其时区、过滤条件、去重规则和已知缺口。后续有人追问时，才能回到同样的输入与口径重新检查。

## 技术异常怎样接回处理者

拿到材料以后，需要把“有一批错误”整理成能处理的问题：现象是什么，相关版本与操作是什么，影响范围有哪些依据，以及目前已经排除了什么。

可以按下面的顺序组织交接：

| 步骤 | 留给后续处理者的内容 |
| --- | --- |
| 登记与归类 | 现象、发生条件、关联版本与来源，重复反馈如何合并 |
| 判断影响与归属 | 已确认和仍未知的范围，谁继续复现、定位或协调 |
| 修复与交接 | 修改内容、适用版本、依赖与需要回归的操作 |
| 发布后复验 | 是否取得修复版本，原失败操作是否恢复，仍有什么限制 |
| 回写生产流程 | 是否新增检查、回归样本、定位入口或处理说明 |

这是组织问题处理的方法。一次具体任务能够确认到哪一步，就记录到哪一步；材料只交付到诊断或数据整理时，不能将后续修复与业务改善一并写成已完成。

本篇语言环境问题中，实际交接已经走过“制作人反馈 → Firebase 崩溃排查 → 猜想与修复方向交给客户端主程 → 修改库并发布 → 该语言问题不再出现 → QA 纳入发布回归”。其他问题也可以照着这些交接位置检查缺口，但不能替缺少记录的事件补上结果。

问题状态与复验的组织方式可参考[Bug 管理与 Playtest]({{< relref "code-quality/bug-management-and-playtest.md" >}})；崩溃上下文与归因见[Crash 上报与分析]({{< relref "code-quality/crash-reporting-crashlytics-bugly-and-symbolication.md" >}})。前面的[AOT 漏包案例]({{< relref "engineering-journey/production-build-runtime.md" >}})则展示了另一种从故障回写构建约束与操作流程的做法。

## 运营数据怎样变成待验证的改进

运营回传的数据，可以帮助提出下一轮问题。解释变化时，我会先核对分母、用户群、版本、观察窗口与来源完整性，再讨论可能原因。

例如，某个版本进入战斗的比例降低，可以先检查事件是否迁移、该版本的样本是否完整、用户群是否变化，再考虑加载或玩法流程中的阻碍。这个例子用于说明分析顺序，不对应一项已经确认的真实业务结论。

经过核对以后，把可能原因写成可以继续检验的假设，交给相关团队决定调整内容、修复技术问题还是补采材料。后续复看也应尽量保留可比条件，并说明同时发生的其他变化。

日志工具可用、分析表成功导出、团队采用了一项建议，以及业务指标改善，分别需要各自的依据。本篇案例已经确认技术问题修复与 QA 回归范围的变化，其他工具材料支撑对应环节的能力；转化或买量效果仍需另外的数据支持。

## 让这次处理留下下一轮能用的东西

一项问题处理完以后，可以继续问：同类现象再出现时，能否更早发现、更快定位，或者让接收者少做一次人工整理？

重复缺少上下文，就补充事件契约或报告字段；来源状态看不清，就完善采集报告；重复筛选和导出占用精力，就改进分析工具；已经定位过的故障，则把处理步骤和回归样例写回日常流程。
