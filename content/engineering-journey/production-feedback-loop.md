版本发布以后，工作还会继续。QA 或玩家反馈某个操作异常，程序需要找到对应的运行记录；运营定期交付线上数据，团队希望知道玩家实际经历了什么，以及下一步应该改哪里。

这些信息不能只停在群消息、日志压缩包或一份统计表里。收到反馈以后，还需要确认它对应哪个版本、什么范围、哪种行为，由谁处理，处理后又怎样确认结果。

在[可发布版本]({{< relref "engineering-journey/production-release-readiness.md" >}})一篇中，交接已经走到运营发布与数据回传。这篇继续整理日志回收和分析工具中的具体做法，并说明怎样把观察接回后续行动。现有材料分别支持采集、整理与分析环节；尚未取得同一事件完整修复记录的部分，保留为处理方法，不拼成一段完整事故经历。

## 先问需要判断什么，再选择数据

“看看数据有没有问题”还不够具体。我会先将它改写成可以继续查证的问题：哪个版本、什么操作或环节出现差异，影响哪些用户，需要谁作出什么判断。

不同来源承担的角色也需要先分开：

| 来源 | 可以帮助回答什么 | 还需要核对什么 |
| --- | --- | --- |
| 技术日志与异常记录 | 哪个阶段报错，调用或加载停在哪里？ | 包版本、设备、时间、操作与相关上下文 |
| 客户端行为事件 | 客户端声明发生过什么操作或流程节点？ | 触发位置、身份、漏报补报及版本覆盖 |
| 服务端业务记录 | 服务端受理了什么，业务处理结果是什么？ | 处理对象、结果语义、记录范围与重复情况 |
| 运营或渠道数据 | 特定窗口与用户群的触达、行为或结果怎样变化？ | 指标分母、归因口径、时间与平台差异 |
| 玩家反馈与工单 | 玩家在什么条件下遇到了什么现象？ | 复现步骤、发生时间、版本及可关联的记录 |

例如，客户端上报了购买按钮点击，不能直接当成服务端购买成功；一个行为同时出现在两类记录中，也不能把两条记录相加计为两次业务结果。日志采到错误信息，同样不能单凭日志条数判断受影响人数。

已有客户端 BI 材料还区分了认证身份、断线队列和服务端记录。队列中接受了一条事件，不等于已经送达；服务端记录了客户端声明，也不会自动把它变成服务端权威业务结果。先说清这些含义，后面的统计和诊断才有对应对象。事件设计可继续看[事件契约与版本上下文]({{< relref "code-quality/game-analytics-integration-event-schema-and-privacy.md" >}})。

## 日志回收：先把检查范围固定下来

现有日志回收流程提供了按环境和时间窗口取得材料的入口，并支持定时执行。一次任务中的各来源共用冻结的窗口，避免因为排队或采集耗时，让每个来源实际查询的起止时间不断变化。

结果按照来源整理、归档，再提供通知与下载入口。服务端业务日志、应用日志与独立客户端观测资料分别呈现，接收者可以继续核对某个来源是否完整，以及这次实际取到了什么。

这里有三个状态值得分别保留：

- **采集执行状态**：任务有没有真正完成准备、获取和归档。
- **各来源状态**：完整、部分缺失或失败，不能被一个总状态掩盖。
- **通知状态**：报告是否已经可取得，通知是否被接口接受；它与报告中的事件是否正确是不同判断。

一份历史回收记录就保留了这种差异：部分来源缺失，其他来源仍有有效产物，最终任务按不完整状态呈现。现有核对到的是回收元数据和清单，不能因此推断缺失来源没有玩家活动，也不能把其余产物存在写成所有业务数据都已验收。

所以，“没有查到”需要继续拆开看：可能确实没有发生，也可能来源缺失、筛选范围不对、目标版本没有记录这个事件，或采集本身失败。把这些状态保留下来，比给一张看起来全部完成的总表更有用。

## 数据整理：让同一问题能够按同一口径重查

已有分析工具可以读取导出的 JSON Lines 数据，合并多份来源，设置时间范围，选择版本，并按平台与版本输出分析表。启动漏斗、教程步骤与任务等结果由工具整理成后续可以查阅的形式。

这类工具接手的，是重复导入、筛选、合并和导出工作。它仍需要使用者确认输入覆盖范围与统计定义。

### 文件范围和时间范围分别确认

一份按天导出的文件未必覆盖问题发生的完整区间，多份导出也可能相互重叠。先看实际数据的起止范围，再按约定窗口筛选；不能只凭文件名判断覆盖到了哪一天。

时间字段的含义也需要明确。以 GA4 / Firebase 的 BigQuery 导出为例，官方区分了报告时区下的 `event_date` 与以 UTC 表达的 `event_timestamp`。不能直接把日期字段视为每位玩家的设备本地日期；使用前应确认目标数据源的定义。参见 [Google 官方字段说明](https://support.google.com/analytics/answer/7029846)及[界面与导出数据差异说明](https://developers.google.com/analytics/blog/2023/bigquery-vs-ui)。

### 去重规则和统计对象分别确认

现有工具在合并时会按既定事件字段组合处理重复记录。这可以帮助处理重叠导出，但规则仍需与实际事件定义对应：漏掉重复记录会抬高次数，把不同事件合并则会丢掉有效行为。

同时，事件次数、应用分析标识数、游戏账号数和角色数是不同对象。统计表中的“人数”应说明按哪个字段去重，不能把一个设备或应用实例的分析标识直接当成游戏账号。

一份能继续使用的分析结果，除了数值，还应带上数据源、版本与平台、观察窗口及其时区、过滤条件、去重规则和已知缺口。后续有人追问时，才能回到同样的输入与口径重新检查。

## 技术异常怎样接回处理者

拿到材料以后，需要把“有一批错误”整理成能处理的问题：现象是什么，相关版本与操作是什么，影响范围有哪些依据，以及目前已经排除了什么。

可以按下面的顺序组织交接：

| 步骤 | 留给后续处理者的内容 |
| --- | --- |
| 登记与归类 | 现象、发生条件、关联版本与来源，重复反馈如何合并 |
| 判断影响与归属 | 已确认和仍未知的范围，谁继续复现、定位或协调 |
| 修复与交接 | 修改内容、适用版本、依赖与需要回归的操作 |
| 发布后复验 | 是否取得修复版本，原失败操作是否恢复，仍有什么限制 |
| 回写生产流程 | 是否新增检查、回归样本、定位入口或处理说明 |

这是组织问题处理的方法。一次具体任务能够确认到哪一步，就记录到哪一步；材料只交付到诊断或数据整理时，不能将后续修复与业务改善一并写成已完成。

前面的[AOT 漏包案例]({{< relref "engineering-journey/production-build-runtime.md" >}})提供了一个已确认的故障处理样例：从运行失败追到产物与阶段顺序，修复后更新包解决问题，再整理成文档与可重复流程。它说明的是相同的处理思路，并不代表该次事故使用了本篇所述的全部日志和数据工具。问题状态与复验的组织方式可参考[Bug 管理与 Playtest]({{< relref "code-quality/bug-management-and-playtest.md" >}})；崩溃上下文与归因见[Crash 上报与分析]({{< relref "code-quality/crash-reporting-crashlytics-bugly-and-symbolication.md" >}})。

## 运营数据怎样变成待验证的改进

运营回传的数据，可以帮助提出下一轮问题。解释变化时，我会先核对分母、用户群、版本、观察窗口与来源完整性，再讨论可能原因。

例如，某个版本进入战斗的比例降低，可以先检查事件是否迁移、该版本的样本是否完整、用户群是否变化，再考虑加载或玩法流程中的阻碍。这个例子用于说明分析顺序，不对应一项已经确认的真实业务结论。

经过核对以后，把可能原因写成可以继续检验的假设，交给相关团队决定调整内容、修复技术问题还是补采材料。后续复看也应尽量保留可比条件，并说明同时发生的其他变化。

日志工具可用、分析表成功导出、团队采用了一项建议，以及业务指标改善，分别需要各自的依据。本篇先说明前面已有材料支持的能力和处理路径，不补写买量收益或某项改动的因果结果。

## 让这次处理留下下一轮能用的东西

一项问题处理完以后，可以继续问：同类现象再出现时，能否更早发现、更快定位，或者让接收者少做一次人工整理？

重复缺少上下文，就补充事件契约或报告字段；来源状态看不清，就完善采集报告；重复筛选和导出占用精力，就改进分析工具；已经定位过的故障，则把处理步骤和回归样例写回日常流程。
