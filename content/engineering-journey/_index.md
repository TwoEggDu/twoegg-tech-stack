## 二、现在：工作重心怎样发生变化

这些项目并不是彼此孤立的经历。随着问题范围扩大，工作重心也在发生变化。

| 阶段 | 主要关注 | 结果边界 |
|------|----------|----------|
| 解决具体问题 | 客户端、引擎、运行时和平台问题 | 让一个功能或问题在当前环境中成立 |
| 承担项目交付 | 构建、资源、热更新、出包和发布 | 让版本可以稳定地产出并进入测试或上线流程 |
| 承担技术质量 | CPU、GPU、内存、启动、包体、崩溃和线上问题 | 让团队知道产品质量处在什么状态，并能得到可执行的优化方案 |
| 支撑项目协作 | 美术、策划、客户端、服务端与平台系统 | 让各工种可以专注业务，同时让跨系统问题有人持续推进到结果 |
| 沉淀公共能力 | 规则、工具、流水线、验证契约和知识 | 让下一次交付不必从头开始 |

这里不会用组织人数定义是否承担技术负责人职责。更重要的判断标准是：问题跨过多个工种以后，是否能够调动所需资源、完成取舍，并对最终交付结果负责。

## 五、FDE × RaaS：让经验形成实践飞轮

这里使用 FDE 和 RaaS，不是为了增加两个身份标签，而是为了约束一套工作方式：

- **FDE（Forward Deployed Engineering）**：进入真实现场，理解业务目标、工程约束和交付风险，完成一次可以被验证的结果。
- **RaaS（Result as a Service）**：把已经成立的结果整理成带有成功条件、验证证据、接入边界和维护方式的公共能力。

一轮完整的实践飞轮需要经过下面几个位置：

```text
真实项目与约束
-> 进入现场并定义问题
-> 完成一次结果
-> 在构建、设备或线上链路中验证
-> 分离项目特例与稳定共性
-> 封装为可接入、可验证、可维护的能力
-> 在下一个项目中复用
-> 把新的失败和边界带回公共层
```

后续每补一个案例，都要能回答它处在飞轮的哪一段。只有一次性解法时，就把它如实写成案例；只有在不同项目或场景中再次成立以后，才把它写成可复用能力。

PX、TopHero / DP 与 Zuma 将作为第一条重点验证的跨项目主线：哪些能力在前一个项目中形成，哪些在后一个项目中被复用，又有哪些边界因为新平台而被重新修正。

## 六、下一步：继续做深的三个方向

### 引擎与运行时

继续把 Unity、C# 运行时、HybridCLR、资源系统和平台差异整理成更稳定的分层认识，并用源码、实验和最小实现校验判断。

### 交付与质量治理

继续把构建、发布、性能、崩溃、线上观测和多团队协作接到同一条结果链上，减少依赖个人记忆的隐性流程。

### FDE、RaaS 与 AI 协作

继续验证怎样让人和 AI 共同执行诊断、交付与验证，同时控制上下文、权限、证据和长期维护成本。

这页最终要留下的不是一组能力标签，而是一条可以被项目和结果验证的路径：

`进入真实现场 -> 对交付结果负责 -> 把有效做法沉淀下来 -> 在新的现场继续检验和修正。`
