先设一个教学情境：场景美术集中提交了 48 张 4096×4096 的建筑贴图。假设目标表示为 RGBA32、只有基础层，理论像素载荷是每张 64 MiB、合计 3 GiB。这不是 PNG 等源文件大小、下载包体或实际进程占用。

如果导入没有核对用途与目标格式，CI 又只检查编译成功，QA 路线还没进入这个场景，那么这些检查都不足以确认资源符合交付和运行预算。Editor 能显示，也不能代替目标设备观察。

接下来应分别查：实际构建用了什么纹理表示、进入了哪些包，运行时加载了哪些层级和副本，以及场景峰值是否越过预算。不能从这组理论像素量直接推出商店拒审、固定包体增量或 OOM；商店限制还需按对应交付方式与当前规则核对。

这个情境要暴露的缺口是：导入时没有配置检查，PR 时没有资源规格审查，构建时没有产物增量报告。三处都缺证据，资源就可能带着未确认的风险进入交付。

> 版本与证据范围：Unity 字段与回调边界参考 6000.0 文档。本文提供规则设计和待执行检查，没有本项目事故、资源检查器运行、CI 阻断、设备性能或画面/听感结果。示例配置不作为已批准的生产预算。

`资源质量要解决的核心问题不是"美术会不会犯错"，而是"不符合规范的资源能不能在进入主干之前被自动拦住"。`

这篇要回答的就是这件事：美术资源从导入到构建，自动化检查应该在哪几个时机介入，每个时机该检查什么，以及怎样把检查结果接进 CI 和构建门禁。

## 美术资源出问题的 6 种常见方式

资源问题的种类很多，下面列出六类检查方向，不按发生频率排序。

### 1. 超预算贴图

UI 图标的尺寸超出实际显示需要、目标纹理表示偏离预算，都是检查线索。尺寸大、未压缩，或法线贴图比颜色贴图大，单独一项都不足以判违规，还要对照用途和批准规则。

累计影响要分开查包体、驻留和实际访问；资源总量不等于它们会同时驻留，源文件大小也不能直接代表运行占用。

### 2. 缺 LOD 的高面数模型

模型的三角形数量较高却没有简化版本，可以列入审查，但没有 LOD 不自动构成质量错误。

应结合目标镜头、屏幕贡献、顶点属性、绘制用途与同屏数量判断：减少细节能否降低当前工作，又是否值得增加网格、配置与维护。LOD 是否启用、级数和阈值均需比较，见[几何与 LOD 成本]({{< relref "performance/mobile-geometry-cost-vertices-screen-triangles-lod.md" >}})。

### 3. 错误的压缩格式

格式是否合适，取决于目标设备/API 的支持、纹理语义、质量和实际产物，不能只凭 Android/iOS 名称判定。使用自动或默认配置也不等于未压缩；显式覆盖同样可能配错。

Editor 中可先查配置和预览，目标构建与设备再确认实际格式、回退和开销；不能把预览通过当成目标验收，见[多端资源差异]({{< relref "delivery-engineering/delivery-content-pipeline-06-multiplatform-assets.md" >}})。

### 4. 引用丢失

材质球引用的 Shader 被删除、资产的 GUID 对应关系被破坏，或动画所需的骨骼路径被改名，都可能造成引用或绑定问题。保留 .meta/GUID 的正常移动不应直接判为引用丢失。

这些问题可能表现为 Missing、材质显示异常或动画绑定失败；后果要按具体使用路径判断，不统一写成运行崩溃。

### 5. 命名违规

若项目的路径、命名或分组约定不允许特定字符、大小写或命名关系，违反这些约定就应提示；中文、空格或大写本身不自动构成引擎错误。

要检查的是现有查找、分组和交付工具依赖哪些约定，再区分功能风险与风格差异。

### 6. 重复资源

同一张贴图在三个不同目录各存了一份，名字不一样但内容完全一样。

内容相同只是重复候选；是否重复进入交付、是否同时加载，应核对资源身份、Bundle 归属与运行引用，不能仅凭存在三个文件推定三份运行占用。

这些方向需要不同证据：命名和引用可在编辑期先查，产物归属看构建报告，驻留与性能看运行记录。某一层检查通过不代表其他层也通过。

## 自动化检查的 3 个时机

资源检查不应该只在某一个环节做。更稳的做法是在 3 个时机分别设防。

### 第一个时机：导入时（AssetPostprocessor）

Unity 的 `AssetPostprocessor` 可以在资源导入到编辑器的瞬间执行检查和修正。

适合在这个时机做的：

- 检查压缩格式并应用已确认可自动修正的规则（按平台、按资源类型）
- 检查 maxTextureSize，并按批准规则设置（按用途、目录或命名）
- 检查模型面数并输出警告
- 检查命名规则
- 自动设置 AssetBundle 标签或 Addressable Group

这个时机的价值在于：在导入阶段尽早提示不符合规则的位置；耗时取决于资产和检查实现。

这里建议把单资源规范化放在导入回调，把跨资源审计放在独立检查器；这是职责安排，不是 `AssetPostprocessor` 只能访问单个资源的 API 限制。

### 第二个时机：PR 时（自定义检查器）

美术提交 PR 后，CI 流水线里运行自定义检查脚本。

适合在这个时机做的：

- 全量引用完整性检查（材质引用的 Shader 是否存在，Prefab 引用的贴图是否存在）
- 跨资源重复检测（内容 hash 比对）
- 资源预算汇总报告（本次提交涉及的所有资源是否在预算内）
- 命名规则全量扫描
- 与上一个稳定版本的 diff 报告

这个时机的价值在于：用独立运行的检查补充导入规则；能拦住哪些问题仍取决于检查范围、规则和执行结果。

### 第三个时机：构建时

正式构建流水线中，在打包之前和之后分别做检查。

适合在这个时机做的：

- 构建产物的体积验证（单个 bundle 不超过阈值，总包体不超过预算）
- 构建后的 bundle 内容审计（哪些资源被打进了哪个 bundle，有没有意外的重复）
- Shader variant 数量验证
- 构建报告归档

这个时机的价值在于：它验证的是真正会被交付给玩家的产物，而不只是编辑器里的状态。

## AssetPostprocessor 的检查能力和边界

Unity 的 `AssetPostprocessor` 提供了 `OnPreprocessTexture`、`OnPreprocessModel`、`OnPreprocessAudio` 等回调，可以在资源导入时自动执行逻辑。

它能做的事：

- 读取和修改导入设置（压缩格式、maxTextureSize、Mesh 压缩等级等）
- 根据资源路径判断资源类型并应用不同规则
- 输出日志或弹出对话框提醒美术

使用时需要注意的边界：

- 单资源预处理阶段不宜假定其他资源已导入完成；Unity 还提供 `OnPostprocessAllAssets` 等批次回调，不能据此说整个 API 无法处理跨资源工作
- 全量资产扫描可以统计配置或估算数据量，但不能直接得到某一运行场景的实际总驻留
- Inspector 修改导入设置并 Apply 后可能触发重导入，不能将手动修改视为必然绕过；规则是否重新生效要检查具体回调和实现
- 重导入整个目录时可能产生大量日志，需要控制输出量

因此本文仍把 `AssetPostprocessor` 主要用于导入规范化，把全局审计放进可重复运行的检查器。回调列表与批次时机见 [AssetPostprocessor](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/AssetPostprocessor.html)和 [OnPostprocessAllAssets](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/AssetPostprocessor.OnPostprocessAllAssets.html)；本篇没有执行回调实验。

## 自定义检查器的规则设计

一个能长期维护的资源检查器，需要满足三个条件：可配置、可扩展、区分严重级别。

### 可配置

检查规则不要写死在代码里，而是用配置文件定义。

例如，下面只演示规则配置的形状；数字和 ASTC 块大小均为未验证的教学候选，仅可在确认支持与使用条件后比较，不可直接启用为生产门禁：

```
ui_texture:
  max_size: 512
  format_android: ASTC_6x6
  format_ios: ASTC_6x6
  allow_alpha: true

character_texture:
  max_size: 2048
  format_android: ASTC_4x4
  format_ios: ASTC_4x4
  allow_alpha: true

scene_texture:
  max_size: 1024
  format_android: ASTC_6x6
  format_ios: ASTC_6x6
  allow_alpha: false
```

采用配置后，美术和 TA 可以看到规则；每条还需附适用平台/版本、用途、计量口径、依据和豁免。候选经确认后才成为当前标准，修改规则不需要改检查代码。

### 可扩展

每条规则实现一个统一接口，新增规则只需要加一个类和一条配置。

不要把所有检查逻辑堆在一个大脚本里；按规则拆分，有助于单独维护和解释检查结果。

### 区分 Block 和 Warn

不是所有违规都应该阻断提交。

- **Block**：必须修复才能合入。例如：贴图超过允许的最大尺寸、材质引用了不存在的 Shader、模型面数超过硬性上限。
- **Warn**：建议修复但不阻断。例如：贴图尺寸接近上限、模型面数接近预算线、命名不完全符合规范但不影响功能。

如果未经确认就把全部候选设为 Block，可能制造无效阻断，增加绕过检查的压力。

## 预算验证：每种资源类型的预算标准

资源预算不是一个全局数字，而是按资源类型分别定义的。

以下列出每类预算应依据什么确认，不提供跨项目统一参数。只有明确目标条件并取得对照记录后，才把数字接入门禁；待验证候选可以先作 Warn，不能伪装成已验收标准。

### 贴图预算

| 类型 | 尺寸依据 | 格式依据 | 需要的接受条件 |
|------|---------|---------|------|
| UI 图标 | 实际显示尺寸、缩放与投影 | 支持、Alpha 与边缘误差 | 小字/边缘清晰度；Mip 按实际使用比较 |
| 角色颜色贴图 | 镜头、UV 分配与渲染分辨率 | 颜色、Alpha 语义与目标支持 | 对应镜头的辨识度与压缩误差 |
| 角色法线 | 表面细节与采样尺度 | 法线及高光误差 | 与最终材质共同观察，不固定比颜色图小一级 |
| 场景贴图 | 覆盖范围、复用与近景需求 | 数据语义、质量与目标支持 | 接缝、重复感与目标镜头质量 |
| 特效贴图 | 覆盖范围、出现方式与采样 | Alpha/颜色/参数误差 | 形状、时序与叠层；短生命周期不等于尺寸可任意降 |

格式、Mip 和理论载荷的区别见[存储基础]({{< relref "rendering/unity-rendering-supp-a-mesh-texture-storage.md" >}})。

### 模型预算

| 类型 | 几何预算依据 | LOD 判断 | 额外检查 |
|------|---------|---------|------|
| 主角 | 近景、完整顶点属性、蒙皮及绘制用途 | 比较简化收益、轮廓误差和维护成本 | 面部、挂点与动作需要 |
| NPC | 同屏规模、屏幕贡献及动画负载 | 按使用镜头决定是否启用及级数 | 不因非主角就忽略玩法提示 |
| 场景主体建筑 | 屏幕贡献与不同用途的绘制 | 比较轮廓、遮挡和切换表现 | 碰撞体使用单独口径 |
| 场景装饰物 | 批量规模与实际工作 | 比较简化、剔除或其他表示 | 不预设该类对象收益最大 |
| 武器 / 道具 | 特写、轮廓与挂点关系 | 按使用范围比较 | 检查角色动作和玩法表现 |

不规定“至少几级”。Unity LODGroup 的切换依据相对屏幕高度，配置细节见 [LODGroup](https://docs.unity3d.com/6000.0/Documentation/Manual/class-LODGroup.html)。三角形、顶点与不同绘制用途需分别计量，不能用 DCC 多边形数直接代替所有成本。

### 动画和音频预算

- 动画片段按使用、循环、切换和交付范围确定边界；时长可作为检查字段，但不设所有片段通用的秒数上限，也不因超过该数就拆分。
- 音频采样率按源频率内容、用途与目标播放条件比较；声道需确认空间定位、立体声关系与混音结果，不设所有 SFX 的统一频率或单声道规则。
- 编码和质量先查目标导入器/后端支持，再比较体积、误差和用途；不把 Vorbis 或某个质量百分比作为所有音乐的标准。
- 单文件体积与语言/按需交付可设项目预算；运行驻留、并发、解码和首播另查，不能由文件大小推定。音频字段见 [Audio Clip Import Settings](https://docs.unity3d.com/6000.0/Documentation/Manual/class-AudioClip.html)，加载边界见[内存音频节]({{< relref "performance/cpu-opt-05-memory-budget.md" >}})。

可以量化的规则应记录明确数值及其条件，视觉、听感和玩法要求则记录接受方法。尚无依据时保留待确认项，不为让门禁“有数字”而编一个阈值。

只靠口头约定，后续很难追溯某条预算的适用范围和依据。

## CI 集成：检查结果怎样阻断构建或生成报告

资源检查接进 CI 后，需要解决两个问题：怎样展示结果，怎样阻断流程。

### 结果展示

CI 产出的资源检查报告应该至少包含：

- 本次提交涉及哪些资源文件
- 每个文件的检查结果（Pass / Warn / Block）
- Block 级问题的具体原因和修复建议
- 与上一个稳定版本相比，新增了哪些资源、删除了哪些资源、哪些资源的体积发生了变化
- 全项目资源预算的当前占用情况

报告应该输出为可读的格式（HTML 或 Markdown），而不是埋在几千行构建日志里。

### 阻断策略

和配表校验一样，资源检查也应该分级阻断：

- **硬阻断**：存在 Block 级问题时，PR 不能合入、构建不能通过。例如：贴图超过最大尺寸上限、引用丢失、Shader 编译失败。
- **软告警**：存在 Warn 级问题时，允许合入但在报告中标注。例如：贴图接近上限、面数接近预算线、命名不完全规范。
- **趋势监控**：不阻断也不告警，但持续追踪。例如：总包体趋势、各类型资源占比变化、重复资源数量变化。

CI 的资源检查脚本通常通过 Unity 的 `-batchmode` 模式执行，调用自定义的检查器代码，输出结果文件，再由 CI 平台解析结果决定是否通过。

## 美术自检：提交前能自己验证的 checklist

不要让所有检查都发生在提交之后。美术应该有能力在提交前自己验证。

一个实用的美术自检清单：

1. **贴图尺寸**：确认规则适用于当前用途与目标，在 Inspector 里检查 maxTextureSize 与实际导入尺寸。
2. **压缩格式**：检查目标配置和实际导入格式是否符合已确认规则，自动选择或显式覆盖都需核对支持与质量。
3. **几何口径**：区分 DCC 多边形、导出三角形与导入顶点/属性，按项目预算分别检查。
4. **LOD**：检查是否需要 LOD，以及已选级数、阈值、引用和切换表现；不按统一层数验收。
5. **引用完整性**：检查必需引用和绑定是否存在；可选贴图为空不等于 Missing，需按 Shader 与功能契约判断。
6. **命名规则**：按项目查找、分组和交付约定检查名称；不将字符偏好直接判为引擎错误。
7. **目录位置**：资源放在了正确的目录下，没有放到临时目录或其他模块的目录里。

这个清单最好做成编辑器内的一键检查工具，美术点一下就能跑完所有检查，而不是靠记忆逐项核对。

## 反模式

### 1. 检查规则和美术规范不同步

美术规范文档写的是"UI 贴图不超过 512"，但检查器里配的是 1024。或者反过来，检查器比文档更严格，美术按文档做了还是被打回。

规范和检查器必须同源。最好的做法是检查器的配置文件本身就是规范的一部分，而不是另外维护一份文档。

### 2. 只检查新增，不检查存量

检查系统上线后只对新提交的资源生效，但项目里已经有几千个不符合规范的存量资源。

美术会觉得不公平：老资源没人管，新资源卡得这么严。

更好的做法是上线检查系统的同时，给存量资源做一次全量扫描，输出一份存量违规清单，分批治理。

### 3. Block 太多导致美术绕过

所有规则不分依据和严重程度都设为 Block，正常提交也可能被不适用的规则打回。

这会增加返工与绕过门禁的压力，不能把强阻断数量当作质量改善结果。

Block 应对应已确认的交付、功能或预算约束，不能只限于崩溃和性能问题；尚待确认或仅供优化参考的规则，可先作 Warn 并记录后续检查。

### 4. 检查工具只有程序能用

如果检查器只有命令行入口，却没有提供使用说明或方便的接入，使用者可能难以自行定位问题。

等到 CI 打回来，美术还是不知道具体哪里有问题。

检查工具应该有编辑器内的 GUI 入口，美术点一下就能看到结果，而不是需要打开终端敲命令。

### 5. 没有豁免机制

某些特殊资源确实需要突破预算（比如过场动画的特写角色贴图可能需要 4096）。但检查系统没有豁免机制，这些资源要么被强制打回，要么被加进全局例外导致规则形同虚设。

更好的做法是支持按路径或按标签的豁免配置，每条豁免都有明确的审批记录和过期时间。

## 一条最小可执行路径

如果团队现在还没有系统化的资源质量检查，我会建议先按这个顺序落：

1. 先选有依据的用途与平台规则，对贴图的 maxTextureSize 和格式做导入检查；已确认可自动修正的再接入 `AssetPostprocessor`。
2. 把各类预算、适用条件、依据与豁免写进可见配置；未验证候选保留待确认状态。
3. 先在 CI 里加一个最小资源检查脚本，检查引用完整性和 Block 级贴图超标。
4. 先给美术做一个编辑器内的一键自检工具。
5. 先对存量资源做一次全量扫描，输出违规清单，分批治理。

这五步站住以后，再逐步扩展：加模型面数检查、加重复资源检测、加构建后 bundle 审计、加趋势报告。

不要一开始就试图把所有规则都配齐。先让最关键的几条规则跑起来、让美术用起来、让 CI 能拦住最危险的问题，就已经比"什么都没有"好得多。

## 结论

所以我现在更愿意把资源质量这件事理解成：

`把有依据的规则、适用条件、分级阻断与检查记录接进导入、提交和构建流程，让团队能够重复检查、解释问题并追溯豁免。`

文档定义规则，自动化负责重复执行；两者都不能代替实际产物、运行和质量验收。
