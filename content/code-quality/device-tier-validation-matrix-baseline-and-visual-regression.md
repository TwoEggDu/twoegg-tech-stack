很多团队做完机型分档之后，心里会自然产生一种"这事已经完成"的感觉：

- 有了高 / 中 / 低档
- 有了设备识别
- 甚至还有首次 Benchmark 和玩家手动改档

但真到版本推进时，最容易出问题的恰恰不是"有没有档位"，而是：

`这套档位到底有没有命中正确设备。`

因为只要分档错了，后面很多现象都会一起变形：

- 该进 `Mid` 的机型被判进 `High`
- 低档设备拿到了高档资源
- 某组 `GPU` 只在高档阴影下花屏
- 自动判定本身没错，但截图回归、热机验证和发布门禁根本没跟上

所以这篇真正要讲的，不是"怎么再写一套分档策略"，而是：

`怎样把机型分档本身变成一个可验证、可回归、可阻断发布的质量对象。`

前面几篇平台文解决的是：

- 档位怎么判
- 线上怎么修
- 热机后怎么降
- 内容预算怎么跟着档位一起变

而这篇要把这条线接回质量体系，回答的是：

`怎么证明这一切没有配错。`

## 分档验证到底在验证什么

如果只说"验证机型分档"，这件事太模糊了。

我更建议先把它拆成五个对象：

### 1. 判定正确性

回答的是：

- 这台设备为什么被分到这个档
- 结果是不是符合当前规则表预期

### 2. 性能稳定性

回答的是：

- 被分到这个档后，关键场景的帧时间是否站得住
- 热机后会不会持续掉出预算

### 3. 视觉一致性

回答的是：

- 这个档位是不是关掉了不该关的东西
- 同一内容在高 / 中 / 低档之间是否仍然保持可接受的一致性

### 4. 加载与资源一致性

回答的是：

- 该档位到底拿到了哪些资源
- 首载、切场景、热更快照是否和档位边界一致

### 5. 异常退化与安全兜底

回答的是：

- 错档时能不能被快速发现
- 有问题时是否有明确的降档、回滚和阻断动作

也就是说，分档验证不是在问"机器上跑起来没有"，而是在问：

`这个档位的判定、表现、资源边界和退化动作是不是都成立。`

## 设备矩阵要围绕档位来选，不要只围绕销量来选

机型分档验证最容易犯的第一个错误，是矩阵选得太像"常规兼容性测试"：

- 核心收入机型
- 几台低端机
- 几台热门旗舰

这当然有价值，但对分档验证来说还不够。

因为分档更关心的是：

`规则边界附近的设备，是否被分到了正确一侧。`

所以围绕分档设计设备矩阵时，可以先分清四类职责。它们可以由同一设备在不同测试条件下承担，不是四种互斥机型，也不规定通用数量；选择依据和未覆盖项可先按[教学能力矩阵]({{< relref "performance/from-model-table-to-capability-fingerprint-android-and-pc-tiering.md" >}}#capability-matrix-teaching)练习。

### 1. 每档代表机

先为实际支持的配置与关键能力组合建立长期固定参照，例如：

- `High` 代表机
- `Mid` 代表机
- `Low` 代表机

它们负责回答：

`这档的预算表本身是不是成立。`

代表样本的数量由 CPU/GPU/内存差异、路径、负载和支持边界决定，不能只因“每档已有一两台”就认为充分。销量/使用占比与回归历史也是选择依据；固定参照便于比较，但它不能代表同档所有设备。

### 2. 边界机

这是最值钱的一组。

例如：

- 刚好位于 `High / Mid` 临界线附近的机型
- 某代际高端芯片的降级市场机
- 相近能力下，请求更高内部渲染分辨率或目标帧率的组合；面板刷新率另记

它们负责回答：

`规则有没有把最容易判错的设备压到正确一边。`

### 3. 异常机

这组不一定占比大，但一旦出事很容易让你误判：

- 驱动已知异常机
- 发热特别敏感的机型
- 存储老化或低可用空间样本机
- 某品牌系统定制很重的设备

它们负责回答：

`这套规则在现实世界最容易失真的地方，有没有被覆盖到。`

### 4. 长尾观察机

这类设备不必每轮都重跑，但应该进入季度或版本级观察样本。

它们负责回答：

`线上长尾问题有没有被逐步吸回验证体系。`

所以分档矩阵和普通兼容性矩阵最大的区别，不是机子更多，而是：

`它更强调边界机和错档高风险样本。`

## 每个档位最值得固定哪些验证

分档验证最怕做成"每轮随便看看"。

更稳的做法，是给每个档位固定一组最小验证链。

### 第一层：判定日志验证

这是最便宜也最值得最先固定的一层。

至少要让每次测试都能看到：

- 设备指纹
- 本地识别结果
- 首次 Benchmark 结果
- 当前生效档位
- 档位来源（本地 / 远程 / 手动 / 安全兜底）

同时保存构建/资源/规则版本、兼容路径、默认建议、玩家请求、会话限制原因和实际生效配置。帧率目标、内部渲染与输出尺寸、屏幕刷新率分别记录；配置在运行中变化时划分记录区间。能力、目标和状态的边界沿[能力指纹]({{< relref "performance/from-model-table-to-capability-fingerprint-android-and-pc-tiering.md" >}})核对，不从一个档位名字反推实际工作量。

否则后面看到一切问题时，第一句永远会变成：

- 它到底现在是哪个档

### 第二层：固定性能 baseline

分档验证里，性能不该只看"平均 `FPS` 还行不行"。

先绑定设备/OS/驱动/API、构建模式与版本、资源快照、任务输入和实际配置。目标帧率、缓存与首次使用状态、初始热状态、电源/后台环境，以及采集工具/启用模块都要固定或记录；两轮有差异时，先判断它改变了哪项条件，再决定能否比较。Baseline 是这些条件下的参照，不能只存一个“Mid：33 ms”。

#### 先给 frame time 一个明确对象

复用[一帧拆解]({{< relref "performance/game-performance-frame-breakdown.md" >}})与[帧预算拆账]({{< relref "performance/game-budget-06-frame-budget-breakdown.md" >}})的定义，至少分开下列口径。表中是采集规格要回答的问题，不承诺每个平台都能取得这些数据。

| 对象 | 起止点与记录范围 | 来源与有效性要写清什么 |
| --- | --- | --- |
| 应用更新间隔 | 同一进程相邻两次约定更新起点之差，单位 ms | 对应插桩/工具及版本、单调时钟、运行与更新编号；包含间隔中的等待和调度，不能当作纯 CPU 执行时间 |
| CPU 工作范围 | 明确主线程或渲染线程的起止标记，单位 ms | 墙钟还是执行时间、是否含等待、关联哪次任务/帧；重叠线程范围不能直接相加 |
| GPU 工作范围 | 明确起止时间戳、队列、Pass 覆盖，单位 ms | 计时支持、有效位、返回延迟及渲染帧关联；CPU 调用耗时不能顶替，局部范围不能冒充完整 GPU 帧 |
| 呈现间隔 | 连续新图像的约定呈现事件之差，单位 ms | 系统事件与帧/图像关联；未取得时写“呈现未测”，不能由应用间隔代填 |
| 请求到呈现反馈 | 同一次输入/请求到对应反馈图像的约定呈现事件，单位 ms | 请求与图像身份、时钟关联；系统呈现事件和屏幕可见观测的边界分别说明，应用提交或 GPU 完成不证明屏幕已显示 |
| 首载/切场景到可交互 | 请求/切换事件到约定用途就绪，单位 ms | 请求 ID、缓存条件、所需资源/输入与业务状态；渲染就绪和首次呈现另记，缺终点不填成功耗时 |

Unity 6.0 的[目标平台采集说明](https://docs.unity.com/en-us/engine/6000.0/manual/analysis/profiler/profiling-applications/profiling-target-device)用于确定设备与构建上的采集入口；UE 5.8 的 [Timing Insights](https://dev.epicgames.com/documentation/en-us/unreal-engine/timing-insights-in-unreal-engine?application_version=5.8)提供 CPU/GPU 分轨与选帧调查。具体计数器范围、支持性和开销仍要按选定版本核对，这些工具入口不等于本表所有口径已实现或校准。

每条规则再关联：指标 ID/定义版本、采集来源和配置、单位、阶段/窗口、聚合算法、有效样本数、预期记录与缺失原因，以及阈值依据/规则版本。多时钟关联须有经过核对的转换或帧标识，不能直接相减 CPU/GPU 的原始时间戳。`avg / P95 / P99` 必须挂在某个明确对象上。分位数的算法与样本量一起保存，不把一轮的很多帧说成很多次独立运行；运行间的波动另列。

不支持、未启用和采集失败分别记状态；支持但丢事件记缺失，不能补 0，也不能无条件丢掉后当完整记录比较。涉及超时的任务保留尝试、截止条件和业务结果，未观察到完成不等于刚好在超时点完成。必要观测不足时，该项保持证据不足，其他有效项可分别报告。

#### 首用事件与分布分别验收：一组教学记录

下面只有**合成教学输入，没有设备实测或推荐阈值**。沿用“首次打开界面并播放特效”的任务，设运行 T0 请求时刻为 0，目标为 30 FPS。采集窗口为 `[0,705) ms`，首次专项窗口为 `[0,650) ms`。应用更新起点来自教学生成的单调时间戳：从 0 开始，先有 19 个连续的 32 ms 间隔，再有 1 个 96 ms 间隔，因此共 21 个起点、20 个有效间隔，最后一段是 `608→704 ms`，没有丢失更新事件。

本例题设两条规则：全采集窗口的应用间隔 P95 不超过 `33.33 ms`；与首次窗口相交的完整应用间隔不超过 `66.67 ms`。两条线仅用于练习，真实阈值要回到项目体验与校准记录。P95/P99 采用 nearest-rank，即排序后取向上取整的 `样本数×分位数` 位置。

| 检查 | 可复算的记录与结果 | 能得出什么 |
| --- | --- | --- |
| 全窗口应用间隔 | 总时长 `19×32+96=704 ms`；平均 `35.2 ms`；P95 取第 19 个，为 `32 ms`；P99 取第 20 个，为 `96 ms` | P95 这一条题设规则通过；平均、P99 是各自统计，不能替代其他规则或直接归因 |
| 首次窗口长间隔 | `608→704 ms` 与 `[0,650) ms` 相交；完整间隔为 `96 ms`，超过题设 `66.67 ms` | 首次长间隔规则失败；不能截成窗口内的 `42 ms` 再判断 |
| GPU 与呈现 | 题设 GPU 计时不支持、无有效 GPU 样本；呈现未采集 | 分别写“不支持”“呈现未测”，均不是 0 ms 或通过；不能据应用间隔宣布 GPU/显示正常 |
| 请求到可交互 | 题设没有提供用途就绪终点 | 此项缺证据；应用更新仍在推进，不证明任务已完成或可交互 |

统计窗口与事件窗口有不同用途。本例分布按间隔的后端点落入 `[0,705)` 取样；首次长间隔检查则保留与 `[0,650)` 相交的**完整**间隔，采集需覆盖窗口边界外的相邻事件。只按后端点是否小于 650 检查首次窗口，会漏掉这条 96 ms；缺少外侧事件时，边界覆盖应记不完整。

这里可以明确报告“P95 规则通过、首次长间隔规则失败、GPU/呈现/可交互证据未齐”。它不能支持“这个档位性能通过”，也不能把 20 个间隔当 20 次独立验证。

理解检查：若最后一个更新起点 704 丢失，还能计算这条 96 ms 并判断首次窗口吗？若拿到的只是 GPU 某个 Pass 的 12 ms，可否补进“完整 GPU 帧时间”？分别说明应该保留什么状态、补什么证据。

这层和 [Baseline：性能 / 包体 / 加载 / Crash 预算怎样立线并进 CI]({{< relref "code-quality/baseline-budgets-in-ci.md" >}}) 是直接连着的。

区别只是：

- 那篇在讲"怎么立基线"
- 这篇在讲"分档验证最该怎么用这些基线"

### 第三层：关键路径 smoke

分档不该只在空场景里测。

至少要固定几条最值钱的路径：

- 启动到主界面
- 主城或主关卡入口
- 一段高特效战斗
- 首次资源切换或热更后入口

这层负责回答：

`这档不仅理论上成立，而且关键路径真的还能活。`

### 第四层：截图回归

分档验证如果没有视觉回归，很容易出现另一种假通过：

- 性能是回来了
- 但画面已经配歪了

更稳的截图回归，不是全世界随便截，而是固定：

- 关键场景
- 固定机位
- 固定时间点
- 固定设备
- 固定档位

然后比较：

- 同设备不同档位
- 同档位不同版本

这层和 [视觉质量测试：感知差异（Perceptual Diff）、渲染 Artifact 自动检测、多平台视觉一致性]({{< relref "code-quality/visual-quality-testing-layered-diff-rules-and-ai-review.md" >}}) 直接相连。

这里先把它当成分档验证的一部分，不展开感知差异算法细节。

### 第五层：热机与长时运行验证

持续运行和状态恢复的风险需要单独覆盖，移动端尤其如此；持续窗口由产品典型会话、代表负载和支持边界决定。“跑了 15～20 分钟”只能说明某段记录的长度，不能当作所有产品的充分条件，也不据一次后段下降直接判定热降频。

可以按下面的关系组织记录，实际时长与规则另由项目确定：

```text
记录初始状态 → 首次任务（单独保留尖峰）→ 同条件重复/持续负载
                                         ↓ 若发生配置/状态变化
                                  分段记录限载、较低负载和恢复
```

1. 固定任务循环、镜头/输入与内容规模，记录缓存、充电/电源、初始热状态、后台和采集条件。首次窗口保留，不把真正的首用异常作为“预热”静默删除。
2. 在约定的早期、后期窗口分别报告同口径指标、样本数与覆盖情况，同时保存实际分辨率/帧率目标、内容方案、平台状态及其有效性。无热信号不填正常；配置改变后不混成同配置的平均值。
3. 单列限载切换、后台返回和恢复事件，核对切换尖峰、必要表现和业务状态。若后段变慢，结合工作量、CPU/GPU、等待和平台信号检查竞争解释；热信号与长帧同现不自动证明因果。
4. 测试协议提前写明计划时长、结束/中断条件与如何处理不完整窗口。只有达到相应覆盖条件，才能判该项；运行中止或计时丢失保留为未完成/证据不足，不能按“已跑时长内没报错”放行。

峰值与持续能力、比较条件和恢复边界继续复用[硬件 02b]({{< relref "performance/mobile-hardware-02b-sustained-performance.md" >}})。本节给验证设计，不预设某设备可持续多久；动态策略的降载/恢复阈值与稳定窗口仍需独立校准。

## 把设备、配置、场景和阶段连接成校准矩阵

选好了代表设备，仍要回答：每份记录究竟证明哪个组合，哪些问题还没有证据？Epic 的 [Scalability and the Developer（UE 5.8）](https://dev.epicgames.com/documentation/en-us/unreal-engine/scalability-and-the-developer-for-unreal-engine?application_version=5.8)建议覆盖不同 CPU/GPU/内存条件，在可复现的场景定义性能水平，并持续记录变化。这里进一步把验证问题拆成四个维度，方便客户端、TA 和 QA 安排及复查；具体矩阵是教学设计，不是官方规定的设备数或测试次数。

### 先固定四个维度，再判断哪些格适用

以下**全是拟验证的教学条件，没有设备、策略或性能结果**。沿[能力矩阵]({{< relref "performance/from-model-table-to-capability-fingerprint-android-and-pc-tiering.md" >}}#capability-matrix-teaching)使用 A/B/C 三份候选设备记录；它们的路径 P0 可运行性只是原题设，OS/驱动与整机条件仍要分别绑定。U 的兼容证据未齐，先留在补证分支，不充作低档性能样本，也不计入下面的性能组合。

配置维度使用固定 N、固定 L、动态 D 三份方案。N/L 是待验证的完整配置；D 是在这两份配置间切换的策略版本，不是第三个画质档。具体参数先按[候选画质矩阵]({{< relref "performance/device-tier-experience-consistency.md" >}}#candidate-quality-matrix-teaching)固定，D 的状态职责沿[降载与恢复推演]({{< relref "performance/mobile-hardware-03-power-thermal.md" >}}#dynamic-load-recovery-teaching)；不能把纸面可用标记当作现实已支持。

两个场景仍走“首开界面并播放特效”的同一业务路径。S0 题设为 1 份界面、1 个特效实例、1 个角色预览及固定背景；S1 为 3 层合法叠加界面、3 个特效实例、2 个角色预览及同一背景。它们只是区分代表负载，实例数量不线性换算耗时；真实项目还需确认这些组合能否出现、镜头/输入/资源身份及必要体验。

四个阶段分别检查首次任务、同条件持续运行、品质切换事件、品质恢复试探。首次保留请求到必要反馈/就绪和尖峰；持续阶段说明负载、缓存及结束条件；切换保留请求、实际配置确认、跨界间隔及资源代价；恢复在恢复后的配置上检查目标。这里的“品质恢复”不包括后台返回等其他恢复职责，后者还要另列异常路径。

| 配置方案（S0/S1 分别安排） | 首次任务 | 持续运行 | 品质切换 | 品质恢复试探 |
| --- | --- | --- | --- | --- |
| 固定 N | 需安排 | 需安排 | 本题不适用：配置固定 | 本题不适用：没有品质恢复 |
| 固定 L | 需安排 | 需安排 | 本题不适用：配置固定 | 本题不适用：没有品质恢复 |
| 动态 D | 需安排，记录初始实际配置 | 需安排，按实际配置分段 | 需安排并观察确认与代价 | 需安排并覆盖成功/失败分支 |

“需安排”不是通过。动态 D 若整次运行都没触发切换，只能支持已观察到的维持行为，切换和恢复格仍未覆盖；不能改填不适用。若固定 N/L 的实现实际还被其他自动缩放模块改写，就已偏离本题固定配置前提，应记录实际配置并修正比较设计。

### 可复算的是计划空间，不是设备覆盖率

```text
名义组合：3 份设备记录 × 3 份配置方案 × 2 个场景 × 4 个阶段 = 72 格
固定方案不适用：3 × 2（固定 N/L）× 2 × 2（切换/品质恢复）= 24 格
适用问题格：72 - 24 = 48 格
只安排 A/B：2 × 2 ×（2 + 2 + 4）= 32 格；C 仍缺 16 格
```

48 格都只是需要回答的问题，32 格也只表示教学计划中只安排 A/B 时的范围；没有一格因此获得运行或通过证据。U 的补证另记，不能靠移入“不适用”让计划看起来完整。若确认必需路径不支持且无已验证替代，应记录兼容性失败或收窄支持范围，不能填 0 ms 或性能通过。

一条完整运行可能覆盖多个阶段格，每格也可能需要多次独立运行；格数不是运行次数，帧数更不是独立运行数。风险选样可缩减本轮范围，但 C 的持续条件不能由 A/B 代为接受。支持结论必须与本次记录覆盖的设备、配置、场景和阶段一致。

### 每格保存身份和结果，怎样从比较走到接受

记录先绑定构建/内容、设备/OS/驱动/路径、配置及策略版本、场景输入、阶段/窗口和指标定义，再关联原始事件、有效性与各条规则。动态 D 按实际 N/L 片段及切换事件分别报告；不能把低配置后的平均值当作原配置持续通过。

固定 N、固定 L 与动态 D 的比较要匹配初始状态、任务及观测条件，记录重复与顺序影响。运行后不同的热状态轨迹可能正是策略结果，不应为了“可比”而强行把后期温度调成相同；仍需结合工作量、执行/等待和平台信号保留竞争解释。检查是否减少超预算时，也要检查质量牺牲、就绪/输入变化、驻留、切换尖峰及恢复速度。

结果与执行进度分开记录：未执行就保持未执行；执行过但缺必要事件、信号过期、切换未确认或未触发目标分支，相关项记证据不足/未覆盖；有效记录违背规则或必要体验才判对应项失败。通过只覆盖证据齐备且满足接受条件的项，不适用必须有本题适用表或实际支持范围的明确理由。性能、正确性和必要体验分别判，不能用一个绿色格抵消另一项失败。

```text
候选身份与适用条件 → 适用问题格 → 本轮安排和缺口
                                         ↓ 后续取得有效记录
                         分项结果 + 必要体验 + 副作用与未覆盖项
                                         ↓
                        接受对应范围 / 修改后复验 / 保留缺证据
```

常规路径之外还需安排边界抖动、信号不支持/过期、切换部分生效/回执缺失、恢复失败和前后台返回等异常。它们是按风险增补的验证问题，不是再给 48 格随意乘一个故障数量；先写预期分支与必须保留的证据，再决定在哪些设备/配置复验。平台紧急保护和业务正确性另有优先级，不能为完成驻留窗口而延迟处理。

### 哪些变化需要重新标定或限制旧结论

| 变化 | 先重查什么 | 旧记录怎样使用 |
| --- | --- | --- |
| 内容、材质、UI 叠层、实例规模或加载依赖变化 | 代表负载、首次/组合成本、资源和必要体验 | 指出受影响格后复验；不能只因档名相同沿用旧通过 |
| N/L 参数、目标帧率/分辨率、动态规则或用户选项变化 | 实际配置、切换/试探、接受目标及维护空间 | 新配置/策略单独绑定；调阈值与复核可接受性的记录分开 |
| 设备、OS/驱动/API、Provider 或信号支持变化 | 兼容、计时/信号语义、适用范围与异常分支 | 不把别的整机或旧路径证据直接迁移；先补相关支持证据 |
| 指标定义、窗口、时钟关联或采集工具变化 | 可比性、缺失、采集扰动和基线口径 | 不能直接接续旧曲线作收益；必要时重建可比基线 |

变化不意味着所有旧记录作废；应保留原始条件，说明哪些依赖未变、哪些结论可复用，以及谁接受复用理由。规则记录包含版本、依据、适用范围、原始证据引用、负责人及复查触发；例外另记期限和后续动作。校准后用匹配条件的复核记录检查边界，不以刚用于调参的同一条记录冒充独立通过，更不能仅为让失败变绿而上调阈值。

理解检查：72、48、32 分别统计什么？动态 D 未发生切换应填不适用还是未覆盖？U 能否直接记 Low？若只换了驱动或指标窗口，哪些旧结论可以保留，哪些需补证？

## 错档、漏档和假高配，最常见的症状长什么样

分档问题最麻烦的一点，是现象经常很像别的问题。

我更建议先把几类典型症状固定下来。

| 现象 | 更可能的问题 | 第一优先排查 |
|------|-------------|-------------|
| 某设备只在高档明显掉帧 | 规则表过于激进，或热机后没有及时降档 | 看当前档位来源、热机后帧时间趋势 |
| 某设备自动判高，玩家大量手动改中 | 默认档位偏激进 | 看玩家改档比例和改档后稳定性 |
| 低档性能正常，但画面明显配歪 | 资源分档或 `Shader` 关键字不一致 | 看资源快照与截图回归 |
| 编辑器与高端机都正常，低端机首载才坏 | 资源首载、首次命中或错档叠加 | 看首载路径和关键资源挂载 |
| 同机型不同批次表现差异很大 | 热、老化、电池、系统扰动 | 看冷机 / 热机样本与长时运行结果 |
| 线上某档崩溃率异常高 | 档位规则和特定驱动 / 特性冲突 | 看设备指纹、图形 API、规则版本 |

这张表的价值不在于穷举，而在于先让团队形成一条统一的排查顺序：

`先确认它现在到底在哪个档，再看这个档是不是应该给它，然后再去分性能、视觉和资源边界。`

## 怎样把分档验证接进 nightly 和 release gate

机型分档验证如果只靠人工抽查，很快就会失控。

更稳的方式，是把验证链按节奏拆开。

### 1. PR / 合并前

只放最轻的自动校验，不要把真机重验证全塞进来。

适合做的通常是：

- 分档日志是否带全必要字段
- 配置表和资源快照是否完整
- 明显错误的规则变更是否被静态校验拦住

### 2. Nightly

这是分档验证真正最值钱的位置。

更适合放：

- 代表机的固定 baseline
- 固定关键路径 smoke
- 固定截图回归

因为这些检查：

- 有固定环境
- 不需要每次提交都跑
- 又足够早地发现趋势性退化

### 3. Release Gate

这里更适合放：

- 边界机复核
- 高风险路径复跑
- 热机样本验证
- 当前规则表与线上稳定版本对比

这层的职责不是"再把所有东西测一遍"，而是：

`证明这次候选版本没有把最容易错档、最容易出事故的那几类边界再打坏一次。`

## 一条最小可执行路径

如果团队现在还没有成型的分档验证链，我会建议先从下面这五步开始：

1. 先列关键能力、兼容边界和必要体验，选固定参照与边界样本，记录选择依据及未覆盖项
2. 先让所有测试都能打印设备指纹、档位和档位来源
3. 先按必要体验和高风险任务阶段固定关键路径 smoke，数量由覆盖问题决定
4. 先给每档固定一组截图回归机位
5. 先把代表机 baseline 放进 nightly，把边界机复核放进 release gate

这五步建立执行入口；还要核对各项记录有效、规则与配置匹配，以及对应结果是否满足要求。流程跑通或 nightly 绿色，都不能代替缺失的设备和体验证据。

## 小结

如果把这篇文章压成一句话，我会这样收：

`机型分档真正要验证的，不只是"这台机子现在跑在哪个档"，而是这个档位的判定、性能、视觉、资源边界和异常兜底是否都成立；只有把代表机、边界机、固定 baseline、关键路径 smoke 和截图回归一起接进 nightly 与 release gate，分档才算从经验判断变成工程事实。`

如果你接下来还想把"默认档位到底怎么判"这件事再往前收，最适合继续看的是 [从型号表到能力指纹：Android 与 PC 的分档判断怎么设计]({{< relref "performance/from-model-table-to-capability-fingerprint-android-and-pc-tiering.md" >}})。

因为分档验证解决的是"怎么证明没配错"，而那篇解决的是：

`最初的默认规则，为什么不能只靠一张型号表。`
